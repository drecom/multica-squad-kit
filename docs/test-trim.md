# 手間の割に守りの薄いテストを絞る

3 つの対象のテストは、契約を守る検査だけにする。本文の表のテストは代表の 10 行で流し、重みを 150 秒と比べる検査は置かず、ひな形のテストは自然文を固定しない。

この文書は、対象ごとに何を絞り、何が守りを引き継ぎ、何を残すかを書く。あわせて、CI がテストを分けて流す時間の上限とシャードの理由を書く。読み手は、原本のテストを変える人と、レビューの役である。

## 目的と範囲

テストの時間と、文言を直すたびにテストを直す手間を減らす。守りを黙って弱めず、外した確認は、ほかのテストが守ることを示す。

次の 3 つを対象にする。

1. 本文の読み方の表を、3 つのコマンドで流すテスト
2. `tests/test-runner-test.sh` の、重みの一覧に関する検査
3. `tests/agent-templates-test.sh` の、役の指示や共通スキルの自然文に関する検査

次は対象にしない。

- 見張りのスクリプトの本体と、役の指示・共通スキルの本文。導入済みのプロジェクトの動作に関わるため、テストの整理では触れない
- 画像の見比べの仕組みと `tests/release-screens-test.sh`
- `tests/leader-eval/` の評価

時間の上限を延ばすことと、流し直しで通すことはしない。

## 本文の表のテスト

3 つのコマンドの本文の表のテストは、表の 61 行から選んだ代表の 10 行だけを流す。全 61 行は、共通部品のテストが 3 つの読み方で流す。

### 代表の行に絞る理由

`squad-review-next`、`squad-review-wait`、`squad-pr-watch` は、本文を `common/monitor/squad-cli-lib` の同じ部品で読む。61 行をコマンドごとに全部流すと、同じ読み方を 3 回確認するので、時間がかかる。

行ごとの読み方の違いは、部品の中で決まる。コマンドが確認するのは、部品の結果を受けて止まる・進む・書くの動作である。動作は結果の種類（制御記録、制御記録でない、読めない）ごとに 1 つなので、行を増やしても新しい動作を確認しない。

### ファイルの数

本文の表のテストは、3 本である。

| コマンド | テスト | 流す行 |
| --- | --- | --- |
| `squad-review-next decide` | `tests/squad-review-next-decide-body-test.sh` | 代表の行。読める行と読めない行の両方を 1 本で流す |
| `squad-review-wait` | `tests/squad-review-wait-body-test.sh` | 代表の行 |
| `squad-pr-watch ci-wait` | `tests/squad-pr-watch-ci-wait-body-test.sh` | 代表の行 |

`decide` のテストは、読める行と読めない行で分けない。代表の 10 行なら 1 本で目安の秒数に収まるので、分ける理由がない。

### 代表の行

`tests/review-body-table.tsv` の 4 列目「代表」に `代表` と書いた次の 10 行が、代表の行である。ほかの行は 4 列目を空にする。表の行は 61 である。

| 期待 | 説明の列 | 選んだ理由 |
| --- | --- | --- |
| `control` | 単独の CR で行を分ける | 単独の CR を含む行。制御記録として読む |
| `notcontrol` | 逆引用符の囲みの中 | 囲みの中なので制御記録でない、いちばん単純な行 |
| `unreadable:閉じない囲み` | 閉じない囲み | この理由の唯一の行 |
| `unreadable:囲みにならない囲みの記号` | 囲みにならない囲みの記号 | この理由の唯一の行 |
| `unreadable:/note の後ろの囲みの記号` | /note の後ろの囲みの記号 | この理由の唯一の行 |
| `unreadable:行頭の空白` | 1 行目の行頭に 空白 | 制御記録の行そのものに掛かる、いちばん単純な行 |
| `unreadable:引用` | 引用（制御記録の前） | 引用のいちばん単純な行 |
| `unreadable:項目の中身` | 項目の記号 - の中身が囲み | 項目の中身の代表の形 |
| `unreadable:HTML` | 1 行目が <!-- | HTML のいちばん単純な行 |
| `unreadable:制御文字` | B に U+0000 | NUL を含む行。bash の変数に置けず、JSON のまま渡す道を通す |

`tests/review-body-table.sh` の `body_table` は、4 つ目の引数に `representative` を受ける。`representative` を渡すと、4 列目が `代表` の行だけを流す。4 つ目を渡さなければ、全行を流す。

3 つのコマンドのテストは、どれも `representative` で流し、流した行が 10 であることを確認する。

### 代表の行が欠けないことの確認

`tests/squad-cli-lib-body-table-test.sh` が、代表の行の組を確認する。代表の 10 行が、`control` 1、`notcontrol` 1、読めない理由 8 種それぞれ 1 であることを確認する。NUL を含む行と単独の CR を含む行が、代表に入っていることも確認する。

表に行を足して代表を変えたときも、この確認が組の欠けを見つける。3 つのコマンドのテストは、組を自分では確認せず、行の数だけを見る。

### 外した行を守るもの

代表から外した行の読み方は、共通部品のテストが守る。`tests/squad-cli-lib-body-table-test.sh` は、全 61 行を `analyze`、`state`、`merge_requested` の 3 つの読み方で流し、どれも表の期待と同じ結果になることを確認する。

外した行は、部品が返す結果の種類が代表の行と同じである。コマンドの動作は結果の種類で決まるので、代表の行でコマンドの動作を確認すれば足りる。

### コマンドのテストが通す呼び方

3 つのコマンドのテストは、部品をコマンドの実際の引数で呼ぶ。共通部品のテストの呼び方と違うものは、全行で守るよう、共通部品のテストに置く。

| 呼び方 | コマンドのテストでの形 | 守る所 |
| --- | --- | --- |
| `merge_requested` で、作者が決める役（リーダーでない） | `ci-wait` が、決める役の書いたマージの依頼を読む | 共通部品のテストが、作者を決める役にした `merge_requested` の読み方を全行で流す |
| `state` で、最上位の役の一覧が `null` | `squad-review-wait status` が `null` で呼ぶ | 共通部品のテストが、`null` で呼ぶ `state` の読み方を全行で流す |
| `analyze` で、回の ID と時刻の違う候補を 2 回読む | `decide` が回をたどる | 代表の行で `decide` のテストが流す。読み方は共通部品のテストの `analyze` が全行で守る |
| `proceed` の 2 回の読み取りと、準備・取得の記録 | `squad-review-wait proceed` が流す | 代表の行で `squad-review-wait` のテストが流す |

この表にない呼び方を足すときは、同じ形で表に足し、守る所を決める。

## 重みの 150 秒の検査

`tests/test-runner-test.sh` は、重みを 150 秒と比べない。150 秒は、ファイルを分けるかを決める目安として文書に残し、機械では確認しない。1 本の上限は、`tests/run.sh` の 450 秒である。

### 消す理由

150 秒の検査は、テストを止めない。テストを止めるのは、`tests/run.sh` の 1 ファイル 450 秒の上限と、CI のジョブの時間の上限である。重みは実測を写すだけなので、150 秒を超えると、テストの速さと関係なく PR が落ちる。

### 検討した案

| 案 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- |
| 検査を置かず、150 秒を目安として書く | 重みの写しで PR が落ちない。止める仕組みは 450 秒とジョブの上限に 1 つずつになる | 150 秒を超えたことに、機械では気づけない | 選んだ |
| 検査の値を 450 秒に上げる | 機械の確認が残る | `tests/run.sh` の上限と同じ値を、2 か所で確認する | 選ばない |
| 検査を警告にして落とさない | 超えたことが出力に出る | 落ちない出力は読まれず、テストの数だけが増える | 選ばない |

150 秒を超えたことは、重みを写す push で、人とレビューの役が読む。`tests/test-weights` は実測を写すので、差分に超えた値が出る。

### 残す検査

重みの一覧の名前が `tests/*-test.sh` と一致する検査は、重みのないファイルを足すと失敗する。重みを 150 秒と比べる関数は持たない。

## ひな形のテストの自然文

`tests/agent-templates-test.sh` は、ひな形の契約の 6 種類だけを確認する。役の指示・共通スキル・参照の文や句は、固定の文字列で探さない。確認するものと確認しないものは、`CONTRIBUTING.md` の「テストを書く決まり」にも書く。

### 自然文の検査を絞る理由

固定の文字列を探す検査の大半は、日本語の文や句を探す。文言を直すたびにテストも直すことになり、意味を変えない言い換えで落ちる。

自然文の検査は、文があることしか確認しない。役がその文に従うかは、`tests/leader-eval/` の評価の範囲である。

### 残す 6 種類

次の 6 種類は、役の指示を読む機械や構成の契約なので残す。

| 種類 | 残す検査 |
| --- | --- |
| a. 構成 | 10 の構成それぞれで、有効な役だけが残り、外した役の名前が出ない |
| b. 役の欄 | 名前、モデル、思考の深さ、同時実行数、スキル。構成とランタイムごとの期待 |
| c. 差し込みとマーク | 値を文字列のまま差し込む。マークが残らない。条件のマークの展開。未知の役・値の不足・マークの不整合で失敗する |
| d. 大きさ | リーダーの指示が 12,288 バイト以内。展開後と、全分岐の上限 |
| e. 機械やほかのファイルが読む文字列 | スクリプトの名前と引数の形、見張りが読む記録の行、環境変数、メンションのリンク、ラベル、metadata の鍵、ほかのファイルから参照される見出しと参照先の実在 |
| f. 構成による出し分け | 出し分ける内容が、出るべき構成に出て、出てはいけない構成に出ない |

e に当たるのは、読む側を名前で示せる文字列だけにする。読む側は、`common/monitor/` や `lib/` のスクリプト、または見出しや節の名前で参照するファイルである。e の検査のまとまりには、読む側の名前をコメントで添える。

無いことの確認（`absent` や `if grep … ; then exit 1; fi`）は、文言を変えても落ちない。f の検査で無いことを確認する文は、出し分けの表の検査で行う。

### 出し分けの表

f の検査は、ひな形の条件のマークの形を、テストの中の出し分けの表と照らして行う。役の指示の文や語を目印にしないので、言い換えで落ちない。

f の契約は、出し分ける塊がどの条件で出るかである。その条件は、塊を包む `<!-- IF … -->` と `<!-- ELSE -->` の並びで決まる。テストは、この並びを表に固定し、塊の中の文言は見ない。

#### 塊と表の行

塊は、IF から ELSE か ENDIF まで、または ELSE から ENDIF までの枝である。入れ子の IF の中を除いた行（直下の行）を、1 行以上持つものに限る。

入れ子の IF だけを包む枝は、塊に数えない。その枝の条件は、中の塊の条件の外側のまとまりとして表に出る。

表は、テストの中に 1 か所だけ置く。1 行が 1 つの塊で、列は次の 2 つである。

| 列 | 中身 |
| --- | --- |
| 展開したファイル | 役の名前、`squad`、`autopilots` のどれか |
| 条件 | 塊を包む IF を外側から順に読んだ、まとまりの並び |

同じファイルに同じ条件の塊が 2 つ以上あれば、その数だけ行を置く。ひな形のすべての塊に行を置く。

まとまりは、役の名前またはランタイムのマーク（`runtime-claude`、`runtime-codex`）の並びである。並びのどれかが有効なら成り立ち、先頭の `!` で反対の条件にする。

条件は、ひな形の `<!-- IF … -->` と同じ読み方にする。`ELSE` の側の塊は、その IF のまとまりの先頭に `!` を付けて書く。

入れ子の塊は、外側の IF から内側へ順に、まとまりを `&` でつないで書く。`&` は前後を空白で区切る。たとえば、`designer` の `ELSE` の中の最上位の役の塊は、`!designer & claude-principal codex-principal` と書く。

#### テストが確認すること

テストは、形の照合と展開の照合の 2 つを行う。どちらもテストの中で行い、`lib/render.sh` は展開に使うだけにする。

形の照合では、テストがひな形のマークを読み、塊ごとに条件を作る。表とひな形の塊の一覧が、ファイルと条件の組と、その数まで一致することを確認する。

形の照合で一致しないときは、表にない塊と、ひな形にない行を、ファイルと条件で出して失敗する。ELSE を消す、外側の IF だけで出す、条件の役を変えると、表の行に合う塊がなくなるので落ちる。

新しい出し分けを足すと、表にない塊として落ちる。足した人が、表に行を足して通す。

展開の照合では、構成ごとにひな形の写しを作り、塊の直下の行を、塊の番号を持つ置き換えの行に替える。写しを `template_filter` で展開し、条件が成り立つ塊の行だけが出ることを確認する。

展開の照合は、テストの条件の読み方が、展開の読み方と同じことを確認する。10 の構成と補助の構成のそれぞれで行い、展開したファイルがその構成にないときは飛ばす。

#### 補助の構成

補助の構成は、10 の構成だけでは成り立たないか外れない入れ子の枝を通すために置く。展開の照合で展開するのは、その枝を持つファイルだけにする。

補助の構成は `no-designer-no-security` の 1 つである。設計の役と `security-reviewer` を外し、`squad` だけを展開する。`common/squad.md` の `!designer & claude-principal codex-principal & !security-reviewer` の枝は、この構成でだけ成り立つ。

`&` を含む行ごとに、条件が成り立つ構成と成り立たない構成を、それぞれ 1 つ以上置く。テストは、`&` の行ごとにこの 2 つを数え、どちらかが 0 なら失敗する。足りないときは、補助の構成を足す。

`&` を含む行はすべて、10 の構成と補助の構成で両方を数えられる。

#### 出し分けの検査で検討した案

出し分けの検査の形として、次の案を比べた。文言を見ない形の照合を選ぶ。

| 案 | 守る範囲 | 守れない範囲 |
| --- | --- | --- |
| 文や句を目印にする | 目印の文がある塊の出し分け | 文の言い換えで落ちる。目印のない塊 |
| 名詞の句に、短い非文の句の例外を足す | 目印を選べた塊の、ELSE の削除と外側だけの展開 | 句の言い換えで落ちる。句と文の境を決められず、文の目印へ戻る |
| 照合の範囲（節や見出し）を表に足す | 塊の外に同じ語がある場合の取り違え | 同じ節で同じ語から始まる IF と ELSE を分けられない。語の言い換えで落ちる |
| 塊の条件を表に置き、ひな形の形と照らす（選ぶ） | ELSE の削除、外側だけの展開、条件の変更、表にない塊の追加。言い換えでは落ちない | 枝の中の文を、別の枝へ動かすことや入れ替えること |
| ひな形の塊に名前のマークを足す | 選ぶ案の範囲と、枝の中の文の取り違え | `common/` を変えるので、テストだけで閉じない |
| 全構成の展開の結果を保存して比べる | すべての変化 | どの言い換えでも落ちる |

選ぶ理由は、f の契約そのものを確認するからである。契約は塊がどの条件で出るかで、それは文言ではなくマークの並びで決まる。

文や語の目印は、契約の代わりに、塊の中に文があることを見る。そのため、言い換えで落ち、目印を選べない塊が残る。`common/squad.md` の設計の役の 2 つの枝は、同じ文から始まり、ほかと違う名詞を持たない。

選ぶ案が守れないのは、どの文をどの枝に置くかである。これは文の意味の判断で、a〜f の外である。人とレビューの役が差分で確認する。

### 構成と役

テストが展開する構成は 10、役は 17 である。出し分けの表の補助の構成は、10 の構成の一覧に数えない。a〜e の検査は、補助の構成では行わない。

## CI の時間の上限とシャードの理由

PR の Checks のジョブは、15 分の上限に届かずに終える。そのために、テストを複数のジョブに分けて流し、実行とジョブに時間の上限を置く。値は `.github/workflows/check.yml`、`tests/run.sh`、`tests/test-weights` が持つ。この節は、その値の理由を書く。

### 実行の取り消し

`concurrency` の `group` は、PR なら PR の番号、push ならコミットの SHA にする。`cancel-in-progress` は PR のときだけ真にする。

同じ PR に新しい push があったら、古い実行を取り消す。古い実行が最後まで流れると、ランナーを取り合い、ほかの PR の待ちも延びる。main への push の実行は取り消さない。マージ後の状態を確認する唯一の実行だからである。

push の `group` は、実行ごとに違う値にする。同じ値にすると、`cancel-in-progress` が偽でも、待っている実行は新しい実行に取り消される。main へ続けて push すると、途中の実行が流れなくなる。

### 時間の上限

ジョブの上限は、各ジョブの `timeout-minutes` に置く。上限がないと、止まったテストを GitHub の既定の 6 時間まで待つ。上限があれば、止まったテストと大きく遅くなったテストが、失敗として見える。短いジョブにも上限を付け、上限の考え方を 1 つにそろえる。

テストの上限は 2 つにする。1 ファイルは、経過時間で 450 秒を上限にする。150 秒の 3 倍の余裕を取り、並列実行やほかのエージェントの負荷による遅れを時間切れにしないためである。ジョブは、`timeout-minutes` を上限にする。

### テストを分けて流す理由

1 つのジョブでは、15 分に収まらない。`tests/run.sh` はファイル単位で並列に流すので、`Tests` の手順の長さは、秒数の合計を並列数で割った値と、最も遅いファイルの大きいほうより短くならない。テストを速くするだけでは、1 つのジョブで 15 分に収まらない。1 つのジョブの並列数を上げても、3 コアのランナーでは速くならない。

15 分から、ジョブの準備と後片付け、重みと実測のずれの余裕を引き、`Tests` の手順は 600 秒以下を目安にする。そのために、テストを複数のジョブへ分け、呼び出しを減らし、長いファイルを分ける。600 秒の理由は、[ci-timeouts.md の「シャードの数と重み」](ci-timeouts.md#シャードの数と重み)にある。

macOS の同じテストでも、実行ごとの速さは 1 割ほど変わる。macOS を PR でも流すのは、bash 3.2 で起きる不具合をマージの前に止めるためである。時間に収めるために、macOS を流さないことも、確認する内容を減らすこともしない。

### シャードの数

シャードの数は、OS ごとに、CI の実測の合計をシャードの数と並列数で割った値が 600 秒以下になる最小の数にする。並列数は、macOS が 3、ubuntu が 4 である。

重みの合計ではなく実測の合計で決めるのは、重みの合計が実測より小さいと、数が足りずに 15 分に近づくためである。macOS の 5 つの上限は置かない。6 つ目からは、同じ実行の中で空きを待つが、待つ時間は `timeout-minutes` に数えない。今の数と、決めた値の根拠は、[ci-timeouts.md の「シャードの数と重み」](ci-timeouts.md#シャードの数と重み)にある。

### 重みの配り方

分け方は、各ファイルの重みから決める。重みは macOS の CI での秒数で、`tests/test-weights` に 1 行 1 ファイルで書く。

1. 重みの大きい順（同じ重みは名前の順）に並べる
2. 先頭から順に、それまでの重みの合計がいちばん小さいシャードへ入れる。合計が同じなら番号の小さいシャードへ入れる
3. 一覧にないファイルは、重みを 30 秒として扱う

同じファイルの一覧と重みからは、どの実行でも同じ分け方になり、手元でも同じ分け方を再現できる。名前の順に配ると、長いファイルが同じシャードに集まり、そのジョブだけが長くなる。前の実行の秒数をキャッシュから読んで分けると、キャッシュがないときに分け方が変わり、手元で再現できない。

重みの一覧は、直し続ける必要がある。重みのないファイルを足すとテストが失敗し、追記に気づける。重みの一覧が古くなると、シャードの長さがそろわず、1 つのジョブだけが長くなる。ジョブの上限で失敗として見えるので、重みを直して気づける。

### 重みを写すとき

重みは、macOS の CI の実測を写す。macOS のランナーは、同じイメージでも論理 CPU の数が 3 と 5 に分かれる。ほとんどの実行は 3 コアに当たるので、3 コアのジョブの実測だけを写す。

5 コアに当たったシャードは速く終わるだけで、時間切れの側には効かない。5 コアのジョブの値を混ぜると、3 コアのジョブでは重みより長くかかる。

重みは分け方を変え、分け方は実測を変える。そのため、テストとワークフローの最後の変更を push し、その CI の実測を写し、重みだけを直す push を最後に置く。重みだけの push の実測で、重みを写し直すことはしない。写し直すたびに分け方が変わり、終わらないためである。

ジョブを流し直したときは、全ジョブを流し直し、全ジョブの最後の試行を使う。ジョブごとに速い試行を選んで混ぜない。

## 残る危うさ

- 代表から外した行で、コマンドだけが違う読み方をするようになっても、コマンドのテストでは気づけない。部品を通さずに本文を読む変更は、レビューで止める
- 枝の中の文を別の枝へ動かしても、出し分けの表の検査は落ちない。どの文をどの構成に出すかは、人とレビューの役が差分で確認する
- 150 秒を超えるファイルが増えても、テストは落ちない。重みを写す差分を、人とレビューの役が読む
- 無料のプランでは、アカウント全体で macOS のジョブを同時に 5 つまでしか流せない。macOS のシャードが 5 つを超えると、1 つの PR でも空きを待ち、PR が重なると待ちはさらに延びる
- ランナーが大きく遅くなると、重いシャードはジョブの上限に近づく。時間切れとして見えるので、流し直す
