# GitHub 連携のないリポジトリで、PR の紐付けを待たずに進める

GitHub 連携のないリポジトリでは、サーバーが PR を見つけられず、PR ごとに待ちと警告と人間への依頼が起きる。この設計では、作った直後の紐付けが 404 で待ち切れたリポジトリを、ホストに「連携なし」と記録する。記録のあるリポジトリの PR では、待ちと警告と依頼を出さず、マージのあとに人間がタスクを `done` にする。

あわせて、PR を作る役は PR のタイトルにタスクの識別子を入れる。自動の関連付けと明示の紐付けのどちらで紐付いても、紐付いたと扱う。

## 目的と範囲

今は、連携のないリポジトリでも、PR を作るたびに次が起きる。PR を作った役が 120 秒待って警告を残し、リーダーが連携の確認と紐付けを人間に頼む。試み直しの記録もタスクに増える。README・手順書・セットアップの案内は、連携を導入の前提にしている。

目的は次の 5 つである。

1. 連携のないリポジトリを、紐付けの結果から見分けて記録する。連携の状態は API で読まない
2. 記録のあるリポジトリの PR では、120 秒の待ち、紐付けの警告と依頼、紐付かなかった試み直しの記録を出さない
3. 記録のあるリポジトリの PR は、人間がマージを確認してタスクを `done` にする。エージェントと見張りは `done` にしない
4. リポジトリの PR が 1 つでも紐付けば、記録を消し、次の PR から今の動作に戻す
5. PR のタイトルにタスクの識別子を入れる。自動の関連付けでも明示の紐付けでも、紐付いたと扱う

次は対象にしない。

- 連携なしのタスクを自動で `done` にすること。連携なしの PR を、タスクの画面の PR の欄に出すこと
- 連携の状態を API で読むこと。セットアップの質問で連携の有無を尋ねること
- 明示の紐付けを、自動の関連付けに置き換えること。連携なしは、明示の紐付けの結果で見分けるため
- ブランチ名に識別子を入れること。ブランチ名は Multica の checkout が決めるため
- 連携のあるリポジトリで、120 秒のうちに紐付かない原因の調査
- 120 秒の待ちの長さと、[試み直し](pr-link-retry.md)の時機と間隔
- CI とコンフリクトの確認。マージ待ちの見張り（`unlinked`・`unlinked-check`）の動作

## 前提と確認したこと

連携のないリポジトリで、サーバーが紐付けの API に 404 を返し続けることは、今の警告の文と手順書の前提である。連携があっても、同期が 120 秒より遅れると同じく 404 で待ち切れる。この設計は、その場合も連携なしと記録し、次に紐付いたときに戻す（[残る危うさ](#残る危うさ)）。

タスクの読み取り（`multica issue get`）は `project_id` を返す。実機の応答で確認した。今の CLI の契約（`squad-cli-lib` の `issue-get`）にはこの欄がないので、任意の欄として足す。

連携のないリポジトリで、タイトルの識別子による自動の関連付けが効くかは、実機で確認していない。公開のソースの読みでは効かない。この設計はどちらでも動くように作り、効くことを前提にしない。

## PR のタイトルの識別子

PR を作る役は、PR のタイトルの末尾にタスクの識別子を入れ、タイトルを直すたびに残す。公開と非公開のリポジトリで同じにし、ブランチ名は変えない。

### タイトルの形

識別子は、タイトルの末尾に半角の丸括弧で置く。先頭の種類（`feat:` など）は、今の決まりのとおり先頭に残す。

```text
feat: 連携なしのリポジトリで紐付けを待たずに進める (DEMO-12)
```

- 識別子は、タスクの読み取りの `identifier` を使う。実行に渡されるタスクの ID（UUID）は入れない
- `gh pr create --title` で作るときから入れる。push のたびに `gh pr edit --title` で直すときも、末尾の識別子を残す
- 決まりの置き場所は、共通スキル `squad-handoff` の `pr.md` の「PR を作る・実装を積む」である。PR を作る役と積む役は、すでにこの節を読んでタイトルを書いている

識別子を入れても、明示の紐付け（`squad-pr-link`）は今のとおり呼ぶ。連携なしは、明示の紐付けの結果で見分けるためである。

### 識別子を持ち出さない決まりとの関係

今の決まりは、タスクの識別子を PR の本文と公開の設計とコミットに持ち出さない。PR のタイトルだけを例外にし、本文・設計・コミットの決まりは変えない。例外の理由は、連携のあるリポジトリで、サーバーがタイトルから PR をタスクに関連付けられるようにするためである。

例外は、識別子の決まりがある 3 か所に同じ文で書く。`CONTRIBUTING.md` の失敗の記録の段落、`AGENTS.md` のコミットの段落、`pr.md` の識別子の項目である。文書の書き方の作業別のルール（`.agents/rules/docs.md`）は識別子に触れていないので、`CONTRIBUTING.md` への案内を 1 文足す。

### 紐付いたと扱う所

紐付いたかは、どの所でもタスクの PR の一覧（`multica issue pull-requests`）の `html_url` で読む。一覧には、自動の関連付けの PR も明示の紐付けの PR も出るので、両方を紐付いたと扱える。紐付いたと読んだ所は、記録があれば消す。

| 所 | 読み方 |
| --- | --- |
| `squad-pr-link` | 紐付けの API が 200 なら、今のとおり紐付いたと読む。失敗したときは、警告と記録の前に一覧を 1 回読み直す |
| `squad-pr-watch link-check` | 今も一覧で読むので、判定は変えない。自動の関連付けの PR も「紐付いている」になる |
| `squad-dependabot-merge` | 紐付けの API の 200 で読む。記録は消すが、書かない |

### 連携の有無と自動の関連付け

自動の関連付けが効くかで、動作は次のとおり分かれる。どちらでも、この設計は変えない。

| リポジトリ | 自動の関連付けが効く | 効かない |
| --- | --- | --- |
| 連携あり | PR の欄に出る。`squad-pr-link` は今のとおり紐付ける | 今の動作と同じ |
| 連携なし | 一覧に PR が出るので、記録を書かず、あれば消す | 404 で記録を書き、連携なしの動作になる |

実機の結果は、人間が受け入れの確認で、1 つ目の PR が PR の欄に出るかを見て、タスクに残す。

## 連携なしの記録

記録は、ホストのエージェントのホームの下に、プロジェクトとリポジトリごとに 1 つのファイルで置く。ファイルがあることだけを「連携なし」と読み、中身は人間が読むためだけに書く。タスクの metadata には、連携なしの印を置かない。

### 置き場所と形

置き場所は次のパスにする。使用率の確認の状態（`squad-usage-check`）と同じ根の下に置き、セットアップの流し直しで消えないようにする。

```text
${PR_LINK_STATE_ROOT:-$HOME/.multica-agent/template/pr-link}/<プロジェクトの ID>/<オーナー>/<リポジトリ>
```

- プロジェクトの ID は、タスクの読み取りの `project_id` を使う。ないときは記録を書かず読まず、今の動作のままにする
- オーナーとリポジトリは、PR の URL から取り、小文字にする
- 各部分は、空・`.`・`..`・英数字と `_.-` 以外の文字を含むものを断る。断ったときは記録を書かず、ないものとして読む
- ディレクトリは 700、ファイルは 600 で作る。中身を同じディレクトリの一時ファイルに書いてから、`ln` で記録のパスに結ぶ
- `ln` は記録のパスがあると失敗するので、同時に作る実行のうち 1 つだけが記録を作る。一時ファイルは、結べたかによらず最後に消す

中身は次の 4 行にする。判定には使わない。

```text
repository: <オーナー>/<リポジトリ>
pr: <記録のきっかけになった PR の URL>
task: <タスクの識別子>
記録した時刻: <UTC の YYYY-MM-DDTHH:MM:SSZ>
```

記録のパスか、その上のプロジェクトとオーナーのディレクトリがシンボリックリンクなら、記録はないものとして読む。書きも消しもしない。普通のファイルでないもの（ディレクトリなど）も同じにし、どちらも標準エラーに 1 行だけ理由を出す。

### 書く時機と消す時機

記録を書くのは `squad-pr-link` だけで、作った直後の紐付けが 120 秒のあいだ 404 だけで終わったときに限る。次のときは書かない。

- 期限の直前の応答が、通信の失敗か 404 以外だった
- トークン・サーバーの URL・`curl` がない
- 作業先（metadata の `repository`）が PR のリポジトリと違うか、ない
- 待ち切れたあとの一覧の読み直しで、PR が一覧にあった

記録を消すのは、そのプロジェクトとリポジトリの PR が紐付いたと分かったときである。分かる所は、[紐付いたと扱う所](#紐付いたと扱う所)の 3 つにする。

どの所も、紐付いたと分かった時点で記録のパスを読み、あれば消す。実行の始めに読んだ記録の有無は使わない。待ちのあいだに、ほかの実行が記録を結ぶことがあるためである。

記録の消去と作成が重なったときは、後に起きたほうが残る。消去が後なら次の PR は 120 秒待ち、作成が後なら次の PR は待たない。どちらも、次の PR の紐付けの結果で正しい状態に戻る。

### 人間が消すとき

人間が連携をつないだあとは、記録を消さなくても、次の PR が 1 回の試みで紐付いて記録が消える。すぐに戻したいときは、手順書の手順で、ホストの記録のファイルを消す。消すと、次の PR から今の 120 秒の待ちに戻る。

## squad-pr-link の動作

`squad-pr-link` は、タスクを読んだあと、作業先が PR のリポジトリと同じで、プロジェクトの ID があるときに記録を読む。記録の有無で、次の 2 つに分かれる。どちらでもないとき（作業先が違う、プロジェクトがない）は、今の動作のままにする。

`pr_url` がすでにあるときは、今と同じく API を呼ばずに `紐付けていません:` の行を出す。記録の有無で変えない。

### 記録がないとき

今と同じく 120 秒まで待つ。200 なら今のとおり `pr_url` を書き、`紐付けました:` を出す。期限まで 404 だけが続いたとき（`PR_LINK_ALL_404=1`）は、先に[一覧の読み直し](#一覧の読み直し)をする。PR が一覧になければ、次の順で連携なしに切り替える。

1. metadata の `pr_link_pending` に PR の URL を書く。書けなくても続けるのは、今と同じである
2. metadata の `pr_url` に PR の URL を書く。書けなければ、記録を作らずに今と同じ警告を出して 1 で終わる
3. 記録を一時ファイルに書き、`ln` で記録のパスに結ぶ。記録のパスがすでにあれば、[記録があるとき](#記録があるとき)の、一覧に PR がない行と同じ出力にして 0 で終わる
4. ほかの理由で結べなければ、今と同じ警告を出して 1 で終わる。PR を作った役は、今の決まりのとおり `pr_url` を書く
5. 結べたら、標準出力に次の 2 行を出して 0 で終わる。標準エラーには何も出さない

```text
連携なしにしました: <タスクの識別子> <PR の URL>
<知らせの文>
```

`pr_url` を記録より先に書くのは、0 で終わる実行が必ず `pr_url` を残すためである。0 のとき、PR を作った役は `branch` だけを書く。知らせを出すのは記録を結べた実行だけなので、同じリポジトリの 2 つの PR が同時に待ち切れても、知らせは 1 つになる。

期限を過ぎても `PR_LINK_ALL_404` が 1 でないときと、404 以外で失敗したときは、記録を書かない。一覧の読み直しで PR がなければ、今の動作（警告・`pr_link_pending`・1 で終わる）を変えない。

### 404 だけが続いたことの判定

`PR_LINK_ALL_404` は、`pr_link_pull_request` に足す結果である。今の `PR_LINK_NOT_FOUND` は、期限を過ぎれば最後の応答によらず 1 になる。通信の失敗や 500 でも 1 になるので、記録の判定には使わない。

| 期限を過ぎたと分かった所 | `PR_LINK_NOT_FOUND` | `PR_LINK_ALL_404` |
| --- | --- | --- |
| 次の試みの前。直前の応答は 404 で、待っていた | 1 | 1 |
| 応答のあと。その応答が 404 | 1 | 1 |
| 応答のあと。その応答が通信の失敗か 404 以外 | 1 | 0 |

404 以外の応答と通信の失敗は、期限の前ならその場で終わる。そのため、期限を過ぎた時点で、それより前の応答はすべて 404 である。`PR_LINK_NOT_FOUND` と、戻り値と待ち方と今の警告は変えない。

### 記録があるとき

待たずに、紐付けの API を 1 回だけ呼ぶ（`pr_link_request_once`、時間切れ 30 秒）。呼ぶ前に API の環境を確認し、なければ呼ばずに失敗として続ける。200 でなければ、[一覧の読み直し](#一覧の読み直し)をする。

| 結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| 200 | 今と同じく `pr_url` を書き、記録を消す | `紐付けました: <タスクの識別子> <PR の URL>` | 0 |
| 失敗し、一覧に PR がある | 一覧の読み直しのとおり | `紐付いていました:` の行 | 0 |
| 失敗し、一覧に PR がない | `pr_link_pending` と `pr_url` を書く | `紐付けていません（連携なし）: <タスクの識別子> <PR の URL>` | 0 |
| 上の行で `pr_url` を書けない | 今と同じ警告を標準エラーに出す | なし | 1 |

失敗は、200 以外の応答、通信の失敗、API の環境がないことの 3 つである。どれでも、記録は消さない。404 以外の応答で消すと、サーバーの一時の失敗で次の PR が 120 秒待つためである。

PR を作った役には、どの 0 も今の成功と同じに読ませる。`紐付けていません（連携なし）:` のときは、引き継ぎに何も足さない。

### 一覧の読み直し

`squad-pr-link` は、紐付けに失敗したとき、警告と記録の前に、タスクの PR の一覧を 1 回だけ読む。自動の関連付けなどで PR がすでに紐付いていれば、失敗として扱わないためである。

読み直すのは、次の 4 つの失敗のときである。120 秒の待ちの期限切れ・200 以外の応答・通信の失敗・API の環境がないことである。作業先が PR のリポジトリと違うとき、200 のあとに `pr_url` を書けないときは読まず、今の動作にする。

一覧は `squad_cli_read issue-pull-requests` で読み、`html_url` を PR の URL と比べる。比べ方は `link-check` と同じにする。

| 一覧の結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| PR がある | `pr_url` を書き、記録があれば消す。`pr_link_pending` は書かない | `紐付いていました: <タスクの識別子> <PR の URL>` | 0 |
| PR がない、または一覧を読めない | 読み直す前の失敗のとおりに続ける | 前の節のとおり | 前の節のとおり |
| PR があり、`pr_url` を書けない | 今と同じ警告を標準エラーに出す | なし | 1 |

紐付けの前には一覧を読まない。サーバーが PR を知っていれば紐付けの API が成功するので、一覧が効くのは失敗のあとだけである。成功の経路の呼び出しを変えず、今のテストを変えずに通すためでもある。

## 知らせ

知らせは、記録を書いたときに、その PR のタスクへ 1 回だけ出す。出すのは PR を作った役で、引き継ぎのコメントに段落として入れる。

`squad-pr-link` は、記録を結べた実行の標準出力の 2 行目に、次の文を 1 行で出す。

```text
<オーナー>/<リポジトリ> を、このプロジェクトでは GitHub 連携なしとして扱います。サーバーが 120 秒待っても PR を見つけなかったためです。このあとの PR では紐付けを待たず、紐付けの警告と依頼を出しません。マージのあとは、人間がタスクを done にしてください。連携しているはずなら、ワークスペースの設定のコードの画面で <オーナー>/<リポジトリ> がつながっていることを確認してください。このリポジトリの PR が 1 つでも紐付けば、自動で連携ありの扱いに戻ります。
```

PR を作った役は、1 行目が `連携なしにしました:` のとき、引き継ぎの成果物の PR の URL のすぐ下に、次の段落を置く。今の `紐付けの失敗:` の段落と同じ置き場所で、`紐付けの失敗:` の段落は置かない。設計の役が自分で人間に承認を頼むコメントでも、この段落を置く。

```text
連携なし: <標準出力の 2 行目>
```

役が段落を書き漏らしても、記録は残り、動作は変わらない。知らせが出ないだけである。リーダーは段落を写し直さず、別の知らせも出さない。段落を出す役を 1 つにして、同じ知らせが重ならないようにするためである。

## link-check の動作

`squad-pr-watch link-check` の判定は、今のとおり一覧で読み、変えない。判定のあとに、タスクの `project_id` と `pr_url` のリポジトリから記録を読む。

| 判定 | 記録 | すること | 行 |
| --- | --- | --- | --- |
| 紐付いている | ある | 記録を消す | 今と同じ |
| 紐付いていない | ある | 末尾に `連携: なし` を足す | `紐付け: 紐付いていない pr: <PR の URL> 連携: なし` |
| そのほか | どちらでも | 今と同じ | 今と同じ |

記録は、試み直しのあとの判定で読む。試み直しで紐付いたときも、記録を消す。

行の先頭は今と同じである。`紐付け: 紐付いていない` で始まるかで読む今の分岐は、そのまま CI とコンフリクトを確認する。分岐は `decide`・`unlinked-check`・リーダーの手順にある。`decide` は `pr:` の次の語だけを URL として読むので、末尾を足しても URL は変わらない。

記録は、新しい PR が待つかを決めるとともに、進行中の PR の扱いも決める。記録が消えると、紐付いていない進行中の PR は、次の `link-check` から今の動作に戻る。

### 試み直しと記録を出さない方法

`連携: なし` のときも、試み直す条件と時機は今と同じにする。条件は、`pr_link_pending` が `pr_url` と同じ PR を指し、一度も紐付いておらず、作業先が同じことである。変えるのは、紐付かなかった試み直しの記録をタスクに書かないことと、間隔の測り方だけである。

| 試み直しの結果 | 今 | `連携: なし` のとき |
| --- | --- | --- |
| `紐付いた` | 記録を書く | 記録を書き、連携なしの記録を消す |
| それ以外（`一覧にない（200）`・`見つからない（404）`・`失敗…`・`未確認…`・`食い違い`） | 記録を書く | 書かない |

試み直しの間隔は、今は前の `紐付けの試み直し:` の記録の時刻から測る。記録を書かないと間隔が測れず、`link-check` のたびに API を呼ぶ。そこで、`連携: なし` のときは、API を呼ぶたびに metadata の `pr_link_tried_at` へ時刻と URL を書く。

```text
<UTC の YYYY-MM-DDTHH:MM:SSZ> <PR の URL>
```

間隔は、前の記録の時刻と `pr_link_tried_at` のうち、新しいほうから測る。`pr_link_tried_at` は、次のどれかのとき、ないものとして読む。形に合わない・今より後の時刻・URL が今見ている PR と正規形で違う、の 3 つである。同じタスクで `pr_url` を差し替えても、前の PR の試みが新しい PR の試み直しを遅らせないためである。

書けなくても、出力の行は変えない。間隔の値（リーダーの確認の 5 分、マージ待ちの見張りの 6 時間）は変えない。一度紐付いたかの判定は、今と同じくコメントの記録で読む。

## リーダーと decide の動作

リーダーと `squad-review-next decide` は、`link-check` の行の末尾の `連携: なし` で、連携なしの PR を見分ける。見分けたら、紐付けの依頼と警告と連携の案内を出さず、マージを頼むときだけ `done` の行を 1 行添える。

| 場面 | 今（紐付いていない） | `連携: なし` のとき |
| --- | --- | --- |
| PR を受け取ったときの知らせ（`leader-pr-ci.md`） | 警告・連携の前提・再発を 1 回知らせる | 知らせない |
| マージを頼むコメント（`leader-pr-merge.md` と `decide`） | `done` か紐付けを頼む行と、`紐付けの失敗:` の段落と連携の案内 | 下の 1 行だけ |
| ほかの理由で人間を呼ぶコメント（同上） | 紐付けを頼む行と、`紐付けの失敗:` の段落と連携の案内 | 何も添えない |
| その場の確認、CI、コンフリクト | 紐付いていない PR として確認する | 変えない |
| マージ待ちの見張りの登録（`unlinked`） | 登録する | 変えない |

マージを頼むコメントに添える 1 行は、次のとおりにする。`見張り:` の行は、今のとおり続ける。

```text
このリポジトリは GitHub 連携なしとして扱っています。マージのあとに、タスクを `done` にしてください。PR: `<正規形>`
```

`decide` は、`紐付け: 紐付いていない pr:` で始まる行で `LINKED=false` とするのを変えない。末尾が `連携: なし` のときだけ、新しい `NO_INTEGRATION=true` を立てる。`LINKED=false` を見る CI と見張りの登録はそのままにし、依頼の行と `print_linkfail` だけを `NO_INTEGRATION` で分ける。

マージ待ちの見張り（`unlinked-check`）は変えない。マージを見たら規則を消して止まり、タスクの状態を変えず、知らせも書かない。人間がマージを確認して `done` にする。

## squad-dependabot-merge の経路

`squad-dependabot-merge` は、Dependabot の PR を自分のタスクに紐付けるとき、`pr_link_pull_request` で 120 秒まで待つ。この経路も、記録を読む。プロジェクトの ID は、引数のプロジェクトを使う。

| 記録 | すること |
| --- | --- |
| ない | 今と同じく 120 秒まで待つ。404 で待ち切れても、記録は書かない |
| ある | 待たずに 1 回だけ呼び、200 なら今の成功と同じにして記録を消す。失敗なら警告を出さず、次に同じ PR を回すときに補う今の続きにする |

記録を書かないのは、Dependabot の PR は作った直後の同期が遅れやすく、PR を作る役の経路と条件が違うためである。記録は、役の PR が待ち切れたときだけに作る。

## セットアップと README・手順書

セットアップは、リポジトリの候補が 0 件のときの案内だけを変える。候補は今のとおり `multica repo list` から選び、連携の有無は尋ねない。

0 件の案内は、管理者が `multica repo add` でリポジトリを登録できることを示す。連携のないリポジトリも、登録すれば候補に出て、導入できる。

README と手順書は、連携を導入の前提とする文をやめ、連携の有無で次のとおり違うことを書く。

| 連携 | PR の欄 | マージのあとの `done` |
| --- | --- | --- |
| あり | タスクの画面の PR の欄に出る | 連携が自動で `done` にする |
| なし | 欄に出ない。PR の場所は metadata の `pr_url` とコメントで示す | 人間が `done` にする |

手順書には、記録の置き場所と、人間が記録を消す手順を書く。消すのは、連携をつないだあと、次の PR を待たずに今の動作に戻したいときである。共通スキルの状態の表（`SKILL.md`）の `done` の行にも、連携なしでは人間が変えることを足す。

## 同じ原因の場面の一覧

連携がないことで起きる場面を、今の main から数え上げた。どの場面も、記録か `連携: なし` の末尾で分ける。

| 場面 | 今の置き場所 | この設計で |
| --- | --- | --- |
| 作った直後の 120 秒の待ちと警告と連携の案内 | `squad-pr-link`（`warn`・`warn_not_found`） | 記録がないときは今のまま。記録を書いたあとと、記録があるときは出さない |
| 役の `紐付けの失敗:` の段落 | `pr.md` の「PR を作る・実装を積む」 | 0 で終わるので置かない。記録を書いた実行だけ `連携なし:` の段落を置く |
| リーダーの紐付けの判定の表と、試み直しの説明 | `leader-pr-link.md` の「PR の紐付けの確認」 | 紐付いていないの行に、`連携: なし` の扱いを足す |
| PR を受け取ったときの知らせ | `leader-pr-ci.md` の「紐付いていない PR を受け取ったときの知らせ」 | 出さない |
| マージを頼むコメントの行と段落と案内 | `leader-pr-merge.md` の「人間を呼ぶコメントに添える行」、`decide` | `done` の 1 行だけにする |

| 試み直しの記録 | `squad-pr-watch link-check` | 紐付かなかった結果は書かない |
| Dependabot の PR の待ちと警告 | `squad-dependabot-merge` の紐付け | 記録があれば待たず、警告を出さない |
| `done` を変える人の表 | `SKILL.md` の「タスクの状態と担当」 | 連携なしでは人間と足す |
| 人間に頼むことの例の「PR の紐付けの連携」 | `leader-repeat.md` | 変えない。連携をつなぐのは今も人間の判断である |
| 依頼の前と止める前の `link-check` | `leader-review-request.md`・`leader-run-stop.md`・`leader-review-stuck.md` | 変えない。行の先頭で分けており、扱いは上の各場面の手順に従う |
| マージ待ちの見張り | `unlinked`・`unlinked-check` | 変えない |
| 候補が 0 件のときの案内 | `lib/questions.sh` | `multica repo add` を示す |
| 連携を前提とする説明 | README の「必要なもの」、手順書の「GitHub 連携とリポジトリの紐付け」と候補が 0 件の説明 | 連携の有無の違いと、記録を消す手順を書く |

## 入力と信頼の表

記録はガードではないが、人間への依頼を止める判定に使うので、読む入力ごとに信頼する条件を決める。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 記録のファイル（ホストのスクリプトか人間だけが書く） | `squad-pr-link`・`link-check`・`squad-dependabot-merge` の記録の有無 | パスの各部分が許した文字だけで、パスと上のディレクトリがシンボリックリンクでなく、普通のファイルである | ないものとして読み、標準エラーに 1 行出す。書きも消しもしない |
| タスクの `project_id`（サーバーが返す） | 記録のパス | 許した文字だけの値である | 記録を書かず読まず、今の動作にする |
| metadata の `repository` と `pr_url`（役と人間が書ける） | 記録のパスのリポジトリと、記録を書く条件 | `pr_url` が PR の URL の形で、`repository` と小文字で同じリポジトリを指す | 今の `作業先と違う`・`不正な pr_url` の判定に従い、記録を読まず書かない |
| metadata の `pr_link_tried_at`（役と人間が書ける） | 試み直しの間隔 | 形が合い、今より前の時刻で、URL が今の PR と正規形で同じ | ないものとして読み、間隔を前の記録の時刻から測る |
| タスクの PR の一覧（サーバーが返す） | 紐付いたかの判定と記録の消去 | 今の `link-check` と同じく、正規形の `html_url` が PR と同じ | 紐付いていないと読む。読めないときは今の未確認の扱いにする |
| 試み直しの記録のコメント（エージェントが書く） | 一度紐付いたかと、間隔 | 今と同じく作者がエージェントで、`/note` の 2 行目が決まった形 | 読まずに飛ばす |
| 役の引き継ぎの `連携なし:` の段落（役が書く） | 人間への知らせ | 人間が読むだけで、どの判定にも使わない | 判定に使わないので、合わないことがない |

記録を人間が手で作ると、そのリポジトリは連携なしとして扱われる。これは記録を消すのと同じく人間の操作であり、次に紐付けば消える。記録の偽造で起きるのは紐付けの依頼が出ないことだけで、マージや状態の変更は起きない。

## 残る危うさ

記録はホストのファイルなので、同じプロジェクトの役が別のホストで動くと、記録がホストごとに分かれる。使用率の確認の状態と同じ前提で、ホストを分けたときは、それぞれのホストで 1 回ずつ待ち切れて記録ができる。

連携があっても、同期が 120 秒より遅れると連携なしと記録する。そのリポジトリでは、次に紐付くまで、紐付けの依頼が出ない。次の PR は 1 回の試みで紐付けば記録が消えるが、同期が遅れ続けると連携なしのままになる。そのあいだ、人間は `done` の行で頼まれたとおりタスクを `done` にする。

記録が消えると、紐付いていない進行中の PR は、次の `link-check` から紐付けの依頼が出る動作に戻る。消えるのは連携がつながったときなので、依頼のとおり紐付けられる。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| タスクごとに連携なしの印を metadata に置き、記録と 2 つで読む | 要件はリポジトリごとの扱いで、印は記録と食い違う状態を増やす。見張りが `done` にしないので、進行中の PR に扱いを固定する理由もない |
| マージ待ちの見張りがマージを確認して `done` にする | 人間が `done` にすると決めたため。見張りに `done` の照合を足すと、誤って閉じる危うさのほうが大きい |
| 連携の状態を API で読む | 読める API がなく、要件で除いた |
| セットアップで連携の有無を尋ねる | 人間が誤って答えると直す所がない。紐付けの結果で見分けるほうが確かである |
| スクリプトがタスクへ知らせを直接投稿する | PR を作った役が引き継ぎに書けば、知らせの置き場所が今の `紐付けの失敗:` と同じになる。投稿の権限と返信先の扱いを増やさない |
| 404 以外の失敗や通信の失敗でも記録する | サーバーの一時の失敗で、連携のあるリポジトリを連携なしにしてしまう |
| Dependabot の経路でも記録を書く | 同期の遅れで記録が増えやすく、役の PR の経路と条件をそろえられない |
