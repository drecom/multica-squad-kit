# GitHub 連携のないリポジトリで、PR の紐付けを待たずに進める

GitHub 連携のないリポジトリでは、サーバーが PR を見つけられず、PR ごとに待ちと警告と人間への依頼が起きる。この設計では、作った直後の紐付けが 404 で待ち切れたリポジトリを、ホストに「連携なし」と記録する。記録のあるリポジトリの PR では、待ちと警告と依頼を出さず、マージ待ちの見張りがマージを確認してタスクを `done` にする。

あわせて、PR を作る役は PR のタイトルにタスクの識別子を入れる。連携のあるリポジトリでは、サーバーがタイトルから PR をタスクに自動で関連付ける。自動の関連付けと明示の紐付けのどちらで紐付いても、紐付いたと扱う。

この文書は、タイトルの識別子と、記録の形と置き場所を書く。`squad-pr-link` と `squad-pr-watch` の動作、知らせの文と出す役も書く。リーダーの手順と `decide` の扱い、セットアップの案内、README と手順書の直しも書く。それぞれの理由も添える。

## 目的と範囲

今は、連携のないリポジトリでも、PR を作るたびに次が起きる。PR を作った役が 120 秒待って警告を残し、リーダーが連携の確認と紐付けを人間に頼み、試み直しの記録がタスクに増える。マージのあとは、人間がタスクを `done` にする。README・手順書・セットアップの案内は、連携を導入の前提にしている。

目的は次の 6 つである。

1. 連携のないリポジトリを、紐付けの結果から見分けて記録する。連携の状態は API で読まない
2. 記録のあるリポジトリの PR では、120 秒の待ち、紐付けの警告と依頼、紐付かなかった試み直しの記録を出さない
3. 記録のあるリポジトリの PR は、マージ待ちの見張りがマージを確認して `done` にする
4. 連携のあるリポジトリは、1 つでも紐付けば記録を消し、今の動作に戻す
5. PR のタイトルにタスクの識別子を入れ、連携のあるリポジトリで自動の関連付けを使えるようにする
6. 自動の関連付けと明示の紐付けのどちらで紐付いても、紐付いたと扱う。連携のないリポジトリで自動の関連付けが効くかは、前提にしない

次は対象にしない。

- 連携なしの PR を、タスクの画面の PR の欄に出すこと。サーバーが PR を持てないため、PR の場所は metadata の `pr_url` とコメントで示す
- 連携の状態を API で読むこと、セットアップの質問で連携の有無を尋ねること
- 120 秒の待ちの長さと、[試み直し](pr-link-retry.md)の時機と間隔
- CI とコンフリクトの確認
- `squad-dependabot-merge` の紐付け。扱いは[検討した案](#検討した案)に書く
- 明示の紐付けを、自動の関連付けに置き換えること。連携なしを、明示の紐付けの結果で見分けるため
- ブランチ名に識別子を入れること。ブランチ名は Multica の checkout が決めるため
- 連携のあるリポジトリで、120 秒のうちに紐付かない原因の調査

## PR のタイトルの識別子と自動の関連付け

PR を作る役は、PR のタイトルの末尾にタスクの識別子を入れ、タイトルを直すたびに残す。公開と非公開のリポジトリで同じにし、ブランチ名は変えない。

### タイトルの形

識別子は、タイトルの末尾に半角の丸括弧で置く。先頭の種類（`feat:` など）は、今の決まりのとおり先頭に残す。

```text
feat: 連携なしのリポジトリで紐付けを待たずに進める (DEMO-12)
```

- 識別子は、タスクの読み取り（`multica issue get`）の `identifier` を使う。実行に渡されるタスクの ID（UUID）は入れない
- `gh pr create --title` で作るときから入れる。push のたびに `gh pr edit --title` でタイトルを直すときも、末尾の識別子を残す
- 決まりの置き場所は、共通スキル `squad-handoff` の「PR を作る・実装を積む」である。設計と実装と修正の役は、すでにこの節を読んでタイトルを書いている

識別子を入れても、明示の紐付け（`squad-pr-link`）は今のとおり呼ぶ。連携なしは、明示の紐付けの結果で見分けるためである。

### 紐付いたと扱う所

紐付いたかは、どの所でもタスクの PR の一覧（`multica issue pull-requests`）で読む。一覧には、自動の関連付けの PR も明示の紐付けの PR も出るので、両方を紐付いたと扱える。

| 所 | 読み方 |
| --- | --- |
| `squad-pr-link` | 紐付けの API が成功すれば、今のとおり紐付いたと読む。失敗したときは、警告と記録の前に一覧を 1 回読み直す（[一覧の読み直し](#一覧の読み直し)） |
| `squad-pr-watch link-check` | 今も一覧の `html_url` で読むので、変えない。自動の関連付けの PR も「紐付いている」になる |

紐付いたと読んだときは、連携なしの記録があれば消す。記録の消去は、紐付き方によらず同じに働く。

### 連携の有無と自動の関連付け

連携のないリポジトリで自動の関連付けが効くかは、前提にしない。公開のソースの読みでは効かないが、実機では確認していない。どちらでも、次のとおり動く。

| リポジトリ | 自動の関連付けが効く | 効かない |
| --- | --- | --- |
| 連携あり | PR の欄に出る。`squad-pr-link` は今のとおり紐付ける | 今の動作と同じ |
| 連携なし | 一覧に PR が出るので、記録を書かず、あれば消す。連携ありの動作になる | 404 で記録を書き、連携なしの動作になる |

実機の結果は、人間が受け入れの確認で、1 つ目の PR が PR の欄に出るかを見てタスクに残す。どちらの結果でも、この設計は変えない。

### 自動の関連付けを確認する方法

自動で関連付いたかは、タスクの PR の一覧の `link_source` で見る。`title` なら自動の関連付け、`manual` なら明示の紐付けである。

```bash
multica issue pull-requests <タスク> --output json | jq '.pull_requests[] | {html_url, link_source}'
```

`squad-pr-link` が一覧の読み直しで紐付いていたと読んだときも、出力の行に `紐付け方:` として `link_source` を出す。役の出力からも、自動の関連付けが効いたかを読める。

明示の紐付けを、自動の関連付けのあとに呼んだときの `link_source` は確認していない。`manual` に替わるかもしれないので、自動の関連付けを確認するときは、明示の紐付けが失敗した PR か、連携のないリポジトリの PR で見る。

## 連携なしの記録

記録は、ホストのエージェントのホームの下に、プロジェクトとリポジトリごとに 1 つのファイルで置く。ファイルがあることだけを「連携なし」と読み、中身は人間が読むためだけに書く。

### 置き場所と形

置き場所は次のパスにする。使用率の確認の状態（`squad-usage-check`）と同じ根の下に置き、セットアップの流し直しで消えないようにする。

```text
${PR_LINK_STATE_ROOT:-$HOME/.multica-agent/template/pr-link}/<プロジェクトの ID>/<オーナー>/<リポジトリ>
```

- プロジェクトの ID は、タスクの読み取り（`multica issue get`）の `project_id` を使う。タスクにプロジェクトがないときは、記録を書かず読まず、今の動作のままにする
- オーナーとリポジトリは、PR の URL から取り、小文字にする。metadata の `repository` との照合も小文字で行う
- 各部分は、`squad-usage-check` と同じく、空・`.`・`..`・英数字と `_.-` 以外の文字を含むものを断る。断ったときは記録を書かず、ないものとして読む
- ディレクトリは 700、ファイルは 600 で作る。ファイルは同じディレクトリの一時ファイルに書いてから `ln` で記録のパスに結び、書きかけを読ませない
- `ln` は記録のパスがあると失敗するので、同時に作る実行のうち 1 つだけが記録を作る（[同時に作るとき](#同時に作るとき)）。一時ファイルは、結べたかによらず最後に消す

中身は次の 4 行にする。判定には使わない。

```text
repository: <オーナー>/<リポジトリ>
pr: <記録のきっかけになった PR の URL>
task: <タスクの識別子>
記録した時刻: <UTC の YYYY-MM-DDTHH:MM:SSZ>
```

記録のパスかその上のプロジェクトとオーナーのディレクトリがシンボリックリンクなら、記録はないものとして読み、書きも消しもしない。普通のファイルでないもの（ディレクトリなど）も同じにする。どちらも標準エラーに 1 行だけ理由を出す。

### 書く時機と消す時機

記録を書くのは `squad-pr-link` だけで、作った直後の紐付けが 120 秒のあいだ 404 だけで終わったときに限る（[記録がないとき](#記録がないとき)）。期限の直前の応答が通信の失敗か 404 以外のときも、書かない。トークンや API の環境がないとき、作業先が PR のリポジトリと違うときも書かない。

記録を消すのは、そのプロジェクトとリポジトリの PR が紐付いたと分かったときである。分かる所は次の 2 つにする。

| 所 | 消す条件 |
| --- | --- |
| `squad-pr-link` | 記録があり、1 回の試みが 200 を返して `pr_url` を書けた。または、紐付けに失敗したあとの[一覧の読み直し](#一覧の読み直し)で、PR が一覧にあった |
| `squad-pr-watch link-check` | 判定が「紐付いている」で、そのタスクのプロジェクトとリポジトリの記録がある。きっかけは試み直しに限らず、自動の関連付けでもよい |

人間が消すときは、手順書の手順で、ホストのファイルを消す。消すと、次の PR から今の 120 秒の待ちに戻る。

## squad-pr-link の動作

`squad-pr-link` は、タスクを読んだあと、作業先が PR のリポジトリと同じで、プロジェクトの ID があるときに記録を読む。記録の有無で、次の 2 つに分かれる。どちらでもないとき（作業先が違う、プロジェクトがない）は、今の動作のままにする。

### 記録がないとき

今と同じく 120 秒まで待つ。期限まで 404 だけが続いたとき（`PR_LINK_ALL_404=1`）は、先に[一覧の読み直し](#一覧の読み直し)をする。PR が一覧になければ、次の順で連携なしに切り替える。

1. 記録の中身を一時ファイルに書く。まだ記録のパスには結ばない（記録がすでにあれば[同時に作るとき](#同時に作るとき)のとおりにし、ほかの理由で作れなければ今と同じ警告を出して 1 で終わる）
2. metadata の `pr_url` に PR の URL を書く。2 つのマークは、まだ書かない
3. `pr_url` を書けなければ、一時ファイルを消し、今と同じ警告を出して 1 で終わる。記録は見える形になっていないので、取り消すものがない
4. 一時ファイルを `ln` で記録のパスに結び、一時ファイルを消す。ほかの実行が先に結んでいれば[同時に作るとき](#同時に作るとき)のとおりにし、ほかの理由で結べなければ今と同じ警告を出して 1 で終わる
5. metadata の `pr_link_pending`・`pr_link_no_integration` に PR の URL を書く。書けなくても続け、`link-check` が後で書き直す（[マークの書き直し](#マークの書き直し)）
6. 標準出力に次の 2 行を出し、0 で終わる。標準エラーには何も出さない

```text
連携なしにしました: <タスクの識別子> <PR の URL>
<知らせの文>
```

マークを記録のあとに書くのは、1 で終わった実行に連携なしのマークを残さないためである。マークを先に書くと、`ln` に失敗して 1 で終わっても `pr_link_no_integration` が残る。すると `link-check` が `連携: なし` を出し、役の紐付けの失敗の報告と食い違う。手順 4 と 5 の間で止まったときは、記録があるので、`link-check` がマークを書き直す。

知らせの文は[知らせ](#知らせ)に書く。0 で終わるので、PR を作った役は今の決まりのとおり metadata の `branch` だけを書く。`pr_url` はスクリプトが書いている。

待っているあいだにほかの実行が記録を結び、そのあとこの実行の紐付けが成功したときは、`pr_url` を書いたあとに記録を消す。記録を残すと、連携ありの PR を連携なしとして扱い続けるためである。

期限を過ぎても `PR_LINK_ALL_404` が 1 でないときと、404 以外で失敗したときは、記録を書かない。一覧の読み直しをして、PR が一覧になければ今の動作（警告・マーク・1 で終わる）を変えない。

### 404 だけが続いたことの判定

`PR_LINK_ALL_404` は、`pr_link_pull_request` に足す結果である。今の `PR_LINK_NOT_FOUND` は、期限を過ぎれば最後の応答によらず 1 になる。通信の失敗、500、遅れて返った 200 でも 1 になるので、記録の判定には使わない。

| 期限を過ぎたと分かった所 | `PR_LINK_NOT_FOUND` | `PR_LINK_ALL_404` |
| --- | --- | --- |
| 次の試みの前。直前の応答は 404 で、待っていた | 1 | 1 |
| 応答のあと。その応答が 404 | 1 | 1 |
| 応答のあと。その応答が通信の失敗か 404 以外（200 を含む） | 1 | 0 |

404 以外の応答と通信の失敗は、期限の前ならその場で終わる。期限を過ぎた時点で、それより前の応答はすべて 404 である。`PR_LINK_NOT_FOUND` と、戻り値と待ち方と今の警告は変えない。

### 同時に作るとき

同じリポジトリの 2 つの PR の待ちが同時に終わると、2 つの実行が記録を作ろうとする。記録は、`pr_url` を書いたあとに `ln` で結び、2 つのマークは結んだあとに書く。`ln` は記録のパスがあると失敗するので、記録を結べるのは 1 つの実行だけである。結ぶまでは記録が見えないので、`pr_url` を書けなかった実行が、ほかの実行が採用した記録を消すことはない。

| 場合 | すること |
| --- | --- |
| `pr_url` を書いたあと、`ln` で記録を結べた | 2 つのマークを書き、知らせの 2 行を出す。知らせを出すのは、この実行だけである |
| 記録を用意する前か、`ln` で結ぶときに、記録のパスがあった | [記録があるとき](#記録があるとき)の、一覧に PR がない行と同じにする。`pr_url` を書いてから 2 つのマークを書き、知らせは出さずに 0 で終わる |
| `pr_url` を書けない | 記録を結ばずに一時ファイルを消す。ほかの実行が結んだ記録は、この実行が触れないので残る |

記録の消去（PR が紐付いたとき）と作成が重なったときは、後に起きたほうが残る。どちらでも、進行中の PR は自分のマークで扱いが決まるので、依頼の有無は変わらない（[進行中の PR の扱い](#進行中の-pr-の扱い)）。

### 記録があるとき

待たずに、紐付けの API を 1 回だけ呼ぶ（`pr_link_request_once`、時間切れ 30 秒）。呼ぶ前に、API の環境を確認する。200 でなければ、[一覧の読み直し](#一覧の読み直し)をする。

| 結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| 200 | 今と同じく `pr_url` を書き、記録を消す | `紐付けました: <タスクの識別子> <PR の URL>` | 0 |
| ほかの応答、通信の失敗、API の環境がなく、一覧に PR がある | 一覧の読み直しのとおり | `紐付いていました:` の行 | 0 |
| ほかの応答、通信の失敗、API の環境がなく、一覧に PR がない | `pr_url` に PR の URL を書いてから、`pr_link_pending`・`pr_link_no_integration` に書く。2 つのマークは書けなくても続ける | `紐付けていません（連携なし）: <タスクの識別子> <PR の URL>` | 0 |
| 上の行で `pr_url` を書けない | 今と同じ警告を標準エラーに出す。`pr_link_no_integration` は書かない | なし | 1 |

`pr_url` がすでにあるときは、今と同じく API を呼ばずに `紐付けていません:` の行を出す。記録の有無で変えない。

PR を作る役には、どちらの 0 も今の成功と同じに読ませる。`紐付けていません（連携なし）:` のときは、引き継ぎに何も足さない。

### 一覧の読み直し

`squad-pr-link` は、紐付けに失敗したとき、警告と記録とマークの前に、タスクの PR の一覧を 1 回だけ読む。自動の関連付けなどで PR がすでに紐付いていれば、紐付けの失敗として扱わないためである。

読み直すのは、次の失敗のときである。120 秒の待ちの期限切れ、ほかの応答、通信の失敗、API の環境がないときの 4 つである。作業先が PR のリポジトリと違うとき、200 のあとに `pr_url` を書けないとき、`pr_url` がすでにあるときは読まず、今の動作にする。

一覧は `squad_cli_read issue-pull-requests` で読み、`html_url` を PR の URL と比べる。比べ方は `link-check` と同じにする。

| 一覧の結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| PR がある | `pr_url` に PR の URL を書き、記録があれば消す。マークと `pr_link_no_integration` は書かない | `紐付いていました: <タスクの識別子> <PR の URL> 紐付け方: <link_source>` | 0 |
| PR がない | 読み直す前の失敗のとおりに続ける（記録を書く、または警告とマーク） | 今と同じ | 今と同じ |
| 一覧を読めない | PR がないときと同じ | 今と同じ | 今と同じ |
| PR があり、`pr_url` を書けない | 今と同じ警告を標準エラーに出す | なし | 1 |

`紐付け方:` には、一覧の `link_source` が英小文字と `_` だけのときにその値を出し、ないときや形が合わないときは `不明` を出す。標準エラーには何も出さない。PR を作る役は、この行も今の成功と同じに読み、引き継ぎに何も足さない。

紐付けの前には一覧を読まない。サーバーが PR を知っていれば紐付けの API が成功するので、一覧が効くのは失敗のあとだけである。成功の経路の呼び出しを変えず、今のテストを変えずに通すためでもある。

## 知らせ

知らせは、記録を書いたときに、その PR のタスクへ 1 回だけ出す。出すのは PR を作った役で、引き継ぎのコメントに段落として入れる。

`squad-pr-link` は、記録を書いた実行の標準出力の 2 行目に、次の文を 1 行で出す。

```text
<オーナー>/<リポジトリ> を、このプロジェクトでは GitHub 連携なしとして扱います。サーバーが 120 秒待っても PR を見つけなかったためです。このあとの PR では紐付けを待たず、紐付けの警告と依頼を出さず、マージ待ちの見張りがマージを確認してタスクを done にします。連携しているはずなら、ワークスペースの設定のコードの画面で <オーナー>/<リポジトリ> がつながっていることを確認してください。このリポジトリの PR が 1 つでも紐付けば、自動で連携ありの扱いに戻ります。
```

PR を作る役は、1 行目が `連携なしにしました:` のとき、引き継ぎの成果物の PR の URL のすぐ下に、次の段落を置く。今の `紐付けの失敗:` の段落と同じ置き場所で、`紐付けの失敗:` の段落は置かない。

```text
連携なし: <標準出力の 2 行目>
```

役が段落を書き漏らしても、記録とマークは残り、動作は変わらない。知らせが出ないだけである。リーダーは段落を写し直さず、別の知らせも出さない。段落を出す役を 1 つにして、同じ知らせが重ならないようにするため。

スクリプトがタスクへ直接投稿する案は選ばなかった。理由は[検討した案](#検討した案)に書く。

## link-check の動作

`squad-pr-watch link-check` の判定は、今のとおり一覧で読み、変えない。自動の関連付けで紐付いた PR も「紐付いている」になる。判定が「紐付いていない」のときだけ、PR が連携なしの扱いかを次のどちらかで読む。

- タスクのプロジェクトとリポジトリの記録がある
- metadata の `pr_link_no_integration` が `pr_url` と同じ PR を指す

どちらかに当たれば、[マークの書き直し](#マークの書き直し)をする。2 つのマークが `pr_url` と同じ PR を指すときだけ、行の末尾に `連携: なし` を足す。

```text
紐付け: 紐付いていない pr: <PR の URL> 連携: なし
```

行の先頭は今と同じである。`紐付け: 紐付いていない` で始まるかで読む今の分岐（`decide`・`unlinked-check`・リーダーの手順）は、そのまま CI とコンフリクトを確認する。`decide` は `pr:` の次の語だけを URL として読んでおり、末尾を足しても URL は変わらない。

判定が「紐付いている」で記録があれば、記録を消す。

### マークの書き直し

`squad-pr-link` は、`pr_link_pending` か `pr_link_no_integration` を書けなくても 0 で終わる。書けなかった欄は、`link-check` が連携なしの扱いと読んだときに書き直す。`link-check` はリーダーの紐付けの確認とマージ待ちの見張りで流れるので、どこで失敗しても次の確認から続けられる。

| 2 つのマーク | すること | 行の末尾 |
| --- | --- | --- |
| どちらも `pr_url` と同じ PR を指す | 書かない | `連携: なし` |
| `pr_url` と違うか、ないものがある | その欄に PR の URL を書く。書けたら上の行と同じ | `連携: なし` |
| 上の行で、書けない欄が残った | 標準エラーに 1 行出す | 足さない |

末尾を足さないときは、今の「紐付いていない」の動作になり、リーダーは人間に紐付けと `done` を頼む。マークのない PR は、見張りが `done` にできないためである。書き直しは、[試み直し](#試み直しと記録を出さない方法)の条件を見る前にする。`pr_link_pending` を書けなかった PR も、同じ確認から試み直す。

### 進行中の PR の扱い

記録は、新しい PR が待つかを決めるもので、リポジトリに 1 つである。進行中の PR に約束した扱いは、そのタスクの `pr_link_no_integration` で持つ。

別の PR が紐付いて記録が消えても、マークのある紐付いていない PR は `連携: なし` のまま進む。紐付けと `done` の依頼は出ず、試み直しの記録も書かない。記録が消えたあとに作った PR は、マークがないので、今の 120 秒の待ちに戻る。

流し直す前に作った紐付いていない PR は、同じリポジトリの記録ができると、次の `link-check` でマークを書き、連携なしとして進む。記録ができるまでは、今の動作のままである。

### 試み直しと記録を出さない方法

`連携: なし` のときも、試み直す条件（マークが `pr_url` と同じ PR を指し、紐付いた一覧が空で、作業先が同じ）と時機は今と同じにする。変えるのは、紐付かなかった試み直しの記録をタスクに書かないことと、間隔の測り方だけである。

| 試み直しの結果 | 今 | `連携: なし` のとき |
| --- | --- | --- |
| `紐付いた` | 記録を書く | 記録を書き、連携なしの記録を消す |
| それ以外（`一覧にない（200）`・`見つからない（404）`・`失敗…`・`未確認…`・`食い違い`） | 記録を書く | 書かない |

試み直しの間隔は、今は前の `紐付けの試み直し:` の記録の時刻から測る。記録を書かないと間隔が測れず、`link-check` のたびに API を呼ぶ。そこで、`連携: なし` のときは、API を呼ぶたびに metadata の `pr_link_tried_at` へ `<時刻> <PR の URL>` を書く。時刻は UTC の `YYYY-MM-DDTHH:MM:SSZ`、URL は API を呼んだ PR で、間は空白 1 つにする。

間隔は、前の記録の時刻と `pr_link_tried_at` のうち新しいほうから測る。

`pr_link_tried_at` は、次のときないものとして読む。形に合わない、今より後の時刻、URL が今見ている PR と正規形で違う（時刻だけの値を含む）。同じタスクで `pr_url` を差し替えても、前の PR の試みが新しい PR の試み直しを遅らせないためである。

書けなくても、出力の行は変えない。間隔の値（リーダーの確認の 5 分、マージ待ちの見張りの 6 時間）は変えない。

一度紐付いたかの判定（`紐付いた` か `紐付いていた` の記録があるか）は、今と同じくコメントの記録で読む。紐付いた記録は、`連携: なし` のときも書くためである。

## マージ待ちの見張りの done

`unlinked-check` は、PR がマージされたことを `gh` で確認し、連携なしの PR ならタスクを `done` にする。連携なしの PR かは、metadata の `pr_link_no_integration` が `pr_url` と同じ PR を指すかで読む。記録ではなく metadata で読むのは、マージの依頼のあとに記録が消えても、依頼に `done` の行を入れなかった PR を `done` にするためである。依頼に見張りが `done` にする行を入れるのは `連携: なし` のときだけで、そのときマークは書けている（[マークの書き直し](#マークの書き直し)）。

metadata と見張りの規則は、役と人間とほかのエージェントが書ける。そこで `done` の根拠は、同じタスクの回のコメントに置き、編集できる値は照合の相手にだけ使う（[見張る PR の固定](#見張る-pr-の固定)）。

今の `unlinked-check` は、PR の状態が `MERGED` か `CLOSED` なら規則を消して止まる。この分岐を次のように分ける。ほかの順と判定は変えない。

| PR の状態 | `pr_link_no_integration` | すること |
| --- | --- | --- |
| `MERGED` | `pr_url` と同じ PR で、[done の照合](#done-の照合)の 4 つがそろう | `multica issue status <タスク> done --no-start` を流し、規則を消して `止めた: PR がマージされたので、タスクを done にした` を記録する |
| `MERGED` | `pr_url` と同じ PR で、照合のどれかが合わない | [done にしなかったときの知らせ](#done-にしなかったときの知らせ)を書き、規則を消して `止めた: PR がマージ済みか閉じている` を記録する。標準エラーに理由を 1 行出す |
| `MERGED` | `pr_url` と同じ PR で、照合のデータを読めない | 知らせを書かず、規則を残す。標準エラーに理由を 1 行出して 1 で終わる（[照合のデータを読めないとき](#照合のデータを読めないとき)） |
| `MERGED` | ないか違う PR | 今と同じく `止めた: PR がマージ済みか閉じている` |
| `CLOSED` | どちらでも | 今と同じく止まる。`done` にしない |

`--no-start` は、`squad-usage-check` がタスクを `done` にするときと同じく付ける。CLI の説明のとおり、状態の変更でエージェントの実行を始めないためである。

`done` にできなかったときは、規則を消さず、標準エラーに理由を出して 1 で終わる。規則の指示のとおり、リーダーが記録のスレッドへ失敗を書き、次の 1 時間後の確認でもう一度試みる。

この分岐は、今の順のとおり、タスクの状態が `in_review` かを見る前に置く。マージは事実なので、マージのあとに人間が状態を変えていても `done` にする。`done` と `cancelled` のタスクは、今と同じく先に止まる。

見張りの間隔（1 時間）と長さ（72 時間）、登録の時機は変えない。

### 見張る PR の固定

見張りは、マージの前に確認した PR を、同じタスクの今の回に結び付けて規則に固定する。規則を作るときと、`done` と知らせを決めるたびに、今の回と照合する。記録がないか、食い違うか、回が今の回でないときは進めない。

回のコメントを根拠にするのは、書き手を選べる記録だからである。回のコメントは `squad-review-next` が書き、`対象の PR:` と `確認するコミット:` の行を持つ。書き手はサーバーが記録し、`squad_cli_control analyze` が回と認めるのは、名簿のリーダーか正しい `前の回:` の記録を持つ `decide` の担当が書いたものだけである。人間とスクワッドの外のエージェントは、回を書けない。

名簿は、タスクの担当のスクワッドから `squad_cli_read_roster` で読む。回の判定のリーダーと最上位の役は、`decide` と同じく名簿から決める。引数の `--leader` と、規則の指示のリーダーの ID は、回の判定に使わない。

今の回は、タスクのコメントを名簿で `squad_cli_control analyze` にかけ、認める回のうちコメントの並びで最も新しいものとする。`status` と `proceed` が最新の回とするもの（`latest_round`）と同じで、`analyze` の出力に `latest` の欄として足す。今の回は、規則・metadata・引数から独立に、判定のたびにコメントから決める。PR を差し替えて次の回が書かれると、今の回は新しい回に移り、前の回で固定した規則では `done` にならない。

#### 登録の照合

`unlinked <タスク> <回のコメント> [<見張り役の ID>] [--leader <ID>]` の 2 つ目の引数を、回のコメントの ID として読む。`decide` は今も回の ID を渡している。手で流すリーダーも、最も新しい回のコメントの ID を渡す（[設計の変更の一覧](#設計の変更の一覧)）。

1. タスクのコメントを名簿で `squad_cli_control analyze` にかけ、引数の回が認められるかを見る
2. 引数の回が今の回かを見る
3. 回の `対象の PR:` の行が 1 つだけあり、正規形が metadata の `pr_url` と同じかを見る
4. 合えば、規則の指示の最後に `見張る PR: <正規形>` と `確認した回: <回のコメントの ID>` の 2 行を足して登録する。ほかの行と `unlinked-check` の引数は変えない

合わないときは、次のとおりにする。どの場合も、合わない規則で `done` にすることはない。

| 合わないこと | 連携なし（`pr_link_no_integration` が `pr_url` と同じ） | それ以外 |
| --- | --- | --- |
| 引数の回が今の回でない | 規則を作らず、`紐付け: 古い回 回: <引数の回> 今の回: <今の回>` を出して 0 で終わる | 同じ |
| `pr_url` が回の `対象の PR:` と違う | 規則を作らず、`紐付け: 食い違い pr: <pr_url> 回の PR: <回の PR>` を出して 0 で終わる | 同じ |
| 回を認められないか、`対象の PR:` の行がないか 2 つある | 規則を作らず、標準エラーに理由を 1 行出して 1 で終わる | 2 行を足さずに今のとおり登録し、標準エラーに理由を 1 行出す。この規則では `done` にしない |

`decide` は、今の `紐付け:` の行と同じく、食い違いと古い回の行で止まり、マージを頼まない。連携なしで 1 で終わったときは、今のとおり 3 で止まる。手でマージへ回すリーダーも、`紐付け:` の行で止まり、マージを頼まない（[設計の変更の一覧](#設計の変更の一覧)）。

#### done の照合

`unlinked-check` は、`issue-wakeups` で規則の一覧を 1 回だけ読み、自分の規則を決める。自分の規則は、1 行目がマークの規則のうち、`unlinked_deduplicate` が残すものと同じく作成が最も早い 1 つである。照合の行、見張りの終わりの時刻、知らせの時機は、すべてこの 1 つの規則から読む。次の 4 つがそろうときだけ、`done` にする。

1. 規則に `見張る PR:` と `確認した回:` の行が 1 つずつある
2. `確認した回:` の回が、判定のときの今の回である。その `対象の PR:` が `見張る PR:` と正規形で同じ
3. metadata の `pr_url` と `pr_link_no_integration` が、`見張る PR:` と正規形で同じ
4. `gh` が、`見張る PR:` の PR を `MERGED` と返す

そろわないときは `done` にせず、見張りの終わりの知らせも書かない。標準エラーに理由を 1 行出し、ほかは今の動作にする。ただし `MERGED` で、metadata の `pr_link_no_integration` が `pr_url` と同じ PR を指すときは、[done にしなかったときの知らせ](#done-にしなかったときの知らせ)を書く。依頼で見張りが `done` にすると伝えたので、黙って止まらないためである。

照合のデータを読めないときは、合わないときと分ける（[照合のデータを読めないとき](#照合のデータを読めないとき)）。

コメントや知らせを書く直前に、規則の一覧を読み直す。自分の規則の ID が変わっていれば書かずに 0 で終わり、次の確認で新しい規則から決め直す。規則の入れ直しのあとに、古い規則の時刻や回で書かないためである。

規則の作り手と `revision` は見ない。誰が規則を作り直しても、`done` にできるのは同じタスクの回で確認した PR がマージされたときだけだからである。マージした head も見ない。`done` の意味は連携があるときと同じく「タスクの PR がマージされた」で、head の照合はマージの依頼の前に `decide` とリーダーが行う。

#### 照合のデータを読めないとき

照合のデータを読めないことは、照合が合わないことと分ける。読めないときは、`done` にせず、知らせも書かず、規則を消さない。標準エラーに理由を 1 行出して 1 で終わり、次の 1 時間後の確認でもう一度照合する。一時の読み取りの失敗で規則を消すと、読めるようになっても `done` にできないためである。

| 照合で起きたこと | 扱い |
| --- | --- |
| 規則の指示を読めない。`見張る PR:` の値を検証する処理が失敗する | 読めない |
| タスクのコメントを読めない。`analyze` の出力や回の `対象の PR:` の行を読む処理が失敗する | 読めない |
| 名簿を読めない（`squad_cli_read_roster` が 1 で終わる） | 読めない |
| タスクの担当がスクワッドでないか、スクワッドが一覧にないかアーカイブ済み（同じく 2 で終わる） | 合わない |
| 規則の行が 1 つずつでない。回と認めない、今の回でない、`対象の PR:` の行がないか 2 つある | 合わない |
| `見張る PR:` が PR の URL の形でない。回の PR、`見張る PR:`、metadata が正規形で違う | 合わない |

`squad_cli_read_roster` は、読み取りの失敗で 1 を、担当のスクワッドがないと確認できたときに 2 を返す。2 は、名簿を読めた上で回の書き手を決められないので、合わないとして扱う。ほかの呼び手は、今のとおり 0 以外を失敗と扱う。

[見張りのあとのマージの知らせ](#見張りのあとのマージの知らせ)の照合も同じにする。読めないときは知らせを書かずに 1 で終わり、次の確認で試みる。合わないときは、今のとおり知らせを書かずに 0 で終わる。

[登録の照合](#登録の照合)で読めないときは、表の 3 行目（回を認められない）と同じにする。規則を作らないか、2 行を足さずに登録するので、読めない回で `done` にすることはない。

読めないことが続いても、照合の 4 つがそろわないので `done` にはならない。どの確認も 1 で終わるので、規則の指示のとおり、リーダーが記録のスレッドへ失敗を書く。

#### done にしなかったときの知らせ

連携なしの PR がマージされたのに照合が合わないときは、`done` にせず、人間に 1 回だけ知らせる。返信先と呼ぶ人間、同じ 1 行目のコメントがあれば書かないことと書けないときの終わり方は、[見張りのあとのマージの知らせ](#見張りのあとのマージの知らせ)と同じにする。本文は次のとおりにする。

```text
連携なしのリポジトリの PR がマージされましたが、見張りはタスクを `done` にしませんでした（<照合の理由>）。このタスクの成果をマージしたなら、タスクを `done` にしてください。PR: `<PR の URL>`
[@<呼ぶ人間の名前>](mention://member/<呼ぶ人間の ID>)
```

照合の理由は、標準エラーに出す 1 行と同じ文にする。人間が `done` を決めるので、合わない値で `done` にすることはない。

#### done の判定の入力

`done` の判定が読む入力と、判定に使わない入力を次に挙げる。どの入力も、変わったときに別の PR で `done` にしない。

| 入力 | 書ける人 | 登録の前後で変わりうるか | 変わったときに `done` にならない理由 |
| --- | --- | --- | --- |
| metadata の `pr_url` | PR を作った役、リーダー、人間 | 前も後も | 登録の前なら、回の PR と違うので規則を作らない。後なら、照合の 3 で合わない |
| metadata の `pr_link_no_integration` | スクリプト、役、人間 | 前も後も | 照合の 3 で `見張る PR:` と比べる。回の PR を指すように書いても、`done` にするのは回で確認した PR だけである |
| metadata の `pr_link_pending`・`pr_link_tried_at`・`ci_watch_thread` | スクリプト、役、人間 | 前も後も | `done` の判定に使わない。`ci_watch_thread` は知らせの返信先だけに使う |
| 規則の `見張る PR:` と `確認した回:` の行 | 規則を作れる人間とエージェント | 後（作り直し・置き換え） | 照合の 2 で、今の回でないか、回の `対象の PR:` と合わなければ止まる。今の回で確認した PR しか `done` にしない |
| 回のコメントの並び（新しい回） | 名簿のリーダーと `decide` の担当 | 後（再レビュー・PR の差し替え） | 新しい回が書かれると今の回が移り、前の回を指す規則は照合の 2 で止まる |
| 規則のコマンドの引数（リーダーの ID など） | 同じ | 後 | 回の判定に使わない。リーダーは名簿で読む |
| 規則の作り手・`revision`・`created_at` | サーバー | 後 | `done` の判定に使わない。`created_at` は知らせの時機だけに使い、照合と同じ 1 つの規則から読む |
| 回のコメントの書き手 | サーバー | 変わらない | 人間とスクワッドの外のエージェントのコメントは、回と認めない |
| 回のコメントの `対象の PR:` | 回を書いた名簿のリーダーか `decide` の担当 | 前も後も（書き手が直す） | 直すと照合の 2 か登録の 2 で合わない。回を書ける役は、今もマージの依頼を書く書き手である |
| 制御の記録（`前の回:` など） | 名簿のリーダーと `decide` の担当 | 前も後も | 回の判定は `decide` と同じで、記録が合わなければ回と認めない |
| 名簿（スクワッドのリーダーと役）とタスクの担当 | スクワッドとタスクを直せる人間 | 前も後も | 回の書き手が名簿から外れると回と認めず、`done` にしない |
| `gh` の PR の状態 | GitHub | 後 | `見張る PR:` の PR だけを読み、`MERGED` のときだけ進む |
| PR の head（マージの前の push） | PR に push できる人 | 後 | 判定に使わない。マージは人間が判断し、別の PR にはならない |
| タスクの状態 | 人間と役 | 前も後も | `done` と `cancelled` は先に止まる。ほかの状態では判定を変えない |
| 連携なしの記録（ホストのファイル） | ホストの同じユーザーの処理 | 前も後も | `done` の判定に使わない |
| PR のタイトル | PR を直せる人 | 後 | `done` の判定に使わない |

#### 時間の流れで変わる場面

入力が時間とともに変わる場面と、`done` にならない理由を次に挙げる。どの場面も、判定のたびに今の回をコメントから決め直し、決められなければ進めないことで止まる。

| 場面 | 止まる所 | 結果 |
| --- | --- | --- |
| 新しい回があるのに、前の回で登録する | 登録の照合の 2 | `紐付け: 古い回` の行を出し、規則を作らない |
| 登録のあとに、同じ PR で新しい回が書かれる | `done` の照合の 2 | `done` にしない。新しい回でマージを頼むとき、`decide` が登録し直す |
| PR を差し替えて新しい回が書かれたあと、前の PR がマージされる | `done` の照合の 2 と 3 | `done` にしない |
| 差し替えのあと、metadata・マーク・規則を前の PR と前の回にそろえ直す | 登録の照合の 2、`done` の照合の 2 | 新しい回が今の回なので、規則を作れず、`done` にもならない |
| 規則を入れ直す（`unlinked` の流し直し、人間やほかのエージェントの規則） | 1 つの規則の読み取りと、書く直前の読み直し | 古い規則の時刻や回で、`done` と知らせを書かない |
| リーダーが手でマージへ回す | 登録の照合 | `紐付け:` の行で止まり、マージを頼まない |
| 新しい回の途中で、人間がマージする | `done` の照合の 2 | `done` にせず、[done にしなかったときの知らせ](#done-にしなかったときの知らせ)を書く |
| 回のコメントを直す、名簿や担当が変わる | 判定のたびの読み直し | 今の回が変わるか回と認めず、`done` にしない |
| 72 時間の見張りのあとにマージする | 見張りがない | `done` にしない。71 時間の知らせで人間に頼んである |
| 見張りのあいだに、コメント・名簿・規則を一時読めない | [照合のデータを読めないとき](#照合のデータを読めないとき) | `done` も知らせもせず、規則を残す。読めるようになった確認で決め直す |
| 読めないことが 72 時間の見張りの終わりまで続く | 見張りがない | `done` にせず、終わりの知らせも書かない。各確認が 1 で終わり、リーダーが失敗を書いている |

## 見張りのあとのマージの知らせ

見張りが終わったあとにマージされた PR は、誰も `done` にしない。人間が `done` にすることを、見張りが終わる前に知らせる。知らせ方は、承認された案（見張りの最後の確認で人間をメンションして 1 回書く）のとおりに、この節に書く。

`unlinked-check` は、次の 4 つがそろった確認で、知らせのコメントを 1 回だけ書く。

1. PR がマージされていない、閉じていない
2. タスクが `in_review` で、紐付いていない
3. [done の照合](#done-の照合)の 1 から 3 がそろう
4. 自分の規則の作成時刻（`created_at`）から 71 時間を過ぎている。72 時間の見張りの、最後の確認に当たる

3 と 4 と本文の終わりの時刻は、[done の照合](#done-の照合)と同じ 1 つの規則から読み、書く直前に読み直す。3 のデータを読めないときは、知らせを書かずに 1 で終わる（[照合のデータを読めないとき](#照合のデータを読めないとき)）。

知らせは、今の `unlinked_link_stop` と同じく、metadata の `ci_watch_thread` のコメントへの返信で書く。同じ 1 行目のコメントがあれば書かない。本文は次のとおりにする。

```text
連携なしのリポジトリの PR のマージ待ちの見張りが、<規則の作成時刻 + 72 時間の UTC> に終わります。そのあとにマージしたときは、タスクを `done` にしてください。マージせずに閉じたときは、`done` にしません。PR: `<PR の URL>`
[@<呼ぶ人間の名前>](mention://member/<呼ぶ人間の ID>)
```

呼ぶ人間は、`decide` の人間を呼ぶコメントと同じく、リーダーのスクワッドの `creator_id` とメンバーの一覧から決める。`squad-review-next` の関数を共通の `squad-cli-lib` に移し、両方から呼ぶ。決められないときは、メンションの行を省いて書き、1 で終わる。規則の指示のとおり、リーダーが記録のスレッドへ失敗を書く。

## リーダーの手順と decide

`連携: なし` の行を、リーダーの手順と `decide` は「紐付いていない」と同じに読み、CI とコンフリクトを確認し、マージ待ちの見張りを登録する。違うのは、人間への依頼と知らせを出さないことだけである。

| 所 | 紐付いていない（今） | `連携: なし` が付く |
| --- | --- | --- |
| リーダーの紐付けの確認（`leader-pr-link.md`） | その場の確認を流して進める | 同じ |
| 紐付いていない PR を受け取ったときの知らせ（`leader-pr-ci.md`） | 1 つの投稿で知らせる | 知らせない。役の `連携なし:` の段落も写さない |
| マージの依頼に添える行（`leader-pr-link.md` の「連携なしの PR」と `decide`） | 紐付けか `done` を頼む行、見張りの行、`紐付けの失敗:` の写しと連携の案内 | 下の 1 行と見張りの行だけ |
| マージ以外で人間を呼ぶコメント（`leader-pr-merge.md` の「それ以外」の行と `leader-pr-link.md` の「連携なしの PR」。設計の承認、判断の依頼など） | 紐付けを頼む行、`紐付けの失敗:` の段落と連携の案内 | 添えない |
| 使用率の待ちで人間を呼ぶコメント（`decide`） | 紐付けを頼む行、`紐付けの失敗:` の段落と連携の案内 | 添えない |
| マージ待ちの見張りの登録（`unlinked`） | 登録する。失敗したら、見張りなしでマージを頼む | 登録する。失敗したら、マージを頼まずに止まる |

マージの依頼に添える 1 行は、次のとおりにする。人間に `done` を頼まず、見張りが `done` にすることを伝える。

```text
連携なしのリポジトリなので、マージのあとは見張りがマージを確認し、タスクを `done` にする。PR: `<PR の URL>`
```

`連携: なし` で見張りの登録に失敗したときは、マージを頼まない。見張りがないと、マージのあとに誰も `done` にしないためである。`decide` は何も書かず、次の行を出して 3 で終わる。

```text
次の依頼を決められません: 連携なしの PR の見張りを登録できない（squad-pr-watch unlinked が 0 以外で終わった）
```

リーダーは、マージを頼まず、ホストでセットアップを流し直すことを人間に頼む。この依頼にも、紐付けと `done` を頼む行は入れない。人間の返事で再開したら `decide` を流し直し、見張りを登録できてからマージを頼む。

`decide` は、`link-check` の行の末尾の `連携: なし` を読み、紐付いていない（`LINKED=false`）に加えて連携なしの印を持つ。読み方の表とテストは[テスト](#テスト)に書く。

### リーダーの参照の置き場所

連携なしのときのリーダーの手順は、`leader-pr-link.md` に新しく置く節「連携なしの PR」にまとめる。`leader-pr-merge.md` には、その節を指す 1 文だけを置く。場面「マージへ回す・人間を呼ぶ」の読む量を、[usage-reduction.md の大きさの上限](usage-reduction.md#大きさの上限)の 13,215 バイト以下に保つためである。上限は上げない。

`連携: なし` は、`link-check` の紐付けの判定の値である。[リーダーの参照の分け方](usage-reduction.md#リーダーの参照の分け方)では、場面の中で別の手順が要る値が出たら、その値を扱う場面の参照へ移る。連携なしの違いを、判定の表を持つ `leader-pr-link.md` に置くのは、この決まりに合わせるためである。

| 参照 | 置くもの |
| --- | --- |
| `leader-pr-merge.md` | 頭の 2 つの段落の次に、「`link-check` の行の末尾に `連携: なし` が付くときは、`leader-pr-link.md` の「連携なしの PR」も読み、従う。」の 1 文を置く。ファイル名は `leader-pr-link.md` へのリンクにし、連携なしの文と表の行はほかに置かない |
| `leader-pr-link.md` の「PR の紐付けの確認」 | 判定の表の `連携: なし` の行の末尾を、「下の「連携なしの PR」に従う」に直す |
| `leader-pr-link.md` の「連携なしの PR」 | `decide` が添える行と止まり方、手で `unlinked` が 0 以外で終わったときの扱い、マージを頼む 1 行と添えないもの。`leader-pr-merge.md` に足していた文は、意味を変えずに移す |

移すとき、`leader-pr-merge.md` の表の連携なしの 2 行は文に直す。表のまま移すと、見出しと区切りの行が 2 つの参照で重なり、分ける前の規則の行の数が合わなくなるためである。手で流す `unlinked` の段落の頭は、節の条件と重なる所を縮めてよい。ほかの文は、言い回しを変えずに移す。

1 文を足す大きさは、`leader-pr-merge.md` の「人間を呼ぶコメントに添える行」から、作業先と違うときと不正なときの段落を移して空ける。段落は、言い回しを変えずに `leader-pr-link.md` の判定の表の下へ移す。同じ決まりは判定の表の「作業先と違う」と「不正な `pr_url`」の行にもあるので、読む所が 1 つの参照にまとまる。`leader-pr-merge.md` の同じ節の「食い違いと未確認は、」は「食い違い・未確認・作業先と違う・不正は、」に直し、移した段落を読む所へ進ませる。

見込みの大きさは、`leader-pr-merge.md` が 13,160 バイト前後、`leader-pr-link.md` が 9,500 バイト前後である。`leader-pr-merge.md` は上限との差が 60 バイトに満たないので、このあと足す文はほかの参照に置く。

## セットアップの案内

セットアップは、リポジトリの候補が 0 件のときの案内だけを直す。質問と、ほかの案内は変えない。

今の案内（`lib/questions.sh`）は、ワークスペースへのリポジトリの紐付けを 3 つの手順で示し、手順書の節を名前で示して止まる。この手順を、登録の 2 つの選び方と、そのあとの確認に組み直す。

```text
ワークスペースのオーナーか管理者に、次のどちらかでリポジトリの登録を依頼してください。
A. GitHub 連携で許可する: ワークスペースの設定 → コードで GitHub 連携を設定し、このプロジェクトで使うリポジトリを許可します。自前サーバーで GitHub App が未設定なら、先にサーバーの管理者に GitHub 連携の準備を依頼します。
B. 連携を使わずに登録する: ワークスペースの管理者が multica repo add <リポジトリの URL> で登録すれば、候補に出ます。
どちらの場合も、導入先のサーバー・ワークスペースで multica repo list --output json を実行し、候補に出ることを確認してから、セットアップを流し直します。
```

止まるときの文が示す手順書の節の名前は、[README と手順書](#readme-と手順書)の直しに合わせる。

## README と手順書

README と手順書は、連携を導入の前提と書くのをやめる。連携があれば使えるものと、連携なしとの違い、人間が記録を消す手順を書く。

| 所 | 直すこと |
| --- | --- |
| README の受け取る人の準備 | 「GitHub 連携を許可したプロジェクトのリポジトリ」を、「ワークスペースに登録したプロジェクトのリポジトリ」にする。連携は手順書の節で示す |
| 手順書の受け取る人の準備 | 同じく、連携を前提から外す |
| 手順書の冒頭の流れの「受け取る人の準備」の項目 | 項目の終わりの「GitHub 連携をそろえる」を「リポジトリの登録をそろえる」にする |
| 手順書の「GitHub 連携とリポジトリの紐付け」 | 節の名前を「リポジトリの登録と GitHub 連携」にし、登録は連携か `multica repo add` で行えると書き、下の違いの表と記録を消す手順を足す。連携を前提とする段落（「GitHub 連携は、PR をタスクに紐付けるための前提である」）は、連携がなければ連携なしとして進むと書き直す |
| 手順書のセットアップの 0 件の案内 | セットアップの案内と同じ文にする |
| 手順書のセットアップの困ったときの表の、道具・ログイン・リポジトリが不足の行 | 「管理者の GitHub 連携」を、「リポジトリの登録（GitHub 連携か `multica repo add`）」にする |
| 手順書の「役の引き継ぎに「サーバーが PR を見つけられない」とあれば」の段落 | 困ったときの表の行に移す。`紐付けの失敗:` の段落は連携なしと記録されなかったときに出るので、案内は今のまま（連携を確認し、つないでからタスクの画面で PR の URL を指定して紐付ける）にする |
| 手順書の困ったときの表 | 役の引き継ぎに `連携なし:` の段落があるときの行を足す。連携なしとして記録されたことと、連携しているはずなら連携を確認して記録を消す手順を示す |

手順書に足す違いの表は、次の 3 行にする。

| 項目 | 連携あり | 連携なし |
| --- | --- | --- |
| タスクの画面の PR の欄 | PR が出る | 出ない。PR は metadata の `pr_url` とコメントで示す |
| マージのあとの `done` | 連携が `done` にする | マージ待ちの見張りが、72 時間まで 1 時間おきに確認して `done` にする。そのあとのマージは人間が `done` にする |
| CI とコンフリクトの確認 | 変わらない | 変わらない |

記録を消す手順は、記録のパスを示し、ホストで `rm` することと、消すと次の PR から 120 秒の待ちに戻ることを書く。連携を足したあとは、消さなくても、PR が 1 つ紐付けば自動で消えることも書く。

## 入力と信頼の表

この設計は、ホストのファイルと、役と人間が書ける metadata を読む。紐付けの API に Multica のトークンを使い、タスクの状態を書く。読む入力と信頼する条件は次のとおりである。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 連携なしの記録（`squad-pr-link` が書く。ホストの同じユーザーの処理と人間も書ける） | `squad-pr-link` の待つかの判定と、`link-check` の `連携: なし` の判定 | パスの各部分が検証を通り、記録とその上のディレクトリがシンボリックリンクでない普通のファイル。中身は読まない | ないものとして読み、今の動作にする。標準エラーに理由を 1 行出す |
| 記録のパスにあるファイル（ほかの実行も同時に作れる） | `squad-pr-link` が記録を結ぶとき | `pr_url` を書いたあと、自分の一時ファイルを `ln` で結べた | 結ばずに一時ファイルだけを消し、[記録があるとき](#記録があるとき)のとおりにする。ほかの実行が結んだ記録は書き換えず、消さない |
| `multica issue get` の `project_id`（サーバーが返す） | 記録のパス | 今の CLI の読み取りの検証を通り、パスの部分の検証を通る | 記録を読まず書かず、今の動作にする |
| PR の URL（PR を作った役が `squad-pr-link` に渡す） | 記録のパスのオーナーとリポジトリ | 今の URL の形の検証を通り、metadata の `repository` と小文字で同じ | 記録を読まず書かず、今の動作にする |
| 紐付けの API の応答の状態コード（サーバーが返す） | 記録を書くかの判定 | 期限を過ぎ、期限の直前の応答まで 404 だけが続いた（足す `PR_LINK_ALL_404`） | 記録を書かず、今の失敗の動作にする |
| metadata の `pr_url`（役と人間が書ける） | `unlinked` の登録 | 回の `対象の PR:` と正規形で同じ | 規則を作らず、`紐付け: 食い違い` の行を出す |
| metadata の `pr_url` と `pr_link_no_integration`（スクリプトと役が書く。人間も書ける） | `unlinked-check` の `done` と見張りの終わりの知らせの判定 | 2 つが、`見張る PR:` と正規形で同じ PR を指す。`gh` が `MERGED` を返す（知らせは、`MERGED` でも `CLOSED` でもない） | `done` にせず、知らせも書かず、今の動作にする |

| `unlinked` の引数の回（`decide` と手で流すリーダーが渡す） | `unlinked` の登録 | 名簿で回と認め、今の回である | 規則を作らず、`紐付け: 古い回` の行を出す |
| 回のコメント（名簿のリーダーと `decide` の担当が書く。コメントはほかの人も書ける） | 登録と `done` の照合の `対象の PR:` | 名簿で `squad_cli_control analyze` が回と認め、`対象の PR:` の行が 1 つだけある | 登録では規則を作らないか 2 行を足さない。`done` の判定では進めない |
| 名簿（サーバーが返す。スクワッドとタスクの担当を直せる人間が変えられる） | 回の判定のリーダーと最上位の役 | 今の `decide` と同じ読み取りの検証を通る | 読めないときは、`done` も知らせもせず、規則を残して 1 で終わる。担当のスクワッドがないと分かったときは、回と認めず、`done` にしない |

| スクワッドの `creator_id` とメンバーの一覧（サーバーが返す） | 知らせでメンションする人間 | 今の `decide` と同じ | メンションを省いて書き、1 で終わる |
| タスクの PR の一覧の `html_url`（サーバーが返す。自動の関連付けは、PR のタイトルを書いた人によらず起きる） | `squad-pr-link` の一覧の読み直しの判定 | 今の `issue-pull-requests` の読み取りの検証を通り、PR の URL と `link-check` と同じ比べ方で同じ | PR がないとして、今の失敗の動作にする |

PR のタイトルは、GitHub で PR を直せる人なら誰でも書ける。別のタスクの識別子を書くと、その PR が別のタスクに関連付くかもしれない。これは今の Multica の自動の関連付けと同じで、この設計はタイトルを判定に使わない。`squad-pr-link` が読むのは、自分のタスクの一覧に PR の URL があるかだけである。

記録と `pr_link_no_integration` を偽ってできるのは、待ちと警告と依頼を止めることだけである。`done` は、同じタスクの回で確認した PR を、`gh` がマージ済みと返したときにだけ書く。metadata や規則を別の PR に書き換えても、回の PR と合わないので `done` にしない（[done の判定の入力](#done-の判定の入力)）。記録を偽っても、紐付けを外したり、ほかのリポジトリへ書き込んだりはできない。

記録は GitHub への書き込みをしないので、書き込んでよいリポジトリの決まりとガードには触れない。トークンの扱いは、今の `squad-pr-link-lib` と同じく、標準入力から curl に渡し、出力と記録に出さない。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイルに手順を足す。足すのは、PR を作る役の `連携なし:` の段落とタイトルの識別子（`references/pr.md`）と、リーダーの `連携: なし` の分岐（`leader-pr-link.md`・`leader-pr-ci.md`・`leader-pr-merge.md`）である。

### 根拠

合意された要件による新しい機能なので、要件を合意したタスクを失敗の記録に代える。連携のないリポジトリで、PR ごとに待ちと警告と依頼が起きた経緯は、タスクのコメントにある。タイトルの識別子も、同じタスクで合意した要件である。

### 働いた跡

手順が働くと、記録を書いた PR のタスクに、役の引き継ぎの `連携なし:` の段落が残る。リーダーの分岐が働くと、マージの依頼に[添える 1 行](#リーダーの手順と-decide)が残る。跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 跡 | 形 | `pattern` | `author_type` |
| --- | --- | --- | --- |
| 役の知らせ | `kind: "comment"` | `(?m)^連携なし:` | `agent` |
| リーダーのマージの依頼 | `kind: "comment"` | `(?m)^連携なしのリポジトリなので、マージのあとは見張りが` | `agent` |

この跡は、連携のないリポジトリのタスクが 20 件の中にないと 0 回になる。0 回のときに削る候補にするかは、見直しで人間が判断する。

タイトルの識別子の手順が働くと、PR のタイトルの末尾に識別子が残り、自動で関連付いた PR はタスクの PR の一覧で `link_source` が `title` になる。どちらも[跡の形](procedure-review.md#跡の形)の 3 つの形では数えられないので、見直しでは跡のない手順になる。跡のない手順として人間が判断するとき、PR の一覧のタイトルで働いたかを読める。

### 仕組みにしない理由

判定・記録・試み直し・`done`・一覧の読み直しは、スクリプトの仕組みにした。手順に残るのは次の 3 つで、どれも仕組みにする案を比べ、選ばなかった。

- 役が知らせの段落を写すこと
- リーダーが依頼と知らせを出し分けること
- 役が PR のタイトルに識別子を入れ、直すたびに残すこと

| 案 | 選ばなかった理由 |
| --- | --- |
| `squad-pr-link` が、知らせをタスクへ直接投稿する | 役の実行はコメントで起きることが多く、スクリプトはきっかけのコメントを知らないので、根のコメントが拒否される。引き継ぎの段落なら、今の `紐付けの失敗:` と同じ置き場所で届く |
| `squad-pr-link` が、PR のタイトルに識別子がなければ `gh pr edit` で足す | 効くのは作った直後だけで、push のたびにタイトルを直すときに消えても見分けられない。識別子が抜けても明示の紐付けは働き、失うのは明示の紐付けが失敗したときの自動の関連付けだけである |
| リーダーの知らせとマージの依頼の行を、すべてスクリプトが書く | リーダーが手で書くマージの依頼は、ほかの理由で人間を呼ぶコメントと 1 つにまとめる決まりがあり、スクリプトが別に投稿すると 2 つに分かれる。`decide` の経路は、スクリプトが行を書く |

### 識別子の決まりの例外

識別子を PR の本文・コミットメッセージ・公開の設計に持ち出さない決まりは残し、PR のタイトルだけを例外にする。足す文は次のとおりで、どれも「PR のタイトルの識別子」の語を含める。

| ファイル | 足す文 |
| --- | --- |
| `references/pr.md` の識別子を持ち出さない項目 | PR のタイトルの識別子だけは例外とする |
| `references/pr.md` のタイトルを直す段落 | タイトルを直すときも、末尾の識別子は残す。PR のタイトルの識別子は、持ち出さない決まりの例外である |
| `CONTRIBUTING.md` | ただし、PR のタイトルには、Multica が PR をタスクに関連付けるため、タスクの識別子を入れる。PR のタイトルの識別子は、この決まりの例外とする |
| `STYLE.md` | タスクの識別子は、PR の本文と公開の文書に書かない。PR のタイトルの識別子だけは例外とし、置き方は `squad-handoff` の「PR を作る・実装を積む」に従う |
| `docs/procedure-review.md` | PR のタイトルの識別子は、この決まりの例外である |

`references/pr.md` に足すタイトルの項目は、次のとおりにする。

```markdown
- PR のタイトルの末尾に、半角の丸括弧でタスクの識別子（例: DEMO-12）を入れる。公開・非公開を問わず、`gh pr create` で作るときから入れる。Multica がタイトルの識別子で PR をタスクに関連付けるため。ブランチ名は変えない
```

この節のバッククォートの語は、紐付けの手順の検査（`tests/pr-link-procedure-check.py`）が種類を見る。鍵の種類の語は `pr_url` と `branch` だけにするので、識別子の例と読み取りの欄の名前はバッククォートで囲まない。足す行（`紐付いていました:` など）は、ラベルの種類として囲んでよい。

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと、見張りのスクリプト・共通スキル・リーダーの手順が替わる。替わったあと、連携のないリポジトリでは、最初の PR で 1 回だけ待ちと知らせが出て、次の PR から待ちと依頼が出なくなる。

| 利用者 | 変わること |
| --- | --- |
| 人間 | 連携なしのリポジトリでは、マージと設計の承認などの依頼から紐付けの依頼が消え、マージのあとの `done` もなくなる。72 時間の見張りのあとにマージしたときだけ、`done` にする |
| PR を作る役 | PR のタイトルの末尾に識別子を入れ、直すたびに残す。`squad-pr-link` が 0 で終わる行が 3 つ増え、`連携なしにしました:` のときに段落を 1 つ書く |
| 原本を変える人 | このリポジトリの PR のタイトルにも識別子が入る。識別子を持ち出さない決まりは、タイトルのほかは変わらない |
| リーダー | `link-check` の行の末尾に `連携: なし` が付くことがあり、そのときは知らせと依頼の行を出さない。見張りの登録に失敗したら、マージを頼まずにセットアップの流し直しを頼む |
| `decide` | マージの依頼と、使用率の待ちで人間を呼ぶコメントの行が、`連携: なし` のときに変わる。見張りの登録に失敗すると、マージを頼まずに 3 で終わる |
| マージ待ちの見張り | 連携なしの PR がマージされると、タスクを `done` にする。72 時間の最後の確認で、人間への知らせを 1 回書く |
| セットアップ | 候補が 0 件のときの案内の文だけが変わる |

エージェントとオートパイロットの登録は変わらない。役のひな形の形式と、拡張との契約も変わらない。

PR のタイトルは公開のリポジトリでも GitHub に出る。マージのコミットにもタイトルが入るので、既定のブランチの履歴に識別子が残る。識別子はタスクの番号だけで、タスクの中身は Multica の権限がないと読めない。

記録はホストごとにある。同じプロジェクトを別のホストでも動かすと、ホストごとに最初の PR で 1 回待つ。流し直す前に作った紐付いていない PR は、記録ができるまで今の動作のままである（[進行中の PR の扱い](#進行中の-pr-の扱い)）。

スクリプトは、セットアップが同じ実行でまとめて置き換える。共通スキルとリーダーの手順も同じ実行で替わる。古い手順が `連携: なし` の付く行を読んでも、先頭は今と同じなので「紐付いていない」と読み、今の依頼を出す。

### 変更の知らせ

この変更の知らせは、バージョンを上げる PR が、`CHANGELOG.md` に次の文で足す（[release.md の変更の知らせ](release.md#変更の知らせ)の決まり）。役の判断とスクリプトの動作が変わることと、ホストに記録が増えることを、更新の前に読めるようにするため。

登録が変わらないと書く文は、同じ節のほかの変更と食い違わないよう、「この変更では」とこの変更の範囲に限る。

```markdown
GitHub 連携のないリポジトリで、PR の紐付けを待たずに進めるようにした。作った直後の紐付けが 120 秒のあいだ見つからないで終わると、そのリポジトリをホストに「連携なし」と記録し、タスクに 1 回だけ知らせる。流し直しで、見張りのスクリプト、共通スキル、リーダーの手順が替わる。

連携なしのリポジトリでは、紐付けの待ちと警告と依頼を出さず、マージ待ちの見張りがマージを確認してタスクを `done` にする。PR が 1 つでも紐付くと記録が消え、連携ありの動作に戻る。この変更では、エージェントとオートパイロットの登録は変わらない。

- 連携のあるリポジトリでも、サーバーの同期が 120 秒より遅れると、一度は連携なしとして扱われる。次に PR が紐付くと戻る
- 72 時間の見張りのあとにマージした PR は、人間がタスクを `done` にする
- PR を作る役は、PR のタイトルの末尾にタスクの識別子を入れる。連携のあるリポジトリでは、サーバーがタイトルから PR をタスクに自動で関連付ける。PR の本文とコミットメッセージには、今のとおり識別子を入れない
- `squad-pr-link` は、紐付けに失敗したとき、タスクの PR の一覧を読み直す。PR がすでに紐付いていれば、警告を出さず、連携なしの記録も消す
- 記録はホストのエージェントのホームの下にあり、人間が消せる。手順は手順書の「リポジトリの登録と GitHub 連携」にある
- README と手順書は、GitHub 連携を導入の前提としなくなった。セットアップは、候補が 0 件のときに `multica repo add` での登録を案内する
```

## テスト

連携なしは、偽の `multica` と偽の curl と偽の `gh` で模し、記録の根は `PR_LINK_STATE_ROOT` で一時ディレクトリに向ける。今のテストにも、この根を空の一時ディレクトリに向ける 1 行を足し、ホストの記録が結果を変えないようにする。

今の `squad-pr-link-test.sh` のうち、120 秒のうちに紐付く場面（試み直しの 200 と遅い成功）は、入力も期待も変えない。受け入れ条件 11 の場面は、これに当たる。

## 残る危うさ

- サーバーは、連携がないときと同期が遅れたときに同じ 404 を返すと、公開のソースから読んでいる。実機では確認していない
- 同期が 120 秒より遅れた連携ありのリポジトリは、一度は連携なしの扱いになり、次に PR が紐付くまで待ちと依頼が出ない
- 連携ありのリポジトリが連携なしの扱いのあいだは、紐付いていない PR の `done` を見張りが行う。サーバーの同期が追いつけば、試み直しで紐付き、記録が消える
- 連携を外したリポジトリは、120 秒の待ちが 404 で終わるまで連携ありの扱いのままで、1 つ目の PR で今の待ちが 1 回起きる
- 記録はホストごとにあるので、同じプロジェクトを複数のホストで動かすと、ホストごとに最初の PR で待つ
- 記録はホストの同じユーザーの処理なら書ける。偽の記録で止まるのは待ちと警告と依頼で、マージしていない PR を `done` にはしない
- 回を書けるリーダーと `decide` の担当は、別の PR を対象にした回を書けば、その PR のマージで `done` にしうる。どちらも今マージの依頼を書く書き手で、この設計で増える書き手ではない
- PR を差し替えたあと、新しい回が書かれるまでは前の回が今の回のままになる。このあいだに metadata を前の PR に戻し、人間が前の PR をマージすると `done` になるが、今の回で確認し最新のマージの依頼が指す PR のマージでしか `done` にしない
- 今の回のコメントを消せるのは、回の書き手とワークスペースの管理者である。消すと前の回が今の回に戻るが、消せる人は回を書ける信頼する書き手の範囲と同じである
- 作成が早い偽の規則があると、それを自分の規則として読み、照合が合わずに `done` にしない。人間が `done` にするまで `in_review` のままになる
- 見張りのあいだに名簿やタスクの担当が変わると、回を認められず `done` にしない
- コメントや名簿を読めないことが 72 時間の見張りの終わりまで続くと、`done` にならず、終わりの知らせも出ない。残るのは、確認のたびにリーダーが書く失敗の記録だけである
- マージの依頼のあとに push してからマージしても、`done` にする。連携があるときと同じく、マージした中身は人間が判断する
- 72 時間の見張りのあとにマージした PR は、人間が `done` にするまで `in_review` のままになる。見張りの終わりの知らせを読み落とすと、そのまま残る
- 見張りの規則の登録が失敗すると、セットアップを流し直すまでマージを頼めない。そのあいだ PR はマージ待ちにならない
- マークを書けない状態が続くと、`連携: なし` が付かず、今の紐付けと `done` の依頼が出る
- 記録の消去と作成が同時に起きると、どちらが残るかは順による。進行中の PR はマークで進むが、次の PR の待ちは残ったほうに従う
- `multica repo add` で登録したリポジトリが、連携のないサーバーで選べてセットアップが通るかは、実機で確認していない。マージの前に人間が確認する
- `squad-dependabot-merge` の紐付けは記録を読まず書かないので、連携なしのリポジトリでも今の待ちが続く
- サーバーがタイトルのどの形の識別子を読むかを、実機で確認していない。末尾の丸括弧の中を読まないときは、自動の関連付けが効かず、今の明示の紐付けだけで動く
- 自動の関連付けのあとに明示の紐付けを呼んだときの、API の応答と `link_source` の値を確認していない。200 でなければ一覧の読み直しで補うが、`link_source` が `manual` に替わると、自動の関連付けを確認できない
- タイトルを直すときに識別子を消しても、明示の紐付けがあるので失敗にならず、誰も気づかない
- タイトルの識別子の手順は、跡の形で数えられず、見直しで跡のない手順になる
- マージのコミットにタイトルが入り、公開のリポジトリの既定のブランチの履歴に識別子が残る

なし

## 検討した案

記録の置き場所と見分け方・知らせの出し方・`done` の判定・試み直しの間隔で、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| 連携の状態を API で読む | メンバーが読める一覧では、リポジトリが連携の許可に含まれるかが分からない。リポジトリの一覧は管理者しか読めない |
| 記録をタスクやプロジェクトの metadata に置く | タスクの metadata は PR ごとに別で、次の PR に効かない。プロジェクトの metadata を書く CLI と約束がなく、役と人間がどこからでも書ける |
| 記録を、404 以外の失敗でも書く | 通信の失敗やサーバーの一時的な失敗で、連携のあるリポジトリを連携なしにしてしまう |
| 記録の判定に、今の `PR_LINK_NOT_FOUND` を使う | 期限を過ぎれば、直前の応答が通信の失敗や 500 でも 1 になる。一時的な障害で、リポジトリ全体を連携なしにしてしまう |
| 記録を、一時ファイルからの `mv` で置く | `mv` は記録のパスがあっても上書きするので、同時に待ち切れた実行がどちらも知らせを出す。片方の失敗の取り消しで、もう片方の記録も消せる |
| `連携: なし` を、記録があるかだけで読む | 別の PR が紐付いて記録が消えると、進行中の PR に紐付けと `done` の依頼が戻る |
| 見張りの登録に失敗したら、マージの依頼に `done` を頼む行を足す | 受け入れ条件の、連携なしのリポジトリで `done` を頼まない決まりに合わない |
| `squad-pr-link` が、知らせをタスクへ直接投稿する | 役の実行はコメントで起きることが多く、スクリプトはきっかけのコメントを知らないので、根のコメントが拒否される |
| 記録があるときも `squad-pr-link` を 1 で終わらせ、役に `紐付けの失敗:` の段落を書かせる | 段落が警告として残り、リーダーが知らせと依頼を出す。要件の「警告を出さない」に合わない |
| 試み直しの間隔を、記録を書かないかわりに毎回呼ぶ形にする | マージ待ちの見張りが 1 時間ごとに API を呼び、試み直しの間隔（6 時間）を変えることになる。間隔は要件の範囲の外である |
| 間隔の時刻を、ホストのファイルに置く | タスクごとの時刻をホストに増やし、ホストが替わると読めない。metadata なら、どのホストの見張りからも読める |
| `done` にするかを、記録があるかで読む | マージの依頼のあと、別の PR が紐付いて記録が消えると、`done` を頼まなかった PR を誰も `done` にしない |
| 紐付いていない PR は、連携の有無によらず見張りが `done` にする | 連携ありのリポジトリの動作を変える。今は人間に紐付けを頼んでおり、要件の「連携ありの動作は変えない」に合わない |
| 見張りのあとの知らせを、マージの依頼の中に「72 時間のあとにマージしたら `done` にしてほしい」と書く | 受け入れ条件の、マージの依頼に `done` を頼む行を入れない決まりに合わない |
| 見張りのあとの知らせを出さず、手順書にだけ書く | 72 時間を過ぎてマージした人間が、`done` を忘れても気づけない |
| 見張りの長さを延ばす | 要件で、見張りの間隔と長さは変えないと決めている |
| 今の回を、最新のマージの依頼のコメントの `前の回:` で決める | 登録は依頼を書く前に流すので、登録のときに依頼がない。依頼の `前の回:` は、認める最新の回と同じになる |
| 今の回を、metadata か規則に残した値で決める | その値は人間と役が書き換えられ、前の回と前の PR にそろえ直せる。今の回は、書き手を選べるコメントだけから決める |
| 照合が合わずにマージされたとき、黙って止まる | 依頼で見張りが `done` にすると伝えてあり、人間が気づかないまま `in_review` に残る |
| 終わりの知らせの時刻を、登録時に metadata や回のコメントへ残し、毎時の確認では規則の一覧を読まない | その値は人間と役が書き換えられ、時機を動かせる。信頼できる時刻は、サーバーが返す規則の `created_at` だけである |
| `squad-pr-link` が、紐付けの前にも一覧を読む | サーバーが PR を知っていれば紐付けの API が成功するので、前に読んでも結果は変わらない。成功の経路の呼び出しが増え、今のテストを変えずに通せなくなる |
| 紐付けの 404 の待ちのあいだも、10 秒ごとに一覧を読む | 404 はサーバーが PR を知らないことを示し、そのあいだは一覧にも出ないと読める。待ちの終わりに 1 回読めば足りる |
| 識別子をタイトルの先頭に置く | 先頭の種類（`feat:` など）で変更の種類を読む今の決まりを崩す |
| 識別子をブランチ名に入れる | ブランチ名は Multica の checkout が決め、要件で変えないと決めている |
| PR のタイトルの識別子を、公開のリポジトリでは入れない | 要件で、公開・非公開を問わず入れると決めている。公開のリポジトリでも、連携があれば自動の関連付けが効く |
| `squad-dependabot-merge` も記録を読む | Dependabot の PR の回し方は、今も次の回で試み直しており、要件の範囲の外である。動作を変えると、回し方の確認をやり直す必要がある |
