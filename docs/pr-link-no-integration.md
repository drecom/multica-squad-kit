# GitHub 連携のないリポジトリで、PR の紐付けを待たずに進める

GitHub 連携のないリポジトリでは、サーバーが PR を見つけられず、PR ごとに待ちと警告と人間への依頼が起きる。この設計では、作った直後の紐付けが 404 で待ち切れたリポジトリを、ホストに「連携なし」と記録する。記録のあるリポジトリの PR では、待ちと警告と依頼を出さず、マージ待ちの見張りがマージを確かめてタスクを `done` にする。

この文書は、記録の形と置き場所、`squad-pr-link` と `squad-pr-watch` の動作、知らせの文と出す役を書く。リーダーの手順と `decide` の扱い、セットアップの案内、README と手順書の直しも書く。それぞれの理由も添える。

## 目的と範囲

今は、連携のないリポジトリでも、PR を作るたびに次が起きる。PR を作った役が 120 秒待って警告を残し、リーダーが連携の確認と紐付けを人間に頼み、試み直しの記録がタスクに増える。マージのあとは、人間がタスクを `done` にする。README・手順書・セットアップの案内は、連携を導入の前提にしている。

目的は次の 4 つである。

1. 連携のないリポジトリを、紐付けの結果から見分けて記録する。連携の状態は API で読まない
2. 記録のあるリポジトリの PR では、120 秒の待ち、紐付けの警告と依頼、紐付かなかった試み直しの記録を出さない
3. 記録のあるリポジトリの PR は、マージ待ちの見張りがマージを確かめて `done` にする
4. 連携のあるリポジトリは、1 つでも紐付けば記録を消し、今の動作に戻す

次は対象にしない。

- 連携なしの PR を、タスクの画面の PR の欄に出すこと。サーバーが PR を持てないため、PR の場所は metadata の `pr_url` とコメントで示す
- 連携の状態を API で読むこと、セットアップの質問で連携の有無を尋ねること
- 120 秒の待ちの長さと、[試み直し](pr-link-retry.md)の時機と間隔
- CI とコンフリクトの確認
- `squad-dependabot-merge` の紐付け。扱いは[検討した案](#検討した案)に書く

## 連携なしの記録

記録は、ホストのエージェントのホームの下に、プロジェクトとリポジトリごとに 1 つのファイルで置く。ファイルがあることだけを「連携なし」と読み、中身は人間が読むためだけに書く。

### 置き場所と形

置き場所は次のパスにする。使用率の確認の状態（`squad-usage-check`）と同じ根の下に置き、セットアップの流し直しで消えないようにする。

```text
${PR_LINK_STATE_ROOT:-$HOME/.multica-agent/template/pr-link}/<プロジェクトの ID>/<オーナー>/<リポジトリ>
```

- プロジェクトの ID は、タスクの読み取り（`multica issue get`）の `project_id` を使う。タスクにプロジェクトがないときは、記録を書かず読まず、今の動作のままにする
- オーナーとリポジトリは、PR の URL から取り、小文字にする。metadata の `repository` との照合も小文字で行う
- 各部分は、`squad-usage-check` と同じく、空・`.`・`..`・英数字と `_.-` 以外の文字を含むものを断る。断ったときは記録を書かず、ないものとして読む
- ディレクトリは 700、ファイルは 600 で作る。ファイルは同じディレクトリの一時ファイルに書いてから `mv` で置き、書きかけを読ませない

中身は次の 4 行にする。判定には使わない。

```text
repository: <オーナー>/<リポジトリ>
pr: <記録のきっかけになった PR の URL>
task: <タスクの識別子>
記録した時刻: <UTC の YYYY-MM-DDTHH:MM:SSZ>
```

記録のパスかその上のプロジェクトとオーナーのディレクトリがシンボリックリンクなら、記録はないものとして読み、書きも消しもしない。普通のファイルでないもの（ディレクトリなど）も同じにする。どちらも標準エラーに 1 行だけ理由を出す。

### 書く時機と消す時機

記録を書くのは `squad-pr-link` だけで、作った直後の紐付けが 120 秒のあいだ 404 で終わったときに限る（[記録がないとき](#記録がないとき)）。通信の失敗、404 以外の応答、トークンや API の環境がないとき、作業先が PR のリポジトリと違うときは書かない。

記録を消すのは、そのプロジェクトとリポジトリの PR が紐付いたと分かったときである。分かる所は次の 2 つにする。

| 所 | 消す条件 |
| --- | --- |
| `squad-pr-link` | 記録があり、1 回の試みが 200 を返して `pr_url` を書けた |
| `squad-pr-watch link-check` | 判定が「紐付いている」で、そのタスクのプロジェクトとリポジトリの記録がある。きっかけは試み直しに限らない |

人間が消すときは、手順書の手順で、ホストのファイルを消す。消すと、次の PR から今の 120 秒の待ちに戻る。

## squad-pr-link の動作

`squad-pr-link` は、タスクを読んだあと、作業先が PR のリポジトリと同じで、プロジェクトの ID があるときに記録を読む。記録の有無で、次の 2 つに分かれる。どちらでもないとき（作業先が違う、プロジェクトがない）は、今の動作のままにする。

### 記録がないとき

今と同じく 120 秒まで待つ。404 で待ち切れたとき（`PR_LINK_NOT_FOUND=1`）だけ、次の順で連携なしに切り替える。

1. 記録を書く。書けなければ、今と同じ警告を出して 1 で終わる
2. metadata の `pr_url`・`pr_link_pending`・`pr_link_no_integration` に PR の URL を書く。ほかの 2 つは書けなくても続ける
3. `pr_url` を書けなければ、1 の記録を消し、今と同じ警告を出して 1 で終わる
4. 標準出力に次の 2 行を出し、0 で終わる。標準エラーには何も出さない

```text
連携なしにしました: <タスクの識別子> <PR の URL>
<知らせの文>
```

知らせの文は[知らせ](#知らせ)に書く。0 で終わるので、PR を作った役は今の決まりのとおり metadata の `branch` だけを書く。`pr_url` はスクリプトが書いている。

404 以外で失敗したときは、今の動作（警告、マーク、1 で終わる）を変えない。

### 記録があるとき

待たずに、紐付けの API を 1 回だけ呼ぶ（`pr_link_request_once`、時間切れ 30 秒）。呼ぶ前に、API の環境を確認する。

| 結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| 200 | 今と同じく `pr_url` を書き、記録を消す | `紐付けました: <タスクの識別子> <PR の URL>` | 0 |
| ほかの応答、通信の失敗、API の環境がない | `pr_url`・`pr_link_pending`・`pr_link_no_integration` に PR の URL を書く | `紐付けていません（連携なし）: <タスクの識別子> <PR の URL>` | 0 |
| 上の行で `pr_url` を書けない | 今と同じ警告を標準エラーに出す | なし | 1 |

`pr_url` がすでにあるときは、今と同じく API を呼ばずに `紐付けていません:` の行を出す。記録の有無で変えない。

PR を作る役には、どちらの 0 も今の成功と同じに読ませる。`紐付けていません（連携なし）:` のときは、引き継ぎに何も足さない。

## 知らせ

知らせは、記録を書いたときに、その PR のタスクへ 1 回だけ出す。出すのは PR を作った役で、引き継ぎのコメントに段落として入れる。

`squad-pr-link` は、記録を書いた実行の標準出力の 2 行目に、次の文を 1 行で出す。

```text
<オーナー>/<リポジトリ> を、このプロジェクトでは GitHub 連携なしとして扱います。サーバーが 120 秒待っても PR を見つけなかったためです。このあとの PR では紐付けを待たず、紐付けの警告と依頼を出さず、マージ待ちの見張りがマージを確かめてタスクを done にします。連携しているはずなら、ワークスペースの設定のコードの画面で <オーナー>/<リポジトリ> がつながっていることを確認してください。このリポジトリの PR が 1 つでも紐付けば、自動で連携ありの扱いに戻ります。
```

PR を作る役は、1 行目が `連携なしにしました:` のとき、引き継ぎの成果物の PR の URL のすぐ下に、次の段落を置く。今の `紐付けの失敗:` の段落と同じ置き場所で、`紐付けの失敗:` の段落は置かない。

```text
連携なし: <標準出力の 2 行目>
```

役が段落を書き漏らしても、記録とマークは残り、動作は変わらない。知らせが出ないだけである。リーダーは段落を写し直さず、別の知らせも出さない。段落を出す役を 1 つにして、同じ知らせが重ならないようにするため。

スクリプトがタスクへ直接投稿する案は選ばなかった。理由は[検討した案](#検討した案)に書く。

## link-check の動作

`squad-pr-watch link-check` は、今の判定のあと、タスクのプロジェクトとリポジトリの記録を読む。記録があり、判定が「紐付いていない」のときだけ、行の末尾に `連携: なし` を足す。

```text
紐付け: 紐付いていない pr: <PR の URL> 連携: なし
```

行の先頭は今と同じである。`紐付け: 紐付いていない` で始まるかで読む今の分岐（`decide`・`unlinked-check`・リーダーの手順）は、そのまま CI とコンフリクトを確認する。`decide` は `pr:` の次の語だけを URL として読んでおり、末尾を足しても URL は変わらない。

`連携: なし` を出すとき、metadata の `pr_link_no_integration` が PR の URL と違えば、PR の URL を書く。書けなくても、出力の行は変えない。

判定が「紐付いている」で記録があれば、記録を消す。

### 試み直しと記録を出さない方法

記録があるときも、試み直す条件（マークが `pr_url` と同じ PR を指し、紐付いた一覧が空で、作業先が同じ）と時機は今と同じにする。変えるのは、紐付かなかった試み直しの記録をタスクに書かないことと、間隔の測り方だけである。

| 試み直しの結果 | 記録がないとき（今） | 記録があるとき |
| --- | --- | --- |
| `紐付いた` | 記録を書く | 記録を書き、連携なしの記録を消す |
| それ以外（`一覧にない（200）`・`見つからない（404）`・`失敗…`・`未確認…`・`食い違い`） | 記録を書く | 書かない |

試み直しの間隔は、今は前の `紐付けの試み直し:` の記録の時刻から測る。記録を書かないと間隔が測れず、`link-check` のたびに API を呼ぶ。そこで、記録があるときは、API を呼ぶたびに metadata の `pr_link_tried_at` に UTC の時刻（`YYYY-MM-DDTHH:MM:SSZ`）を書く。

間隔は、前の記録の時刻と `pr_link_tried_at` のうち新しいほうから測る。`pr_link_tried_at` が形に合わないか、今より後の時刻なら、ないものとして読む。書けなくても、出力の行は変えない。間隔の値（リーダーの確認の 5 分、マージ待ちの見張りの 6 時間）は変えない。

一度紐付いたかの判定（`紐付いた` か `紐付いていた` の記録があるか）は、今と同じくコメントの記録で読む。紐付いた記録は、記録があるときも書くためである。

## マージ待ちの見張りの done

`unlinked-check` は、PR がマージされたことを `gh` で確かめ、連携なしの PR ならタスクを `done` にする。連携なしの PR かは、metadata の `pr_link_no_integration` が `pr_url` と同じ PR を指すかで読む。記録ではなく metadata で読むのは、マージの依頼のあとに記録が消えても、依頼に `done` の行を入れなかった PR を `done` にするためである。

今の `unlinked-check` は、PR の状態が `MERGED` か `CLOSED` なら規則を消して止まる。この分岐を次のように分ける。ほかの順と判定は変えない。

| PR の状態 | `pr_link_no_integration` | すること |
| --- | --- | --- |
| `MERGED` | `pr_url` と同じ PR | `multica issue status <タスク> done` を流し、規則を消して `止めた: PR がマージされたので、タスクを done にした` を記録する |
| `MERGED` | ないか違う PR | 今と同じく `止めた: PR がマージ済みか閉じている` |
| `CLOSED` | どちらでも | 今と同じく止まる。`done` にしない |

`done` にできなかったときは、規則を消さず、標準エラーに理由を出して 1 で終わる。規則の指示のとおり、リーダーが記録のスレッドへ失敗を書き、次の 1 時間後の確認でもう一度試みる。

この分岐は、今の順のとおり、タスクの状態が `in_review` かを見る前に置く。マージは事実なので、マージのあとに人間が状態を変えていても `done` にする。`done` と `cancelled` のタスクは、今と同じく先に止まる。

見張りの間隔（1 時間）と長さ（72 時間）、登録の時機は変えない。

## 見張りのあとのマージの知らせ

見張りが終わったあとにマージされた PR は、誰も `done` にしない。人間が `done` にすることを、見張りが終わる前に知らせる。知らせ方は[決まっていないこと](#決まっていないこと)にあり、承認まではこの節の案のとおりに作る。

`unlinked-check` は、次の 4 つがそろった確認で、知らせのコメントを 1 回だけ書く。

1. PR がマージされていない、閉じていない
2. タスクが `in_review` で、紐付いていない
3. `pr_link_no_integration` が `pr_url` と同じ PR を指す
4. 自分の規則の作成時刻（`created_at`）から 71 時間を過ぎている。72 時間の見張りの、最後の確認に当たる

知らせは、今の `unlinked_link_stop` と同じく、metadata の `ci_watch_thread` のコメントへの返信で書く。同じ 1 行目のコメントがあれば書かない。本文は次のとおりにする。

```text
連携なしのリポジトリの PR のマージ待ちの見張りが、<規則の作成時刻 + 72 時間の UTC> に終わります。そのあとにマージしたときは、タスクを `done` にしてください。マージせずに閉じたときは、`done` にしません。PR: `<PR の URL>`
[@<呼ぶ人間の名前>](mention://member/<呼ぶ人間の ID>)
```

呼ぶ人間は、`decide` の人間を呼ぶコメントと同じく、リーダーのスクワッドの `creator_id` とメンバーの一覧から決める。`squad-review-next` の関数を共通の `squad-cli-lib` に移し、両方から呼ぶ。決められないときは、メンションの行を省いて書き、1 で終わる。規則の指示のとおり、リーダーが記録のスレッドへ失敗を書く。

## リーダーの手順と decide

`連携: なし` の行を、リーダーの手順と `decide` は「紐付いていない」と同じに読み、CI とコンフリクトを確認し、マージ待ちの見張りを登録する。違うのは、人間への依頼と知らせを出さないことだけである。

| 所 | 紐付いていない（今） | `連携: なし` が付く |
| --- | --- | --- |
| リーダーの紐付けの確認（`leader-pr-link.md`） | その場の確認を流して進める | 同じ |
| 紐付いていない PR を受け取ったときの知らせ（`leader-pr-ci.md`） | 1 つの投稿で知らせる | 知らせない。役の `連携なし:` の段落も写さない |
| マージの依頼に添える行（`leader-pr-merge.md` と `decide`） | 紐付けか `done` を頼む行、見張りの行、`紐付けの失敗:` の写しと連携の案内 | 下の 1 行と見張りの行だけ |
| 使用率の待ちで人間を呼ぶコメント（`decide`） | `紐付けの失敗:` の段落と連携の案内 | 添えない |
| マージ待ちの見張りの登録（`unlinked`） | 登録する | 同じ |

マージの依頼に添える 1 行は、次のとおりにする。人間に `done` を頼まず、見張りが `done` にすることを伝える。

```text
連携なしのリポジトリなので、マージのあとは見張りがマージを確かめ、タスクを `done` にする。PR: `<PR の URL>`
```

見張りの登録に失敗したときは、今の「見張りを登録できませんでした」の行のあとに、マージのあとにタスクを `done` にしてほしいと 1 行足す。見張りがないと、誰も `done` にしないためである。

`decide` は、`link-check` の行の末尾の `連携: なし` を読み、紐付いていない（`LINKED=false`）に加えて連携なしの印を持つ。読み方の表とテストは[テスト](#テスト)に書く。

## セットアップの案内

セットアップは、リポジトリの候補が 0 件のときの案内だけを直す。質問と、ほかの案内は変えない。

今の案内（`lib/questions.sh`）は、ワークスペースへのリポジトリの紐付けを 3 つの手順で示し、手順書の節を名前で示して止まる。手順に、次の文を足す。

```text
GitHub 連携がなくても、ワークスペースの管理者が multica repo add <リポジトリの URL> で登録すれば、候補に出ます。
```

止まるときの文が示す手順書の節の名前は、[README と手順書](#readme-と手順書)の直しに合わせる。

## README と手順書

README と手順書は、連携を導入の前提と書くのをやめる。連携があれば使えるものと、連携なしとの違い、人間が記録を消す手順を書く。

| 所 | 直すこと |
| --- | --- |
| README の受け取る人の準備 | 「GitHub 連携を許可したプロジェクトのリポジトリ」を、「ワークスペースに登録したプロジェクトのリポジトリ」にする。連携は手順書の節で示す |
| 手順書の受け取る人の準備 | 同じく、連携を前提から外す |
| 手順書の「GitHub 連携とリポジトリの紐付け」 | 節の名前を「リポジトリの登録と GitHub 連携」にし、登録は連携か `multica repo add` で行えると書く。連携を前提とする文を消し、下の違いの表と記録を消す手順を足す |
| 手順書のセットアップの 0 件の案内 | セットアップの案内と同じ文にする |
| 手順書の困ったときの表の、サーバーが PR を見つけられない行 | 連携なしとして扱われたことと、連携しているはずなら記録を消す手順を示す |

手順書に足す違いの表は、次の 3 行にする。

| 項目 | 連携あり | 連携なし |
| --- | --- | --- |
| タスクの画面の PR の欄 | PR が出る | 出ない。PR は metadata の `pr_url` とコメントで示す |
| マージのあとの `done` | 連携が `done` にする | マージ待ちの見張りが、72 時間まで 1 時間おきに確かめて `done` にする。そのあとのマージは人間が `done` にする |
| CI とコンフリクトの確認 | 変わらない | 変わらない |

記録を消す手順は、記録のパスを示し、ホストで `rm` することと、消すと次の PR から 120 秒の待ちに戻ることを書く。連携を足したあとは、消さなくても、PR が 1 つ紐付けば自動で消えることも書く。

## 入力と信頼の表

この設計は、ホストのファイルと、役と人間が書ける metadata を読む。紐付けの API に Multica のトークンを使い、タスクの状態を書く。読む入力と信頼する条件は次のとおりである。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 連携なしの記録（`squad-pr-link` が書く。ホストの同じユーザーの処理と人間も書ける） | `squad-pr-link` の待つかの判定と、`link-check` の `連携: なし` の判定 | パスの各部分が検証を通り、記録とその上のディレクトリがシンボリックリンクでない普通のファイル。中身は読まない | ないものとして読み、今の動作にする。標準エラーに理由を 1 行出す |
| `multica issue get` の `project_id`（サーバーが返す） | 記録のパス | 今の CLI の読み取りの検証を通り、パスの部分の検証を通る | 記録を読まず書かず、今の動作にする |
| PR の URL（PR を作った役が `squad-pr-link` に渡す） | 記録のパスのオーナーとリポジトリ | 今の URL の形の検証を通り、metadata の `repository` と小文字で同じ | 記録を読まず書かず、今の動作にする |
| 紐付けの API の応答の状態コード（サーバーが返す） | 記録を書くかの判定 | 120 秒のあいだ 404 だけが続いた（今の `PR_LINK_NOT_FOUND`） | 記録を書かない |
| metadata の `pr_link_no_integration`（スクリプトが書く。役と人間も書ける） | `unlinked-check` の `done` と見張りの終わりの知らせの判定 | `pr_url` と正規形で同じ PR を指し、`gh` が `MERGED` を返す（知らせは、`MERGED` でも `CLOSED` でもない） | `done` にせず、知らせも書かず、今の動作にする |
| metadata の `pr_link_tried_at`（スクリプトが書く。役と人間も書ける） | 試み直しの間隔 | `YYYY-MM-DDTHH:MM:SSZ` の形で、今より後でない | ないものとして読み、間隔をコメントの記録だけで測る |
| `gh` の PR の状態（GitHub が返す） | `done` にするかの判定 | 今の `gh-pr-mergeable` の読み取りの検証を通る | 今と同じく状態を読めないとして扱い、`done` にしない |
| 見張りの規則の `created_at`（サーバーが返す） | 見張りの終わりの知らせの時機 | 今の `issue-wakeups` の読み取りの検証を通り、時刻として読める | 知らせを書かない |
| スクワッドの `creator_id` とメンバーの一覧（サーバーが返す） | 知らせでメンションする人間 | 今の `decide` と同じ | メンションを省いて書き、1 で終わる |
| `squad-pr-link` の標準出力の 2 行目（スクリプトが出す） | 役の `連携なし:` の段落 | 1 行目が `連携なしにしました:` で、同じ実行の出力である | 段落を書かない |

記録を偽ってできるのは、待ちと警告と依頼を止めることと、マージした PR を `done` にすることだけである。`done` は `gh` がマージを返した PR にだけ書き、閉じた PR とマージ待ちの PR は `done` にしない。記録を偽っても、紐付けを外したり、ほかのリポジトリへ書き込んだりはできない。

記録は GitHub への書き込みをしないので、書き込んでよいリポジトリの決まりとガードには触れない。トークンの扱いは、今の `squad-pr-link-lib` と同じく、標準入力から curl に渡し、出力と記録に出さない。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイルに手順を足す。足すのは、PR を作る役の `連携なし:` の段落（`references/pr.md`）と、リーダーの `連携: なし` の分岐（`leader-pr-link.md`・`leader-pr-ci.md`・`leader-pr-merge.md`）である。

### 根拠

合意された要件による新しい機能なので、要件を合意したタスクを失敗の記録に代える。連携のないリポジトリで、PR ごとに待ちと警告と依頼が起きた経緯は、タスクのコメントにある。

### 働いた跡

手順が働くと、記録を書いた PR のタスクに、役の引き継ぎの `連携なし:` の段落が残る。リーダーの分岐が働くと、マージの依頼に[添える 1 行](#リーダーの手順と-decide)が残る。跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 跡 | 形 | `pattern` | `author_type` |
| --- | --- | --- | --- |
| 役の知らせ | `kind: "comment"` | `(?m)^連携なし:` | `agent` |
| リーダーのマージの依頼 | `kind: "comment"` | `(?m)^連携なしのリポジトリなので、マージのあとは見張りが` | `agent` |

この跡は、連携のないリポジトリのタスクが 20 件の中にないと 0 回になる。0 回のときに削る候補にするかは、見直しで人間が判断する。

### 仕組みにしない理由

判定・記録・試み直し・`done` は、スクリプトの仕組みにした。手順に残るのは、役が知らせの段落を写すことと、リーダーが依頼と知らせを出し分けることである。この 2 つも仕組みにする案を比べ、選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| `squad-pr-link` が、知らせをタスクへ直接投稿する | 役の実行はコメントで起きることが多く、スクリプトはきっかけのコメントを知らないので、根のコメントが拒否される。引き継ぎの段落なら、今の `紐付けの失敗:` と同じ置き場所で届く |
| リーダーの知らせとマージの依頼の行を、すべてスクリプトが書く | リーダーが手で書くマージの依頼は、ほかの理由で人間を呼ぶコメントと 1 つにまとめる決まりがあり、スクリプトが別に投稿すると 2 つに分かれる。`decide` の経路は、スクリプトが行を書く |

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと、見張りのスクリプト・共通スキル・リーダーの手順が替わる。替わったあと、連携のないリポジトリでは、最初の PR で 1 回だけ待ちと知らせが出て、次の PR から待ちと依頼が出なくなる。

| 利用者 | 変わること |
| --- | --- |
| 人間 | 連携なしのリポジトリでは、紐付けの依頼と、マージのあとの `done` がなくなる。72 時間の見張りのあとにマージしたときだけ、`done` にする |
| PR を作る役 | `squad-pr-link` が 0 で終わる行が 2 つ増える。`連携なしにしました:` のときに段落を 1 つ書く |
| リーダー | `link-check` の行の末尾に `連携: なし` が付くことがあり、そのときは知らせと依頼の行を出さない |
| `decide` | マージの依頼と、使用率の待ちで人間を呼ぶコメントの行が、`連携: なし` のときに変わる |
| マージ待ちの見張り | 連携なしの PR がマージされると、タスクを `done` にする。72 時間の最後の確認で、人間への知らせを 1 回書く |
| セットアップ | 候補が 0 件のときの案内の文だけが変わる |

エージェントとオートパイロットの登録は変わらない。役のひな形の形式と、拡張との契約も変わらない。

記録はホストごとにある。同じプロジェクトを別のホストでも動かすと、ホストごとに最初の PR で 1 回待つ。流し直す前に作った PR は、記録もマークもないので、今の動作のままである。

スクリプトは、セットアップが同じ実行でまとめて置き換える。共通スキルとリーダーの手順も同じ実行で替わる。古い手順が `連携: なし` の付く行を読んでも、先頭は今と同じなので「紐付いていない」と読み、今の依頼を出す。

### 変更の知らせ

この変更の知らせは、バージョンを上げる PR が、`CHANGELOG.md` に次の文で足す（[release.md の変更の知らせ](release.md#変更の知らせ)の決まり）。役の判断とスクリプトの動作が変わることと、ホストに記録が増えることを、更新の前に読めるようにするため。

登録が変わらないと書く文は、同じ節のほかの変更と食い違わないよう、「この変更では」とこの変更の範囲に限る。

```markdown
GitHub 連携のないリポジトリで、PR の紐付けを待たずに進めるようにした。作った直後の紐付けが 120 秒のあいだ見つからないで終わると、そのリポジトリをホストに「連携なし」と記録し、タスクに 1 回だけ知らせる。流し直しで、見張りのスクリプト、共通スキル、リーダーの手順が替わる。

連携なしのリポジトリでは、紐付けの待ちと警告と依頼を出さず、マージ待ちの見張りがマージを確かめてタスクを `done` にする。PR が 1 つでも紐付くと記録が消え、連携ありの動作に戻る。この変更では、エージェントとオートパイロットの登録は変わらない。

- 連携のあるリポジトリでも、サーバーの同期が 120 秒より遅れると、一度は連携なしとして扱われる。次に PR が紐付くと戻る
- 72 時間の見張りのあとにマージした PR は、人間がタスクを `done` にする
- 記録はホストのエージェントのホームの下にあり、人間が消せる。手順は手順書の「リポジトリの登録と GitHub 連携」にある
- README と手順書は、GitHub 連携を導入の前提としなくなった。セットアップは、候補が 0 件のときに `multica repo add` での登録を案内する
```

## 残る危うさ

- サーバーは、連携がないときと同期が遅れたときに同じ 404 を返すと、公開のソースから読んでいる。実機では確かめていない
- 同期が 120 秒より遅れた連携ありのリポジトリは、一度は連携なしの扱いになり、次に PR が紐付くまで待ちと依頼が出ない
- 連携ありのリポジトリが連携なしの扱いのあいだは、紐付いていない PR の `done` を見張りが行う。サーバーの同期が追いつけば、試み直しで紐付き、記録が消える
- 連携を外したリポジトリは、120 秒の待ちが 404 で終わるまで連携ありの扱いのままで、1 つ目の PR で今の待ちが 1 回起きる
- 記録はホストごとにあるので、同じプロジェクトを複数のホストで動かすと、ホストごとに最初の PR で待つ
- 記録はホストの同じユーザーの処理なら書ける。偽の記録で止まるのは待ちと警告と依頼で、マージしていない PR を `done` にはしない
- 72 時間の見張りのあとにマージした PR は、人間が `done` にするまで `in_review` のままになる。見張りの終わりの知らせを読み落とすと、そのまま残る
- 見張りの規則の登録が失敗すると、`done` にする見張りがない。マージの依頼に、人間に `done` を頼む行を足して補う
- `multica repo add` で登録したリポジトリが、連携のないサーバーで選べてセットアップが通るかは、実機で確かめていない。マージの前に人間が確かめる
- `squad-dependabot-merge` の紐付けは記録を読まず書かないので、連携なしのリポジトリでも今の待ちが続く

## 決まっていないこと

| 決まっていないこと | 今決めない理由 | 決める人 | いつまでに | 決まるまでの扱い |
| --- | --- | --- | --- | --- |
| 見張りのあとにマージされた PR の `done` を、人間にどう知らせるか（[見張りのあとのマージの知らせ](#見張りのあとのマージの知らせ)） | 要件は人間が `done` にすると決めたが、知らせ方を決めていない。案ごとに、人間に届くコメントの数が違う | 人間 | 設計の承認 | 推す案の、見張りの最後の確認で人間をメンションして 1 回知らせる形で作る |

## 検討した案

記録の置き場所と見分け方・知らせの出し方・`done` の判定・試み直しの間隔で、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| 連携の状態を API で読む | メンバーが読める一覧では、リポジトリが連携の許可に含まれるかが分からない。リポジトリの一覧は管理者しか読めない |
| 記録をタスクやプロジェクトの metadata に置く | タスクの metadata は PR ごとに別で、次の PR に効かない。プロジェクトの metadata を書く CLI と約束がなく、役と人間がどこからでも書ける |
| 記録を、404 以外の失敗でも書く | 通信の失敗やサーバーの一時的な失敗で、連携のあるリポジトリを連携なしにしてしまう |
| `squad-pr-link` が、知らせをタスクへ直接投稿する | 役の実行はコメントで起きることが多く、スクリプトはきっかけのコメントを知らないので、根のコメントが拒否される |
| 記録があるときも `squad-pr-link` を 1 で終わらせ、役に `紐付けの失敗:` の段落を書かせる | 段落が警告として残り、リーダーが知らせと依頼を出す。要件の「警告を出さない」に合わない |
| 試み直しの間隔を、記録を書かないかわりに毎回呼ぶ形にする | マージ待ちの見張りが 1 時間ごとに API を呼び、試み直しの間隔（6 時間）を変えることになる。間隔は要件の範囲の外である |
| 間隔の時刻を、ホストのファイルに置く | タスクごとの時刻をホストに増やし、ホストが替わると読めない。metadata なら、どのホストの見張りからも読める |
| `done` にするかを、記録があるかで読む | マージの依頼のあと、別の PR が紐付いて記録が消えると、`done` を頼まなかった PR を誰も `done` にしない |
| 紐付いていない PR は、連携の有無によらず見張りが `done` にする | 連携ありのリポジトリの動作を変える。今は人間に紐付けを頼んでおり、要件の「連携ありの動作は変えない」に合わない |
| 見張りのあとの知らせを、マージの依頼の中に「72 時間のあとにマージしたら `done` にしてほしい」と書く | 受け入れ条件の、マージの依頼に `done` を頼む行を入れない決まりに合わない |
| 見張りのあとの知らせを出さず、手順書にだけ書く | 72 時間を過ぎてマージした人間が、`done` を忘れても気づけない |
| 見張りの長さを延ばす | 要件で、見張りの間隔と長さは変えないと決めている |
| `squad-dependabot-merge` も記録を読む | Dependabot の PR の回し方は、今も次の回で試み直しており、要件の範囲の外である。動作を変えると、回し方の確認をやり直す必要がある |
