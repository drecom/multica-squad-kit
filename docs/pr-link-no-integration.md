# GitHub 連携のないリポジトリで、PR の紐付けを待たずに進める

GitHub 連携のないリポジトリでは、サーバーが PR を見つけられず、PR ごとに待ちと警告と人間への依頼が起きる。この設計では、作った直後の紐付けが 404 で待ち切れたリポジトリを、ホストに「連携なし」と記録する。記録のあとの PR は待たない。連携なしになった PR には警告と依頼を出さず、マージのあとに人間がタスクを `done` にする。

あわせて、PR を作る役は PR のタイトルにタスクの識別子を入れる。自動の関連付けと明示の紐付けのどちらで紐付いても、紐付いたと扱う。

## 目的と範囲

今は、連携のないリポジトリでも、PR を作るたびに次が起きる。PR を作った役が 120 秒待って警告を残し、リーダーが連携の確認と紐付けを人間に頼む。試み直しの記録もタスクに増える。README・手順書・セットアップの案内は、連携を導入の前提にしている。

目的は次の 5 つである。

1. 連携のないリポジトリを、紐付けの結果から見分けて記録する。連携の状態は API で読まない
2. 記録のあるリポジトリの PR では、120 秒待たない。連携なしになった PR では、紐付けの警告と依頼、紐付かなかった試み直しの記録を出さない
3. 連携なしになった PR は、人間がマージを確認してタスクを `done` にする。エージェントと見張りは `done` にしない
4. リポジトリの PR が 1 つでも紐付けば記録を消し、次の PR から今の動作に戻す。連携なしで始めた進行中の PR は、その PR が紐付くまで扱いを変えない
5. PR のタイトルにタスクの識別子を入れる。自動の関連付けでも明示の紐付けでも、紐付いたと分かった PR には警告を出さない

次は対象にしない。

- 連携なしのタスクを自動で `done` にすること。連携なしの PR を、タスクの画面の PR の欄に出すこと
- 連携の状態を API で読むこと。セットアップの質問で連携の有無を尋ねること
- 明示の紐付けを、自動の関連付けに置き換えること。連携なしは、明示の紐付けの結果で見分けるため
- ブランチ名に識別子を入れること。ブランチ名は Multica の checkout が決めるため
- 連携のあるリポジトリで、120 秒のうちに紐付かない原因の調査
- 120 秒の待ちの長さと、[試み直し](pr-link-retry.md)の間隔の値
- CI とコンフリクトの確認。マージ待ちの見張り（`unlinked`・`unlinked-check`）の動作

## 前提と確認したこと

連携のないリポジトリで、サーバーが紐付けの API に 404 を返し続けることは、今の警告の文と手順書の前提である。連携があっても、同期が 120 秒より遅れると同じく 404 で待ち切れる。この設計は、その場合も連携なしと記録し、次に紐付いたときに戻す（[残る危うさ](#残る危うさ)）。

タスクの読み取り（`multica issue get`）は `project_id` を返す。実機の応答で確認し、テストのタスクの見本（`tests/fixtures/cli/issue-get.json`）にもある。今の CLI の契約（`squad-cli-lib` の `issue-get`）にはこの欄がないので、任意の欄として足す。

コメントの投稿（`multica issue comment add`）には、同じ投稿を重ねないための鍵がない。このため、知らせは 1 つの実行が 1 回だけ投稿し、ほかの所は数えも消しもしない（[知らせ](#知らせ)）。コメントの消去と、同じエージェントの実行が順に動くことは前提にしない。

コメントがきっかけの実行は、きっかけのコメントへの返信でしか投稿できず、根のコメントは断られる。CLI のヘルプの `--parent` の説明で確認した。きっかけのコメントの ID は環境の値になく、実行に渡されるだけなので、スクリプトには引数で渡す。

連携のないリポジトリで、タイトルの識別子による自動の関連付けが効くかは、実機で確認していない。公開のソースの読みでは効かない。この設計はどちらでも動くように作り、効くことを前提にしない。

## PR のタイトルの識別子

PR を作る役は、PR のタイトルの末尾にタスクの識別子を入れ、タイトルを直すたびに残す。公開と非公開のリポジトリで同じにし、ブランチ名は変えない。

### タイトルの形

識別子は、タイトルの末尾に半角の丸括弧で置く。先頭の種類（`feat:` など）は、今の決まりのとおり先頭に残す。

```text
feat: 連携なしのリポジトリで紐付けを待たずに進める (DEMO-12)
```

- 識別子は、タスクの読み取りの `identifier` を使う。実行に渡されるタスクの ID（UUID）は入れない
- `gh pr create --title` で作るときから入れる。push のたびに `gh pr edit --title` で直すときも、末尾の識別子を残す
- 決まりの置き場所は、共通スキル `squad-handoff` の `pr.md` の「PR を作る・実装を積む」である。PR を作る役と積む役は、すでにこの節を読んでタイトルを書いている

識別子を入れても、明示の紐付け（`squad-pr-link`）は今のとおり呼ぶ。連携なしは、明示の紐付けの結果で見分けるためである。

### 識別子を持ち出さない決まりとの関係

今の決まりは、タスクの識別子を PR の本文と公開の設計とコミットに持ち出さない。PR のタイトルだけを例外にし、本文・設計・コミットの決まりは変えない。例外の理由は、連携のあるリポジトリで、サーバーがタイトルから PR をタスクに関連付けられるようにするためである。

例外は、識別子の決まりがある 3 か所に同じ文で書く。`CONTRIBUTING.md` の失敗の記録の段落、`AGENTS.md` のコミットの段落、`pr.md` の識別子の項目である。文書の書き方の作業別のルール（`.agents/rules/docs.md`）と `STYLE.md` は、識別子にもタイトルにも触れていないことを確認した。`.agents/rules/docs.md` には `CONTRIBUTING.md` への案内を 1 文足し、`STYLE.md` は変えない。

### 紐付いたと扱う所

紐付いたかは、紐付けの API の 200 か、タスクの PR の一覧（`multica issue pull-requests`）の `html_url` で読む。一覧には自動の関連付けの PR も明示の紐付けの PR も出るので、両方を紐付いたと扱える。紐付いたと読んだ所は、記録があれば消す。

| 所 | 紐付いたと読むとき |
| --- | --- |
| `squad-pr-link` | 期限内の 200 か、失敗のあとの一覧の読み直しで PR がある |
| `squad-pr-watch link-check` | 今のとおり一覧で読み、判定は変えない。自動の関連付けの PR も「紐付いている」になる |
| `squad-dependabot-merge` | 期限内の 200 か、失敗のあとの一覧の読み直しで PR がある。記録は消すが、書かない |

`pr_url` がすでにあって API を飛ばしたときは、紐付いたとは読まない。記録を消す根拠がないので、消さない。紐付いていれば、次の `link-check` が一覧で読んで消す。

### 連携の有無と自動の関連付け

自動の関連付けが効くかで、動作は次のとおり分かれる。どちらでも、この設計は変えない。

| リポジトリ | 自動の関連付けが効く | 効かない |
| --- | --- | --- |
| 連携あり | PR の欄に出る。`squad-pr-link` は今のとおり紐付ける | 今の動作と同じ |
| 連携なし | 一覧に PR が出るので記録を書かず、あれば消す。連携なしの動作は起きない | 404 で待ち切れて記録を書き、連携なしの動作になる |

実機で効くかは、人間が受け入れの確認で、連携のないリポジトリの 1 つ目の PR が PR の欄に出るかを見て、どちらでもタスクに残す。効くときは、その PR で連携なしの動作が起きない。そのときの連携なしの動作は、関連付けの起きない状態を作れるリポジトリで確認する。

## 連携なしの記録と印

連携なしは、ホストの記録とタスクの印の 2 つで持つ。記録はリポジトリごとで、新しい PR が待つかだけを決める。印は PR ごとで、その PR を連携なしとして扱うかだけを決める。

| もの | 単位 | 書く所 | 決めること |
| --- | --- | --- | --- |
| 記録 | プロジェクトとリポジトリ | `squad-pr-link` | 新しい PR で 120 秒待つか |
| 印 | タスクの PR | `squad-pr-link` | その PR に警告と依頼を出すか |

2 つに分けるのは、別の PR が紐付いて記録が消えても、連携なしで始めた進行中の PR の扱いを変えないためである。記録だけで両方を決めると、記録が消えたとたん、進行中の PR に紐付けの依頼が出る。

### 記録の置き場所と形

記録は、ホストのエージェントのホームの下に、プロジェクトとリポジトリごとに 1 つのファイルで置く。使用率の確認の状態（`squad-usage-check`）と同じ根の下に置き、セットアップの流し直しで消えないようにする。

```text
${PR_LINK_STATE_ROOT:-$HOME/.multica-agent/template/pr-link}/<プロジェクトの ID>/<オーナー>/<リポジトリ>
```

- プロジェクトの ID は、タスクの読み取りの `project_id` を使う。ないときは記録を書かず読まず、今の動作のままにする
- オーナーとリポジトリは、PR の URL から取り、小文字にする
- 各部分は、空・`.`・`..`・英数字と `_.-` 以外の文字を含むものを断る。断ったときは記録を書かず、ないものとして読む
- ディレクトリは 700、ファイルは 600 で作る。中身を同じディレクトリの一時ファイルに書いてから、`ln` で記録のパスに結ぶ
- `ln` は記録のパスがあると失敗するので、同時に作る実行のうち 1 つだけが記録を作る。一時ファイルは、結べたかによらず最後に消す

ファイルがあることを「連携なし」と読む。中身は次の 4 行で、`pr:` の行だけを[途中で止まったときの戻し](#途中で止まったとき)に使う。

```text
repository: <オーナー>/<リポジトリ>
pr: <記録のきっかけになった PR の URL>
task: <タスクの識別子>
記録した時刻: <UTC の YYYY-MM-DDTHH:MM:SSZ>
```

記録のパスか、その上のプロジェクトとオーナーのディレクトリがシンボリックリンクなら、記録はないものとして読む。書きも消しもしない。普通のファイルでないもの（ディレクトリなど）も同じにし、どちらも標準エラーに 1 行だけ理由を出す。

### 印の形

印は、タスクの metadata の `pr_link_no_integration` に、種類と PR の URL を空白でつないで置く。

```text
<記録した | 記録があった> <PR の URL>
```

- `記録した` は、その PR の待ち切れで記録を作ったことを示す。リポジトリを連携なしにした知らせは、この種類の印を書けた切り替えの実行だけが出す
- `記録があった` は、記録があったので待たずに連携なしにしたことを示す。知らせは出さない
- 印は知らせに使わない。知らせを出したかを印で覚えず、印を消す時機も知らせで変えない
- 印が効くのは、形が合い、URL が `pr_url` と正規形で同じときだけである。同じタスクで `pr_url` が新しい PR に替わると、前の印は効かない

### 書く時機と消す時機

記録を書くのは `squad-pr-link` だけで、作った直後の紐付けが 120 秒のあいだ 404 だけで終わり、一覧の読み直しで PR がないと分かったときに限る。印を書くのも `squad-pr-link` だけで、[連携なしへの切り替え](#連携なしへの切り替え)の中で書く。

記録を消すのは、そのプロジェクトとリポジトリの PR が紐付いたと分かったときである。分かる所は、[紐付いたと扱う所](#紐付いたと扱う所)の 3 つにする。どの所も、分かった時点で記録のパスを読み、あれば消す。実行の始めに読んだ記録の有無は使わない。

印を消すのは `link-check` で、その PR が紐付いていると判定したときである。種類によらず、その回に消す。ほかの PR が紐付いても、印は消さない。

記録の消去と作成が重なったときは、後に起きたほうが残る。消去が後なら次の PR は 120 秒待ち、作成が後なら次の PR は待たない。どちらも、次の PR の紐付けの結果で正しい状態に戻る。

### 人間が消すとき

人間が連携をつないだあとは、記録を消さなくても、次の PR が 1 回の試みで紐付いて記録が消える。すぐに戻したいときは、手順書の手順で、ホストの記録のファイルを消す。消すと、次の PR から今の 120 秒の待ちに戻る。

記録を消しても、連携なしで始めた進行中の PR は、印で連携なしのまま扱う。その PR も今の動作に戻したいときは、そのタスクの metadata の `pr_link_no_integration` を消す。

## squad-pr-link の動作

`squad-pr-link` は、タスクを読んだあと、作業先が PR のリポジトリと同じで、プロジェクトの ID があるときに記録を読む。記録の有無で、次の 2 つに分かれる。どちらでもないとき（作業先が違う、プロジェクトがない）は、今の動作のままにする。

`pr_url` がすでにあるときは、今と同じく API を呼ばずに `紐付けていません:` の行を出す。記録の有無で変えず、記録も印も触らず、知らせも出さない。

引数に、任意の 3 つ目としてきっかけのコメントの ID を足す。[知らせ](#知らせ)の返信先にだけ使う。

```text
squad-pr-link <タスク> <PR の URL> [<きっかけのコメントの ID>]
```

3 つ目は UUID の形（16 進と `-` の 8-4-4-4-12）に限る。形が合わないときと引数が 4 つ以上のときは、今の引数の誤りと同じく 2 で終わる。

### 記録がないとき

今と同じく 120 秒まで待つ。結果ごとに次のとおりにする。

| 結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| 期限内の 200 で、`pr_url` を書けた | 記録があれば消す | `紐付けました: <タスクの識別子> <PR の URL>` | 0 |
| 期限内の 200 で、`pr_url` を書けない | 記録があれば消す | `紐付けました（pr_url を書けない）: <タスクの識別子> <PR の URL>` | 3 |
| 失敗 | [一覧の読み直し](#一覧の読み直し)をする | 一覧の読み直しのとおり | 一覧の読み直しのとおり |

一覧が空で、`PR_LINK_ALL_404` が 1 なら、[連携なしへの切り替え](#連携なしへの切り替え)をする。`PR_LINK_ALL_404` が 1 でなければ、今の動作（警告・`pr_link_pending`・1 で終わる）を変えない。

### 404 だけが続いたことの判定

`PR_LINK_ALL_404` は、`pr_link_pull_request` に足す結果である。今の `PR_LINK_NOT_FOUND` は、期限を過ぎれば最後の応答によらず 1 になる。通信の失敗や 500、期限後の 200 でも 1 になるので、記録の判定には使わない。

| 期限を過ぎたと分かった所 | `PR_LINK_NOT_FOUND` | `PR_LINK_ALL_404` |
| --- | --- | --- |
| 次の試みの前。直前の応答は 404 で、待っていた | 1 | 1 |
| 応答のあと。その応答が 404 | 1 | 1 |
| 応答のあと。その応答が 200・404 以外・通信の失敗 | 1 | 0 |

404 以外の応答と通信の失敗は、期限の前ならその場で終わる。そのため、期限を過ぎた時点で、それより前の応答はすべて 404 である。`PR_LINK_NOT_FOUND` と、戻り値と待ち方と今の警告は変えない。

あわせて、期限内に 200 を受けたことを `PR_LINK_LINKED` に 1 で返す。`pr_url` を書けずに 1 を返すときも 1 にし、呼び出し元が紐付いたことと書けなかったことを分けて読めるようにする。

### 記録があるとき

待たずに、紐付けの API を 1 回だけ呼ぶ（`pr_link_request_once`、時間切れ 30 秒）。呼ぶ前に API の環境を確認し、なければ呼ばずに失敗として続ける。

| 結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| 200 で、`pr_url` を書けた | 記録を消す | `紐付けました: <タスクの識別子> <PR の URL>` | 0 |
| 200 で、`pr_url` を書けない | 記録を消す | `紐付けました（pr_url を書けない）: <タスクの識別子> <PR の URL>` | 3 |
| 失敗 | [一覧の読み直し](#一覧の読み直し)をする。一覧が空なら、種類 `記録があった` で切り替える | 一覧の読み直しか切り替えのとおり | 同左 |

失敗は、200 以外の応答、通信の失敗、API の環境がないことの 3 つである。どれでも、記録は消さない。404 以外の応答で消すと、サーバーの一時の失敗で次の PR が 120 秒待つためである。

### 一覧の読み直し

`squad-pr-link` は、紐付けの API が失敗したとき、警告と記録の前に、タスクの PR の一覧を 1 回だけ読む。自動の関連付けなどで PR がすでに紐付いていれば、失敗として扱わないためである。

読み直すのは、120 秒の待ちの期限切れ・200 以外の応答・通信の失敗・API の環境がないことの 4 つである。作業先が PR のリポジトリと違うときと、`pr_url` があるときは読まず、今の動作にする。一覧は `squad_cli_read issue-pull-requests` で読み、`html_url` を `link-check` と同じ比べ方で PR の URL と比べる。

| 一覧の結果 | すること | 標準出力 | 終了コード |
| --- | --- | --- | --- |
| PR があり、`pr_url` を書けた | 記録を消す。`pr_link_pending` と印は書かない | `紐付いていました: <タスクの識別子> <PR の URL>` | 0 |
| PR があり、`pr_url` を書けない | 記録を消す | `紐付いていました（pr_url を書けない）: <タスクの識別子> <PR の URL>` | 3 |
| 一覧が空 | 前の 2 つの節のとおりに続ける | 前の節のとおり | 前の節のとおり |
| この PR はなく、ほかの PR がある | 記録も印も書かず、今と同じ警告と `pr_link_pending` | なし | 1 |
| 一覧を読めない | 記録も印も書かず、今と同じ警告と `pr_link_pending` | なし | 1 |

一覧を読めないときに連携なしにしないのは、自動の関連付けで紐付いているかもしれないためである。紐付いていないと分かったときだけ、連携なしにする。

ほかの PR があるときも連携なしにしない。`link-check` はこのタスクを `食い違い` と判定し、印を読まないので、連携なしにしても扱いが効かないためである。今の警告で 1 にすると、`link-check` の食い違いの手順で人間に両方の PR を示す。

紐付けの前には一覧を読まない。サーバーが PR を知っていれば紐付けの API が成功するので、一覧が効くのは失敗のあとだけである。

### 連携なしへの切り替え

切り替えは、次の順に書く。種類は、記録がないときの待ち切れでは `記録した`、記録があるときは `記録があった` にする。

1. metadata の `pr_link_pending` に PR の URL を書く
2. metadata の `pr_url` に PR の URL を書く
3. 種類が `記録した` のときだけ、記録を一時ファイルに書き、`ln` で記録のパスに結ぶ。記録のパスがすでにあれば、種類を `記録があった` に替えて続ける
4. metadata の `pr_link_no_integration` に印を書く
5. 種類が `記録した` のときだけ、[知らせ](#知らせ)を 1 回投稿する。失敗しても投稿し直さず、6 へ進む
6. 標準出力に 1 行を出し、0 で終わる。標準エラーには何も出さない

標準出力の行は、種類が `記録した` なら `連携なしにしました: <タスクの識別子> <PR の URL>` にする。`記録があった` なら `紐付けていません（連携なし）: <タスクの識別子> <PR の URL>` にする。どちらも、PR を作った役は今の成功と同じに読み、引き継ぎに何も足さない。

1〜4 のどこかで書けなければ、切り替えをやめ、知らせを出さず、今と同じ警告を出して 1 で終わる。0 で終わるのは、4 の印を書けたときだけである。5 の投稿の成否は、終了コードと出力を変えない。印は PR ごとなので、0 で終わった PR の扱いは、別の PR が紐付いて記録が消えても変わらない。

| 書けなかった所 | 終了コード | 残る状態 |
| --- | --- | --- |
| 1 の `pr_link_pending` | 1 | マークがないので、今のマークを書けなかったときと同じになる。役が書く `紐付けの失敗:` の段落で、リーダーが人間に頼む |
| 2 の `pr_url` | 1 | マークがあるので、役が `pr_url` を書いたあと、`link-check` が今のとおり試み直す |
| 3 の `ln`（パスがある以外の失敗） | 1 | 同上。記録はない |
| 4 の印 | 1 | 結んだ記録を残し、記録の `pr:` がこの PR なら `link-check` が[印を戻す](#途中で止まったとき)。戻す前に記録が消えるか、`pr:` がほかの PR なら、2 と同じになる |

切り替えは、自分で結んだ記録を消して戻すことをしない。消しても、消せなかったときには「3 のあとに止まった」と同じ状態が残るので、どちらにしても戻しの扱いが要るためである。

順の理由は 4 つある。マークを先に書くのは、どこで止まっても今の試み直しが働くようにするためである。`pr_url` を記録より先に書くのは、0 で終わる実行が必ず `pr_url` を残すためである。

記録を印より先に書くのは、記録のない状態で連携なしと扱わないためである。知らせを印のあとに出すのは、連携なしとして扱う PR にだけ知らせが残るようにするためである。

同じリポジトリの 2 つの PR が同時に待ち切れても、記録を結べるのは 1 つだけなので、`記録した` の印と知らせも 1 つの PR にだけ出る。

### 途中で止まったとき

PR を連携なしとして扱うかは、`link-check` の印と、下の戻しの条件だけで決める。`squad-pr-link` の終了コードは、役が引き継ぎに書くものだけを決める。切り替えが途中で止まったときも、止まった所ごとに次のとおりに戻る。

| 止まった所 | 残る状態 | 戻り方 |
| --- | --- | --- |
| 1 か 2 のあと | マークはあり、記録と印はない | 今の試み直しと依頼の動作になる |
| 3 のあと | 記録はあり、印はない | `link-check` が、記録の `pr:` の行から印を戻す。知らせは出ない |
| 4 のあと、5 の前 | 記録と印がそろい、知らせはない | 連携なしとして扱うが、知らせは出ない。役が書いた `紐付けの失敗:` の段落は、依頼に使わない |
| 5 のあと、出力の前 | 記録と印と知らせがそろう | 連携なしとして扱う。役が書いた `紐付けの失敗:` の段落は、依頼に使わない |

`link-check` が印を戻すのは、印がなく、次の 2 つを満たすときだけである。

- `pr_link_pending` と `pr_url` が、正規形で同じ PR を指す
- 記録の `pr:` の行が、その PR と正規形で同じである

戻すのは、判定が紐付いていないときだけである。戻すときは種類を `記録した` にする。書けなくてもその回は `連携: なし` を付け、次の回に戻し直す。戻した回も戻せない回も、知らせは出さない（[知らせ](#知らせ)）。

1 で終わった PR でも、戻しの条件を満たせば `link-check` が連携なしとして扱う。当てはまるのは、4 の印を書けなかったとき、3 のあとに止まったとき、同じ PR の記録が前の実行から残っていたときである。そのときは `link-check` の扱いを正とし、役が書いた `紐付けの失敗:` の段落は、依頼に使わない。リーダーと `decide` は `連携: なし` で段落を外す（[リーダーと decide の動作](#リーダーと-decide-の動作)）。

戻す前に別の PR が紐付いて記録が消えると、戻さず、今の試み直しと依頼の動作になる。役は 1 で紐付けの失敗を引き継いでいるので、知らせのないまま依頼が出ても、役の引き継ぎと食い違わない。

#### 切り替えと link-check が重なったとき

`link-check` が切り替えの途中に流れても、見えるのは上の表の止まった所と同じ状態である。順は決めず、どの順でも次のとおりに同じ扱いへ落ち着く。

| `link-check` が見た所 | `link-check` の扱い | そのあと |
| --- | --- | --- |
| 1 か 2 のあと | 今の動作。試み直しの記録が 1 件出ることがある | 切り替えが終われば、次の回から印で扱う |
| 1 か 2 のあとで、試み直しが 200 で紐付く | `紐付いた` の記録を書く。消す記録と印はまだない | 切り替えが記録と印を書いて知らせを出しても、次の `link-check` が紐付いていると読み、記録と印を消す。知らせは消さない |
| 3 のあと、4 の前 | 印を `記録した` で戻す。知らせは出さない | `squad-pr-link` が同じ値の印を書いて 5 で知らせを出す。4 を書けずに 1 で終わると、戻した印で扱い、知らせは出ない |
| 4 のあと | 印で扱う | なし |

3 と 4 のあいだの種類は、記録を結んだ実行では必ず `記録した` になる。記録のパスがすでにあって `pr:` がこの PR の場合だけ、`squad-pr-link` は `記録があった` を書き、知らせを出さない。知らせを出すのは、記録を結んだ実行だけである。

### PR を作った役の扱い

PR を作った役は、終了コードで引き継ぎに書くものを決める。0 と 1 などの扱いは今のとおりで、3 を足す。

| 終了コード | metadata に書くもの | `紐付けの失敗:` の段落 |
| --- | --- | --- |
| 0 | `branch` | 置かない |
| 3 | `branch` と `pr_url` | 置かない |
| ほか（127 を含む） | `branch` と `pr_url` | 今のとおり置く |

3 は、紐付いたのに `squad-pr-link` が `pr_url` を書けなかったことを示す。役が `pr_url` を書けば、`link-check` は一覧で紐付いていると読む。決まりは `pr.md` の「PR を作る・実装を積む」に足す。終了コードの `0` と `3` は、バッククォートで囲んで書く。

手順の語の検査（`tests/pr-link-procedure-check.py`）は、今は説明文の数字を見ないので、`3` を別の数に変えても通る。数字だけの語を「終了コード」の種類とし、`0` と `3` がそろうことを契約に足す。表（`tests/pr-link-procedure-table.tsv`）には、終了コードを別の数に変えた写しが落ちる行を足す。

## link-check の動作

`squad-pr-watch link-check` の判定は、今のとおり一覧で読み、変えない。判定のあとに、タスクの印を読み、記録の有無は進行中の PR の扱いには使わない。`link-check` は、どの役が流しても同じに動き、知らせを書かず読まず消さない。

| 判定 | 印 | すること | 行 |
| --- | --- | --- | --- |
| 紐付いている（試み直しで紐付いたを含む） | どちらでも | 記録を消す。印は、種類によらず消す | 今と同じ |
| 紐付いていない | 効く | 末尾に `連携: なし` を足す | `紐付け: 紐付いていない pr: <PR の URL> 連携: なし` |
| そのほか | どちらでも | 今と同じ | 今と同じ |

判定が紐付いていないで印がないときは、[途中で止まったとき](#途中で止まったとき)の戻しを試す。紐付いていると判定したときの記録は、タスクの `project_id` と `pr_url` のリポジトリから読む。

行の先頭は今と同じである。`紐付け: 紐付いていない` で始まるかで読む今の分岐は、そのまま CI とコンフリクトを確認する。分岐は `decide`・`unlinked-check`・リーダーの手順にある。`decide` は `pr:` の次の語だけを URL として読むので、末尾を足しても URL は変わらない。

### 試み直しの扱い

印が効くときも、試み直す条件は今と同じにする。条件は、`pr_link_pending` が `pr_url` と同じ PR を指し、一度も紐付いておらず、作業先が同じことである。変えるのは、次の 4 つである。

| 場面 | 今 | 印が効くとき |
| --- | --- | --- |
| API の環境がない | 呼ばず、`失敗（<理由>）` の記録を書く | 呼ばず、記録も `pr_link_tried_at` も書かない。試みに数えない |
| API を呼ぶ前 | 何もしない | metadata の `pr_link_tried_at` に時刻と URL を書く。書けなければ、その回は呼ばない |
| 試み直しの結果が `紐付いた` | 記録を書く | 記録を書き、記録と印を消す |
| 結果がそれ以外（`一覧にない（200）`・`見つからない（404）`・`失敗…`・`未確認…`・`食い違い`） | 記録を書く | 書かない |

`pr_link_tried_at` の値は、次の 1 行にする。

```text
<UTC の YYYY-MM-DDTHH:MM:SSZ> <PR の URL>
```

間隔は、前の `紐付けの試み直し:` の記録の時刻と `pr_link_tried_at` のうち、新しいほうから測る。`pr_link_tried_at` は、形に合わない・今より後の時刻・URL が今の PR と正規形で違う、のどれかのとき、ないものとして読む。同じタスクで `pr_url` を差し替えても、前の PR の試みが新しい PR の試み直しを遅らせないためである。

呼ぶ前に書くのは、呼んだあとに書けないと間隔の跡が残らず、`link-check` のたびに API を呼ぶためである。API の環境がない回を数えないのは、トークンが戻った次の `link-check` で、すぐに試み直せるようにするためである。間隔の値（リーダーの確認の 5 分、マージ待ちの見張りの 6 時間）は変えない。

### 知らせ

知らせは、記録を結んで種類 `記録した` の印を書けた `squad-pr-link` の実行が、[切り替え](#連携なしへの切り替え)の 5 で 1 回だけ投稿する。ほかの所（`link-check`・リーダー・`decide`・見張り・PR を作った役の手順）は、知らせを書かず、数えず、消さない。

保証は、PR ごとに多くて 1 件である。投稿に失敗した回と、`ln` と投稿のあいだで止まった回は 0 件になる。多くて 1 件になる理由は次の 3 つである。

- `ln` で記録を結べるのは、同時に作る実行のうち 1 つだけである。結べなかった実行は `記録があった` になり、投稿しない
- `squad-pr-link` は、2 で `pr_url` を書いてから投稿する。同じ PR で流し直すと、`pr_url` があるので API も切り替えも飛ばす
- 投稿は 1 回だけで、失敗しても投稿し直さない。応答が失敗でもコメントができていることがあるので、投稿し直すと重なる

0 件のときも、連携なしの PR では、マージを頼むコメントに `done` の行が 1 行出る（[リーダーと decide の動作](#リーダーと-decide-の動作)）。連携なしとして扱うことと、人間が `done` にすることは、その行で伝わる。

投稿は、3 つ目の引数のきっかけのコメントへの返信にする。引数がなければ、根のコメントにする。コメントがきっかけの実行で引数がないと根のコメントが断られ、投稿の失敗として 0 件になる。文面は次のとおりにする。

```text
/note
連携なしの知らせ: <PR の正規形>

<オーナー>/<リポジトリ> を、このプロジェクトでは GitHub 連携なしとして扱います。サーバーが 120 秒待っても PR を見つけなかったためです。この PR をタスクの画面で紐付ける必要はなく、このあとの PR では紐付けを待ちません。マージのあとタスクが done にならなければ、人間が done にしてください。連携しているはずなら、ワークスペースの設定のコードの画面で <オーナー>/<リポジトリ> がつながっていることを確認してください。このリポジトリの PR が 1 つでも紐付けば、次の PR から連携ありの扱いに戻ります。
```

`done` を「ならなければ」と書くのは、知らせのあとに PR が紐付いても、文面が誤った依頼にならないようにするためである。紐付いた PR はマージのあとの状態が連携の設定で決まり、`done` にならなければ人間が `done` にする。知らせのあとに紐付いても、知らせを出し直さず、消さない。

知らせは記録を読まない。投稿の前に別の PR が紐付いて記録が消えても、印を書けた実行は投稿する。その PR を連携なしとして扱い、人間が `done` にすることは変わらないためである。

## リーダーと decide の動作

リーダーと `squad-review-next decide` は、`link-check` の行の末尾の `連携: なし` で、連携なしの PR を見分ける。見分けたら、紐付けの依頼と警告と連携の案内を出さず、マージを頼むときだけ `done` の行を 1 行添える。

| 場面 | 今（紐付いていない） | `連携: なし` のとき |
| --- | --- | --- |
| PR を受け取ったときの知らせ（`leader-pr-ci.md`） | 警告・連携の前提・再発を 1 回知らせる | 知らせない。連携なしの知らせは、切り替えた `squad-pr-link` が出す |
| マージを頼むコメント（`leader-pr-merge.md` と `decide`） | `done` か紐付けを頼む行と、`紐付けの失敗:` の段落と連携の案内 | 下の 1 行だけ |
| ほかの理由で人間を呼ぶコメント（同上） | 紐付けを頼む行と、`紐付けの失敗:` の段落と連携の案内 | 何も添えない |
| その場の確認、CI、コンフリクト | 紐付いていない PR として確認する | 変えない |
| マージ待ちの見張りの登録（`unlinked`） | 登録する | 変えない |

マージを頼むコメントに添える 1 行は、次のとおりにする。`見張り:` の行は、今のとおり続ける。

```text
このリポジトリは GitHub 連携なしとして扱っています。マージのあとに、タスクを `done` にしてください。PR: `<正規形>`
```

`decide` は、`紐付け: 紐付いていない pr:` で始まる行で `LINKED=false` とするのを変えない。末尾が `連携: なし` のときだけ、新しい `NO_INTEGRATION=true` を立てる。`LINKED=false` を見る CI と見張りの登録はそのままにし、依頼の行と `print_linkfail` だけを `NO_INTEGRATION` で分ける。

マージ待ちの見張り（`unlinked-check`）は変えない。マージを見たら規則を消して止まり、タスクの状態を変えず、知らせも書かない。人間がマージを確認して `done` にする。

## squad-dependabot-merge の経路

`squad-dependabot-merge` は、Dependabot の PR を自分のタスクに紐付けるとき、`pr_link_pull_request` で 120 秒まで待つ。この経路も記録を読み、紐付いたと分かれば記録を消す。プロジェクトの ID は、引数のプロジェクトを使う。

| 記録 | 紐付けの試み |
| --- | --- |
| ない | 今と同じく 120 秒まで待つ |
| ある | 待たずに 1 回だけ呼ぶ |

どちらも、試みが失敗したら一覧を 1 回読む。結果ごとに次のとおりにする。

| 結果 | すること | 標準エラー |
| --- | --- | --- |
| 200 か一覧に PR があり、`pr_url` を書けた | 記録を消す | なし（今の成功と同じ） |
| 200 か一覧に PR があり、`pr_url` を書けない | 記録を消す | `タスク <識別子> に PR を紐付けましたが、metadata の pr_url を書けませんでした。次に同じ PR を回すときに補います。` |
| 記録がなく、一覧に PR がないか読めない | なし | 今の 1 行 |
| 記録があり、一覧に PR がないか読めない | なし | なし。次に同じ PR を回すときに補う今の続きにする |

記録と印は書かない。Dependabot の PR は作った直後の同期が遅れやすく、PR を作る役の経路と条件が違うためである。記録は、役の PR が待ち切れたときだけに作る。

## セットアップと README・手順書

セットアップは、リポジトリの候補が 0 件のときの案内だけを変える。候補は今のとおり `multica repo list` から選び、連携の有無は尋ねない。0 件の案内は、管理者が `multica repo add` でリポジトリを登録できることを示す。

README と手順書は、連携を導入の前提とする文をやめ、連携の有無で次のとおり違うことを書く。

| 連携 | PR の欄 | マージのあとの `done` |
| --- | --- | --- |
| あり | タスクの画面の PR の欄に出る | 連携が自動で `done` にする |
| なし | 欄に出ない。PR の場所は metadata の `pr_url` とコメントで示す | 人間が `done` にする |

今の main で、連携を前提とする文は次の 5 か所にある。直すときは、この 5 か所だけでなく README と手順書の全体を読み、前提とする文が残らないようにする。

- README の「必要なもの」の、GitHub 連携を許可したリポジトリの項目
- 手順書の章の一覧の「受け取る人の準備」の、GitHub 連携をそろえる項目
- 手順書の「GitHub 連携とリポジトリの紐付け」の節
- 手順書の、候補が 0 件のときの説明
- 手順書の止まったときの表の「道具・ログイン・リポジトリが不足」の行

手順書には、連携なしでは人間が `done` にすることと、記録の置き場所と、人間が記録と印を消す手順を書く。共通スキルの状態の表（`SKILL.md`）の `done` の行にも、連携なしでは人間が変えることを足す。

## 範囲の原本に足す手順

この設計は、`CONTRIBUTING.md` の範囲のファイルに手順を足す。足す手順ごとに、防ぐ失敗・働いた跡・仕組みにしない理由を書く。

防ぐ失敗は、どの手順も同じである。連携のないリポジトリで、PR を作るたびに 120 秒の待ちと警告と紐付けの依頼が起き、人間が同じ依頼に答え続けた。失敗の記録は、要件を合意したタスクのコメントにある。

| 手順 | 置き場所 | 働いた跡 |
| --- | --- | --- |
| PR のタイトルの末尾に識別子を入れ、直すときも残す | `pr.md` | Multica のコメント・状態の変化・実行には残らない。跡は GitHub の PR のタイトルにあり、跡の定義は置かない（`trace` を `null` にする） |
| 終了コード 3 で `pr_url` を書き、段落を置かない | `pr.md` | 引き継ぎに残る固定の行がない。3 はまれな失敗なので、跡の定義は置かない |
| `squad-pr-link` に、きっかけのコメントの ID を渡す | `pr.md` | 跡は、知らせがきっかけへの返信になることである。切り替えはまれなので、跡の定義は置かない |
| `連携: なし` のとき、PR を受け取ったときの知らせを出さない | `leader-pr-ci.md`・`leader-pr-link.md` | 出さないことなので、跡の定義は置かない。かわりに、`squad-pr-link` の知らせのコメントが残る |
| `連携: なし` のとき、マージの依頼に `done` の 1 行だけを添える | `leader-pr-merge.md` | コメントの跡。`pattern` は `(?m)^このリポジトリは GitHub 連携なしとして扱っています。`、`author_type` は `agent` |

仕組みにしない理由は、次のとおりである。

- タイトル: ガードは書き込み先のリポジトリを見る仕組みで、`--fill` やエディタで書くタイトルまで検査すると、この設計の範囲を超える。決まりがあることは、`tests/agent-templates-test.sh` で検査する
- 終了コード 3: `squad-pr-link` が書けなかった `pr_url` は、役の引き継ぎでしか補えない。0 にすると役が `branch` だけを書き、`link-check` が PR を読めない
- きっかけのコメントの ID: ID は実行に渡されるだけで、環境の値にない。スクリプトが自分で読めないので、役が引数で渡す
- リーダーの 2 つ: 依頼の行は `decide` が作り、知らせは `squad-pr-link` が投稿するので、仕組みにできる所は仕組みにした。残るのは、リーダーがほかのコメントに段落を添えないことだけで、文を組むのはリーダーである

## 同じ原因の場面の一覧

連携がないことで起きる場面を、今の main から数え上げた。どの場面も、記録か `連携: なし` の末尾で分ける。

| 場面 | 今の置き場所 | この設計で |
| --- | --- | --- |
| 作った直後の 120 秒の待ちと警告と連携の案内 | `squad-pr-link`（`warn`・`warn_not_found`） | 記録がないときは今のまま待つ。切り替えたあとは出さない |
| 役の `紐付けの失敗:` の段落 | `pr.md` の「PR を作る・実装を積む」 | 0 と 3 で終わるので置かない |
| リーダーの紐付けの判定の表と、試み直しの説明 | `leader-pr-link.md` の「PR の紐付けの確認」 | 紐付いていないの行に、`連携: なし` の扱いを足す |
| PR を受け取ったときの知らせ | `leader-pr-ci.md` の「紐付いていない PR を受け取ったときの知らせ」 | 出さない。切り替えた `squad-pr-link` が連携なしの知らせを多くて 1 回出す |
| マージを頼むコメントの行と段落と案内 | `leader-pr-merge.md` の「人間を呼ぶコメントに添える行」、`decide` | `done` の 1 行だけにする |
| ほかの理由で人間を呼ぶコメントの行と段落と案内 | 同上 | 添えない |
| 試み直しの記録と間隔 | `squad-pr-watch link-check` | 紐付かなかった結果は書かず、間隔は `pr_link_tried_at` で測る |
| Dependabot の PR の待ちと警告 | `squad-dependabot-merge` の紐付け | 記録があれば待たず、警告を出さない |
| `done` を変える人の表 | `SKILL.md` の「タスクの状態と担当」 | 連携なしでは人間と足す |
| 人間に頼むことの例の「PR の紐付けの連携」 | `leader-repeat.md` | 変えない。連携をつなぐのは今も人間の判断である |
| 依頼の前と止める前の `link-check` | `leader-review-request.md`・`leader-run-stop.md`・`leader-review-stuck.md` | 変えない。行の先頭で分けており、扱いは上の各場面の手順に従う |
| マージ待ちの見張り | `unlinked`・`unlinked-check` | 変えない |
| 候補が 0 件のときの案内 | `lib/questions.sh` | `multica repo add` を示す |
| 連携を前提とする説明 | README と手順書の 5 か所 | 連携の有無の違いと、記録と印を消す手順を書く |

## 同じ形の経路の一覧

紐付いたのに警告が出る、途中の失敗で試み直しや知らせが失われる、別の PR の紐付けで進行中の PR の扱いが変わる、初回の知らせが 2 件以上になる。この 4 つの形の経路を、今の main のスクリプトと手順から数え上げた。

### 紐付いたのに警告が出る経路

| 経路 | この設計で |
| --- | --- |
| `squad-pr-link` の期限内の 200 のあと、`pr_url` を書けない（記録の有無どちらも） | 3 で終わり、警告を出さない。記録を消す |
| 期限後に届いた 200 | 404 だけではないので記録を書かない。一覧の読み直しで PR があれば `紐付いていました:` で 0 |
| 失敗のあとの一覧に PR があり、`pr_url` を書けない | 3 で終わり、記録を消す |
| 失敗のあとの一覧を読めない | 紐付いたか分からないので、今の警告で 1。紐付いていれば、次の `link-check` が一覧で紐付いていると読む |
| `pr_url` があり、API を飛ばした | 今と同じ `紐付けていません:` で 0。警告は出さず、記録は消さない |
| Dependabot の 200 のあと、`pr_url` を書けない | 紐付けの失敗の文でなく、書けなかったことの 1 行にする |
| Dependabot の 200 以外のあと、一覧に PR がある | 紐付いたと扱い、`pr_url` を書いて記録を消す |
| `link-check` の試み直しで 200 なのに一覧にない | 今と同じ `一覧にない（200）`。紐付いたとは読まない |

### 途中の失敗で試み直しや知らせが失われる経路

| 経路 | この設計で |
| --- | --- |
| 切り替えの 1〜3 のどこかを書けない | 切り替えをやめて今の警告で 1。マークがあれば今の試み直しが働く（[切り替えの表](#連携なしへの切り替え)） |
| 切り替えの 4 で印を書けない | 1 で終わり、記録は残す。記録の `pr:` がこの PR なら `link-check` が印を戻し、ほかの PR なら今の動作 |
| 4 で印を書けず、`link-check` の前に別の PR が紐付いて記録を消す | 戻さず、今の試み直しと依頼の動作。役は 1 で失敗を引き継いでいる |
| 印を書けたあと、知らせの前に別の PR が紐付いて記録を消す | 知らせは記録を読まないので、切り替えの 5 で 1 回出す |
| タスクの一覧にほかの PR があり、この PR が 404 で待ち切れる | 連携なしにせず、今の警告で 1。`link-check` の食い違いの手順になる |
| 切り替えの途中に `link-check` が流れる | [重なったとき](#切り替えと-link-check-が重なったとき)の表のとおり、同じ扱いに落ち着く |
| 切り替えの途中で実行が止まる | [途中で止まったとき](#途中で止まったとき)の表のとおり戻る |
| PR を作った役が、引き継ぎを書く前に止まる | 知らせは `squad-pr-link` の中で出るので、役の引き継ぎに左右されない |
| 知らせの投稿に失敗する | 投稿し直さず 0 件。マージを頼むコメントの `done` の行で、人間に `done` を頼む（[初回の知らせの経路](#初回の知らせの経路)） |
| `pr_link_tried_at` を書けない | その回は呼ばない。書けた回から間隔が働く |
| API の環境がない | 試みに数えず、トークンが戻った次の回で試み直す |
| 試み直しの `紐付いた` の記録を投稿できない | 次の `link-check` が一覧で紐付いていると読み、記録と印を消す |
| 記録を消せない | 次の PR が 1 回の試みで紐付いて消す |
| 印や `pr_link_pending` を消せない | 紐付いている PR では、印を `連携: なし` に使わない。次の `link-check` が消し直す |
| 記録があるときの切り替えで印を書けない | 今の警告で 1。記録の `pr:` はほかの PR なので戻さず、今の試み直しと依頼の動作になる |
| 1 で終わった PR を、`link-check` が連携なしとして扱う | 戻しの条件を満たすときだけ起きる。`link-check` の扱いを正とし、リーダーと `decide` は役の段落を外す |
| 0 で終わった PR の印がない | 起きない。0 で終わるのは印を書けたときだけである |

### 別の PR の紐付けで、進行中の PR の扱いが変わる経路

連携なしで始めた進行中の PR を A、あとで紐付いた PR を B、B のあとに作る PR を C とする。A の扱いは A の印だけで決まり、記録の有無で変わらない。

| 経路 | A | C |
| --- | --- | --- |
| B が `squad-pr-link` の 200 で紐付く | 連携なしのまま。依頼を出さない | 記録がないので 120 秒待つ |
| B が一覧の読み直しで紐付く | 同上 | 同上 |
| B が `link-check` の試み直しで紐付く | 同上 | 同上 |
| Dependabot の PR が紐付く | 同上 | 同上 |
| 人間が記録を消す | 同上 | 同上 |
| 記録が読めない（シンボリックリンクなど） | 同上 | 記録がないものとして 120 秒待つ |
| A のタスクの `pr_url` が新しい PR に替わる | 印の URL が合わないので、新しい PR は自分の紐付けの結果で決まる | 変わらない |
| A 自身が紐付く | `link-check` が記録と印を消して、今の動作に戻る。知らせは消さない | 120 秒待つ |
| A が 4 の印を書けずに 1 で終わり、A の `link-check` の前に B が紐付く | A は連携なしになっていない。今の試み直しと依頼の動作で、知らせは出ない | 120 秒待つ |
| A が印を書けたあと、A の知らせの前に B が紐付く | 連携なしのまま。A の切り替えの 5 で知らせを 1 回出す | 120 秒待つ |

### 初回の知らせの経路

知らせを書くのは、記録を結んで印を書けた `squad-pr-link` の実行の 5 だけである。最後の列の件数は、そのあとどの役の `link-check` と見張りを流しても変わらない。

| 経路 | この設計で | 最後の知らせ |
| --- | --- | --- |
| 404 で待ち切れ、記録を結び、印を書けた | 5 で投稿する | 1 件 |
| 上のあと、担当のスクワッドのリーダー・別のスクワッドのリーダー・`decide`・CI の見張り役が `link-check` を流す | どの役の `link-check` も、知らせを書かず、読まず、消さない | 1 件 |
| 上のあと、PR がマージされ、マージ待ちの見張りが止まる | 見張りは知らせを書かない | 1 件 |
| 切り替えのあと、最初の `link-check` の前に同じ PR が紐付く | 知らせは 5 で出ている。次の `link-check` が記録・`pr_link_pending`・印を消し、知らせは消さない | 1 件 |
| 切り替えの 1 か 2 のあとに、`link-check` の試み直しで紐付く | 切り替えは続いて 5 で投稿する。次の `link-check` が記録と印を消す | 1 件 |
| 切り替えの 3 と 4 のあいだに `link-check` が流れる | `link-check` は印を戻すが投稿しない。`squad-pr-link` が 4 で同じ印を書き、5 で投稿する | 1 件 |
| 同じリポジトリの 2 つの PR が同時に待ち切れる | 記録を結べるのは 1 つだけで、もう 1 つは `記録があった` になり投稿しない | 結んだ PR に 1 件、もう 1 つは 0 件 |
| 同じ PR で `squad-pr-link` を流し直す | `pr_url` があるので、API と切り替えを飛ばす | 前の件数のまま |
| 5 の投稿に失敗する。返信先を断られたときと、引数がなく根のコメントを断られたときを含む | 投稿し直さず、終了コードと出力も変えない | 0 件 |
| 投稿の応答は失敗だが、コメントはできていた | 投稿し直さないので重ならない | 1 件 |
| 4 と 5 のあいだで止まる | 印で連携なしとして扱うが、知らせは出ない | 0 件 |
| 4 の印を書けずに 1 で終わり、`link-check` が印を戻す | `link-check` は投稿しない | 0 件 |
| 4 の印を書けず、`link-check` の前にこの PR か別の PR が紐付く | 切り替えは成り立っていない。役は 1 で失敗を引き継いでいる | 0 件 |
| 種類が `記録があった` | 投稿しない | 0 件 |
| 印を書けたあと、5 の前に別の PR が紐付くか、人間が記録を消す | 5 は記録を読まないので投稿する | 1 件 |
| 人間が印を消す | 出ていた知らせは残る | 消す前の件数 |
| タスクの `pr_url` が新しい PR に替わる | 前の PR の知らせは残る。新しい PR は自分の切り替えで決まる | PR ごとに多くて 1 件 |
| 別のホストで同じリポジトリの PR が待ち切れる | 記録がホストごとなので、ホストごとに記録を結んだ PR が出す | PR ごとに多くて 1 件 |
| スクワッドの担当やリーダーが替わる | 知らせは役やリーダーで決まらないので変わらない | 前の件数のまま |

## 入力と信頼の表

記録と印はガードではないが、人間への依頼を止める判定に使うので、読む入力ごとに信頼する条件を決める。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 記録のファイル（ホストのスクリプトか人間だけが書く） | `squad-pr-link`・`link-check`・`squad-dependabot-merge` の記録の有無 | パスの各部分が許した文字だけで、パスと上のディレクトリがシンボリックリンクでなく、普通のファイルである | ないものとして読み、標準エラーに 1 行出す。書きも消しもしない |
| 記録の `pr:` の行（同上） | `link-check` の印の戻し | 記録のファイルの条件を満たし、`pr_link_pending` と `pr_url` が正規形で同じ PR で、`pr:` がその PR と正規形で同じ | 印を戻さない |
| metadata の印 `pr_link_no_integration`（`squad-pr-link` が書く。役と人間も書ける） | `link-check` の `連携: なし` | 形が合い、URL が `pr_url` と正規形で同じ | 印がないものとして読み、今の動作にする |
| タスクの `project_id`（サーバーが返す） | 記録のパス | 許した文字だけの値である | 記録を書かず読まず、今の動作にする |
| metadata の `repository` と `pr_url`（役と人間が書ける） | 記録のパスのリポジトリと、記録を書く条件 | `pr_url` が PR の URL の形で、`repository` と小文字で同じリポジトリを指す | 今の `作業先と違う`・`不正な pr_url` の判定に従い、記録を読まず書かない |
| metadata の `pr_link_tried_at`（`link-check` が書く。役と人間も書ける） | 試み直しの間隔 | 形が合い、今より前の時刻で、URL が今の PR と正規形で同じ | ないものとして読み、間隔を前の記録の時刻から測る |
| タスクの PR の一覧（サーバーが返す） | 紐付いたかの判定と、記録と印の消去 | 今の `link-check` と同じく、正規形の `html_url` が PR と同じ | 紐付いていないと読む。読めないときと、ほかの PR があるときは、連携なしにせず今の扱いにする |
| 試み直しの記録のコメント（書き手を選べない） | 一度紐付いたかと、間隔 | 今と同じく作者がエージェントで、`/note` の 2 行目が決まった形 | 読まずに飛ばす |
| `squad-pr-link` の 3 つ目の引数のきっかけのコメントの ID（PR を作った役が渡す） | 知らせの返信先 | UUID の形である。どのタスクのコメントかは、サーバーが投稿のときに照合する | 形が合わなければ引数の誤りで 2 で終わる。サーバーが断れば投稿の失敗とし、投稿し直さない |

記録や印を人間が手で作ると、そのリポジトリや PR は連携なしとして扱われる。これは記録を消すのと同じく人間の操作であり、次に紐付けば消える。記録と印の偽造で起きるのは紐付けの依頼が出ないことだけで、マージや状態の変更は起きない。知らせは、ほかの役や人間が書いた同じ形のコメントを読まないので、偽の知らせで動作は変わらない。

## 残る危うさ

記録はホストのファイルなので、同じプロジェクトの役が別のホストで動くと、記録がホストごとに分かれる。使用率の確認の状態と同じ前提で、ホストを分けたときは、それぞれのホストで 1 回ずつ待ち切れて記録ができる。知らせは、記録を作った PR ごとに多くて 1 件である。

連携があっても、同期が 120 秒より遅れると連携なしと記録する。次の PR は 1 回の試みで紐付けば記録が消えるが、同期が遅れ続けると連携なしのままになる。そのあいだ、人間は `done` の行で頼まれたとおりタスクを `done` にする。

知らせは、切り替えた実行の 1 回の投稿だけで出し、投稿し直さない。投稿に失敗した回と、4 と 5 のあいだで止まった回と、4 の印を書けずに `link-check` が印を戻した回は、0 件になる。そのときも、マージを頼むコメントの `done` の行で、連携なしとして扱うことと `done` を頼む。連携の確認の案内と、紐付けば戻ることは伝わらない。

PR を作った役がきっかけのコメントの ID を渡し忘れると、コメントがきっかけの実行では根のコメントが断られ、0 件になる。重ならない向きの失敗なので、受け入れた。

人間が記録と `pr_url` を消して、同じ PR で `squad-pr-link` を流し直すと、切り替えをやり直して知らせがもう 1 件出る。人間が切り替えをやり直す操作なので、受け入れた。

なし。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| `link-check` が知らせを書き、コメントを数えて 1 件にそろえる。書き手をリーダーや担当のスクワッドのリーダーに絞る案を含む | `link-check` は何度も、いくつもの役から流れる。投稿に重ねない鍵がないので数えて消す決まりが要り、書く役や、マージで見張りが止まったあとにそろえる役の穴が続いた |
| 投稿の前に metadata に投稿中の印を書き、ほかの実行を止める | metadata は後に書いたほうが残るだけなので、重なった 2 つの実行がどちらも自分が書けたと読む。止まった実行の印が残ると、知らせが出なくなる |
| `squad-pr-link` が投稿に失敗したら、投稿し直す | 応答が失敗でもコメントができていることがあり、鍵がないので重なる。0 件のときも、マージを頼むコメントの `done` の行で同じことを頼める |
| `squad-pr-link` が、4 の印より前に知らせを投稿する | 印を書けずに 1 で終わり、戻す前に別の PR が記録を消すと、連携なしとして扱わない PR に知らせが残る |
| `squad-pr-link` が、きっかけを知らないまま根のコメントで投稿する | コメントがきっかけの実行では根のコメントが断られる。きっかけの ID は引数で渡せる |
| 記録だけで、新しい PR の待ちと進行中の PR の扱いの両方を決める | 別の PR が紐付いて記録が消えると、連携なしで始めた進行中の PR に紐付けの依頼が出る |
| PR を作った役が、引き継ぎに知らせの段落を書く | 手順にすると書き漏らしを仕組みで防げない。`squad-pr-link` が記録を結んだ場で投稿すれば、役の手順に頼らない |
| リーダーが知らせを書く | 手順にすると、書き漏らしを仕組みで防げない。リーダーの回は何度も流れるので、重ねない決まりも要る |
| 4 の印を書けなくても、記録の `pr:` がこの PR なら 0 で終わる | 印のないまま 0 で終わり、`link-check` の前に別の PR が記録を消すと、連携なしと伝えた PR に試み直しと依頼が出て、知らせが出ない |
| 期限内の 200 のあと `pr_url` を書けないときも 1 で終わり、文だけ変える | 役が `紐付けの失敗:` の段落を置き、紐付いた PR に警告が残る |
| 一覧を読めないときも、404 だけなら連携なしにする | 自動の関連付けで紐付いている PR を、連携なしにしてしまう |
| `pr_link_tried_at` を、呼んだあとに書く | 書けないと間隔の跡が残らず、`link-check` のたびに API を呼ぶ |
| マージ待ちの見張りがマージを確認して `done` にする | 人間が `done` にすると決めたため。見張りに `done` の照合を足すと、誤って閉じる危うさのほうが大きい |
| 連携の状態を API で読む | 読める API がなく、要件で除いた |
| セットアップで連携の有無を尋ねる | 人間が誤って答えると直す所がない。紐付けの結果で見分けるほうが確かである |
| 404 以外の失敗や通信の失敗でも記録する | サーバーの一時の失敗で、連携のあるリポジトリを連携なしにしてしまう |
| Dependabot の経路でも記録を書く | 同期の遅れで記録が増えやすく、役の PR の経路と条件をそろえられない |
