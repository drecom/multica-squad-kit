# 作った直後に紐付かなかった PR を、あとの区切りで紐付け直す

PR を作った直後の紐付けが失敗した PR を、あとの区切りで見張りのスクリプトが紐付け直す。紐付け直しは、リーダーと `squad-review-next decide` が流す `squad-pr-watch link-check` の中で行う。マージ待ちの見張りの `unlinked-check` でも、間隔を空けて行う。試みるたびに、時刻と結果をタスクに記録する。

この文書は、試み直す時機とマークと記録の形を書く。人間が外した紐付けを戻さない条件と、`squad-dependabot-merge` の経路の扱いも書く。それぞれの理由も添える。

## 目的と範囲

今は、PR を作った役が `squad-pr-link` を 1 回だけ呼び、120 秒のうちにサーバーが PR を見つけなければ、紐付けは人間の手に移る。metadata に `pr_url` があると API を呼ばないので、あとで呼び直しても紐付かない。サーバーが PR をあとから同期しても、人間がタスクの画面で紐付けるか、マージのあとにタスクを `done` にするまで、紐付かないままになる。

目的は次の 4 つである。

1. 最初の 120 秒で紐付かなかった PR を、あとの区切りで自動で紐付け直す
2. 紐付いたあとは、人間を呼ぶコメントに、紐付けの依頼と `紐付けの失敗:` の段落を添えない
3. 紐付かないあいだは、今の依頼（タスクの画面で紐付けるか、マージのあとに `done` にする）を続ける
4. 試み直すたびに時刻と結果をタスクに残し、遅れて同期したのか、サーバーが保存しなかったのかを見分けられるようにする

次は対象にしない。

- 120 秒の待ちを延ばすこと。`squad-pr-link` の待ち方は変えない
- サーバーが PR を保存しない原因を調べること
- `squad-dependabot-merge` の紐付けの動作。扱いは [squad-dependabot-merge の経路](#squad-dependabot-merge-の経路)に書く
- 更新の前に紐付けが失敗したタスク。[試み直す PR のマーク](#試み直す-pr-のマーク)がないので、試み直さない

## 試み直す時機

試み直しは、`squad-pr-watch link-check` が「紐付いていない」と判定する直前に 1 回行う。`link-check` は、要件の 3 つの時機にすでに流れているので、新しい呼び出しを足さずに済む。

| 要件の時機 | 流れる `link-check` | 流す人 |
| --- | --- | --- |
| 役が PR に push したあと | 役が push して返した引き継ぎを、リーダーが受けたとき | リーダー |
| リーダーが PR を受け取ったとき | PR を受け取ったとき | リーダー |
| マージを頼む前 | 人間のマージへ回す前の確認と、`decide` の紐付けの確認 | リーダーか、返事をそろえた役の `decide` |

役が push する実行の中では試み直さない。push した役は、すぐあとにリーダーへ返し、リーダーの `link-check` が試み直すためである。push のあとの GitHub の通知でサーバーが PR を同期することがあるので、少し遅れて試すほうが紐付きやすいと見ている。

リーダーの手順の参照ファイル（`leader-pr-checks.md`）の時機の一覧では、「PR を受け取ったとき」に、役が push して返した引き継ぎを受けたときを含めると書く。今もリーダーは引き継ぎのたびに `link-check` を流していると読めるが、文で決めて、1 つ目の時機が抜けないようにする。

### マージ待ちの見張りでの試み直し

`unlinked-check` は、マージ待ちのあいだ 1 時間ごとに、中で紐付けを判定する。この判定でも、前の記録から 6 時間たっていれば試み直す。条件と動作は `link-check` と同じで、間隔だけが違う。

マージ待ちで紐付くと、`unlinked-check` は今の動作のとおり見張りを止める。マージのあとは、GitHub 連携がタスクを `done` にする。人間は、マージの依頼にある「マージのあとに `done` にする」作業をしなくて済む。

1 時間ごとに試み直すと、最大 72 時間のマージ待ちで記録が 72 件まで増える。6 時間の間隔なら記録は最大 12 件で、遅れて同期した PR も 6 時間のうちに紐付く。記録の数と紐付くまでの遅れを比べ、6 時間にした。

### 間隔

前の試み直しから間隔がたっていなければ、試み直さずに「紐付いていない」と判定する。リーダーは 1 回の実行で `link-check` を何度か流すことがあり、同じ結果の記録を重ねないためである。

| 呼び出し | 間隔 |
| --- | --- |
| `link-check`（リーダーと `decide`） | 5 分 |
| `unlinked-check` の中の判定 | 6 時間 |

前の試み直しの時刻は、[信頼する記録](#信頼する記録)のうち、最後のもののコメントの作成時刻で読む。

## 試み直す PR のマーク

試み直すのは、作った役の `squad-pr-link` が失敗をマークに残した PR だけである。マークは metadata の `pr_link_pending` で、値は `squad-pr-link` に渡した PR の URL である。

`squad-pr-link` は、紐付けに失敗して 1 で終わる前にマークを書く。書くのは、タスクを読めて `pr_url` がなく、作業先が PR のリポジトリと同じだったときの失敗である。404 で待ち切れたとき・通信の失敗・ほかの状態コード・トークンなどがないときが当たる。

作業先と違うときは書かない。試み直しても、同じ理由で断るためである。

マークを書けなかったときは、標準エラーに何も足さず、今と同じ警告だけを出す。`紐付けの失敗:` の段落の形を変えないためである。試み直しは起きず、今の動作と同じになる。

マークは、紐付いたと分かったときに消す。試み直しで紐付いたときと、試み直す前に紐付いていたと分かったときである。マークを消すのに失敗しても、[一度紐付いた PR](#一度紐付いた-pr) の判定で試み直しを止める。

## 一度紐付いた PR

一度紐付いた PR は、マークが残っていても試み直さない。人間がタスクの画面で外した紐付けを、試み直しで戻さないためである。

一度紐付いたかは、タスクのコメントの[信頼する記録](#信頼する記録)で読む。同じ PR の正規形で、結果が `紐付いた` か `紐付いていた` の記録が 1 つでもあれば、一度紐付いた PR とする。

記録は、判定が紐付きを見たときにだけ残る。判定と判定の間に付いて、次の判定の前に外れた紐付けは記録に残らず、一度紐付いた PR としない。この PR は試み直すので、人間が外した紐付けを戻すことがある（[残る危うさ](#残る危うさ)）。

一度紐付いた PR では、API を呼ばず、記録も書かない。マークを消し直し、今と同じ「紐付いていない」を出す。紐付けの依頼は、今のとおり人間に届く。

タスクのコメントを読めないときは、一度紐付いたかを決められないので、試み直さない。マークも記録も変えず、今と同じ「紐付いていない」を出す。

紐付いたと分かったときは、先に記録を書き、そのあとマークを消す。片方が失敗しても、もう片方は行う。記録が残れば、マークが残っても試み直しは止まる。記録とマークの削除の両方が失敗したときにも、[残る危うさ](#残る危うさ)に書いた場面が起こり得る。

記録は、きっかけごとのスレッドに分かれて残る（[置き場所](#置き場所)）。判定はタスクのすべてのコメントから信頼する記録を読むので、どのスレッドにある記録も数える。

## 試み直しの動作

`link-check` は、今の判定のあとに次を行う。出力の 1 行の形、終了コード、判定の種類は変えない。

1. 判定が「紐付いていない」で、マークがあり、マークの URL が `pr_url` と同じ PR を指すときだけ、次へ進む。比べるのは、`link-check` が `pr_url` に使う正規形どうしで、大文字と小文字を区別しない
2. タスクのコメントを読む。読めなければ、試み直さずに「紐付いていない」を出す
3. [一度紐付いた PR](#一度紐付いた-pr) なら、マークを消し直し、試み直さずに「紐付いていない」を出す
4. [間隔](#間隔)の中なら、試み直さずに「紐付いていない」を出す
5. 紐付けの API を 1 回だけ呼び、404 でも待たない。時間切れは `squad-pr-link` と同じ 30 秒にする
6. 紐付いた PR の一覧を読み直す。[結果](#結果)の表で、出す行、マーク、記録の結果を決める

判定が「紐付いている」でマークがあるときは、API を呼ばない。タスクのコメントを読み、同じ PR の `紐付いた` か `紐付いていた` の[信頼する記録](#信頼する記録)がなければ、`紐付いていた` の記録を書いてマークを消す。人間かサーバーが紐付けた時点を、記録から読めるようにするためである。

その記録がすでにあれば、記録を書かずにマークだけを消し直す。マークの削除が続けて失敗しても、`link-check` のたびに同じ記録が増えないようにするためである。コメントを読めないときは、記録を書かずにマークを消す。紐付いていることは一覧で分かっており、マークを消せば試み直しは起きないためである。

判定が「食い違い」「作業先と違う」「不正な pr_url」「pr_url なし」「未確認」のときは、試み直さず、マークも記録も書かない。

マークを消すことと記録を書くことが失敗しても、出力の行と終了コードは変えない。記録が書けずマークが残れば、次の `link-check` が `紐付いていた` の記録を書き直す。記録が書けてマークの削除だけが失敗したときは、次の `link-check` はマークだけを消し直す。

API を呼ぶ部分は、`squad-pr-link-lib` に 1 回だけ呼ぶ関数として切り出す。`pr_link_pull_request` は、待ちの繰り返しの中でこの関数を呼ぶ形に変え、入力・出力・待ち方を変えない。トークンは、今と同じく標準入力から curl に渡し、引数と出力に出さない。

`link-check` は、今は書き込まないと決めている。この設計で、マークの削除、記録のコメント、紐付けの API の呼び出しを書き込む。`squad-pr-watch` の使い方のコメントと、この決まりを書いた文書の文を直す。

`link-check` の使い方は `link-check <タスク> [<きっかけのコメント>]` にする。きっかけのコメントは、記録を返信にする元である（[置き場所](#置き場所)）。省いたときの判定と出力は、渡したときと同じである。

## 試み直しの記録

試み直しの結果は、タスクのコメントに 1 回 1 行で残す。遅れて同期したかは、`見つからない（404）` のあとに `紐付いた` が続くかで読む。マージまで `見つからない（404）` だけが続けば、最後の試み直しの時刻まで、サーバーは PR を持っていなかったことになる。

### 行の形

記録のコメントは、1 行目を `/note` にし、2 行目に次の行を置く。`/note` にするのは、記録でエージェントの実行を起こさないためである。

```text
紐付けの試み直し: <結果> pr: <PR の正規形> 時刻: <UTC の時刻>
```

時刻は `2026-11-24T03:04:05Z` の形にする。`紐付けの試み直し:` は新しい固定の行である。記録と、間隔と一度紐付いたかの判定だけに使い、ほかの判定には読ませない。

### 結果

API を呼んだあとの結果は、読み直した一覧を先に見て決める。一覧が API の応答より後の状態を表すためである。上の行から順に見て、最初に当たる行を使う。

| 読み直した一覧 | API の結果 | 記録の結果 | 出す行 | マーク |
| --- | --- | --- | --- | --- |
| 読めない | どれでも | `未確認（一覧を読めない）` | 今と同じ「未確認」の行 | 残す |
| PR がある | どれでも | `紐付いた` | `紐付け: 紐付いている` | 消す |
| ほかの PR がある | どれでも | `食い違い` | 今と同じ「食い違い」の行 | 残す |
| 空 | 200 | `一覧にない（200）` | `紐付け: 紐付いていない` | 残す |
| 空 | 404 | `見つからない（404）` | `紐付け: 紐付いていない` | 残す |
| 空 | 通信の失敗、ほかの状態コード、トークンなどがない | `失敗（<理由>）` | `紐付け: 紐付いていない` | 残す |

API を呼ばずに書く記録の結果は、`紐付いていた` だけである。試み直す前の判定で、すでに紐付いていたときに書く。

`失敗（<理由>）` の理由は、`squad-pr-link-lib` の理由の文を写す。`一覧にない（200）` は、サーバーが受け付けたのに一覧に出ない場面で、次の試み直しを待つ。`食い違い` と `未確認（一覧を読めない）` のあとは、次の判定が「紐付いていない」にならないかぎり試み直さない。

### 信頼する記録

間隔と一度紐付いたかの判定に数えるのは、次の 3 つをすべて満たすコメントだけである。

1. そのタスクのコメントで、書き手がエージェントである
2. 1 行目が `/note` で、2 行目が `紐付けの試み直し:` で始まる
3. 2 行目の `pr:` の値が、今の `pr_url` の正規形と同じである

時刻はコメントの作成時刻を使い、本文の `時刻:` は読まない。本文の時刻は書き手が選べるためである。

### 置き場所

記録は、`link-check` に渡されたきっかけのコメントへの返信にする。コメントで起きた実行は、きっかけへの返信しか書けず、根のコメントの投稿は拒否されるためである。この約束は、CLI の `multica issue comment add --help` の `--parent` の説明にある。

要件の 3 つの時機の `link-check` は、どれもコメントで起きた実行で流れる。`ci` と `unlinked` が、きっかけを `ci_watch_thread` に残して返信するのと同じ形にする。

| 呼び出す人 | 渡すきっかけ |
| --- | --- |
| リーダー | その実行のきっかけのコメントで、コメントの返信に使う親と同じ値である。コメントで起きていない実行では渡さない |
| `decide` | `<回のコメント>`。`decide` が依頼を返信で書く元と同じである |
| `unlinked-check` | metadata の `ci_watch_thread` で、見張りの規則と `止めた:` の記録の返信先と同じである。ないときは渡さない |

きっかけを渡さないときだけ、記録を根のコメントにする。根のコメントを書けるのは、割り当てで起きた実行など、コメントで起きていない実行だけだからである。

記録は、きっかけごとのスレッドに分かれる。間隔と一度紐付いたかの判定は、タスクのすべてのコメントから信頼する記録を読むので、分かれても変わらない。返信はスレッドを増やさないので、試み直しのたびにスレッドが増えることもない。

記録をまとめる元のコメントの ID は、metadata に残さない。返信の元をきっかけで決めるので、元のコメントを覚えておく必要がないためである。

きっかけと別のスレッドへの返信が通るかは、未確認である。試せるのはコメントで起きた実行の中で、試すと余分なコメントがタスクに残るため、実機で試していない。`--help` の文は「きっかけの下に返信しなければならない」と読めるので、通らない前提にし、きっかけと別のスレッドへは書かない。

投稿が拒否されたときは、ほかの投稿の失敗と同じに扱い、出力の行と終了コードは変えない。記録が残らないので、次の `link-check` は[間隔](#間隔)の中でも試み直す。一度紐付いたかの判定にも数えられない。呼び出す人がきっかけを渡すのは、この 2 つを働かせるためである。

記録は、PR の本文と PR のコメントには書かない。タスクの識別子と進行の記録は、Multica 側に置く決まりのためである。

## 人間への依頼と警告

人間を呼ぶコメントの、紐付けの依頼と `紐付けの失敗:` の段落は、`link-check` が「紐付いていない」と出したときだけ添える。試み直しは「紐付いていない」と出す前に行うので、紐付けばこの 2 つは添わらない。リーダーの手順と、`decide` のマージの依頼は、判定の読み方を変えない。

`decide` が使用率の待ちで人間を呼ぶコメントは、今は紐付いていても `紐付けの失敗:` の段落と連携の案内を添える。段落を書く関数を、紐付いていないときの条件の外で呼んでいるためである。この設計で、その呼び出しを条件の中へ移し、マージの依頼と同じく紐付いていないときだけ添える。[review-next-step.md](review-next-step.md#24-時間を超えるとき) は今も紐付いていないときだけ添えると書いており、コードを文書に合わせる。

紐付かないあいだは、`link-check` が今と同じ「紐付いていない」を出す。紐付けの依頼とマージのあとに `done` にする依頼は、今のまま続く。`unlinked` の登録と、紐付いていない PR を受け取ったときの知らせも変わらない。

マージ待ちで紐付いたときは、書き済みのマージの依頼を直さない。見張りが止まり、マージのあとは連携が `done` にするので、人間が `done` にする作業は要らなくなる。人間が `done` にしても、結果は同じである。

PR を作った役の引き継ぎにある `紐付けの失敗:` の段落は、作ったときの事実なので、そのまま残る。リーダーは、紐付いたあとはこの段落を写さない。

## squad-dependabot-merge の経路

`squad-dependabot-merge` の紐付けの動作は変えない。この経路は、失敗しても `pr_url` を書かず、同じ PR を次に回すときに 120 秒の待ちで紐付け直している。今も試み直しがあるので、要件の目的を満たしている。

この経路は `squad-pr-link` を呼ばないので、マークは書かれない。そのタスクは `pr_url` を持たないので、`link-check` も試み直さない。

変えるのは、`squad-pr-link-lib` の API を 1 回呼ぶ部分を関数に切り出すことだけである。`pr_link_pull_request` の入力・出力・待ち方は変えないので、この経路の動作は同じである。今の `squad-dependabot-merge` のテストを変えずに通すことで確認する。

## 入力と信頼の表

この設計は、紐付けの API に Multica のトークンを使い、役と人間が書ける metadata とコメントを読む。読む入力と信頼する条件は次のとおりである。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| metadata の `pr_link_pending`（`squad-pr-link` が書く。役と人間も書ける） | `link-check` の、試み直すかの判定 | 正規形にでき、`pr_url` の正規形と同じ PR を指す。紐付いた一覧が空で、作業先が PR のリポジトリと同じ | 試み直さず、今の判定の行を出す |
| metadata の `pr_url`（役が書く。人間も書ける） | 紐付けの API に渡す URL | 今の `link-check` の検証（正規形、作業先と同じリポジトリ）を通る | 今と同じく「作業先と違う」か「不正な pr_url」を出し、試み直さない |
| タスクのコメントの `紐付けの試み直し:` の行（書き手を選べない） | 間隔の判定と、一度紐付いたかの判定 | [信頼する記録](#信頼する記録)の 3 つを満たす。時刻はコメントの作成時刻を使う | 判定に数えない |
| タスクのコメントの一覧（サーバーが返す） | 上の 2 つの判定 | 読めて、今の CLI の読み取りの検証を通る | 試み直さず、マークも記録も変えず、今の判定の行を出す |
| `link-check` のきっかけのコメントの引数（リーダー、`decide`、`unlinked-check` が渡す） | 記録を返信にする元のコメント | 書くのは記録の返信だけで、判定には使わない。元のコメントの書き手と形は確認しない | サーバーが投稿を拒否すれば記録は残らず、出力の行と終了コードは変えない |
| metadata の `ci_watch_thread`（見張りのスクリプトが書く。役と人間も書ける） | `unlinked-check` が渡すきっかけ | 今の `unlinked-check` が `止めた:` の記録に使うのと同じ | サーバーが投稿を拒否すれば記録は残らず、出力の行と終了コードは変えない |
| 紐付いた PR の一覧（サーバーが返す） | 試み直しの前後の判定 | 今の `link-check` の欄の検証を通る | 前は今と同じく「未確認」を出して試み直さない。後は[結果](#結果)の表の 1 行目にする |
| 環境変数の `MULTICA_TOKEN` と `MULTICA_SERVER_URL`（ランタイムが渡す） | 紐付けの API の呼び出し | 今の `squad-pr-link-lib` と同じ。トークンは標準入力から curl に渡し、出力と記録に出さない | 試みたことにし、[結果](#結果)の表で記録を決める。マークは残す |

エージェントが偽の記録を書いても、働くのは試み直しを止める側だけである。紐付けを戻す向きには働かないので、記録の書き手はエージェントであることだけを確認する。

試み直しが呼ぶのは、`pr_url` を Multica のタスクに紐付ける API だけである。GitHub への書き込みはしないので、書き込んでよいリポジトリの決まりとガードには触れない。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイル（リーダーの手順の参照ファイル）で、`link-check` を流す時機を文で決める。条件の 3 つを次に書く。

### 根拠

合意された要件による新しい機能なので、要件を合意したタスクを失敗の記録に代える。要件のもとになった、紐付けが失敗した 2 件の記録は、タスクのコメントにある。

### 働いた跡

手順が働くと、試み直しの対象のタスクに、[行の形](#行の形)の記録のコメントが残る。跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 項目 | 値 |
| --- | --- |
| 形 | `kind: "comment"` |
| `pattern` | `(?m)^紐付けの試み直し:` |
| `author_type` | `agent` |

この跡は、紐付けが失敗したタスクが 20 件の中にないと 0 回になる。0 回のときに削る候補にするかは、見直しで人間が判断する。

### 仕組みにしない理由

試み直しそのものは、`link-check` の中の仕組みにした。手順に残るのは、役が push して返したときにリーダーが `link-check` を流すことだけである。この時機も仕組みで流す案を 2 つ比べ、選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| ホストの `git push` のガードが、push のあとに試み直す | ガードは書き込み先を止める安全の境界で、トークンを使う書き込みを足すと境界の役目が広がる。ガードは push の相手のタスクを知らず、metadata を読めない |
| 定期のオートパイロットが、紐付いていないタスクを見回って試み直す | 導入先でオートパイロットの登録が増え、流し直しで登録が変わる。要件の時機（push・受け取り・マージの前）と合わず、タスクのない時刻にも実行を使う |

2 つの案は、作る手間ではなく、上の表の理由で選ばなかった。リーダーは、役が返すたびに今も `link-check` を流しており、手順の文はその動きを時機として決めるものである。

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと見張りのスクリプトとリーダーの手順が替わる。替わったあとに紐付けが失敗した PR は、あとの区切りで紐付き得る。

| 利用者 | 変わること |
| --- | --- |
| 人間 | 遅れて同期した PR では、紐付けの依頼と、マージのあとに `done` にする作業が要らなくなる。紐付けが失敗したタスクで、リーダーと役のコメントのスレッドに `/note` の記録の返信が足される |
| リーダー | `link-check` の出力の読み方は変わらない。`link-check` が最大 30 秒ほど長くかかることがある |
| PR を作る役 | 変わらない。`squad-pr-link` は作った直後に 1 回だけ呼ぶ |
| `decide` | 判定の読み方は変わらない。使用率の待ちで人間を呼ぶコメントは、紐付いていれば `紐付けの失敗:` の段落と連携の案内を添えなくなる |
| マージ待ちの見張り | 6 時間ごとに試み直し、紐付けば今の動作のとおり止まる |

エージェントとオートパイロットの登録は変わらない。役のひな形の形式と、拡張との契約も変わらない。

流し直す前に紐付けが失敗したタスクには、マークがないので試み直さない。今と同じく、人間がタスクの画面で紐付けるか、マージのあとに `done` にする。

スクリプトは、セットアップが同じ実行でまとめて置き換える。古い `squad-pr-link` と新しい `squad-pr-watch` の組み合わせでは、マークが書かれず試み直さない。新しい `squad-pr-link` と古い `squad-pr-watch` の組み合わせでは、マークは書かれるが読まれない。どちらも今と同じ動作になる。

### 変更の知らせ

この変更の知らせは、バージョンを上げる PR が、`CHANGELOG.md` に次の文で足す（[release.md の変更の知らせ](release.md#変更の知らせ)の決まり）。人間の紐付けの作業が減ることと、タスクに増える記録を、更新の前に読めるようにするため。

登録が変わらないと書く文は、同じ節のほかの変更と食い違わないよう、「この変更では」とこの変更の範囲に限る。

```markdown
PR を作った直後にタスクとの紐付けが失敗した PR を、あとで自動で紐付け直すようにした。試み直すのは、リーダーの紐付けの確認のときと、マージ待ちの見張りの 6 時間ごとである。流し直しで、見張りのスクリプトとリーダーの手順が替わる。

あとで紐付いた PR では、人間がタスクの画面で紐付けることと、マージのあとに `done` にする作業が要らなくなる。この変更では、エージェントとオートパイロットの登録は変わらない。

- 紐付けが失敗したタスクでは、試み直しの記録の `/note` の返信が、リーダーと役のコメントのスレッドに足される
- リーダーの紐付けの確認が、最大 30 秒ほど長くかかることがある
- 流し直す前に紐付けが失敗したタスクは、試み直さない。今と同じく、人間がタスクの画面で紐付けるか、マージのあとに `done` にする
```

## テスト

試み直しの動作は、偽の `multica` と偽の curl で、新しいテスト `tests/squad-pr-watch-link-retry-test.sh` に置く。今の `link-check` と `unlinked` のテストは、マークのない場面なので、変えずに通す。

偽の `multica` のコメントの投稿は、実機の約束に合わせる。今のスタブは、`--parent` のない根のコメントを無条件に受けており、コメントで起きた実行の約束と合わない。

スタブは、コメントで起きた実行を模す場面を持つ。その場面では、根のコメントと、きっかけと別の親への返信を拒否し、0 以外で終わって標準エラーに理由を出す。別の親も拒否するのは、通るかが未確認で、通らない前提で設計したためである。下の表の拒否の場面は、このスタブで流す。

| 場面 | 期待 |
| --- | --- |
| マークがあり、紐付いていない。API が 200 を返し、読み直すと紐付いている | `紐付け: 紐付いている` を出す。マークが消え、`紐付いた` の記録がきっかけのコメントへの返信として書かれる |
| 同じ場面で、API が 404 を返す | `紐付け: 紐付いていない` を出す。マークが残り、`見つからない（404）` の記録が書かれる |
| API が 200 を返し、読み直した一覧が空 | `紐付け: 紐付いていない` を出す。マークが残り、`一覧にない（200）` の記録が書かれる |
| API を呼んだあと、一覧を読み直せない | 今と同じ「未確認」の行を出す。マークが残り、`未確認（一覧を読めない）` の記録が書かれる |
| API が 404 を返し、読み直すと紐付いている | `紐付け: 紐付いている` を出し、`紐付いた` の記録が書かれる |
| 前の記録が別のスレッドにあり、5 分を過ぎている | API を 1 回呼び、記録は今回のきっかけのコメントへの返信になる |
| 前の記録が別のスレッドにあり、5 分の中 | API を呼ばず、記録も書かない |
| コメントで起きた実行を模し、きっかけを渡す | 記録はきっかけのコメントへの返信になり、スタブが受ける。根のコメントは書かない |
| コメントで起きた実行を模し、きっかけを渡さない | スタブが根のコメントを拒否するが、出力の行と終了コードは投稿が通ったときと同じ。次の `link-check` は 5 分の中でも API を呼ぶ |
| コメントで起きていない実行を模し、きっかけを渡さない | 記録は根のコメントになる |
| 書き手が人間の `紐付けの試み直し:` の行だけがある | 間隔に数えず、API を 1 回呼ぶ |
| マークがない | API を呼ばず、マークも記録も書かない。出力は今と同じ |
| マークの URL が `pr_url` と違う PR を指す | API を呼ばない |
| マークがあり、すでに紐付いている | API を呼ばず、`紐付いていた` の記録が書かれ、マークが消える |
| マークがあり、すでに紐付いていて、同じ PR の `紐付いた` か `紐付いていた` の記録がある | API を呼ばず、記録を書かず、マークを消し直す |
| マークがあり、すでに紐付いていて、タスクのコメントを読めない | API を呼ばず、記録を書かず、マークを消す |
| 紐付いていた記録を書いたあとマークの削除が失敗し、人間が紐付けを外す | 次の `link-check` で API を呼ばず、記録も書かない。マークを消し直し、`紐付け: 紐付いていない` を出す |
| 試み直しで紐付いたあとマークの削除が失敗し、人間が紐付けを外す | 同じく API を呼ばない |
| マークがあり、タスクのコメントを読めない | API を呼ばず、マークも記録も変えない |
| マークがあり、食い違い・作業先と違う・不正な pr_url | API を呼ばず、マークも記録も変えない |
| `unlinked-check` が流れ、最後の記録から 6 時間を過ぎている | API を 1 回呼び、記録は `ci_watch_thread` のコメントへの返信になる。紐付けば見張りの規則が消え、`止めた: PR がタスクに紐付いた` を記録する |
| `unlinked-check` が流れ、最後の記録が 6 時間の中 | API を呼ばない |
| 通信の失敗 | `失敗（通信に失敗した）` の記録が書かれ、マークが残る |
| 記録の投稿が失敗する | 出力の行と終了コードは、投稿が通ったときと同じ。マークの削除は行う |

`tests/squad-pr-link-test.sh` には、404 で待ち切れたとき・通信の失敗・ほかの状態コードでマークが書かれることを足す。作業先と違うときと、成功したときは書かれないことも足す。標準出力と標準エラーの文が今と同じことも確認する。

`tests/squad-review-next-decide-unlinked-test.sh` には、マークがある紐付いていない PR で、2 つの場面を足す。試み直しで紐付けば、マージの依頼に紐付けの依頼の行と `紐付けの失敗:` の段落がない。404 のままなら、今と同じく両方がある。どちらの場面でも、試み直しの記録が回のコメントへの返信として書かれることを見る。

`tests/squad-review-next-decide-fix-test.sh` の人間を呼ぶコメントの確認は、紐付いているときに段落と連携の案内がないことを見る形に直す。紐付いていないときは、紐付けの依頼の行、段落、連携の案内があることを見る。

`squad-dependabot-merge` のテスト（`tests/squad-dependabot-merge-*-test.sh`）は、変えずに通す。

## 残る危うさ

- 試み直しは、要件の時機と 6 時間ごとのマージ待ちの判定でだけ起きる。マージ待ちで最後の試み直しのあとに同期した PR は、紐付かないままマージされることがある
- `link-check` が API と記録の分だけ長くなる。API の時間切れは 30 秒で、紐付いていないタスクでしか呼ばない
- マークの metadata は役と人間も書ける。誤ったマークでも API を呼ぶのは、`pr_url` と同じ PR で一覧が空、作業先が同じときだけで、今も人間に紐付けを頼んでいる PR に当たる
- 人間が外した紐付けを試み直しで戻し、そのまま PR がマージされるとタスクが `done` になることがある。起こるのは次の 2 つの場面である
  - 紐付いたと分かったときに、記録の投稿とマークの削除の両方が失敗し、次の判定の前に人間が紐付けを外したとき
  - マークが残るタスクで、判定と判定の間にサーバーか人間が紐付け、次の判定の前に人間が外したとき。どの判定も紐付きを見ないので記録が残らず、次の判定で[間隔](#間隔)が過ぎていれば試み直す
- 一度紐付いた記録がある PR では、人間が外したあとにサーバーが同期し直しても、試み直さない。紐付けの依頼は今のとおり人間に届く
- リーダーがコメントで起きた実行できっかけを渡し忘れると、記録の投稿が拒否され、間隔が働かずに `link-check` のたびに API を呼ぶ。一度紐付いた記録も残らないので、マークの削除も失敗していれば、人間が外した紐付けを戻すことがある
- きっかけと別のスレッドへの返信が通るかは未確認である。通らない前提で書いたので、通っても動作は変わらない
- 同じタスクで `link-check` がほぼ同時に 2 回流れると、間隔の判定をすり抜けて記録が 2 件になることがある。紐付けの API は同じ PR を 2 回受けるだけで、判定の行は読み直した一覧で決まる

## 検討した案

試み直す時機と記録の置き場所、人間が外した紐付けの扱い、`squad-dependabot-merge` の経路で、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| PR を作る役・実装の役・修正の役が、push のたびに `squad-pr-link` の試み直しの形を呼ぶ | 5 つの役のひな形と共通スキルに手順が増える。push のすぐあとはサーバーの同期がまだのことがあり、リーダーが受けるときに試すのと比べて利点がない |
| `squad-pr-link` を、`pr_url` があっても API を呼ぶ形に変える | 人間が外した紐付けを、呼び直しで戻す。`紐付けていません:` の読み方も変わる |
| `unlinked-check` の 1 時間ごとの判定で毎回試み直す | マージ待ちの最大 72 時間で記録が 72 件まで増える。6 時間の間隔でも、紐付くまでの遅れは 6 時間までに収まる |
| `unlinked-check` では試み直さない | マージ待ちで同期した PR が紐付かず、見張りが止まらない。マージのあとに人間が `done` にする作業が残る |
| マークを使わず、`pr_url` があり紐付いていないタスクをすべて試み直す | 人間が外した紐付けを戻す。更新の前のタスクも試み直し、記録が急に増える |
| 一度紐付いたかを、マークが消えたことだけで読む | マークの削除が失敗すると、人間が外した紐付けを戻す |
| 判定が見ていない紐付けを人間が外したことを、サーバーの情報から読んで試み直しを止める | サーバーが外した操作を返すかを確認していない。判定に新しい情報源と止める条件が増える |
| 記録を 1 つのスレッドにまとめ、元のコメントの ID を metadata に残す | 要件の時機はどれもコメントで起きた実行で、最初の記録の根のコメントが拒否される。2 回目からも、きっかけと別のスレッドへの返信になり、通るかが未確認である |
| `link-check` が、きっかけのコメントを自分で読み取る | 実行の環境変数にきっかけのコメントがなく、スクリプトから読めない。`ci` と `unlinked` と同じく、呼び出す人が渡す |
| 記録を毎回スレッドの元のコメントにする | コメントで起きた実行では拒否される。試み直しのたびにスレッドも増える |
| マークがあり紐付いているときは、記録の有無によらず毎回 `紐付いていた` を書く | マークの削除が続けて失敗すると、`link-check` のたびに同じ結果の記録が増える |
| 記録を metadata に書く | metadata は上書きで、試みた回ごとの時刻と結果が残らない |
| 記録を PR のコメントに書く | タスクの識別子と進行の記録を PR に持ち出さない決まりに反する |
| `squad-dependabot-merge` もマークと記録の形にそろえる | 今も次の回で試み直しており、要件の範囲の外である。動作を変えると、Dependabot の PR の回し方の確認をやり直す必要がある |
