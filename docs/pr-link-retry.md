# 作った直後に紐付かなかった PR を、あとの区切りで紐付け直す

PR を作った直後の紐付けが失敗した PR を、あとの区切りで見張りのスクリプトが紐付け直す。紐付け直しは、リーダーと `squad-review-next decide` が流す `squad-pr-watch link-check` の中で行う。試みるたびに、時刻と結果をタスクに記録する。

この文書は、試み直す時機と印と記録の形を書く。`squad-dependabot-merge` の経路の扱いと、それぞれの理由も書く。

## 目的と範囲

今は、PR を作った役が `squad-pr-link` を 1 回だけ呼び、120 秒のうちにサーバーが PR を見つけなければ、紐付けは人間の手に移る。metadata に `pr_url` があると API を呼ばないので、あとで呼び直しても紐付かない。サーバーが PR をあとから同期しても、人間がタスクの画面で紐付けるか、マージのあとにタスクを `done` にするまで、紐付かないままになる。

目的は次の 4 つである。

1. 最初の 120 秒で紐付かなかった PR を、あとの区切りで自動で紐付け直す
2. 紐付いたあとは、人間を呼ぶコメントに、紐付けの依頼と `紐付けの失敗:` の段落を添えない
3. 紐付かないあいだは、今の依頼（タスクの画面で紐付けるか、マージのあとに `done` にする）を続ける
4. 試み直すたびに時刻と結果をタスクに残し、遅れて同期したのか、サーバーが保存しなかったのかを見分けられるようにする

次は対象にしない。

- 120 秒の待ちを延ばすこと。`squad-pr-link` の待ち方は変えない
- サーバーが PR を保存しない原因を調べること
- `squad-dependabot-merge` の紐付けの動作。扱いは [squad-dependabot-merge の経路](#squad-dependabot-merge-の経路)に書く
- 更新の前に紐付けが失敗したタスク。[試み直す PR の印](#試み直す-pr-の印)がないので、試み直さない

## 試み直す時機

試み直しは、`squad-pr-watch link-check` が「紐付いていない」と判定する直前に 1 回行う。`link-check` は、要件の 3 つの時機にすでに流れているので、新しい呼び出しを足さずに済む。

| 要件の時機 | 流れる `link-check` | 流す人 |
| --- | --- | --- |
| 役が PR に push したあと | 役が push して返した引き継ぎを、リーダーが受けたとき | リーダー |
| リーダーが PR を受け取ったとき | PR を受け取ったとき | リーダー |
| マージを頼む前 | 人間のマージへ回す前の確認と、`decide` の紐付けの確認 | リーダーか、返事をそろえた役の `decide` |

役が push する実行の中では試み直さない。push した役は、すぐあとにリーダーへ返し、リーダーの `link-check` が試み直すためである。push のあとの GitHub の通知でサーバーが PR を同期することがあるので、少し遅れて試すほうが紐付きやすいと見ている。

リーダーの手順の参照ファイル（`leader-pr-checks.md`）の時機の一覧では、「PR を受け取ったとき」に、役が push して返した引き継ぎを受けたときを含めると書く。今もリーダーは引き継ぎのたびに `link-check` を流していると読めるが、文で決めて、1 つ目の時機が抜けないようにする。

### 試み直さない呼び出し

`unlinked-check` は、マージ待ちのあいだ 1 時間ごとに、中で紐付けを判定する。この判定では試み直さない。最大 72 回流れるので、試み直すと記録が 72 件まで増えるためである。マージの依頼はすでに書いたあとなので、紐付いても依頼の文は変わらない。

### 間隔

同じタスクで、前の試み直しから 5 分たっていなければ、試み直さずに「紐付いていない」と判定する。リーダーは 1 回の実行で `link-check` を何度か流すことがあり、同じ結果の記録を重ねないためである。前の試み直しの時刻は、[記録の置き場所](#置き場所)の最後の記録のコメントの作成時刻で読む。

## 試み直す PR の印

試み直すのは、作った役の `squad-pr-link` が失敗を印に残した PR だけである。印は metadata の `pr_link_pending` で、値は `squad-pr-link` に渡した PR の URL である。

`squad-pr-link` は、紐付けに失敗して 1 で終わる前に印を書く。書くのは、タスクを読めて `pr_url` がなく、作業先が PR のリポジトリと同じだったときの失敗である。404 で待ち切れたとき・通信の失敗・ほかの状態コード・トークンなどがないときが当たる。

作業先と違うときは書かない。試み直しても、同じ理由で断るためである。

印を書けなかったときは、標準エラーに何も足さず、今と同じ警告だけを出す。`紐付けの失敗:` の段落の形を変えないためである。試み直しは起きず、今の動作と同じになる。

印は、紐付いたと分かったときに消す。試み直しで紐付いたときと、試み直す前に紐付いていたと分かったときである。

印を使うのは、人間が外した紐付けを、あとの試み直しで戻さないためである。紐付いたと分かった時点で印を消すので、そのあとに人間が外しても、試み直しは起きない。

## 試み直しの動作

`link-check` は、今の判定のあとに次を行う。出力の 1 行の形、終了コード、判定の種類は変えない。

1. 判定が「紐付いていない」で、印があり、印の URL が `pr_url` と同じ PR を指すときだけ、次へ進む。比べるのは、`link-check` が `pr_url` に使う正規形どうしで、大文字と小文字を区別しない
2. [間隔](#間隔)の 5 分の中なら、試み直さずに「紐付いていない」を出す
3. 紐付けの API を 1 回だけ呼び、404 でも待たない。時間切れは `squad-pr-link` と同じ 30 秒にする
4. 紐付いた PR の一覧を読み直し、その一覧で判定し直した行を出す。読めなければ、今と同じ「未確認」の行を出す
5. 読み直した一覧で紐付いていれば印を消す。結果を[試み直しの記録](#試み直しの記録)に残す

判定が「紐付いている」で印があるときは、API を呼ばずに印を消し、`紐付いていた` の記録を残す。人間かサーバーが紐付けた時点を、記録から読めるようにするためである。

判定が「食い違い」「作業先と違う」「不正な pr_url」「pr_url なし」「未確認」のときは、試み直さず、印も記録も書かない。

印を消すことと記録を書くことが失敗しても、出力の行と終了コードは変えない。印が残れば、次の `link-check` が `紐付いていた` の記録をもう一度書くことがある。

API を呼ぶ部分は、`squad-pr-link-lib` に 1 回だけ呼ぶ関数として切り出す。`pr_link_pull_request` は、待ちの繰り返しの中でこの関数を呼ぶ形に変え、入力・出力・待ち方を変えない。トークンは、今と同じく標準入力から curl に渡し、引数と出力に出さない。

`link-check` は、今は書き込まないと決めている。この設計で、印の削除、記録のコメント、紐付けの API の呼び出しを書き込む。`squad-pr-watch` の使い方のコメントと、この決まりを書いた文書の文を直す。

## 試み直しの記録

試み直しの結果は、タスクのコメントに 1 回 1 行で残す。遅れて同期したかは、`見つからない（404）` のあとに `紐付いた` が続くかで読む。マージまで `見つからない（404）` だけが続けば、最後の試み直しの時刻まで、サーバーは PR を持っていなかったことになる。

### 行の形

記録のコメントは、1 行目を `/note` にし、2 行目に次の行を置く。`/note` にするのは、記録でエージェントの実行を起こさないためである。

```text
紐付けの試み直し: <結果> pr: <PR の正規形> 時刻: <UTC の時刻>
```

時刻は `2026-11-24T03:04:05Z` の形にする。結果は次の 4 つのどれかである。

| 結果 | 当てはまるとき |
| --- | --- |
| `紐付いた` | API を呼んだあと、読み直した一覧に PR がある |
| `見つからない（404）` | API が 404 を返し、読み直した一覧に PR がない |
| `失敗（<理由>）` | 通信の失敗、ほかの状態コード、トークンなどがない。理由は `squad-pr-link-lib` の理由の文を写す |
| `紐付いていた` | 試み直す前の判定で、すでに紐付いていた |

`紐付けの試み直し:` は新しい固定の行である。記録だけに使い、ほかの判定には読ませない。

### 置き場所

記録は、タスクの 1 つのスレッドにまとめる。最初の記録をスレッドの元のコメントにし、その ID を metadata の `pr_link_record` に書く。2 回目からは、そのコメントへの返信にする。試み直しのたびにスレッドが増えると、人間がタスクを読むときの邪魔になるためである。

`pr_link_record` のコメントは、そのタスクのコメントで書き手がエージェントのときだけ使う。加えて、1 行目が `/note` で、2 行目が `紐付けの試み直し:` で始まることを確かめる。合わないときと読めないときは、新しい元のコメントを書き、`pr_link_record` を書き直す。

記録は、PR の本文と PR のコメントには書かない。タスクの識別子と進行の記録は、Multica 側に置く決まりのためである。

## 人間への依頼と警告

人間を呼ぶコメントの、紐付けの依頼と `紐付けの失敗:` の段落は、今も `link-check` が「紐付いていない」と出したときだけ添える。試み直しは「紐付いていない」と出す前に行うので、紐付けばこの 2 つは添わらない。リーダーの手順と `decide` のマージの依頼は、判定の読み方を変えない。

紐付かないあいだは、`link-check` が今と同じ「紐付いていない」を出す。紐付けの依頼とマージのあとに `done` にする依頼は、今のまま続く。`unlinked` の登録と、紐付いていない PR を受け取ったときの知らせも変わらない。

PR を作った役の引き継ぎにある `紐付けの失敗:` の段落は、作ったときの事実なので、そのまま残る。リーダーは、紐付いたあとはこの段落を写さない。

## squad-dependabot-merge の経路

`squad-dependabot-merge` の紐付けの動作は変えない。この経路は、失敗しても `pr_url` を書かず、同じ PR を次に回すときに 120 秒の待ちで紐付け直している。今も試み直しがあるので、要件の目的を満たしている。

この経路は `squad-pr-link` を呼ばないので、印は書かれない。そのタスクは `pr_url` を持たないので、`link-check` も試み直さない。

変えるのは、`squad-pr-link-lib` の API を 1 回呼ぶ部分を関数に切り出すことだけである。`pr_link_pull_request` の入力・出力・待ち方は変えないので、この経路の動作は同じである。今の `squad-dependabot-merge` のテストを変えずに通すことで確かめる。

## 入力と信頼の表

この設計は、紐付けの API に Multica のトークンを使い、役と人間が書ける metadata を読む。読む入力と信頼する条件は次のとおりである。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| metadata の `pr_link_pending`（`squad-pr-link` が書く。役と人間も書ける） | `link-check` の、試み直すかの判定 | 正規形にでき、`pr_url` の正規形と同じ PR を指す。紐付いた一覧が空で、作業先が PR のリポジトリと同じ | 試み直さず、今の判定の行を出す |
| metadata の `pr_url`（役が書く。人間も書ける） | 紐付けの API に渡す URL | 今の `link-check` の検証（正規形、作業先と同じリポジトリ）を通る | 今と同じく「作業先と違う」か「不正な pr_url」を出し、試み直さない |
| metadata の `pr_link_record`（`link-check` が書く。役と人間も書ける） | 記録を返信にする元と、間隔の判定 | そのタスクのコメントで、書き手がエージェント、1 行目が `/note`、2 行目が `紐付けの試み直し:` で始まる | 新しい元のコメントを書き、ID を書き直す。間隔は判定せずに試み直す |
| 記録のスレッドの返信（書き手を選べない） | 間隔の判定に使う、最後の記録の時刻 | 書き手がエージェントで、2 行目が `紐付けの試み直し:` で始まる。時刻はコメントの作成時刻を使い、本文の時刻は読まない | 間隔の判定に数えない |
| 紐付いた PR の一覧（サーバーが返す） | 試み直しの前後の判定 | 今の `link-check` の欄の検証を通る | 今と同じく「未確認」を出し、試み直さず、印を消さない |
| 環境変数の `MULTICA_TOKEN` と `MULTICA_SERVER_URL`（ランタイムが渡す） | 紐付けの API の呼び出し | 今の `squad-pr-link-lib` と同じ。トークンは標準入力から curl に渡し、出力と記録に出さない | 試みたことにし、`失敗（<理由>）` を記録する。印は残す |

試み直しが呼ぶのは、`pr_url` を Multica のタスクに紐付ける API だけである。GitHub への書き込みはしないので、書き込んでよいリポジトリの決まりとガードには触れない。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイル（リーダーの手順の参照ファイル）で、`link-check` を流す時機を文で決める。条件の 3 つを次に書く。

### 根拠

合意された要件による新しい機能なので、要件を合意したタスクを失敗の記録に代える。要件のもとになった、紐付けが失敗した 2 件の記録は、タスクのコメントにある。

### 働いた跡

手順が働くと、試み直しの対象のタスクに、[行の形](#行の形)の記録のコメントが残る。跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 項目 | 値 |
| --- | --- |
| 形 | `kind: "comment"` |
| `pattern` | `(?m)^紐付けの試み直し:` |
| `author_type` | `agent` |

この跡は、紐付けが失敗したタスクが 20 件の中にないと 0 回になる。0 回のときに削る候補にするかは、見直しで人間が判断する。

### 仕組みにしない理由

試み直しそのものは、`link-check` の中の仕組みにした。手順に残るのは、役が push して返したときにリーダーが `link-check` を流すことだけである。この時機も仕組みで流す案を 2 つ比べ、選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| ホストの `git push` のガードが、push のあとに試み直す | ガードは書き込み先を止める安全の境界で、トークンを使う書き込みを足すと境界の役目が広がる。ガードは push の相手のタスクを知らず、metadata を読めない |
| 定期のオートパイロットが、紐付いていないタスクを見回って試み直す | 導入先でオートパイロットの登録が増え、流し直しで登録が変わる。要件の時機（push・受け取り・マージの前）と合わず、タスクのない時刻にも実行を使う |

2 つの案は、作る手間ではなく、上の表の理由で選ばなかった。リーダーは、役が返すたびに今も `link-check` を流しており、手順の文はその動きを時機として決めるものである。

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと見張りのスクリプトとリーダーの手順が替わる。替わったあとに紐付けが失敗した PR は、あとの区切りで紐付き得る。

| 利用者 | 変わること |
| --- | --- |
| 人間 | 遅れて同期した PR では、紐付けの依頼が来なくなる。紐付けが失敗したタスクに、`/note` の記録のスレッドが 1 つ増える |
| リーダー | `link-check` の出力の読み方は変わらない。`link-check` が最大 30 秒ほど長くかかることがある |
| PR を作る役 | 変わらない。`squad-pr-link` は作った直後に 1 回だけ呼ぶ |
| `decide` | 判定の読み方は変わらない。紐付けの確認が試み直しの分だけ長くかかることがある |

エージェントとオートパイロットの登録は変わらない。役のひな形の形式と、拡張との契約も変わらない。

流し直す前に紐付けが失敗したタスクには、印がないので試み直さない。今と同じく、人間がタスクの画面で紐付けるか、マージのあとに `done` にする。

スクリプトは、セットアップが同じ実行でまとめて置き換える。古い `squad-pr-link` と新しい `squad-pr-watch` の組み合わせでは印が書かれず、試み直さない。新しい `squad-pr-link` と古い `squad-pr-watch` の組み合わせでは、印は書かれるが読まれない。どちらも今と同じ動作になる。

## テスト

試み直しの動作は、偽の `multica` と偽の curl で、新しいテスト `tests/squad-pr-watch-link-retry-test.sh` に置く。今の `link-check` と `unlinked` のテストは、印のない場面なので、変えずに通す。

| 場面 | 期待 |
| --- | --- |
| 印があり、紐付いていない。API が 200 を返し、読み直すと紐付いている | `紐付け: 紐付いている` を出す。印が消え、`紐付いた` の記録が元のコメントとして書かれ、ID が `pr_link_record` に入る |
| 同じ場面で、API が 404 を返す | `紐付け: 紐付いていない` を出す。印が残り、`見つからない（404）` の記録が書かれる |
| 前の記録があり、5 分を過ぎている | API を 1 回呼び、記録は前の元のコメントへの返信になる |
| 前の記録が 5 分の中 | API を呼ばず、記録も書かない |
| `pr_link_record` が別の書き手のコメントか、形の違うコメントを指す | 新しい元のコメントを書き、`pr_link_record` を書き直す |
| 印がない | API を呼ばず、印も記録も書かない。出力は今と同じ |
| 印の URL が `pr_url` と違う PR を指す | API を呼ばない |
| 印があり、すでに紐付いている | API を呼ばず、印が消え、`紐付いていた` の記録が書かれる |
| 印があり、食い違い・作業先と違う・不正な pr_url | API を呼ばず、印も記録も変えない |
| 印があり、`unlinked-check` が流れる | API を呼ばない |
| 通信の失敗 | `失敗（通信に失敗した）` の記録が書かれ、印が残る |
| 記録の投稿が失敗する | 出力の行と終了コードは、投稿が通ったときと同じ |

`tests/squad-pr-link-test.sh` には、404 で待ち切れたとき・通信の失敗・ほかの状態コードで印が書かれること、作業先と違うときと成功したときは書かれないことを足す。標準出力と標準エラーの文が今と同じことも確かめる。

`tests/squad-review-next-decide-unlinked-test.sh` には、印がある紐付いていない PR で、2 つの場面を足す。試み直しで紐付けば、マージの依頼に紐付けの依頼の行と `紐付けの失敗:` の段落がない。404 のままなら、今と同じく両方がある。

`squad-dependabot-merge` のテスト（`tests/squad-dependabot-merge-*-test.sh`）は、変えずに通す。

## 残る危うさ

- 試み直しは、要件の時機にリーダーか `decide` が流れたときだけ起きる。最後の試み直しのあとに同期した PR は、マージの依頼に紐付けの依頼が残る
- `link-check` が API と記録の分だけ長くなる。API の時間切れは 30 秒で、紐付いていないタスクでしか呼ばない
- 印と記録の metadata は役と人間も書ける。誤った印でも API を呼ぶのは、`pr_url` と同じ PR で一覧が空、作業先が同じときだけで、今も人間に紐付けを頼んでいる PR に当たる
- 同じタスクで `link-check` がほぼ同時に 2 回流れると、間隔の判定をすり抜けて記録が 2 件になることがある。紐付けの API は同じ PR を 2 回受けるだけで、判定の行は読み直した一覧で決まる

## 検討した案

試み直す時機、記録の置き場所、`squad-dependabot-merge` の経路について、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| PR を作る役・実装の役・修正の役が、push のたびに `squad-pr-link` の試み直しの形を呼ぶ | 5 つの役のひな形と共通スキルに手順が増える。push のすぐあとはサーバーの同期がまだのことがあり、リーダーが受けるときに試すのと比べて利点がない |
| `squad-pr-link` を、`pr_url` があっても API を呼ぶ形に変える | 人間が外した紐付けを、呼び直しで戻す。`紐付けていません:` の読み方も変わる |
| `unlinked-check` の 1 時間ごとの判定でも試み直す | マージ待ちの最大 72 時間で記録が 72 件まで増える。マージの依頼はすでに書いてあり、紐付いても依頼の文は変わらない |
| 印を使わず、`pr_url` があり紐付いていないタスクをすべて試み直す | 人間が外した紐付けを戻す。更新の前のタスクも試み直し、記録が急に増える |
| 記録を毎回スレッドの元のコメントにする | 試み直しのたびにスレッドが増え、人間がタスクを読むときの邪魔になる |
| 記録を metadata に書く | metadata は上書きで、試みた回ごとの時刻と結果が残らない |
| 記録を PR のコメントに書く | タスクの識別子と進行の記録を PR に持ち出さない決まりに反する |
| `squad-dependabot-merge` も印と記録の形にそろえる | 今も次の回で試み直しており、要件の範囲の外である。動作を変えると、Dependabot の PR の回し方の確認をやり直す必要がある |
