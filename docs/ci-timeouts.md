# CI のテストの止まりと遅さを、原因を確認して直す

PR の Checks で起きる時間切れを、止まり・遅さ・ジョブの打ち切りの 3 つの型に分け、型ごとに原因と直し方を決める。直すのはテストとその補助と CI の設定だけで、450 秒と 15 分の上限は変えない。

この文書は、各型の原因と根拠、止まりを再現する手順と直し方を書く。時間切れのときに止まった場所を残す記録と、PR #25 が型に効いたかの測り方も書く。

## 目的と範囲

main の Checks は、PR #25 のマージ前から 3 つの型で落ちている。目的は、型ごとに原因を根拠つきで示し、流し直しに頼らずに通る状態にすることである。

| 型 | 出たところ | 例 |
| --- | --- | --- |
| 止まり | 通れば 1 分以内のテストが、macOS と Ubuntu で 450 秒まで進まない | `tests/tty-session-test.sh`、`tests/release-test.sh`、`tests/release-check-test.sh` |
| 遅さ | 通ったときも長いテストが、macOS で 450 秒に届く | `tests/squad-review-next-decide-merge-test.sh` が 3 回、`tests/squad-review-next-decide-control-test.sh` が 375 秒 |
| ジョブの打ち切り | 時間切れのテストがないまま、scripts のジョブが 15 分で打ち切られる | 491bef8 の scripts (macos-latest, 3/5) |

目的は次の 5 つである。

1. 3 つの型の原因を、CI の実測と再現で示す
2. 止まりの 3 本が、macOS と Ubuntu で終わる
3. macOS で 450 秒に届くテストをなくす
4. scripts と terminal のジョブが、15 分に届かない
5. 時間切れのとき、どこで止まったかをログに残す

次は対象にしない。

- 450 秒と 15 分の上限を変えること。自動の流し直し、ケースの削除、テストの飛ばし
- main の b44260d の Private terms のワークフローの失敗。時間切れではないため
- PR #25 自身の失敗（`tests/agent-templates-test.sh` と `tests/squad-pr-watch-ci-handoff-test.sh`）
- 配布するスクリプトの変更。原因がそこにあると分かったときは、[原因が配布する原本にあったとき](#原因が配布する原本にあったとき)に従う

## 3 つの型の原因

止まりは、端末の補助 `tests/tty-session.py` の包みが、子の終了の通知を取り落とすことが原因だと見ている。遅さとジョブの打ち切りは、1 ファイルとシャードの実測が、上限と重みの前提を超えたことが原因である。

根拠は、main と PR #25 のブランチの CI のログである。読んだ実行は次のとおりである。

| ブランチ | コミット（実行の ID） |
| --- | --- |
| main | b44260d（45848389622）、90cf251（45771944993）、3ede094（45573567532） |
| main | 01c741e（45544002971）、b962df9（45535257319）、491bef8（45430244296） |
| PR #25 | 9e76b18（45842481436）、deb038a（45837536199）、69395e6（45828757146） |

### 止まり

止まった 3 本は、どれも `tests/tty-session.py` を使う。release の 2 本は、`tests/release-test-lib.sh` の `run_release_capture` を通して使う。止まったケースは実行ごとに違い、直前に通ったケースは T05〜T07・T03/T04/T20・T17・なしと散っている。決まったケースの不具合ではなく、時機の競合を示している。

包みは、子の終了を SIGCHLD の Python のハンドラで自己パイプに書き、期限のない `select` で待つ。ループは、`WNOHANG` の `waitpid` のあとに `select` を呼ぶ。Python は、届いたシグナルのハンドラを、命令の切れ目でだけ動かす。SIGCHLD が最後の切れ目と `select` のシステムコールの間に届くと、ハンドラは `select` が返るまで動かない。

`select` が返らないのは、子の終わりを知る道が通知だけになったときである。包みは、制御・通知・保持（子の fd 9）・exec の 4 本のパイプを見張る。exec のパイプは `exec` のときに、保持のパイプは子が fd 9 を閉じたときに終わりを読み、見張りから外れる。子は終わるとき、ゾンビになる前に fd を閉じる。

保持の終わりで `select` が返ったあと、`WNOHANG` の `waitpid` がまだ子を読めず 0 を返すと、見張る fd は制御と通知の 2 本だけになる。この直後の通知を取り落とすと、どの fd も読めるようにならず、包みは待ち続ける。

包みが終わりのマークを書かないので、親の `run()` も端末を読み続けて止まる。

9e76b18 の 1 回目は、この順序と合う。`tests/tty-session-cases.py` の 266 行の `assert inline('pass')[0] == 0` が落ちた。この行は、`WNOHANG` の `waitpid` が常に 0 を返すように差し込んだケースで、保持の終わりのあとは、子の終了を知る道が SIGCHLD の通知だけになる。時間切れの TERM で `run()` が 143 を返したと読める。

`tests/release-clock-driver.py` も期限のない `select` で待つが、シグナルを待たず、パイプの読み書きだけで進む。同じ取り落としは起きないので、直さない。

この原因は、手元の負荷をかけた繰り返しでは再現しなかった。[止まりの再現の手順](#止まりの再現の手順)の、順序を決めて作るケースで確認する。

### 遅さ

macOS で 150 秒を超えるファイルが、並列の負荷による揺れで 450 秒に届く。450 秒は、150 秒の 3 倍の余裕として決めた値である（[test-trim.md の「時間の上限」](test-trim.md#時間の上限)）。

b44260d の macOS の実測で、150 秒を超えたファイルは 15 本、200 秒を超えたものは 10 本ある。長い順に、`decide-control` 311 秒、`decide-fix` 293 秒、`decide-merge-note` 258 秒である。同じファイルでも揺れは大きく、`decide-control` は読んだログの中で 108〜375 秒だった。分ける前の `decide-merge` は、90cf251 で 419 秒かかり、3 回 450 秒に届いた。

長いファイルは、1 ケースごとに `squad-review-next decide` などのスクリプトを丸ごと流す。ケースの数に比例して延び、macOS ではプロセスの起動が重いので長くなる。重みの一覧は 97de5dd の実測で、`decide-control` の重みは 70 秒のままである。

### ジョブの打ち切り

重みの一覧が古く、重みでそろえたシャードの実測がそろわない。重いシャードの `Tests` の手順が、15 分に近づく。

| ジョブ（b44260d） | 重みの合計 | 実測の合計 | `Tests` の手順 |
| --- | --- | --- | --- |
| scripts (macos-latest, 3/5) | 1157 | 2633 | 約 14 分 42 秒 |
| scripts (macos-latest, 4/5) | 1157 | 1607 | 約 9 分 |
| scripts (ubuntu-24.04, 1/2) | 2894 | 3360 | 約 14 分 02 秒 |
| scripts (ubuntu-24.04, 2/2) | 2893 | 1927 | 約 8 分 |

重みの合計は 5787 秒だが、b44260d の macOS の実測の合計は 9915 秒、Ubuntu は 5287 秒だった。均等に分けても、1 シャードの `Tests` の手順は macOS・Ubuntu ともに約 661 秒になる。重みのずれが 1.3 倍あれば、15 分に届く。491bef8 の打ち切りと、90cf251 の止まりのあとの打ち切りは、この余裕の薄さの上で起きた。

今の [test-trim.md の「シャードの数」](test-trim.md#シャードの数)は、重みの合計を 750 秒以下にすると決めている。今の重みでも 5 つで 1157 秒になり、決まりを満たしていない。

## 時間切れの記録

時間切れのとき、`tests/run-one.sh` がテストを止める前に、セッションのプロセスの一覧と、登録した Python のスタックをテストのログに足す。`tests/run.sh` は失敗したファイルのログを出すので、CI のログで止まった場所を読める。

記録は次の順で行い、あとは今のとおり TERM、5 秒の待ち、KILL で止める。

1. ログに `---- 時間切れの記録` の行を足す
2. セッションのプロセスの一覧を足す
3. 登録を終えた同じプロセスだと確認できたものだけに SIGUSR2 を送り、1 秒待って、書かれたスタックを足す。送らなかったものは、PID と理由を 1 行ずつ足す

手順 3 で 1 つも送れなくても、記録をそこで終えて、TERM と KILL の後処理を続ける。

### プロセスの一覧

`tests/stop-session.py` に `LIST` の動作を足す。セッションのプロセスを 1 行ずつ標準出力に出す。列は、PID・親の PID・プロセスグループ・状態・経過時間・コマンドである。

`ps -A -o pid=,ppid=,pgid=,stat=,etime=,command=` を読み、今の動作と同じく `os.getsid()` でセッションを引く。セッションを引けたゾンビは出す。終わったのに回収されていない子は、止まりの手がかりになるためである。終了コードは今の動作と同じく、1 つでもあれば 0、なければ 1 にする。

セッションを引けないプロセスは、ゾンビも含めて一覧から外す。macOS では、`ps` に出るゾンビの `os.getsid()` が ESRCH で失敗する。所属を親の PID やプロセスグループから推して入れると、セッションの外の PID を含め、そこへ SIGUSR2 を送るおそれがあるためである。

### 外したゾンビの記録

macOS では、ゾンビの行が記録から欠ける。欠けるのは、ゾンビの PID・親の PID・状態・経過時間で、子が終わったのに回収されていないことは一覧から読めない。

止まった場所は、セッションに残る親の `run()` のスタックで確認する。`run()` が包みの知らせを待つ `select` で止まっていれば、包みかその下で止まったと読む。包みの中のどこで止まったかは、記録に出ない。

### スタックの書き出し

`tests/run-one.sh` は、テストの環境に `SQUAD_KIT_TEST_STACK_DIR` を渡し、`$work/stacks` を作る。`tests/tty-session.py` は、この変数があるとき、`faulthandler.register(signal.SIGUSR2, all_threads=True)` で、スタックをファイルに書くよう登録する。

登録は、次の順で行う。PID の名前のファイルは、登録を終えたプロセスにだけある。

1. 整数でない一時の名前のファイルを開き、先頭に登録の印の行を書く。印は、PID・親の PID・プロセスグループ・セッションの 4 つである
2. そのファイルへ書くよう `faulthandler.register` を呼ぶ
3. 登録に成功したら、ファイルを自分の PID の名前に改名して公開する。失敗したら、一時のファイルを消し、動作は変えない
4. 正常に終わるときは、登録を取り下げる。`faulthandler.unregister` は呼ばない（既定の動作は終了で、遅れて届いた SIGUSR2 がプロセスを止めるため）。書き先を `/dev/null` へ付け替えて登録を残し、自分の PID の名前のファイルを消す

取り下げは、`run()` を抜けるときと、`fork` の子が `os._exit` で終わる前に行う。`os._exit` は `atexit` を呼ばないので、終わる直前に明示して呼ぶ。消すのは、印の PID が自分と同じファイルだけである。

KILL や落ちたことで正常に終わらなかったプロセスのファイルは残る。残ったファイルは、名前と印では今のプロセスのものと見分けられない。`$work/stacks` はテストのファイルごとに作るので、残るのは同じテストの中で先に終わったプロセスのものに限られる。

印は `os.getpid()` などで読み、時計を使わない。`faulthandler` は、印の行のあとにスタックを書く。

登録は、`run()` の始めと、包みを作る `fork` のあとで行う。`fork` の子は親の登録を引き継ぐが、書き先が親のファイルのままになるためである。C は `exec` で登録が消えるので、`exec` の前に C の PID のファイルを作らない。

どのテストの入口でも、親の `run()` を登録する。`tests/tty-session-test.sh` のように fd の数を比べるケースがあっても、変数を消して登録を止めない。登録で開くファイルは、比べる fd から外す。`python3 -I` は `PYTHON` で始まる変数だけを読まないので、`SQUAD_KIT_` の変数は読める。

包みは `os.setsid()` で別のセッションへ移るので、`LIST` に出ず、SIGUSR2 を受けない。包みの登録は残すが、`tests/run-one.sh` の経路では使われない。

登録は、時計・眠り・期限を足さない。[terminal-tests.md の「テスト」](terminal-tests.md#テスト)の、補助のファイルに時計・眠り・期限・アラームの呼び出しがないという決まりは保つ。

### SIGUSR2 を送るプロセス

SIGUSR2 は、登録を終えた同じプロセスだと、送る直前に確認できた PID にだけ送る。登録していないプロセスは、SIGUSR2 の既定の動作で終わり、止まった場所が消えるためである。PID が使い回されると、同じ実行ユーザーの別のプロセスを止めるおそれもある。

送り先を選ぶ処理と送る処理は、`tests/stop-session.py` の新しい動作 `STACKS` にまとめる。`tests/run-one.sh` は、自分が作った `$work/stacks` とテストのセッションを渡して呼ぶ。PID ごとに、確認と送信を同じプロセスの中で続けて行い、確認から送信までの間を短くする。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| スタックのディレクトリのファイルの名前（`tests/tty-session.py` が書く。変数を受け継いだテストのコマンドも、同じ実行ユーザーなので書ける） | `STACKS` の送り先の候補 | 名前が正の整数である。一時の名前は、登録を終えていないので候補にしない | 読み飛ばし、送らない |
| ファイルの先頭の登録の印（`tests/tty-session.py` が登録の前に書く。テストのコマンドも書ける） | `STACKS` の同じプロセスの確認 | 印の PID がファイルの名前と同じで、印のセッションが時間切れのテストのセッションと同じ | 送らず、記録に `送らなかった <PID> 印が合わない` を足す |
| OS のプロセスの情報（`ps` の親の PID とプロセスグループ、`os.getsid()`） | `STACKS` が送る直前に、その PID だけ読み直す | 親の PID・プロセスグループ・セッションが、印と同じ | ESRCH や読めないときも含め、送らず、記録に `送らなかった <PID> プロセスが合わない` を足す |
| `SQUAD_KIT_TEST_STACK_DIR` の変数（`tests/run-one.sh` が渡す。テストのコマンドが上書きできる） | `tests/tty-session.py` の登録 | 変数があり、その場所にファイルを作れる | 登録せず、動作は変えない。`tests/run-one.sh` は自分が作った場所だけを読むので、ほかの場所の登録には送らない |

残ったファイルの印に、使い回された PID が親の PID・プロセスグループ・セッションまで一致したときは、送る直前の確認でも見分けられない。この重なりは、[残る危うさ](#残る危うさ)に置く。

条件が合わなかった PID には送らず、ほかの PID の確認を続ける。`STACKS` の失敗や、送れた PID が 0 のときも、`tests/run-one.sh` は TERM・5 秒の待ち・KILL の後処理を変えずに続ける。

確認から送信までの間に、そのプロセスが終わり、同じ PID が使い回されることは、`kill` の仕組みでは防げない。テストは時間切れで止まっている途中なので、この間にプロセスが終わることは少ないと見ている。macOS には、プロセスを PID でなく指す送り方がない。

## 止まりの再現の手順

[止まり](#止まり)の順序を、差し込みと FIFO で決めて作る。保持のパイプが先に終わり、見張る fd が制御と通知の 2 本だけになってから、子が終わって通知が読まれない順序である。眠りや期限に頼らず、直す前の包みでは毎回落ち、直したあとの包みでは毎回通る。

### 再現のケース

`tests/tty-session-cases.py` の T27 を、次の形にする。T18 と T23 と同じく、補助を同じプロセスで動かし、包みのプロセス（PID が持ち主と違うプロセス）でだけ差し込む。

1. コマンドは `sh -c 'exec 9>&-; read _ < "$1"'` の形で、fd 9 を閉じてから、ケースが作った FIFO の 1 行を読んで終わる。子は、FIFO に書かれるまで終わらない
2. `select.select` を差し替え、見張る fd が 2 本だけで、子がまだ回収されていない最初の呼び出しを、差し込みの対象にする。exec と保持のパイプは、それより前の呼び出しで終わりを読んで外れている
3. 対象の呼び出しでは、SIGCHLD のハンドラを何もしないハンドラに替えてから、FIFO に 1 行書いて子を終わらせる。`os.waitid(P_PID, 子, WEXITED | WNOWAIT)` で子が終わるのを待ち、元のハンドラに戻す
4. 本物の `select` を同じ fd と期限 0 で呼び、見張った fd の数と、読めた fd を記録する。読めた結果はそのまま返し、読めなければ空を返す
5. `os.waitpid` も差し替え、対象の呼び出しのあと最初の呼び出しが、`WNOHANG` を付けたかと、子を返したかを記録する

手順 3 は、通知が届いたのに Python のハンドラが自己パイプに書かなかった状態を作る。子は手順 3 まで終わらないので、包みが先に子を回収して差し込みを通らない順序は起きない。

T27 は、次の 2 つを満たすときに通る。どちらか 1 つでも満たさないときは、記録を添えて失敗の行を出す。

| 確認すること | 直す前の包み | 直したあとの包み |
| --- | --- | --- |
| 手順 4 の記録 | 見張る fd 2 本のどれも読めない。本物なら全 fd が待ちのまま止まる | 見張る fd は 2 本で、通知のパイプだけが読める |
| 手順 5 の記録と終了コード | 空を返したので、次の `WNOHANG` の `waitpid` で子を回収して終わる。ケースは止まらない | 通知を読んだので、次の `waitpid` は `WNOHANG` なしで子を返す。`inline` は 0 を返す |

直す前の包みでも、空を返したあとは `WNOHANG` の `waitpid` で子を回収するので、ケースは止まらずに失敗として出る。

### 直す前と後の流し方

同じ手順を、直す前の包みと直したあとの包みで流す。手順は、PR の結果のコメントに出力を添えて残す。

| 流すもの | コマンド | 満たしたと読む結果 |
| --- | --- | --- |
| 直す前 | `git checkout <PR の base> -- tests/tty-session.py` のあと、`bash tests/run.sh tests/tty-session-test.sh` | 0 以外で終わり、T27 の失敗の行に、見張る fd 2 本と読めた fd 0 本の記録が出る |
| 直したあと | `git checkout HEAD -- tests/tty-session.py` のあと、同じコマンド | 0 で終わり、`PASS tty-session T27` の行が出る |

直す前の包みで、見張る fd が 2 本になる呼び出しが来ないか、読めた fd があったときは、全 fd の待ちを再現できなかったと読む。このときは包みの直しを外し、受け入れ条件 8 に従って、記録と調べた結果を PR のコメントに書いて人間に返す。

## 止まりの直し方

包みが、`signal.set_wakeup_fd()` に通知の自己パイプの書き込み側を渡す。SIGCHLD が届くと、インタプリタの C のハンドラが自己パイプに 1 バイト書くので、Python のハンドラが動く前でも `select` が返る。

- 書き込み側は今も非停止にしているので、そのまま渡せる
- Python のハンドラは残す。ハンドラがないと SIGCHLD は既定で捨てられ、C のハンドラも動かないため
- 包みの `finally` で、`set_wakeup_fd(-1)` に戻してからハンドラを戻す
- 自己パイプから読んだバイトは、今と同じく通知があったという印にだけ使う

`select` には今のとおり期限を付けない。[terminal-tests.md の「包みの動き」](terminal-tests.md#包みの動き)に、通知の書き方を足す。

## 遅いファイルの分け方

macOS の CI の実測で 150 秒を超えるファイルを、1 本 150 秒以下の複数のファイルに分ける。ケースは消さず、確認する内容も変えない。例外は、[セットアップを何回も流すファイル](#セットアップを何回も流すファイル)にだけ置く。

1. 対象は、[PR #25 の影響の測り方](#pr-25-の影響の測り方)で読む複数の実行の、macOS の中央値で決める
2. ケースを、まとまりのある単位で新しいファイルへ移す。共通の準備は、今の補助のライブラリか、テストのディレクトリの新しい補助に置く
3. 新しいファイルは、[test-trim.md の「重みを写すとき」](test-trim.md#重みを写すとき)に従い、重みの一覧に足す

分けても、合計の秒数はほとんど減らない。1 本の長さが 450 秒から遠くなり、シャードへ細かく配れるようになる。分けて 150 秒以下にできないファイルがあり、その原因が配布するスクリプトの遅さにあるときは、[原因が配布する原本にあったとき](#原因が配布する原本にあったとき)に従う。

### セットアップを何回も流すファイル

`setup.sh` を何回も流すファイルには、次の 2 つの例外を置く。どちらも、450 秒と 15 分の上限は変えない。

- 初回の登録の確認を、同じランタイムの選び方の別のファイルが持つときは、初回の流しの確認を省いてよい。その流しで、確認するケースの状態を作る
- 同じ状態で `setup.sh` を続けて流すこと自体が確認の中身のファイルは、150 秒を超えても分けない。分けると部分の間に順序の依存ができ、別のシャードで流せなくなるため

前者に当たるのは `setup-runtimes-both-issues` である。最後の起票の失敗を、流し直しでなく初回の流しで確認し、`setup.sh` を 3 回から 2 回にする。失敗と復旧の確認の行は変えない。初回の確認は、同じ both の `setup-runtimes-both` と `setup-runtimes-both-changes` が持つ。

後者に当たるのは `setup-runtimes-both-changes` である。初回、変更の流し直し、2 回目の流し直しの 3 回が確認の中身で、CI で 190 秒前後になる見込みである。`setup.sh` を速くすることは、この文書では扱わない。

## シャードの数と重み

シャードの数は、OS ごとに、実測の合計をシャードの数と並列数で割った値が 600 秒以下になる最小の数にする。macOS の 5 つの上限は外す。重みは、今の決まりのとおり、最後の重みだけの push で実測を写す。

600 秒は、`Tests` の手順の目安である。準備と後片付け、重みのずれ（b44260d では最大 1.3 倍）を足しても、15 分に届かない値として選んだ。並列数は、macOS が 3、Ubuntu が 4 である。

| OS | b44260d の実測の合計 | 並列数 | 今のシャード | 決まりで決まる数 |
| --- | --- | --- | --- | --- |
| macOS | 9915 秒 | 3 | 5 | 6（1 つあたり 551 秒） |
| Ubuntu | 5287 秒 | 4 | 2 | 3（1 つあたり 441 秒） |

数は、遅いファイルを分けたあとの CI の実測で決め直す。分けたあとの合計で数が変われば、その数にする。重みはすべて macOS の実測で、Ubuntu の分け方にも同じ重みを使う。

macOS のジョブは、無料のプランで同時に 5 つまで流れる。terminal の macOS の 2 つと合わせて 8 つになり、3 つは空きを待つ。待つ時間はジョブの `timeout-minutes` に数えないので、上限には効かない。実行の全体は延びる。

## PR #25 の影響の測り方

PR #25 の影響を、負荷と順序に分けて判定する。読むのは終わった実行だけで、新しく流し直さない。区別できないものは、「未特定」として人間に返す。

| 要因 | 意味 |
| --- | --- |
| 負荷 | PR #25 が足した・変えたテストが、対象と同じジョブで同時に流れたこと |
| 順序 | 重みの一覧が変わり、対象のシャード・位置・同時に流れたファイルが変わったこと |

対象は、止まりと遅さのファイルと、ジョブの打ち切りのシャードである。ファイルは OS ごとに別の対象とし、シャードはジョブごとに 1 つの対象とする。

ファイルの対象では、そのファイルと同時に流れたファイルで組を分ける。シャードの対象では、シャードに入ったファイルの一覧で組を分ける。2 つは結果の表で別の列に書き、混ぜない。直列のジョブでは、ファイルと同時に流れたファイルはないが、シャードに入ったファイルには PR #25 のテストが入りうる。

1. マージ前は 90cf251・3ede094・01c741e・b962df9、マージ後は b44260d・9e76b18・deb038a と、この PR の実行を読む。各ジョブの最後の試行の `done PASS <ファイル> <秒>s` の行と時間切れの行を、ログの行の時刻とともに使う
2. 比べる実行をそろえる。同じ OS・同じ並列数で、対象のファイルとそれが読む補助が、比べるコミットの間で変わっていない実行だけを使う
3. 行の時刻と秒数から各ファイルが流れた区間を求め、同じジョブで 1 秒を超えて重なったものを同時に流れたファイルとする（1 秒以内は時刻の丸めとして数えない）。シャードと位置は、各コミットの重みの一覧と `tests/run.sh` の配り方で求める
4. マージ前とマージ後の実行の組ごとに、次の表で、負荷と順序のどちらを判定できるかを決める
5. 判定できる組で、マージ後の秒数が、マージ前の同じ対象の最小から最大の幅を超えたら「影響あり」とする。止まりは、秒数でなく時間切れの有無で読む

| 組の違い | 負荷 | 順序 |
| --- | --- | --- |
| シャード・位置・同時に流れたファイルがすべて同じ | 変わっていない | 変わっていない（対照） |
| シャードと位置が同じで、同時に流れたファイルの違いが PR #25 のテストだけ | 判定できる | 変わっていない |
| 前後とも同時に流れたファイルに PR #25 のテストがなく、シャード・位置・同時に流れたファイルのどれかが変わった | 変わっていない | 判定できる |
| PR #25 のテストが同時に流れ、ほかの同時のファイルかシャードも変わった | 未特定 | 未特定 |

対照の組は、負荷も順序も変わっていない組である。ランナーの揺れの幅を見るためだけに使い、負荷にも順序にも「影響なし」の根拠にしない。たとえば、直列のジョブで前後の起動の順が同じなら、その組は対照である。

型ごとに、負荷と順序をそれぞれ「はい」「いいえ」「未特定」で書く。型の中の対象に 1 つでも影響ありがあれば「はい」、判定できた対象がすべて影響なしなら「いいえ」とする。判定できる組のない対象が残れば、「いいえ」でなく「未特定」とし、その対象と理由（両方が変わった・変わった組がない・そろう実行がない）を添える。対照の組しかない対象も、判定できる組のない対象に数える。

結果は PR のコメントに書き、実行・ジョブ・対象ごとの秒数と、同時に流れた PR #25 のテストを添える。中央値だけでなく、1 回ごとの秒数を残す。

## テスト

止まりの直しは T27 で、時間切れの記録は `tests/test-runner-test.sh` の新しいケースで確認する。遅さとジョブの打ち切りは、CI の実測で確認する。

- T27: 同じ子の終了の順序で、直す前の包みは見張る fd がすべて待ちのままで落ち、直したあとの包みは通知で進んで子を回収して通る

- `STACKS` は、整数でない名前・印が合わないファイル・セッションの外の PID・登録に失敗したプロセスへ SIGUSR2 を送らない。送らなかった行を記録に足し、TERM と KILL の後処理を続ける
- `tests/tty-session-test.sh` を、スタックの場所を渡して流すと、fd の数を比べるケースも通る。流し終えたあと、正常に終わったプロセスの PID の名前のファイルが残らない

- 最後の push の CI で、全ジョブが最初の試行で通る。scripts と terminal の全ジョブの `done PASS` の行で、最も長いテストが 450 秒未満、最も長いジョブが 15 分未満である

1. 流し直して通った結果で、最初の失敗を置き換えない
2. 450 秒と 15 分の上限、ケースの数を変えていないことを、PR の base との差分で確認する

## 残る危うさ

- T27 は、取り落としの順序を差し込みと FIFO で作る。CI の止まりが同じ順序だったかは、時間切れの記録が出るまで直接には見えない
- 正常に終わったテストのプロセスは、登録を外さず `/dev/null` へ付け替えるので、取り下げと送信が前後しても SIGUSR2 では止まらない。残るのは、確認から送信までの間に、登録のないプロセスへ PID が使い回される場合だけである。確認は、印の PID・親・プロセスグループ・セッションの一致で行い、使い回された先が同じ組まで一致する必要があるので、現実にはまれである。確認から送信までの隙間はなくせないので、ここは残す
- 正常に終わらなかったプロセスの登録のファイルは残る。同じテストの中で、その PID が親の PID・プロセスグループ・セッションまで同じプロセスに使い回されると、送る直前の確認を通り、SIGUSR2 で止める
- PR #25 の影響は、終わった実行だけで判定するので、そろう組がなく「未特定」が残ることがある。そのときは人間が、流し直して比べるかを決める
- 直したあとに止まりが出たら、時間切れの記録のスタックで場所を読む
- 包みの中の止まりは、記録に出ない。親の `run()` のスタックで包みかその下と絞り、場所は T27 のような再現で特定する
- macOS の記録には、ゾンビの行が出ない。回収されない子が原因の止まりは、親のスタックと一覧に残る行から推すことになる
- テストを足すたびに、合計の秒数は増え、重みを写さないとシャードの実測は再びずれる。重みのないファイルを足すとテストが落ちるので、足したときには気づける
- macOS のシャードが増えると、ほかの PR と重なったときの待ちが延びる
- `setup-runtimes-both-changes` は 190 秒前後で残り、450 秒までの余裕は 3 倍より小さい。負荷の揺れで 450 秒に届いたら、時間切れの記録で場所を読む
- `setup-runtimes-both-issues` は、登録済みの状態からの流し直しで最後の起票が失敗する経路を、直接には確認しない
- 600 秒の目安は、b44260d の 1 回のずれから決めた。ランナーがさらに遅くなると、15 分に近づく

## 検討した案

型ごとに、選んだ案と選ばなかった案を書く。

### 止まりの直し方の案

`set_wakeup_fd` を選んだ。期限つきの `select` と定期の `waitpid` でも止まりは消えるが、補助に期限を足さない決まりに反し、待つ長さを決める必要がある。シグナルの受け方を `signalfd` や `sigwait` に替える案は、macOS にないか、包みの作りを大きく変えるので選ばなかった。

### 再現の作り方の案

順序を差し込みで決めるケースを選んだ。負荷をかけた繰り返しは、手元では再現せず、再現しないことが直った根拠にならない。`select` を本物の期限なしで呼ぶ再現は、直す前に 450 秒まで止まるので選ばなかった。

子の終わりは、FIFO で差し込みの時点まで止めることにした。`pass` のようにすぐ終わる子では、包みが最初の `waitpid` で先に回収し、差し込みを通らないことがある。保持のパイプを開けたまま終わる子では、直す前の包みでも保持の終わりで `select` が返り、全 fd の待ちを作れない。

### 時間切れの記録の案

SIGUSR2 と `faulthandler` を選んだ。`py-spy` などの外の道具は、CI への導入が要り、macOS では権限が要る。全プロセスに SIGABRT を送る案は、登録していないプロセスを止めてしまう。

macOS のゾンビは、セッションを引けないので一覧から外すことにした。macOS で別の方法から所属を引く案は、使える方法を確認できていないので選ばなかった。親の PID から所属を推す案は、セッションの外の PID を含めるおそれがある。

包みのスタックは記録に含めないことにした。別のセッションの包みにも送る案は、セッションの外の PID へ送らない決まりを弱めるので選ばなかった。

送り先は、登録の印と送る直前の読み直しで確認することにした。Linux の pidfd で送る案は、macOS にないので選ばなかった。登録したプロセスだけが読む専用の通り道で頼む案は、止まった `select` の中のプロセスに届けるにはシグナルが要り、通り道だけでは足りない。印にプロセスの開始の時刻を入れる案は、補助に時計を足すので選ばなかった。

### PR #25 の影響の案

終わった実行だけで、負荷と順序を組ごとに判定することにした。負荷か順序の片方だけを変えて新しく流し比べる案は、区別ははっきりするが、流し直しの回数と待ちが増える。終わった実行で区別できないものは「未特定」として返し、流し直すかは人間が決める。

### シャードの数の案

600 秒を選んだ。今の 300 秒の目安を保つと、macOS は 11 のシャードが要り、待ちが大きくなる。macOS を 5 つのままにする案は、テストを短くしても 15 分に届かないと言い切れない。OS ごとに別の重みを持つ案は、重みを写す手間が倍になるので、今は選ばない。

### 遅いファイルの案

分けることを選んだ。並列数を下げる案は、全体の時間が延びる。上限を延ばす案は、要件で外した。

セットアップを何回も流すファイルでは、3 つの案を比べた。例外を置く案を選んだ。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 例外を置く（選んだ） | 確認の行を減らさず、上限も変えない | 150 秒を超える 1 本が残る |
| `setup-runtimes-both-changes` の流しを 2 回に減らす | 150 秒以下になる | 2 回目の流し直しでタスクが増えないことを確認しなくなる |
| 流し直しの状態を 1 回作り、部分どうしで使い回す | 流しの回数が減る | 部分の間に順序の依存ができ、別のシャードで流せない |
