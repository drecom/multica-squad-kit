# CI のテストの止まりと遅さを、原因を確認して直す

PR の Checks で起きる時間切れを、止まり・遅さ・ジョブの打ち切りの 3 つの型に分け、型ごとに原因と直し方を決める。直すのはテストとその補助と CI の設定だけで、450 秒と 15 分の上限は変えない。

この文書は、各型の原因と根拠、止まりを再現する手順と直し方を書く。時間切れのときに止まった場所を残す記録と、PR #25 が型に効いたかの測り方も書く。

## 目的と範囲

main の Checks は、PR #25 のマージ前から 3 つの型で落ちている。目的は、型ごとに原因を根拠つきで示し、流し直しに頼らずに通る状態にすることである。

| 型 | 出たところ | 例 |
| --- | --- | --- |
| 止まり | 通れば 1 分以内のテストが、macOS と Ubuntu で 450 秒まで進まない | `tests/tty-session-test.sh`、`tests/release-test.sh`、`tests/release-check-test.sh` |
| 遅さ | 通ったときも長いテストが、macOS で 450 秒に届く | `tests/squad-review-next-decide-merge-test.sh` が 3 回、`tests/squad-review-next-decide-control-test.sh` が 375 秒 |
| ジョブの打ち切り | 時間切れのテストがないまま、scripts のジョブが 15 分で打ち切られる | 491bef8 の scripts (macos-latest, 3/5) |

目的は次の 5 つである。

1. 3 つの型の原因を、CI の実測と再現で示す
2. 止まりの 3 本が、macOS と Ubuntu で終わる
3. macOS で 450 秒に届くテストをなくす
4. scripts と terminal のジョブが、15 分に届かない
5. 時間切れのとき、どこで止まったかをログに残す

次は対象にしない。

- 450 秒と 15 分の上限を変えること。自動の流し直し、ケースの削除、テストの飛ばし
- main の b44260d の Private terms のワークフローの失敗。時間切れではないため
- PR #25 自身の失敗（`tests/agent-templates-test.sh` と `tests/squad-pr-watch-ci-handoff-test.sh`）
- 配布するスクリプトの変更。原因がそこにあると分かったときは、[原因が配布する原本にあったとき](#原因が配布する原本にあったとき)に従う

## 3 つの型の原因

止まりは、端末の補助 `tests/tty-session.py` の包みが、子の終了の通知を取り落とすことが原因だと見ている。遅さとジョブの打ち切りは、1 ファイルとシャードの実測が、上限と重みの前提を超えたことが原因である。

根拠は、main と PR #25 のブランチの CI のログである。読んだ実行は次のとおりである。

| ブランチ | コミット（実行の ID） |
| --- | --- |
| main | b44260d（45848389622）、90cf251（45771944993）、3ede094（45573567532） |
| main | 01c741e（45544002971）、b962df9（45535257319）、491bef8（45430244296） |
| PR #25 | 9e76b18（45842481436）、deb038a（45837536199）、69395e6（45828757146） |

### 止まり

止まった 3 本は、どれも `tests/tty-session.py` を使う。release の 2 本は、`tests/release-test-lib.sh` の `run_release_capture` を通して使う。止まったケースは実行ごとに違い、直前に通ったケースは T05〜T07・T03/T04/T20・T17・なしと散っている。決まったケースの不具合ではなく、時機の競合を示している。

包みは、子の終了を SIGCHLD の Python のハンドラで自己パイプに書き、期限のない `select` で待つ。ループは、`WNOHANG` の `waitpid` のあとに `select` を呼ぶ。Python は、届いたシグナルのハンドラを、命令の切れ目でだけ動かす。SIGCHLD が最後の切れ目と `select` のシステムコールの間に届くと、ハンドラは `select` が返るまで動かず、`select` は返らない。

包みが終わりのマークを書かないので、親の `run()` も端末を読み続けて止まる。

9e76b18 の 1 回目は、この順序と合う。`tests/tty-session-cases.py` の 266 行の `assert inline('pass')[0] == 0` が落ちた。この行は、`WNOHANG` の `waitpid` が常に 0 を返すように差し込んだケースで、子の終了を知る道が SIGCHLD の通知だけになる。時間切れの TERM で `run()` が 143 を返したと読める。

`tests/release-clock-driver.py` も期限のない `select` で待つが、シグナルを待たず、パイプの読み書きだけで進む。同じ取り落としは起きないので、直さない。

この原因は、手元の負荷をかけた繰り返しでは再現しなかった。[止まりの再現の手順](#止まりの再現の手順)の、順序を決めて作るケースで確認する。

### 遅さ

macOS で 150 秒を超えるファイルが、並列の負荷による揺れで 450 秒に届く。450 秒は、150 秒の 3 倍の余裕として決めた値である（[test-trim.md の「時間の上限」](test-trim.md#時間の上限)）。

b44260d の macOS の実測で、150 秒を超えたファイルは 15 本、200 秒を超えたものは 10 本ある。長い順に、`decide-control` 311 秒、`decide-fix` 293 秒、`decide-merge-note` 258 秒である。同じファイルでも揺れは大きく、`decide-control` は読んだログの中で 108〜375 秒だった。分ける前の `decide-merge` は、90cf251 で 419 秒かかり、3 回 450 秒に届いた。

長いファイルは、1 ケースごとに `squad-review-next decide` などのスクリプトを丸ごと流す。ケースの数に比例して延び、macOS ではプロセスの起動が重いので長くなる。重みの一覧は 97de5dd の実測で、`decide-control` の重みは 70 秒のままである。

### ジョブの打ち切り

重みの一覧が古く、重みでそろえたシャードの実測がそろわない。重いシャードの `Tests` の手順が、15 分に近づく。

| ジョブ（b44260d） | 重みの合計 | 実測の合計 | `Tests` の手順 |
| --- | --- | --- | --- |
| scripts (macos-latest, 3/5) | 1157 | 2633 | 約 14 分 42 秒 |
| scripts (macos-latest, 4/5) | 1157 前後 | 1607 | 約 9 分 |
| scripts (ubuntu-24.04, 1/2) | 2894 | 3360 | 約 14 分 02 秒 |
| scripts (ubuntu-24.04, 2/2) | 2893 | 1927 | 約 8 分 |

重みの合計は 5787 秒だが、b44260d の macOS の実測の合計は 9915 秒、Ubuntu は 5287 秒だった。均等に分けても、1 シャードの `Tests` の手順は macOS・Ubuntu ともに約 661 秒になる。重みのずれが 1.3 倍あれば、15 分に届く。491bef8 の打ち切りと、90cf251 の止まりのあとの打ち切りは、この余裕の薄さの上で起きた。

今の [test-trim.md の「シャードの数」](test-trim.md#シャードの数)は、重みの合計を 750 秒以下にすると決めている。今の重みでも 5 つで 1157 秒になり、決まりを満たしていない。

## 時間切れの記録

時間切れのとき、`tests/run-one.sh` がテストを止める前に、セッションのプロセスの一覧と、登録した Python のスタックをテストのログに足す。`tests/run.sh` は失敗したファイルのログを出すので、CI のログで止まった場所を読める。

記録は次の順で行い、あとは今のとおり TERM、5 秒の待ち、KILL で止める。

1. ログに `---- 時間切れの記録` の行を足す
2. セッションのプロセスの一覧を足す
3. スタックを登録したプロセスに SIGUSR2 を送り、1 秒待って、書かれたスタックを足す

### プロセスの一覧

`tests/stop-session.py` に `LIST` の動作を足す。セッションのプロセスを 1 行ずつ標準出力に出す。列は、PID・親の PID・プロセスグループ・状態・経過時間・コマンドである。

`ps -A -o pid=,ppid=,pgid=,stat=,etime=,command=` を読み、今の動作と同じく `os.getsid()` でセッションを引く。ゾンビも出す。終わったのに回収されていない子は、止まりの手がかりになるためである。終了コードは今の動作と同じく、1 つでもあれば 0、なければ 1 にする。

### スタックの書き出し

`tests/run-one.sh` は、テストの環境に `SQUAD_KIT_TEST_STACK_DIR` を渡し、`$work/stacks` を作る。`tests/tty-session.py` は、この変数があるとき、`faulthandler.register(signal.SIGUSR2, all_threads=True)` で、自分の PID の名前のファイルにスタックを書くよう登録する。

登録は、`run()` の始めと、包みと C を作る `fork` のあとで行う。`fork` の子は親の登録を引き継ぐが、書き先が親のファイルのままになるためである。C は `exec` で登録が消えるので、`exec` の前に C の PID のファイルを作らない。`python3 -I` は `PYTHON` で始まる変数だけを読まないので、`SQUAD_KIT_` の変数は読める。

登録は、時計・眠り・期限を足さない。[terminal-tests.md の「テスト」](terminal-tests.md#テスト)の、補助のファイルに時計・眠り・期限・アラームの呼び出しがないという決まりは保つ。

### SIGUSR2 を送るプロセス

SIGUSR2 は、スタックのディレクトリにファイルがあり、かつ `LIST` でそのテストのセッションにいる PID にだけ送る。登録していないプロセスは、SIGUSR2 の既定の動作で終わり、止まった場所が消えるためである。

ファイルの名前は、テストのプロセスが書く。PID が使い回されて、セッションの外のプロセスを指すこともある。そのため、名前が正の整数でないファイルと、セッションにいない PID は読み飛ばす。

## 止まりの再現の手順

子の終了の通知が、`select` に入る前に届いて読まれない順序を、差し込みで決めて作る。眠りや期限に頼らず、直す前の包みでは毎回落ち、直したあとの包みでは毎回通る。

### 再現のケース

`tests/tty-session-cases.py` に T27 を足す。T18 と T23 と同じく、補助を同じプロセスで動かし、包みのプロセス（PID が持ち主と違うプロセス）でだけ差し込む。

1. `select.select` を差し替える。子がまだ回収されていない最初の呼び出しだけを差し込みの対象にする
2. 対象の呼び出しでは、SIGCHLD のハンドラを何もしないハンドラに替え、`os.waitid(P_PID, 子, WEXITED | WNOWAIT)` で子が終わるのを待つ。そのあと元のハンドラに戻す
3. 本物の `select` を期限 0 で呼び、通知の自己パイプが読めるかを記録する。読めた結果をそのまま返し、読めなければ空を返す
4. `inline('pass')` が 0 を返し、記録が「読めた」だけであることを確認する

手順 2 は、通知が届いたのに Python のハンドラが自己パイプに書かなかった状態を作る。直す前の包みでは、手順 3 で読めず、本物なら止まる場所を、期限 0 の確認で失敗として出す。空を返すと、包みは次の `WNOHANG` の `waitpid` で子を回収して終わるので、ケースは止まらない。

### 直す前と後の流し方

同じ手順を、直す前の包みと直したあとの包みで流す。手順は、PR の結果のコメントに出力を添えて残す。

| 流すもの | コマンド | 満たしたと読む結果 |
| --- | --- | --- |
| 直す前 | `git checkout <PR の base> -- tests/tty-session.py` のあと、`bash tests/run.sh tests/tty-session-test.sh` | 0 以外で終わり、T27 の失敗の行が出る |
| 直したあと | `git checkout HEAD -- tests/tty-session.py` のあと、同じコマンド | 0 で終わり、`PASS tty-session T27` の行が出る |

## 止まりの直し方

包みが、`signal.set_wakeup_fd()` に通知の自己パイプの書き込み側を渡す。SIGCHLD が届くと、インタプリタの C のハンドラが自己パイプに 1 バイト書くので、Python のハンドラが動く前でも `select` が返る。

- 書き込み側は今も非停止にしているので、そのまま渡せる
- Python のハンドラは残す。ハンドラがないと SIGCHLD は既定で捨てられ、C のハンドラも動かないため
- 包みの `finally` で、`set_wakeup_fd(-1)` に戻してからハンドラを戻す
- 自己パイプから読んだバイトは、今と同じく通知があったという印にだけ使う

`select` には今のとおり期限を付けない。[terminal-tests.md の「包みの動き」](terminal-tests.md#包みの動き)に、通知の書き方を足す。

## 遅いファイルの分け方

macOS の CI の実測で 150 秒を超えるファイルを、1 本 150 秒以下の複数のファイルに分ける。ケースは消さず、確認する内容も変えない。

1. 対象は、[PR #25 の影響の測り方](#pr-25-の影響の測り方)で読む複数の実行の、macOS の中央値で決める
2. ケースを、まとまりのある単位で新しいファイルへ移す。共通の準備は、今の補助のライブラリか、テストのディレクトリの新しい補助に置く
3. 新しいファイルは、[test-trim.md の「重みを写すとき」](test-trim.md#重みを写すとき)に従い、重みの一覧に足す

分けても、合計の秒数はほとんど減らない。1 本の長さが 450 秒から遠くなり、シャードへ細かく配れるようになる。分けて 150 秒以下にできないファイルがあり、その原因が配布するスクリプトの遅さにあるときは、[原因が配布する原本にあったとき](#原因が配布する原本にあったとき)に従う。

## シャードの数と重み

シャードの数は、OS ごとに、実測の合計をシャードの数と並列数で割った値が 600 秒以下になる最小の数にする。macOS の 5 つの上限は外す。重みは、今の決まりのとおり、最後の重みだけの push で実測を写す。

600 秒は、`Tests` の手順の目安である。準備と後片付け、重みのずれ（b44260d では最大 1.3 倍）を足しても、15 分に届かない値として選んだ。並列数は、macOS が 3、Ubuntu が 4 である。

| OS | b44260d の実測の合計 | 並列数 | 今のシャード | 決まりで決まる数 |
| --- | --- | --- | --- | --- |
| macOS | 9915 秒 | 3 | 5 | 6（1 つあたり 551 秒） |
| Ubuntu | 5287 秒 | 4 | 2 | 3（1 つあたり 441 秒） |

数は、遅いファイルを分けたあとの CI の実測で決め直す。分けたあとの合計で数が変われば、その数にする。重みはすべて macOS の実測で、Ubuntu の分け方にも同じ重みを使う。

macOS のジョブは、無料のプランで同時に 5 つまで流れる。terminal の macOS の 2 つと合わせて 8 つになり、3 つは空きを待つ。待つ時間はジョブの `timeout-minutes` に数えないので、上限には効かない。実行の全体は延びる。

## PR #25 の影響の測り方

PR #25 のマージ前と後の main の実行を、それぞれ 3 回以上読み、ファイルごとの秒数を比べる。読むのは終わった実行だけで、新しく流し直さない。

1. マージ前は 90cf251・3ede094・01c741e・b962df9、マージ後は b44260d・9e76b18・deb038a と、この PR の実行を読む。各ジョブの最後の試行の `done PASS <ファイル> <秒>s` の行を使う
2. PR #25 が変えていないファイルの秒数を、前後の中央値で比べる。前の実行の間の揺れの幅を超えて伸びたかを見る
3. 止まりと遅さのファイルが、前後でどのシャードの何番目に起きたかを、各コミットの重みの一覧と `tests/run.sh` の配り方で求める
4. 型ごとに、PR #25 が影響したかを「はい」か「いいえ」で、秒数を添えて PR の結果のコメントに書く

## 原因が配布する原本にあったとき

実装の途中で、型の原因が配布するスクリプトにあると分かったら、そのスクリプトは変えずに止まり、設計に返す。設計の役が、原因と直し方をこの文書に足し、人間の承認を受けてから直す。

配布するものは、`MANIFEST` に載るファイルのうち、`tests/` と `.github/` の外のものである。止まりの原因が補助でなく `scripts/release.sh` にある場合や、遅さの原因が `squad-review-next` の 1 回の起動の重さにある場合が当たる。

## 互換性

導入したプロジェクトに配るものは変わらない。変わるのは原本のテストと CI だけである。

- `tests/run.sh` と `tests/run-one.sh` の使い方と終了コードは変わらない。時間切れのログが長くなる
- `tests/stop-session.py` の `TERM`・`KILL`・`ALIVE` は変わらない
- `tests/tty-session.py` の引数、出力、終了コードは変わらない
- PR の Checks のジョブの名前は、シャードの番号の分母が変わる。ブランチの保護で必須のジョブを名前で指定しているときは、人間が設定を直す

## テスト

止まりの直しは T27 で、時間切れの記録は `tests/test-runner-test.sh` の新しいケースで確認する。遅さとジョブの打ち切りは、CI の実測で確認する。

- T27: 直す前の包みで落ち、直したあとの包みで通る
- 時間切れの記録: 上限 2 秒で、`tests/tty-session.py` の下で眠るテストを流す。ログに `---- 時間切れの記録`、セッションのプロセスの一覧、`tty-session.py` の `select` の行を含むスタックが出る
- `LIST` に、セッションの外のプロセスが出ない。スタックのディレクトリに、セッションの外の PID と整数でない名前のファイルを置いても、そこへ SIGUSR2 を送らない
- 最後の push の CI で、全ジョブが最初の試行で通る。最も長いテストが 450 秒未満、最も長いジョブが 15 分未満である

次を、確かな結果として扱う。[terminal-tests.md の「テスト」](terminal-tests.md#テスト)の 1 と 2 と同じ扱いである。

1. 流し直して通った結果で、最初の失敗を置き換えない
2. 450 秒と 15 分の上限、ケースの数を変えていないことを、PR の base との差分で確認する

## 残る危うさ

- T27 は、取り落としの順序を差し込みで作る。CI の止まりが同じ順序だったかは、時間切れの記録が出るまで直接には見えない

- 600 秒の目安は、b44260d の 1 回のずれから決めた。ランナーがさらに遅くなると、15 分に近づく

## 検討した案

型ごとに、選んだ案と選ばなかった案を書く。

### 止まりの直し方の案

`set_wakeup_fd` を選んだ。期限つきの `select` と定期の `waitpid` でも止まりは消えるが、補助に期限を足さない決まりに反し、待つ長さを決める必要がある。シグナルの受け方を `signalfd` や `sigwait` に替える案は、macOS にないか、包みの作りを大きく変えるので選ばなかった。

### 再現の作り方の案

順序を差し込みで決めるケースを選んだ。負荷をかけた繰り返しは、手元では再現せず、再現しないことが直った根拠にならない。`select` を本物の期限なしで呼ぶ再現は、直す前に 450 秒まで止まるので選ばなかった。

### 時間切れの記録の案

SIGUSR2 と `faulthandler` を選んだ。`py-spy` などの外の道具は、CI への導入が要り、macOS では権限が要る。全プロセスに SIGABRT を送る案は、登録していないプロセスを止めてしまう。

### シャードの数の案

600 秒を選んだ。今の 300 秒の目安を保つと、macOS は 11 のシャードが要り、待ちが大きくなる。macOS を 5 つのままにする案は、テストを短くしても 15 分に届かないと言い切れない。OS ごとに別の重みを持つ案は、重みを写す手間が倍になるので、今は選ばない。

### 遅いファイルの案

分けることを選んだ。並列数を下げる案は、全体の時間が延びる。上限を延ばす案は、要件で外した。
