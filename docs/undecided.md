# 設計文書に「決まっていないこと」の節を置き、期限ごとに人間へ出す

設計の役は、設計文書に「決まっていないこと」の節を置き、決める期限ごとに人間への依頼に出す。期限が設計の承認の行は承認を頼むコメントの「決めてほしいこと」に、期限がマージの前の行は PR の本文の注意の先頭に書く。この文書は、共通スキルに足す節の全文と、置き場所とその理由を書く。

## 目的と範囲

今は、設計を承認する人間とマージを判断する人間が、決まっていないことを 1 か所で読めない。選ばなかった案と残る危うさは、この原本の設計文書に節としてある。決まっていないことに当たる節を持つ文書は 0 で、節の中の 1 文として 3 文書に散っている。

過去の設計 1 件では、決める期限がマージの前の問いが、承認を頼むコメントの段落の最後の 1 文に埋まっていた。人間の承認は設計とフェーズだけを指し、その問いはマージまで決まらなかった。設計文書には、食い違う 2 文がそのまま残った。

目的は次の 3 つである。

1. 設計文書で、決まっていないことと、決める人・期限・決まるまでの扱いを 1 か所で読める
2. 期限が設計の承認の行を、承認を頼むコメントで人間に問う
3. 期限がマージの前の行を、PR の本文の注意に置き、マージの依頼まで届ける

次は対象にしない。

- 今ある設計文書へ遡って節を足すこと。配る側に足すだけと合意した
- マージの依頼に別の行を足すこと。マージの依頼は注意を写すので、注意に書けば届く
- 本物のモデルを流す確認。確認は、役のひな形のテストと書き方・リンクの検査だけにする

## 足す節

共通スキル squad-handoff（`common/skills/squad-handoff/SKILL.md`）の「PR を作る・実装を積む」に、小節を 1 つ足す。置き場所は「PR の本文の置き場所と順序」の小節のあと、「PR にレビューやテストの結果を書く」の節の前である。

### 置き場所を共通スキルにする理由

設計の役の指示には、足す文が入る空きがない。展開後の大きさは最大 12,261 バイトで、テストの上限 12,288 バイトまで 27 バイトしかない。足す節の全文は 2,500 バイトほどで、指示に入れるには、ほかの決まりを同じだけ削る必要がある。

共通スキルなら、設計の役の指示を変えずに届く。設計の役の指示は、PR の本文を「PR を作る・実装を積む」のとおりに書くと、すでにこの節を指している。設計の役は、受け取ったら最初に共通スキルの「タスクの作業先を決める」に従うので、設計文書を書く前に共通スキルを読む。

共通スキルには、もう 1 つ利点がある。PR の本文を書き直す実装の役と修正の役も、同じ節を読む。注意の先頭の行を書き直しで消さない決まりを、役の指示を変えずに届けられる。

### 節の全文

足す節の全文は次のとおりである。

````markdown
### 設計文書の決まっていないこと

設計の役は、設計文書に「決まっていないこと」の節を置き、期限ごとに人間への依頼に出す。問いが文の中に埋もれると、決める人も期限も読めず、決まらないままマージまで進むため。

節は「残る危うさ」の後、「検討した案」の前に置く。作業先のリポジトリに節の名前や並びの決まりがあれば、それに従う。今ある設計文書には、その文書を変えるときに、決まっていないことがあるときだけ足す。

節は次の列の表にする。決まっていないことがないときは、表を置かず「なし」と書く。

| 決まっていないこと | 今決めない理由 | 決める人 | いつまでに | 決まるまでの扱い |
| --- | --- | --- | --- | --- |
| 例: 端末の仕事を、毎回の PR で流すか | かかる時間は実装のあとに分かる | 人間 | マージの前 | 毎回流す |

いつまでにの欄は、`設計の承認`・`マージの前`・`マージのあと（<時機>）` のどれかにする。期限ごとに、次の書き先へ出す。

| いつまでに | 書き先 | 書く役 |
| --- | --- | --- |
| 設計の承認 | 承認を頼むコメントの「決めてほしいこと」。行ごとに案ごとの良い点・悪い点と推す案を添え、違う案を選ぶなら設計を直して承認を頼み直すと書く | 設計の役 |
| マージの前 | PR の本文の注意の始め。ほかの行より先に、1 行ごとに下の形で書く | PR を作る役と、本文を書き直す役 |
| マージのあと | 設計文書の節だけ | 設計の役 |

```text
- マージの前に決めること: <決まっていないこと>。決まるまでは<決まるまでの扱い>
```

- 注意の始めのこの行は、本文を書き直すときも残す。設計文書の表から行が消えたときだけ消す
- 期限が設計の承認の行は、決まるまでの扱いに推す案を書く。推す案のままで承認されたら、推す案に決まる
- 人間が推す案と違う案を選んだら、承認ではなく設計の直しの依頼として扱う。設計の役が設計文書を直し、承認を頼み直す
- 実装の役は、表に残る行を、決まるまでの扱いのとおりに作る
- 決まった行は、設計の役が次にその設計文書を変えるときに表から消し、決めたことを該当する節に書く
````

### 期限ごとの書き先

書き先は、人間がその期限に読むものにする。設計の承認では承認を頼むコメントを読み、マージでは、注意を写したマージの依頼を読むためである。

| いつまでに | 書き先 | 人間が読む時機 |
| --- | --- | --- |
| 設計の承認 | 承認を頼むコメントの「決めてほしいこと」 | 設計を承認するとき |
| マージの前 | PR の本文の注意の始め | マージの依頼を読むとき。マージの依頼は、注意を `マージの前に人間がすること:` の行に写す |
| マージのあと | 設計文書の節だけ | 設計の承認で、設計文書の差分を読むとき |

マージの依頼を書くスクリプトは変えない。注意が「なし」でなくなるので、マージの依頼の読む深さは「このコメントと PR の注意」以上になる。注意の写し方と読む深さの決め方は、[マージの依頼に読む深さと残した指摘を足す](merge-request-reading.md)の設計のままである。

期限が設計の承認の行は、承認の答えを設計文書へ書き戻す手順を置かない。推す案を決まるまでの扱いに書いておけば、推す案のままの承認で、設計文書は承認された内容と食い違わない。推す案と違う答えは設計の直しとして扱うので、設計文書は直してから承認し直される。どちらでも、実装の役は設計文書の扱いのとおりに作ればよい。

PR の本文は、設計文書にある情報を写さず節の名前で示す決まりである。注意の行はその例外にする。マージの依頼が読むのは PR の本文の注意だけで、設計文書は読まないためである。写すのは問いと決まるまでの扱いの 1 文にとどめ、理由と決める人は設計文書に残す。

### 表の列

列は、決まっていないこと・今決めない理由・決める人・いつまでに・決まるまでの扱いの 5 つにする。「今決めない理由」「決める人」「いつまでに」は、要件の合意で根拠にした記事の未決定事項の書き方に当てた。「決まるまでの扱い」は、過去の設計 1 件で、決まらない間の動作が設計文書の 2 文で食い違っていたことから足した。

「いつまでに」は 3 つの値に限る。書き先を値で決めるためである。マージのあとに決めることは、この PR の中で人間に問う時機がないので、設計文書だけに置く。

### この原本の節の並び

この原本の `STYLE.md` の「文書の種類ごとの構成」は、設計の節の並びと、すでにある文書の構成の決まりを持つ。共通スキルの節は作業先の決まりに従うので、両方を直さないと、この原本では節を置けない。

新しく書く文書のために、並びに「決まっていないこと」を足し、「残る危うさ」と「検討した案」の間に置く。

```diff
-| 設計 | `docs/` | 目的と範囲・決めたことの節・文書と指示の変更・互換性・テスト・残る危うさ・検討した案 |
+| 設計 | `docs/` | 目的と範囲・決めたことの節・文書と指示の変更・互換性・テスト・残る危うさ・決まっていないこと・検討した案 |
```

すでにある文書のために、小節「すでにある文書の構成」に例外を足す。今の決まり「並びの表にあって文書にない節は、足さない」のままでは、すでにある設計文書を変える設計で節を置けない。置かなければ表がなく、PR の注意の行を消してよいかを決める根拠もなくなる。main で 9 月以降に 6 回以上変えた設計文書は 11 あり、すでにある文書を変える設計はまれではない。

小節の表のあとに、次の段落を足す。表の行は変えない。

```markdown
例外として、「決まっていないこと」の節は、すでにある設計文書にも、その文書を変える PR に決まっていないことがあるときに足す。置く位置は「検討した案」の前とし、その節がない文書では最後にする。ほかの節は動かさない。
```

決まっていないことがないときは、すでにある文書に「なし」の節を足さない。問いのない節は、人間に出すものがないうえ、文書を変えるたびに差分が増えるためである。

`docs/doc-style.md` にある同じ並びと 3 つの決まりの写しは変えない。今ある設計文書には差分を出さないと合意したためである。写しの表は、正本を `STYLE.md` の小節として示しているので、例外は正本で読める。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイル（共通スキル）に、役にさせる文を足す。条件の 3 つを次に書く。

### 根拠

合意された要件による新しい手順なので、要件の合意を失敗の記録に代える。合意の記録と、過去の設計 1 件の実物は、タスクのコメントにある。

過去の 1 件では、マージの前に決める問いが、承認を頼むコメントの段落に 1 文で書かれていた。人間の「OK」は設計とフェーズの承認と読まれ、問いはマージの前の未確認の一覧にも入らなかった。

### 働いた跡

手順が働くと、リーダーのマージの依頼に、注意を写した `マージの前に決めること:` の行が残る。見直しの跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 項目 | 値 |
| --- | --- |
| 形 | `kind: "comment"` |
| `pattern` | `マージの前に決めること:` |
| `author_type` | `agent` |

期限が設計の承認の行は、承認を頼むコメントの今の項目「決めてほしいこと」に書くので、ほかの問いと見分けて数えない。この跡は、マージの前の問いを持つ設計が 20 件の中にないと 0 回になる。0 回のときに削る候補とするかは、見直しで人間が判断する。

### 仕組みにしない理由

仕組みの案は 3 つある。どれも、この手順に代えない。

| 案 | 選ばなかった理由 |
| --- | --- |
| マージの依頼を書くスクリプトが、設計文書の表を読んで行を足す | 要件の合意で、マージの依頼に別の行を足さないと決めた。導入先ごとに設計文書の置き場所と節の名前が違い、スクリプトから表を見つけられない |
| CI が、`docs/` の新しい文書に「決まっていないこと」の節があるかを検査する | この原本にしか効かない。節があっても、文の中に埋もれた問いを表に出したかは見分けられない |
| スクリプトが、設計文書の表の行と PR の本文の注意の行を突き合わせる | 設計の役が PR を作るときに通る仕組みは紐付けのスクリプトだけで、本文を読まない。導入先ごとの文書の形に合わせて表を読む手間に、起きた失敗 1 件が見合わない |

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと、共通スキルが新しいものに替わる。替わったあとに設計するタスクで、設計の役の出力が変わる。

| 利用者 | 変わること |
| --- | --- |
| 設計の役 | 新しく書く設計文書と、決まっていないことがあるときの変える設計文書に、「決まっていないこと」の節が増える。期限に応じて、承認を頼むコメントの「決めてほしいこと」と、PR の本文の注意に行が増える |
| 実装の役・修正の役 | PR の本文を書き直すときに、注意の始めの `マージの前に決めること:` の行を残す。表に残る行は、決まるまでの扱いで作る |
| リーダー | 手順は変わらず、マージの依頼は今のとおり注意を写して人間に届ける。推す案と違う案を選ぶ人間の答えには、承認でない返事として今のとおり設計の役に直しを頼む |
| 導入したプロジェクトの担当 | 設計の承認とマージのときに、決まっていないことを 1 件ずつ読める |

エージェントとオートパイロットの登録は変わらない。役のひな形の形式と、拡張との契約も変わらない。見張りのスクリプトが読む固定の行も変えない。

共通スキルはすべての役が読むので、流し直しで、すべての役が新しい共通スキルを読む。節の手順を行うのは、設計の役と、PR の本文を書き直す役だけである。

流し直す前に動いている設計のタスクは、前の決まりのまま進む。その設計文書や PR に節や行がなくても、誤りにはしない。

### 変更の知らせ

この変更の知らせは、バージョンを上げる PR が、`CHANGELOG.md` に次の文で足す（[release.md の変更の知らせ](release.md#変更の知らせ)の決まり）。設計の承認とマージの依頼に増える行を、導入したプロジェクトの担当が更新の前に知れるようにするため。

登録が変わらないと書く文は、同じ節のほかの変更と食い違わないよう、「この変更では」とこの変更の範囲に限る。

```markdown
設計の役が新しく書く設計文書に、「決まっていないこと」の節を置くようにした。決める期限が設計の承認なら承認を頼むコメントの「決めてほしいこと」に、マージの前なら PR の本文の注意の `マージの前に決めること:` の行に書く。流し直しで、共通スキルが替わる。

実装の役と修正の役は、PR の本文を書き直すときに `マージの前に決めること:` の行を残す。リーダーの手順は変わらない。この変更では、エージェントとオートパイロットの登録は変わらない。

流し直す前に動いている設計のタスクは、前の決まりのまま進む。その設計文書や PR に節や行がなくても、誤りにはしない。
```

## テスト

`tests/agent-templates-test.sh` に、次を確認する 1 つの PASS を足す。確認するのは、[テストを書く決まり](../CONTRIBUTING.md#テストを書く決まり)のひな形の契約に当たるものだけである。

| 確認すること | 失敗したときに直すこと |
| --- | --- |
| 共通スキルに、見出し `### 設計文書の決まっていないこと` がちょうど 1 つある | 節を足すか、重なった節を消す |
| その節が「PR を作る・実装を積む」の節の中で、「PR の本文の置き場所と順序」の小節より後にある | 節を置き場所へ戻す |
| 節の中に、表の列の見出しの行と、`- マージの前に決めること:` で始まる行の形が、行のまま 1 つずつある | 行の形を戻す |
| 節の中に、いつまでにの 3 つの値 `設計の承認`・`マージの前`・`マージのあと` がある | 値を戻す |

設計の役の指示の大きさは、今のテスト（12,288 バイト以内）で確認する。指示を変えないので、このテストは今と同じく通る。

行の形を確認するのは、`マージの前に決めること:` を[働いた跡](#働いた跡)の定義が読むためである。テストには、読む側として跡の定義をコメントで添える。

節の説明の文は、固定の文字列で確認しない。設計の役の指示、マージの依頼を書くスクリプト、今ある設計文書に差分がないことは、テストに足さない。設計の承認を頼むコメントの成功の条件で、実装の役が main との分岐点からの差分を見るコマンドで確認する。

## 残る危うさ

次の 4 つは、この決まりで残る。

1 つ目は、決まっていないことを設計の役が気づかないことである。節があっても、設計の役が知らない問いは書けない。承認のあとに設計を変える理由の多くは、承認のときに設計の役が知らなかったことで、この節では防げない。

2 つ目は、決まった行が設計文書に残ることである。期限が設計の承認の行は承認で決まり、期限がマージの前の行は人間がマージの直前に決めることが多い。どちらも、設計の役がその設計文書を次に変えるまで、表に行が残る。設計の承認の行は、決まるまでの扱いが承認された推す案なので、残っても実装を誤らせない。

3 つ目は、期限がマージのあとの行に、人間を呼ぶ時機がないことである。設計の承認で設計文書の差分を読むときにだけ、人間の目に触れる。

4 つ目は、人間が推す案と違う案を、承認の言葉と同じ返事に書くことである。リーダーが承認と読むと、設計文書は推す案のまま実装へ進む。承認を頼むコメントの決めてほしいことで、違う案を選ぶときは設計を直して承認し直すと示して減らす。

## 検討した案

置き場所・書き先・表について、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| 設計の役の指示に節を置き、ほかの文を縮めて空きを作る | 足す文は 2,500 バイトほどで、空きの 27 バイトに入らない。縮める文を選ぶと、今の決まりを弱める変更が同じ PR に入る |
| 設計の役の指示に、共通スキルの節を指す 1 文だけを足す | 1 文でも 27 バイトを超える。指示はすでに「PR を作る・実装を積む」を指しているので、足さなくても届く |
| 共通スキルの参照ファイル（`references/`）に、設計の役の手順として置く | 参照ファイルはリーダーの手順だけで、設計の役は読まない。読ませるには、指示に参照の文を足す必要がある |
| 導入先のひな形 `skeleton/.agents/rules/docs.md` に置く | 導入先が記入するひな形で、記入のときに消されることがある。この原本では使わない |
| 「検討した案」と「残る危うさ」も、同じ節に名前を入れる | 要件にない。共通スキルは、PR の本文の決まりで「検討した案」をすでに指している |
| 期限がマージのあとの行も、PR の本文の注意に書く | 注意はマージの依頼で `マージの前に人間がすること:` に写る。マージの前に人間がすることと読み違える |
| すでにある文書には、`STYLE.md` のとおり節を足さない | 表がないと、PR の注意の行を消してよいかを決める根拠がない。すでにある文書を変える設計は、まれではない |
| すでにある文書を変えるときは、決まっていないことがなくても「なし」の節を足す | 人間に出す問いがないのに、文書を変えるたびに差分が増える |
| 設計の承認の答えを、承認のあとに設計の役が設計文書へ書く | 承認のあと、リーダーは設計の役を呼ばずに実装へ回す。書かせるにはリーダーの手順に実行を 1 回足す必要があり、推す案を扱いに書けば要らない |
| 決まった行を、マージの前に設計の役が消す | 人間がマージの直前に決めると、設計の役を呼ぶ実行が 1 回増える。マージの依頼を変えないと合意したので、消す時機を足せない |
