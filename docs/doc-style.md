# 文書の書き方のガイドと検査

人間が読む文書の書き方を、リポジトリの直下の `STYLE.md` にまとめる。機械で判定できる決まりは CI で検査し、書き直しの前後を照合するコマンドと、構成と図を確認する検査表を用意する。

この文書は、ガイドの決まりの案・検査・照合・検査表と、役が書く文の言い回しの決まりと、その理由を書く。用語は [terms.md](terms.md) を、コメントの形は共通スキル `squad-handoff` を正本とし、この文書は写さない。

## 目的と範囲

目的は、人間が読む文書の書き方を 1 つの正本にそろえ、書き直したあとも崩れないようにすることである。

ガイドと検査の対象は、次の 3 つである。

- 入口の 5 文書。`README.md`・`manual.md`・`CONTRIBUTING.md`・`EXTENSIONS.md`・`skeleton/README.md` である
- `docs/` のすべての文書。この文書も含む
- ガイドの `STYLE.md` 自身

決めるのは次の 8 つで、それぞれの節に書く。

1. お手本と、取り入れた点。[お手本](#お手本)に書く
2. ガイドの置き場所と節の並び。[ガイドの置き場所と構成](#ガイドの置き場所と構成)に書く
3. 10 項目の決まりの案。[決まりの案](#決まりの案)に書く
4. CI の検査と、対象外の一覧。[検査](#検査)に書く
5. 書き直しの前後の照合。[照合のコマンド](#照合のコマンド)に書く
6. 構成・図・分かりやすさの検査表。[検査表](#検査表)に書く
7. 書き直しで決めた扱いの決まりと、照合の限界。[書き直しの扱いを決まりにする](#書き直しの扱いを決まりにする)に書く
8. 役が書く文の言い回しの決まりと、その対象。[言い回しの決まり](#言い回しの決まり)に書く

次は、この文書の範囲の外である。

- コメントの形の型。`squad-handoff` が決める
- 用語の変更と、手順・コマンド・設計の中身の改善
- AI が読むもの（役の指示・共通スキル・`AGENTS.md`・作業別のルール・記入用のひな形）に、10 項目の決まりと検査を当てること

ただし、言い回しの決まりは、AI が読むものを書くときと変えるときにも使う。対象は[対象と優先](#対象と優先)に書く。

## お手本

お手本は、5 件を比べて 4 件を選んだ。3 つの基準は 5 件とも満たすので、取り入れる点の多さで選んだ。

### 基準を満たす根拠

4 件とも、README と CONTRIBUTING があり、下の節を持つ。

| お手本 | コマンドで導入する道具と読み手 | README と CONTRIBUTING |
| --- | --- | --- | --- |
| astral-sh/uv | `curl` の導入スクリプトで入れる Python のパッケージ管理。読み手は端末で使う開発者 | README に特徴・導入・文書の案内。CONTRIBUTING に準備・テスト・整形・lint の節 |
| nvm-sh/nvm | `curl` の導入スクリプトで入れる Node.js のバージョン管理。読み手はシェルを使う開発者 | README に導入・導入の確認の方法・使い方・環境ごとの止まったとき。CONTRIBUTING に報告・開発の準備・決まり |
| ohmyzsh/ohmyzsh | `curl` か `wget` の導入スクリプトで入れる zsh の設定の枠組み。読み手はシェルを使う開発者 | README に始め方・使い方・応用・更新。CONTRIBUTING に報告・PR・コミットの決まり |
| cli/cli | パッケージ管理の道具で入れる GitHub の CLI。読み手は GitHub で開発する人 | README に文書の案内と OS ごとの導入。CONTRIBUTING にすること・しないこと・作り方・設計の決まり |

選ばなかった Homebrew/brew も、3 つの基準を満たす。ただし README の大半はほかの文書へのリンクで、CONTRIBUTING も詳細を外の文書に任せている。取り入れる点がほかの 4 件と重なるので、外した。

### 取り入れた点

お手本からは、主に文書の種類ごとの節の並びを取り入れた。ガイドの節の列は、取り入れた先の `STYLE.md` の節である。

| お手本 | 見たところ | 取り入れた点 | ガイドの節 |
| --- | --- | --- | --- |
| astral-sh/uv | README の冒頭 | 冒頭の 1 文で何の道具かを書き、詳細は別の文書へ送る | 文書の種類ごとの構成 |
| astral-sh/uv | README の図 | 図に、何を示す図かを 1 文で添える | 図 |
| astral-sh/uv | CONTRIBUTING | 準備・テスト・整形の順に、流すコマンドをコードブロックで示す | 文書の種類ごとの構成 |
| nvm-sh/nvm | README の導入 | 導入の手順の直後に、導入を確認する手順を置く | 文書の種類ごとの構成 |
| nvm-sh/nvm | README の後半 | 環境ごとの止まったときの節を、手順の後ろにまとめる | 文書の種類ごとの構成 |
| ohmyzsh/ohmyzsh | README の始め方 | 対応する環境と要るものを、手順の前に置く | 文書の種類ごとの構成 |
| ohmyzsh/ohmyzsh | README の応用 | 基本の手順と応用を分け、応用を後ろの節に置く | 文書の種類ごとの構成 |
| cli/cli | README の導入 | OS ごとの詳しい手順を別の文書へ分け、README を短く保つ | 文書の種類ごとの構成 |
| cli/cli | CONTRIBUTING | すること・しないことを、分けた箇条書きにする | 箇条書き・表・コード・注記 |

お手本の図は画像なので、図そのものは取り入れない。図は、差分で読める Mermaid だけにする。句読点と全角・半角は英語の文書から取れないので、JTF 日本語標準スタイルガイドを手本にする。

## ガイドの置き場所と構成

ガイドは、リポジトリの直下の `STYLE.md` に置き、題を「文書の書き方」とする。ファイルの名前は、ほかの入口の文書と同じく大文字の ASCII にする。

`README.md` の「次に読むもの」の表には、原本の文書を書く人の行があり、`STYLE.md` を指す。節は次の順に並べ、見出しの名前もこのとおりにする。ほかの文書がこの見出しへリンクするので、名前を変えるときは参照もすべて直す。

1. 対象と検査。対象の文書、対象外の一覧、検査のコマンドを書く
2. 文体
3. 改行
4. 句読点
5. 全角と半角
6. 文と段落の長さ
7. 文書の種類ごとの構成
8. 箇条書き・表・コード・注記
9. 図
10. リンク
11. 用語とコメントの型
12. 言い回し。役と人が書く文の言い回しの決まりを書く
13. 書き直しの照合。照合のコマンドの使い方を書く
14. 検査表

2〜11 が 10 項目の決まりで、12 が言い回しの決まりである。各節は、結論の 1〜2 文、決まりの箇条書き、直す前と直した後の例の順に書く。CI で検査する決まりには、その旨を添える。

例は、言語を `text` にしたコードブロックに書く。直す前の例は決まりに反するので、検査の外に置くためである。例の形は次のとおりである。

```text
直す前: 設定を確認してください。
直した後: 設定を確認する。
```

## 決まりの案

表の CI の列は、決まりを確認するところを示す。「検査」は文書の検査、「リンクの検査」はリンクの検査で落とし、「レビュー」は PR のレビューで読む。

書き直しで決めた扱いは、[書き直しの扱いを決まりにする](#書き直しの扱いを決まりにする)に書く。

### 文体

文体は、対象のすべての文書で常体（である調）にそろえる。

| 決まり | CI |
| --- | --- |
| 文末を `です`・`ます`・`ください`・`ません`・`でした`・`ました`・`でしょう`・`ましょう` にしない | 検査 |
| 読み手への指示は「〜する」と書き、「〜してください」と書かない | 検査 |
| 画面の文と引用は、元の文体のまま「」かインラインコードで囲む | レビュー |

### 改行

1 つの段落は 1 行に書き、文ごとに改行しない。`squad-handoff` の「本文の書き方」と同じ決まりである。

| 決まり | CI |
| --- | --- |
| 段落・箇条書きの項目・注記の文は、途中で改行しない | 検査 |
| 行の末尾に空白を置かない。末尾の半角空白 2 つによる改行も使わない | 検査 |
| 段落の間・見出しの前後・表とコードブロックの前後に、空行を 1 つ置く | レビュー |

### 句読点

句読点と括弧は、JTF 日本語標準スタイルガイドに合わせる。

| 決まり | CI |
| --- | --- |
| 句読点は「、」と「。」にし、全角のカンマ `，` とピリオド `．` を使わない | 検査 |
| 箇条書きの項目・表のセル・見出しの末尾に「。」を付けない。途中の文には付ける | 検査 |
| 日本語を含む括弧は全角の（）にし、引用と画面の文は「」で囲む | 検査 |

### 全角と半角

英数字は半角にし、日本語と半角の英数字の間に半角の空白を 1 つ置く。空白を置く決まりは、JTF と違う。文書と `squad-handoff` が広く使っており、変えるとすべての文書に機械的な差分が出るためである。

| 決まり | CI |
| --- | --- |
| 全角の英数字・全角の空白・半角のカタカナを使わない | 検査 |
| 日本語と、半角の英数字・インラインコードの間に、半角の空白を 1 つ置く | 検査 |
| 句読点と括弧の前後には、空白を置かない | 検査 |

### 文と段落の長さ

長さは、`squad-handoff` の「本文の書き方」の目安を本文の決まりにし、CI はそれより広い上限で検査する。目安を CI の上限にすると、名前を並べる文まで不自然に分けることになるためである。

| 決まり | 目安 | CI の上限 |
| --- | --- | --- |
| 1 文の字数 | 60 字 | 80 字 |
| 1 文の読点 | 2 つ | 3 つ |
| 1 段落の文の数 | 2〜4 文 | 4 文 |
| 1 段落の字数 | 200 字 | 240 字 |
| 箇条書きの 1 項目の文の数 | 1〜2 文 | 2 文 |
| 表のセルの文の数 | 語句か 1 文 | 2 文 |

字数と文の数え方は、[字数と文の数え方](#字数と文の数え方)に書く。

### 文書の種類ごとの構成

文書を 4 つの種類に分け、種類ごとに節の並びを決める。並びは、[取り入れた点](#取り入れた点)のお手本から取った。

| 種類 | 文書 | 節の並び |
| --- | --- | --- |
| 入口 | `README.md`・`skeleton/README.md` | 何かを 1〜2 文・始め方・対応する範囲・次に読むもの。詳細は別の文書へ送る |
| 手順 | `manual.md` | 前提と要るもの・手順・確認の方法・応用・止まったとき |
| 決まり | `CONTRIBUTING.md`・`EXTENSIONS.md`・`STYLE.md` | 決まりの要約・決まりごとの節・確認の方法とコマンド |
| 設計 | `docs/` | 目的と範囲・決めたことの節・互換性・テスト・残る危うさ・検討した案 |

見出しの決まりのうち、次は CI で検査する。H1 は文書の先頭の 1 つだけにし、見出しの階層は 1 つずつ下げて `####` までにする。見出しのすぐ後に見出しを続けず、その節の結論を 1〜2 文で書く。

### 箇条書き・表・コード・注記

箇条書きと表の使い分けは、`squad-handoff` の「本文の書き方」と同じにする。ガイドは決まりを写さず、その節を指し、文書だけの決まりを別に持つ。

| 決まり | CI |
| --- | --- |
| 箇条書きの入れ子は 1 段までにする | 検査 |
| コードブロックには言語を書く。コマンドは `bash`、出力は `text` にする | 検査 |
| コマンドの前に、プロンプトの `$` を付けない | 検査 |
| 注記は GitHub の `> [!NOTE]` と `> [!WARNING]` だけにし、1 つの節に 1 つまでにする | レビュー |
| すること・しないことのように対になる決まりは、分けた箇条書きにする | レビュー |

### 図

図は Mermaid のコードブロックで書き、画像は置かない。図を置くのは、3 つ以上の手順・役・状態が、順序か分岐でつながるときである。

| 決まり | CI |
| --- | --- |
| 画像（`![` と `<img`）を置かない。図は言語を `mermaid` にしたコードブロックにする | 検査 |
| 役の間の引き継ぎ、状態の移り変わり、条件による分かれ道に図を置く | レビュー |
| 2 つ以下の手順や、表で比べられるものには図を置かない | レビュー |
| 図の直前に、図が示すことを 1 文で書く。図に本文にない事実を足さない | レビュー |
| 図の語は、本文と [terms.md](terms.md) の語にそろえる。色と `style` は指定しない | レビュー |

色を指定しないのは、GitHub の明るい表示と暗い表示の片方で読めなくなるためである。1 つの図の箱は、12 個ほどまでを目安にする。

### リンク

リポジトリの中は相対パスで指し、リンクの文字で行き先が分かるようにする。

| 決まり | CI |
| --- | --- |
| リポジトリの中のファイルを、GitHub の URL で指さない | 検査 |
| リンク先のファイルと見出しがある | リンクの検査 |
| リンクの文字を「こちら」「ここ」「リンク」にせず、節やファイルの名前にする | 検査 |
| 正本がほかにある決まりは写さず、その節へリンクする | レビュー |

### 用語とコメントの型

用語とコメントの型は、ガイドに写さず正本を指す。

- 用語は [terms.md](terms.md) に従い、`tests/terms-test.sh` で検査する
- タスクと PR のコメントの書き方と型は、`squad-handoff` の「本文の書き方」と各節に従う
- ガイドは、`squad-handoff` の節の名前で案内する。節の名前が変わったら、同じ PR でガイドの案内を直す

## 検査

検査は、3 つのコマンドと、それぞれのテストで行う。どのコマンドも Python の標準ライブラリだけで動くので、CI に新しい道具は要らない。

| コマンド | 役目 | テスト |
| --- | --- | --- |
| `scripts/check-style.py` | ガイドの決まりのうち、機械で判定できるものを検査する | `tests/style-test.sh` |
| `scripts/check-links.py` | リポジトリの中のリンクとアンカーを検査する | `tests/links-test.sh` |
| `scripts/doc-compare.py` | 書き直しの前後を照合する | `tests/doc-compare-test.sh` |

テストは `tests/run.sh` が拾うので、CI の Tests の手順で流れる。`tests/style-test.sh` と `tests/links-test.sh` は、リポジトリの実際の文書も検査する。決まりに反する文書を入れると、この 2 つのテストが落ちる。

### 対象と対象外の一覧

対象外の一覧は `scripts/style-exempt.txt` に置き、1 行に 1 つのパスを名前順に書く。一覧を `tests/` の外に置くのは、書き直しの PR がテストのファイルを変えずに一覧から外せるようにするためである。

一覧は、書き直していない文書を検査から外すときに使う。`STYLE.md` とこの文書は一覧に入れず、検査を通す。書き直した文書は、その行を一覧から消す。

`scripts/check-style.py` は、一覧に次の誤りがあると、行の番号を添えて止まる。

- 対象の文書でないパス、またはないファイル
- 名前順でない行、重なった行、空の行

対象外の文書を変えるときは、書き直すまでそのファイルの今の書き方に合わせる。

### 検査のコマンドと出力

引数がなければ、対象の文書のうち一覧にないものをすべて検査する。ファイルを引数に渡すと、一覧にあっても検査するので、書き直しの途中で使える。

```bash
python3 scripts/check-style.py
python3 scripts/check-style.py docs/doc-style.md
```

違反は、1 件を 1 行にして標準エラーに出す。行は `<パス>:<行>: <節>: <決まり>` の形で、節はガイドの見出しの名前にする。

```text
docs/example.md:12: 文体: 文末を「です」「ます」にしない
docs/example.md:15: 文と段落の長さ: 1 文は 80 字まで（92 字）
```

終了コードは、違反がなければ 0、違反があれば 1、引数や一覧の誤りは 2 にする。コードブロック、インラインコード、HTML のコメントの中は検査しない。文体と文の区切りでは、「」の中も検査しない。

### 字数と文の数え方

字数と文は、表示される文字で数える。数え方を決めておくと、誰が数えても同じ結果になる。

- 文は「。」「？」「！」で区切る。「」と（）の中の記号では区切らない
- 段落・箇条書きの項目・表のセルの最後の文は、「。」がなくても 1 文に数える
- インラインコードは、長さによらず 1 字に数える。リンクは、リンクの文字だけを数える
- 半角の空白と、文の終わりの「。」「？」「！」は字数に数えない。半角の英数字は 1 字に数える
- 読点は「、」の数で数える。「」と（）の中の「、」も数え、インラインコードの中の「、」は数えない

### リンクの検査

`scripts/check-links.py` は、Git が追跡するすべての Markdown のリンクを検査する。対象の文書に限らないのは、リンクの切れはどの文書でも読み手を迷わせるためである。

| 調べるもの | 決まり |
| --- | --- |
| 調べるリンク | `[文字](先)` と参照の定義 `[名前]: 先`。コードの中は除く |
| 調べないリンク | `http:`・`https:`・`mailto:`・`mention:` で始まる先 |
| ファイル | 書いたファイルのディレクトリから相対で解き、ファイルかディレクトリがある |
| アンカー | 先が Markdown なら、見出しから作るアンカーか `<a id>` に一致する |

アンカーは GitHub と同じ規則で作る。英字を小文字にし、文字・数字・空白・`-`・`_` 以外を消し、空白を `-` にする。同じアンカーが 2 つ目からは、`-1`・`-2` を末尾に付ける。

切れは `<パス>:<行>: リンク: <先> のファイルがない` か、`のファイル` を `の見出し` にした形で 1 件 1 行に出し、終了コード 1 で止まる。

## 照合のコマンド

照合のコマンドは、書き直しの前後で 4 つの要素の集合が一致するかを、ファイルごとに比べる。要素は、コードブロックの中身・インラインコードの語・数値・リンク先である。

```bash
python3 scripts/doc-compare.py --base origin/main
python3 scripts/doc-compare.py --base origin/main --head HEAD docs/metrics.md
```

`--base` は比べる前のコミットで、省略できない。`--head` を省略すると作業ツリーと比べ、ファイルを省略すると、前と後で違う対象の文書をすべて比べる。マージの前は、最新の main を取り込んでから `--base origin/main` で流し直す。

要素は、次のとおりにそろえてから比べる。そろえ方で消える差は、改行・字下げ・言語の名前のように意味を持たないものだけである。

| 種類 | 拾うもの | そろえ方 |
| --- | --- | --- |
| コード | 言語が `mermaid` 以外のコードブロックの中身 | 共通の字下げと行の末尾の空白を除く。言語の名前は比べない |
| 図 | 言語が `mermaid` のコードブロックの中身 | コードと同じ |
| インラインコード | インラインコードの中の文字列 | 前後の空白を除く |
| 数値 | コードとリンク先の外の数字の並び。`1.13.0` や `2026-11-17` は 1 つに数える | 番号付きの箇条書きの番号は除く |
| リンク先 | リンクと参照の定義の先 | 相対の先を、リポジトリの直下からのパスに直す。アンカーは残す |

出力は、1 行目が比べたコミット、2 行目からが差で、最後が件数である。差は、ファイル・種類の順・前後・値の順に並べるので、誰が流しても同じ結果になる。

```text
照合: 1c021af → 作業ツリー
差: docs/metrics.md 数値 - 60
差: docs/metrics.md インラインコード + squad-metrics
差: docs/metrics.md 図 + 3f2a9c1e flowchart LR
照合の結果: 差 3 件
```

コードと図の値は、中身の sha256 の先頭 8 文字と、1 行目の先頭 40 字である。終了コードは、差がなければ 0、差があれば 1、コミットやパスの誤りは 2 にする。

ファイルをまたいで節を移すと、元のファイルの `-` と、移した先の `+` の 2 行になる。PR の照合の記録では、この 2 行を対にして理由を書く。

## 検査表

構成・図・分かりやすさ・言い回しは機械で判定できないので、はい・いいえで答える検査表で確認する。検査表は `STYLE.md` の「検査表」の節に、言語を `markdown` にしたコードブロックで置く。書き直しの PR に、そのまま写して答えられるようにするためである。

検査表の項目は、次のとおりである。どの項目も、はいが望ましい答えになるように書く。構成の 2・3 と図の 1 は、書き直しの扱いの決まりで除くものがある。

構成の項目は次の 5 つである。

1. 冒頭の段落で、文書の目的と読み手が分かるか
2. 節の並びと名前が、「文書の種類ごとの構成」の決まりのとおりか
3. テストがすぐ下を読む見出しを除き、どの見出しのすぐ下にも、その節の結論が 1〜2 文であるか
4. 1 つの節が 1 つの話題だけを扱っているか
5. 正本がほかにある決まりを写さず、その節へリンクしているか

図の項目は次の 4 つである。

1. 「図」の決まりで図にしなくてよいものを除き、3 つ以上の手順・役・状態が順序か分岐でつながる箇所に、図があるか
2. 図の直前に、図が示すことを書いた 1 文があるか
3. 図にある事実が、すべて本文にも書かれているか
4. 図の語が、本文と [terms.md](terms.md) の語と同じか

分かりやすさの項目は次の 4 つである。

1. 1 つの文が 1 つのことだけを書いているか
2. 「これ」「その」などの指す先が、同じ段落の中で分かるか
3. 読み手がすることを、誰が何をするかの形で書いているか
4. 打ち消しを重ねた文がないか

言い回しの項目は次の 5 つである。読み直しの決まりは、この 5 つを見ることなので、項目にしない。

1. 依頼・資料・実行の結果にない事実・理由・数値・予定を書いていないか
2. 前置き・依頼の言い直し・末尾のまとめ直し・頼まれていない別案・していないことの列挙がないか
3. 予定と推測を、確認したことと文末で書き分けているか
4. 同じものを同じ語で書き、新しい語を作っていないか
5. 長さの目安に合わせるために、理由や条件のつながりを切っていないか

## 書き直しの扱いを決まりにする

書き直しでは、ガイドの決まりだけでは決まらない扱いが出る。ガイドは、その扱いを 8 つの決まりと照合の限界 2 つとして持つ。

次に文書を書く人が、同じ迷いをくり返さないようにするためである。この 8 つの決まりはどれもレビューで読み、検査と照合のコードとテストでは確認しない。

### 足す決まり

8 つの決まりは、主題の合う節に置く。`STYLE.md` の H2 の名前は、検査の出力とテストが使うので変えない。

| 決まり | 文言 | 置く節 |
| --- | --- | --- |
| 節の名前 | 並びの表にない名前の節は、名前を変えない。並びは、節の位置で当てはめる | 「文書の種類ごとの構成」の小節「すでにある文書の構成」 |
| ない節 | 並びの表にあって文書にない節は、足さない | 「文書の種類ごとの構成」の小節「すでにある文書の構成」 |
| 節の順 | 節の順が並びの表と違う文書は、節を動かさない | 「文書の種類ごとの構成」の小節「すでにある文書の構成」 |
| 設計でない文書 | `docs/` にあっても設計でない文書には、設計の並びを当てはめない。例は `dependency-audit.md` である | 「文書の種類ごとの構成」の種類の表の直後 |
| 条件の表 | 上から順に当てはめる条件の表は、分かれ道に当たっても図にしなくてよい | 「図」の表 |
| 番号の手順 | 1 人か 1 つのスクリプトが順に行う番号の手順は、3 つ以上でも図にしなくてよい。1 人には 1 つの役も含める | 「図」の表 |
| 外から指される見出し | 範囲の外の文書やテストが指す見出しは、変えない。テストが見出しのすぐ下を読むときは、すぐ下も変えない | 「リンク」の表 |
| 表の行の分け方 | セルが 2 文に収まらない行は、同じ対象の行に分ける。前の行に頼る行には、前提の語を補う | 「箇条書き・表・コード・注記」の表 |

節の名前・ない節・節の順は、すでにある文書だけに当てはめる。すでにある文書は、PR の base の main にある文書をいう。新しく書く文書は、並びの表に従う。

ほかの語は、次のとおりに定める。

- 設計でない文書は、決めたことと理由でなく、手順や一覧の正本を持つ文書である
- 外から指される見出しの範囲は、その PR が変える文書である
- 番号の手順の「1 人」は、人と役のどちらでもよい。`vm.md` の「中の準備」のように、スクリプトが順に流す手順も同じに扱う

### 照合の限界と補い方

照合のコマンドが見逃す差が 2 つあり、`STYLE.md` の「書き直しの照合」の最後に表で書く。補い方は、レビューと書く人の検索にする。

| 限界 | 見逃す差 | 補い方 |
| --- | --- | --- |
| 集合で比べる | 2 つある同じ値の片方が消えても、差に出ない | レビューで、前と後の文を読んで比べる |
| テストが読む文言を知らない | テストが読む見出しや文を変えても、検査も照合も落ちない | 書く人が、変える文言をリポジトリの中で検索する |

検索の例は次のとおりである。文言は固定の文字列で探し、`tests/` と `scripts/` の当たりを見る。

```bash
git grep -n -F '### Pillow のコマンド'
```

## 言い回しの決まり

役が書く文に、言い回しの決まりを 6 つ足す。同じ文言を共通スキル `squad-handoff` と `STYLE.md` に置き、書き直しで見比べる 4 つの項目も決める。

今の決まりは、文と段落の長さや型など、文の形を決めている。言い回しの決まりは、何を書き、何を書かないかという中身の書き方を決める。

### 6 つの決まり

決まりは次の 6 つである。名前と文言は、共通スキルと `STYLE.md` で同じにする。

| 名前 | 文言 |
| --- | --- |
| 事実 | 依頼・資料・実行の結果にない事実・理由・数値・予定を書かない。分からないことは、分からないと書く |
| 足さないもの | 前置き・依頼の言い直し・末尾のまとめ直し・頼まれていない別案・していないことの列挙を書かない |
| 確かさ | 確認したこと・予定・推測を、文末で書き分ける。予定や推測を言い切りにしない |
| 語 | 同じものを同じ語で書く。普段使う漢語と技術の語はそのまま使い、新しい語を作らない |
| 文の分け方 | 長さの目安に合わせるために、理由や条件のつながりを切らない |
| 読み直し | 出す前に 1 回読み直し、上の 5 つを見る |

2 か所には、`- <名前>: <文言>` の形の箇条書きで 1 行ずつ置く。テストがこの行を比べるためである。

### 対象と優先

決まりは、次の 4 つの文を書くときと変えるときに使う。

- タスクの本文とコメント、PR の本文、レビューと QA の結果
- 原本の人間が読む文書。`STYLE.md` の対象の文書である
- 導入したプロジェクトのリポジトリに、役が書く文書
- AI が読むもの。役の指示・共通スキル・`AGENTS.md`・作業別のルール・記入用のひな形である

今の決まりと食い違うときは、今の決まりを優先する。今の決まりは、常体・文と段落の長さの目安と CI の上限・[terms.md](terms.md) の語・コメントと本文の型と固定の行である。たとえば、足さないものの決まりがあっても、型の「残っていること」は書く。

導入したプロジェクトのリポジトリに書く文書では、そのリポジトリの書き方の正本を優先する。正本がないときは 6 つの決まりだけを使い、`STYLE.md` のほかの決まりは当てない。`STYLE.md` は、導入先に配置しないためである。

AI が読むものでは、判定に使う語・固定の行・スクリプトが読む行を、言い回しを理由に変えない。変えると、役の判断やスクリプトの動作が変わるためである。すでにある文は、この変更では書き直さず、後のステージで読み直す。

### 書き直しで直す所

書き直しと修正では、読める文は直さず、読み手が止まる理由を言える所だけを直す。好みの言い換えは、意味を変えるおそれがあり、差分も読みにくくするためである。

直したあとは、前と後の文で次の 4 つが同じかを、人が見比べる。照合のコマンドが拾わない差なので、`STYLE.md` の「書き直しの照合」の限界の表のあとに置く。

| 項目 | 見ること | 例 |
| --- | --- | --- |
| 否定・条件・例外 | 打ち消し・条件・例外の語が、消えたり足されたりしていない | 「しない」「とき」「ただし」「除く」 |
| 求める強さ | 義務・許可・可能・推奨の別が変わっていない | 「する」「してよい」「できる」「望ましい」 |
| 誰がするか | する人や役が、変わったり消えたりしていない | 「人間が承認する」が「承認する」になる |
| 確かさ | 確認したこと・予定・推測の別が変わっていない | 「通った」が「通る見込み」になる |

### 置き場所

決まりは、共通スキル `squad-handoff` と `STYLE.md` の 2 か所に置く。役は共通スキルを読み、原本の文書を書く人は `STYLE.md` を読むためである。

共通スキルには、「本文の書き方」の最後に小節「言い回し」を足す。「既存の定型は」で始まる段落のあとで、「コメントと本文の型」の前である。小節は次のとおりで、足す字数は 1,500 字以内にする。

````markdown
### 言い回し

役が書く文は、次の 6 つの決まりで言い回しを決める。食い違うときは、上の決まり・コメントと本文の型・固定の行・作業先の書き方の正本を優先する。

- 事実: 依頼・資料・実行の結果にない事実・理由・数値・予定を書かない。分からないことは、分からないと書く
- 足さないもの: 前置き・依頼の言い直し・末尾のまとめ直し・頼まれていない別案・していないことの列挙を書かない
- 確かさ: 確認したこと・予定・推測を、文末で書き分ける。予定や推測を言い切りにしない
- 語: 同じものを同じ語で書く。普段使う漢語と技術の語はそのまま使い、新しい語を作らない
- 文の分け方: 長さの目安に合わせるために、理由や条件のつながりを切らない
- 読み直し: 出す前に 1 回読み直し、上の 5 つを見る

この決まりは、「本文の書き方」の始めに挙げた本文に加え、作業先のリポジトリに書く文書にも使う。AI が読むもの（役の指示・共通スキル・`AGENTS.md`・作業別のルール・記入用のひな形）を書くときと変えるときも同じである。判定に使う語、固定の行、スクリプトが読む行は、言い回しを理由に変えない。

次は、確かさと足さないものの例である。手元の行は、書く人が持つ依頼・資料・実行の結果である。直した後の文は、直す前の文と手元の行にないことを書かない。

```text
手元: 原因は推測で、CI はまだ流し直していない。
直す前: 原因はキャッシュの古さである。CI を流し直せば通る。
直した後: 原因はキャッシュの古さだと見ている。CI を流し直せば通る見込みである。

直す前: 依頼を確認した。依頼はリンクの切れを直すことである。2 件を直した。以上、リンクの切れを 2 件直した。
直した後: リンクの切れを 2 件直した。
```

書き直しと修正では、読める文は直さず、読み手が止まる理由を言える所だけを直す。直したあとは、否定・条件・例外、求める強さ、誰がするか、確かさが前と同じかを見比べる。
````

共通スキルの例は、確かさと足さないものの 2 つだけにする。すべての役が毎回の実行で読む文なので、ほかの例は `STYLE.md` に置く。

`STYLE.md` には、H2「言い回し」を「用語とコメントの型」と「書き直しの照合」の間に足す。節は、結論の 1〜2 文・対象と優先・6 つの決まり・決まりごとの例の順に書く。

対象と優先は、上の[対象と優先](#対象と優先)の中身を写す。最後の文は、「この変更では書き直さず、後のステージで読み直す」の代わりに「すでにある文は、この決まりを足しただけでは書き直さない。」と写す。読み直しの予定は、恒久の文書に置かず、この設計にだけ残す。

例の前に、共通スキルと同じく「手元の行は、書く人が持つ依頼・資料・実行の結果である。直した後の文は、直す前の文と手元の行にないことを書かない。」と書く。例は次のとおりである。

```text
事実
手元: `bash tests/run.sh tests/links-test.sh` を流し、通った。CI の結果は読んでいない。遅れの原因を示す資料はない。
直す前: テストは通った。遅れの原因はキャッシュで、CI も明日には通る。
直した後: `bash tests/run.sh tests/links-test.sh` は通った。CI の結果は、まだ読んでいない。遅れの原因は分からない。

足さないもの
直す前: 依頼を確認した。依頼はリンクの切れを直すことである。2 件を直した。以上、リンクの切れを 2 件直した。
直した後: リンクの切れを 2 件直した。

確かさ
手元: 原因は推測で、CI はまだ流し直していない。
直す前: 原因はキャッシュの古さである。CI を流し直せば通る。
直した後: 原因はキャッシュの古さだと見ている。CI を流し直せば通る見込みである。

語
直す前: 前と後の文を照合する。突き合わせで差が出たら、比較の結果を PR に書く。
直した後: 前と後の文を照合する。照合で差が出たら、照合の結果を PR に書く。
直す前: 型の外にある項目を、外項目と呼んで扱う。
直した後: 型の外にある項目として扱う。

文の分け方
手元: 直す前の 3 つの文は、理由でつながる 1 文を、長さの目安に合わせて切ったものである。
直す前: 流し直しは、動いているタスクがないときに行う。途中のタスクがある。前と後の手順が混ざる。
直した後: 流し直しは、動いているタスクがないときに行う。途中のタスクで、前と後の手順が混ざるためである。

読み直し
手元: 足したテストは 2 件で、`bash scripts/check.sh` はまだ流していない。
直す前: テストを 3 件足した。`bash scripts/check.sh` は通る。
直した後: テストを 2 件足した。`bash scripts/check.sh` は、まだ流していない。
```

「書き直しの照合」には、限界の表のあとに[書き直しで直す所](#書き直しで直す所)の決まりと 4 つの項目の表を足す。「検査表」には、観点を「言い回し」とする 5 つの行を足す。項目は[検査表](#検査表)に書く。

### 取り入れた決まりと理由

6 つの決まりは、どれも読み手が止まる理由を 1 つずつ防ぐ。

| 決まり | 取り入れた理由 |
| --- | --- |
| 事実 | 依頼や結果にない理由・数値・予定は、読み手が確認せずに次の判断に使う。分からないと書けば、読み手が確認しに行ける |
| 足さないもの | 前置きや言い直しは、要点に届くまでの文を増やす。頼まれていない別案は、決めることを増やす |
| 確かさ | 予定や推測を言い切ると、読み手は済んだことと読み、確認を飛ばす |
| 語 | 同じものを別の語で書くと、読み手は別のものかと止まる。新しい語は、意味を探させる |
| 文の分け方 | 長さの目安に合わせて文を切ると、「ため」「とき」のつながりが消え、理由や条件を読めなくなる |
| 読み直し | ほかの 5 つを見る時機を、出す前と決める。1 回にしたのは、すべての役が毎回の実行で行うためである |

決まりには、直す前と直した後の例を組にする。決まりの文だけでは、どこまで直すかが読み手によって変わるためである。共通スキルの例を 2 つにしたのは、すべての役が毎回読む字数を抑えるためである。

書き直しで直す所と、見比べる 4 つの項目も取り入れた。言い回しを直すと、照合のコマンドが拾わない意味の差が出ることがある。直す所を絞り、意味を運ぶ語を人が見比べて防ぐ。

### 入れなかった決まりと理由

次の案は、決まりに入れなかった。

| 案 | 入れなかった理由 |
| --- | --- |
| 外の書き方の手引きやスキルを、そのまま取り込む | 外への依存が増え、原本の今の決まりと食い違う。すべての役が読む字数も増える |
| メール・敬語・画面の文の決まり | 役が書く文は常体のコメントと文書で、メールと敬語は使わない。画面に出す文は `CONTRIBUTING.md` の「画面に出す文」が決める |
| 書く人ごとの好みを登録する仕組み | 役と人間で書き方が分かれ、同じものを同じ語で書く決まりと合わない |
| 避ける語の一覧で、言い回しを機械で検査する | 語だけでは、確かさや足したものの良し悪しを決められない。正しい文を止めることもある |
| 直さない書き方を細かく並べる | 一覧が長くなり、すべての役が毎回読む字数が増える。直す所の決まり 1 つで足りる |
| 何回も読み直す | 毎回の実行の時間と字数が増える。1 回で 5 つを見る |
| 読みやすさを AI に点数で判定させる | 判定が実行ごとに揺れ、根拠を言えない。人間の読み比べで確認する |
| 7 つの役の指示に、言い回しを指す行を足す | 役はすでに共通スキルを読む。7 つの役が持つ「本文の書き方」を指す行で、小節も指される |

### 手順を足す条件

共通スキルの小節は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲に入る。防ぐ失敗は、合意した要件を根拠にして失敗の記録に代える。要件の合意はタスクのコメントにある。

働いた跡は、役が書いたコメントと文書そのものである。決まりに名前があるので、レビューは決まりの名前を添えて、どの決まりに反したかを指せる。読み直しには、跡を残す行を足さない。自分で書く行は確認できず、コメントも長くなるためである。

### 変更の知らせ

`CHANGELOG.md` の「次のバージョン」の節に、次の知らせを書く。節がなければ、いちばん上のバージョンの節の前に作る。書き方は [release.md](release.md) に従う。

```markdown
## 次のバージョン

役が書く文に、言い回しの決まりを足した。共通スキル squad-handoff の「本文の書き方」の小節「言い回し」に、6 つの決まりがある。

- タスクの本文とコメント、PR の本文、レビューと QA の結果の書き方が変わる
- 導入したプロジェクトのリポジトリに役が書く文書と、AI が読むものにも使う。そのリポジトリに書き方の正本があれば、正本を優先する
- 書き直しと修正では、読み手が止まる理由を言える所だけを直す

導入済みのプロジェクトは、セットアップを流し直すと、新しい共通スキルがすべての役に届く。エージェントとオートパイロットの登録は変わらない。
```

## 互換性と影響を受ける利用者

`STYLE.md` と検査は、導入したプロジェクトに関わらない。言い回しの決まりは共通スキルにあるので、セットアップを流し直すと導入したプロジェクトの役に届く。エージェントとオートパイロットの登録は変わらない。

| 利用者 | 関わること |
| --- | --- |
| 導入・更新する人 | 流し直すと、共通スキルの小節「言い回し」が役に届く。`STYLE.md` と検査のコマンドは、セットアップで配置しない |
| 導入したプロジェクトの担当 | 役が書くコメント・PR の本文・文書の言い回しが変わる。リポジトリに書き方の正本があれば、役は正本を優先する |
| 原本を変える人 | `docs/` に足す文書と `STYLE.md` は、最初から検査を通す必要がある。リンクの切れも CI で落ちる |
| 原本を変えるエージェント | 文書を変えたときは、`tests/style-test.sh` と `tests/links-test.sh` を流す。AI が読むものを書くときも、言い回しの決まりを使う |

エージェントが流すテストは、外の検証スキル `squadkit-verify` が決める。流し忘れても、CI が同じ検査を流すので、違反は PR で見つかる。

## テスト

3 つのテストで検査する。どのテストも、`tmp/` の下に作る一時のディレクトリだけを使う。

`tests/style-test.sh` は、次を確認する。

- リポジトリの対象の文書が、一覧にあるものを除いて検査を通る
- 検査する決まりごとに、反する例が行の番号と決まりの名前を添えて落ち、直した例が通る
- コードブロック、インラインコード、「」の中は、文体と文の区切りで数えない
- 一覧のファイルは引数がないと飛ばし、引数に渡すと検査する。一覧の誤りでは止まる

`tests/links-test.sh` は、次を確認する。

- リポジトリの Markdown のリンクとアンカーに、切れがない
- ないファイル、ない見出し、2 つ目の同じ見出しへのリンクの扱いを、それぞれの例で確認する
- 「・」や（）を含む日本語の見出しのアンカーが、GitHub と同じ規則で作られる

`tests/doc-compare-test.sh` は、一時の Git のリポジトリで前と後のコミットを作り、次を確認する。

- 改行と文だけを変えた書き直しで、差が 0 件で終了コードが 0 になる
- 4 つの要素と図のそれぞれを 1 つ変えると、その 1 行だけが出て終了コードが 1 になる
- 2 回流した出力が同じで、ないコミットを渡すと終了コードが 2 になる

`tests/agent-templates-test.sh` には、言い回しの決まりの確認を足す。

- 共通スキルに見出し `### 言い回し` があり、「本文の書き方」と「コメントと本文の型」の間にある
- 小節に、6 つの決まりの行が `- <名前>: <文言>` の形で 1 行ずつある
- 6 つの行が、`STYLE.md` にも同じ文字列で 1 行ずつある

言い回しそのものは、機械で確認しない。決まりに合うかはレビューで読み、読みやすくなるかは[読み比べ](#読み比べ)で確認する。

書き直しの扱いの決まりは、どれもレビューで読むので、機械で確認するテストがない。`tests/style-test.sh` と `tests/links-test.sh` は、`STYLE.md` とこの文書も検査するので、ガイド自身が検査を通ることはこの 2 つで確認する。

### 読み比べ

言い回しの決まりで文が読みやすくなるかは、人間が 5 つの題で読み比べて確認する。この変更のマージの前に 1 回行い、決まりを変えるときも同じ進め方で行う。

題は、次の 5 つの種類から 1 つずつ選ぶ。選ぶのと直した後の文を書くのは、実装の役である。

- 引き継ぎのコメント
- 人間を呼ぶコメント
- PR の本文
- レビューの結果
- 設計文書の節

題は、読み比べを始める日の前 14 日に役が書いた文から、種類ごとにいちばん新しいものを選ぶ。コメントはこの原本を扱う Multica のプロジェクトのタスクから、PR の本文とレビューの結果はこのリポジトリの PR から選ぶ。設計文書の節は、いちばん新しい設計の PR が変えた `docs/` の文書の、H2 の節 1 つにする。14 日に当てはまる文がない種類は、日を区切らずにいちばん新しいものを選ぶ。

6 つの決まりを当てても直す所がない文は、題にせず、同じ種類の次に新しい文に替える。前と後が同じ文になり、比べられないためである。外した文の数は、種類ごとに題のコメントに書く。日を区切らずに探しても当てはまる文がないときは、その題に共通の本文を 1 つだけ置き、判定を差なしにする。

言い回しの決まりを入れる変更そのものの、要件と設計のタスクと PR は題にしない。新しい決まりを知って書いた文が混ざるためである。秘密の情報を含む文と、非公開の一覧の語に当たる文も題にせず、次に新しい文に替える。

PR は公開されるので、題の文は載せる前に次のとおり伏せる。伏せたあとも、文の意味と長さは変えない。

- メンションは `@役の名前` か `@人間` に替え、人の名前を消す
- タスクの識別子と ID、リポジトリの外を指す URL を消す
- 非公開の一覧の語で題の文を探し、当たりが 0 件であることを確認する

直した後の文は、実装の役が、直す前の文に 6 つの決まりだけを当てて書く。直す前の文にない事実・理由・数値・予定は足さない。事実・固定の行・型の項目は変えず、[書き直しで直す所](#書き直しで直す所)の 4 つの項目が前と同じかを自分で見る。

人間が判定する前に、書いた実装の役とは別のレビューの役が、題ごとに直す前と直した後を読み比べる。直す前にない事実・理由・数値・予定と、4 つの項目の差がないかを見る。あれば実装の役が直し、題を載せ直す。

実装の役は、5 つの題を 1 つの PR のコメントにまとめて載せる。題ごとに種類と出どころを書き、直す前の文を「前」、直した後の文を「後」として並べる。出どころは、PR なら番号、タスクのコメントなら種類と日付にし、タスクの識別子はタスクのコメントに書く。

人間は、題ごとに前と後を読み、後が読みやすいかを、はい・いいえ・差なしのどれかで答える。差なしは、読みやすさに差がないと見たときに選ぶ。前と比べて意味が変わった文があれば写し、次の表を PR のコメントに書く。

```markdown
| 題 | 意味が変わった文 | 後が読みやすいか |
| --- | --- | --- |
| 引き継ぎのコメント | なし | はい |
| 人間を呼ぶコメント | なし | 差なし |
```

最後の列は、はい・いいえ・差なしのどれかにする。後が読みやすい題の件数は、はいの行だけを数え、いいえと差なしの行は数えない。

はいの題が 3 つ以上あり、意味が変わった文が 0 件なら、読み比べを通ったとする。通らなければマージせず、リーダーが設計の見直しを頼む。題・判定・結果は PR のコメントに残す。

判定の前に題を替えたときは、実装の役が 5 つの題を新しい PR のコメントに載せ直す。直した後の文が上の決まりに反していれば、その文も直す。人間は、いちばん新しい題のコメントで判定する。

## 残る危うさ

画面の文を「」やインラインコードで囲まずに引用している箇所は、文体の検査に当たる。画面の文は変えられないので、書き直しの PR では囲むだけで直す。

数え方や文の区切りに誤りがあると、正しい文書を止めたり、違反を通したりする。テストの例で防ぎ、決まりを変えるときは PR で人間が承認する。

対象外の一覧にある文書は、書き直すまで検査されない。一覧にある文書は、決まりに合わない書き方のまま残りうる。

アンカーの規則は、GitHub の実装を写したものである。絵文字や珍しい記号を含む見出しでは、GitHub と結果がずれることがある。

書き直しの扱いの決まりは、どれもレビューで読み、CI では落ちない。決まりの当てはめ方を誤っても、検査は通るので、レビューで決まりの名前を添えて指す。

すでにある文書の 3 つの決まりは、節を足さず動かさない書き直しを認める。この決まりを新しい文書に当てはめると、並びの表が効かなくなる。決まりの冒頭で、PR の base の main にある文書だけに当てはめると書いて防ぐ。

照合の限界は、決まりを書いても残る。2 つある同じ値の片方が消えた差と、テストが読む文言の変更は、レビューと書く人の検索だけで見つける。

言い回しの決まりの文言は、共通スキルと `STYLE.md` の 2 か所にある。テストは 6 つの行だけを比べるので、対象と優先の文や例は食い違いうる。変えるときは、同じ PR で 2 か所を直す。

言い回しの決まりは、CI では落ちない。当てはめ方の誤りは、レビューで決まりの名前を添えて指す。読み直しは跡を残さないので、したかどうかは確認できない。

読み比べは、すでにある文の書き直しで確認する。新しく書く文に決まりが効くかは、確認しない。人間はどちらが直した後かを知って読むので、後を選ぶほうへ寄ることがある。

題は、決まりを当てて直す所があった文に限る。決まりを当てても変わらない文がどれだけあるかは、判定の結果に入らず、題のコメントの外した文の数でだけ分かる。

## 検討した案

文体を敬体にそろえる案は採らなかった。文書の大半が常体で、`squad-handoff` と [terms.md](terms.md) も常体だからである。入口の文書だけを敬体にする案も、検査の決まりが 2 つになるので採らなかった。

改行を 1 行 1 文にそろえる案は採らなかった。ほとんどの文書と `squad-handoff` は 1 段落 1 行である。段落を 240 字までにするので、1 段落 1 行でも差分を読める。

textlint の JTF の規則集や markdownlint を CI で使う案は採らなかった。Node.js の依存が CI に増え、決まりをこのガイドに合わせて変えにくいからである。

対象外の一覧と検査を `tests/` に置く案は採らなかった。書き直しの PR は、テストのファイルを変えずに通すことになっているからである。

照合で、ファイルをまたいだ移動を自動で対にする案は採らなかった。対の作り方に誤りがあると差を見落とすので、`-` と `+` を並べて人が対にする。要素の回数を比べる案も、重なりを消す書き直しで差が出るので採らなかった。

書き直しの扱いでは、書き直した文書を並びの表に合わせて直す案を採らなかった。節を足すと中身が増え、見出しを変えると外のリンクとテストが切れる。人間が、ガイドのほうを実際の扱いに合わせると決めた。

照合のコードを変えて、2 つの限界をなくす案も採らなかった。回数で比べる案は採らず、テストが読む文言を探すコードは、検査の範囲の外である。限界はガイドに書き、レビューと検索で補う。

足す決まりのために、`STYLE.md` に新しい H2 を置く案も採らなかった。決まりを主題の合う今の節に置けば、書く人が 1 つの節で読める。今の H2 の名前は、検査の出力とテストが使うので変えない。

設計を新しい文書に書く案も採らなかった。この文書の決まりの一覧と検査表の問いが、ガイドと食い違ったまま残るためである。

言い回しの決まりのために、`STYLE.md` に H2「言い回し」を足す案は採った。言い回しは文の形でなく語と中身の決まりで、合う節が今の H2 にないためである。書き直しの扱いの決まりで新しい H2 を採らなかったのは、合う節があったからである。

`STYLE.md` から共通スキルの小節を指すだけにする案は採らなかった。`STYLE.md` を読む人が、例を共通スキルまで探しに行くことになる。共通スキルに `STYLE.md` と同じ数の例を置くと、すべての役が毎回読む字数が増える。

決まりを共通スキルの `references/` に分ける案も採らなかった。`references/` の手順はリーダーだけが読み、ほかの役に届かないためである。

読み直しのあとに `読み直し: 済み` のような行を書く案は採らなかった。自分で書く行は確認できず、コメントも長くなるためである。

読み比べで、どちらが直した後かを伏せて人間に選ばせる案は採らなかった。伏せを保つには、判定までのレビューや引き継ぎに直した所を書けず、隠す作業も要る。前と後を並べれば、人間は何が変わったかを読んで、そのまま判定できる。
