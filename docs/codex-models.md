# Codex のモデルを GPT-6.2 の世代に上げる

Codex で動く役のモデルを、実装の格は `gpt-6.2-sol`（GPT-6.2 Sol）、最上位の格は `gpt-6.2-astra`（GPT-6.2 Astra）に上げる。Claude のモデルと、役ごとのモデルの格と思考の深さは変えない。片方のランタイムだけのときの移し方も変えない。

この文書は、構成ごとのモデルと Codex CLI のバージョンの条件を書く。変えるファイルと実物から取った見本の扱い、流し直しで変わる登録も書く。

## 目的と範囲

Codex CLI 0.171.0 で、GPT-6.2 Sol と GPT-6.2 Astra が使えるようになった。0.172.0 の CLI は、この 2 つを推奨のモデルとして出す。原本の役は、まだ前の世代の ID で動いている。

目的は次の 3 つである。

1. Codex で動く役のモデルを、同じ格の新しい ID にする
2. 導入する人に、Codex CLI 0.171.0 以上が要ることを伝える
3. 流し直しでエージェントの登録が変わる導入先と、変わらない導入先を、変更の知らせに書く

次は対象にしない。

- セットアップで Codex CLI のバージョンを確認すること
- Claude のモデルの変更
- 役ごとのモデルの格と思考の深さの見直し
- `VERSION` を上げること
- VM の実機での確認

前の世代の ID は、この文書にも書かない。受け入れ条件で、原本の指示と文書（`common/` `lib/` `manual.md` `docs/`）に前の世代の ID が残らないことを確認するためである。前の世代の ID は、流し直しのテストの中にだけ書く。

## 構成ごとのモデル

下の表のひな形の、Codex のモデルの行を新しい ID に替える。どの役が実装の格で、どの役が最上位の格かは変えない。

| ひな形 | Codex のモデル | Codex のモデルが使われる構成 |
| --- | --- | --- |
| `codex-implementer`、`codex-fixer` | `gpt-6.2-sol` | 両方、Codex だけ |
| `code-reviewer`、`security-reviewer`、`performance-reviewer`、`ux-reviewer` | `gpt-6.2-sol` | 両方、Codex だけ |
| `ci-monitor`、`dependabot-merger`、`usage-monitor` | `gpt-6.2-sol` | 両方、Codex だけ |
| `orchestrator`、`qa`、`designer` | `gpt-6.2-sol` | Codex だけ |
| `codex-principal` | `gpt-6.2-astra` | 両方、Codex だけ |
| `planner` | `gpt-6.2-astra` | Codex だけ |

変える行は、`gpt-6.2-sol` にする行が 12 か所、`gpt-6.2-astra` にする行が 2 か所である。`<!-- IF runtime-claude -->` の側の Claude のモデルの行と、`thinking_level` の行は変えない。

構成ごとに読むと、次のとおりになる。

| 構成 | 変わること |
| --- | --- |
| 両方 | Codex の実装・修正、レビューの 4 役、見張りの 3 役が `gpt-6.2-sol` に、`codex-principal` が `gpt-6.2-astra` になる |
| Codex だけ | `planner` と `codex-principal` が `gpt-6.2-astra` に、ほかのすべての役が `gpt-6.2-sol` になる |
| Claude Code だけ | 変わらない。Codex のモデルの行はどの役でも使われない |

片方のランタイムだけのときの移し方（`common/agents/FORMAT` の決まり）は変えない。Claude Code だけの構成で Codex の役を移す先は Claude の実装の役のモデルなので、この変更の影響を受けない。

スクリプトは、モデルの ID を `claude-` と `gpt-` の頭だけで系統に分ける。`lib/project.sh`、`lib/installation.sh`、見張りのスクリプトは、新しい ID でも同じ系統に分けるので変えない。

## Codex CLI のバージョン

Codex CLI は 0.171.0 以上を使う。新しい 2 つのモデルは 0.171.0 で使えるようになり、前のバージョンの CLI から呼べるかは確認していないためである。

この条件は、`manual.md` と `CHANGELOG.md` に書く。セットアップではバージョンを確認しない（要件の合意で範囲の外にした）。

`manual.md` では、必要な道具の節の「Claude Code と Codex CLI は、利用する組織の手順で導入する。」の文のすぐ後に、次の文を足す。

```markdown
Codex CLI は 0.171.0 以上にする。Codex で動く役のモデル（`gpt-6.2-sol` と `gpt-6.2-astra`）は、0.171.0 で使えるようになったため。
```

`docs/leader-principles.md` の「原本で確認した Codex のモデル」の文は、次の ID に替える。確認したことの根拠は、新しい 2 つのモデルを Codex CLI 0.171.0 以上から 1 回ずつ呼んで応答を得ることで、人間がマージの前に行う。

```markdown
原本で確認した Codex のモデルは、`gpt-6.2-sol` と、最上位の役の `gpt-6.2-astra` だけである。
```

## モデルの名前の書き方

`manual.md` と `docs/` でモデルを名前で書く所は、`GPT-6.2 Sol` と `GPT-6.2 Astra` にする。Claude のモデルを `Fable 5.2` や `Opus 5.5` とバージョンまで書いているので、Codex もバージョンまで書いてそろえる。

世代を付けずに書いている所は、すべてこの名前に替える。ID の後ろの括弧の名前も同じにする（例: `` `gpt-6.2-astra`（GPT-6.2 Astra） ``）。

世代を付けない名前が残らないことは、次のコマンドで確認する。前に GPT-6.2 と空白のない名前の行を、ファイルの名前と行の番号を付けて出す。何も出なければ、残っていない。

```bash
perl -ne 'print "$ARGV:$.:$_" if /(?<!GPT-6\.2 )\b(S[o]l|Astr[a])\b/; close ARGV if eof' manual.md docs/*.md
```

### 変更の知らせ

`CHANGELOG.md` の先頭（`# 変更の記録` の見出しと `## v1.1.0` の節の間）に、次の節を置く。[変更の知らせ](release.md#変更の知らせ)の決まりのとおり、節の見出しはバージョンを上げる PR で `## <バージョン>` にする。

```markdown
## 次のバージョン

Codex で動く役のモデルを、GPT-6.2 の世代に上げた。実装の格の役は `gpt-6.2-sol`、最上位の格の役（`codex-principal` と、Codex だけの構成の要件定義の役）は `gpt-6.2-astra` で動く。Claude のモデルと、役ごとの思考の深さは変えていない。

Codex を使う導入先は、Codex CLI を 0.171.0 以上にしてから、セットアップを流し直す。新しいモデルは 0.171.0 で使えるようになった。セットアップは CLI のバージョンを確認しない。

- 使うランタイムに Codex がある導入先では、流し直しで、Codex で動く役のエージェントのモデルの登録が新しい ID に替わる。思考の深さとオートパイロットの登録は変わらない
- Claude Code だけの導入先では、流し直してもエージェントとオートパイロットの登録は変わらない
```

## 実物から取った見本の扱い

テストの中の前の世代の ID は、値の出どころで扱いを分ける。ひな形を展開した結果を確認する期待値と、今の登録を表す手書きの値は、新しい ID にする。実物の CLI の応答から取った見本と、評価の場面の入力は、そのまま残す。

| 置き場所 | 値の出どころ | 扱い |
| --- | --- | --- |
| `tests/` の `agent-templates-test.sh` `project-runtimes-test.sh` `project-runtimes-first-test.sh` `setup-runtimes-test-lib.sh` `project-create-test.sh` | ひな形を展開した結果の期待値 | 新しい ID にする |
| `tests/` の `squad-usage-wait-test-lib.sh` `installation-fixture.py` `extensions-test.sh` | 登録済みのエージェントや拡張の役を表す手書きの値 | 新しい ID にする。格は変えず、役と値の組も変えない |
| `tests/fixtures/cli/agent-get.json` | multica の CLI の実物の応答を匿名にしたもの | 残す |
| `tests/leader-eval/scenes/` の `cli.json` と `scene.md` | リーダーの評価の場面の入力 | 残す |

`tests/fixtures/cli/agent-get.json` を残す理由は 3 つある。

1. 見本は「実物から取る」決まりで、取り直すのは multica や `gh` の CLI のバージョンが上がったときである。モデルの変更は、取り直す条件に当たらない
2. 手で値を書き換えると、実物から取った見本でなくなる
3. この見本を読むテストは、`model` を jq で上書きしてから使い、見本の値を期待値にしていない

評価の場面を残す理由は 2 つある。リーダーは設計の役のモデルを系統の頭（`claude-` か `gpt-`）だけで読むので、前の世代の ID でも判断が変わらない。場面の入力を変えると、指示の新旧を比べる評価で、入力の違いが結果に混ざる。

受け入れ条件で前の世代の ID が残らないことを確認する範囲（`common/` `lib/` `manual.md` `docs/`）に、`tests/` は入らない。残す見本は、この範囲の外にある。

## 互換性と影響を受ける利用者

使うランタイムに Codex がある導入先では、セットアップを流し直すと、Codex で動く役のエージェントのモデルの登録が替わる。流し直しは、登録のモデルが新しい値と違えば更新するので、セットアップのコードは変えない。

| 利用者 | 変わること |
| --- | --- |
| Codex を使う導入先の担当 | 流し直す前に、Codex CLI を 0.171.0 以上にする。流し直すと、Codex で動く役のモデルの登録が新しい ID に替わる |
| Claude Code だけの導入先の担当 | 変わらない。流し直しても、エージェントの登録は替わらない |
| 拡張を使う導入先の担当 | 拡張の役のモデルは、拡張に書いた値のまま使われる。前の世代の ID を書いた拡張の役は、拡張の側で直すまで前の ID のまま登録される |
| 原本を変える人 | Codex のモデルを書くときは新しい ID と名前を使う |

思考の深さと同時実行数、指示とスキルは変わらない。オートパイロットの登録も変わらない。役のひな形の形式と、拡張との契約も変わらない。

Codex CLI が 0.171.0 より前のまま流し直すと、Codex で動く役の実行が失敗するおそれがある。セットアップでは止めないので、変更の知らせと `manual.md` で、先に CLI を上げる順を伝える。

戻すときは、前のバージョンの原本でセットアップを流し直す。流し直しは、登録のモデルがひな形の値と違えば更新するので（`lib/project.sh` のエージェントの設定）、前のバージョンのひな形の ID に戻る。

## テスト

ひな形の期待値と手書きの値を新しい ID にし、流し直しで前の世代の ID の登録が新しい ID に替わることを確認する。テストの確認は、`bash tests/run.sh <テストのファイル>` で流す。

### 期待値と手書きの値を替える

[実物から取った見本の扱い](#実物から取った見本の扱い)の表で「新しい ID にする」としたファイルの、前の世代の ID を替える。`tests/agent-templates-test.sh` は、`manual.md` の「片方だけのランタイムで動かす」の表の行を文字列で確認しているので、その行も新しい名前にする。PASS の文と注釈にあるモデルの名前も、`GPT-6.2 Sol` と `GPT-6.2 Astra` にそろえる。

### 流し直しの確認を足す

`tests/project-runtimes-test.sh` に、次を確認するケースを足す。両方と Codex だけは、今の「設計の役が前のモデルで登録済み」のケースと同じく、完了した見本の登録を書き換えてから流す。完了した見本は両方の構成の登録なので、Claude Code だけは、先に Claude Code だけへ移してから流し直す。

| 構成 | 流す前の登録 | 確認すること |
| --- | --- | --- |
| 両方 | Codex で動くすべての役のモデルを、同じ格の前の世代の ID にする | Codex で動く役のモデルが新しい ID になり、Claude で動く役のモデルと、すべての役の思考の深さは変わらない。エージェントとオートパイロットは作られない |
| Codex だけ | すべての役のモデルを、同じ格の前の世代の ID にする | `planner` と `codex-principal` が `gpt-6.2-astra`、ほかの役が `gpt-6.2-sol` になり、思考の深さは変わらない。エージェントとオートパイロットは作られない |
| Claude Code だけ | 完了した見本を Claude Code だけで 1 回流して移した登録 | 流し直しで `agent update` を呼ばず、すべての役のモデルが Claude の決まった ID（両方の構成と同じ値）で、思考の深さも変わらない |

今の「設計の役が前のモデルで登録済み」のケースの、Codex だけの構成の前の値は、最上位の格の前の世代の ID である。このケースは、前の値を `gpt-6.2-astra`、新しい値を `gpt-6.2-sol` にする。設計の役が最上位の格から実装の格に替わることを確認する目的は変えない。

Claude のモデルの期待値は、どのテストでも替えない。Claude Code だけの構成が変更の前と同じであることは、差分で確認する。ひな形の差分に Claude の ID の行がなく、テストの差分で消した行の Claude の ID が、すべて足した行にもあることを見る。

### 前の世代の ID が残らないことの確認

テストのファイルは足さない。`common/` `lib/` `manual.md` `docs/` に前の世代の ID が残らないことは、実装の役が grep で確認する。ひな形に前の世代の ID を書き戻す変更は、期待値のテストで落ちる。文書に書き戻す変更は、レビューで見る。

## 検討した案

名前の書き方、見本の扱い、CLI のバージョンの伝え方について、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| 名前を世代を付けずに残す | 世代を上げても文書を替えずに済むが、Claude のモデルはバージョンまで書いていて、そろわない。どの世代で確認したかも名前から読めない |
| `tests/fixtures/cli/agent-get.json` の `model` を新しい ID に書き換える | 実物から取る決まりに反する。見本を読むテストは `model` を上書きするので、書き換えても確認することは増えない |
| `agent-get.json` を multica の CLI から取り直す | multica の CLI のバージョンは変わっておらず、取り直す条件に当たらない。取り直すと、モデルと関係のない値の差も混ざる |
| 評価の場面の入力を新しい ID にする | リーダーの判断は系統の頭だけで決まり、結果は変わらない。入力を変えると、指示の新旧を比べる評価に入力の違いが混ざる |
| 前の世代の ID が残らないことを確認するテストを足す | ひな形への書き戻しは期待値のテストで落ちる。世代を上げるたびに、テストの中の前の世代の ID の一覧を直す手間が増える |
| `CHANGELOG.md` の知らせを、バージョンを上げる PR で書く | 変更の知らせの決まりでは、利用者に影響する変更の PR が `## 次のバージョン` に書く。後で書くと、書き忘れることがある |
