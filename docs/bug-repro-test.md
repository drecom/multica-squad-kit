# バグの修正で、再現するテストを先に流す

実装の役は、バグのタスクでコードを直す前に、再現するテストを足して流し、落ちることを見る。落ちたことと、直したあとに通ったことを、引き継ぎのコメントと PR の本文の確認に 1 行ずつ残す。この文書は、実装の役の指示に足す節の全文と、記録の行の形と、その理由を書く。

## 目的と範囲

今は、バグを直した証拠が「直したあとに通ったテスト」だけである。直したあとに通っただけでは、そのテストが不具合を見ているかが分からない。テストが不具合を捉えていなくても、レビューする役と人間は気づけない。

過去のバグ修正 1 件では、直す前に落ちた記録が、タスクと PR のコメントのどこにもなかった。テストと直しは同じ 1 つのコミットに入り、直す前のコードにテストを当てた状態は履歴に残っていなかった。あとから確認する人は、直す前のコードを作り直す必要がある。テストを書いた直後の実装の役なら、1 回流すだけで済む。

目的は次の 3 つである。

1. バグのタスクで、実装の役がコードを直す前に、再現するテストを流して落ちることを見る
2. 落ちたことと、直したあとに通ったことを、決まった形の 1 行で残す
3. テストにできないバグでは、その理由と代わりに確認したことを、同じ行頭の 1 行で残す

次は対象にしない。

- 設計の実装のフェーズ。新しい機能のテストには、この決まりを当てない
- 修正の役。レビューの指摘・コンフリクト・CI の失敗の直しには当てない
- コードレビューの役の確認。行があるかをレビューで見ることはしない
- わざと壊して、テストが落ちるかを見る手当て
- 過去のバグ修正へ遡ること
- 本物のモデルを流す確認。確認は、役のひな形のテストだけにする

QA がバグのタスクを出すときの本文の決まりは、変えない。再現手順・実際の動作・証拠を背景に書く今の決まりのまま、その再現手順をテストにする。

## 足す節

実装の役のひな形 2 つ（`common/agents/claude-implementer.md` と `common/agents/codex-implementer.md`）に、同じ節を足す。置き場所は「変えてよいもの」の節のあと、「push の前の照合」の節の前である。

この置き場所を選んだのは、役が読む順と、作業の順を合わせるためである。「受け取ったら最初に確認すること」で再現手順で再現するかを見たあと、コードを直す前にこの節を読む。直したあとにする「push の前の照合」より前に置く。

### 節の全文

足す節の全文は次のとおりである。差し込みの値（`{{...}}`）を含まないので、2 つのひな形で同じバイト列になる。

````markdown
## バグの再現のテスト

バグのタスクでは、コードを直す前に、再現するテストを足して流す。直したあとに通っただけでは、そのテストが不具合を見ているかが分からないため。設計の実装のフェーズには当てない。

1. タスクの再現手順を、期待する動作を確認するテストにする
2. コードを直す前に、そのテストを流す。落ちることと、落ちた出力がタスクの実際の動作と合うことを見る
3. 落ちなければ、テストが不具合を見ていない。テストを直すか、タスクを出したエージェントに確認する
4. コードを直し、同じテストが通ることを見る

テストと直しは、別のコミットに分けなくてよい。直す前の結果は、手元で流した出力から書く。

テストにできないときは、テストを足さず、再現手順で確認する。実機でしか起きない不具合や、文書だけの直しが当たる。

結果は、引き継ぎのコメントの「確認したこと」と、PR の本文の確認に、次のどちらかの 1 行で書く。箇条書きの項目の先頭は `再現のテスト:` にそろえる（後から検索で数えられるようにするため）。

```text
再現のテスト: `<コマンド>`。直す前: 落ちた（終了コード <数>、<落ちた出力の要点>）。直した後: 通った（終了コード <数>）
再現のテスト: 書けない（<理由>）。代わりに確認したこと: <再現手順での確認と結果>
```

- 直した後は、最新の push のコミットで流した結果にする。push のあとにコードを変えたら、流し直して書き換える
- PR の本文を書き直すときも、この行を残す
````

### 記録の行の形

記録の行は、行頭を `再現のテスト:` にそろえた 2 つの形にする。行頭をそろえるのは、`見直し:` の行と同じく、跡を検索で数えられるようにするためである。

| 形 | 使うとき | 書くこと |
| --- | --- | --- |
| 流した | 再現するテストを足したとき | 流したコマンド、直す前の終了コードと落ちた出力の要点、直した後の終了コード |
| 書けない | テストにできないとき | 書けない理由と、再現手順で代わりに確認したことと結果 |

置く場所は 2 つである。タスクのコメントでは、引き継ぎの型の「確認したこと」の箇条書きの 1 項目にする。PR の本文では、テンプレートの見出し「確認」の 1 項目にする。

```text
タスクのコメント:
- 再現のテスト: `bash tests/run.sh tests/gh-test.sh`。直す前: 落ちた（終了コード 1、「フラグの型が分からないので止めた」）。直した後: 通った（終了コード 0）
PR の本文の確認:
- [x] 再現のテスト: `bash tests/run.sh tests/gh-test.sh`。直す前: 落ちた（終了コード 1、「フラグの型が分からないので止めた」）。直した後: 通った（終了コード 0）
```

落ちなかったときの形は置かない。落ちなければ、テストを直すか、タスクを出したエージェントに確認するので、引き継ぎまで進まないためである。

### PR の本文の確認との関係

PR の本文の確認は、最新の push の分だけを書く決まりである。この行の「直す前」は、最新の push より前の結果になる。そこで、この行だけは直す前の結果も書き、「直した後」を最新の push のコミットで流した結果にする。

直す前の結果は、直したあとのコードから作り直せない。PR の本文を書き直すたびに消えると、記録がタスクのコメントにしか残らなくなる。そのため、書き直しでも残すと節に書く。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイル（役のひな形）に、役にさせる文を足す。条件の 3 つを次に書く。

### 根拠

合意された要件による新しい手順なので、要件の合意を失敗の記録に代える。合意の記録と、過去のバグ修正 1 件の実物は、タスクのコメントにある。

過去の 1 件では、テストは正しかった。直す前のコードにテストだけを当てると、2 本とも落ちた。実害の出た例は、見た 1 件にはない。

### 働いた跡

手順が働くと、実装の役のタスクのコメントに、行頭が `- 再現のテスト:` の項目が残る。見直しの跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 項目 | 値 |
| --- | --- |
| 形 | `kind: "comment"` |
| `pattern` | `(?m)^- 再現のテスト:` |
| `author_type` | `agent` |

この跡は、バグのタスクが 20 件の中にないと 0 回になる。0 回のときに削る候補とするかは、見直しで、20 件の中のバグのタスクの数と合わせて人間が判断する。

### 仕組みにしない理由

仕組みの案は 2 つある。どちらも、この手順に代えない。

| 案 | 選ばなかった理由 |
| --- | --- |
| CI か見張りが、PR の本文に `再現のテスト:` の行があるかを判定する | PR にはバグのタスクの印がなく、設計の実装の PR と見分けられない。行があっても、直す前に流したかは見分けられない |
| CI が、変えたテストを PR の base のコードに当てて、落ちるかを流す | 導入先ごとに、言語とテストの道具とコマンドが違う。テストと直しが同じファイルにあると、テストだけを base に当てられない |

2 つ目の案は、テストが不具合を見ているかを、役の文を読まずに確認できる。ただし、起きた失敗は過去の 1 件で、実害はなかった。導入先ごとの道具に合わせて作る手間に見合わないと判断した。

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと、実装の役の指示が新しいものに替わる。替わったあとのバグのタスクで、実装の役の手順と出力が変わる。

| 利用者 | 変わること |
| --- | --- |
| 実装の役 | バグのタスクで、直す前にテストを流す。引き継ぎのコメントと PR の本文の確認に、`再現のテスト:` の行が 1 行ずつ増える |
| 導入したプロジェクトの担当 | バグの修正の PR で、テストが不具合を見ている証拠を読める |
| リーダー・レビューの役・QA | 変わらない。行を読む決まりも足さない |

エージェントとオートパイロットの登録は変わらない。役のひな形の形式と、拡張との契約も変わらない。`確認したこと` の項目が 1 つ増えるだけで、見張りのスクリプトが読む固定の行は変えない。

流し直す前に動いているバグのタスクは、前の指示のまま進む。その PR に行がなくても、誤りにはしない。

## テスト

`tests/agent-templates-test.sh` に、次を確認する 1 つの PASS を足す。確認するのは、[テストを書く決まり](../CONTRIBUTING.md#テストを書く決まり)のひな形の契約に当たるものだけである。

| 確認すること | 失敗したときに直すこと |
| --- | --- |
| 実装の役のひな形 2 つに、見出し `## バグの再現のテスト` がちょうど 1 つある | 節を足すか、重なった節を消す |
| 2 つのひな形で、その節の中身が同じバイト列である | 片方だけ変えた文を、もう片方にそろえる |
| 節の中に、[記録の行の形](#記録の行の形)の 2 つの行が、行のまま 1 つずつある | 行の形を戻す |
| 節が「変えてよいもの」の節より後、「push の前の照合」の節より前にある | 節を置き場所へ戻す |
| 修正の役 2 つ・コードレビューの役・設計の役のひな形に、`再現のテスト:` がない | 対象の外の役に足した文を消す |

節は、ひな形の原本（`common/agents/` のファイル）から、見出しで切り出して比べる。節に差し込みの値がないので、展開の前後で同じになるためである。

記録の行の形を確認するのは、行頭の `再現のテスト:` を[働いた跡](#働いた跡)の定義が読むためである。テストには、読む側として跡の定義をコメントで添える。

節の説明の文は、固定の文字列で確認しない。対象がバグのタスクだけで、設計の実装のフェーズに当てないことは、人間がマージの前に PR の差分で節を読んで確認する。言い換えでテストが落ちないようにし、役が文に従うかは評価の範囲に残すためである。

## 残る危うさ

次の 3 つは、この決まりで残る。

1 つ目は、行の書き忘れである。行がないことには、だれも気づかない。合意では、まず行だけで始め、書き忘れが実際に起きたら、確認を足すかを考える。

2 つ目は、修正の役が PR の本文を書き直すときに、この行を消すことである。修正の役の指示は変えないので、本文の確認は修正の役の最新の push の分になる。直す前の記録は、実装の役のタスクのコメントに残る。

3 つ目は、不具合と別の理由で落ちるテストである。準備の誤りなどで落ちても、直す前に落ちたことにはなる。落ちた出力が実際の動作と合うかを見る手順で減らすが、見るのは実装の役だけである。わざと壊して落ちるかを見る手当ては、範囲の外である。

## 検討した案

文面・置き場所・記録の行について、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| 「受け取ったら最初に確認すること」の再現の確認の項目に、文を足す | 手順が 4 つあり、1 つの項目に収まらない。記録の行の形も置けない |
| 「結果の出し方」の節に、記録の行の形だけを置く | 直す前に流す手順と、記録の行が離れる。役が直したあとに節を読み、直す前の結果を取り逃す |
| 「push の前の照合」の表のバグのタスクの行に、テストの確認を足す | 照合は直したあとの見直しで、直す前の手順に合わない。照合のサブエージェントの観点も変わる |
| 記録の行を、`見直し:` と同じく箇条書きの外の独立の行にする | テストの結果は「確認したこと」の 1 件で、PR の本文の確認にも同じ形で置ける。項目にすると、2 か所で同じ文になる |
| 直す前に落ちたテストを、直しと別のコミットに分けて残す | 合意で求めないと決めた。導入先の CI が、落ちるコミットを main に入れることを止める設定のことがある |
| 共通スキル squad-handoff の、既存の定型の一覧に `再現のテスト:` を足す | 読むのは実装の役だけで、ほかの役に届ける必要がない。共通スキルを変えると、すべての役の指示が流し直しで替わる |
