# 役の指示・共通スキル・ひな形を、言い回しの決まりで読み直す

AI が読む 35 のファイルを、言い回しの 6 つの決まりに照らして読み直す。読み手が止まる理由を言える所だけを直し、意味と、役の判断や手順は変えない。

この文書は、読む対象と読み方・直す所の基準・直さない語と行・PR に残す記録・確認の方法を書く。6 つの決まりと 4 つの項目の正本は `STYLE.md` の[言い回し](../STYLE.md#言い回し)と[書き直しの照合](../STYLE.md#書き直しの照合)で、この文書は写さない。決まりを足した設計は [doc-style.md](doc-style.md#言い回しの決まり) にある。

## 目的と範囲

目的は、決まりを足す前に書かれた AI が読む文を、決まりに合わせることである。決まりを足しただけでは、すでにある文は書き直さないと決めたためである。

対象は、次の 35 のファイルである。読む組は、[読む組と順](#読む組と順)に書く。

| 種類 | ファイル | 数 |
| --- | --- | --- |
| 役の指示 | `common/agents/` の `FORMAT` を除くすべて | 17 |
| スクワッドとオートパイロットの指示 | `common/squad.md`・`common/autopilots.md` | 2 |
| 共通スキル | `common/skills/squad-handoff/` の `SKILL.md` と `references/` の 6 つ | 7 |
| 記入用のひな形 | `skeleton/` の下のすべて | 9 |

`skeleton/README.md` は、`STYLE.md` の対象の入口の文書でもある。要件が数える 35 に入るので、読む対象に含める。直すときは、`STYLE.md` のほかの決まりと検査も守る。

次は範囲の外である。

- 役の判断と手順の変更。事実と違う文を見つけても、この変更では直さない（[直さずに記録する所](#直さずに記録する所)）
- このリポジトリの `AGENTS.md` と `.agents/rules/`、人間が読む文書の書き直し
- 導入先で人間が記入したもの。`docs/terms.md` の[書き換えないもの](terms.md#書き換えないもの)である
- 言い回しを機械で確認する検査を足すこと
- バージョンを上げること

## 読み方

ファイルごとに、先頭から最後まですべての行を読む。読んだ範囲を飛ばさないよう、1 つのファイルを読み終えてから次のファイルへ進む。

読む人は、組ごとに次の順で進める。番号の手順は 1 人が順に行うので、図にしない。

1. 組を始める時点のコミットを、読んだコミットとして控える
2. ファイルを先頭から読み、止まる所を見つけたら、[直す所の基準](#直す所の基準)で直すかを決める
3. 直すと決めた所は、[直さない語と行](#直さない語と行)に当たらないかを確認してから直す
4. 直した所ごとに、前と後の文で 4 つの項目を見比べる。どれか 1 つでも違えば、前の文に戻す
5. ファイルを読み終えたら、[機械の確認](#機械の確認)を流す
6. 組のすべてのファイルを読み終えたら、[PR に残す記録](#pr-に残す記録)を書く

4 つの項目は、`STYLE.md` の「書き直しの照合」の表にある。否定・条件・例外、求める強さ、誰がするか、確かさである。

### 読む組と順

35 のファイルを 8 つの組に分け、組の番号の順に読む。1 つの組は、500〜750 行ほどにする。

| --- | --- | --- |

| 3 | `references/` の `leader-principal.md`・`leader-pr-checks.md` | 582 |
| 4 | `orchestrator.md`・`planner.md`・`designer.md`・`common/squad.md` | 548 |
| 5 | `claude-implementer.md`・`codex-implementer.md`・`claude-fixer.md`・`codex-fixer.md` | 698 |
| 6 | `claude-principal.md`・`codex-principal.md`・`code-reviewer.md`・`security-reviewer.md` | 510 |
| 7 | `performance-reviewer.md`・`ux-reviewer.md`・`qa.md`・`ci-monitor.md`・`usage-monitor.md`・`dependabot-merger.md`・`common/autopilots.md` | 554 |

`claude-` と `codex-` で始まる対のファイルは、同じ組で読む。対の片方だけを直すと、ランタイムによって同じ役の文が食い違うためである。対の両方にある文を直すときは、両方を同じに直す。

## 直す所の基準

直すのは、読み手が止まる理由を、5 つの決まりのどれかの名前で言える所だけである。読み直しの決まりは、読む人が出す前にすることなので、止まる理由には使わない。

読み手は、その文を読む役である。役がどちらの意味か決められないとき、別のものと取り違えるとき、どこまでを求められたか決められないときに、止まると見る。

| 決まり | 直す所 | 直さない所 |
| --- | --- | --- |
| 事実 | なし。事実と違う文は直さずに記録する | 実際の動作と違う文。直すと役の判断が変わるため |
| 足さないもの | 同じ節の中で、同じ決まりを 2 回言い直す文 | 禁止の文。「しない」を並べた文は、していないことの列挙でなく決まりである |
| 確かさ | 決まっていない動作を言い切り、役が必ずそうなると読む文 | 手順を言い切る文。指示の文は、することを決める文なので言い切ってよい |
| 語 | 同じものを 2 つの語で書き、別のものと読める所 | 判定に使う語と、[直さない語と行](#直さない語と行)に当たる語 |
| 文の分け方 | 理由や条件を別の文に切り、どの文の理由か分からない所 | 長いだけの文。AI が読むものには、長さの目安を当てないため |

止まる理由を言えない所は、読みにくいと感じても直さない。好みの言い換えは、意味を変えるおそれがあり、差分も読みにくくするためである。

### 直さずに記録する所

止まる理由を言えても、直すと意味が変わる所は直さず、記録に残す。次の 3 つが当たる。

- 事実と違う文。たとえば、スクリプトの実際の動作と違う説明である
- 直すには、[直さない語と行](#直さない語と行)を変える必要がある所
- 直すと 4 つの項目のどれかが変わる所

記録した所は、この変更では記録するだけにし、この PR のマージのあとに別のタスクで扱う。読み直しで記録した 6 件の一覧は、タスクの本文と、PR の組ごとの記録にある。6 件の扱いは [reread-followups.md](reread-followups.md) にある。

## 直さない語と行

判定に使う語・固定の行・スクリプトが読む行・コメントの型の項目名は、言い回しを理由に変えない。変えると、役の判断やスクリプトの動作が変わるためである。

| 種類 | 当たるもの |
| --- | --- |
| 判定に使う語 | 状態・ラベル・metadata のキー・マークの値と、役やスクリプトが一致を見る語。`重要`・`小さい`・`大きい`・`表に載せる`・`あり` などである |
| 固定の行 | `<名前>:` の形で、決まった位置に置く行。`確認したコミット:`・`見直し:`・`返事を待つ役:`・`頼む範囲:`・`設計への指摘:`・`紐付けの失敗:`・`未実行:` などと、`/note` の行である |
| スクリプトが読む行 | front matter・`<!-- IF -->` などの展開の印・`{{` で始まる値の印・`[記入:` の印と、`skeleton/.agents/review-paths` のコメントでない行 |
| オートパイロットの登録の値 | `common/autopilots.md` の見出しと、`- 範囲:`・`- 担当:`・`- 実行:`・`- スケジュール:` の行と、`指示:` の行 |
| コメントの型の項目名 | 結論・成果物・確認したこと・決めてほしいこと・残っていること |
| 外から指される見出し | テストやほかのファイルが名前で指す見出し。テストがすぐ下を読むときは、すぐ下の文も含む |

表に名前のない語や行も、ほかのファイルが読んでいれば変えない。変える前に、変える文言を固定の文字列で探し、そのファイルの外の当たりを見る。

```bash
git grep -n -F '<変える文言>' -- common skeleton lib scripts tests vm setup.sh install.sh
```

当たりが変えるファイルの外にあれば、その文言は変えない。直したい理由があれば、[直さずに記録する所](#直さずに記録する所)に従って記録する。

## 機械の確認

ファイルを読み終えるたびに、照合のコマンドで、コード・インラインコード・数値・リンク先が変わっていないかを確認する。言い回しの直しでは、この 4 つは変わらないはずだからである。

```bash
python3 scripts/doc-compare.py --base origin/main <読み終えたファイル>
```

差は 0 件にする。差が出たら、その所を前の文に戻す。

ただし、`common/autopilots.md` の `指示:` のコードブロックは、オートパイロットの指示の文である。この中の文を直すと、照合はコードの差を出す。この差だけは、直した所の番号と対にして記録に書く。

組を終えるたびに、[テスト](#テスト)の関連テストを流す。照合のコマンドには、`STYLE.md` の「書き直しの照合」にある 2 つの限界がある。2 つある同じ値の片方が消えた差は、4 つの項目を見比べるときに前と後の文で確認する。

## PR に残す記録

読んだファイルと直した所は、組ごとに 1 つの PR のコメントに残す。最後の組のあとに、35 のファイルの一覧を 1 つのコメントにまとめる。

PR の本文は 3,000 字を目安にしており、35 のファイルと直した所の表は収まらない。共通スキルの「PR の本文の置き場所と順序」に従い、長い根拠は PR のコメントに置き、本文の確認の行から一覧のコメントへリンクする。

### 組ごとの記録

組ごとのコメントには、次の 3 つの表を置く。1 行目には、組の番号とファイルの数を書く。

読んだファイルの表は、組のファイルを 1 行に 1 つ並べる。

| ファイル | 行数 | 読んだコミット | 直した所の数 |
| --- | --- | --- | --- |
| `common/agents/planner.md` | 66 | `0123456789ab` | 2 |

行数は読んだコミットでの行数で、コミットは 12 文字で書く。直した所がないファイルも、直した所の数を 0 にして載せる。

直した所の表は、直した所を 1 行に 1 つ並べる。前と後の文は、そのコミットの差分で読む。

| 番号 | 場所 | 決まり | 止まる理由 | 否定・条件・例外 | 求める強さ | 誰がするか | 確かさ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 4-1 | `common/agents/planner.md:12` | 語 | 「要望」と「依頼」が同じものを指し、別のものと読める | 同じ | 同じ | 同じ | 同じ |

番号は `<組>-<連番>` にし、場所は直した後のファイルと行にする。4 つの項目は、どれも「同じ」になる。違う所は直さないためである。

直さずに記録する所の表は、場所・決まり・止まる理由・直さない理由の 4 つの列にする。当たる所がなければ、表の代わりに「なし」と書く。

### 一覧

最後の組のあとの一覧は、35 のファイルを 1 行に 1 つ並べる。列は、ファイル・行数・読んだコミット・直した所の数・記録のコメントへのリンクにする。

一覧の行の数が 35 で、どの行にも読んだコミットがあることで、すべてのファイルを読んだと分かる。直した所の数の合計は、組ごとの記録の直した所の表の行の数の合計と同じにする。

直した所の数がどの行も 0 のときは、直した所の表と 4 つの項目の照合は要らない。代わりに、35 のファイルに差分がないことを次のコマンドで確認する。終了コードが 0 なら差分はない。

```bash
git diff --quiet origin/main...HEAD -- common skeleton
```

## 評価の流し直し

リーダーの評価の場面を、すべての組を読み終えた head で流し直す。共通スキルはすべての役が読むので、場面を絞らずに流す。

```bash
bash tests/leader-eval/run.sh --only new
bash tests/leader-eval/run.sh --role principal
```

1 つ目は、リーダーの場面のすべてを新しい指示だけで流す。合否は新しいリーダーだけで決まるので、今のリーダーは流さない。2 つ目は、最上位の役の場面を流す。最上位の役の指示と `leader-principal.md` も対象だからである。

合格は、[leader-principles.md の評価](leader-principles.md#評価)の決まりのとおりで、すべての場面で新しい指示が 3 回とも合格することである。記録は、同じ文書の[記録の形](leader-principles.md#記録の形)に従ってタスクに残す。

落ちた場面は、次の表を上から順に当てはめて扱う。

| 条件 | 扱い |
| --- | --- |
| 落ちたのがリーダーの場面で、`--only old` で流すと今の指示も落ちる | 直した文が原因と言えないので、両方の結果を添えて人間に判断を求める |
| 落ちた基準に関わる文を直していない | 同じく、人間に判断を求める |
| 落ちた基準に関わる文を直している | その所を前の文に戻し、記録の表から行を消して、落ちた場面を流し直す |

前の文に戻したあとは、落ちた場面だけを流し直し、通った場面は流し直さない。戻した所は、評価が通った前の文に戻るだけで、新しい文を足さないためである。

## 変更の知らせ

`CHANGELOG.md` には知らせを書かない。35 のファイルを読み終えて直した文が 0 件になり、導入先に届く変更がないためである。

[release.md の変更の知らせ](release.md#変更の知らせ)は、導入したプロジェクトの動作が変わらない変更には知らせを足さないと決めている。この変更も、それに当たる。

### 手順を足す条件

この変更は、役の指示と共通スキルに手順を足さない。[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)は言い換えを手順の追加に数えないので、PR のテンプレートの手順の項目は当たらないとする。

## 文書と指示の変更

この設計の PR では、この文書を足し、[doc-style.md の対象と優先](doc-style.md#対象と優先)の最後の文からこの文書へリンクする。実装では、35 のファイルのうち直す所のあるものを変える。`CHANGELOG.md` は、[変更の知らせ](#変更の知らせ)のとおり変えない。

`STYLE.md` と共通スキルの決まり、テストのファイル、セットアップのスクリプトは変えない。

## 互換性と影響を受ける利用者

役の判断と手順は変わらない。読み直しで直した文は 0 件なので、流し直しても導入先に届く変更はない。

| 利用者 | 関わること |
| --- | --- |
| 導入・更新する人 | 直した文がないので、流し直しても役の指示・共通スキル・スクワッドとオートパイロットの指示は変わらない |
| 導入したプロジェクトの担当 | 役の判断と手順は変わらない。判定に使う語と固定の行も変わらないので、コメントの読み方も変わらない |
| 原本を変える人 | 直した文がないので、35 のファイルでは同じ時期の PR とコンフリクトにならない |

記入用のひな形の直しは、導入済みのプロジェクトのリポジトリには届かない。人間が記入したものを、更新で書き換えないためである。

## テスト

新しいテストは足さない。言い回しは機械で確認しないと決めているためである。今のテストで、直さない語と行が変わっていないことを確認する。

組を終えるたびに、次を流す。

| テスト | 確認すること |
| --- | --- |
| `tests/agent-templates-test.sh` | 役の指示と共通スキルの見出し・固定の行・展開の印が、今のとおりにある |
| `tests/leader-eval-test.sh` | リーダーの評価の場面が読む参照の語句が、今のとおりにある |
| `tests/terms-test.sh` | 用語の表の語が、使ってはいけない語に替わっていない |
| `tests/links-test.sh` | リンクとアンカーが切れていない |
| `tests/style-test.sh` | `skeleton/README.md` を直したとき、`STYLE.md` の検査を通る |

関連テストは、変えたファイルを読むテストからも選ぶ。`common/autopilots.md` を変えたときは、見出しを読む `tests/role-choices-test.sh` も流す。`MANIFEST` は `bash scripts/manifest.sh` で作り直し、生成した差分を確認する。

すべての組のあとに、[評価の流し直し](#評価の流し直し)を行う。

## 残る危うさ

読んだかどうかは、機械で確認できない。一覧の読んだコミットは、読む人が書く行なので、すべての行を読んだ証拠にはならない。

4 つの項目は、人が見比べる。項目に入らない語感の差、たとえば強調の度合いの差は、見比べても拾えないことがある。

評価は、本物のモデルで流すので、同じ指示でも結果が揺れる。前の文に戻したあとに落ちた場面だけを流し直すので、戻した所が通った場面に効く場合は見逃す。

固定の文字列で探す確認は、語の言い換えで指している場合を拾わない。役が意味で読む語は、判定に使う語として表に挙げたものに頼る。

記入用のひな形を直した場合は、導入済みのプロジェクトに届かない。新しく導入した所と前から導入した所で、記入の案内の文が違う。この変更ではひな形を直していないので、この違いは生じていない。

## 検討した案

すべての文を決まりに合わせて書き直す案は採らなかった。止まる理由のない言い換えは、意味を変えるおそれがあり、差分も読みにくくするためである。

事実と違う文を見つけたら、この変更で直す案も採らなかった。直すと役の判断が変わり、この変更の範囲の外になるためである。記録に残し、別のタスクで扱う。

直す前と直した後の文を、記録の表に写す案は採らなかった。差分と同じ中身が 2 か所になり、PR のコメントも長くなるためである。前と後の文は、差分で読む。

記録を 1 つの PR のコメントにまとめる案も採らなかった。組ごとに書けば、途中で止まっても、それまでの組の記録が残るためである。

評価を、直したファイルを読む場面だけに絞る案は採らなかった。共通スキルはすべての場面が読むので、絞れないためである。

直した文が 0 件でも、「導入先に届く変更はない」という知らせを書く案は採らなかった。利用者が読んでもすることがなく、知らせの決まりにも合わないためである。

評価で今の指示も流す案は採らなかった。合否は新しい指示だけで決まり、今の指示は落ちた場面の原因を見るときだけ流せば足りるためである。
