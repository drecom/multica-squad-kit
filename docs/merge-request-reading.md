# マージの依頼に読む深さと残した指摘を足し、前からある不具合を分けて数える

レビューの結果に、この PR より前からある不具合の欄と件数を足す。マージを頼むコメントには、読む深さ・マージの前に人間がすること・直さずに残した指摘・前からある不具合の件数の 4 行を足す。この文書は、足す文の全文と行の形、スクリプトの読み方、その理由を書く。

## 目的と範囲

マージを判断する人間には、困りごとが 2 つある。

1 つ目は、レビューで気づいた前からある不具合が、行き先のないまま消えることである。過去の PR では、最上位の役が差分の外の同じ誤りを 6 行見つけた。書く場所がないので、推奨の指摘の「直し方」の中に書いた。マージの依頼には載らず、その 6 行は main に残り、別のタスクにもならなかった。

2 つ目は、マージの依頼が役の結論を並べるだけなことである。PR の本文の注意にある人間の作業も、直さずに残した指摘の中身も載らない。過去の PR では、人間が「推奨はなに？」と聞き直し、リーダーの実行が 1 回増えた。人間の作業をしたかの記録がないまま、その PR はマージされた。

目的は次の 4 つである。

1. レビューの役と最上位の役が、前からある不具合を指摘と別の欄に書き、件数を結果の先頭の行に添える
2. 前からある不具合だけの結果では ❌ にせず、修正の役へ回さない。別のタスクにするかは人間が決める
3. `squad-review-next decide` が書くマージの依頼に、上の 4 行を足す。モデルの実行は増やさない
4. リーダーが手で書くマージの依頼にも、同じ 4 行を同じ形で置く

次は対象にしない。

- 読まずにマージする変更の種類を増やすこと。マージするのは人間のままと合意した
- 前からある不具合を、自動で別のタスクにすること
- QA の E2E の失敗の扱い
- 過去の PR へ遡ること。上の 6 行と同じ形の行は、起票しない
- 本物のモデルを流す確認と、追加の評価
- 設計の承認を頼むコメントの形

要件の合意と、過去の 2 件の実物は、タスクのコメントにある。

## 前からある不具合の欄

前からある不具合は、レビューの結果の新しい項目として、指摘と別に書く。マークは、この PR の指摘だけで決める。

| 項目 | 決めたこと |
| --- | --- |
| 書く役 | レビューの役（コード・セキュリティ・UX・性能）と最上位の役。QA・実装・修正の役は書かない |
| 書くもの | 差分を読む中で気づいた、PR の base にもある不具合。この PR が入れたものと、悪くしたものは入れない |
| 探し方 | 探しには行かない。読んだ所で目に入ったものだけを書く |
| 欄の名前と置き場所 | `前からある不具合:` の行。指摘の項目のあと、見た範囲の項目の前 |
| 1 件の形 | `- <場所>: <影響>` の 1 行 |
| 先頭の行の件数 | 1 件以上のときだけ、結論に `前からある不具合 <N> 件` を足す。ないときは 0 件と読む |
| マーク | この欄はマークを変えない。ほかに指摘がなければ ✅ にする |
| 修正の依頼 | 回さない。リーダーも `decide` も修正の役へ渡さず、修正の役も直さない |

この PR の受け入れ条件を満たさなくなる不具合は、前からあっても欄に書かず、指摘に書く。マージを止めるかは、指摘の重大度で決めるためである。

再確認の結果でも、残っているものを書き直す。マージの依頼は、役ごとの最新の結果だけを数えるためである。

### 結果の型に足す文

共通スキル squad-handoff の「PR にレビューやテストの結果を書く」の、結果を書く順の一覧と見本を、次のとおりにする。マークの表と、一覧の前後の文は変えない。

````markdown
1. マークの行。結論に重大度ごとの件数を `推奨 1 件` の形で添える。前からある不具合があれば、`前からある不具合 1 件` の形で件数も添える
2. 固定の行。`確認したコミット:`、`列挙した範囲:` など、役の指示が決める行
3. 前提。環境と確認した範囲を 1 文で書き、QA のほかの役は要るときだけ書く
4. 結果の表。QA だけが書き、列はケース・手順・期待する結果・実際の結果・判定・成功の条件の番号にする
5. 指摘。重大度の順に番号を付けて 1 件 5 行ほどで書き、1 行目を `<重大度>: <場所>` にして影響と直し方を続ける
6. 前からある不具合。レビューの役と最上位の役だけが、`前からある不具合:` の行に続けて、1 件ずつ `- <場所>: <影響>` の行で書く
7. 見た範囲。指摘がないときだけ、`見た範囲:` で始めて 3 行以内で書き、確認した項目を長く並べない
8. 人間が確認する条件。QA だけが、確認する人が人間の成功の条件の番号を並べる
9. スクリーンショット。載せ方は「画像を載せる」に従う

前からある不具合は、差分を読む中で目に入った、PR の base にもある不具合である。探しには行かず、この PR が入れたものや悪くしたものは指摘に書く。この欄だけではマークを変えず、ほかに指摘がなければ ✅ にする。修正の役へは回さず、別のタスクにするかは人間が決める。再確認の結果でも、残っているものを書き直す。

場所の書き方と、影響に足す中身は、役ごとに違う。場所をファイルと行・画面・ケースのどれで示すかは、役の指示に従う。攻撃の経路や数値を足すかも、役の指示に従う。

次は、コードのレビューで指摘と前からある不具合が 1 件ずつある結果の見本である。

```text
⚠️ example-code-reviewer: 推奨 1 件、前からある不具合 1 件。マージは止めない
確認したコミット: 0123456789abcdef0123456789abcdef01234567

1. 推奨: `lib/answers.sh:42`
   - 影響: 回答ファイルに空の行があると、登録の名前が空になる
   - 直し方: 読む前に空の行を飛ばし、空の行の例をテストに足す

前からある不具合:
- `lib/answers.sh:88`: 同じ読み方の別の欄も、空の行で名前が空になる。差分の外で、base でも同じ
```
````

`前からある不具合:` の行と `- <場所>: <影響>` の項目は、字下げしない。スクリプトが件数を読むのはタスクの要約のマークの行だけだが、人間が欄を探せるように、決まった名前で始める。

### 修正の依頼と数え方

`decide` の判定は変えない。マークの行の記号で ❌・⚠️・✅ を読む今の読み方のままなので、前からある不具合だけの ✅ の結果は、修正の依頼にならない。リーダーの手順の「指摘は ❌ だけを数える」も変えない。

修正の役の指示は変えない。今の指示が、既存のコードの不具合は直さず、範囲の外として分けて書くと決めているためである。

## マージを頼むコメントの行

マージを頼むコメントに、4 行を足す。`マージの依頼:`・`前の回:`・コンフリクトと CI の行の位置は変えない。CI の待ちの `ci-wait` と、制御記録を読む部品が、今の行を読むためである。

### 行の順

[返事がそろったあとの次の依頼](review-next-step.md#マージを頼むコメント)の「マージを頼むコメント」の行を、次の順にする。足すのは 5〜8 である。

1. マージを頼む 1 行
2. `マージの依頼: <head の完全な SHA>`
3. `前の回: <回のコメントの ID>`
4. コンフリクトの行と CI の行
5. `読む深さ: <深さ>（<理由>）`
6. `マージの前に人間がすること: <PR の本文の注意>`
7. `直さずに残した指摘: <N> 件`。1 件以上なら、指摘ごとの行を続ける
8. `前からある不具合: <N> 件`。1 件以上なら、役ごとの内訳を括弧で添える
9. 各役の結論の 1 行
10. 紐付いていないときだけ、今の行を続ける

人間がすることと残した指摘を、各役の結論より前に置く。人間が上から読み、読む深さで止められるようにするためである。

数える結果は、マージの依頼の各役の結論の 1 行と同じ組である。役ごとの最新の結果と、最終レビューの回の最上位の役の結果を指す。最終レビューの結果が組の結果と同じ行なら、1 回だけ数える。

### 読む深さ

深さは、新しい種類を作らず、重要のラベル・PR の注意・残した件数の 3 つで決める。上の行から順に当て、最初に当たった深さにする。

| 深さ | 当てはまるとき | 人間が読むもの |
| --- | --- | --- |
| PR の概要と設計文書まで | タスクに重要のラベルがある | このコメント、PR の本文の注意と概要、設計文書の該当の節 |
| このコメントと PR の注意 | 注意が「なし」でない、注意を読めない、残した指摘が 1 件以上、前からある不具合が 1 件以上のどれか | このコメント、PR の本文の注意、残した指摘と前からある不具合を書いた役の結果 |
| このコメントだけ | 上のどれにも当たらない | このコメント |

合意した表（仮）との違いは、前からある不具合を「このコメントと PR の注意」の条件に足したことである。前からある不具合は、別のタスクにするかを人間が決めるので、件数だけでなく役の結果を読む必要がある。

重要のラベルは、`decide` が観点の選び方で使う値と同じものを使う。リーダーが手で書くときは、タスクのラベルを読む。

理由は、次の決まった語を並べる。人間が、どの値で深さが決まったかを読めるようにするためである。

```text
<重要のタスク | 重要でない>。<注意あり | 注意なし | 注意を読めない>、残した指摘 <N> 件、前からある不具合 <M> 件
```

### マージの前に人間がすること

PR の本文の `## 注意` の見出しから、次の `##` の見出しの前までを写す。見出しの行は写さない。中身は、下の[写す文の整え方](#写す文の整え方)で 1 行ずつにしてから、行の数で形を決める。

| 中身 | 行の形 |
| --- | --- |
| 空の行を除いて `なし` か `なし。` だけ | `マージの前に人間がすること: なし` |
| 1 行 | `マージの前に人間がすること: <その行>` |
| 2 行以上 | `マージの前に人間がすること: PR の注意の <N> 行` に続けて、1 行ずつ `- <行>` |
| 中身が空 | `マージの前に人間がすること: 読めない（PR の本文の注意が空）` |
| `## 注意` の見出しがない | `マージの前に人間がすること: 読めない（PR の本文に注意の見出しがない）` |
| PR の本文を読めない | `マージの前に人間がすること: 読めない（PR の本文を読めなかった）` |

読めないときも、マージの依頼は書く。依頼を止めると、人間が待つだけになるためである。読めないときは、読む深さを「このコメントと PR の注意」以上にし、人間に PR の注意を読んでもらう。

長い注意は、10 行か 800 字のどちらかに届く手前の行で切る。切ったときは、最後に `- 続きは PR の本文の注意を読む（残り <M> 行）` を置く。過去の PR で最も長い注意は 604 字で、番号付きの手順を含んでいた。800 字までなら、多くの注意はそのまま載る。

「決まっていないこと」のための別の行は置かない。要件のとおり、PR の本文の注意を写すだけにする。

### 直さずに残した指摘

数える組のうち、マークが ⚠️ の結果から、指摘を写す。❌ の結果はマージの依頼まで進まず、✅ の結果は指摘を持たないためである。

指摘の中身は、PR のコメントではなく、役がタスクに返す要約から読む。今の契約では、指摘の全文は PR の結果のコメントにあり、タスクの要約は結論と PR のコメントへのリンクだけを持つ。そこで、⚠️ の結果を返す役は、PR の結果の指摘の先頭の行を、要約の `指摘の一覧:` の行に写す。写す決まりは、下の[タスクの要約に指摘を写す](#タスクの要約に指摘を写す)にある。

`decide` が読むのは、組の結果として認めたタスクの返事のコメントだけである。そのコメントは、今の組の決め方で 3 つを確認済みである。作者が回で頼んだ役で、`返事の回:` がその回で、`確認したコミット:` が回のコミットと合う。

`指摘の一覧:` は、その同じコメントの中からだけ読み、PR のコメントは読まない。一覧の行は、字下げのない `指摘の一覧: <N> 件` の形にする。続く行のうち、`-` と空白で始まる行を、指摘の項目として読む。そうでない行か空の行で、一覧は終わる。

```text
直さずに残した指摘: 2 件
- example-code-reviewer 1. 推奨: `lib/answers.sh:42`。影響: 回答ファイルに空の行があると、登録の名前が空になる
- example-principal 1. 推奨: `docs/example.md:12`。影響: 読む人が、ない違いを探す
```

| 場合 | 数え方と行 |
| --- | --- |
| `指摘の一覧:` があり、項目が読める | 件数は `<N>` と項目の数の大きいほうにする。項目を 1 件 1 行で `- <役> <項目>` の形で写す |
| ⚠️ なのに `指摘の一覧:` がない、2 回以上ある、件数が 0 か数字でない | 1 件と数え、`- <役>: 指摘の行を読めない。結果を読む` を書く |
| 件数が項目の数より多い | 項目を写したあとに、`- <役>: ほか <M> 件は結果を読む` を書く |
| 写す項目が全体で 11 件以上 | 10 行まで写し、`- ほか <N> 件は各役の結果を読む` で終える。件数の行は全件を数える |
| 1 行が 200 字を超える | 200 字で切り、末尾に `…` を足す |

⚠️ で推奨 0 件の結果を 1 件と数えるのは、⚠️ が「指摘がある」の意味だからである。0 件にすると、読む深さが「このコメントだけ」になり、人間が結果を読まずに済ませうる。

#### タスクの要約に指摘を写す

共通スキル squad-handoff の「レビューと E2E の返事を返す」の、`設計への指摘:` の行の段落のあとに、次の段落を足す。前後の段落は変えない。

```markdown
マークが ⚠️ の結果は、固定の行のあと、成果物の前に `指摘の一覧: <N> 件` の行を置く。続けて、PR の結果の指摘を 1 件ずつ、`- <番号>. <重大度>: <場所>。影響: <影響>` の 1 行で写す。件数は PR の結果の指摘の数にし、写すのは 10 件までにする。影響は 1 文にし、1 行を 150 字ほどまでにする。マークの行は PR の結果の先頭の行と同じ文にし、前からある不具合の件数も写す。マージの依頼を書く `squad-review-next decide` は PR のコメントを読まず、この要約から指摘と件数を写すためである。
```

前からある不具合の件数も、タスクの要約のマークの行から読む。そのため、要約のマークの行を PR の結果の先頭の行と同じ文にする決まりを、同じ段落に置く。

役のひな形（`common/agents/`）は変えない。レビューの役・最上位の役・QA の指示は、要約の形を共通スキルの「レビューと E2E の返事を返す」に従うと決めているためである。

### 前からある不具合の件数

数える組のすべての結果について、タスクの要約のマークの行から `前からある不具合 <N> 件` を読んで足す。マークは問わない。件数がない結果は 0 件にする。読むのは、[直さずに残した指摘](#直さずに残した指摘)と同じ、組の結果として認めたコメントだけである。

```text
前からある不具合: 3 件（example-code-reviewer 1 件、example-principal 2 件）
前からある不具合: 0 件
```

欄の中身は写さない。要件が写すのは件数であり、中身は役の結果にあるためである。読む深さを「このコメントと PR の注意」にして、人間に役の結果を読んでもらう。

### 写す文の整え方

PR の本文と役の結果から写す行は、次の順に整える。写した行が制御の行として読まれず、マージの依頼が[読める本文](review-next-step.md#読める本文)のままになるようにするためである。

1. 制御文字を除く。タブは空白にする
2. 行頭の空白、`>`、箇条書きの記号（`-`・`*`・`+`・`<数>.`・`<数>)`）を、なくなるまで繰り返し外す。指摘の行は、番号を `<番号>.` の形で残す
3. 外したあとに空の行は、捨てる
4. コードの囲みの行（` ``` ` か `~~~` で始まる）と囲みの中、HTML コメントに触れた行、`<` で始まる行は捨てる（読み方は、下の[注意の入力の種類と写し方](#注意の入力の種類と写し方)の表に従う）。捨てた行があれば、`- （コードの囲みや HTML は PR の本文の注意を読む）` を 1 行だけ足す
5. メンションのリンク `[<文字>](mention://<種類>/<ID>)` は、`<文字>` だけにする。残った `mention://` の文字列は、`mention: //` にする

写した行は、必ず `マージの前に人間がすること:` や `-` などの決まった語と空白のあとに置く。そのため、写した行が `マージの依頼:` や `前の回:` などの制御の行の行頭になることはない。

書く前の `squad_cli_control body` の確認は、今のまま残す。整えたあとも本文が読めないときは、注意の行を `マージの前に人間がすること: 読めない（写すと読めない本文になる）` に替え、指摘の行を件数の行だけにして、1 回だけ確認し直す。それでも読めなければ、今のとおり何も書かずに失敗する。

### 注意の入力の種類と写し方

PR の本文の `## 注意` の節と、役の返事の `指摘の一覧:` の項目は、同じ規則でコードの囲みと HTML コメントを見分ける。本文の先頭から行を順に読み、囲みの中かコメントの中かを覚えておく。写す文を整える 4 は、この表の規則である。

規則は次のとおり。

- 囲みは、記号を外したあとに逆引用符かチルダが 3 個以上並ぶ行で開き、開きと同じ文字が開きの長さ以上並ぶ行で閉じる。短い行、違う文字の行、記号のあとに文字がある行では閉じない
- コメントは `<!--` で開き、そのあとの最初の `-->` で閉じる（`<!-->` と `<!--->` は開いてすぐ閉じる）。入れ子にはしない
- 囲みの中ではコメントの記号を、コメントの中では囲みの記号を見ない。1 行の中のコードスパン（`` ` `` で囲んだ所）の中と、バックスラッシュのあとの `<!--` は、コメントを開かない
- 囲みかコメントに触れた行は、見える文字が残っていても行ごと捨てる。触れた行は、開く行・中の行・閉じる行・同じ行で開いて閉じる行である
- `##` の見出しは、囲みにもコメントにも入っていない行のものだけを、節の開始と終了に使う。`## 注意` が複数見えるときは、最初の節だけを写す
- 閉じていない囲みやコメントは、本文の終わりまで続くものとして以降を捨て、見える行と捨てた旨の行を写す。「なし」にはせず、`## 注意` の見出しがその中に入ったときは、見出しがないものとして読めない行にする

### PR の本文を読む部品

PR の本文は、`squad-cli-lib` に新しい読み取り `gh-pr-body` を足して読む。今の `gh-pr-head` は、Dependabot の自動マージとテストも使う。応答の形を変えないため、別の読み取りにする。

| 項目 | 値 |
| --- | --- |
| コマンド | `gh pr view {number} --repo {repo} --json body` |
| 形 | オブジェクト |
| 記録の種類 | 外部（GitHub の応答を記録した見本を使う） |
| `body` | 必須の文字列で、null にしない。本文がない PR は空の文字列になる |

`decide` は、マージの依頼の確認がすべて通ったあと、依頼を書く直前に 1 回だけ読む。PR は、マージの依頼の確認の 2 で head を読んだのと同じ正規形の PR にする。

読み取りが失敗したとき、`body` がないとき、文字列でないときは、[マージの前に人間がすること](#マージの前に人間がすること)の「PR の本文を読めない」の行にする。`decide` は失敗にしない。

### 見本

次は、重要でないタスクのマージの依頼の見本である。注意は 2 行、残した指摘は 2 件、前からある不具合は 1 件とする。

```text
[@<呼ぶ人間>](mention://member/<ユーザーの ID>) レビューと確認が済みました。PR のマージを判断してください。
マージの依頼: 0123456789abcdef0123456789abcdef01234567
前の回: <回のコメントの ID>
コンフリクト: MERGEABLE head: 0123456789abcdef0123456789abcdef01234567
読む深さ: このコメントと PR の注意（重要でない。注意あり、残した指摘 2 件、前からある不具合 1 件）
マージの前に人間がすること: PR の注意の 2 行
- マージの前に、人間がリーダーの評価を流し直す。本物のモデルを使うので CI では流れない。
- 非公開の一覧による混入の検査は、人間の手元で流してほしい。
直さずに残した指摘: 2 件
- example-principal 1. 推奨: `docs/example.md:12`。影響: 読む人が、ない違いを探す
- example-code-reviewer 1. 推奨: `lib/answers.sh:42`。影響: 回答ファイルに空の行があると、登録の名前が空になる
前からある不具合: 1 件（example-code-reviewer 1 件）
⚠️ example-principal: 推奨 1 件。マージは止めない
⚠️ example-code-reviewer: 推奨 1 件、前からある不具合 1 件。マージは止めない
✅ example-security-reviewer: 指摘なし
```

## リーダーが手で書くマージの依頼

リーダーの手順 `leader-pr-checks.md` の「マージの前の確認」の 6 を、次のとおりにする。

```markdown
6. マージの依頼。同じコメントに `マージの依頼: <head の完全な SHA>` の行を置き、「手で書くマージの依頼の行」と「人間を呼ぶコメントに添える行」を続ける。同じ head で 1 回だけ依頼する
```

同じ節の「手で書くマージの依頼は、字下げ、…」の段落のあとに、次の節を足す。

````markdown
### 手で書くマージの依頼の行

手で書くマージの依頼にも、`decide` が書く依頼と同じ 4 行を、同じ形と順で置く。人間が、どちらの依頼でも同じ所を読めばよいようにするため。置き場所は、コンフリクトと CI の行のあと、各役の結論の行の前である。

```text
読む深さ: <深さ>（<重要のタスク | 重要でない>。<注意あり | 注意なし | 注意を読めない>、残した指摘 <N> 件、前からある不具合 <M> 件）
マージの前に人間がすること: <なし | 注意の 1 行 | PR の注意の <N> 行>
直さずに残した指摘: <N> 件
前からある不具合: <M> 件（<役> <n> 件、…）
```

1. 読む深さは、タスクに重要のラベルがあれば `PR の概要と設計文書まで` にする。ないときは、注意が「なし」でない・読めない、または残した指摘か前からある不具合が 1 件以上なら `このコメントと PR の注意`、どれもなければ `このコメントだけ` にする
2. 人間がすることには、PR の本文の注意を写す。2 行以上なら、続けて 1 行ずつ `- ` で始めて写す。10 行までにし、残りは `- 続きは PR の本文の注意を読む（残り <M> 行）` で示す
3. 残した指摘は、⚠️ の結果を返した役のタスクの要約から、`指摘の一覧:` の項目を 1 件ずつ `- <役> <番号>. <重大度>: <場所>。影響: <影響>` の行で続ける。⚠️ なのに `指摘の一覧:` がない要約は 1 件と数え、`- <役>: 指摘の行を読めない。結果を読む` と書く
4. 前からある不具合は、各役のタスクの要約のマークの行の件数を足す。0 件なら括弧を付けない

数えるのは、マージへ回す各役の最新の結果と、最終レビューの結果である。どちらも、作者がその回で頼んだ役で、`確認したコミット:` がマージを頼む head と合う要約だけを使う。写す行は字下げ・引用・HTML・コードの囲みを外し、メンションのリンクは文字だけにする。
````

`leader-flow.md` は変えない。先に入った再発の手当ての表と、指摘は ❌ だけを数える決まりは、そのまま使う。

## 入力と信頼の表

マージを頼むコメントに、役や人間が書いた文を写す。そのコメントは、`ci-wait` と制御記録の部品が読む。そのため、写す入力ごとに次のとおり扱う。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| PR の本文の `## 注意` の節（PR を作った役か、本文を直した人間が書ける） | マージの前に人間がすることの行に写す | 中身は信頼しない。整えたうえで、決まった語のあとにだけ置く | 見出しがない・空・読めないときは「読めない」の行にし、読む深さを「このコメントと PR の注意」以上にする |
| タスクの要約の `指摘の一覧:` の行と項目（要約を返した役が書く。タスクのコメントは、ほかの役や人間も書ける） | 直さずに残した指摘の行に写す | 組の結果として認めたコメントの中だけを読む。その作者・回・コミットは今の `decide` が確認済みで、中身は信頼せず整えてから `-` と空白のあとに置く | 組に入らないコメントの一覧は読まない。⚠️ の要約に読める一覧がなければ 1 件と数え、「読めない」の行にする |
| タスクの要約のマークの行の `前からある不具合 <N> 件`（同じ組の役） | 件数を足す | 作者・回・コミットの確認は上と同じ。数字だけを読む | 形が合わなければ 0 件と読む。件数の行に誤りが出ても、マージの判断は人間がする |
| PR の結果のコメント（同じ GitHub の認証で、どの役も人間も書ける） | 読まない | 作者で役を見分けられないので、`decide` の入力にしない | 人間が、読む深さの案内で成果物のリンクから読む |
| タスクの重要のラベル（リーダーか人間が付ける） | 読む深さの「PR の概要と設計文書まで」 | 今の観点の選び方と同じ値を使う | ラベルを読めないときは、今の `decide` のとおり失敗にする |

写した文から、メンションも制御の行も生まれない。人間を呼ぶリンクは、1 行目の呼ぶ人間の 1 つだけである。役のリンクを書かないので、モデルの実行は増えない。

## 手順を足す条件の記載

この変更は、[手順を足す条件](../CONTRIBUTING.md#手順を足す条件)の範囲のファイル（共通スキル squad-handoff とリーダーの手順の参照ファイル）に、役にさせる文を足す。条件の 3 つを次に書く。

### 防ぐ失敗

合意された要件による新しい手順なので、要件の合意を根拠にする。失敗の記録は 2 件あり、タスクのコメントにある。

1 件目は、前からある不具合が消えた失敗である。最上位の役が差分の外の 6 行を見つけたが、推奨の直し方の中に書くしかなかった。マージの依頼に載らず、6 行は main に残った。

2 件目は、マージの依頼に人間の作業と指摘の中身が載らなかった失敗である。人間が推奨の中身を聞き直し、注意にあった評価の流し直しは記録のないままマージされた。

### 働いた跡

手順が働くと、タスクのコメントに次の行が残る。見直しの跡の定義は、[跡の形](procedure-review.md#跡の形)のコメントの形で、次のとおりにする。

| 手順 | 形 | `pattern` | `author_type` |
| --- | --- | --- | --- |
| 結果の前からある不具合の欄 | `kind: "comment"` | `(?m)^(✅\|⚠️?\|❌) \S+: .*前からある不具合 \d+ 件` | `agent` |
| 手で書くマージの依頼の行 | `kind: "comment"` | `(?m)^読む深さ:` | `agent` |
| タスクの要約に指摘を写す | `kind: "comment"` | `(?m)^指摘の一覧: \d+ 件` | `agent` |

前からある不具合の跡は、気づいたものがなければ 0 回になる。0 回のときに削る候補とするかは、見直しで人間が判断する。手で書くマージの依頼の跡は、`decide` が書く依頼でも同じ行が残る。リーダーが書いた分だけを分けるには、作者がリーダーのコメントに絞る。

### 仕組みにしない理由

数えることと写すことは、仕組みにした。`decide` が件数を足し、注意と指摘を写し、読む深さを決める。手順に残すのは、次の 3 つだけである。

| 手順に残すこと | 仕組みの案 | 選ばなかった理由 |
| --- | --- | --- |
| 役が前からある不具合を欄に書く | スクリプトが、差分の外の行と base を比べて、前からある不具合を見つける | 不具合かどうかと、この PR が悪くしたかは、意味の判断である。行の比較では見分けられない |
| 役が指摘をタスクの要約に写す | `decide` が、要約の成果物のリンクから PR の結果のコメントを読む | PR のコメントは同じ GitHub の認証で書かれ、作者で役を見分けられない。リンクを書き換えれば別のコメントを読ませうるうえ、新しい読み取りと見本も要る |
| リーダーが手で同じ 4 行を書く | リーダーが `decide` の部品を呼んで、4 行を出してもらう | 手で書く依頼は、コンフリクトの解消の引き継ぎのあとなど、`decide` の回を通らない場面で書く。数える組を決める回がないことがある |

自動で別のタスクにする案は、要件の合意で採らないと決めた。

役のひな形（`common/agents/`）と `leader-flow.md` は変えない。`VERSION` と `CHANGELOG.md` は、バージョンを上げる PR で書く。

## 互換性と影響を受ける利用者

導入済みのプロジェクトでは、セットアップを流し直すと、共通スキル・リーダーの手順・見張りのスクリプトが替わる。エージェントとオートパイロットの登録は変わらない。

| 利用者 | 変わること |
| --- | --- |
| マージを判断する人間 | マージの依頼に 4 行が増え、長くなる。読む深さで、どこまで読むかが分かる |
| レビューの役と最上位の役 | 前からある不具合を欄に書き、先頭の行に件数を添える。⚠️ の要約に `指摘の一覧:` を写す |
| QA | ⚠️ の要約に `指摘の一覧:` を写す |
| リーダー | 手で書くマージの依頼に 4 行を書く |
| 修正の役・実装の役 | 変わらない |

PR の本文の書き方は変えない。注意の見出しがない古い形の本文でも、依頼は「読めない」の行で書かれる。

流し直す前の結果には、件数も `指摘の一覧:` もない。件数がない結果は 0 件と読み、一覧がない ⚠️ の結果は 1 件と数えて「読めない」の行にするので、途中のタスクも止まらない。マージの依頼が今の行を持つかを読む `ci-wait` と制御記録の部品は、足した行を読まないので、動きは変わらない。

## テスト

確認するのは、[テストを書く決まり](../CONTRIBUTING.md#テストを書く決まり)のとおり、スクリプトの動きと、機械が読む行の形だけである。説明の文は固定の文字列で確認しない。

| テスト | 確認すること |
| --- | --- |
| `tests/squad-review-next-decide-merge-test.sh` | 4 行が決まった順に出る。読む深さの 3 つがそれぞれ出る |
| 同上 | 注意の「なし」・1 行・2 行以上・11 行以上・見出しなし・読み取りの失敗で、行の形が表のとおりになる |
| 同上 | 注意のコードの囲み・HTML・字下げ・引用・メンションのリンクを整えたあと、本文が読める。`mention://` を含むリンクが 1 つだけになる |
| `tests/review-note-table-test.sh` | [注意の入力の種類と写し方](#注意の入力の種類と写し方)の表の全行を 1 行ずつ確認し、種類が共通の行は、注意の写し方と指摘の一覧の読み方に同じ入力を通す。設計の表の番号と、テストの表（`tests/review-note-table.tsv`）の番号が同じ順に並ぶ |
| 同上 | ⚠️ の要約の `指摘の一覧:` が写り、一覧がない ⚠️ は 1 件と数える。11 件以上は 10 行で切る |
| 同上 | 指摘の全文を PR のコメントに置き、要約に一覧と件数だけを置いた場合で、2 件の指摘と前からある不具合の件数がマージの依頼に出る。PR のコメントの読み取りを呼ばない |
| 同上 | 回で頼んでいない作者、前の回、コミットの合わない返事にある `指摘の一覧:` は写らない |
| 同上 | 前からある不具合の件数を、⚠️ と ✅ の結果と最終レビューから足し、内訳を出す。件数がない結果は 0 件 |
| `tests/squad-review-next-decide-fix-test.sh` | 前からある不具合の件数と欄だけを持つ ✅ の結果で、修正の依頼を書かずにマージの依頼へ進む |
| `tests/squad-cli-lib-gh-test.sh` | `gh-pr-body` の見本が契約に合う。`body` がない応答は契約の誤りになる |
| `tests/agent-templates-test.sh` | 共通スキルの見本のマークの行が、`decide` の件数の読み方に合う。`前からある不具合:` の行が見本にある |
| 同上 | リーダーの手順に、4 行の名前が行頭の形で 1 回ずつある |
| 同上 | 共通スキルの「レビューと E2E の返事を返す」に、`指摘の一覧: <N> 件` と項目の形がある |

テストを足すたびに、`bash tests/run.sh <テスト>` で流す。モデルの実行が増えていないことは、マージの依頼のテストで、エージェントへのメンションがないことで確認する。

## 残る危うさ

次の 5 つは、この決まりで残る。

1 つ目は、役が欄に書き忘れることである。書き忘れても、だれも気づかない。合意のとおり、まず欄だけで始める。

2 つ目は、要約の一覧の形がそろわないことである。一覧を書き忘れた ⚠️ の要約は、1 件と数えて結果を読む案内を出すので、件数が 0 に落ちることはない。

3 つ目は、件数の行と欄の中身が食い違うことである。スクリプトは要約のマークの行の件数だけを読み、PR の結果の欄の項目の数とは照らさない。

4 つ目は、要約の一覧と PR の結果の指摘が食い違うことである。スクリプトは PR の結果を読まないので、気づかない。人間は、読む深さの案内で役の結果を読むときに見比べられる。

5 つ目は、QA の「人間が確認する条件」が、マージの前に人間がすることの行に入らないことである。要件は PR の本文の注意を写すと決めているので、QA の行は今のとおり QA の結論から読む。

## 検討した案

| 案 | 選ばなかった理由 |
| --- | --- |
| 前からある不具合だけの結果を ⚠️ にする | ⚠️ は、この PR の直さずに残した指摘を表す。前からある不具合を混ぜると、残した指摘の件数と読む深さが、この PR の質と関係なく増える |
| 前からある不具合を、推奨の指摘として書く | 今の書き方で、過去に消えた。指摘は修正の役へ回るので、範囲の外の直しを招く |
| 欄の中身もマージの依頼に写す | 要件が写すのは件数である。中身は役の結果にあり、読む深さの「このコメントと PR の注意」で読んでもらう |
| 合意の表（仮）のとおり、写す行を `-` なしで置く | 写した行が `マージの依頼:` などで始まると、制御の行として読まれる。決まった語のあとに置けば起きない |
| 指摘を、要約の成果物のリンクから PR の結果のコメントを読んで写す | PR のコメントは同じ GitHub の認証で書かれ、作者で役を見分けられない。要約は作者・回・コミットを確認済みなので、要約に写すほうが信頼の条件を足さずに済む |
| `gh-pr-head` の読み取りに `body` を足す | Dependabot の自動マージも同じ読み取りを使う。応答の形と見本を変えると、関係のない部品のテストも変わる |
| PR の本文を読めないとき、`decide` を失敗にする | マージの依頼が書かれず、人間が待つだけになる。「読めない」と書けば、人間が PR を読んで判断できる |
| ⚠️ で推奨 0 件の結果を 0 件と数える | 読む深さが「このコメントだけ」になり、⚠️ の中身を人間が読まずに済ませうる |
| 注意を全文写す | 長い注意で、依頼が数千字になりうる。切った所と残りの行の数を示せば、人間は PR で続きを読める |
| 「決まっていないこと」の行を足す | 要件で足さないと決めた。PR の本文の注意を写すだけにする |
