# 判定の API と専門の決まりを足す手がかり

この文書は、原本を変える人に向けて、拡張の文書とプロジェクトのひな形に足す例と記入の欄を決める。足すのは次の 4 つで、拡張の文書の 2 つの例と、ひな形の 2 つの変更である。判定の API を足す例・公開されているスキルを足す例・DB と画面の作業別のルールのひな形・検証スキルのひな形の記入の指示である。

## 目的と範囲

目的は、導入したプロジェクトの担当が、判定の API や専門のスキルを足すときの手がかりを、文書とひな形に置くことである。今の拡張の文書には、外の API の鍵の渡し方がない。作業別のルールのひな形はコード・テスト・ドキュメントの 3 つだけで、記入の例がない。

この文書で決めるのは、次の 6 つである。

1. 拡張の文書に足す「判定の API を足す例」の全文と置き場所。[判定の API を足す例](#判定の-api-を足す例)に書く
2. 拡張の文書に足す「公開されているスキルを足す例」の全文と置き場所。[公開されているスキルを足す例](#公開されているスキルを足す例)に書く
3. 検証スキルのひな形の、2 つの欄の記入の指示。[検証スキルのひな形](#検証スキルのひな形)に書く
4. DB と画面の作業別のルールのひな形の名前と全文。[作業別のルールのひな形](#作業別のルールのひな形)に書く
5. ひな形の説明の置き場所の表に足す行。[ひな形の説明](#ひな形の説明)に書く
6. 例が検査に通ることと、鍵のファイルの約束を保つ確認。[確認](#確認)と[確認の方法](#確認の方法)に書く

次は、この文書の範囲の外である。

- キーを 1 つだけ足す補助のコマンド。文書の警告で足り、使う導入先がまだないため
- 配布元のスキルを原本に同梱すること
- 検証スキルのひな形に節を新しく作ること。今ある節と中身が重なるため
- 役の指示に、マイグレーションや画面の品質の観点を足すこと。導入先でその原因の失敗が記録されたら、別に扱う
- 判定の API を呼ぶコード、製品の名前、API の呼び方
- 鍵や環境変数を実際に読み書きする確認と、本物のモデルを流す確認

## 判定の API を足す例

拡張の文書の末尾に、`##` の節として足す。今の「ファイルごとの決まり」は 1 つのファイルの決まりを並べる節で、この例は 3 つのファイルと人の手順にまたがるためである。

節には、製品の名前と API の呼び方を書かない。呼び方は提供元ごとに違い、原本が特定の提供元を勧めることになるためである。例の場面は、リーダーが振り分けの前に判定を呼ぶ形にする。振り分けは、役が自分で呼ぶ判定の結果を参考にする場面として、最も分かりやすいためである。

足す節の全文は、次のとおりにする。

````markdown
## 判定の API を足す例

判定の API は、はい・いいえの確率や選択肢のような、型の決まった値だけを返す外部のサービスである。原本には入れず、使いたいプロジェクトが拡張で足す。この節は、その足し方を例で示す。

拡張で足せるのは、役が自分で呼ぶ判定である。判定の結果は、役への参考になる。

- 足せること: 役の指示に、いつ判定を呼び、結果をどう使うかを追記する。判定を呼ぶスクリプトも置く
- 足せないこと: 原本のスクリプトとガードに、判定を差し込むこと。役が呼び忘れても、ガードと次の工程の判断は判定を待たずに進む

### 置くファイル

置くファイルは、追記の指定、追記の指示、判定を呼ぶスクリプトの 3 つである。次の例は、リーダーが振り分けの前に判定を呼ぶ形である。

```text
extension/
  kit-version
  additions.json
  instructions/orchestrator.md
  monitor/squad-judge
```

`additions.json` は、追記のファイルだけを指す。

```json
{
  "orchestrator": {
    "instructions_file": "instructions/orchestrator.md"
  }
}
```

`instructions/orchestrator.md` には、判定をいつ呼び、結果をどう使うかを書く。判定を得られないときの進め方も書く。

```markdown
## 判定の API

依頼を振り分ける前に、`squad-judge <タスク>` を流す。出力の `判定:` の行を、振り分けの参考にする。判定に従わないときは、理由をタスクのコメントに 1 行で書く。

`squad-judge` が 0 以外で終わったときは、判定なしで振り分ける。鍵の値を、コメントやファイルに書かない。
```

`monitor/squad-judge` は、「`monitor`」の決まりに従って置く。鍵は環境変数から読み、スクリプトにも拡張のディレクトリにも書かない。

- 鍵の環境変数がないとき、API が応えないとき、時間切れのときは、0 以外で終える
- 判定の値は、標準出力に `判定:` で始まる 1 行で出す。鍵と、送った内容は出さない

### 鍵を渡す

鍵は、人間がエージェントの環境変数に置く。拡張には、環境変数を渡す口がない。`mcp_config` に鍵を書くと、拡張のディレクトリに鍵が残るので使わない。

置けるのは、エージェントの持ち主か、ワークスペースのオーナーか管理者である。判定を呼ぶ役ごとに、次の順に行う。

1. 今の環境変数を読み、`custom_env` の中身を新しい一時ファイルに保存する
2. エディタでファイルを開き、鍵のキーを 1 つ足す
3. ファイルの中身を、エージェントに反映する
4. ファイルを消す

次のコードブロックを、bash か zsh の 1 つのシェルに 1 行ずつ貼る。2 行目のあとに、`$env_file` のファイルをエディタで開いて鍵を足す。どこかの行が失敗したら、そこから先は最後の行だけを流す。

```bash
env_file=$(mktemp "${TMPDIR:-/tmp}/squad-custom-env.XXXXXX")
multica agent env get <エージェントの ID> --output json | jq '.custom_env' > "$env_file"
multica agent env set <エージェントの ID> --custom-env-file "$env_file"
rm -f "$env_file"
```

`mktemp` は、新しいファイルを所有者だけが読める権限で作り、前からある同名のファイルやリンクを使わない。最後の行を流すまで、ファイルには鍵が残る。途中でやめたときは、同じシェルで最後の行を流す。シェルを閉じたあとは、`ls "${TMPDIR:-/tmp}"/squad-custom-env.*` で探して消す。

> [!WARNING]
> `multica agent env set` は、環境変数の全体を置き換える。鍵だけを渡すと、セットアップが置いた値が消える。消したときは、同じプロジェクトでセットアップを流し直す。

- キーの名前は、プロジェクトで決める。例は `JUDGE_API_KEY` である
- セットアップは、流し直すたびに自分が置くキーだけを付け直し、ほかのキーを残す。足した鍵は、流し直しても消えない
- 手順 1 で読んだときにあるキーと、同じ名前は使わない。`PATH`・`HOME`・`SHELL`・`CODEX_HOME` などは、Multica が受け付けない
- 鍵を、拡張のディレクトリ、リポジトリ、タスクのコメントに置かない。コマンドの引数にも書かない

### 送る内容を決める

判定の API へ送る内容は、プロジェクトが決める。タスクのコメントや PR の内容を送ると、その内容は API の提供元へ渡る。

- 送ってよい内容と送らない内容を、追記の指示かスクリプトに書く
- 提供元の利用の条件と、送った内容の扱いを、使う前に確認する
````

### セットアップが置くキーを載せない

節には、セットアップが置くキーの一覧を載せない。代わりに、手順 1 で読んだときにあるキーと同じ名前を使わない、と書く。

セットアップが置くキーは、役によって 6〜12 個あり、バージョンを上げると変わることがある。一覧を節に写すと、セットアップのスクリプトと文書の 2 か所を合わせ続けることになる。セットアップは流すたびに自分のキーを置くので、手順 1 で読んだキーには、セットアップのキーがすべて入っている。

### 鍵の手順と警告

鍵の手順は、読む・足す・反映する・消すの 4 つにする。`multica agent env set` は、渡した中身で環境変数の全体を置き換える。このため、今の中身を読んでから 1 つ足す手順にし、警告で理由を示す。

鍵だけを渡す誤りをしても、セットアップを流し直すと、セットアップのキーは戻る。セットアップがほかのキーを残す動作は、`tests/project-environment-test.sh` が確認している。文書に書いたあとは、この動作を導入先への約束として扱う。

鍵を入れる一時ファイル（以下、鍵のファイル）で決めることは、下の 5 つの小節に置く。節の文は、ここで決めた約束する範囲を超えて言い切らない。

#### 入力と信頼

鍵のファイルは、同じマシンのほかの利用者に読ませない。同じ利用者のプロセスからは守らない。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 鍵のファイルのパス（1 行目で `mktemp` が返し、人間のシェルの変数 `env_file` に入る） | 保存・編集・反映・削除の行 | 同じシェルの 1 行目で `mktemp` が新しく作ったもの。手で書いたパスや、前の回のパスではない | 1 行目が失敗したら、最後の行だけを流し、1 行目からやり直す |
| 鍵のファイルの中身（`env get` の出力に、人間が鍵を 1 つ足したもの） | 反映の行（`env set`） | 人間がエディタで見て、手順 1 で読んだキーが残り、足したキーが 1 つだけである | 反映の行を流さず、最後の行を流して 1 行目からやり直す |
| 足す鍵の値（人間が提供元から受け取ったもの） | 人間がエディタで鍵のファイルに足す | 足すのは、エージェントの持ち主か、ワークスペースのオーナーか管理者である。コマンドの引数、コメント、リポジトリには書かない | その鍵を使わず、提供元で取り直す |

| 相手 | 扱い | 理由 |
| --- | --- | --- |
| 同じマシンのほかの利用者 | 読ませない。反映に渡すのは、所有者だけが読める新しいファイルにする | VM や共有のサーバーでは、ほかの利用者が同じディスクを読める |
| 同じ利用者のプロセスと管理者（root） | 守らない | 0600 のファイルも、エージェントの環境変数も読める。手順では防げない |
| エディタが作る控えのファイル、ディスクのバックアップ | 守らない | エディタの設定と、マシンの運用で決まり、原本の手順では決められない |

#### 流し方

手順は、人間が bash か zsh の対話シェルに、コードブロックを 1 行ずつ貼って流す。シェルは、`README.md` の「対応する範囲」にある標準の bash・zsh である。スクリプトにして流す使い方は、約束の外にする。

- 4 行を同じシェルで流す。あとの行が、1 行目の変数 `env_file` を使うため
- 鍵は、2 行目と 3 行目の間に、好きなエディタで足す。エディタは利用者ごとに違うので、コードブロックに入れない
- どこかの行が失敗したら、そこから先は最後の行だけを流す。反映が失敗しても、最後の行は流す
- コードブロックにコメントの行を置かない。zsh の対話シェルは、既定ではコメントを命令として読むため

#### 一時ファイルの置き場

鍵のファイルは、`mktemp "${TMPDIR:-/tmp}/squad-custom-env.XXXXXX"` で作る。`mktemp` は、テンプレートの名前で新しいファイルを作り、同名のファイルやリンクがあれば別の名前にする。権限は 0600 から umask で外した値で、umask が 022 か 077 なら 0600 になる。

置き場は `TMPDIR` を使い、なければ `/tmp` にする。macOS の `TMPDIR` は、利用者ごとの置き場である。macOS の引数なしの `mktemp` は `TMPDIR` を見ないので、テンプレートで置き場を明示する。これで、macOS と Linux で同じ規則になり、テストも `TMPDIR` で置き場を決められる。

名前の頭を `squad-custom-env.` に決めるのは、途中でやめた人間が、残ったファイルを探せるようにするためである。

#### 約束する範囲

約束するのは、反映に渡すファイルの権限と、最後の行まで流したあとに残らないことの 2 つである。途中でやめたあとの自動の削除は約束しない。

| 場面 | 約束 |
| --- | --- |
| 反映に渡すファイル | 1 行目で新しく作った 0600 のファイルで、umask が 022 か 077 なら、シェル（bash・zsh）によらない。前からある同名のファイルやリンクを使わず、変えない |
| 最後の行まで流したとき | 反映が成功しても失敗しても、鍵のファイルは残らない |
| 途中でやめたとき（Ctrl-C、端末を閉じる、シグナル、電源断） | 自動では消さない。文書に、同じシェルで最後の行を流すか、残ったファイルを探して消すと書く |

権限の約束は、確認する umask の 022 と 077 に限る。umask で 0600 より広がることはないが、0777 のような値では 0000 のように狭くなる。

この範囲では、途中でやめた鍵のファイルが、人間が消すまで 0600 で残る。そのあいだ、ほかの利用者は読めず、同じ利用者のプロセスは読める。Linux で `TMPDIR` がなければ、残る場所は `/tmp` である。`trap` で消す案を選ばなかった理由は、[検討した案](#検討した案)にある。

#### 確認の方法

約束する範囲は、表に沿ったテストで確認する。表の列は、約束する範囲を決める軸だけにする。

- 表は `tests/extensions-key-file-table.tsv` に置く。列は、行の名前・シェル・保存先の状態・umask・流れ・反映時の権限・既存の保存先・終了後の鍵・理由である
- シェルは bash と zsh、保存先の状態は、なし・既存の 0644・既存の 0600・0644 へのリンク・誰でも書ける一時の置き場である。umask は 022 と 077 にする
- 流れは、通常と反映の失敗の 2 つにする。通常は、シェル・保存先の状態・umask のすべての組を行に置き、組が欠けたらテストを落とす
- 反映の失敗は、シェルごとに、保存先の状態がなしと既存の 0644 の 2 行を置く
- 途中でやめたとき（中断）と、同じ場所での流し直しの行は置かない。中断は約束の外で、流し直しは既存の保存先の状態で足りるため
- テストは `tests/extensions-key-file-test.sh` に置き、`EXTENSIONS.md` の節のコードブロックをそのまま読む
- テストは、`multica` と `jq` を固定の JSON を返す関数に置き換え、実際の鍵と環境変数を使わない
- テストは、`TMPDIR` を検証の領域の中に向け、シェルの `-c` で `-e` を付けずに流す。前の行が失敗しても次の行が流れるので、人間が 1 行ずつ貼るのと同じ順に流れる
- テストは、コードブロックに `trap` がないことと、節に `squad-custom-env.` を探して消す案内があることも見る
- zsh がない環境では、`tests/install-command-test.sh` と同じく、zsh の行を飛ばしたと出力する

約束が `trap` やシグナルに頼らないので、擬似端末の対話シェルで流す確認は置かない。

## 公開されているスキルを足す例

拡張の文書の「プロジェクトのスキル」と「拡張から消したときの扱い」の間に、`###` の小節として足す。拡張でスキルを足す人が読む「プロジェクトのスキル」のすぐ後ろに置くと、置き方の決まりと例を続けて読めるためである。

例には、Anthropic が公開している `frontend-design` を、Claude の実装の役に足す形を使う。この小節は判定の API の節とは違い、配布元の名前を書く。どこから取得したものかが分かると、ライセンスと更新の確認先が分かるためである。原本は、スキルの中身も取得元の URL も持たない。

足す小節の全文は、次のとおりにする。

````markdown
### 公開されているスキルを足す例

配布元が公開しているスキルも、拡張の `skills` に置けば役に足せる。次は、Anthropic が公開している `frontend-design` を、Claude の実装の役に足す例である。

```text
extension/
  kit-version
  additions.json
  skills/frontend-design/SKILL.md
```

```json
{
  "claude-implementer": {
    "skills": ["frontend-design"]
  }
}
```

- スキルのファイルは、拡張を作る人が配布元から取得して `skills/frontend-design/` に置く。原本は中身と URL を持たない
- 配布元のライセンスの確認と、更新の取り込みは、拡張を持つプロジェクトが行う
- Multica の画面や CLI で役に手で割り当てたスキルは、セットアップの流し直しで外れる。残すスキルは `additions.json` に書く
````

3 つ目の項目は、今の文書にない注意である。セットアップは、役に割り当てたスキルの一覧が、原本と拡張から作った一覧と違えば、作った一覧で置き換える（`lib/project.sh`）。手で割り当てたスキルを残したい人が、流し直しのたびに割り当て直さないよう、ここに書く。

## 検証スキルのひな形

`skeleton/verify-repository.md` の節は増やさず、今ある 2 つの欄の記入の指示に 1 文ずつ足す。節の数は 8 のままにする。DB や画面のないリポジトリで、「対象外」と書く欄を増やさないためである。

| 欄 | 足す文 | 足す位置 |
| --- | --- | --- |
| サービスやデータを使う検証 | 「マイグレーションを変えたときに、使い捨ての DB で流すコマンドと成功の基準。」 | 「不要なら対象外」の前 |
| E2E と画面の確認 | 「画面を変えたときに撮る幅（PC とスマホ）と、その幅で撮る方法。」 | 「画面がなければ必要な E2E の方法を書く」の前 |

足したあとの 2 行は、次のとおりにする。

```text
[記入: 必要なサービスの起動、専用環境の名前・接続先の確認、テストデータの用意、他の作業へ影響を与えない方法。マイグレーションを変えたときに、使い捨ての DB で流すコマンドと成功の基準。不要なら対象外]
[記入: アプリの起動、使う利用者の役割、ログイン、操作に使う道具、受け入れ条件の確認の方法、スクリーンショットやログの保存と添付方法。画面を変えたときに撮る幅（PC とスマホ）と、その幅で撮る方法。画面がなければ必要な E2E の方法を書く。実施しないものは対象外]
```

セットアップは、登録済みの検証スキルを書き換えない。このため、導入済みのプロジェクトの検証スキルは、担当が取り入れるまで変わらない。

## 作業別のルールのひな形

DB と画面のルールのひな形を、`skeleton/.agents/rules/` に 2 つ足す。名前は `database.md` と `ui.md` にする。今の `code.md`・`tests.md`・`docs.md` と同じく、作業の対象を表す英語の 1 語にそろえる。

今の 3 つのひな形は記入の指示だけだが、新しい 2 つには箇条書きで記入の例を置く。DB と画面の決まりは、プロジェクトによらず同じものが多く、例があると記入が速いためである。例であることと、合わない行を消すことは、ファイルの冒頭に書く。

### DB を変える作業

全文は、次のとおりにする。

```markdown

## 変えてよいものと順序

- 出荷済みのマイグレーションは書き換えません。直すときは、新しいマイグレーションを足します
- 新旧のアプリが同時に動く間も壊れない順で変えます。列の削除と名前の変更は、古いアプリが止まったあとのリリースに分けます
- 本番や共有の DB には接続しません。流す前に接続先を確認します
```

合意のときに仮で足した 2 文は、残す。「直すときは、新しいマイグレーションを足します」と「列の削除と名前の変更は、古いアプリが止まったあとのリリースに分けます」である。

## 確認

例の拡張が通ることは、実装のときに拡張を確認するスクリプト（`lib/extensions.py`）で確認する。テストに例の拡張を足すことはしない。例は文書の一部で、拡張の決まりそのものは `tests/extensions-test.sh` が確認しているためである。

鍵を渡す手順だけは、表に沿ったテストを足す。鍵のファイルの約束は、文書を直すたびに崩れうるためである。表とテストの中身は、[確認の方法](#確認の方法)に書く。

| 確認すること | 方法 |
| --- | --- |
| 判定の API の例の拡張が通り、リーダーの指示の末尾に追記が足される | 節の 4 つのファイルを置いた拡張を、`lib/extensions.py` の `materialize` に渡す |
| 公開されているスキルの例の拡張が通り、実装の役のスキルに `frontend-design` が足される | 節の 3 つのファイルと、仮の `SKILL.md` を置いた拡張を、同じく渡す |
| ひな形と拡張のテストが、今のまま通る | ひな形を読むテストと、拡張のテストを流す |
| 鍵を渡す手順が、約束する範囲を満たす | `tests/extensions-key-file-test.sh` を流し、`tests/extensions-key-file-table.tsv` のすべての行が bash と zsh で通る |
| 文書の書き方・リンク・用語の検査が通る | `tests/style-test.sh`・`tests/links-test.sh`・`tests/terms-test.sh` を流す |

`additions.json` に `custom_env` のキーを書くと、拡張を確認するスクリプトが止まる。節が `mcp_config` に鍵を書かないと書くのは、`mcp_config` は止まらずに通るためである。

## 互換性と影響を受ける利用者

導入済みのプロジェクトの動作は変わらない。セットアップは、登録済みの検証スキルとリポジトリのルールを書き換えず、作業別のルールのひな形を写さないためである。役の指示と共通スキルも変えない。

影響を受けるのは、次の 2 者である。

- 拡張を作る人。判定の API と公開されているスキルの足し方を、コードを読まずに文書で知れる
- 新しく導入するプロジェクトの担当。検証スキルの 2 つの欄で記入を促す項目が増え、DB と画面のルールのひな形を使える

## 検討した案

足し方について、次の案を選ばなかった。

| 案 | 選ばなかった理由 |
| --- | --- |
| キーを 1 つだけ足す補助のコマンドを原本に足す | 使う導入先がまだないのに、鍵を扱うコードとテストを原本が持つ。誤っても、流し直しで戻る |
| 判定の API の節を「ファイルごとの決まり」の小節にする | 3 つのファイルと人の手順にまたがり、1 つのファイルの決まりではない |
| 節にセットアップが置くキーの一覧を載せる | 役ごと・バージョンごとに変わり、スクリプトと文書の 2 か所を合わせ続けることになる |
| 検証スキルのひな形に節を 2 つ新しく作る | 今ある節と中身が重なる。DB や画面のないリポジトリが「対象外」を 2 回多く書く |
| 記入の例を `code.md` の中に置く | DB や画面のないリポジトリにも例が入り、消す手間が増える |
| DB の例から仮の 2 文を外す | 書き換えを禁じたあとの直し方と、「壊れない順」の具体が分からなくなる |
| 公開されているスキルの例でも配布元の名前を伏せる | 取得元が分からないと、ライセンスと更新の確認先が分からない |
| 鍵の手順に `trap` を補助として残す | 端末を閉じたときに消える利点はあるが、同じシェルで流し直した前のファイルが残り、利用者の EXIT の `trap` を置き換える。確認に擬似端末も要る |
| 鍵のファイルを使わず、`--custom-env-stdin` で渡す | 人間が中身を見ずに、環境変数の全体を置き換える。空の入力を渡したときの `env set` の動作も確認していない |
