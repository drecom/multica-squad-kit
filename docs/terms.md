# 用語をそろえる

原本の文書・役の指示・共通スキル・ひな形・画面に出す文・コメントとテストで、同じものを同じ語で書く。この文書は、原本を変える人に向けて、使う語と迷う語の決め方を書く。変えないもの、導入済みの環境との互換性、確認の方法も書く。

語の正本はこの文書にする。役の指示や共通スキルに用語集を写さず、それぞれの文の中で、この文書で決めた語を使う。持ち主とオーナーの違いは役が読む共通スキル `squad-handoff` に、原本と正本の違いは原本を変える人が読む `CONTRIBUTING.md` に書く（[違いを書く場所](#違いを書く場所)）。

## 目的と範囲

目的は、意味ごとに語を一つに決め、同じものを同じ語で書いて、読み手と役が取り違えないようにすることである。語を決めないと、同じものを指す語が文書ごとに違い、一つの語が別の意味にも使われる。たとえば、Multica の `issue` を次の 3 通りで書けてしまう。

- 「タスク」
- 置き換える語（`U+8AB2 U+984C`）
- 英語のままの `issue`

設計を実装に分けた単位、sub-issue の順番、処理の手順の 1 つを、同じ 1 字（`U+6BB5`）で書くことも同じである。

見て正しいかを判断する意味の語も、「確認」と、`U+78BA U+304B U+3081` で始まる語の 2 通りで書けてしまう。役の指示とスクリプトが読む行の名前にも、後者が入りうる。この語は確認にそろえ、文に合わなければ検証か照合にする。

対象は、リポジトリで管理する日本語の文のすべてである。

- 利用者向けの文書（`README.md`、`manual.md`、`CONTRIBUTING.md`、`EXTENSIONS.md`）と `docs/`
- 役の指示と `FORMAT`、スクワッドとオートパイロットの指示、共通スキルとラベルの説明、セットアップが起票するタスクの題と本文
- ひな形（`skeleton/`）と、このリポジトリの `AGENTS.md` と `.agents/rules/`
- セットアップ・見張り・ガード・VM のスクリプトが画面に出す文と、コードのコメント
- テストの名前と、テストが期待する文、テストの場面の入力（`tests/leader-eval/scenes/` など）
- `CHANGELOG.md` の過去の節を含むすべての節

次は対象にしない。

- 公開済みの Release の本文とタグ。動かさない決まり（[タグと Release を出す](../CONTRIBUTING.md#タグと-release-を出す)）を保つ
  - 過去の Release の本文は、`CHANGELOG.md` の節と語が食い違うことがある
- 外部の CLI・API の名前と、外から受け取る値（[変えないもの](#変えないもの)）
- 英語の識別子とファイル名
- バージョンを上げる PR（`VERSION` の書き換え）
- 導入先で人間が記入したもの（[書き換えないもの](#書き換えないもの)）

## 語の対応

意味ごとに、書く語を一つにする。置き換える前の語は、リポジトリに残さないため、この文書でもコードポイントで書く。`printf '\u7248\n'` のように端末で文字に戻せる。

| 意味 | 書く語 | 置き換える語 |
| --- | --- | --- |
| 配るもののバージョン、道具のバージョン | バージョン | `U+7248` |
| PR の本文を最初に作ったもの（`squad-handoff`、PR の本文） | 最初の本文 | `U+521D U+7248` |
| 最初に出したバージョン（`CHANGELOG.md`） | 最初のバージョン | `U+521D U+7248` |
| 古いバージョンで配った指示 | 古いバージョンの指示 | `U+65E7 U+7248` の指示 |
| 設計を実装に分けた単位 | フェーズ | `U+6BB5` |
| 修正の役が 1 回の依頼で受ける作業 | フェーズ（実装の役と同じ書き方） | 同じ `U+6BB5` の中で |
| sub-issue の順番（`--stage` で付けるもの） | ステージ | `U+6BB5`、`U+6BB5 U+968E` |
| 処理の手順の 1 つ（失敗した手順、進めない手順など） | 手順 | `U+6BB5` |
| Multica の `issue` | タスク | `U+8AB2 U+984C`、文中の `issue` |
| GitHub の `issue` | GitHub の issue | `issue` |
| スクワッドのリーダーの役 | リーダー | 進行の後に役を付けた語、進行の後に「の役」「の担当」を付けた語、役の名前としての進行 |
| AI の使用の上限 | 使用上限、使用率 | AI の後に「の残量」を付けた語は「AI の使用上限」にする |
| 見て正しいかを判断すること | 確認。文に合わなければ検証か照合（[確認・検証・照合の決め方](#確認検証照合の決め方)） | `U+78BA U+304B U+3081` で始まる語 |
| 目で見つけるための記号、ラベルや表示の記号、条件を表す記号（目印の語を除く） | マーク。合成語もマーク（役のマーク、完了のマーク、マーク付き） | `U+5370` |
| ラベル `重要` を指すマーク、レビューと QA の結果の行の ❌・⚠️・✅ | 重要のマーク、結果のマーク（[重要のマークと結果のマーク](#重要のマークと結果のマーク)） | 同じ `U+5370` の中で |
| 設計の役がフェーズごとに書く、作業の量の語 | 見積もり。値は `小さい`・`大きい`（[フェーズの見積もり](#フェーズの見積もり)） | 「フェーズの `U+5927 U+304D U+3055`」、値の `U+5C0F U+3055 U+306A`・`U+5927 U+304D U+306A` |
| 許可していないリポジトリへの `gh` の書き込みと `git push` を、エージェントの実行で止める仕組み | ガード（[ガード](#ガード)）。仕組みでない確認は、確認・判定・決まりなど | `U+95A2 U+6240` |

次の語は、意味が違うので残す。

| 語 | 意味 |
| --- | --- |
| 段落、普段、入れ子の深さ（1 段まで、一段下げる） | 文の区切り、ふだん、箇条書きと見出しの深さ |
| 工程 | タスクの中の次の仕事 |
| 進行（作業の進行、進行の記録など） | 作業が進むこと。役の名前ではない |
| 利用枠 | その人が提供する AI の契約の枠 |
| 持ち主とオーナー | [違いを書く場所](#違いを書く場所)で分ける |
| 原本と正本 | [違いを書く場所](#違いを書く場所)で分ける |
| `U+78BA U+304B` の後に `U+3081` が続かない語（確かに、確かな） | 間違いないこと。判断する動作ではない |
| 目印 | 見つけるための手がかり。手順の跡、メンバーの区別（目印の文、前回の目印） |
| 印字 | 表示できる文字（印字できる ASCII） |
| 矢印 | 画面の記号の「→」（矢印の行） |

### 重要のマークと結果のマーク

ラベル `重要` を指すマークと、結果の行の ❌・⚠️・✅ が同じ文書に出るときは、「重要のマーク」と「結果のマーク」で呼び分ける。片方だけが出る文書では、呼び分けなくてよい。ただし、ラベル `重要` を指すときは、文書によらず「重要のマーク」を使うと取り違えにくい。

「目印」「印字」「矢印」のほかに、`U+5370` を含む語はリポジトリに残さない。置き換えた語の検査（`tests/check-terms.py`）の対象に入れず、作業の最後に検索して確認する。

### フェーズの見積もり

設計の役がフェーズごとに書く語は、「見積もり」と、値の `小さい`・`大きい` にする。値はいつもバッククォートで囲み、「見積もり」と並べて、「見積もりが `小さい` のフェーズ」のように書く。

`squad-dispatch-pick` は `小さい` のときだけ小さいとして選び、ほかの値と省略は `大きい` として扱う。`squad-usage-wait pick` は、`小さい`・`大きい`・空だけを受け付ける。

[作業の時間の内訳](time-breakdown.md)の区分「小さい実装」は、実績の秒で決まる別のものである。集計の区分にだけ使い、バッククォートで囲まない。「小さいフェーズ」「大きいフェーズ」とは書かない。

決まった語でない「大きさ」「小さな」「大きな」は変えない。端末の大きさ、引数の大きさ、大きな JSON のような普通の言い方である。

### ガード

ガードは、エージェントの実行で、許可していないリポジトリへの `gh` の書き込みと `git push` を止める仕組みである。ホストの `gh` の代わりの実行ファイルと、`pre-push` の hook の 2 つからなる（[エージェントの実行で選ぶ仕組み](agent-path.md)）。動作は変えず、語と画面に出す文だけを変える。

置き換える前の語（`U+95A2 U+6240`）は、この仕組みのほかの意味にも使われていた。意味ごとに、次の語にする。

| 使っていた意味 | 書く語 | 例 |
| --- | --- | --- |
| 上の仕組み。`common/guard/` の 2 つと、それを置くディレクトリ | ガード | `gh` のガード、ガードのディレクトリ、既存のガードの確認 |
| 書き込みを止める安全の仕組みの総称。認証・権限・秘密の情報と並べるもの、役が越えない決まり、手順の見直しの分類 | ガード | 認証・権限・秘密の情報・ガード、ガードを越えない |
| 標準入力が端末かを見る確認（`docs/terminal-tests.md`、`tests/questions-ui-test.sh`） | 端末の確認 | 標準入力の端末の確認 |
| 書き漏れや誤りを止める、公開の前やレビューの確認（`docs/terminal-tests.md`、`docs/usage-answer.md`、`docs/procedure-review.md`） | 確認、判定、決まり | 公開の前の確認、人間を呼ぶかどうかの判定 |

手順の見直しの分類の値 `gate` は英語の識別子なので変えない。表の 3 行目と 4 行目は仕組みを指さないので、ガードにすると読み手が取り違える。

#### 画面に出す文と、それを読むところ

拒否の文の頭は、`gh のガード:` と `git push のガード:` にする。頭を読むところは次の 3 つで、同じ変更で新しい頭だけを読むようにする。

| 読むところ | 読み方 |
| --- | --- |
| セットアップの確認（`lib/host.sh` の `host_check_guards`） | 空の許可で流した拒否の標準エラーが、頭で始まる行を持つか |
| `squad-handoff` の「人間に操作を頼む前に」の表 | 標準エラーが `gh のガード:` で始まる失敗を、ガードに止められたものとして分ける |
| テスト（`tests/gh-test.sh`、`tests/pre-push-test.sh`） | 拒否の文が頭で始まるか |

ほかに画面に出す文は、次のとおりにする。どれも、文の中の語だけを変える。

- セットアップが表示する `使用する gh のガード:` と `使用する git push のガード:` の行。`tests/host-test.sh` が照合する
- `squad-handoff` と見張りの役の指示が報告に使う「ガードのディレクトリが PATH にありません」
- `squad-preflight` の「ガードの gh と、すべての見張りが使えます」。`tests/leader-eval/` の場面の入力も同じ文にする
- `lib/host.sh` が、ガードを使えないときや確認に失敗したときに出して止まる文（「ガードの確認に失敗しました」など）。`tests/project-failure-test.sh`、`tests/guard-check-test.sh`、`tests/host-test.sh` が照合する

拒否を確認できなかったときの文には、頭が違う場合を分ける文を 1 つ足す（[頭が違うガードの直し方](#頭が違うガードの直し方)）。ほかの文は、語のほかを変えない。

#### 見出しの変更

置き換える語を含む見出しは 2 つある。[迷う語の決め方](#迷う語の決め方)のとおり、見出しと参照を同じ変更で直す。

| 文書 | 新しい見出し | 同じ変更で直す参照 |
| --- | --- | --- |
| `manual.md` の「既存の」で始まる節 | 既存のガードの確認 | `manual.md` の流れの図の節点、`lib/host.sh` がセットアップの止まりで出す案内の 3 つの文 |
| `docs/agent-path.md` の題 | エージェントの実行でガードと見張りを PATH から選ぶ | `manual.md` からのリンクの文 |

#### 頭が違うガードの直し方

前の頭で拒否するガードを置いたホストでは、セットアップが止まる（[ガードの頭と流し直し](#ガードの頭と流し直し)）。管理者が原因にたどり着けるよう、画面に頭が違うことを出し、「既存のガードの確認」に直し方を足す。

止まるのは、マークのないガードだけである。マークのあるガードは、確認の前のホストの準備で新しいものに置き換わる。

`host_check_guards` は、空の許可で拒否を確認できなかったとき、拒否の標準エラーの頭を見て、頭が違う場合を分けて出す。

| 場合 | 見分ける条件 | 出す文 |
| --- | --- | --- |
| 頭が違う | コマンドが 0 以外で終わり、標準出力が空で、標準エラーに行があるが新しい頭で始まる行がない | 「gh の拒否の文が `gh のガード:` で始まりません。前のバージョンのガードか、マークのないガードです」。pre-push も同じ形にする |
| それ以外 | 上に当たらない | 今の文のまま |

どちらの場合も、今と同じく拒否の標準エラーをそのまま表示し、「既存のガードの確認」を案内して止まる。頭の読み分けは表示の文を選ぶだけで、拒否と数える条件は変えない。

「既存のガードの確認」には、次の見分け方と直し方を 1 段落と番号付きの手順で足す。見分け方は、頭が違う文が出たことと、表示した標準エラーの頭が新しい頭でないことである。

1. 同居するすべてのプロジェクトの管理者と合意し、どのプロジェクトでも動いているタスクがないことを確認する
2. マークのない `gh` と `pre-push` を、消すか、ガードのディレクトリの外へ移す。マークを足して通すことはしない
3. 同じセットアップを流し直す。セットアップが、マークのある新しいガードを置いて確認する
4. 同居するほかのプロジェクトも、同じバージョンで流し直す

自分で作ったガードを使い続けるときは、2 で片付けずに、拒否の文の頭を新しい頭に直す。`SQUAD_KIT_ALLOWED_REPOS` を読むことなど、今の節の決まりはそのまま守る。

#### 説明の文を添える文書

人間と役が読む文書では、その文書でガードを初めて使う所に、何を止めるかの 1 文を添える。初めて使う所が表か箇条書きなら、その直前の段落に添える。文は次の言い回しにし、文書の前後に合わせて、つなぎだけを変えてよい。

> ガードは、エージェントの実行で、許可していないリポジトリへの `gh` の書き込みと `git push` を止める仕組みである。

| 文書 | 添える所 | 選んだ理由 |
| --- | --- | --- |
| `docs/terms.md` | 語の対応の表の意味の欄と、この節の最初の段落 | 語の正本 |
| `manual.md` | 「受け取る人の準備」の、道具の表の直前の段落 | 導入と運用をする人が最初に読む |
| `squad-handoff` | 「実行の始めの確認」の、PATH の報告の文の前 | すべての役が実行ごとに読む |
| `README.md` | 最初の段落 | 原本を初めて見る人の入口 |
| `CONTRIBUTING.md` | 「判定と人間に示す一覧」の表の直前の段落 | 原本を変える人の入口 |
| `EXTENSIONS.md` | 「決まりの要約」の段落 | 拡張を作る人の入口 |
| `docs/agent-path.md` | 題の直後の段落 | ガードそのものの設計 |

表の 7 つの文書のほかに、`CHANGELOG.md` の次のバージョンの節にも同じ 1 文を置く。導入済みのプロジェクトを更新する人が、語の変更を知る所だからである（下の「CHANGELOG.md に書く内容」の 1 番目の項目）。

次には添えない。

- 役の指示と `common/autopilots.md`。役は同じ実行で `squad-handoff` を読むので、そこで説明が届く
- `AGENTS.md`、`leader-flow.md`、最上位の役・設計の役・security-reviewer の指示にある語の並び。語を並べるだけの文である
- `common/setup-issues.json` の本文。止めるものを文そのものが書いている
- `CHANGELOG.md` の過去の節。次のバージョンの節で語の変更を説明する
- 上の表にない `docs/` の文書。読み手は `manual.md` か、この文書から来る
- スクリプトの出力とコメント、テストの入力と名前

## 迷う語の決め方

一つの語が複数の意味で使われているものは、文の意味から次のとおり決める。

- `U+6BB5` は、設計を実装に分けた単位ならフェーズ、sub-issue の順番ならステージ、処理の流れの 1 つなら手順にする。段落・普段・入れ子の深さだけ残す
  - ほかの語の一部として入るもの（ひな形の「E2E の」の後の語など）は、別の語（「方法」など）に言い換える
- `squad-handoff` の「完了した範囲」と「経緯」に付いている `U+6BB5` は、実装のフェーズを指すので、フェーズにする
- 文中で Multica の `issue` を指す `issue` は、タスクにする。`multica issue` のコマンド、CLI のフラグ（`--stage` など）、JSON のキー、`sub-issue` は英語の識別子なので残す
- GitHub の `issue` は「GitHub の issue」と書く。`issue` だけでは Multica のタスクと読み分けられないため
- 役の名前としての進行はリーダーにする。見出しの「開発の」の後の語も同じにする
  - 作業が進む意味の「進行」は残す
- 原本は、この配布するキット（`multica-squad-kit` とそのファイル）だけを指す。決まりや情報の拠り所になる一つの場所は、正本と書く
  - `squad-handoff` の「原本がある情報」と「原本へのリンク」は、正本にする
- 使用上限と使用率を使う。外から受け取る値は変えない

置き換える語を含む見出しを書き換えるときは、見出しを変えたら、リンク・節の名前の引用・コードのコメントの参照を、同じ変更でリポジトリ全体から直す。見出しより先に参照だけを変えない。

### 確認・検証・照合の決め方

`U+78BA U+304B U+3081` で始まる語は、確認にするのを基本にする。次の 2 つに当たるときだけ、検証か照合にする。語を選んだら、活用は下の表のとおりにする。

| 書く語 | 使うところ | 例 |
| --- | --- | --- |
| 検証 | 決まった手順で正しさを判定し、通るか止まるかが出るもの。証明・チェックサム・署名・配布物の一覧・入口の `--verify` | 配布物の検証、検証が通りました、展開の前の検証 |
| 照合 | 決まった値と突き合わせて、一致を見るもの。依頼の SHA、記録の文、`MANIFEST` の一覧 | 返ってきたコミットを依頼と照合する |
| 確認 | 上の 2 つに当たらないものすべて。見て判断する、読んで状態を知る、動くことを見る | 受け取ったら最初に確認すること、実機で確認する |

役の指示と `squad-handoff` では、検証の語は検証スキルとテストを流すことを指している。そこでは、手順で判定するものでも、検証スキルと読み違えるおそれがあれば確認にする。

| 置き換える語の形 | 書く形 |
| --- | --- |
| `U+78BA U+304B U+3081 U+308B`、`U+78BA U+304B U+3081 U+305F`、`U+78BA U+304B U+3081 U+3066` | 確認する、確認した、確認して（検証・照合も同じ） |
| 「られない」「られる」を付けた形 | 確認できない、確認できる |
| 「直す」を付けた形 | 確認し直す |
| `U+78BA U+304B U+3081` だけの名詞の形 | 確認（「公開の前の」の後なら検証） |
| `U+78BA U+304B U+3081 U+65B9` | 確認の方法、検証の方法 |

置き換えたあとに「確認を確認する」のように同じ語が重なるときは、片方を「見る」「読み直す」などに言い換える。英語の `verify`・`check` などの識別子は変えない。

## 変えないもの

外から来る値と、名前で照合する登録は変えない。変えると、外の動作と合わなくなるか、導入済みの登録を見つけられなくなるため。

- 外部の CLI と API の名前と値。`multica issue`・`gh issue`・`--stage`・`sub-issue`・Multica の画面の英語の文言（「After PRs merge, move the issue to」など）
- 外から受け取って表示する値。たとえば、Multica の実行の失敗の理由（`squad-review-wait` が表示する「利用上限」など）
- 英語の識別子とファイル名。metadata のキー（`squad_kit_task`、`repository` など）、役のキー、スクリプトとスキルの名前
- フェーズの見積もりの値（`小さい`、`大きい`）。`squad-dispatch-pick` の引数として渡すため
- 見張りが書いて、あとで照合する記録のマーク。`squad-review-wait` の `返事を待つ役:`、`返事がそろいました` などは、置き換える語を含まないので、そのままにする

役が書き、リーダーと見張りが読む固定の行名のうち、置き換える語を含む 3 つは、[固定の行名](#固定の行名)に書く。

## 登録済みの名前と互換性

Multica に登録する名前には、置き換える語が入っていない。そのため、導入済みの状態から更新を流しても、名前で照合する登録は同じものを見つけ、重複も取り残しも出ない。更新が書き換えるのは、同じ登録の説明と指示の中身だけである。

| 登録 | 名前 | 照合と更新 | 更新で書き換えるもの |
| --- | --- | --- | --- |
| エージェント | `<p>-<role>-<m>`（英語） | 名前で探し、`multica agent update` で説明と指示を書き換える | 説明と指示 |
| スクワッド | `<P>-<M>`（英大文字） | 名前で探し、指示を書き換える | 指示 |
| 共通スキル・検証スキル | `squad-handoff`、`<p>-verify` | 名前で探し、中身を書き換える | 中身 |
| オートパイロット | 「週 1 回の依存ライブラリの脆弱性チェック …」「Dependabot の PR の週次の確認 …」「使用上限の見張り …」 | 題で探し、説明と指示を書き換える | 説明と指示 |
| ラベル | 開発、運用、検証、指示の改善 | 名前で探し、`multica label update` で説明を書き換える | 説明 |
| Webhook のトリガー | 「プロジェクトの拡張」「Dependabot の PR」 | 名前で探す | なし |
| セットアップが起票するタスク | `common/setup-issues.json` の 10 種の題 | metadata の `squad_kit_task` と `squad_kit_targets` で探す。マークのない古いタスクだけ題で探す | 新しく作るタスクの本文 |
| 使用上限の見張りのタスク | 「[使用上限] …」 | 手元の状態ファイルのタスクの ID で探す | なし |
| Dependabot の PR を人間に回すタスク | 「Dependabot の PR を確認する: …」 | 題の末尾で探す | なし |

エージェントの説明は、`FORMAT` の `description` を写す。説明の文が変わっても、名前で見つけて書き換えるので、新しいエージェントは作らない。

起票済みのタスクの本文は書き換えない。セットアップは、対象を足したときに本文の末尾へ追記するだけで、そのときも同じ追記がすでにあるかを確認する。追記の途中で止まったあとに、言い回しの違うバージョンで流し直すと、言い回しの違う追記が 1 つ増えることがある。読む人が困らないので、この場合は防がない。

### 見張りがあとで照合する記録

`squad-pr-watch` は、リーダーが保留した CI の失敗を引き継ぎで受けたことを、タスクに `/note` の記録で残す。あとでその文と一致するかを見て、同じ失敗を重ねて知らせないようにしている。

記録の文は「CI <短い SHA>: 保留した失敗をリーダーが引き継ぎで受けた」である。照合は、決まった一つの文との一致でなく、`/note` の次の行が「CI <短い SHA>: 保留した失敗を」で始まり「が引き継ぎで受けた」で終わる記録を受け入れる。

役の名前の語が違う古い記録も、新しい記録も一致し、置き換える前の語をコードに残さずにすむ。照合の前提は、エージェントが書いた記録で、同じ SHA であることである。

照合しない記録（「CI <短い SHA>: 失敗をリーダーに知らせた」）と、起こす指示の文は、新しい語で書く。登録済みの起こす指示に残る古い語は、役が読む文で、同じ役を指すと分かるので、書き換えない。

見張りのスクリプトは、ホストでセットアップを流し直すまで更新されない（[manual.md の更新](../manual.md#更新と途中で止まったあとの再実行)）。複数のホストで、古いスクリプトと新しいスクリプトが同じタスクを扱うと、古いスクリプトは新しい記録を照合できず、保留した失敗を 1 回重ねて知らせることがある。役が同じ失敗をもう一度受けるだけで、作業は壊れないので、ホストごとに流し直すことで足りるとする。

### 固定の行名

役が決まった形で書き、リーダーと見張りが行の頭で読む行名のうち、置き換える語を含む 3 つは、次の行名にする。行名の後ろの値は、完全な SHA、`なし` と理由、1 件 1 行の結果である。

| 置き換える行名 | 書く行名 | 書くもの | 読むもの |
| --- | --- | --- | --- |
| `U+78BA U+304B U+3081 U+308B` の後に `コミット:` | `確認するコミット:` | リーダー。レビュー・E2E・最上位の役への依頼（`leader-review-wait.md`、`leader-principal.md`） | レビューの 4 役、QA、最上位の役。`squad-handoff` の「レビューと E2E の返事を返す」と、役の指示 |
| `U+78BA U+304B U+3081 U+305F` の後に `コミット:` | `確認したコミット:` | レビューの 4 役、QA、最上位の役の結果。`squad-review-wait report` が `/note` で投稿する | リーダーの照合（`leader-review-wait.md` の照合の節、`leader-principal.md`）と、`squad-pr-watch` の `ci-check` |
| `U+78BA U+304B U+3081 U+305F` の後に `こと:` | `確認したこと:` | 引き継ぐすべての役。`squad-handoff` の「引き継ぐとき」の 3 番目の項目 | リーダーと人間。スクリプトは読まない |

古い行名は受け付けない。リーダーの手順、役の指示、`squad-pr-watch` は、書く行名だけを読む。古い行名を一致の候補に残すと、置き換える前の語がコードと指示に残り、受け付けるのをやめる時機も決めることになるため（[検討した案](#検討した案)）。古い行名の行は、行がないものとして扱う。

| 古い行名が来たとき | 起きること |
| --- | --- |
| リーダーが、結果に `確認したコミット:` の行を見つけられない | 今の決まりの「行がない」に当たり、同じコミットの新しい回でその役だけを頼み直す。2 回続けば人間を呼ぶ |
| 役が、依頼に `確認するコミット:` の行を見つけられない | 今の決まりの「指定がなければ PR の head」を使う。head が依頼と違えば、リーダーの照合で頼み直しになる |
| `squad-pr-watch` が、レビューの報告を引き継ぎと数えない | 報告した役の実行が動いている間は、CI の失敗を作業中として保留する。実行が終われば、ふだんの知らせに進む |

`squad-pr-watch` は、`/note` の次の行が `確認したコミット:` で始まるかで、レビューの報告を引き継ぎと数える。照合の前提は、その実行を起こした役が書いたコメントで、同じ実行のものであることである。メンションによる引き継ぎは、別に判定する。

リーダーが書き、あとで読む行名もある。`重要のマーク:` は、ラベル `重要` を付けたか、人間が付けたマークを確認したかを残す。

| 行名 | 書くもの | 読むもの |
| --- | --- | --- |
| `重要のマーク:` | リーダー。タスクにラベル `重要` を付けたとき、または人間が付けたマークを確認したとき | リーダーの手順。security-reviewer に頼むかの判断、手戻りの記録、設計の役の基準の確認 |

旧い行名（`U+91CD U+8981 U+306E U+5370 U+003A`）の行は、互換として読まない。行がないものとして扱う。スクリプトは、この行を読まずにラベルを読む。

### 書き換えないもの

プロジェクトの説明は、セットアップが空のときだけ書く。導入先のリポジトリの `AGENTS.md`、作業別のルール、検証スキルは、人間がひな形から記入する。どちらも更新で書き換えないので、古い語が残る。古い語でも同じものを指すと読めるので、セットアップでは直さず、新しい語にそろえたい人が手で直す。

起票済みのタスクの本文も書き換えない。人間が記入したものに古い行名が残っていても、役は固定の行名を指示と `squad-handoff` から読むので、動作は変わらない。

共通スキルはワークスペースで共有するので、プロジェクトごとに取り出したタグが違うと、共通スキルと役の指示の語が一時的に食い違う。どちらも同じ役とタスクを指すと分かる語なので、動作は変わらない。ただし固定の行名は、食い違うと照合が合わないので、すべてのホストとプロジェクトで一度に流し直す。

### ガードの頭と流し直し

ガードの拒否の頭は、新しい頭だけを受け付ける。前の頭を一致の候補に残すと、置き換える前の語がコードに残り、受け付けるのをやめる時機も決めることになるため（[検討した案](#検討した案)）。[固定の行名](#固定の行名)と同じ扱いである。

登録の名前には置き換える語が入っていないので、流し直してもエージェント・オートパイロット・ラベル・スキル・起票するタスクの題は変わらない。流し直しが書き換えるのは、置き場所ごとに次のものである。

| 置き場所 | 共有する範囲 | 流し直しで変わるもの |
| --- | --- | --- |
| ホスト | 同じホストのすべてのプロジェクト | 管理のマークのあるガード、`squad-preflight` と見張り、シェルの起動ファイル |
| ワークスペース | 同じワークスペースのすべてのプロジェクト | 共通スキル `squad-handoff` |
| プロジェクト | そのプロジェクト | 役の指示とスクワッドの指示 |

このため、一部だけを流し直すと、ガードが出す頭と `squad-handoff` が期待する頭が食い違うことがある。

| 流し直していないところ | 起きること |
| --- | --- |
| 同じホストで、別のワークスペースのプロジェクト | ガードは新しい頭を出すが、そのワークスペースの `squad-handoff` は前の頭を期待する。役は、ガードに止められた失敗を権限など別の理由と読み違えることがある |
| 同じワークスペースで、別のホスト | `squad-handoff` は新しい頭を期待するが、そのホストのガードは前の頭を出す。読み違えは上と同じである |
| 古いバージョンで流し直したホスト | 管理のマークのあるガードが前のものに戻る。上の行と同じになる |
| 管理のマークのないガードを置いたホスト | セットアップの確認が拒否を新しい頭で見分けられず、頭が違う文を出して止まる。止まるのはホストの準備と共通スキルの更新のあとなので、置き換えるまで 2 行目と同じ読み違えが続く |

読み違えても、ガードは書き込みを止め続ける。拒否の文の本文と、ガードを避けない決まりは前の指示にもあるので、役がガードを避ける動作にはならない。それでも、すべてのホストとプロジェクトを、同じバージョンで一度に流し直すよう案内する。同じホストの別のプロジェクトで、流し直しの前に動いているタスクがないことも確認してもらう。

#### CHANGELOG.md に書く内容

`CHANGELOG.md` の「次のバージョン」の節に、今ある段落とは別の段落で、次の 5 つを書く。置き換える前の語は書かず、この文書の語の対応の表を示す。

1. 語の変更。書き込みを止める仕組みの語をガードにしたこと、ガードが何を止めるかの 1 文、置き換える前の語は `docs/terms.md` の語の対応の表にあること
2. 拒否の頭の変更。`gh のガード:` と `git push のガード:` で始まるので、標準エラーの頭で拒否を見分けている人は読み方を変えること
3. 流し直していない導入先への影響。上の表の 4 つの行を、それぞれ 1 文で書く
4. 流し直しの案内。各ホストのマークのないガードを `manual.md` の「既存のガードの確認」に従って先に置き換え、そのあとすべてのホストとプロジェクトを同じバージョンで一度に流し直すこと
5. 登録。エージェントとオートパイロットの登録は変わらないこと

#### 入力と信頼の表

ガードの頭と、始めの確認の結果を読むところで、何を信頼するかを次のとおりにする。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 拒否の標準エラーの頭 `gh のガード:`・`git push のガード:`。マークのあるガードはセットアップが置き、マークのないガードは人が置く | セットアップの `host_check_guards` の拒否の確認 | コマンドが 0 以外で終わり、標準出力が空で、標準エラーに頭で始まる行がある | 拒否と数えない。頭が違うときはその文を出し、セットアップを止めて「既存のガードの確認」を案内する |
| 同じ頭。役の実行で、ホストの `gh` が書く | 役が `squad-handoff` の「人間に操作を頼む前に」の表で失敗を分けるところ | その実行で `squad-preflight` が通り、名前で呼んだ `gh` の標準エラーである | ガードを避ける理由に使わない。分からない失敗として、呼ぶ人間に知らせる |
| `squad-preflight` の終了コードと標準出力。ホストのスクリプトが書く | 役の実行の始めの確認 | 終了コードだけで決める。標準出力の文は読まない | 0 以外と 127 は、`squad-handoff` の「実行の始めの確認」のとおり止まる |

頭は、標準エラーを読める人なら誰でも同じ文を作れる。頭は失敗の分け方にだけ使い、書き込みを許すかの判断には使わない。書き込みを許すかは、ガードが許可ファイルで決める。

## 違いを書く場所

二つの語の違いは、その語を使い分ける人が読む場所に一度だけ書く。

`squad-handoff` の「呼ぶ人間」に、持ち主とオーナーの違いを書く。オーナーは、ワークスペースの権限の名前（オーナー・管理者・メンバー）である。持ち主は、スクワッドやエージェントなどを作り、そのランタイムと利用枠を提供する人で、`creator_id` や `owner_id` で読む。呼ぶ相手は持ち主で、オーナーとは限らない。

`CONTRIBUTING.md` に、原本と正本の違いを書く。原本は、この配布するキットとそのファイルである。正本は、決まりや情報の拠り所になる一つの場所で、原本の中にも導入先のプロジェクトにもある。

## テスト

置き換える語が残っていないことを、常に流すテスト `tests/terms-test.sh` で確認する。新しい文を古い語の癖で書き足すと、すぐ戻るため。判定は Python の補助 `tests/check-terms.py` に置き、置き換える語はコードポイントのエスケープで書く。テスト自身が語を含まないようにするため。

対象は、Git で管理するテキストのファイルすべてである。次のどれかがあれば、ファイルと行を出して失敗する。

| 検査 | 失敗にするもの |
| --- | --- |
| `U+7248` | すべて |
| `U+6BB5` | 段落・普段・一段・「数字と空白の後の 1 字と、まで」を除いたもの |
| `U+6BB5 U+968E`、`U+8AB2 U+984C` | すべて |
| 役の名前としての進行 | 進行の後に役、「の役」、「の担当」を付けた語 |
| AI の使用上限 | AI の後に「の残量」を付けた語 |
| 文中の `issue` | 日本語の文字と接している `issue`（大文字と小文字を区別しない）。除くものは表の下に書く |
| `U+78BA U+304B U+3081` | すべて。止める理由と、止めない語は表の下に書く |
| `U+95A2 U+6240` | すべて。止める理由は「ガードにする（仕組みでなければ、確認・判定・決まり）」 |

文中の `issue` の検査では、次を除く。

- バッククォートの中
- URL
- `GitHub の issue`
- `sub-issue`
- 補助に並べた外の値

`U+78BA U+304B U+3081` を止める理由は「確認にする（文に合わなければ検証か照合）」とする。`U+78BA U+304B` の後に `U+3081` が続かない語は止めない。

次の使い分けは、機械で判定できないので、レビューで確認する。

- フェーズ・ステージ・手順
- 原本と正本
- 持ち主とオーナー
- 確認・検証・照合

`squad-pr-watch-ci-test.sh` は、古い記録の文がある状態で同じ失敗を重ねて知らせないことと、新しい記録の文でも同じになることを確認する。登録の名前は変わらないので、更新で重複と取り残しが出ないことは、既存の流し直しのテストが通ることで確認する。

語をそろえる変更では、次の登録する名前を `main` と比べ、変わっていないことを PR で示す。

- エージェント
- スクワッド
- オートパイロットの題
- ラベル
- Webhook のトリガー
- スキル
- 起票するタスクの題

次のテストが、確認の語と固定の行名を照合する。テストと設計文書は、置き換える前の語そのものを書かない。

| テスト | 確認すること |
| --- | --- |
| `tests/terms-test.sh` | 仮の記号で書いた置き換える語（`U+95A2 U+6240` を含む）を、場所と理由を添えて止めること。確かに・確かな・確認・検証・照合・ガードは止めないこと |
| `tests/gh-test.sh`、`tests/pre-push-test.sh` | 拒否の文が `gh のガード:`・`git push のガード:` で始まること |
| `tests/host-test.sh` | セットアップが表示する「使用する」の行と、ガードを選ばないときに止まる文が、ガードの語であること |
| `tests/project-failure-test.sh` | ガードの確認に失敗して止まる文が、ガードの語であること |
| `tests/guard-check-test.sh` | マークのないガードが前の頭で拒否すると、頭が違う文を出して止まり、「既存のガードの確認」を案内すること。前の頭は下のとおりバイト列で書く |
| `tests/squad-preflight-test.sh` | 始めの確認が通ったときの文が、ガードの語であること |
| `tests/squad-pr-watch-ci-handoff-test.sh` | `/note` の次の行が `確認したコミット:` で始まる報告を、引き継ぎと数えること。前の行名で始まる報告は数えず、作業中の保留を続けること |
| `tests/agent-templates-test.sh`、`tests/leader-eval-test.sh` と評価の場面 | 期待する行名と見出しが、確認の語の形であること。場面の入力のコメントも同じ行名で書くこと |

`tests/squad-pr-watch-ci-handoff-test.sh` の前の行名は、jq の文字列の `\uXXXX` のエスケープで書く。`tests/guard-check-test.sh` の前の頭は、テストの中のガードの差し替えが、UTF-8 のバイト列を `printf` の 16 進のエスケープ（`\xHH`）で書いて出す。bash 3.2 の `printf` と `$'…'` は、コードポイントのエスケープを展開しないためである。

## 検討した案

語を残す場所と検査の時機、固定の行名の扱い、確認・検証・照合の使い分けについて、次の案を選ばなかった。

- 置き換える語を、この文書と `CHANGELOG.md` の節にだけ書く案。読みやすいが、「リポジトリ全体で 0 件」という受け入れ条件と合わず、テストに例外を設けることになるので、コードポイントで書く
- 保留の記録の照合に、古い文を一致の候補として残す案。照合は正しくできるが、置き換える語がコードに残るので、前後の文で照合する
- 語の確認を、実装の最後の 1 回だけの検索にする案。テストを増やさずにすむが、あとから古い語が戻るのを止められないので、常に流すテストにする
- 固定の行名で、前の行名も一致の候補に残す案。更新の間の取りこぼしはなくなるが、置き換える語がコードと指示に残り、受け付けるのをやめる時機も決めることになる
  - 受け付けないと決めたので、すべてのホストとプロジェクトで一度に流し直して、食い違う期間をなくす
- 固定の行名だけを変えず、テストの例外にする案。流し直しの順序は要らないが、「リポジトリ全体で 0 件」と合わないので、行名も変える
- ガードの拒否の頭で、前の頭も一致の候補に残す案。一部だけを流し直したホストでも、セットアップの確認と役の読み分けが合う
  - 置き換える前の語がコードに残り、受け付けるのをやめる時機も決めることになるので、[固定の行名](#固定の行名)と同じく新しい頭だけにする
- 説明の文を、ガードを使うすべての文書に添える案。どこから読んでも分かるが、役は同じ実行で `squad-handoff` も読むので同じ文が重なる
  - 役の指示が長くなるので、読み手の入口になる文書にだけ添える
- 置き換える前の語を、意味によらずすべてガードにする案。機械的に置き換えられるが、標準入力の端末の確認や公開の前の確認は書き込みを止める仕組みではないので、ガードと読むと取り違える
- すべてを確認に置き換える案。機械的に置き換えられるが、証明やチェックサムの判定は `--verify` と同じ検証のほうが、意味が正確に伝わる
  - 決まった値と突き合わせるところは、照合のほうが意味が正確に伝わる。このため、決め方を分ける
