# 依存の脆弱性の監査

このリポジトリが使う依存の、既知の脆弱性を調べる手順の正本である。プロジェクトの検証スキルの監査の節は、この文書を指すだけにし、手順を写さない。この形にした理由は、[正本をリポジトリに置く理由](#正本をリポジトリに置く理由)に、宣言と対象の表を照らすテストは、[宣言と対象の表を照らすテスト](#宣言と対象の表を照らすテスト)に書く。

監査する役は、対象ごとに下のコマンドを流し、結果を「検出なし」「検出あり」「取得失敗」のどれかに読む。結果の報告のしかたと、手順がない依存の扱いは、役の指示に従う。

## 監査の対象

対象は、このリポジトリがバージョンを宣言している依存である。表の 1 列目は、宣言にある名前をそのまま書く。

| 依存 | 種類 | 宣言のある場所 | 手順 |
| --- | --- | --- | --- |
| `actions/attest-build-provenance` | GitHub Actions | `.github/workflows/` | [GitHub Actions](#github-actions) |
| `actions/cache` | GitHub Actions | `.github/workflows/` | [GitHub Actions](#github-actions) |
| `actions/checkout` | GitHub Actions | `.github/workflows/` | [GitHub Actions](#github-actions) |
| `github/codeql-action` | GitHub Actions | `.github/workflows/` | [GitHub Actions](#github-actions) |
| `Pillow` | Python のパッケージ | `tests/release-screens-requirements.txt` | [Pillow](#pillow) |

表にバージョンは書かない。バージョンは Dependabot の PR で変わるので、コマンドが宣言から読む。

## 対象にしない道具

次の道具は、リポジトリにバージョンの宣言がないので、対象にしない。宣言がないと、調べるバージョンを決められず、結果が流した環境ごとに変わるため。

| 道具 | 使うところ | 対象にしない理由 |
| --- | --- | --- |
| `npx markdownlint-cli2` | Markdown の検査 | バージョンを指定せずに呼ぶので、流すたびにその時点のバージョンが使われる |
| Homebrew や apt で入れるパッケージ | 手元と CI の準備 | 入るバージョンをホストとランナーが決める |
| `multica`、`gh`、`jq`、`python3` などの外部の CLI | セットアップ、テスト、この監査 | 使う人のホストに入っているバージョンを使う |

これらの道具にバージョンの宣言を足したときは、[依存が変わるとき](#依存が変わるとき)に従い、対象の表へ移す。

## 準備

コマンドは、リポジトリのルートで流す。依頼がコミットやブランチを指定していればそれを、なければ `main` の最新を checkout する。

- `gh` がログイン済みであること。`gh auth status` の終了コードが 0 であることを見る
- `python3` と `jq` が入っていること
- 結果を置く、コミットしない `tmp/` があること。なければ `mkdir -p tmp` で作る

依存のインストールは要らない。どちらの手順も、宣言を読んで GitHub Advisory Database に照らすだけで、依存のコードを動かさない。

## GitHub Actions

ワークフローが固定したアクションは、`tests/check-action-advisories.py` で調べる。検査の中身は、[サプライチェーンの対策の設計](supply-chain.md#固定したアクションの既知の脆弱性)に書く。

### Actions のコマンド

```bash
mkdir -p tmp
python3 -I tests/check-action-advisories.py --sarif tmp/action-advisories.sarif .github/workflows
```

### Actions の結果の読み方

終了コードと、出力の 1 行目の両方で読む。両方が同じ行に合わないときは、取得失敗にする。

| 終了コード | 出力の 1 行目 | 結果 |
| --- | --- | --- |
| 0 | `PASS action-advisories: 検出 0 件` | 4 つのアクションとも検出なし |
| 1 | `FAIL action-advisories: 検出 <件数> 件` | 表の行にあるアクションは検出あり。行にないアクションは検出なし |
| 2 | `ERROR action-advisories: <理由>` | 4 つのアクションとも取得失敗。理由を写す |
| そのほか | そのほか | 4 つのアクションとも取得失敗。終了コードと出力の 1 行目を写す |

検出ありのときは、1 行目のあとの表を読む。列は、規則・アクション・場所・内容の順である。

### Actions の ID・別名・重大度

ID は、規則の列の GHSA ID である。別名と重大度は表にないので、ID ごとに次で読む。

```bash
gh api /advisories/<GHSA ID> --jq '[.ghsa_id, (.cve_id // "CVE なし"), .severity] | @tsv'
```

出力は、GHSA ID、別名の CVE ID、重大度をタブで区切った 1 行である。重大度の読み替えは、[重大度の読み替え](#重大度の読み替え)に従う。終了コードが 0 でないときは、別名と重大度を「未確認」と書き、検出は消さない。

規則が `version-mismatch` の行は、勧告ではなく、固定した SHA と注記のバージョンのタグが合わないことを示す。検出ありとして扱い、ID の代わりに `version-mismatch` とアクションの名前を書く。その行のアクションは勧告に照らされていないので、勧告の有無は「未確認」と添える。

### Actions の影響するモジュールと到達性

影響するモジュールは、場所の列にあるワークフローのファイルと行である。到達性は「未確認」と書く。GitHub Advisory Database は、アクションの脆弱な箇所がワークフローから実際に呼ばれるかを返さないため。

## Pillow

Pillow は、リリースの画面の PNG を描くときにだけ使う。宣言したバージョンを、`gh` で GitHub Advisory Database に照らす。

### Pillow のコマンド

```bash
mkdir -p tmp
version=$(sed -n 's/^Pillow==//p' tests/release-screens-requirements.txt)
gh api -X GET /advisories -f ecosystem=pip -f type=reviewed -f is_withdrawn=false -f "affects=Pillow@${version:?}" -f per_page=100 --paginate --slurp >tmp/pillow-advisories.json &&
  jq -r 'if type == "array" and length > 0 and all(.[]; type == "array") then add else error("勧告のページを読めません") end | "検出 \(length) 件", (.[] | [.ghsa_id, (.cve_id // "CVE なし"), .severity, .summary] | @tsv)' tmp/pillow-advisories.json
```

### Pillow の結果の読み方

最後のコマンドの終了コードと、出力の 1 行目の両方で読む。

| 終了コード | 出力の 1 行目 | 結果 |
| --- | --- | --- |
| 0 | `検出 0 件` | 検出なし |
| 0 | `検出 <1 以上の件数> 件` | 検出あり |
| 0 以外 | 問わない | 取得失敗。終了コードと標準エラーの 1 行目を写す |
| 0 | `検出` で始まらない | 取得失敗。出力の 1 行目を写す |

次の 3 つのときは、どれも終了コードが 0 以外になり、`検出` の行は出ない。

- `gh` が失敗したとき
- バージョンを宣言から読めなかったとき
- 応答が勧告のページの配列でなかったとき

出力が空であることを、検出 0 件と読まない。

### Pillow の ID・別名・重大度

検出ありのときは、1 行目のあとに、勧告ごとの行がタブで区切られて出る。列は、GHSA ID・別名の CVE ID・重大度・要約の順である。ID は GHSA ID、別名は CVE ID を使う。CVE ID がない勧告は `CVE なし` と出るので、別名なしとして扱う。

### Pillow の影響するモジュールと到達性

影響するモジュールは `tests/ansi-to-png.py` である。Pillow を読み込むのはこのファイルだけで、`tests/release-screens.sh` から呼ばれる。原本を導入する人のホストと、セットアップの動作には入らない。

到達性は「未確認」と書く。GitHub Advisory Database は、脆弱な関数が呼ばれるかを返さないため。

## 重大度の読み替え

GitHub Advisory Database の重大度は、タスクに書く 3 つの区分へ次のとおり読み替える。

| 勧告の重大度 | タスクに書く重大度 |
| --- | --- |
| `critical`、`high` | 高 |
| `medium` | 中 |
| `low` | 低 |
| `unknown`、または読めなかった | 未確認。低とは読まない |

## 依存が変わるとき

バージョンを宣言する依存を足す・外す変更は、同じ PR でこの文書を直す。対象の表の行を足すか消し、新しい種類の依存なら、コマンド・結果の読み方・ID と別名と重大度・影響するモジュールと到達性の節を足す。

宣言と対象の表が合っていることは、テストが確認する。表を直さずに依存を足すと、テストが失敗する。確認の範囲は、[宣言と対象の表を照らすテスト](#宣言と対象の表を照らすテスト)に書く。

## 正本をリポジトリに置く理由

監査の手順の正本は、検証スキルの本文ではなく、リポジトリのこの文書に置く。理由は 3 つある。

- 依存を足す PR が、同じ PR で手順を直せる。検証スキルは Multica の登録で、PR のレビューにも差分にも出ない
- 宣言と手順が合っていることを、テストで確認できる。登録の本文は、CI から読めない
- セットアップは既存の検証スキルを書き換えないので、本文に写した手順は、依存が変わるたびに人間が直さないと古くなる。指すだけの節は、依存が変わっても直さなくてよい

検証スキルの監査の節は、この文書を作業先のリポジトリで読んで従うことだけを書く。この文書がない、または読めないときは、監査を成功にせず、すべての依存を「手順なし」として不足を人間へ返す。

正本の中身は、次のとおり決めている。

- 対象は、リポジトリがバージョンを宣言している依存にする。宣言のない道具は、調べるバージョンを決められないので対象にしない
- アクションは `tests/check-action-advisories.py` で調べ、Pillow は `gh` で GitHub Advisory Database に照らす。監査のためだけの別の道具は入れない
- 結果は、終了コードと出力の 1 行目の両方で読む。片方だけで読むと、`gh` の失敗で空になった出力を、検出 0 件と読むおそれがあるため
- 到達性は「未確認」と書く。どちらの手順も、脆弱な箇所が呼ばれるかを返さないため
- 対象の表にバージョンは書かない。バージョンは Dependabot の PR で変わり、コマンドが宣言から読むため

## 宣言と対象の表を照らすテスト

宣言にある依存の名前の集合と、「監査の対象」の表の 1 列目の集合が同じであることを、テストで見る。依存を足してこの文書を直さない変更と、依存を外して行を残す変更の、どちらも失敗させる。

照らすスクリプトは `tests/check-audit-targets.py <リポジトリのルート>` で、標準ライブラリだけで書く。

| 読むもの | 取り出す名前 |
| --- | --- |
| `.github/workflows/` の `*.yml` と `*.yaml` の `uses:` の行 | `OWNER/REPO` を取り出し、`./` で始まる手元のアクションは飛ばし、`PATH` は落とす |
| `tests/` の下の、名前に `requirements` を含む `*.txt` | `==` の前のパッケージの名前。空行と `#` の行は飛ばす |
| この文書の「監査の対象」の表 | 1 列目のバッククォートの中の名前 |

名前は、大文字と小文字を区別せずに比べる。終了コードは、合えば 0、合わなければ 1、読めなければ 2 にする。合わないときは、足りない名前と余る名前を 1 行ずつ出す。読めなかった結果を、合ったとして通さないためである。

読み方を知らない宣言は、黙って通さない。リポジトリに次のファイルが 1 つでもあれば、失敗にする。

- `package.json`
- `package-lock.json`
- `pyproject.toml`
- `Pipfile`
- `go.mod`
- `Cargo.toml`
- `Gemfile`
- `.tool-versions`
- `tests/` の外の `*requirements*.txt`

新しい種類の宣言を扱うときは、スクリプトの読み方とこの文書の節を同じ PR で揃える。

テスト `tests/audit-targets-test.sh` は、次を確認する。

- リポジトリで、スクリプトが 0 で終わる
- リポジトリの写しに依存を 1 つ足すと、1 で終わり、足した名前が出る。アクションと、requirements の行の、両方で確認する
- 写しのこの文書から行を 1 つ消すと、1 で終わる。知らない宣言のファイルを置くと、失敗する
- 「Pillow のコマンド」の節のコードブロックを取り出し、スタブの `gh` で流す。勧告なしの応答で `検出 0 件`、勧告ありの応答で `検出 <件数> 件` と勧告の行が出る
- `gh` の失敗と、配列でない応答では、終了コードが 0 以外で、`検出` の行が出ない

最後の確認は、コマンドを書き写さずに、この文書から取り出して流す。文書のコマンドと、テストが確認したコマンドが、ずれないようにするためである。アクションの手順の終了コードと出力は、`tests/action-advisories-test.sh` が確認する。
