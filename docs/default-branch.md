# 定期の依存の確認をリモートのデフォルトブランチに向ける

週次の依存の監査と、Dependabot の PR の週次の確認は、対象のブランチを毎回リモートから取得する。`main` に固定しないので、デフォルトブランチが `develop` などのリポジトリでも、そのブランチの最新を監査し、そのブランチ向けの PR だけを進める。この文書は、2 つの指示と見張りのスクリプト `squad-dependabot-merge` の決まりと、その理由を書く。

## 目的と範囲

定期の処理の原本は、対象のブランチを `main` に固定していた。デフォルトブランチが `develop` で、`main` に README しかないリポジトリで、週次の依存の監査が止まった。固定は、[オートパイロットの原本](../common/autopilots.md)の 2 つの指示と、`squad-dependabot-merge` の 3 か所にある。

目的は次の 4 つである。

1. 2 つの指示が、実行のたびに `git ls-remote --symref origin HEAD` でデフォルトブランチを取得し、そのブランチの最新のコミットを読む
2. 取得できないときは、ブランチを推測せず、監査も PR の確認も始めずに、失敗した操作と理由を返す
3. 結果の先頭に、対象にしたブランチとコミットを書き、人間がどのブランチを見た結果かを読めるようにする
4. `squad-dependabot-merge` が、渡されたブランチをデフォルトブランチと照らし、そのブランチ向けの PR だけを進める

次は対象にしない。

- 実装と修正の役の指示にある `origin/main` との比較。PR の base を読む別の変更で扱う
- デフォルトブランチ以外に向いた Dependabot の PR のマージ
- VERSION と CHANGELOG。バージョンを上げる PR で扱う
- 導入済みのプロジェクトに登録された指示の手での直し。セットアップの流し直しで原本の指示に置き換わる

## デフォルトブランチの取得

2 つの指示は、同じ手順で対象のブランチを決める。手元のリポジトリのルートで、毎回 `git ls-remote --symref origin HEAD` を流す。手元の `origin/HEAD` は使わない。clone のあとにデフォルトブランチが変わっても、手元の値は変わらないためである。

### 取得の成功と失敗

出力のうち、`ref:` で始まる行がちょうど 1 行で、その行が次の形のときだけ、取得の成功とする。

```text
ref: refs/heads/<ブランチ名><タブ>HEAD
```

`<タブ>` は 1 つのタブの文字である。ブランチ名は、英数字と `.`・`_`・`/`・`-` だけでできていて、`-` で始まらないものに限る。

取得の失敗は、次の 3 つのどれかである。

| 失敗 | 当てはまるとき |
| --- | --- |
| コマンドの失敗 | `git ls-remote` の終了コードが 0 でない |
| `ref:` の行がない | `ref:` で始まる行がない。または、その行が上の形に合わない |
| `ref:` の行が 2 行以上 | `ref:` で始まる行が 2 行以上ある |

上の形に合わない `ref:` の行は、「`ref:` の行がない」として扱う。読めない行からブランチ名を切り出すと、推測と同じになるためである。ブランチ名の文字を絞るのは、名前をコマンドと API のパスにそのまま渡すためである。この形に合わない名前のデフォルトブランチは、取得の失敗として止まる。

返す理由は、次の 4 つの文から選ぶ。分類は上の 3 つのままで、「`ref:` の行がない」だけを 2 つの文に分ける。人間が、名前の文字が原因だと読めるようにするためである。

| 分類 | 返す理由 |
| --- | --- |
| コマンドの失敗 | `git ls-remote が終了コード <N> で失敗した` |
| `ref:` の行がない | `ref: の行がない` |
| `ref:` の行がない | `ref: の行はあるが形に合わない（ブランチ名に英数字と . _ / - 以外の文字があるか、- で始まる）` |
| `ref:` の行が 2 行以上 | `ref: の行が <N> 行ある` |

形に合わない行の文には、受け取った `ref:` の行を添えない。行の中の名前は外から来る文字で、返答にそのまま写さないためである。

失敗したときは、`main` や `develop` を代わりに使わない。手元の `origin/HEAD` も代わりにしない。

### 最新のコミットにする

取得したブランチは、次の 3 つのコマンドで手元に用意する。

```bash
git fetch origin +refs/heads/<ブランチ名>:refs/remotes/origin/<ブランチ名>
git checkout --detach refs/remotes/origin/<ブランチ名>
git rev-parse HEAD
```

`git rev-parse HEAD` の 40 桁の SHA を、確認したコミットとして結果に書く。`git checkout` の失敗も、`git fetch` の失敗と同じに扱って止まる。

`git fetch` の前に、手元がクリーンかを見る。`git status --porcelain` の出力があるときは、未コミットの作業があるので止まる。HEAD のコミットがリモートのどのブランチにも含まれないとき（`git branch -r --contains HEAD` の出力がない）も、未 push の作業とみなして止まる。この 2 つのどちらでもなければ、HEAD を外しても作業は消えない。

### 追跡の ref を更新する

fetch には、取り先と置き先の両方を書いた refspec を渡す。取得したコミットを、追跡の ref `refs/remotes/origin/<ブランチ名>` にも置くためである。clone の refspec が一部のブランチに絞られていても、この形なら追跡の ref ができる。手元の refspec の設定は変えない。

追跡の ref を置くのは、次の実行の未 push の判定が、追跡の ref を読むためである。`FETCH_HEAD` だけに取得すると、絞られた refspec の手元では追跡の ref ができない。次の実行では HEAD を含むリモートのブランチがなく、公開済みのコミットを未 push と取り違えて止まる。checkout も追跡の ref から行い、判定が読む ref と HEAD を同じものにする。

先頭の `+` は、デフォルトブランチが force push で書き換わっても、fetch を通すためである。clone の既定の refspec と同じ扱いである。手元の判定は fetch の前に流すので、書き換えの前のコミットにいる HEAD も、まだ更新していない追跡の ref に含まれる。

ほかの fetch が早送りで追跡の ref を進めただけのときは、止まらない。HEAD は、進んだあとの追跡の ref にも含まれるためである。

止まるのは、デフォルトブランチの書き換えのあとに、ほかの fetch が先に追跡の ref を更新していたときである。既定の refspec の `git fetch` などが、書き換えたあとのコミットを追跡の ref に置く。HEAD は書き換えの前のコミットのままで、更新された追跡の ref に含まれない。ほかのリモートのブランチにも含まれなければ、判定は未 push の作業とみなして止まる。

止まる側に倒れるので、作業は消えない。ただし、同じ手元は次の実行でも止まり続ける。判定は fetch の前に止まるので、追跡の ref も HEAD も変わらないためである。理由は未 push と返るが、HEAD は書き換えの前に公開されていたコミットで、手元に未 push の作業はない。

#### 止まり続ける手元を再開する

役は、この手元と本当の未 push の作業を見分けない。人間が、止まった手元のリポジトリのルートで、見分けてから操作する。見分けで公開されていたと言えないときは、操作せず、作業を手元に残す。

先に `git status --porcelain` を流す。出力があるときは未コミットの作業なので、操作せず、作業を残す。

次に、HEAD が追跡の ref のかつての値かを、追跡の ref の reflog で見分ける。手順は追跡の ref から checkout するので、公開されていたコミットにいる HEAD は、その reflog に残る。手元で作ったコミットは、追跡の ref の reflog に入らない。

```bash
git for-each-ref --format='%(refname)' refs/remotes/origin/ | while read -r ref; do git reflog show --format='%H' "$ref" --; done | grep -x "$(git rev-parse HEAD)"
```

出力がないときは、未 push の作業として扱い、操作せず、作業を残す。reflog の記録がない手元や、古い記録が消えた手元でも、出力はない。このときも、公開されていたと言えないので操作しない。

出力があるときは、HEAD は公開されていたコミットである。[取得の成功と失敗](#取得の成功と失敗)の手順でブランチ名を得て、手元を対象ブランチの最新へ移す。

```bash
git fetch origin +refs/heads/<ブランチ名>:refs/remotes/origin/<ブランチ名>
git checkout --detach refs/remotes/origin/<ブランチ名>
```

移したあと、`git status --porcelain` に出力がなく、`git branch -r --contains HEAD` に出力があることを確認する。この 2 つが判定と同じなので、次の実行はこの手元で判定を通る。

手元のリポジトリがないときは、`--ref` を付けずに `multica repo checkout https://github.com/{{repository}}` で用意してから、取得を流す。

## 週次の依存の監査

監査の指示の手順 1 を、上の取得と最新のコミットにする手順に替える。次のどれかに当たるときは、監査をせず、チェックを `done` にせず、失敗した操作と理由を人間へ返す。

- デフォルトブランチの取得の失敗
- `git fetch` の失敗
- 手元がクリーンでない、または未 push の作業がある

結果には、次の 2 行を、`監査の結果:` の行より前に置く。

```text
対象ブランチ: <ブランチ名>
確認したコミット: <40 桁の SHA>
```

上の失敗で止まったときは、2 行ともに `なし` と書く。ブランチを取得できたあとに `git fetch` で止まったときも、`対象ブランチ:` は `なし` にする。監査していないブランチを、監査の対象として読ませないためである。

行の形は、監査の指示の手順 6 に書く。役の指示の[依存の監査を頼まれたとき](../common/agents/security-reviewer.md#依存の監査を頼まれたとき)は変えない。この節は、週次でない監査の依頼でも使うので、週次の監査だけの行を足さない。

指示から「main の最新」の語を消す。[依存の脆弱性の監査](dependency-audit.md#準備)の準備の節も、`main` の最新ではなく、デフォルトブランチの最新を読むと書き直す。

## Dependabot の PR の週次の確認

Dependabot の指示も、手順 1 で同じ取得と最新のコミットにする手順を流す。取得したブランチを、この文書では対象ブランチと呼ぶ。指示の冒頭の「main に追従させて」を「対象ブランチに追従させて」に替える。

冒頭の「開いている Dependabot の PR をすべて確認する」も、すべてを一覧にして、対象ブランチ向けの PR を確認する文に替える。[対象ブランチ向けでない PR](#対象ブランチ向けでない-pr) の決まりを、冒頭の文にもそろえるためである。

### 取得に失敗したとき

取得・`git fetch`・手元の確認のどれかで止まったときは、`squad-dependabot-merge` を呼ばない。PR の確認・追従・マージ・タスクの作成を始めず、最後の返答に失敗した操作と理由を書いて終える。

### 見張りに渡す

`list` と `advance` に、`--base <対象ブランチ>` を渡す。

```text
squad-dependabot-merge {{repository}} {{project_id}} list --base <対象ブランチ>
squad-dependabot-merge {{repository}} {{project_id}} advance <PR> --base <対象ブランチ> --reviewed-head <SHA> --run-deadline <締め切り>
```

`list` が 0 以外で終わったときは、PR の確認・追従・マージ・タスクの作成を始めない。最後の返答の 1 行目を `対象ブランチ: なし` にし、次の行に `squad-dependabot-merge list の失敗:` と標準エラーの 1 行目を書いて終える。スクリプトが照合で退けた名前を、`対象ブランチ:` に載せないためである。

`list` が空配列を返したときは、最後の返答を `対象ブランチ: <ブランチ名>` と「なし」の 2 行にする。今の指示の手順 2 の「「なし」とだけ返して終える」を、この 2 行に替える。

### 対象ブランチ向けでない PR

`list` の結果の `base` が対象ブランチと違う PR は、確認・追従・マージ・人間に回すことをしない。PR にもコメントしない。最後の返答では、マージしなかった一覧に、理由「対象外のブランチ向け」で載せる。

この PR を一覧から消さずに載せるのは、手順 2 のすべての PR を、最後の返答のどちらかの一覧に載せる決まりを保つためである。

### 結果の語

PR の結果と最後の返答の理由から、`main` の名前を消す。

| 今の語 | 変えた語 |
| --- | --- |
| main に追いつけない | 対象ブランチに追いつけない |
| 反映後に main がまた進んだ場合 | 反映後に対象ブランチがまた進んだ場合 |
| （なし） | 対象外のブランチ向け |

### 最後の返答

最後の返答は、どの終わり方でも 1 行目を `対象ブランチ:` の行にする。PR のない週も、止まった週も、どのブランチを見た結果かを読めるようにするためである。

| 終わり方 | 1 行目 | 2 行目から |
| --- | --- | --- |
| PR を確認した | `対象ブランチ: <ブランチ名>` | 「マージした」と「マージしなかった（理由）」の 2 つの一覧 |
| `list` が空配列 | `対象ブランチ: <ブランチ名>` | 「なし」 |
| 取得・`git fetch`・手元の確認で止まった | `対象ブランチ: なし` | 失敗した操作と理由 |
| `list` が 0 以外で終わった | `対象ブランチ: なし` | `squad-dependabot-merge list の失敗:` と標準エラーの 1 行目 |

`list` のあとに `advance` や `escalate` が失敗したときは、対象ブランチは照合を通っているので、1 行目は `対象ブランチ: <ブランチ名>` のままにする。未完了の PR と理由は、今の決まりのとおり一覧に残す。

2 つの一覧には、`list` が返したすべての PR を載せる。対象外のブランチ向けの PR も、マージしなかった一覧に載せる。

### 役の指示

この返答の形は、オートパイロットの指示だけでなく、Dependabot の役の指示の[結果の出し方](../common/agents/dependabot-merger.md#結果の出し方)でも決まっている。役の指示は「その回の対象の PR」を一覧に載せ、「最初から対象の PR がなければ「なし」とだけ返す」と書く。この 2 つを次のとおり替える。

- 一覧に載せるのは、「その回の対象の PR」ではなく、`list` が返したすべての PR にする。対象外のブランチ向けの PR も載せる
- 最後の返答の 1 行目を `対象ブランチ:` の行にし、その形はオートパイロットの指示の「最後の返答」に従うと書く。「最初から対象の PR がなければ「なし」とだけ返す」は、`対象ブランチ:` の行と「なし」の 2 行に替える

役の指示とオートパイロットの指示は、同じセットアップの流し直しで置き換わる。

## 見張りのスクリプト

`squad-dependabot-merge` の `list` と `advance` は、`--base <ブランチ名>` を必須にする。スクリプトは、渡されたブランチを GitHub のデフォルトブランチと照らしてから、PR を読む。`escalate` は、ブランチを使わないので変えない。

### 引数と照合

`list` と `advance` は、PR の読み取りと書き込みの前に、次の順で確認する。どこかで止まったときは、追従の依頼もマージもしない。

| 確認 | 合わないとき |
| --- | --- |
| `--base` が 1 回だけ渡されている | 使い方を出し、終了コード 2 |
| ブランチ名が英数字と `.`・`_`・`/`・`-` だけで、`-` で始まらない | 使い方を出し、終了コード 2 |
| `repos/<OWNER/REPO>` の `default_branch` を読める | 理由を出し、終了コード 1 |
| `--base` が `default_branch` と同じ | 2 つの名前を出し、終了コード 1 |

`default_branch` は、`squad-cli-lib` に足す読み取り `gh-default-branch` で読む。約束のコマンドは、今の `gh-branch-rules` などと同じく、引数 1 つをまるごと `{endpoint}` にした `gh api {endpoint} --jq 'with_entries(select(.key == "default_branch"))'` にする。スクリプトは `{endpoint}` に `repos/<OWNER/REPO>` を渡す。形は `default_branch` の文字列だけを持つオブジェクトである。

見本は、`tests/fixtures/cli/README.md` の決まりで、公開のリポジトリから採取する。

`--base` がないときに `main` を代わりに使わない。古い指示が `--base` なしで呼んでも、終了コード 2 で止まり、マージしない。

### list

必須 CI のルールを、`repos/<OWNER/REPO>/rules/branches/<対象ブランチ>` から読む。出力の PR ごとに、PR の `baseRefName` を `base` の欄で足す。ほかの欄は変えない。

`list` は、対象ブランチ向けでない PR も一覧に残し、`base` で見分けさせる。指示が最後の返答にすべての PR を載せるためである。

### advance

進める PR の条件の `.baseRefName == "main"` を、`.baseRefName == <対象ブランチ>` に替える。合わないときの文は、`<対象ブランチ> 向けの、開いている Dependabot の通常の PR だけを進められます。` にする。終了コードは 1 のままで、追従の依頼もマージもしない。

必須 CI のルールも、`list` と同じく対象ブランチから読む。`behind-limit` の文は、`この実行で 3 回依頼しても対象ブランチ <ブランチ名> に追いつけませんでした。` にする。

## 入力と信頼の表

この変更は、マージの許可を持つ役が進める PR の範囲を決める。対象のブランチを決める入力ごとに、信頼する条件を次のとおりにする。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| `git ls-remote --symref origin HEAD` の出力（GitHub が返す。`origin` は `{{repository}}` から checkout した手元） | 2 つの指示の対象ブランチ | 終了コードが 0 で、`ref:` の行がちょうど 1 行あり、[取得の成功と失敗](#取得の成功と失敗)の形に合う | 取得の失敗として止まり、監査も PR の確認も始めない |
| `--base` の引数（指示に従うエージェントが書く。PR の本文やリリースノートの文に影響されうる） | `list` と `advance` の対象ブランチ | 形の確認に合い、GitHub の `default_branch` と同じ | PR の読み取りと書き込みの前に、0 以外で終わる |
| `repos/<OWNER/REPO>` の `default_branch`（GitHub が返す。リポジトリの管理者が設定する） | `--base` の照合 | `squad-cli-lib` の読み取りの形に合う、空でない文字列 | 0 以外で終わる |
| PR の `baseRefName`（GitHub が返す。Dependabot の設定でブランチを選べる） | `advance` で進める PR の判定と、`list` の `base` | 照合を通った対象ブランチと同じ | `advance` は進めずに 0 以外で終わる。指示は対象外として飛ばす |

`--base` をスクリプトの中で照らすのは、指示に従うエージェントを信頼の根拠にしないためである。外の文に動かされたエージェントが別のブランチを渡しても、スクリプトが止める。

## 互換性と影響を受ける利用者

セットアップを流し直すと、登録済みの 2 つのオートパイロットの指示が、この文書の指示に置き換わる。見張りのスクリプトも、同じ流し直しで置き換わる。登録済みの指示だけを手で直しても、次の流し直しで原本の指示に戻る。

デフォルトブランチが `main` のプロジェクトでは、対象のブランチは今と同じである。変わるのは、結果の先頭の行と、理由の語だけである。

デフォルトブランチが `main` でないプロジェクトでは、監査と Dependabot の確認が、そのブランチを対象に動くようになる。今の `advance` は `main` 向けの PR しか進めないので、このプロジェクトでは Dependabot の PR の自動マージが、流し直しのあとに新しく始まる。

自動マージは、対象ブランチの必須チェックの規則で CI を判定する。対象ブランチに必須チェックの規則がないと、`list` の `ci` は、必須以外のチェックによらず `success` になる。流し直す人間は、その前に対象ブランチの規則を見ておく。規則を足すか決めるのは人間で、この変更では規則を変えない。

デフォルトブランチの名前が[取得の成功と失敗](#取得の成功と失敗)の文字に合わないプロジェクトでは、2 つの定期の処理が毎週止まる。`+` や日本語を含む名前と、`-` で始まる名前がこれに当たる。返す理由は「`ref:` の行はあるが形に合わない」になる。動かすには、人間がデフォルトブランチの名前を変える。

流し直しの途中などで、指示とスクリプトの新旧が食い違う間は、どちらの組み合わせでも `list` が終了コード 2 で止まる。

| 指示 | スクリプト | 止まり方 |
| --- | --- | --- |
| 古い（`--base` なし） | 新しい | `--base` がないので、使い方を出して終了コード 2 |
| 新しい（`--base` あり） | 古い | `list` の引数の数が合わないので、使い方を出して終了コード 2 |

どちらもマージはせず、その回の PR は次の週に扱われる。新しい指示では、最後の返答が `対象ブランチ: なし` と `list` の失敗の行になる。

GitHub のガードは変えない。ガードは Dependabot の PR のマージだけを許し、base のブランチは見ない。base の判定は、上のとおり `advance` が行う。

### 変更の知らせ

この変更の知らせは、バージョンを上げる PR が、`CHANGELOG.md` に次の文で足す（[release.md の変更の知らせ](release.md#変更の知らせ)の決まり）。`main` でないプロジェクトで自動マージが新しく始まることを、更新の前に読めるようにするため。

登録が変わらないと書く文は、同じ節のほかの変更と食い違わないよう、「この変更では」とこの変更の範囲に限る。

```markdown
週次の依存の監査と Dependabot の PR の週次の確認が、`main` でなく、プロジェクトのデフォルトブランチを対象に動くようにした。流し直しで、2 つのオートパイロットの指示と見張りのスクリプトが替わる。この変更では、オートパイロットの名前とスケジュール、エージェントの登録は変わらない。

デフォルトブランチが `main` のプロジェクトでは、対象は今と同じで、結果の先頭の行と理由の語だけが変わる。`main` でないプロジェクトでは、流し直しのあとに、Dependabot の PR の自動マージが新しく始まる。

自動マージは、対象ブランチの必須チェックの規則で CI を判定する。規則がないと、必須以外のチェックによらず、CI が通ったと読む。`main` でないプロジェクトでは、流し直す前に、対象ブランチの規則を確認する。

- `+` や日本語を含む名前と、`-` で始まる名前のデフォルトブランチでは、2 つの定期の処理が毎週止まる。動かすには、ブランチの名前を変える
- 流し直しの途中で指示とスクリプトの新旧が食い違う間は、Dependabot の確認がマージせずに止まる。その回の PR は、次の週に扱われる
```

## 足す手順と防ぐ失敗

足す手順は、デフォルトブランチの取得と、`--base` の照合の 2 つである。防ぐ失敗の 1 つは、`main` がデフォルトでないリポジトリで、週次の監査が `main` を読んで止まった失敗である。あわせて、refspec を絞った手元で、取得済みのコミットを未 push と取り違えて止まる失敗も防ぐ。この手順は、合意された要件にもとづく。

働いた跡は、次のテストに残す。

- 展開した 2 つの指示に、取得のコマンドと結果の行があり、`main` を名指す checkout と fetch がないことを、`tests/agent-templates-test.sh` で見る
- 展開した Dependabot の役の指示の結果の出し方が、`対象ブランチ:` の行を 1 行目にすることを、同じテストで見る
- デフォルトブランチが `develop` のスタブで、`list` が `develop` のルールを読み、`advance` が `main` 向けの PR を進めないことを、`squad-dependabot-merge` のテストで見る
- セットアップを 2 回流したあとの登録の指示に、上の行が残ることを、`tests/project-followup-test.sh` で見る
- refspec を `main` に絞った clone とデフォルトの `develop` で手順を 2 回続けて流し、2 回目も判定を通ることを、`tests/default-branch-fetch-test.sh` で見る
- 同じテストで、未コミットの変更と未 push のコミットがあると判定で止まり、どちらも手元に残ることを見る
- このテストは、原本の 2 つの指示に同じ fetch と checkout の文字列があることを確認してから、`<ブランチ名>` を置き換えて流す。リモートのコミットは push で作らず、bare のリポジトリの中で作る

実行のたびに、役の結果にも跡が残る。監査の結果には `対象ブランチ:` と `確認したコミット:`、Dependabot の最後の返答には先頭の `対象ブランチ:` の行が入る。止まったときは、同じ行が `なし` になり、失敗した操作と理由が人間への返答に書かれる。

### 仕組みにしない理由

同じ失敗を止める仕組みの案は 3 つある。どれも、取得・手元の保護・checkout を役の指示に残す手順の代わりにしない。

#### 手元の準備を見張りのスクリプトにまとめる案

取得から checkout までを 1 つのスクリプトで流し、ブランチと SHA を返す案である。手順の書き間違いと順序の違いは止められる。選ばなかった理由は 4 つある。

- 既存の見張りは、どれも git を呼ばない。GitHub と Multica の API だけで動き、手元の作業ツリーを持たない
- 手元は、タスクごとに `multica repo checkout` が作る。スクリプトはその場所を知らない
- 場所を渡す仕組みを足すと、導入済みのプロジェクトの見張りの更新が要る
- スクリプトを呼ぶかと、準備した手元で監査するかは、役の判断のままである。止まる・返すも指示に残る

#### fetch と checkout を止めるガードを足す案

決まった ref 以外の checkout を止める案である。選ばなかった理由は 3 つある。

- 既存のガードは、push の宛先と GitHub の書き込みだけを見る
- fetch と checkout は、実装や修正の役も日常で流す。定期の処理かどうかは、ガードに見分けられない
- 対象のブランチは、実行のたびにリモートへ問い合わせて決まる。ガードに固定の値を持たせられない

#### テストと CI で守る案

指示の文字列、取得の手順の実際の動き、登録の残り方を守れる。すでに採用している。ただし、定期の処理が実際に動く手元と、実行の順序は、テストでは見られない。

失敗が起きたのは、週次の監査が `main` を読んで止まった 1 回である。refspec を絞った手元の取り違えは、設計のレビューで見つかったもので、実行では起きていない。この回数では、導入先すべてに新しい部品を足す理由にならない。

仕組みで止める範囲と、手順に残す範囲は、次のように分ける。

- 仕組みが止める範囲は、`list` と `advance` の `--base` の照合である。スクリプトが GitHub の値と照らす
- テストが見る範囲は、指示に `main` の固定と `FETCH_HEAD` がないことである
- テストは、取得の手順が実際の git で 2 回通ることと、未コミットと未 push の作業が残ることも見る
- 流し直したあとも登録に残ることも、テストが見る
- 手順に残す範囲は、実行のたびの取得と、失敗したときの停止である
- 止まったときの `なし` と理由の返答、準備した手元での監査と確認も、手順に残す

## 検討した案

対象のブランチを決める場所、対象外の PR の扱い、手元の値を使うか、取得したコミットの置き場所の 4 つを比べた。

### 対象のブランチをどこで決めるか

指示が取得してスクリプトに渡し、スクリプトが GitHub の値と照らす案にした。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 指示が取得し、スクリプトが照らす（選んだ案） | 指示とスクリプトが同じブランチを使い、違えば止まる | 読み取りが 1 つ増え、見本の採取が要る |
| 指示が取得し、スクリプトは渡された値を信じる | 変更が小さい | 外の文に動かされたエージェントが、別のブランチへのマージを広げられる |
| スクリプトだけが API で決める | 引数が増えない | 指示の checkout と、スクリプトの対象が別々に決まる。渡されないときに止まる要件を満たせない |

### 対象外の PR を list から消すか

`list` に残し、`base` の欄で見分ける案にした。消すと、最後の返答に載らない PR ができ、人間がその PR の存在に気づかないためである。

### 手元の origin/HEAD を使うか

使わない。`origin/HEAD` は clone の時点の値で、リポジトリの設定を変えても手元は変わらない。毎回 `git ls-remote` で読めば、設定の変更が次の実行から効く。

### 取得したコミットをどこに置くか

追跡の ref にも置く案にした。次の実行の未 push の判定を変えずに、取得済みのコミットを公開済みと読めるためである。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 追跡の ref にも置く（選んだ案） | 判定はそのままで、refspec の設定も変えない | 手元に追跡の ref が 1 つ増える |
| `FETCH_HEAD` だけに置く（前の設計） | 追跡の ref を増やさない | 絞られた refspec の手元で、次の実行が公開済みのコミットを未 push と取り違えて止まる |
| 判定で `FETCH_HEAD` も見る | fetch の形を変えない | `FETCH_HEAD` はほかの fetch でも上書きされ、次の実行まで残る保証がない |
| `git remote set-branches --add` で refspec の設定を足す | 以降の fetch がすべて追跡の ref を更新する | 共有されうる手元の設定を書き換え、定期の処理の外にも効く |
