# 定期確認の対象を拡張の設定で絞る

範囲がリポジトリの定期確認は、セットアップで選んだすべてのリポジトリに展開される。この文書は、拡張のディレクトリに置く設定で、定期確認ごとに対象のリポジトリとリポジトリごとの値を決める仕組みと、その理由を書く。

使う人への書き方は `EXTENSIONS.md` の「`autopilot-targets.json`」に、流し直しでの動きは `manual.md` に書く。定期確認の登録と一時停止の今の決まりは `common/autopilots.md` と `lib/autopilots.sh` が正本である。

## 目的と範囲

目的は、対象のブランチや CI のないリポジトリに定期確認を作らず、要らない報告と人間への確認を減らすことである。あわせて、ブランチや成果物の名前をリポジトリごとに定義へ差し込めるようにする。

次は対象にする。

- 拡張のオートパイロットのうち、範囲が `repository` の定義
- 原本の「週 1 回の依存ライブラリの脆弱性チェック」と「Dependabot の PR の週次の確認」
- Dependabot の Webhook の登録と、その登録とフィルターの設定を頼むタスクの起票
- セットアップの確認の表示と、導入の確認

次は対象にしない。

- 原本に DAST の定期確認を足すこと。DAST の定義は拡張に置く
- 原本の 2 つの定期確認の文面。`main` を前提にした手順のまま変えない
- 設定をセットアップの質問で聞くことと、リポジトリの役割から対象を自動で決めること
- 一時停止した登録とその履歴を消すこと
- 範囲が `member` の定義（使用上限の見張り）の対象を絞ること

## 設定のファイル

設定は、拡張のディレクトリの `autopilot-targets.json` に置く。拡張を使わないプロジェクトが対象を絞るときは、`kit-version` とこのファイルだけの拡張を作る。

### 形

ファイルは、定義の名前をキーにした JSON のオブジェクトである。値は、対象のリポジトリをキーにしたオブジェクトで、その値がリポジトリごとの値のオブジェクトになる。

```json
{
  "DAST の結果の確認": {
    "example/app": {"branch": "develop", "artifact": "zap-report"}
  },
  "週 1 回の依存ライブラリの脆弱性チェック": {
    "example/app": {}
  },
  "Dependabot の PR の週次の確認": {
    "example/app": {}
  }
}
```

この例では、3 つの定期確認を `example/app` にだけ作る。ほかのリポジトリを選んでいても、その分は作らない。

| 項目 | 決まり |
| --- | --- |
| 定義の名前 | 見出しの `##` と空白のあとから、空白に続く最初の `{{` の前までの文字列。名前の中の空白はそのまま残す |
| 対象のリポジトリ | `OWNER/REPO` の形で、1 つの定義に 1 つ以上書く。大文字と小文字を区別せず、重なりは誤りにする |
| 値の名前 | 英小文字で始まり、英小文字・数字・ハイフンだけを使う |
| 値 | 1 文字以上 200 文字以下の 1 行の文字列。制御文字・バッククォート・`{{`・`}}` を含めない |

設定に書いていない定義は、今までどおり選んだすべてのリポジトリに作る。書いた定義は、書いたリポジトリにだけ作る。

設定に書いた名前は、範囲が `repository` の定義の 1 つにだけ一致させる。見出しが `## 週 1 回の依存ライブラリの脆弱性チェック {{project_key}} {{repository}}` なら、名前は次のとおりである。

```text
週 1 回の依存ライブラリの脆弱性チェック
```

同じ名前の定義が 2 つ以上あるかは、設定に書いた名前についてだけ見る。

### 値の差し込み

定義の中の `{{target.<値の名前>}}` に、その定義とリポジトリの組の値を差し込む。たとえば、上の例の `{{target.branch}}` は `example/app` の分で `develop` になる。

`{{target.*}}` を書けるのは、節の「指示:」のあとの `text` のコードブロックの中だけである。見出し・範囲や担当やスケジュールの行・コードブロックの外の文に書いたときは、拡張の確認で誤りにする。見出しは名前の規則を作るときに値なしで展開し、スケジュールの行は値で変えると登録の比較が崩れるためである。

値を定義ごとに持つのは、同じリポジトリでも定義によってブランチや成果物が違うことがあるためである。差し込みは今の `template_apply` を使い、差し込んだ値は再解釈しない。

値を 1 行に限り、バッククォートを除くのは、差し込んだ値で定義の節の区切りやコードブロックが変わらないようにするためである。改行を許すと、値の中の `##` で始まる行が新しい定義の見出しとして読まれる。

## 設定の確認

設定の誤りは、登録を始める前に止める。見つけた誤りは 1 件目で止めず、すべてを 1 行ずつ表示してから止める。

確認は 2 回に分ける。ファイルだけで決まる誤りは拡張の確認で、選んだリポジトリが要る誤りは質問のあとで見る。

| 時機 | 処理 | 見る誤り |
| --- | --- | --- |
| 拡張の確認（`choose_extension`） | `lib/extensions.py` | 形と名前と値の決まりに合わないもの。定義にない名前・範囲が `member` の名前・同じ名前の定義の重なり・足りない値・指示の外の `{{target.*}}` |
| 質問のあと（`check_autopilot_targets`） | `lib/autopilot-targets.sh` | セットアップで選んでいないリポジトリ。紐付けだけのリポジトリも選んでいないものとして扱う |

足りない値は、書いた定義とリポジトリの組ごとに、その定義の節が使う `{{target.*}}` がすべてあるかで見る。設定に書いていない定義が `{{target.*}}` を使うときも、値がないので誤りにする。使わない値があっても誤りにしない。

`lib/extensions.py` は、原本と拡張の `autopilots.md` を合わせた文から定義を読む。見出しと範囲の行は、`autopilot_sections` と同じ規則で読む。役のマークは無視し、外した役の定義も名前として認める。

確認が通ると、`lib/extensions.py` は正規化した設定を作業場所の `extension-autopilot-targets.json` に書く。リポジトリは小文字にし、値の名前は `target.<値の名前>` のキーにする。設定がないときは空のオブジェクトを書く。

表示は次の形にする。どの場合も、オートパイロットやエージェントの登録は何も変えずに止まる。

```text
autopilot-targets.json: DAST の結果の確認 example/app: 値 artifact がありません
autopilot-targets.json: Wiki の確認: 定義にない名前です
autopilot-targets.json: DAST の結果の確認: target.branch は指示の中にだけ書けます
autopilot-targets.json: DAST の結果の確認 example/wiki: セットアップで選んでいないリポジトリです
```

選んでいないリポジトリを誤りにするのは、書き誤りで定期確認が作られないまま気づかれないことを避けるためである。

## 定義の展開

`prepare_autopilots` は、役で絞った定義を節ごとに分け、リポジトリと節の組ごとに展開する。今はファイル全体をリポジトリごとに 1 回展開しているが、値が定義ごとに違うので節ごとにする。

節の分け方は `autopilot_sections` と同じで、`text` のコードブロックの外にある、`##` と空白で始まる行で分ける。最初の見出しより前の文は登録しないので、展開しない。

リポジトリと節の組ごとに、次のとおり扱う。

1. 節の定義の名前が設定にあり、そのリポジトリが対象にないときは、その組を飛ばす
2. 展開の値は、今の値に `repository` と、設定にある `target.<値の名前>` を足したものにする
3. `template_apply` で節を展開し、リポジトリごとにつないでから `autopilot_sections` で読む

範囲が `member` の節は、今と同じく最初のリポジトリの値で 1 回だけ展開する。名前の重なりと担当の確認は、今のまま `autopilots.json` の全体で行う。

対象から外した組は `autopilots.json` に入らない。そのため、作成と更新の対象にならず、次の節の一時停止と、導入の確認の対象からも外れる。

## 流し直しでの登録の扱い

対象から外した kit 管理の登録は、今の一時停止の処理で一時停止する。新しい処理と表示は足さない。

今の処理は、元の名前の規則（`autopilots.known`）に合い、`autopilots.json` にない登録を一時停止の候補にする。リポジトリは選んだままなので、役や定義を外したときと同じ経路（定義にない登録の分岐）を通り、次がそろう登録だけを止める。

- 同じプロジェクトにある
- 担当が、この実行で管理する役のエージェントで、その役の今の担当と同じ
- 状態が `active` か `paused` である

止めた登録は、名前を「一時停止しました」と表示し、「外した役のエージェントを消すか決める」のタスクの対象に足す。登録と履歴とトリガーは消さない。

次の登録は変えない。「保持しました（別の担当）」の表示は、リポジトリを選択から外したときの分岐だけで出し、この分岐では出さない。

- 担当が今の管理する役のエージェントと違う登録と、別のプロジェクトの登録。この分岐は表示せずに飛ばす
- 名前の規則に合わない、利用者が作った登録
- 人間が止めた登録。セットアップは一時停止を再開しない

同じ設定でもう一度流すと、止めた登録は `paused` のままで書き込みは起きない。対象のままの登録は名前で見つかり、内容が同じなら書き込まない。起票は対象ごとのマークで重ならないので、作成も変更も 0 件になる。

対象に戻したリポジトリの登録は、名前で見つけて指示とスケジュールを合わせるが、一時停止は再開しない。今のリポジトリを選び直したときと同じ扱いである。kit には、自分が止めた登録と人間が止めた登録を分ける記録がなく、再開すると人間の止めた状態を変えるためである。

戻した登録は、導入の確認で要確認になる。理由は「一時停止しています。止めたままでよいか確認し、動かすなら画面で再開してください。」にし、再開の操作が分かるようにする。

## Webhook の扱い

Dependabot の Webhook の登録とタスクは、「Dependabot の PR の週次の確認」の対象のリポジトリだけで行う。対象から外したリポジトリには、登録もその設定を頼むタスクも作らない。

`prepare_project_webhooks` は、選んだリポジトリを設定で絞った一覧を回す。作る間の一覧に出す数（`webhook_summary`）も、絞った数にする。

フィルターの設定を頼むタスク（「OWNER/REPO の Dependabot の Webhook のフィルターを設定する」）は、`prepare_project_issues` が起票する。この起票も、同じ絞った一覧だけで行う。ほかのリポジトリごとの起票（`AGENTS.md` と作業別のルールを置くタスク）は、定期確認と関わらないので絞らない。

対象から外したリポジトリは、前の実行の Webhook が残っていないかを見る。見るのは Multica のトリガーの種類だけで、トリガーも GitHub の Webhook も消さない。

| 外したリポジトリの状態 | 扱い |
| --- | --- |
| kit 管理の Dependabot の登録がない | 何も表示せず、起票もしない |
| 登録があり、Webhook のトリガーがない | 何もしない |
| 登録があり、Webhook のトリガーが残っている | 残っていると表示し、「Dependabot の Webhook を外す」を起票する |
| 一覧や登録を読めない | 確認できないと表示する |

起票は、Webhook を使わない答えのときと同じ種類のタスクを使い、リポジトリごとのマークで重ならないようにする。タスクの本文は、Webhook を使わない答えと、対象から外したリポジトリの両方に読めるように直す。

登録がないときに黙るのは、初めから対象にしなかったリポジトリで毎回警告が出ないようにするためである。そのため、登録の一覧を読めなかったときと、登録がないときを分ける。

完了の表示は、残っている理由ごとに文を分ける。外したリポジトリの文は「Dependabot の確認の対象から外しましたが、前の実行で作った Webhook のトリガーが残っています。外すよう起票しました。」にする。

## 確認の表示と導入の確認

セットアップの確認の表示と導入の確認は、対象から外した分を不足や失敗として扱わない。どちらも、設定で絞ったあとの一覧だけを数える。

確認の表示の計画は、リポジトリごとに原本の 2 つの定期確認を並べている。この並びを設定で絞り、対象から外したリポジトリの分は出さない。役を外すときの一覧（外す役の行）も、同じく対象のリポジトリの分だけを並べる。

導入の確認（`installation_autopilots`）は、`autopilots.json` にある登録だけを確認する。対象から外した分は `autopilots.json` に入らないので、確認の対象は変えない。テストで、絞った状態で確認が通ることを見る。

変えるのは、要確認の理由だけである。定義と一致し、状態だけが `paused` の登録は、理由を「一時停止しています。止めたままでよいか確認し、動かすなら画面で再開してください。」にする。ほかの不一致は、今の「定義と一致しません。」のままにする。

## 入力と信頼

この設計は、拡張から定義の文に値を差し込み、kit 管理の登録の状態を変える。そのため、読む入力ごとに信頼する条件を決め、合わない入力は使わない。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| 拡張の `autopilot-targets.json`（拡張のディレクトリに書ける人） | 対象の絞り込みと値の差し込み | 形・名前・値の決まりに合い、定義と選んだリポジトリに一致する | 登録を始める前に止め、誤りをすべて表示する |
| 設定の値（同じく拡張のディレクトリに書ける人） | 定期確認の指示の文 | 1 行で 200 文字以下、制御文字・バッククォート・`{{`・`}}` を含まない | 登録を始める前に止める |
| 選んだリポジトリ（セットアップを流す人の答え） | 設定のリポジトリとの照合 | 今の質問の答えで、リポジトリの一覧の検証を通ったもの | 選んでいないリポジトリを書いた設定は止める |
| Multica の既存のオートパイロット（kit・ほかの人・人間が作れる） | 一時停止の候補 | 同じプロジェクトで、担当が管理する役の今の担当、名前が元の名前の規則と選んだリポジトリの形に合う | 変えずに飛ばす。対象から外したリポジトリでは表示しない |
| Multica のトリガーの種類（kit と人間が作れる） | 外したリポジトリの Webhook の残り | 管理する Dependabot の役が担当する、同じプロジェクトの登録のトリガー | 起票しない。読めないときは確認できないと表示する |

Webhook の URL と署名の秘密は、この設計では読まない。外したリポジトリでは、トリガーの種類だけを見る。

## 文書と指示の変更

利用者向けの文書には、設定の書き方と、流し直しでの動きを書く。原本の役の指示と共通スキルは変えない。

| ファイル | 変えること |
| --- | --- |
| `EXTENSIONS.md` | 「決まりの要約」に絞り込みの例外を、新しい「`autopilot-targets.json`」の節に形と差し込みと誤りの扱いを書く。「拡張から消したときの扱い」に、全リポジトリへ戻ることを書く |
| `manual.md` | 「更新と、途中で止まったあとの再実行」の表に、対象を絞ったときの一時停止と、戻したときに再開しないことと再開の手順を書く。「Dependabot の Webhook の登録」と「Dependabot の Webhook を外す」に、外したリポジトリの扱いを書く |
| `manual.md` の起票の一覧 | 「外した役のエージェントを消すか決める」の条件に、定期確認の対象から外したときを足す。フィルターの設定の条件を、確認の対象のリポジトリごとにする |
| `common/autopilots.md` | 見出しより前の説明の「リポジトリごとに 1 つにする」に、拡張の設定で対象を絞れることを足す。定期確認の見出しと指示の文は変えない |
| `common/setup-issues.json` | 「Dependabot の Webhook を外す」の本文を、対象から外したリポジトリにも読めるように直す |
| `docs/setup-completion.md` | 起票の表の「Webhook を外す」の条件に、対象から外したリポジトリを足す。「フィルターの設定」の条件を、確認の対象のリポジトリにする |
| `docs/screens.md` の導入の確認 | 要確認の理由の例に、一時停止の理由を足す |
| `docs/screens.md` | 完了の表示の例に、対象から外したリポジトリの Webhook の行を足す |

例外を「追加と追記だけ」の決まりに足すのは、原本の定義の中身を置き換えず、作る範囲だけを狭めるためである。原本の指示・モデル・共通スキル・ガードは、今までどおり置き換えられない。

## 互換性

設定のない拡張と、拡張のないプロジェクトでは、登録の名前・指示・スケジュールが今と同じになる。既存のテストは、そのまま通す。

節ごとの展開は、設定がないとき、今のファイル全体の展開と同じ `autopilots.json` を作る。見出しより前の文は今も登録に使っていないので、展開しなくても結果は変わらない。

既存の拡張の定義は、`{{target.*}}` を使っていない。そのため、設定がなくても値の不足は起きない。

`autopilot-targets.json` は、拡張の確認で知っている項目に足す。古いバージョンの原本は、このファイルを含む拡張を「未知の拡張の項目」として止める。拡張の `kit-version` が原本のバージョンと同じであることを今も求めているので、混ざって動くことはない。

設定を消した、または拡張を外したときは、原本の 2 つの定期確認は選んだすべてのリポジトリに戻る。前に止めた登録は再開せず、導入の確認が一時停止の理由で要確認にする。`manual.md` に再開の手順を書く。

導入の確認の理由を分けても、要確認の数と起票は変わらない。今のテストは理由の文の有無を見るだけで、定義と違う項目は今の理由のまま残る。

| 選んでいないリポジトリを書いた設定で、登録の前に止まり、書き込みがない | `tests/autopilot-targets-test.sh` |

## 残る危うさ

対象に戻したリポジトリの登録は、止めたままになる。人間が画面で再開するまで、その定期確認は動かない。導入の確認は、一時停止の理由で要確認にし、再開の操作を示す。

止める処理は、担当が今の管理する役のエージェントと同じ登録だけを対象にする。人間が担当を別のエージェントに替えた登録は、対象から外しても止まらず、表示もない。役や定義を外すときの今の扱いと同じで、新しい表示は足さない。

定義の名前は見出しから読むので、拡張の作者が見出しを変えると、設定の名前と合わなくなる。この場合は「定義にない名前」で止まるので、気づかずに全リポジトリへ戻ることはない。

設定の値は、拡張のディレクトリに書ける人が定期確認の指示に入れられる。拡張の指示の追記と同じ信頼の範囲で、値の決まりは文の構造を壊さないことだけを守る。

## 検討した案

設定は定義の名前で絞り、拡張のディレクトリの 1 つのファイルに置く案を選んだ。ほかに検討した案と、選ばなかった理由を次に書く。

### 定義の名前でなく役のキーで絞る

役のキーで絞ると、同じ役の定義が 2 つ以上あるとき、別々に絞れない。拡張は 1 つの役に複数の定期確認を置けるので、定義の名前を使った。

### 定義の側に対象の行を足す

`autopilots.md` の節に `- 対象:` の行を足す案である。原本の 2 つの定義の文面を拡張から変えられないので、原本の分を絞れない。設定を 1 つのファイルにまとめた。

### セットアップの質問で聞く

定義とリポジトリの組ごとに質問が増え、値まで聞くと答えが長くなる。拡張と同じく、ファイルを用意して流す形にした。

### リポジトリの役割から対象を決める

プロジェクトの説明の役割の表は、人が読む文で、形が決まっていない。推測で対象を決めると、誤って作らないことに気づきにくい。対象は設定に書いたものだけにした。

### 対象から外した登録を消す

消すと履歴も消え、誤った設定を戻しても取り返せない。今のリポジトリを外すときと同じく、一時停止にとどめた。

### 設定を保存する答えに置く

答えのファイルは前回の値を質問の既定にするだけで、登録の正本にしない決まりである。拡張のディレクトリに置けば、拡張と同じくバージョン管理と見直しの対象になる。
