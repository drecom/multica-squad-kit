# 評価の見本に、回す役の pick の応答があるかを確認する

リーダーの評価の場面で、合格の基準が回す先とする役ごとに、`cli.json` に `squad-usage-wait pick` の応答の見本があるかを、本物のモデルを呼ばないテストで確認する。見本が欠けた場面は、評価を流す前に CI で落とす。

この文書は、pick の見本の形と、欠けを見つける判定の決まりを書く。決まりに当てはまらない場面（例外）の扱いと、テストの設計、その理由も書く。評価の仕組みと場面の形は [leader-principles.md](leader-principles.md#評価) にある。

## 目的と範囲

リーダーの手順は、要件を決める役と設計の役へ頼む前に pick を流すと決めている（`leader-flow.md`）。場面の見本に回す先の役の pick の応答がないと、見本にない呼び出しはスタブが失敗（終了コード 1、出力なし）を返す。すると、手順どおりに動いたリーダーが失敗の応答を受けて迷う。

この欠けは、本物のモデルで評価を流さないと見つからない。評価は使用枠と手元の CPU・メモリを多く使うので、見本の欠けで流し直すのは避けたい。そこで、場面の基準と見本だけを読む静かな確認を CI で行い、この種類の欠けを流す前に見つける。

次は対象にしない。

- 評価の流し直し。見本を直したあとの合否は、評価を流して確認する
- `scene.md`、リーダーの指示（`common/agents/orchestrator.md`）、squad-handoff の変更
- pick 以外のコマンドの見本の欠け。どのコマンドを流すかは手順の読み方で変わり、基準から機械で決められないため
- 評価そのものを軽くすること

## pick の見本の形

回す先の役の pick の見本は、ほかの場面の pick の見本と同じ形にする。終了コードは 0 で、`役:` と `振り分け:` の 2 行を返す。

| 場面 | `match` | 出力の形 |
| --- | --- | --- |
| add-2 | `squad-usage-wait pick issue-shop-1 designer` | `役: designer` と、`振り分け:` で始まり `。工程: designer` で終わる行 |
| add-4 | `squad-usage-wait pick issue-shop-1 planner` | `役: planner` と、`振り分け:` で始まり `。工程: planner` で終わる行 |

`振り分け:` の行の中身は、同じ場面の principal の見本と同じ使用率（Claude 週 20%、Codex 週 30%）にする。`exit` は省略し、スタブの既定の 0 を使う。`expected_records` に pick は挙げない。pick は読み取りの呼び出しのためである。

## 判定の決まり

場面ごとに、合格の基準が求める「回す先の工程」を集め、工程ごとに pick の見本があるかを見る。集めるのは `[記録]` の判定の式だけで、`[採点]` の文は読まない。

### 工程を集める

`[記録]` の判定の式を ` && ` で項に分け、次の 2 種類の項から工程を集める。項の分け方は、評価の判定（`parse_predicate`）と同じにする。

1. 回す先の項: `posted:` の項で、正規表現が `mention://agent/` を含むもの。基準が「この役をメンションして回す」と求めている
2. pick の項: `called:` の項と、`before:` の左側で、正規表現が `squad-usage-wait pick` を含むもの。基準が pick を流すこと自体を求めている

`not-posted:` と `not-called:` は、呼ばないことの確認なので集めない。

回す先の項は、正規表現のうち `mention://agent/` の直後から、空白か、対になっていない `)` の前までを ID の部分とする。ID の部分を、`values.json` のすべての `agent.<役>.id` の値に全体一致で照らし、一致した役を工程に直す。

| 一致した役 | 工程 |
| --- | --- |
| `planner` | `planner` |
| `designer` | `designer` |
| `claude-implementer`、`codex-implementer` | `implement` |
| `claude-fixer`、`codex-fixer` | `fix` |
| `claude-principal`、`codex-principal` | `principal` |
| 上のどれでもない役（レビュー、QA、見張り、リーダーなど） | なし。pick を流さずに頼む役のため |

`agent-(claude|codex)-fixer` のように選択を含む正規表現は、一致した役がすべて同じ工程なら、その工程とする。一致した役の工程が 2 つ以上に分かれるとき（「なし」を含む）は、工程を決められないので、その項を誤りとして報告する。どの役にも一致しないときも、読めない項として報告する。基準の書き違いを、確認されないまま通さないため。

pick の項は、正規表現の中の `squad-usage-wait pick` に続く 2 つの語のうち、2 つ目の先頭の英小文字の並びを工程として読む。`fix( |$)` や `principal$` の後ろの正規表現は読まない。読んだ値が `planner`・`designer`・`implement`・`fix`・`principal` のどれでもないときは、読めない項として報告する。`before:` の右側は、呼ばれなくても判定が通るので読まない。

### 見本を照らす

集めた工程ごとに、`cli.json` の `commands` に、その工程の pick の見本があるかを見る。pick の見本は、`match` を空白で区切った 1・2 語目が `squad-usage-wait` と `pick` で、4 語目が工程と一致するものとする。3 語目のタスクと、5 語目以降（`principal Claude`、`implement 小さい` など）は問わない。

| 集めた項 | 足りるとする見本 |
| --- | --- |
| 回す先の項 | その工程の見本のうち 1 つ以上が、終了コード 0 で、出力に `振り分け:` で始まる行を持つ |
| pick の項 | その工程の見本が 1 つ以上ある。終了コードと出力は問わない |

回す先の項は、pick が役を選んだあとに回すことを求めるので、選んだことを示す見本が要る。pick の項は、待ち（終了コード 3）を確認する keep-27 のように、選べない応答も見本になるので、形を問わない。終了コードは `exit` の値で、省略時は 0 とする。

1 つの工程が両方の項から集まったときは、回す先の項の決まりで照らす。足りない工程は、場面・基準の番号・工程の組で 1 件として報告する。

### 決まりの限り

この決まりは、基準が判定の式で求める回し先と pick だけを見る。次は見つけられないので、評価の結果で確認する。

- `[採点]` の文だけが求める回し先。文を機械で読まないため
- 回す先の項がなく、基準が回すこと自体を求めていない場面で、リーダーが手順どおり pick を流すこと
- 見本の出力の中身（`役:` の行の役が工程と合うか）。`振り分け:` の行があることだけを見る

## 例外

決まりに当てはまるが pick を要らない基準は、その場面の `cli.json` のキー `pick_exceptions` に書く。テストは、書いた例外を除いて判定し、書いた例外が今も要るかも確認する。

### 例外の書き方

`pick_exceptions` は配列で、1 件が 1 つの基準と工程の組を表す。キーを省略したときは空の配列とする。

```json
"pick_exceptions": [
  {
    "criterion": 3,
    "process": "implement",
    "reason": "metadata の pr_url を補ってもらうため、PR を作った実装の役へ返す。役を選び直さないので pick を流さない"
  }
]
```

| キー | 値 |
| --- | --- |
| `criterion` | 例外にする `[記録]` の基準の番号。整数 |
| `process` | 例外にする工程。`planner`・`designer`・`implement`・`fix`・`principal` のどれか |
| `reason` | pick を要らない理由で、空でない文字列。手順のどの決まりによるかを書く |

例外は、指定した基準の指定した工程だけを外す。同じ場面のほかの基準や、同じ基準のほかの工程は、通常どおり判定する。

### 例外を誤りとするとき

次のどれかに当たる例外は、誤りとして報告する。古くなった例外が欠けを隠さないようにするため。

1. `criterion` の番号の基準がないか、`[記録]` でない
2. `process` が 5 つの工程のどれでもない。`reason` がないか空である
3. 同じ `criterion` と `process` の組が 2 件以上ある
4. その基準から、決まりがその工程を集めない。基準が変わり、例外が要らなくなった
5. 例外がなくても、その工程の見本が足りている。見本が足され、例外が要らなくなった

`pick_exceptions` が配列でないときと、要素がオブジェクトでないときも、誤りとして報告する。

### 今の例外

今の場面で例外に当たるのは、keep-3 の基準 3 の `implement` だけである。

keep-3 は、実装の役が PR を返したが、metadata に `pr_url` がない場面である。手順（`leader-pr-checks.md`）は、`pr_url` がなければ PR を作った役に補ってもらうと決めている。これは新しく役を選ぶのではなく、成果物を出した役へ返すことなので、pick を流さない。基準 3 は `posted: mention://agent/agent-claude-implementer` で、決まりは `implement` を集めるので、例外に書く。

## サブコマンドの I/F

確認は、場面の補助 `leader_eval.py` のサブコマンド `picks` で行う。基準の式の読み方を、評価の判定と同じ関数（`parse_scene`、`parse_predicate`）で共有するため。

```text
python3 -I -B tests/leader-eval/leader_eval.py picks <場面のディレクトリ> <values.json>
```

`<場面のディレクトリ>` の直下の、`scene.md` と `cli.json` を持つディレクトリを、名前の順にすべて確認する。どちらかがないディレクトリは、場面ではないので飛ばす。

| 結果 | 終了コード | 標準出力 |
| --- | --- | --- |
| 欠けも誤りもない | 0 | `pick の見本: <場面の数> 場面を確認した` の 1 行 |
| 欠けか誤りがある | 1 | 1 件 1 行。場面の名前の順、基準の番号の順に並べる |
| 引数の誤り、`values.json` や `cli.json` を読めない | 2 | なし。標準エラーに理由を出す |

欠けと誤りの行は、次の形にする。テストは行をそのまま比べるので、形を変えるときはテストも変える。

| 種類 | 行の形 |
| --- | --- |
| 見本の欠け | `<場面>: 基準 <番号>: <工程> の pick の見本がない` |
| 見本はあるが選んだ応答でない | `<場面>: 基準 <番号>: <工程> の pick の見本に、終了コード 0 で振り分けの行のある応答がない` |
| 読めない項 | `<場面>: 基準 <番号>: 回す先を決められない: <項>` |
| 例外の誤り | `<場面>: pick_exceptions <添字>: <理由>` |

`<項>` には、基準の式の項をそのまま写す。場面のファイルは公開のリポジトリにあり、実在の値を含まないので、写してよい。

## テスト

テスト `tests/leader-eval-picks-test.sh` は、`claude` と `codex` を起動せず、`python3` と `jq` だけで流す。`tests/run.sh` が `tests/*-test.sh` として拾い、CI の macOS と Ubuntu で流れる。

テストは、本物の場面を一時ディレクトリへ写し、写しの `cli.json` を `jq` で変えて `picks` を流す。リポジトリの場面は書き換えない。一時ディレクトリは、ほかのテストと同じくリポジトリの `tmp/` の下に作り、終わったら消す。

| 確認すること | 方法 | 期待する結果 |
| --- | --- | --- |
| 今の場面が通る | リポジトリの場面と `values.json` で流す | 終了コード 0 |
| add-2 と add-4 の欠けを落とす | 写しで、add-2 の designer と add-4 の planner の見本を消す | 終了コード 1 で、欠けの行が add-2 の基準 1 の designer と add-4 の基準 1 の planner の 2 行だけ |
| fix の見本の欠けを落とす | 写しで、keep-26 の fix の見本を消す | keep-26 の欠けの行が出る |
| principal の見本の欠けを落とす | 写しで、keep-8 の principal の見本（`principal Codex` などの後ろの語を含む）をすべて消す | keep-8 の欠けの行が出る |
| pick の項は待ちの見本でも足りる | リポジトリの keep-27（終了コード 3 の見本だけ）で流す。写しで、その見本を消す | 今の場面は通る。消した写しでは keep-27 の基準 2 の欠けの行が出る |
| 選んだ応答でない見本を落とす | 写しで、add-2 の designer の見本の終了コードを 3 にする | 選んだ応答でない行が出る |
| implement の回し先を照らす | keep-3 の写しから `pick_exceptions` を消す | keep-3 の基準 3 の implement の欠けの行が出る |
| 選択を含む正規表現を照らす | 6-1 の写しで fix の見本を消す | 6-1 の基準 2 の fix の欠けの行が出る |
| 工程が分かれる項を落とす | 合成の場面に `posted: mention://agent/agent-(designer\|planner)` を置く | 回す先を決められない行が出る |
| どの役にも一致しない項を落とす | 合成の場面に `posted: mention://agent/agent-nobody` を置く | 回す先を決められない行が出る |
| 回す先でない役を求めない | 合成の場面に `posted: mention://agent/agent-qa` を置き、pick の見本を置かない | 終了コード 0 |
| 古い例外を落とす | keep-3 の写しに implement の見本を足す。別の写しで基準 3 の式を `posted:` のない式にする | どちらも、例外が要らない誤りの行が出る |
| 例外の形の誤りを落とす | keep-3 の写しで、`reason` を空に・`criterion` を 4（`[採点]`）や 9（ない番号）に・`process` を `review` に・同じ組を 2 件に変える | それぞれ例外の誤りの行が出る |

合成の場面は、テストの中で `scene.md` と `cli.json` を書いて作る。今の場面に、`planner`・`designer`・`implement` の欠けを作れる見本が足りないので、工程ごとの欠けも合成の場面で 1 件ずつ確認する。それぞれ、見本がないと欠けの行が出て、見本を置くと終了コード 0 になることを見る。

テストの重みは、場面の確認（`tests/leader-eval-test.sh` の 30）より軽く、`tests/test-weights` に 5 で置く。

## 残る危うさ

決まりは、判定の式に回し先が書かれた基準だけを見る。回し先を `[採点]` だけで求める場面や、基準が求めずにリーダーが pick を流す場面の欠けは、評価を流して見つける。

ID の部分の読み方は、今の場面の式の形（`mention://agent/` の直後に役の ID の正規表現が続く）に合わせている。これと違う形の式を書くと、読めない項として落ちるので、基準の書き方をそろえるか、決まりを広げる。

## 検討した案

例外の置き場所、確認の置き場所、keep-3 の扱いについて、次の案を比べた。採ったのは、例外を場面の `cli.json` に書く案である。確認は専用のテストに置き、keep-3 の見本には implement の pick の応答を置かない。

| 案 | 採るか | 理由 |
| --- | --- | --- |
| 例外を場面の `cli.json` に書く | 採る | 例外が場面のそばにあり、場面を写すと例外も一緒に動く。`planner` や `ci_monitor` のように、場面ごとの設定を `cli.json` に置く前例がある |
| 例外を `scene.md` にマークで書く | 採らない | `scene.md` にマークを足さない。基準の文に評価と関係のないマークが混ざる |
| 例外をテストの中に一覧で書く | 採らない | 場面と例外が離れ、場面の ID を変えたときに一覧が古くなりやすい |
| keep-3 に implement の pick の見本を足し、例外をなくす | 採らない | 手順は `pr_url` がないとき pick を流さないので、手順にない応答を見本に置くことになる。評価の入力も変わる |
| 確認を `tests/leader-eval/run.sh` の流す前にも入れる | 採らない | CI で落とせば足り、評価の仕組みを変えない範囲に留めるため |
| 確認を `tests/leader-eval-test.sh` に足す | 採らない | このテストは 700 行を超え、CI の重みも大きい。別のファイルにすれば、CI の分け方で別の組に回せる |
| `[採点]` の文からも回し先を読む | 採らない | 文は機械で読めず、読み違えが誤った欠けを出す |
