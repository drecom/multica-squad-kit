# コードレビューの見逃しを、指示の新旧で比べる

コードレビュアーが実際に見逃した指摘を評価の場面にし、今のコードレビュアーの指示（`common/agents/code-reviewer.md`）と、変えた指示を同じ場面で流して比べる。指示を直したとき、見逃しが減ったかを確認するためである。

この文書は、評価を流す人と場面を足す人に向けて、道具の作りと、新旧の比べ方と合格の決め方を書く。流す回数の上限と場面を足す条件、元の出来事との対応の残し方も書く。リーダーの評価の仕組みは [leader-principles.md](leader-principles.md#評価) にあり、この評価はそれを使う。ここには、コードレビュアーで違うところだけを書く。

## 目的と範囲

コードレビュアーの見逃しは、あとの工程で人間が見つけるまで残る。指示を直しても、同じ見逃しが減ったかは、本物のモデルで流さないと分からない。一方で、評価は使用枠を多く使う。そこで、人間が見逃しと認めた出来事だけを場面にし、人間が頼んだときだけ、決まった回数の中で流す。

次は対象にしない。

- 配布するコードレビュアーの指示と、共通のスキルの変更。この評価は、変えた指示を比べる道具で、指示そのものは変えない
- コードレビュアー以外の役（セキュリティ、QA など）への広げ
- 本物のモデルで流した結果の判断。合否を読んで指示を採るかは、流すよう頼んだ人間が決める

## 道具の作り

リーダーの評価の道具を広げて使い、この節にはコードレビュアーで違うところだけを書く。

### 流す仕組み

リーダーの評価の道具 `tests/leader-eval/run.sh` に、役の指定 `--role code-reviewer` を足す。場面の形とスタブの CLI は、リーダーの評価と同じものを使う。作業ディレクトリの分離と採点の役と記録の形も同じにする。新しい道具を別に作らないのは、スタブと分離と採点の決まりを二重に持たないためである。

| 項目 | リーダーの評価 | コードレビュアーの評価 |
| --- | --- | --- |
| 役の指定 | `--role orchestrator`（既定）か `principal` | `--role code-reviewer` |
| 場面の置き場所 | `tests/leader-eval/scenes/` ほか | `tests/leader-eval/reviewer-scenes/<場面の ID>/` |
| 場面の ID | `add-1` など | `review-<n>`（`n` は 1 からの連番） |
| 比べる指示 | `common/agents/orchestrator.md` と squad-handoff | `common/agents/code-reviewer.md` と squad-handoff |
| 流すランタイム | `claude` か `codex` | `claude` だけ。`--runtime codex` は終了コード 2 で止める |
| 流す回数の上限 | なし | 1 回の評価で 18 回（[流す回数の上限](#流す回数の上限)） |

`--role code-reviewer` の `--scenes` を省いたときは、`reviewer-scenes` のすべての場面を流す。`--old-skills new` と `--thinking` は、コードレビュアーでは受け付けず、終了コード 2 で止める。比べる軸を、指示の新旧の 1 つに絞るためである。

### 役の指示の作り方

今の指示は、`--baseline` の参照（既定は `origin/main`）の `common/agents/code-reviewer.md` と、同じ参照の squad-handoff から作る。新しい指示は、作業ツリーの同じファイルから作る。どちらも、リーダーの評価と同じく `lib/render.sh` のひな形の展開と `tests/leader-eval/values.json` の値で描画する。

前置きの文書 `tests/leader-eval/runtime-brief.md` は、Agent Identity の名前と ID を `agent.code-reviewer.` の値に替えて渡す。`values.json` には、`agent.code-reviewer.id`・`.name`・`.mention` がすでにある。

### 流すモデル

流す役のモデルと思考の深さは、描画した指示の front matter の値を使う。`claude` のランタイムでは、`claude-sonnet-5-5` と `high` になる。配布するコードレビュアーが実際に動くモデルで比べるためである。新旧で front matter のモデルが違うときは、それぞれの値で流し、記録にモデルを並べて書く。

採点の役は、リーダーの評価と同じ `claude-opus-5-5` の `high` に固定する。

### 作業ディレクトリと道具

作業ディレクトリの分離と、許可する道具は、リーダーの評価と同じにし、次の 3 つだけを足す。

1. git のスタブを必ず使う。依頼の `確認するコミット:` を手元に用意するため、場面の `cli.json` に `"git": true` と `git fetch`・`git checkout`・`git rev-parse` などの見本を置く
2. `Skill(verify)` を許可する。指示が `verify` のスキルを読むので、場面の `files` に、架空のプロジェクトの検証の手順を書いた `.claude/skills/verify/SKILL.md` を置く
3. PR へのコメントを記録する。`gh pr comment` と `gh pr review` を書き込みとして扱い、`--body-file` と `--body` の本文を投稿として記録して、タスクのコメントと同じく採点の役に渡す

3 の扱いは、`--role code-reviewer` のときだけにする。リーダーの評価で、見本にない `gh pr comment` が失敗を返す今の動作を変えないためである。

## 新旧の比べ方と合格の決め方

1 回の評価では、選んだ場面ごとに、今の指示と新しい指示をそれぞれ `--runs` の回数（既定は 3）流す。1 回の実行は、エラーがなく、合格の基準をすべて満たしたときに合格とする。判定はリーダーの評価の `[記録]` と `[採点]` のとおりである。

新しい指示は、選んだすべての場面で、すべての回が合格したときに合格とする。3 回のうち 1 回でも見逃すなら、見逃しが減ったとは言えないためである。今の指示の結果は、比べるために並べて書き、合否には使わない。

`summary.md` の表は、リーダーの評価と同じ列にし、役の名前だけを替える。

| 場面 | 型 | 今の指示 | 新しい指示 | 落ちた基準 |
| --- | --- | --- | --- | --- |
| review-1 | 見逃し | 0/3 | 3/3 | - |

今の指示も 3/3 で通る場面は、表の下に「今の指示でも通る場面」として挙げる。その場面は、指示の変更が効いたことを示さないためである。場面は消さず、今の指示で通らなくなる変更を見つける場面として残す。

## 流す回数の上限

1 回の評価で流す役の実行は、18 回までにする。数え方は、場面の数 × `--runs` × 流す指示の数（`--only` がなければ 2）である。3 つの場面を、3 回ずつ、新旧で流すと 18 回になる。採点の役の呼び出しは数えない（場面ごとの基準の数 × 役の実行の回数で、基準が 3 つなら最大 54 回）。

`run.sh` は、役の実行を始める前に回数を数え、18 を超えるときは、何も流さずに終了コード 2 で止める。止めたときは、数えた回数と上限を出す。

上限を超えて流すのは、人間に頼んで承認を得たときだけにする。承認を得たら、承認したコメントの ID を `--over-limit <コメントの ID>` で渡す。`run.sh` はその ID を `summary.md` の先頭に書き、上限を超えて流したことを記録に残す。`--over-limit` を、承認を得ずに使わない。

1 回の評価は、`run.sh` の 1 回の実行とする。合否を見たあとに流し直すのは、別の評価として、もう一度人間に頼む。

`run.sh --help` には、上限の 1 行と、この節への案内を出す。

## 誰がいつ流すか

本物のモデルで流すのは、人間がタスクのコメントで流すよう頼んだときだけにする。次のときは流さない。

- 作るとき。実装と修正の役は自動のテストだけを流し、場面を足したときは [review-rework.md](review-rework.md#テスト) の、評価の場面を足した実装の決まりに従う
- CI と `tests/run.sh`。`run.sh` はリーダーの評価と同じく、CI のテストの一覧に入れない
- レビューと最終レビュー。結果を確認するために流さない

## 場面を足す条件

場面は、人間がコードレビュアーの見逃しを見逃しと認めたときだけ、1 件ずつ足す。認めたことは、タスクのコメントで人間が書いたものに限る。エージェントが見逃しと考えただけでは足さない。

1 つのタスクで足す場面は 1 つにする。場面ごとに、置き換えと元の出来事との対応を確認できるようにするためである。

場面が 4 つ以上になると、すべての場面を新旧で 3 回ずつ流すと 18 回を超える。そのときは、`--scenes` で 3 つまでに絞るか、[上限](#流す回数の上限)のとおり人間に頼む。どの場面を流すかは、流すよう頼む人間が決める。

## 場面の形

`scene.md` と `cli.json` の形は、リーダーの評価の場面と同じである。コードレビュアーの場面では、次のとおりにする。

| 項目 | 書くこと |
| --- | --- |
| `- 場面の ID:` | `review-<n>` |
| `- 型:` | `見逃し` |
| `## 元の出来事` | 見逃した指摘の中身。名前と ID は置き換えたものだけを書く |
| `## 入力` | リーダーのレビューの依頼のコメント。`確認するコミット:` と `返事を待つ役:` の行を含める |
| `## 合格の基準` | 見逃した指摘を場所と影響つきで挙げ、指摘があるのに結論のマークを ✅ にしないこと。`確認したコミット:` の行に依頼のコミットを書くこと |

見逃した指摘が 2 つあり、同じ PR の同じ種類の誤りなら、1 つの場面にまとめてよい。

実在のプロジェクト・人・ID は書かない。名前の置き換えと、UUID を使わない決まりは、リーダーの評価と同じである（[leader-principles.md](leader-principles.md#評価)）。プロジェクトは `shop`、人は `member1`、エージェントは `values.json` の値を使う。コミットの SHA は、元のコミットの値を使わず、作った値にする。

## 元の出来事との対応の残し方

場面のファイルには、置き換えた名前だけを書く。元の出来事との対応は、場面を足すタスクのコメントに残す。

実装の役は、場面を置いたフェーズで、そのタスクに 1 つのコメントを書く。コメントには次を書く。

| 項目 | 書くこと |
| --- | --- |
| 場面の ID | `review-<n>` |
| 元の PR | リポジトリと PR の番号 |
| 元のコミット | 見逃したコミットと、直したコミットの SHA |
| 元の場所 | 見逃した指摘のファイルと行 |
| 名前の対応 | 場面の名前・ID・コミットと、元の値の対応 |

コメントを書いたら、そのコメントの ID をフェーズの結果に添える。レビューは、場面のファイルに元の値が残っていないことと、対応のコメントがあることを確認する。

## 場面と道具を確認するテスト

本物のモデルを呼ばないテストを、`tests/leader-eval-test.sh` に足す。リーダーの評価のテストと同じく、スタブの `claude` で流し、CI の `tests/run.sh` で動く。

| 確認すること | 満たしたと言える状態 |
| --- | --- |
| 指示の作り | `--role code-reviewer` で、今の指示が基準の参照の `code-reviewer.md`、新しい指示が作業ツリーの `code-reviewer.md` から作られ、前置きの名前が `agent.code-reviewer.` の値になる |
| 流すモデル | スタブに渡るモデルと思考の深さが、描画した front matter の値になる |
| 上限 | 19 回以上になる指定は、スタブの `claude` を一度も呼ばずに終了コード 2 で止まり、18 回ちょうどは流れる。`--over-limit` を付けると流れ、`summary.md` にコメントの ID が載る |
| 受け付けない指定 | `--runtime codex`・`--old-skills new`・`--thinking` が、終了コード 2 で止まる |
| PR へのコメント | `gh pr comment --body-file` の本文が投稿として記録され、採点の役に渡る。リーダーの評価では、今のとおり見本にない呼び出しになる |
| 場面の形 | `reviewer-scenes` のすべての場面が、場面の読み取りを通り、`"git": true` と `verify` のスキルのファイルを持ち、UUID を含まない |

## 検討した案

| 案 | 採らなかった理由 |
| --- | --- |
| コードレビュアーの評価の道具を別に作る | スタブと分離と採点と記録の決まりを二重に持ち、片方だけ直す誤りが起きる |
| 新しい指示だけを流す（最上位の役の評価と同じ） | 見逃しが減ったかは、今の指示の結果と並べないと分からない |
| 3 回のうち 2 回の合格で合格とする | 1 回でも見逃す指示は、実際のレビューでも見逃す。見逃しを減らす目的に合わない |
| 流す役のモデルを固定する | 配布するコードレビュアーが動くモデルと違うと、比べた結果が実際の動作を示さない |
| 上限を文書だけに書く | 場面が増えて既定の流し方が上限を超えても気づけない。流す前に止めれば、使用枠を使う前に分かる |
| 元の出来事との対応を場面のファイルに書く | 実在のプロジェクト・人・ID を場面に書かない決まりに反する |
| codex のランタイムも流す | 1 回の評価の回数が倍になり、上限の中で流せる場面が減る。要るときは、場面と上限と合わせて別に決める |
