# リーダーの指示を、目的と判断の原則を軸に書き直す

リーダーが細かい指示なしに要点をつかみ、自分で確認して決め、人間には判断だけを頼めるようにする。リーダーの指示は、役の目的と判断の優先の原則を先頭に置く形で書かれ、手順の細目は共通スキル squad-handoff の参照のファイルに置かれる。リーダーのモデルは Sonnet で、思考の深さは high である。

この文書は、リーダーの役のひな形（`common/agents/orchestrator.md`）と squad-handoff の構成、リーダーの指示の効果を確認する評価の設計と、その理由を書く。

## 目的と範囲

リーダーの指示に「X なら Y を流す」形の手順を並べると、役の目的と、何を優先して判断するかが埋もれる。書かれていない場面で判断できず、人間が細かく指示し・問い直し・催促することになる。そのため、リーダーの指示は、役の目的と判断の優先の原則を先頭に置き、手順の細目は参照のファイルへ置く。

人間が問い直した場面は、次の 6 つの型に分けられる。この設計は、型ごとに原則を 1 つ置き、評価の場面で効果を確認する。

| 型 | 起きたこと |
| --- | --- |
| 1 | 確認せずに「できない」「分からない」「見えない」と言う |
| 2 | 推測を事実のように書く |
| 3 | 決められることを人間へ投げる。報告の結論が読み取れない |
| 4 | 人間の言葉の意図を読み違える |
| 5 | 同じ失敗をそのまま頼み直し、原因と再発の防止に向き合わない |
| 6 | コンフリクトや遅れに人間が先に気づき、指示や催促をする |

この設計が決めるものは次のとおりである。

- リーダーの指示の構成と文。冒頭に役の目的と判断の優先の原則を置き、手順は場面ごとの索引から参照のファイルへ案内する
- squad-handoff に置く、リーダーだけが読む参照のファイル。リーダーの手順の細目の置き場所である
- リーダーの思考の深さ。モデルは Sonnet である
- リーダーの指示の効果を確認する評価の場面と、それを流す仕組み

次は対象にしない。

- リーダー以外の役の指示。squad-handoff の本文（`SKILL.md`）は、参照のファイルへの案内だけを持つ
- 見張りのスクリプトの動作。手順の文は参照のファイルに置き、呼び方と判定はスクリプトが持つ
- 実装・修正の役の検証の時間。型 6 は、リーダーが人間より先にコンフリクトと遅れに気づいて回すところだけを扱う
- 導入後の指標（人間の問い直し・催促・コンフリクトの解消の指示の回数）の計測。この設計の外で追う
- Multica 本体の変更

## 新しい指示の構成

リーダーの指示は、次の順の節にする。手順を一度に全部読ませず、原則で判断させ、場面に入ったときだけ細目を読ませるためである。目安の大きさは 12KB 以内とする。

| 順 | 節 | 中身 |
| --- | --- | --- |
| 1 | 冒頭の段落 | 役の目的（[役の目的](#役の目的)） |
| 2 | 判断の優先の原則 | 7 つの原則を優先の順に書く（[判断の優先の原則](#判断の優先の原則)） |
| 3 | 受け取ったら確認すること | 実行の始めの確認と、どの場面かを決めるまでに読むもの（[受け取ったら確認すること](#受け取ったら確認すること)） |
| 4 | 場面と手順 | 場面ごとに、必ずすることと、読む参照のファイルの表（[場面と手順](#場面と手順)） |
| 5 | 重要の基準 | 共通の基準 4 つと、プロジェクトの基準の読み方 |
| 6 | このスクワッドの役 | 展開で決まる事実。有効な役、系統、メンションのリンク（[このスクワッドの役](#このスクワッドの役)） |
| 7 | 人間を待つところ | 受け渡しと人間を待つところを、原則 1 の具体として書く |
| 8 | このプロジェクトの値 | 名前と ID、スクワッドと呼ぶ人間のメンションのリンク、見張りの 3 役のリンク。ほかの役のメンションのリンクは「このスクワッドの役」にあり、ここには置かない（[review-rework.md の上限の余白](review-rework.md#上限の余白)） |

重要の基準を指示に残すのは、手順ではなく判断の基準だからである。`manual.md` の「最上位の役の最終レビューと重要のマーク」も、共通の基準をリーダーの指示に書くとしている。

### 役の目的

冒頭の段落には、次の内容を書く。

あなたは {{project_name}} のスクワッドのリーダーである。合意された要件を、人間の判断の場所以外では止めずにマージ待ちまで進める。人間には判断だけを頼む。要件定義・設計・実装・修正・レビュー・テストは代行せず、有効な役へ回す。

### 判断の優先の原則

原則は 7 つで、番号の小さいほうを優先する。原則がぶつかったときに、どちらを取るかを指示の上で決めておくためである。たとえば、自分で決めて進める（原則 5）よりも、人間が決めるところを越えない（原則 1）を優先する。各原則には、対応する型を添える。

1. **人間が決めるところと関所を越えない**: 要件の合意・設計とフェーズの分け方の承認・外部の I/F の合意・マージ・実行を止めること・ラベル `重要` を外すことは、人間が決める。実行の始めの確認が通らないときも止まり、ここでは squad-handoff の「人間を呼んで止まるとき」に従う
2. **言う前に確認する**（型 1）: 状態・原因・できるかどうかは、答える前に確認する。確認する方法は、CLI（`--help` を含む）・実行の状態と記録・PR・タスクのコメント・原本の手順である
3. **事実と推測を分ける**（型 2）: 事実には、出所（流したコマンドと読んだ値）を添える。推測は推測と書き、確認する方法を添える
4. **言葉の意図を読む**（型 4）: 人間の言葉は、直前の流れと貼られたものから、何をしてほしいかを読む。貼られたログは、言葉がなくても「これが起きたので手を打ってほしい」と読む
5. **決められることは自分で決める**（型 3）: 原則と手順で決められることは、自分で決めて進める。報告は、1 行目に起きたことと次の一手を書く
6. **人間より先に気づく**（型 6）: PR のあるタスクで起きたら、待っている返事の途中でない限り、コンフリクトの状態と、動いている実行の長さを確認する。解消を修正の役へ頼むのは、タスクがマージ待ちの `in_review` で、その PR に触れる実行が動いていないときだけにする
7. **再発には原因と手当てを出す**（型 5）: 1 回目の失敗は、原因を確認して書いてから頼み直してよい。同じ誤りや差し戻しが 2 回続いたら、3 回目は頼まず、原因と再発を防ぐ手当てを添えて人間を呼んで止まる

原則 2 では、進捗や遅れを聞かれたら、実行の状態と記録を読んでから答える。確認しても分からないときは、確認した方法を添えて「未確認」と書く。

原則 3 では、読めなかった値を「なし」「通った」と書かない。

原則 4 では、読みが 2 つに割れ、取り違えると戻しにくいときだけ、1 つ聞く。

原則 5 では、人間に聞くときは、決めてほしいことを 1 つに絞り、推す案と理由を添える。

原則 6 では、解消を頼む条件に当たらないときは、作業中の PR に修正の役を重ねて呼ばない。45 分を超えて動いている実行は、記録を読み、同じ実行につき 1 回だけ人間に知らせる。

原則 7 の手当ては、手順の直し方か、指示の改善のタスクの起票である。指示の実物は勝手に変えない。

原則 2 は、進捗を聞かれたときに実行の記録を確認する決まり（`leader-run-status.md`）を一般にした原則である。原則 6 の 45 分は、実装のフェーズの目安の 30 分の 1.5 倍である。1 回の実行がフェーズの目安を大きく超えたら、人間が「遅い」と気づく前に知らせるためである。

原則 6 の確認は、コンフリクトの知らせで起きたときだけでなく、PR のあるタスクで起きたときはいつも行う。

解消を頼む条件は、マージ待ちの `in_review` で、返事の待ちの途中でなく、PR に触れる実行が動いていないことである。動いている実行がある PR に修正の役を重ねると、同じブランチに 2 つの実行が push するためである。解消を頼んだあとに 2 回続けて `CONFLICTING` なら 3 回目は頼まない。

遅れの知らせには実行の ID を書き、前のコメントに同じ ID の知らせがあれば、もう知らせない。起きるたびに同じ知らせを繰り返さないためである。知らせても、実行を止めるかは人間が決める（原則 1）。

原則 7 は、同じ誤りや差し戻しが 2 回続いたら人間を呼んで止まる決まりに、1 回目の頼み直しの前に原因を書くことと、止まるときに原因と手当てを添えることを合わせる。人間が同じ失敗の原因を自分で調べ直さずに、手当てを選べるようにするためである。

判断が決まらないときと、指示や環境の問題が疑われるときに人間を呼んで止まる決まりは、「人間を待つところ」に置く。同じ部品の別の抜けへの指摘が続くときの決まり（2 回目は種類単位で頼み、3 回目で止まる）は、[review-rework.md の同じ部品に指摘が続くとき](review-rework.md#同じ部品に指摘が続くとき)にある。原則 7 は、同じ部品の指摘について `leader-flow.md` に従う。

原則 7 の「差し戻し」は同じ誤りの差し戻しだけを指し、その数え方は [review-rework.md の同じ誤りが続くとき](review-rework.md#同じ誤りが続くとき)にある。

原則 5 の 1 行目は「結論」でなく「起きたこと」と書く。結論とだけ書くと、次の一手だけを書き、何を受けて動いたかが 1 行目に残らないためである（場面 3-1）。人間に聞くときは 1 つに絞り、推す案と理由を添える。

紐付けの漏れの再発（場面 5-2）は、原則 7 でなく、`leader-pr-checks.md` の手順で扱う。原則 7 の止まる決まりは頼み直しが 2 回続いたときのもので、紐付けの漏れは頼み直しを伴わず、止まらずに進むためである。原因と手当てを出すことは、原則 7 の見出しのとおりである。漏れを受け取ったときに何をいつ投稿するかは、`leader-pr-checks.md` の「PR の紐付けの確認」にある。

指示の展開後の大きさは、上限の 12,288 バイトに収める。展開した大きさは 11,161 バイトで、指示に文を足すときは、ほかを縮めて余裕の中に収める。冒頭と原則 4・7 は縮めた文で、原則 5 の聞き方は省かずに書く。縮めた内容の置き場所は、[planner-requirements.md のリーダーの指示の大きさ](planner-requirements.md#リーダーの指示の大きさ)の表にある。

同じ誤りの再発と同じ部品の 3 回目は、最上位の役があるとき、人間を呼ぶ前に最上位の役が診断する。最上位の役がないときは、この節の原則 7 のとおりにする。診断の手順は `leader-flow.md` の「同じ誤りや差し戻しが続くとき」にある。

### 受け取ったら確認すること

最初の項目は、squad-handoff の「実行の始めの確認」に従い、ほかの処理より先に `squad-preflight <タスク>` を流すことである。関所を崩さないためで、`tests/agent-templates-test.sh` もこの項目を確認している。

2 つめ以降の項目は、場面を決めるまでに読むものだけにする。コメントから済んだ工程・合意・待っている結果を確認すること、プロジェクトが未設定なら設定すること、PR があれば紐付けを確認することである。書き込み先と見張りの呼び方の項目は、squad-handoff に正本があるので、指示に置かない。

### 場面と手順

場面ごとに、必ずすることと、読む参照のファイルを表にする。必ずすることを指示に残すのは、参照のファイルを読み落としても、関所と人間の待ちを崩さないためである。細目は参照のファイルにだけ書き、指示と二重に書かない。

| 場面 | 必ずすること | 読む参照のファイル |
| --- | --- | --- |
| 新しい要望を受けた・作業先を決める・要件と設計を進める・フェーズを頼む | 振り分けの前に metadata の `repository` を決めて一覧と照合する。合意や承認のないものを先へ回さない | `leader-flow.md` |
| 実装・修正を頼む | その場の使用率で役を選ぶ。頼む前に重要のマークを確認する | `leader-dispatch.md`、`leader-principal.md` |
| 重要の判断の時機・最上位の役を呼ぶ | 2 つの時機にだけ重要のマークを判断して記録を残し、手戻りの合図では重要のマークを付けずに見直しを頼む。最終レビューはすべてのタスクで返事の待ちを付けて頼む | `leader-principal.md` |
| レビューと E2E を頼む・返事で起きた | 頼む前に `squad-review-wait watch` を流し、依頼に `返事を待つ役:` と `確認するコミット:` の行を置く。`返事の待ち: 次に進む` の実行だけが進む | `leader-review-wait.md` |
| PR を受け取った・待つ回を始める・マージへ回す | PR の紐付けを確認し、紐付いていなければ止まる。マージ前に最終レビューの head・コンフリクト・CI を確認する | `leader-pr-checks.md` |
| 進捗や遅れを聞かれた・実行を止める | 実行の状態と記録を確認してから答える。止めるのは人間の指示か承認があるときだけ | `leader-run-status.md` |
| PR のあるタスクで、ほかのきっかけで起きた | 返事の待ちの途中でなければ、コンフリクトの状態と動いている実行の長さを確認する。解消を頼むのはマージ待ちで PR に触れる実行がないときだけで、遅れは同じ実行につき 1 回だけ知らせる | `leader-pr-checks.md`、`leader-run-status.md` |

参照のファイルは、squad-handoff のスキルのディレクトリの `references/` にある。場面に入ったら、その実行の中で読む。前の実行で読んだ記憶で済ませない。

参照のファイルが見つからないときは、手順を推測で補わず、セットアップの流し直しを頼んで人間を呼んで止まる。スキルの更新が権限で飛ばされた（`manual.md` の「更新と、途中で止まったあとの再実行」）ときに、古い指示の手順を思い出して動かないためである。

### このスクワッドの役

展開で決まる事実は、指示に残す。参照のファイルは展開されないので、有効な役やメンションのリンクを書けないためである。この節には、次の条件つきの文と一覧を置く。

- 要件を決める役と設計の役の有無。ないときの「次の有効な役へ直接回す」「自分で設計や draft PR を作らない」の文
- 実装・修正の系統。「両系統がある」「Claude 系統だけがある」「Codex 系統だけがある」のどれかと、有効な実装・修正の役の一覧
- 最上位の役の有無と一覧。ないときの「最上位の役は置かない」の文
- レビューと E2E の役の有無と、ないときの「レビューと E2E の役は置かない」の文。QA があるときの画面の E2E の確認
- CI の見張りの有無と、`squad-pr-watch ci` に渡す見張りの ID

参照のファイルは、系統や役の有無で分かれる手順を、「両系統があるとき」「Claude 系統だけのとき」のような場合分けで書く。どの場合かは、この節の文で決まる。

## 手順の移し先

リーダーの手順の細目は、squad-handoff の `references/` に、場面ごとのファイルとして置く。最終レビューと CI の待ちの仕様は、[principal-review.md](principal-review.md) に従う。

新しいスキルではなく squad-handoff に置くのは、補助のファイルがすでに取り込みと照合の対象（`lib/workspace.sh` の `workspace_local_files`）で、セットアップの処理を増やさずに済むためである。

| ファイル | 中身 |
| --- | --- |
| `leader-flow.md` | 作業先の決め方・複数のリポジトリの分け方・要件と設計の進め方・フェーズの頼み方・受け渡しの書き方 |
| `leader-dispatch.md` | 実装・修正の振り分け。系統ごとの `squad-dispatch-pick` と `squad-usage-read` の使い方と終了コードの扱い |
| `leader-principal.md` | 判断する時機・重要のマークの記録・修正の依頼の数え方・設計の変更の行・すべてのタスクの最終レビュー。重要のマークのあるタスクの設計の見直し・見る範囲・head の照合・返事の待ち方・選び方 |
| `leader-review-wait.md` | レビューと E2E の依頼、`squad-review-wait` の watch・proceed・status、確認したコミットの照合 |
| `leader-pr-checks.md` | PR の紐付けの確認、CI の見張りと待ち、マージ依頼の重複防止、コンフリクトの状態の確認と規則の入れ直し |
| `leader-run-status.md` | 実行の状態を確認して答える、実行を止める、止めたあと |

参照のファイルは、条件のマークを場合分けの文に直して書く。手順の細目のほかに、原則のための次の 3 つを置く。それぞれの理由は、各節に書く。

- 原則 6 のための「起きたときの確認」を、`leader-pr-checks.md` と `leader-run-status.md` に置く。確認するきっかけは PR のあるタスクで起きたときすべてで、解消を頼む条件に、PR に触れる実行がないことを含める（[判断の優先の原則](#判断の優先の原則)）
- 原則 7 のための、1 回目の頼み直しの前に原因を書くことと、止まるときに原因と手当てを添えることを、`leader-flow.md` の受け渡しに置く。2 回続いたら人間を呼んで止まる（[判断の優先の原則](#判断の優先の原則)）
- 下の PR の紐付け

`SKILL.md` には、「リーダーの手順」の節を置く。`references/leader-*.md` はリーダーの手順で、ほかの役は読まないこと、リーダーは指示の「場面と手順」から読むことを書く。ほかの役が読み込む本文を増やさないため、細目は書かない。

`leader-pr-checks.md` の PR の紐付けの手順には、次の 2 つがある。

- 紐付けの一覧が空で人間に頼むときは、引き継ぎに写された警告の文をそのまま添える。連携の案内があれば、ワークスペースの設定のコードの画面で連携を先に確認するよう頼む
- 引き継ぎや出力に `紐付けていません:` の行があっても、紐付いているとは読まず、一覧で確認する

連携を先に確認するのは、連携がないと、タスクの画面からも紐付けられないためである。

この 2 つは、人間への頼みを、紐付けられる形にするためである。

### 崩さない手順

次の手順は、指示を書き直しても動きを変えない。どれも、人間の判断の場所か、見張りのスクリプトとの約束だからである。それぞれを確認する場面と、語句を確認するテストを置く。

| 手順 | 置き場所 | 確認する場面 | 確認するテスト |
| --- | --- | --- | --- |

## モデルと思考の深さ

リーダーのモデルは Sonnet で、思考の深さは high である。リーダーは受け渡しのたびに起きるので、モデルを重くすると、使用枠が足りずに作業の流れが回らなくなるためである。

| ランタイム | モデル | 思考の深さ |
| --- | --- | --- |
| Claude | `claude-sonnet-5-5` | high |
| Codex | `gpt-6.1-sol` | high |

Claude のリーダーは、`claude-opus-5-5` にしない。リーダーは 1 つのタスクで十回以上起きるので、Opus の high では使用枠の消費が大きすぎる。人間が、Sonnet でなければ作業の流れが回らないと判断した。

思考の深さを high にするのは、確認してから答える、原因を探す、といった原則の判断に考える量を回すためである。使用枠は、medium のときより 1 回の実行の思考の分だけ大きい。モデルの単価は Sonnet のままなので、その差は Opus にするより小さい。medium にすると使用枠は小さいが、原則の判断に回せる考える量も小さい。

Codex も、モデルは `gpt-6.1-sol` で、思考の深さは high である。原本で確認した Codex のモデルは、`gpt-6.1-sol` と、最上位の役の `gpt-6-astra` だけである。`gpt-6-astra` をリーダーに使うと、すべてのタスクの最終レビューと、重要なタスクの設計の見直しに使う最上位のモデルの枠を、毎回の振り分けでも使うことになる。

front matter は、`IF runtime-claude` で Claude のモデル、`ELSE` で Codex のモデルを書く形にする。片方のランタイムだけのときの移し方は `common/agents/FORMAT` に従う。

設計の役のモデルは、Claude で `claude-opus-5-5`、Codex だけの構成で `gpt-6.1-sol` にし、思考の深さは high にする。最上位のモデル（Claude の `claude-fable-5-2`、Codex の `gpt-6-astra`）にしないのは、設計の役を最上位のモデルにすると、Claude の上限に早く届くようになるためである。最上位のモデルの使用の大半を設計の役が占め、上限で失敗した設計の役の実行は成果が残らない。

要件を決める役が占める割合は小さいので、要件を決める役は最上位のモデルである。最上位の役のモデルと、呼ぶ場面は、設計の役のモデルの選び方に左右されない。

設計の役を最上位のモデルにしたときに、Fable 5.2 の 1 トークンが Opus 5.5 に比べて上限へどれだけ重く数えられるかは、確認できていない。最上位のモデルの設計が手戻りを減らすかも、確認できていない。後者は件数が少なく測れていない。そのため、設計が原因の手戻りが増えるおそれがあり、増えたときは、設計の役を最上位のモデルへ戻す案を人間に出す。

## 評価

リーダーの指示の効果を、マージの前に評価で確認する。6 つの型の過去の事例を評価の場面に書き起こし、基準のコミット（既定は `origin/main`）のリーダーと作業ツリーのリーダーに同じ場面を解かせて、基準で採点して比べる。以下、前者を「今のリーダー」、後者を「新しいリーダー」と呼ぶ。新しいリーダーが、すべての場面で 3 回とも基準を満たせば合格とする。

### 場面の置き場所と形

場面は `tests/leader-eval/scenes/` に、1 場面 1 ディレクトリで置く。ディレクトリの名前は場面の ID（`1-1`、`keep-1` など）にする。ディレクトリの名前は、`CONTRIBUTING.md` の「ファイルとディレクトリの名前」のとおり、印字できる ASCII で書く。型の「保」の場面の ID は `keep-<番号>` にする。

| ファイル | 中身 |
| --- | --- |
| `scene.md` | 場面の ID・型・元の出来事・リーダーへ渡す入力・合格の基準 |
| `cli.json` | リーダーが流すコマンドと、その出力の見本の表 |

`scene.md` は、次の見出しを持つ。

- `## 元の出来事`: 過去の事例で、何が起き、人間がどう返したか。2〜3 文で書く
- `## 入力`: リーダーの実行に渡す、きっかけのコメントとタスクの状態。実際の実行に渡る形に合わせる
- `## 合格の基準`: 番号付きの項目で、各項目の先頭に `[記録]` か `[採点]` を付ける
  - `[記録]`: 呼んだコマンドの記録から機械で判定するもの
  - `[採点]`: 採点の役が応答を読んで判定するもの

場面の入力（`## 入力` の文と `cli.json` の見本）は、1 つの出来事を表す。場面を足す・変えるときは、入力のすべての項目を、リーダーの手順がその項目をどう読むかと照らす。照らす項目は次のとおりである。

- コマンドの出力
- PR の head（`headRefOid`、`conflicts-check` と `ci-check` の SHA）
- コメントの `確認したコミット:`
- タスクと PR の題・branch・ファイル・本文
- `修正の依頼:` などの行の件数
- コメントの日時の順

項目ごとの読み方と合う形は [review-rework.md の照合する範囲](review-rework.md#照合する範囲)にある。ずれそのものを入力にするとき（古いコミットへの返事など）は、そのずれを `## 入力` の文に書く。

場面の入力は、その場面の役の構成とも合わせる。役の構成は、`scene.md` の `- 外す役:` の行と、`cli.json` の真偽値（`ci_monitor`・`planner`・`security_reviewer`）で決まる。ある構成の依頼にだけ置く行を、その構成でない場面の入力に書かない。

設計の役を外さない場面の入力には、`設計を用意した人: 人間` の行を置かない。この行は、設計の役がない構成の依頼にだけリーダーが置くためである。機械で確認する範囲は[役の構成と合わない入力の検査](#役の構成と合わない入力の検査)にある。

場面の文と出力の見本には、実在のプロジェクト・人・ID を書かない。名前は `shop` や `member1` のような置き換えにし、ID は `agent-planner` のような読める値にする。公開のリポジトリに置き、混入の検査（`CONTRIBUTING.md` の「MANIFEST と混入の検査」）が UUID の形を拒むため。元の事例のタスクの識別子は、場面のファイルに書かず、タスクに残す評価の記録に場面の ID と並べて書く。

### 流す仕組み

場面は `tests/leader-eval/run.sh` で流す。`tests/run.sh` には入れず、CI でも流さない。本物のモデルを呼び、使用枠を使うためである。

1. 比べる 2 つの指示を作る
   - 今のリーダーは、引数のコミット（既定は `origin/main`）の `common/agents/orchestrator.md` を `git show` で、squad-handoff を `git archive` で取り出す
   - `git archive` の中身は、ファイルに書いてから展開する
   - 新しいリーダーは作業ツリーのものを使う
2. 指示を、セットアップと同じ展開（`lib/render.sh`）で、決まった見本の値（`tests/leader-eval/values.json`）に展開する
   - 見本は、すべての役が有効で、両方のランタイムを使うプロジェクトにする
   - モデルと思考の深さは、展開した front matter から読む
3. 場面と回ごとに、結果のディレクトリの `runs/` の下に作業ディレクトリを作る
   - 結果のディレクトリは、既定で一時ディレクトリ（`${TMPDIR:-/tmp}`）の下に `leader-eval.XXXXXX` として作り、シンボリックリンクを解いたパスで使う
   - 祖先に指示やスキルがある場所では流さない（[作業ディレクトリの分離](#作業ディレクトリの分離)）
   - 作業ディレクトリには、Multica の実行と同じ配置で、展開した指示と squad-handoff（`SKILL.md` と `references/`）を置く
4. `multica`、`gh`、`squad-` の見張りをスタブにして PATH の先頭に置く
   - スタブは、引数を `cli.json` の表と前方一致で照らして見本を返し、呼び出しを記録する
   - 表にない呼び出しは、失敗を返して記録する
   - 書き込み（コメント・状態・ラベル・metadata・起票・止める）は、成功を返して中身を記録する
5. ランタイムの CLI（`claude -p`）に、場面の入力を渡して流す
   - 使える道具は、スタブのコマンドの Bash、作業ディレクトリの中の読み書き、squad-handoff だけを読み込む Skill に絞る（[道具と許可](#道具と許可)）
   - 思考の深さは、Multica が実行に渡すのと同じ指定にする
6. 合格の基準を判定する
   - `[記録]` はスタブの記録から機械で判定する
   - `[採点]` は、採点の役（`claude-opus-5-5`、high で固定。[評価するモデル](#評価するモデル)）に判定させる
   - 採点の役には、基準の 1 項目・場面の入力・呼んだコマンド・投稿したコメントを渡し、合否と理由を JSON で返させる
7. 1 回の実行は、すべての基準を満たしたときに合格とする。場面は 3 回とも合格したときに合格とする

並列数は引数で決め、既定は 4 とする。19 場面を 3 回ずつ、2 つの指示で流すと 114 回になるため。採点の役は、今のリーダーと新しいリーダーのどちらの記録にも同じものを使い、どちらの指示かを渡さない。

Codex のランタイムでの評価は、`--runtime codex` で同じ場面を流せる。合否は Claude のランタイムで決め、Codex は使える環境で流して記録に足す。評価する人の使用枠と、`codex` の CLI の有無が環境ごとに違うため。

`cli.json` の `ci_monitor` と `planner` は真偽値で指定し、省略時は有効にする。`false` の役だけを外して場面ごとの指示を描き、比較する新旧どちらの作業場所にも渡す。両方を同時に外す構成にも対応する。本文の値を出すため、読み取り用の標準のコマンドに `shasum` を含める。

`repositories` は `OWNER/REPO` の文字列の配列で指定する。省略時は `values.json` の値を使う。指定した場面は、各値をバッククォートで囲み、読点でつないだ一覧で場面ごとの指示を描く。各リポジトリの役割は、場面の入力にプロジェクトの説明として書く。

`cli.json` の `pick_exceptions` は、回す先の役の pick の見本を求めない基準を、場面ごとに書く。形と使い方は [leader-eval-picks.md](leader-eval-picks.md#例外) にある。

### 道具と許可

評価のリーダーに、実際の Multica の実行と同じ手がかりを渡す。Skill の道具を使え、許可は squad-handoff だけにする。前置きの近似（`tests/leader-eval/runtime-brief.md`）に、実際の前置きと同じ Skills の節を置く。

| 項目 | 値 |
| --- | --- |
| `--tools` | `Bash Read Write Edit Skill` |
| `--allowedTools` | `Skill(squad-handoff)`、スタブのコマンド、読むだけの標準のコマンド、一時ファイルを消す `rm` と作業ディレクトリの中の読み書き |
| 前置きの近似 | `## Skills` の節に squad-handoff を挙げる |
| 前置きの近似 | 評価の実行だけの制限を書いた節を置く |

Skill の道具は、スキルの本文と置き場所を会話に読み込むだけで、書き込みも通信もしない。許可を squad-handoff に限るので、ほかのスキルを呼ぶと拒否され、実行は失敗になる。

評価の実行だけの制限の節には、次を書く。実際の実行は許可を問わないので、エージェントは評価で拒否される書き方を普通に使う。制限を先に知らせれば、拒否を避けて同じ仕事ができる。比べる 2 つのリーダーは同じ前置きを読むので、比べる条件は変わらない。

- 作業ディレクトリで始まり、`tmp/` はすでにある
- ファイルは Write の道具で、`tmp/<名前>.md` のような相対パスに書く
- Bash では `cd`・`mkdir`・`sed`・`awk`、`$(...)`、`${...}`、heredoc での書き込みを使わない
- 許可にない呼び出しは拒否され、評価では失敗になる

許可の一覧に、通信するコマンドと、作業ディレクトリの外へ書くコマンドは足さない。`mkdir` や `cd` を許可して拒否を減らす案は採らない（[検討した案](#検討した案)）。

拒否は失敗にする。拒否が 1 件でもある実行は失敗にし、`[採点]` を採点に回さない。拒否の一覧は `runs.jsonl` の `permission_denials` と、`calls` の `denied` の行に残す。

### 作業ディレクトリの分離

評価のリーダーには、作業ディレクトリに置いた指示とスキルだけを読ませる。ランタイムは祖先のディレクトリの指示とスキルも読むので、置き場所によって評価の入力が変わるためである。

- `run.sh` の結果のディレクトリの既定は、一時ディレクトリ（`${TMPDIR:-/tmp}`）で、リポジトリの `tmp/` には置かない。理由は、リポジトリの根に `AGENTS.md` があり、Multica の作業ディレクトリに `CLAUDE.md` と `.claude/skills` があるためである
- 結果のディレクトリは、シンボリックリンクを解いたパス（`pwd -P`）で使う。エージェントが `pwd` で見るパスと、許可を照らすパスをそろえるため
- 流す前に、結果のディレクトリとその祖先に、`CLAUDE.md`・`CLAUDE.local.md`・`AGENTS.md`・`AGENTS.override.md`・`.claude`・`.codex` があるかを調べる
  - あれば、見つけたパスを示して、どの場面も流さずに 0 以外で終わる
  - `--out` で指定したときも同じに扱う
  - 調べるのは補助（`leader_eval.py` の `ancestors`）で、`run.sh` は根まで調べる

`AGENTS.override.md` は、Codex がディレクトリごとに `AGENTS.md` より先に読む上書き用の指示である。祖先にこれだけがあっても、Codex で流した評価の入力が置き場所で変わるので、`AGENTS.md` と同じに扱って止める。Claude のランタイムは読まないので、合否を決める Claude での評価には影響しない。それでも、Codex で流した記録を合否の参考に足すため、名前を分けずに同じ確認で止める。

スタブの `claude` で流すテストは、祖先を調べずに流す指定（環境変数 `LEADER_EVAL_SKIP_ANCESTOR_CHECK=1`）を使う。テストの一時ディレクトリはリポジトリの `tmp/` の下にあり、スタブは祖先の指示を読まないためである。この指定は、評価のコマンド（`--runtime` の `claude` か `codex`）と採点の `claude` の両方の先頭に目印（`LEADER_EVAL_STUB_AGENT`）があるスタブのときだけ効く。

評価のコマンドは、スタブの環境と同じ PATH で 1 回だけ絶対パスに解決する。その PATH は、空の項目と、見張り役のコマンドがあるディレクトリを除き、相対の項目を絶対パスにしたものである。目印の確認も、評価と採点の起動も、その同じ絶対パスを使い、起動時に名前で引き直さない。そのため、目印付きのディレクトリが PATH から除かれても、目印のない別の `claude` が代わりに起動して指定が効くことはない。

呼び出し元の環境から継承しても、本物の CLI では確認を外せない。目印のないコマンドや、見つからないコマンドでは、指定があっても祖先を調べる。

テストの一時ディレクトリは `tmp/` の下にあり、祖先に原本の `AGENTS.md` がある。`mktemp -d` が `TMPDIR` を見るかは、GNU と macOS で違う。そのため「祖先に指示がない」ことは、置き場所に頼らず、補助に止める場所（テストの一時ディレクトリ）を渡して確認する。`run.sh` は止める場所を渡さない。

### 評価するモデル

リーダーは、展開した front matter のモデルと思考の深さで流し、今のリーダーは基準のコミットの値、新しいリーダーは作業ツリーの値を使う。たとえば、基準のコミットが medium、作業ツリーが high なら、同じ `claude-sonnet-5-5` で思考の深さだけが違う。流す仕組みと場面の基準は、モデルの名前を前提にしない。評価は、利用者のプロジェクトで実際に動くモデルで流さなければ、結果が実際の動作を表さないためである。

新しいリーダーの合否は、Sonnet の high で 3 回とも合格したかで決める。Opus のような強いモデルは、指示が足りなくても力で補って通ることがある。軽いモデルで通れば、指示と原則そのものが効いている、より強い証拠になる。今と新しいリーダーは同じモデルなので、差は指示と思考の深さから出る。

採点の役は、リーダーのモデルと分けて `claude-opus-5-5` の high に固定する。採点は 1 つの基準の合否を読むだけで、リーダーの実行より呼ぶ量が少ない。今と新しいリーダーを同じ物差しで測るため、リーダーのモデルに合わせて変えない。

リーダーを Opus にして流した評価の結果は、合否に使わない。Sonnet で流し直す。

### 記録の形

`run.sh` は、作業ディレクトリに次の 2 つを書く。

| ファイル | 中身 |
| --- | --- |
| `summary.md` | 場面ごとに 1 行の表。列は、場面の ID・型・今のリーダーの合格の回数（n/3）・新しいリーダーの合格の回数・落ちた基準の番号 |
| `runs.jsonl` | 実行ごとに 1 行。場面・指示・回・モデル・呼んだコマンド・投稿したコメント・最後の応答・基準ごとの合否と理由 |

記録はタスクに残す。`summary.md` の表と、場面の ID と元の事例のタスクの対応をコメントに書き、`runs.jsonl` を添付する。新旧の応答と採点を並べて読めるようにし、採点の役の判定を人間があとから確認できるようにするため。PR の本文には写さない。

### 場面を確認するテスト

`tests/leader-eval-test.sh` は、本物のモデルを呼ばずに次を確認する。CI で流す。

- すべての場面に、3 つの見出しと、`[記録]` か `[採点]` の付いた基準が 1 つ以上ある。`cli.json` が JSON として読める
- 型 1〜6 に、それぞれ場面が 2 つ以上ある。[崩さない手順](#崩さない手順)の表の場面がすべてある
- 場面の中に、UUID の形の値がない
- 設計の役を外さない場面の入力に、`設計を用意した人: 人間` の行がない（[役の構成と合わない入力の検査](#役の構成と合わない入力の検査)）
- 型「新」の ID が `add-<番号>` で、要件の見直しの 8 場面がそろっている
  - `ci_monitor` と `planner` は真偽値以外を拒み、無効な役を新旧の指示と作業場所から外す
  - `repositories` は `OWNER/REPO` の文字列の配列以外を拒み、指定した一覧を新旧の指示と作業場所に使う
- スタブの `claude` で `run.sh` を流し、今と新しい指示が展開されること、スタブのコマンドが呼び出しを記録すること、`[記録]` の判定と記録の形を確認する
- リーダーを、展開した front matter のモデルと思考の深さで呼ぶこと。期待するモデルの名前をテストに書き込まず、front matter から読む
- 評価の道具がスキルの参照に届くこと。スタブの `claude` が、次を満たさなければ失敗で終わる
  - `--tools` に `Skill` があり、`--allowedTools` に `Skill(squad-handoff)` がある
  - 作業ディレクトリの `CLAUDE.md` に `## Skills` の節があり、squad-handoff を挙げている
  - 作業ディレクトリの `.claude/skills/squad-handoff/references/` に、リーダーの指示の「場面と手順」の表が挙げる参照のファイルがすべてある
- 許可の一覧（`ALLOWED_TOOLS`）が、テストに書いた一覧と一致すること。許可を足すときはテストも変わるので、通信や作業ディレクトリの外への書き込みが足されていないことを、PR の差分で読める
- 祖先に指示がある結果のディレクトリでは流さないこと
  - `CLAUDE.md` を置いたディレクトリの下を `--out` に指定し、どの場面も流さずに 0 以外で終わることを確認する
  - `AGENTS.override.md` だけを置いた祖先でも、補助が見つけて止めることを確認する
  - 指示がない場合は、補助に止める場所を渡して見つからないことを確認する
  - 祖先の確認を飛ばす指定は、スタブの目印がない評価のコマンドでは効かず、指定を付けても祖先の指示で止まることを確認する
  - 目印付きの `claude` と見張り役のコマンドを同じディレクトリに置いて PATH から除かれる場合も、背後の目印のない `claude` が起動せず、本物の評価として拒否されることを確認する
  - 相対の PATH でも、確認したファイルを起動することを確認する
  - PATH の空の項目は除かれ、相対の項目は絶対パスになることを確認する
- 拒否が 1 件でもある実行は失敗になり、拒否の一覧が記録に残ること。拒否された状態の変更を記録と判定に含めることを、keep-6 の場面で確認する

合格の基準が回す先とする役の pick の見本が `cli.json` にあるかは、別のテスト `tests/leader-eval-picks-test.sh` が確認する（[leader-eval-picks.md](leader-eval-picks.md)）。

### 役の構成と合わない入力の検査

設計の役を外さない場面の入力に `設計を用意した人: 人間` の行が残っていないことを、`tests/leader-eval-test.sh` で確認する。本物のモデルは呼ばず、CI で流す。

この行は、設計の役がない構成の依頼にだけ置く。設計の役がある場面に残ると、その場面は起きない出来事を表す。リーダーは依頼のコメントを読んで次の一手を決めるので、設計の直しを人間に頼む構成だと読み違える手がかりにもなる。`add-44` は設計の役を置く場面で、設計の見直しの依頼と診断の依頼にこの行が残る誤りを、この検査が見つける。

検査の決まりは次のとおりである。

| 項目 | 決まり |
| --- | --- |
| 検査する場面 | `tests/leader-eval/scenes/` と `tests/leader-eval/compat-scenes/` の場面のうち、外す役に `designer` がないもの。`- 外す役:` の行がない場面も含む |
| 役の構成の読み方 | 流す仕組みと同じ `leader_eval.py` の場面の読み取りが返す、外す役の一覧を使う。テストの中で `- 外す役:` の行を別に読み直さない |

| 探すもの | `設計を用意した人: 人間` の文字の並び。行の頭と終わりは問わない |
| 入れ子の見本 | `cli.json` の文字列が JSON として読めるときは、読んだ値の中の文字列も同じように探す。`stdout` に JSON の文字列で入れたコメントの一覧も読むためである |
| 見つけたとき | 場面の ID と、見つけた場所（`scene.md` の `## 入力` か `cli.json`）を標準エラーに出し、0 以外で終わる |

次のものは、入力ではないので見ない。

| `tests/leader-eval/principal-scenes/` | 最上位の役の場面である。この行は最上位の役が読む行で、最上位の役の場面では正しい入力になりうる |

## 互換性と影響を受ける利用者

導入済みのプロジェクトは、ホストでセットアップを流し直すと、リーダーの指示と思考の深さが更新される（`manual.md` の「更新と、途中で止まったあとの再実行」）。エージェントの数と登録の名前、スクワッド、オートパイロットは変わらない。流し直すまでは、更新前の指示のままで動く。

squad-handoff は、流し直しで `references/` の補助のファイルが取り込まれる。スキルはワークスペースで共有するので、同じワークスペースの別のプロジェクトにも参照のファイルが届く。更新前の指示のリーダーは参照のファイルを読まないので、動作は変わらない。

スキルの更新は、オーナー・管理者か最初に取り込んだ人でなければ飛ばされる。そのときは、参照のファイルを見つけられない。[場面と手順](#場面と手順)のとおり、推測で補わずに人間を呼んで止まる。

リーダーの実行の使用枠は、思考の深さが high である分だけ、medium のときより大きい。モデルは Sonnet なので、その差は Opus にするより小さい。

## 残る危うさ

- 評価の場面は過去の事例の書き起こしで、場面にない状況での判断は確認できない。場面を足していく
- 採点の役の判定は誤ることがある。記録に理由を残し、人間が落ちた場面と際どい場面を読んで確認する
- 参照のファイルをその場で読まずに動くと、手順を落とす。「場面と手順」の表に必ずすることを残し、崩さない手順の場面で確認する
- 評価は Claude のランタイムで合否を決める。Codex のリーダーは、流せる環境がなければ評価されずに出る
- 評価の作業ディレクトリの配置が Multica の実行と違うと、評価の結果が実際の動作を表さない。配置は実際の実行の作業ディレクトリと照らして確認する
- 評価の前置きには、実際の実行にない制限の節がある。制限を避ける書き方を覚えたリーダーと、実際の実行のリーダーの動きは、書き込みの方法だけ違うことがある
- 作業ディレクトリの中の絶対パスへの Write が拒否された原因は確定していない。実際のランタイムで再び出たら、拒否の一覧を残して設計へ返す

## 検討した案

手順の置き場所・思考の深さ・評価の流し方・評価の検査の見方・原則の書き方について、次の案を採らなかった。

- 新しいスキル（`squad-lead` など）を作り、リーダーにだけ割り当てる案。ほかの役が読む量は減るが、セットアップの取り込みと導入の確認（`lib/installation.sh`）に新しいスキルを足す変更が要る
  - 採らない理由: 要件が squad-handoff を移し先に挙げている
- 手順を指示に残し、冒頭に原則を足すだけの案。変更は小さいが、指示の大きさがほとんど変わらず、手順の量に原則が埋もれ、要件の「手順の細目をスキルとスクリプトへ寄せる」を満たさない
- 参照のファイルをひな形として展開し、プロジェクトのスキルとして登録する案。役の有無を書けるが、スキルの登録と更新の仕組みを新しく作ることになる
  - 採らない理由: 展開で決まる事実は指示の「このスクワッドの役」に残せば足りる
- 遅れに気づくため、振り分けのたびに時刻のウェイクアップを登録する案。人間に言われる前に気づけるが、実行が増え、要件が型 6 で扱うのはコンフリクトに気づいて回すところまでである
  - 代わりに: 起きたときに動いている実行の長さを確認するだけにする
- Claude のリーダーを `claude-opus-5-5` の high にする案。判断は重くなるが、リーダーは受け渡しのたびに起きるので使用枠が大きく増え、作業の流れが回らない
- Codex のリーダーに `gpt-6-astra` を使う案。判断は重くなるが、最上位の役の枠を毎回の振り分けで使う
- 評価を `tests/run.sh` に入れて CI で流す案。毎回確認できるが、本物のモデルを呼ぶので、CI に認証と使用枠が要る
  - 代わりに: CI では場面の形とスタブでの流れだけを確認する
- 評価の拒否を減らすため、`find`・`mkdir`・`cd` の Bash や、作業ディレクトリの外の Read を許可する案。拒否は減るが、作業ディレクトリの外を読み書きでき、分離が崩れる
  - 代わりに: 実際の実行との差は、置き場所が渡らないことにあるので、Skill の道具で渡す
- squad-handoff の置き場所を、前置きの近似に絶対パスで書く案。Skill の道具は要らないが、実際の前置きにない文で、評価だけの手がかりになる
  - 代わりに: 実際の実行と同じ Skills の節と Skill の道具にする
- 許可を問わない（`bypassPermissions`）で流す案。拒否はなくなるが、スタブの外のコマンドや作業ディレクトリの外への書き込みを止められない
- 祖先の `CLAUDE.md` を設定（`claudeMdExcludes`）で読ませない案。置き場所を選ばずに済むが、効くことを確認しておらず、祖先のスキルと Codex のランタイムには別の手当てが要る
  - 代わりに: 祖先に指示がない場所で流すことにする
- 役の構成と合わない入力の検査を、`add-44` だけを名指しして見る案。変更は小さいが、次に足す場面の同じ誤りを見つけられない
  - 代わりに: 設計の役を外さないすべての場面を見る
- 同じ検査で、`cli.json` を JSON として読まず、ファイルの文字をそのまま探す案。書くのは簡単だが、`expected_records` を分けられず、エスケープした文字も見つけられない
  - 代わりに: JSON として読み、入れ子の文字列もたどる
- 同じ検査で、ほかの構成だけの行（security-reviewer を置く構成の `返事を待つ役:` の並びなど）も見る案。広く見つけられるが、行ごとに置く条件が違い、今の場面に誤りが見つかっていない
  - 代わりに: 誤りが見つかった行だけを見て、行を足すときはこの節の表に足す
- 原則 5 の 1 行目を「起きたこと・結論・次の一手」の 3 つにする案。読み手に残るものは多いが、指示の余裕を超える
  - 代わりに: 次の一手が結論を兼ねるので、起きたことと次の一手の 2 つにした
- 原則 7 に、紐付けの漏れの再発には止まらずに原因と手当てを出すと足す案。指示から手当てが読めるが、指示の余裕を超える
  - 代わりに: 止まる決まりと同じ原則に置くと、止まるのか進むのかを読み違えやすいので、`leader-pr-checks.md` の手順に置いた
- 指示の「場面と手順」の表に、紐付いていない PR を受け取ったときの知らせを足す案。索引から手順が見えるが、余裕を超える
  - 代わりに: PR を受け取ったときは「場面と手順」の行が `leader-pr-checks.md` へ案内するので、参照のファイルに置けば届く
