# スクワッドの作業の指標を数える

スクワッドの作業の指標を、同じ入力から同じ数で数え直せる手順を説明する。範囲と時刻を替えれば、同じ手順で測り直せる。

手順は、Multica の記録を読んでスナップショットに残す手順と、スナップショットから数える手順に分ける。役ごとのトークン数は、Multica が実行ごとに残す使用量から数える。原本に保存の処理は置かない。

## 目的と範囲

目的は、ワークフローの改善の効果を、同じ数え方で数えた値どうしで比べて判断できるようにすることである。範囲と時刻を替えても、数え方は変えない。

対象は次のとおりである。

- 原本の開発用のスクリプト `scripts/metrics.py` と、そのテスト
- 4 つの指標と、役ごとのトークン数を、タスクごとに数える手順
- 数えた結果と入力のスナップショットを、Multica のタスクに添付する決まり

次は対象にしない。

- 指標の目標の判断と、改善の効果の評価
- コメントの分類。主な指標は分類によらない総数で測るため
- 導入先で使用量を集計・表示する機能
- セットアップ、役のひな形、共通スキル、見張りのスクリプトとの連携

## 手順の形

手順は、記録を読む `collect` と、数える `count` の 2 つからなる。読む手順だけが Multica に触れる。数える手順はスナップショットだけを読むので、同じスナップショットからは何度でも同じ結果が出る。

```bash
python3 scripts/metrics.py collect --project <プロジェクト ID> --output tmp/metrics/snapshot.json
python3 scripts/metrics.py count tmp/metrics/snapshot.json \
  --cutoff <時刻> --truncate <時刻> \
  --human <呼ぶ人間のメンバー ID> --project-key <プロジェクトのマーク> --member-key <メンバーのマーク> \
  --output tmp/metrics/result
```

置き場所は、Git が無視する原本の `tmp/` の下にする。スナップショットと結果には、タスクの識別子と、タスクごとの値が入るためである。どちらも公開のリポジトリにコミットしない。

### 記録を読む

`collect` は、`multica` の CLI でプロジェクトの記録を読み、決まった形の JSON に直して書く。読むものと、残す欄は次のとおりである。

| 記録 | 読むコマンド | 残す欄 |
| --- | --- | --- |
| タスク | `multica issue list --project` | ID、識別子、作られた時刻、今の状態 |
| コメント | `multica issue comment list`（すべてのページ） | ID・タスク・書き手の種類と ID・作られた時刻、本文にあるメンバーのメンションの ID |
| 状態の変化 | `multica issue timeline --activity-only` | タスク、変化の前と後の状態、作られた時刻 |
| 実行 | `multica issue runs` | ID・タスク・エージェント・状態、作られた・開始・終了の時刻、使用量の各行 |
| エージェント | `multica agent list --include-archived` | 収集した実行の `agent_id` が参照するエージェントの ID、名前だけ |

コメントの本文は残さない。数えるのに要るのはメンバーのメンションの ID だけで、本文を添付に広げないためである。メンションは、本文の `mention://member/<ID>` の形を読む。

手順の見直しで跡の定義を渡したときは、コメントごとに合った跡の ID の一覧も残す。このときも本文は残さない。跡の形と判定は [procedure-review.md の見直しの手順](procedure-review.md#見直しの手順)にある。

`collect` は、`--traces <跡の定義 JSON>` を指定すると、コメントの `trace_matches` と、入力ファイルのバイト列から計算した `trace_definitions_sha256` を保存する。定義の入力の形は [procedure-review.md の跡の形](procedure-review.md#跡の形)にある。省略すると、この 2 つの欄は足さない。

保存した跡の集計と手順の判定は、`traces` で行う。入力の形と出力は [procedure-review.md の集計と一覧の入力](procedure-review.md#集計と一覧の入力)を参照する。

時間の内訳を測るときは、`--marks` を指定して、コメントのマークと、タスク・実行の欄を足す。このときも本文は残さない。足す欄は [time-breakdown.md の記録を読む](time-breakdown.md#記録を読む)にある。省略すると、足さない。

エージェント一覧は、収集した実行が参照する ID で絞る。コメントの書き手だけのエージェントや、ほかのプロジェクトの無関係なエージェントは保存しない。タスクが 0 件なら `agents` は空の配列になる。残す欄は上の表の範囲に限り、名前は添付前に[別名へ置き換える](#置き場所と公開の範囲)。

読み落としは、少なく数える誤りになる。コメントはすべてのページを読み、状態の変化で CLI が切り詰めの警告を出したときは、スナップショットを書かずに止まる。CLI の応答に要る欄がないときも止まる。

スナップショットは、キーの順と配列の並び（作られた時刻、次に ID）を固定して書く。読んだ時刻と CLI のバージョンも記録するが、数える手順の結果には影響させない。

数える手順の入力は、次の欄を持つ JSON である。各配列の欄と合成の例は `tests/fixtures/metrics/snapshot.json` にある。

- `schema_version: 1`
- `project_id`
- `collected_at`
- `cli_version`
- `issues`
- `comments`
- `transitions`
- `runs`
- `agents`

コメントのメンションの ID は `member_mentions`、状態の変化は `from_status` と `to_status` に残す。実行の時刻と使用量の欄は `created_at`、`started_at`、`completed_at`、`usage` とする。開始・終了の時刻がないときは `null`、使用量がないときは空の配列にする。

`usage` の各行は、CLI と同じ欄を持つ。欄は `input_tokens`、`cache_write_tokens`、`cache_read_tokens`、`output_tokens` である。

### 数える

`count` は、スナップショットと次の入力から、タスクごとの値を数える。入力は、すべて引数で受け、環境や今の時刻を読まない。

| 入力 | 意味 |
| --- | --- |
| `--cutoff` | 対象を切る時刻。これより前に作られたものだけを数える |
| `--truncate` | 実行時間を打ち切る時刻 |
| `--from` | 対象のタスクの範囲の始め。省略すると始めを切らない |
| `--limit` | `--from` 以後の先頭の N 件だけを数える。`--from` と一緒に指定する |
| `--settled` | 対象のタスクの `--cutoff` の時点の状態が `done`・`cancelled`・`in_review` のどれでもないものがあれば止まる |
| `--human` | 呼ぶ人間のメンバー ID。複数を渡せる |
| `--project-key`、`--member-key` | エージェントの名前から役を読むためのマーク |

4 つの指標は、人間のコメントと人間の呼び出し、実行時間と差し戻しである。数え方と境目は次のとおりである。

1. 対象のタスクは、作られた時刻が `--from` 以後で `--cutoff` より前のものとする。状態は問わない
2. コメント・状態の変化・実行は、対象のタスクのもので、作られた時刻が `--cutoff` より前のものだけを数える。`--cutoff` ちょうどのものは数えない
3. 人間のコメントは、書き手の種類がメンバーのコメントの数とする
4. 人間の呼び出しは、書き手の種類がエージェントのコメントのうち、`--human` のどれかのメンションを含むものの数とする。1 件に何度メンションがあっても 1 と数える
5. 実行は、開始の時刻があるものだけを数える。開始の時刻がない実行は、開始する前に取り消されたものとして、回数にも時間にも入れない
6. 実行時間は、開始から「終了の時刻」と `--truncate` の早い方までの秒を足す。終了の時刻がない実行は `--truncate` で終わったとみなし、開始が `--truncate` 以後なら 0 秒とする
7. 差し戻しは、役が `claude-fixer` か `codex-fixer` の、数えた実行の数とする
8. 参考の値として、`in_review` へ移った状態の変化の数も出す

時刻は、秒の小数を含めて比べる。合計は整数の秒で足し、分への直しと 1 タスクあたりの平均は、表示するときにだけ行う。四捨五入は小数第 1 位までとし、浮動小数点を使わずに計算する。

実行ごとの秒の小数は、切り捨ててから整数の秒を足す。JSON の合計とタスクごとの値は整数、分と平均は小数第 1 位までの文字列で残す。使用量が読めた実行は内訳と合計を足し、未確認の実行数を別に残す。

役のすべての実行が未確認なら、その役のトークン数は `null` にする。対象のタスクが 0 件なら平均も `null` にする。

実行の役は、エージェントの名前から読む。セットアップは名前を `<プロジェクトのマーク>-<役>-<メンバーのマーク>` にするので、前後のマークを外した残りが [common/agents](../common/agents/) の役の名前と一致すれば、その役とする。一致しないエージェントの実行は「その他」にまとめ、エージェントの名前を添える。

### トークン数を数える

役ごとのトークン数は、実行の記録の使用量（`usage`）を足して数える。数える実行は、上の 5 と同じ開始した実行で、時刻の打ち切りはしない。

使用量は、1 つの実行に、モデルごとに 1 行以上ある。入力・キャッシュの作成・キャッシュの読み出し・出力を行ごとに足し、4 つの合計も出す。使用量の行がない実行は 0 にせず「未確認」とし、役ごとにその数を出す。

### 結果の形

結果は、`metrics.json` と `metrics.md` の 2 つのファイルにする。JSON が正本で、Markdown は同じ値を人が読む表にしたものである。

| 部分 | 中身 |
| --- | --- |
| 入力 | 引数の値と、スナップショットの SHA-256、読んだ時刻、CLI のバージョン |
| タスクごと | 識別子・4 つの指標・実行の回数・`in_review` へ移った数・役ごとのトークン数と未確認の数 |
| 合計 | 対象のタスクの数、4 つの指標と参考の値の合計、役ごとのトークン数の合計と未確認の数 |
| 1 タスクあたり | 合計を対象のタスクの数で割った値 |
| 計画の表との差 | 次の節で決める比較 |

同じスナップショットと引数からは、2 つのファイルが 1 バイトも違わない。キーの順、行の並び、数の書き方を固定し、今の時刻や実行した機械の情報を入れないためである。

結果の 2 つのファイルとスナップショットは、測る作業のタスクのコメントに添付する。コメントには、使った引数と、スナップショットの SHA-256 を書く。

### 比べる値

結果には、比べる値との差と、その理由を添える。比べる値は、指標ごとの合計と、役ごとのトークン数の合計である。

比べる値は、`count` に `--compare` で渡すファイルに書く。原本には `scripts/metrics-plan.json` を置く。合計だけを持ち、タスクごとの値を持たないためである。差の理由は、数えた人が結果のコメントに書く。

比較ファイルの形は `tests/fixtures/metrics/plan.json` にある。`metrics` に指標名と整数の合計（実行時間は `run_seconds`）、`roles` に役名と `total_tokens` を渡す。未確認のトークン合計は `null` にする。

差は、今回の確認済みの合計から比べる値を引き、どちらかが未確認なら `null` にする。未確認の実行数は差と並べて出す。

トークン数は、数え方の出どころが違う値と比べると差が出る。この手順は実行の記録の使用量から数え、会話の記録から数えた値とは出どころが違うためである。差のある役について、差と、その役の未確認の数を並べて書く。

## トークン数の出どころ

役ごとのトークン数は、Multica の実行の記録の使用量から数える。使用量はサーバーに残るので、作業ディレクトリが片付けられた Codex の実行も読めるからである。

`multica issue runs` の応答には、実行ごとに `usage` がある。`usage` には、プロバイダ、モデルと、入力・出力・キャッシュの読み出し・キャッシュの作成のトークン数が入る。原本の CLI の見本（`tests/fixtures/cli/issue-runs.json`）にも、この欄がある。

実行の記録は、その実行のタスクに付いてサーバーに残る。原本は何も保存しないので、公開のリポジトリには何も置かず、コメントも通知も増えず、実行を止める処理もない。

使用量がない実行は、失敗または途中で止まった実行に多い。0 にせず「未確認」として別に数える。

実行の記録の使用量は、会話の記録より抜けが少ない。会話の記録は作業ディレクトリが片付けられると読めず、Claude の応答をメッセージと要求の ID で重ねない処理も要る。この処理はランタイムが使用量を記録するときのものになり、この手順では行わない。

## 置き場所と公開の範囲

原本に置くのは、数える手順と、合成した見本のデータによるテストだけである。タスクの識別子、タスクごとの値、コメントの本文は、原本の差分に入れない。

| もの | 置き場所 |
| --- | --- |
| 数える手順と、比べる値の合計 | `scripts/metrics.py` と `scripts/metrics-plan.json` |
| テストと合成の見本 | `tests/metrics-test.sh` と `tests/fixtures/metrics/` |
| CLI の応答の実物の見本 | `tests/fixtures/cli/`。足す応答は [CLI の実物の見本](../tests/fixtures/cli/README.md)の取り方に従う |
| スナップショットと結果 | 手元の `tmp/metrics/` と、数えたタスクの添付 |

収集したエージェントの名前にも個人名やメールが含まれうる。添付前に、手元で次の手順を行う。

1. 元のスナップショットを `count` に渡し、タスクごとの指標と役ごとのトークン数を比較用に残す
2. 添付用のコピーで、`agents` の名前を別名へ置き換える
3. コピーを `--project-key example --member-key anonymous` で数え直し、置き換え前の結果と照合する
4. コピーと数え直した結果に個人名やメールが残っていないことを確認し、この 2 つだけを添付用に使う

手順 2 の別名は、次のとおりに決める。既知の役は `example-<役>-anonymous` とし、`<役>` は変えない。「その他」の名前は `other-agent-001` など、既知の役に一致しない別名にする。

同じ元の名前には同じ別名を使う。「その他」の異なる名前には異なる別名を使う。名前だけを替え、ID などほかの欄は替えない。

手順 3 では、次が置き換え前と一致することを確認する。タスクごとと合計・平均の指標、役の分類、トークン数と未確認の数である。入力の SHA-256 と「その他」に添える名前は変わる。

再実行に使う引数と SHA-256 は、別名へ置き換えたコピーのものを記録する。元の名前や比較用の結果、対応表は添付しない。

タスクの識別子と ID まで置き換える添付用のコピーは、[time-breakdown.md の匿名にする](time-breakdown.md#匿名にする)の `anonymize` で作る。

`scripts/` は配布物に入るが、セットアップは `scripts/metrics.py` を読まず、導入先にも配置しない。`scripts/check.sh` と同じ、原本を変える人のための開発用のスクリプトである。

## 互換性と影響を受ける利用者

この手順は、導入済みのプロジェクトの動作を変えない。変わるのは、原本の開発用のスクリプトとテスト、文書だけで、セットアップが配置・登録するものに触れないためである。

セットアップを流し直しても、エージェント・オートパイロット・スキル・スクワッドの登録は変わらない。ホストの共有のファイル（`gh` のガード、見張りのスクリプト、Codex の設定、シェルの設定）も変わらない。回答ファイルの形も変わらないので、移し替えは要らない。

実行ごとの使用量は、導入先のセットアップによらず、Multica が実行の記録に残している。使用量を記録しないランタイムやデーモンのバージョンの実行は、この手順で「未確認」として数える。

影響を受けるのは、原本を変える人だけである。数える人は、Python 3.11 以上と、プロジェクトの記録を読める `multica` のログインが要る。

## テスト

テストは `tests/metrics-test.sh` に置き、合成した見本のスナップショットで `count` を確認する。外部の CLI とサーバーには触れない。

| 確認すること | 見本の作り方 |
| --- | --- |
| 区切りの直前のコメント・実行は数え、ちょうどとその後は数えない | 区切りの 1 秒前、ちょうど、1 秒後に作られた記録 |
| 区切りをまたいだ実行は、区切りまでの秒だけを足す | 区切りの前に始まり、後に終わる実行と、終わっていない実行 |
| 開始する前に取り消された実行は、回数にも時間にも入らない | 開始の時刻がなく、状態が取り消しの実行 |
| メンバーのコメントだけが人間のコメントに、呼ぶ人間のメンションを含むエージェントのコメントだけが呼び出しになる | メンバーとエージェントのコメント、ほかのメンバーへのメンション、1 件に 2 回のメンション |
| 修正の役の開始した実行だけが差し戻しになる | 2 つの修正の役と実装の役の実行、修正の役の開始前の取り消し |
| 役ごとのトークン数が出て、使用量のない実行が未確認と件数で出る | 使用量が 2 行の実行、0 行の実行、名前が規則に合わないエージェント |
| 同じ入力から 2 回流した結果が 1 バイトも違わない | 上の見本で 2 回流し、`cmp` で比べる |
| 区切りと範囲を替えて流せる | `--from` と `--cutoff` を替え、対象のタスクの数と値が変わる |
| 比べる値との差を出せる | `--compare` に合計の見本を渡す |

`collect` は、`tests/cli-stub.py` の CLI のスタブで確認する。すべてのページを読むこと、切り詰めの警告で止まること、欄の欠けで止まること、本文を残さずメンションの ID だけを残すことを見る。スタブの応答は、実物の見本から作る。状態の変化（`issue timeline`）を含めて追加採取した見本のコマンドとバージョンは、`tests/fixtures/cli/METRICS-CAPTURE.json` にある。

収集は、タスク一覧の `has_more` に従って `offset` を進める。コメントは `--recent` と `--full` で読み、CLI が標準エラーへ出す `Next thread cursor` の時刻と ID で次へ進める。このカーソル以外の標準エラーは警告として止める。

状態変更の前後は実応答の `details.from` と `details.to` から読む。実行の `started_at` と `completed_at` は null を許し、`usage` が省略された形は未確認として空の配列へ直す。それ以外の、スナップショットへ残す必須欄の欠落はエラーにする。読み取りと検証がすべて成功してから出力を置き換えるので、失敗しても前のスナップショットは保つ。

## 検討した案

トークン数の出どころとして 3 つの案を比べ、実行の記録の使用量を使う案を採る。案 C は、原本に保存の処理を入れる案で、採らない理由と、採るときの形を下に残す。

| 案 | 原本と導入先への影響 | 未確認になる実行 | 判断 |
| --- | --- | --- | --- |
| 実行の記録の使用量を読む（採る） | なし | 使用量を記録しない実行だけ | 目的を満たし、導入先に何も配らない |
| C. 原本に、実行が終わるたびに保存する処理を入れる | ホストの共有の設定が変わり、流し直しが要る | 流し直す前の実行と、保存に失敗した実行 | Multica がすでに残す値を二重に残す。導入先の全員に変更を配る |
| 会話の記録だけから数える | なし | 作業ディレクトリが片付けられた Codex の実行 | 作業ディレクトリが片付けられた Codex の実行は読めず、未確認が多くなる |

案 C を採るなら、次の形になる見込みである。どれも採る前に確認が要る。

- Claude は、エージェント用の設定のディレクトリ（`CLAUDE_CONFIG_DIR`）の `settings.json` に、セッションの終わりのフックを足す。フックは会話の記録の使用量を、メッセージと要求の ID で重ねずに足す
- Codex は、セッションの終わりのフックがない（未確認）。タスクごとの `CODEX_HOME` が片付けられる前に読むには、`notify` で応答のたびに累計を上書きする形になる
- 原本の Codex の設定は、人の `notify` と切り離すために `notify` を持たない。上の形では、その決まりを変える
- 保存先は、実行のタスクの metadata にする。実行の環境には実行の ID（`MULTICA_TASK_ID`）だけがあり、タスクの ID を CLI から引く方法は未確認である
- 失敗しても実行を止めないよう、フックは時間を区切り、常に 0 で終える。コメントは書かない
- ホストの共有のファイルが変わるので、セットアップの流し直しで保存が始まる。エージェント、オートパイロット、スキルの登録は変わらない見込みである
