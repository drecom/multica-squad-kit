# 手戻りの見直しの記録を、共有の判定の出力から読む

`squad-review-next` の `decide` は、リーダーの `手戻りの見直し:` の行を、共有の判定の `analyze` の出力から読む。記録を読むためだけに、すべてのコメントの本文の解析・並べ替え・判定をもう 1 回流すことはしない。行き先・終了コード・書くコメントは、記録の読み方に左右されない。

この文書は、記録の読み方と、その理由を書く。書く内容は、想定する規模と許容時間、重複した解析がないことの確認の方法、想定規模での測り方である。手戻りの見直しの決まりはリーダーの指示の「手戻りの見直し」、本文の読み方は [読める本文](review-next-step.md#読める本文)が正本である。

## 目的と範囲

目的は、`decide` が記録を読むために、すべてのコメントの本文の解析を重ねて流さないことと、性能を見る役が読める想定規模と許容時間を置くことである。

次は、記録の読み方に左右されない。

- 記録を信頼する条件（作者がリーダーのエージェントである）と、[読める本文](review-next-step.md#読める本文)の決まり
- `decide` の行き先、終了コード、書くコメント、止まる理由の行
- 共有の判定の `analyze` 以外のモードと、`squad-review-wait`・`squad-pr-watch` の動作

次は対象にしない。

- 許容時間を CI のテストの失敗の条件にすること
- `decide` のほかの処理の性能の見直し。測って分かったことは[残る危うさ](#残る危うさ)に書く
- 性能を見る役に検証のスキルを割り当てること

許容時間を CI のテストの失敗の条件にしない理由は、機械の性能がそろわないためである。重複した解析がないことは、時間ではなく処理の数で確認する。

## 記録の読み方

共有の判定の `analyze` が、リーダーの記録があるかを出力に含め、`decide` の判定はその値を読む。本文の解析は `analyze` の 1 回だけで、記録を読むために共有の判定のソースをもう 1 回実行しない。

`analyze` の出力は、真偽の欄 `rework_reviewed` を持つ。次の 3 つがそろうコメントが 1 つでもあれば `true`、なければ `false` にする。

1. 作者の種類がエージェントである
2. 作者の ID が、判定に渡したリーダーの ID のどれかである
3. [読める本文](review-next-step.md#読める本文)で、囲みの外の「ほかの行」に、`手戻りの見直し:` で始まる行がある

時刻と指す回は問わない。記録は 1 タスクにつき 1 回で、どの回より前に書かれていても数えるためである（記録の決めはリーダーの指示の「手戻りの見直し」にある）。`返事の回:` の行の有無も問わない。

欄は、`analyze` がコメントごとに作っている解析の結果（作者、作者の種類、置き方を満たす行）から求める。解析したコメントを 1 つずつ確認し、本文をもう 1 回読むことはしない。欄を出すのは `analyze` のモードだけで、`merge_requested`・`body`・`state` のモードの出力には入らない。

`decide` が `analyze` に渡すリーダーの ID は、名簿のリーダーの 1 つだけである。ほかの入力は要らない。

`decide` の判定は、次のとおり動く。

- `decide_py` は、共有の判定のソースを受け取らず、実行もしない。`analyze`・`lineage`・`linkfail` のどのモードも、`decide` の判定のプログラムだけを起こす
- [修正の依頼の 2 つめの規則](review-next-step.md#修正の依頼)は、`judge.json` の `rework_reviewed` が `true` のときに、リーダーの記録があるとする
- `rework_reviewed` は、`rounds` や `finals` と同じ読み方で読む
- `rework_reviewed` の欄がないときは、`decide` は読めない出力と同じく失敗で終わり、何も書かない。記録があるものとして進めない

## 想定する規模と許容時間

`decide` がコメントの本文を読んで行き先を決める処理は、次の規模で、次の時間に収める。性能を見る役は、この節を基準にする。

| 項目 | 値 |
| --- | --- |
| 想定する規模 | 1 つのタスクのコメントが 500 件、本文（`content`）の合計が 100 万バイト（UTF-8） |
| 許容時間 | 想定する規模で、1 回の `decide` につき 1 秒以内 |
| 許容時間の対象 | コメントの一覧を受けて本文を読み、行き先を決める 2 つの処理の合計。共有の判定の `analyze` と、`decide` の判定（`decide_py analyze`）である |
| 対象に含めない | CLI の読み取りとその出力の検証（`squad_cli_read`）、名簿と PR の読み取り、`jq` での受け渡し、依頼を書く処理 |

対象を 2 つの処理に限るのは、本文を 1 行ずつ読むのがこの 2 つだけで、規模で時間が伸びるためである。CLI の読み取りは、この設計で対象から外している。

許容時間は、手元で 1 回測って確認する（[想定規模で 1 回測る](#想定規模で-1-回測る)）。CI では確認しない。CI で毎回確認するのは、[処理の数](#処理の数で確認する)である。

`AGENTS.md` の「性能の想定規模と許容時間」は、この節へのリンクだけを置き、数字を写さない。同じ決まりを 2 か所に置かないためである。性能を見る役は、`AGENTS.md` からこの節へ進める。

## 処理の数で確認する

重複が消えたことは、1 回の `decide` が起こす `python3` の数で確認する。数は機械によらないので、CI のテストの失敗の条件にできる。

テストは、数えるための `python3` の包みを `PATH` の先頭に置く。包みは、起動ごとに次を記録してから、本物の `python3` に同じ引数を渡す。

| 記録すること | 見分け方 |
| --- | --- |
| 共有の判定の起動か | `-c` に渡したプログラムの文が、共有の判定のソース（`SQUAD_CLI_CONTROL_PY`）と一致する |
| 共有の判定のソースを引数に持つ起動か | プログラムの文より後ろの引数のどれかが、共有の判定のソースと一致する |
| モード | プログラムの文の次の引数 |

包みは bash のスクリプトで、`tests/squad-review-next-decide-rework-record-test.sh` が置く。テストの偽の CLI も `python3` を起こすが、プログラムの文が共有の判定のソースではないので、どちらの数にも入らない。

共有の判定の解析・並べ替え・判定は、このソースの中にしかない。そのため、ソースをプログラムとして起こした回数と、引数で受け取った回数を数えれば、すべてのコメントの解析が何回流れたかが分かる。

1 回の `decide` で期待する数は、次のとおりである。❌ の結果があって修正の依頼を書く場面と、❌ の結果がなく最終レビューの依頼を書く場面の、両方で確認する。

| 数えるもの | 数 |
| --- | --- |
| 共有の判定を `analyze` のモードで起こした回数 | 1 |
| 共有の判定のソースを引数に持つ起動の回数 | 0 |

`body` のモードの起動は数に入れない。書く本文が読めるかを確認する処理で、コメントの一覧を渡さないためである。マージの前の CI を待つ場面は、待ちの記録を書いたあとに `analyze` をもう 1 回流すので、この表の場面にしない。頼み直しの場面も、頼み直しの行を作る処理が共有の判定のソースを引数で受け取るので、この表の場面にしない（[残る危うさ](#残る危うさ)）。

## 想定規模で 1 回測る

許容時間は、処理を想定規模で 1 回流して測り、結果を PR の確認に残す。測るのは、同じテストのファイルを、規模を変えて流す 1 つのコマンドである。

[処理の数](#処理の数で確認する)の包みは、本物の `python3` の実行にかかった秒も記録する。bash の `time` で本物の実行だけを測るので、包みの起動は含まれない。

時間を足すのは、対象の 2 つの起動だけである。共有の判定は、[処理の数](#処理の数で確認する)で `analyze` のモードと見分けた起動である。`decide` の判定は、`-c` に渡したプログラムの文が共有の判定のソースではなく、次の引数が `analyze` の起動である。`squad-review-next` がこの形で起こすのは `decide_py analyze` だけである。

テストは、規模の場面を環境変数で受け取る。

| 環境変数 | 意味 | 既定 |
| --- | --- | --- |
| `REVIEW_NEXT_TEST_SCALE_COMMENTS` | コメントの件数。ちょうどこの件数にする | 20 |
| `REVIEW_NEXT_TEST_SCALE_BYTES` | 本文の合計のバイト数。この値以上で、最も近い大きさにする | 20000 |

規模の場面のコメントは、リーダー・レビューの役・メンバーが書いたものを混ぜ、本文に囲み・引用・項目と、その中の `手戻りの見直し:` の見本の行を入れる。リーダーの記録の行は 1 つだけ置く。場面は、❌ の結果がある場面とない場面の 2 つで、行き先と処理の数を確認したあと、次の形の行を出す。

```text
測定: コメント <件数> 件、本文 <バイト数> バイト、❌ <あり | なし>、共有の判定 <秒> 秒、decide の判定 <秒> 秒、合計 <秒> 秒
```

時間は出すだけで、失敗の条件にしない。CI は既定の小さい規模で流れ、同じ場面の作り方と数え方を毎回通す。想定規模の場面を CI で毎回流さないのは、テストの偽の CLI と読み取りの検証で 1 場面に時間がかかり、CI の時間を使うためである。

測るときは、2 つの環境変数に 500 と 1000000 を渡して、テストのファイルを直接流す。PR の確認には、次の 4 つを残す。

1. 流したコマンド
2. 規模（`測定:` の行の件数とバイト数）
3. 時間（2 つの場面の `測定:` の行の合計）
4. 測った機械（CPU、OS、Python と bash のバージョン）

合計が 1 秒を超えたときは、PR をそのまま進めず、設計の役へ返す。

## 入力と信頼の表

読む入力と信頼する条件は、リーダーの指示の「手戻りの見直し」の記録の決めに従う。条件を確認する場所は、共有の判定の `analyze` である。

| 入力（誰が書いた何か） | 読むところ | 信頼する条件 | 合わないとき |
| --- | --- | --- | --- |
| タスクのコメントの `手戻りの見直し:` の行（どの役も人間も書ける） | 共有の判定の `analyze`。`rework_reviewed` の値にする | 作者の種類がエージェントで、作者の ID が判定に渡したリーダーの ID である。行が読める本文の、囲みの外の「ほかの行」にある | 読まずに飛ばし、行がないものとして扱う。`rework_reviewed` は `false` になる |
| `judge.json` の `rework_reviewed`（同じ `decide` の実行が、共有の判定の出力から書く） | `decide` の判定の、修正の依頼の 2 つめの規則 | 値が `true` である。ファイルは `decide` が実行ごとに作る作業のディレクトリにあり、ほかの役は書かない | `false` なら記録がないものとして、理由の行でリーダーを起こして止まる。欄がなければ失敗で終わり、何も書かない |
| `analyze` に渡すリーダーの ID（`decide` が名簿から読む） | 上の 1 行目の作者の確認 | [スクワッドとリーダーの決め方](review-next-step.md#スクワッドとリーダーの決め方)で決めた値である | リーダーを決められなければ、`decide` は `analyze` の前に止まる |

リーダーの ID を渡さない呼び出しでは、`rework_reviewed` は必ず `false` になる。作者を確認できない行を、記録と読まないためである。

## 互換性と影響を受ける利用者

セットアップを流し直す前と後で、同じコメントの一覧とタスクに対する `decide` の行き先、終了コード、書くコメントは同じである。

共有の判定は、ID のないコメントを読まない。Multica のコメントは必ず ID を持つので、実際の一覧では起きない。起きたとしても、リーダーの記録が読まれずに止まる側に倒れる。

見張りのスクリプトは、セットアップが同じ実行でまとめて置き換える。新しい `squad-review-next` と古い `squad-cli-lib` の組み合わせでは、`rework_reviewed` の欄がなく、`decide` は失敗で終わる。古い `squad-review-next` と新しい `squad-cli-lib` の組み合わせは動く。古い `squad-review-next` は共有の判定のソースを自分で実行し、出力の欄が増えても影響を受けないためである。

`analyze` の出力を読むほかの処理は、欄を名前で読むので、知らない欄があっても影響を受けない。`squad-review-wait` と `squad-pr-watch` は `analyze` のモードを使わない。

## テスト

`decide` のテスト（`tests/squad-review-next-decide-*-test.sh`）は、すべて通す。記録を読む場面の多くは `tests/squad-review-next-decide-fix-test.sh` にあり、`tests/squad-review-next-decide-rework-record-test.sh` は、そこにない場面と処理の数を置く。

| テスト | 確認すること |
| --- | --- |
| `tests/squad-review-next-decide-fix-test.sh` | リーダーの行があれば、止まらずに修正の依頼を書く。リーダー以外の役の行とメンバーの行、囲み・HTML のコメント・引用・字下げ・項目の中の行、閉じない囲みや制御文字のある本文の行では、リーダーを起こして止まる |
| `tests/squad-cli-lib-control-test.sh` | リーダーのエージェントが読める本文に書いた行で、`rework_reviewed` が `true` になる。行がない・リーダー以外の役の行・メンバーの行・囲みの中の行・読めない本文の行・リーダーの ID を渡さない呼び出しでは `false` になる |
| `tests/squad-review-next-decide-rework-record-test.sh` | 下の表の場面と、[処理の数](#処理の数で確認する)と、[規模の場面](#想定規模で-1-回測る) |

`tests/squad-review-next-decide-rework-record-test.sh` に置く、記録を読む場面は次のとおりである。どれも、`設計の変更: 実装を始めたあと` の行があり、マークがなく、❌ の結果がある。

| 場面 | 期待 |
| --- | --- |
| 作者の ID がリーダーと同じで、作者の種類がメンバーのコメントに行がある | リーダーを起こして止まる |
| リーダーのコメントで、行が行頭でなく文の途中にある | リーダーを起こして止まる |
| 行が、コメントではなくタスクの本文にある | リーダーを起こして止まる |
| リーダーのコメントが 2 つあり、読めない本文のほうだけに行がある | リーダーを起こして止まる |
| リーダーのコメントが 2 つあり、読めない本文と読める本文の両方に行がある | 止まらずに修正の依頼を書く |
| リーダーの行が、回のコメントより前の、別のスレッドの返信にある | 止まらずに修正の依頼を書く |

止まる場面は、理由の行が `設計の変更が実装を始めたあとで、マークも 手戻りの見直し: もない（手戻りの見直しの判断）` であることも確認する。

`common/monitor/squad-cli-lib` を変えたときは、手元で全件（`bash tests/run.sh`）を流す（[変更の進め方](../CONTRIBUTING.md)）。

## 残る危うさ

- 許容時間の対象は 2 つの処理だけである。`decide` の全体は、想定規模ではこれより長くかかる
- コメントの一覧の読み取りと出力の検証（`squad_cli_read issue-comments`）は、想定規模では許容時間より長くかかる。読み取りはこの設計で対象から外しているので、ここでは扱わない
- `jq` での受け渡しは対象に含めない。共有の判定へ一覧を渡す `jq` は、想定規模でも許容時間に比べて十分短い
- 頼み直しの行を作る処理（`enumeration_lines`）も、共有の判定のソースを実行して本文を読む関数を取り出す。記録を読む処理ではないので、記録の読み方の対象にせず、同じ形の重複として残る
- 処理の数のテストは、共有の判定のソースを通らない解析を見つけない。`decide` の判定のプログラムに本文の解析を書き足す変更は、レビューで見る
- 許容時間は CI で確認しないので、あとの変更で遅くなっても、テストは失敗しない。性能を見る役が、[想定する規模と許容時間](#想定する規模と許容時間)を基準に、変更ごとに見る

## 検討した案

記録の読み方として、次の案を比べた。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| `analyze` の出力に、記録があるかの真偽の欄を持たせる（採用） | 解析が 1 回になる。作者と本文の確認が共有の判定の 1 か所に集まり、`judge.json` はほとんど増えない | 共有の判定が、手戻りの見直しの行の名前を知る |
| `analyze` の出力に、コメントごとの置き方を満たす行をすべて足す | `decide` の判定が、ほかの行も同じ方法で読める | `judge.json` が本文と同じ大きさになり、受け渡しと読み込みが増える。作者の確認が `decide` の判定に残る |
| 共有の判定を、本文を読む関数の部分と判定の部分に分け、`decide` の判定は関数の部分だけを実行する | 並べ替えと判定の重複は消える | リーダーのコメントの解析は 2 回のまま残る。3 つのスクリプトが使うソースの形が変わる |
| リーダーのコメントの行を、行頭の語を引数で指定して探す汎用の欄にする | ほかの行にも使える | 使う行が今は 1 つだけで、引数と出力の形の決まりが増える |
| 重複を残す | 手を入れずに済む | 要らない解析・並べ替え・判定が、❌ の結果がなくても毎回流れる |

確認の方法と測り方として、次の案を比べた。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| 処理の数を CI のテストで確認し、時間は手元で 1 回測って PR に残す（採用） | 数は機械によらず、毎回確認できる。時間の目標を CI に置かない決まりに合う | 時間は、あとの変更では確認できない |
| 想定規模の時間を、CI のテストの失敗の条件にする | あとの変更で遅くなると失敗する | ランナーの性能と混み具合で結果が揺れる。時間の目標を CI に置かない決まりに反する |
| `decide` の全体の時間を測る | 測り方が単純である | テストの偽の CLI と読み取りの検証が時間のほとんどを占め、対象の処理の時間が読めない |
| 測るためだけのスクリプトを、テストとは別に置く | テストが小さいままになる | CI で流れないので、場面の作り方が古くなっても気づかない |
| 想定規模の場面を、CI で毎回流す | 規模での処理の数も毎回確認できる | 1 場面に時間がかかり、CI の時間を使う |
