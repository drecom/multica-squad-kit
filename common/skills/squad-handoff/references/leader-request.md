# リーダーの手順: 作業先・要件と設計・受け渡し

このファイルはリーダーの手順で、リーダーだけが読む。ほかの役は読まない。リーダーの指示の「場面と手順」から、新しい要望を受けたとき、作業先を決めるとき、要件と設計を進めるとき、実装のフェーズを頼むとき、依頼を書くときに読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## 作業先を決める

最初に振り分ける前に、タスクの metadata の `repository` を決めて書く。一覧が一つならそれを使い、二つ以上ならプロジェクトの説明にある各リポジトリの役割とタスクの本文から決める。どの役割にも当たらない、二つ以上に当たる、説明が未記入で決められないときは、人間を呼んで止まる。選択の先頭を自動で使わない。ただし、要件を決める役がなく最上位の役がある構成で、要望が二つ以上のリポジトリの役割に当たるときは、親に `repository` を書かず、止まらずに下の「複数のリポジトリにまたがる要望」に従う。

振り分けのたびに、`repository` が「このプロジェクトの値」の一覧にあるかを確認する。人間が書いた値も同じく確認し、一覧にない値や外したリポジトリのタスクは、人間を呼んで止まる。上の複数のリポジトリにまたがる親は、親ではなく各 sub-issue の `repository` で確認する。書き方と各役の確認は、squad-handoff の `references/repo-target.md` の「タスクの作業先を決める」に従う。

### 複数のリポジトリにまたがる要望

要件を決める役があるときは、その役が要件を合意するときにリポジトリごとの sub-issue に分ける。親にはリポジトリ間の I/F の合意を残し、sub-issue ごとに作業先と stage を確認し、設計からの流れを通す。

要件を決める役がなく、最上位の役がないときは、人間と合意済みの要件をリポジトリごとの sub-issue に分ける。親にはリポジトリ間の I/F の合意を残し、sub-issue ごとに作業先と stage を設定して、設計からの流れを通す。要件を自分で定義しない。

要件を決める役がなく、最上位の役があるときは、親に `repository` を書かず、人間も呼ばない。要件の見直しを頼む前に、次の順で進める。どのリポジトリに分けるかを本文から決められないときは、今のとおり人間を呼んで止まる。

1. リポジトリごとの sub-issue を、担当なしの `backlog` で作る。最初のステージも `backlog` にする。本文には、親の要件のうちそのリポジトリの分を書き、リポジトリ間の I/F は親に残す。要件を自分で定義しない
2. 各 sub-issue の metadata の `repository` に `OWNER/REPO` を書き、先に入れるリポジトリから順に `--stage` を付ける。値が「このプロジェクトの値」の一覧にあることを確認する
3. 親のタスクで要件の見直しを頼む。見直しの頼み方は `leader-principal-pick.md` の「最上位の役を呼ぶところ」にある。sub-issue では見直さない
4. 結果を受けるまで、sub-issue の担当と状態を変えない

結果のあとは、`leader-principal-design.md` の「要件の見直し」に従う。✅ で本文の値が合えば、人間を呼ばずに最初のステージの sub-issue にスクワッドの担当と状態を付けて回す。各 sub-issue は、設計からの流れを通す。❌ か ⚠️ なら、指摘を添えて人間を呼ぶ。分け方を直すときは、人間が本文とあわせて sub-issue も直す。最初のステージも担当なしの `backlog` で作るのは、squad-handoff の `references/new-task.md` の「新しいタスクを作るとき」の決まりの例外である。

## 要件と設計を進める

要件を決める役があるときは、新しい要望をその役に頼んで要件を合意してもらう。合意されていない要件を設計や実装へ回さない。

要件を決める役がないときは、合意済みの要件と受け入れ条件を確認する。不足や未合意があれば、人間に準備と合意を頼んで止まる。自分で要件を定義しない。そろっていて最上位の役があれば、次の有効な役へ回す前に、`leader-principal-pick.md` の「最上位の役を呼ぶところ」に従って要件の見直しを頼み、結果を受けてから回す。最上位の役がなければ、そのまま次の有効な役へ直接回す。複数のリポジトリにまたがる要望は、見直しの前に、上の「複数のリポジトリにまたがる要望」の順で sub-issue を作る。

設計の役があるときは、合意された要件の設計をその役に頼む。人間の設計とフェーズの分け方の承認を受けてから実装へ回す。ラベル `重要` のあるタスクは、`leader-principal-design.md` に従い、承認の前に最上位の役の見直しを挟む。

設計の役がなく、最上位の役があるときは、人間の設計が届いたら実装を頼まず、`leader-principal-pick.md` の「最上位の役を呼ぶところ」に従って設計の見直しを頼む。共通 2 の対象で security-reviewer にも頼んだときは、結果の扱いと見せ直しを `leader-principal-final.md` と `leader-principal-reshow.md` に従う（次の「結果を受けたら」の文は、最上位の役だけに頼んだときの扱いである）。結果を受けたら、人間をメンションして結果を示し、指摘を直したうえで設計とフェーズを承認するよう頼み、`in_review` にする。直した設計を最上位の役に見せ直さない。最上位の役の結果より前に人間が承認と書いていても、結果のあとにもう一度承認を頼む。承認を受けてから、次の有効な実装の役へ回す。設計が必要なのに届いていなければ、人間に設計の手配を頼んで止まる。自分で設計や draft PR を作らない。

設計の役も最上位の役もないときは、必要な設計と承認が揃っているか確認し、次の有効な実装の役へ直接回す。設計が必要なのに未準備なら、人間に設計の手配と承認を頼んで止まる。自分で設計や draft PR を作らない。

要件を決める役と設計の役へ頼む前に、`squad-usage-wait pick <タスク> planner` か `squad-usage-wait pick <タスク> designer` を流す。コマンドの時間切れは 120 秒以上にする。終了コード 0 なら、その役へ頼み、出力の `振り分け:` の行を依頼に添える。終了 3 は、役の系統が上限に近いので、依頼を書かず、出力の `使用率の待ち:` の行をタスクのコメントに写して終える。起こしは `pick` が置いていて、人間は呼ばない。終了 4 と 1 の扱いは [leader-dispatch.md](leader-dispatch.md) の「役の選び方」に従う。使用率の待ちの起こしで起きたときも、同じ `pick` から頼み直す。

## フェーズを頼む

承認された実装のフェーズは、一覧の順に、一度に 1 フェーズだけ頼む。前のフェーズの成果物が共有されてから次へ進む。全部のフェーズが揃うまでレビューを始めない。バグは再現手順と期待する動作を確認し、なければ起票した担当に補ってもらう。

実装のフェーズを頼む前の役の選び方は、`leader-dispatch.md` に従う。

## 依頼の書き方と受け渡し

- 依頼は、スキル squad-handoff の「引き継ぐとき」の「リーダーの依頼」の型で書く。実装のフェーズならフェーズ番号とそのフェーズの内容だけを写す。成果物と合意の記録はタスクのコメントと metadata を参照してもらう
- 担当はスクワッドのままにし、依頼先をメンションする。返事の先として自分をメンションしない。振り分けたら今回の実行を終える
- ステージのある sub-issue は、親の children を見て、次がすでに backlog から出ていれば重ねて進めない
- `multica squad activity` がリーダーの実行でないため失敗したら、流し直さず、追加コメントもせず、最後の返答に失敗を 1 行書く
