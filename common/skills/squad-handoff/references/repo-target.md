# 作業先の決め方

このファイルは、タスクの作業先を決める場面で読む。リーダーと、リポジトリで作業する役が読む。

## タスクの作業先を決める

リポジトリで作業するタスクは、1 タスクにつき 1 リポジトリ・1 PR にする。作業先はタスクの metadata の `repository` に `OWNER/REPO` で残す。役ごとに本文から推測し直さない。紐付け専用の一覧は、タスクの作業先や定期処理の対象には使わない。

| 担当する仕事 | 確認することと作業 |
| --- | --- |
| リーダー | 最初に振り分ける前に `repository` を決めて書く。既存の値も人間が書いた値も、プロジェクトの一覧にあることを確認してから振り分ける。要件を決める担当がなく最上位の役がある構成で、要望が二つ以上のリポジトリにまたがる親は、親に `repository` を書かず、sub-issue の値で確認する。 |
| 要件を決める | 作業先を確認し、複数のリポジトリにまたがる要望は、要件を合意するときにリポジトリごとの sub-issue に分ける。 |
| 設計・実装・修正 | `repository` のリポジトリを checkout し、そのリポジトリの `AGENTS.md` と作業別のルールを読む。そこで PR を作るか既存の PR に積む。 |
| レビュー・QA | 依頼の PR の URL からリポジトリを決め、プロジェクトの一覧と照合して checkout する。metadata の読み取りは不要。 |
| 定期の確認や見張り | オートパイロットや依頼で明示された一つのリポジトリを一覧と照合して使う。リポジトリを使わない見張りのために checkout しない。 |

リーダーは、一覧が一つならそれを `repository` に書く。二つ以上なら、プロジェクトの説明にある各リポジトリの役割とタスクの本文から決める。どの役割にも当たらない、二つ以上に当たる、役割が未記入などで決められなければ、人間を呼んで止まる。選択の先頭を代わりに使わない。ただし、要件を決める担当がなく最上位の役がある構成の、二つ以上に当たる親は、止まらずに分割へ進む。親に `repository` を書かず、`leader-flow.md` の「複数のリポジトリにまたがる要望」に従う。

metadata は `multica issue metadata set <タスク> --key repository --value <OWNER/REPO> --type string` で書く。既存の値が一覧になければ、勝手に別の値へ直さず人間を呼んで止まる。外したリポジトリを作業先に持つタスクも同じ扱いにする。

要件・設計・実装・修正の担当は、`repository` がないか一覧にないとき、作業を始めずリーダーに返す。既存の PR がその値と違うリポジトリにあれば、作業を進めず不一致を返す。レビュー・QA は PR の URL を使うが、一覧にない PR は同じくリーダーへ返す。PR 以外の検証は、依頼が明示した対象を一覧と照合し、作業先が分からなければ推測せず返す。

複数リポジトリの sub-issue には、それぞれの作業先を `repository` に書く。先に入れるリポジトリから順にステージを付け、リポジトリの間で合わせる I/F は親のタスクの要件として合意する。各 sub-issue は一つのリポジトリのタスクとして、設計からの流れを通す。要件を決める担当を置かないときは、リーダーがこの分割を行う。最上位の役があれば、要件の見直しの前に、担当なしの `backlog` で分ける。
