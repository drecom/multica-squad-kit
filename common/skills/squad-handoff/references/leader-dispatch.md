# リーダーの手順: 実装・修正の振り分け

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、実装や修正を頼むときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

役の有無と系統で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。有効な実装・修正の役の一覧も、そこにある。

## 回し先と使用率

新しくコードを書く仕事とバグは実装の役へ、レビューの指摘・コンフリクト・CI の失敗は修正の役へ回す。依頼ごとに `squad-usage-wait pick` で使用率を読み直して選び、30 分より古い値は使わない。上限に近くても、モデルを下げたり工程を飛ばしたりしない。空いている系統の役へ回すか、空きが戻る時刻まで待つ。

実装のフェーズを頼む前と、修正を頼む前に、`leader-principal.md` の「判断する時機」でマークを確認する。マークのないタスクでは、同じ `leader-principal.md` の「手戻りの見直し」で、手戻りの合図も確認する。最上位の役がないときは、この確認を飛ばす。修正を頼む前は、先に `leader-fix-request.md` の「修正の依頼の前に確認する順」に従い、人間を呼ぶ確認と手戻りの見直しの確認の順を守る。

頼む前に、`squad-run-cut state <タスク>` が `待ち` か `動いている` を返す役がいないかを確認する。いれば、どの役にも新しく頼まない。`leader-run-cut.md` の「区切りの途中」に従う。

## 役の選び方

`squad-usage-wait pick <タスク> <implement | fix> [小さい | 大きい]` で選ぶ。実装のフェーズは `小さい` か `大きい` を添え、バグは添えない。修正は `fix` で、添えない。読み取りは 90 秒で打ち切るのでコマンドの時間切れは 120 秒以上にする。両系統の構成かは、スクリプトが名簿で決める。

| 終了コード | 意味 | すること |
| --- | --- | --- |
| 0 | 役を選んだ。`役:` と `振り分け:` の行を出す | `役:` のマークを、リーダーの指示の「このスクワッドの役」にある有効な役の一覧に対応させ、その完成したリンクで依頼する。`振り分け:` の行はそのまま依頼に添える |
| 3 | 待つ。起こしを置き、`使用率の待ち:` の行を出す | 依頼を書かず、その行をタスクのコメントに写して終える。人間は呼ばない |
| 4 | 待ち始めから通算 24 時間を超える | `使用率の待ち:` の行を写して人間を呼び、「待つ」「進める」「利用枠を足した」のどれかを決めてもらう。3 つの答えと、「待つ」と「進める」がスクワッドのすべてのタスクに効くことを書く。`in_review` にする。人間の返事は、「使用率の待ちで人間が答えたとき」で扱う |
| 1 | 使い方や読み取りの誤り | 標準エラーの要約を添えて人間を呼ぶ |

使用率を読めないときの代わりの決まりは、スクリプトに任せる。両系統があれば `squad-dispatch-pick` の代わりの決まりで、片系統ならその系統に固定して選ぶ。読めないことを理由に待たない。使用率の取得に失敗したとき、古い値を使わない。

## 使用率の待ちの起こしで起きたとき

指示が `使用率の待ちの起こしで起きました。` で始まる実行は、止めた工程をもう一度頼む。指示にある工程と、`decide` から待った回なら回のコメントの ID を読む。

1. 止めた工程が実装か修正なら、この手順で `squad-usage-wait pick` を流し直す。終了 0 なら依頼を書き、終了 3 なら、また待つ行を写して終える
2. 要件を決める役と設計の役の工程は、[leader-request.md](leader-request.md) の `pick` から頼み直す。最上位の役の工程は、[leader-principal-pick.md](leader-principal-pick.md) の `pick` から頼み直す
3. `decide` から待った回は、`squad-review-next decide <タスク> <回のコメント>` を流し直す。出力の `次の依頼:` の行を最後の返答にする。ただし、その回を指す人間を呼ぶコメント（`前の回:` の行がその回の ID）があれば、`decide` を流し直さず、「`decide` が人間を呼んだ回の続き」の手順で進める

空きが戻っていれば、`pick` が役を選ぶので、そのまま工程が続く。まだ上限に近ければ、`pick` が起こしを置き直す。

## 使用率の待ちで人間が答えたとき

`pick` が終了 4 で終わると、リーダーは `squad-task-post` で人間を呼んで `in_review` にする。人間が返事をしたら、答えを読み分ける。答えの記録の行は手で書かない。`使用率の待ちの延長:` の行も、もう書かない。

| 人間の返事 | すること |
| --- | --- |
| 待つ、進める | `squad-usage-wait answer <タスク> <工程> <待つ \| 進める> <返事のコメントの ID>` を流す。工程は、人間を呼んだ `使用率の待ち:` の行の工程にする。`answer` は 8 日以内に動きのあったタスクのコメントも読むので、コマンドの時間切れは 600 秒以上にする。終了 0 ならタスクを `in_progress` に戻し、止めた工程の `pick` を流し直す。`pick` が終了 0 なら頼み、終了 3 なら行を写して終える |
| 利用枠を足した | `answer` を流さず、`in_progress` に戻して `pick` を流し直す。役が選べれば、工程が再開する |
| 質問、はっきりしない答え、エージェントのコメント | `answer` を流さず、3 つの答えを示して、もう一度人間に決めてもらう。`in_review` のままにする |

`answer` が終了 1 で終わったときは、`pick` を流さず、標準エラーの要約を添えて人間を呼ぶ。タスクは `in_review` のままにする。使用率を読めなかったときは、答えを記録できなかったことと、同じ答えをもう一度返事してほしいことを書く。記録もマークも書いていないので、同じ返事で `answer` を流し直せば記録できる。

「待つ」と「進める」の答えは、答えたときに上限に近かった枠のリセット時刻までの期限つきで、同じスクワッドのすべてのタスクと工程に効く。効いている答えを人間が変えたいと書いたときも、同じ `answer` を流す。人間を呼んでいないタスクのコメントでもよい。変えたあとは、新しい答えに従う。

## `decide` が人間を呼んだ回の続き

`decide` が人間を呼んだ回の続きは、人間が答えたあと、リーダーが頼む。同じ回の `decide` は流し直さない。流し直すと `次の依頼: 書き済み` で終わり、次の依頼も起こしも書かれない。3 つの答えのどれでも同じである。

人間を呼ぶコメントに `前の回:` の行があれば、`decide` が呼んだ回である。コメントは、作者が、その回の返事を待つ役かリーダーのエージェントで、行が引用や囲みの中でなく行の頭にあるものだけを読む。そうでないコメントは、`decide` が呼んだ回として扱わず、上の「使用率の待ちで人間が答えたとき」の手順で進める。頼む回を決められなければ、依頼を書かずに人間を呼ぶ。返事は上の表で扱い、止めた工程の `pick` を次のとおり流す。

1. 工程は、人間を呼ぶコメントの `使用率の待ち:` の行の工程にする。`fix` か `principal` で、`principal` は `leader-principal-pick.md` の手順のとおり系統を添える
2. `--round` は渡さない。渡すと、置かれる起こしの指示が同じ回の `decide` の流し直しになり、起きたあとに書き済みで止まる
3. 頼む回は、その工程の最新の人間を呼ぶコメントの、`前の回:` の行が指す回にする

| `pick` の終了コード | すること |
| --- | --- |
| 0 | その回の依頼を、手で頼む手順で書く。`fix` は、`leader-review-stuck.md` の `修正の依頼が 2 回目から` の行と同じに扱う。`principal` は、`leader-principal-final.md` の、手で最終レビューを頼む手順で頼む |
| 3 | 待つ行を写して終える。`前の回:` の行は置かない |
| 4 | 行を写し、3 つの答えを示して人間を呼ぶ |

`fix` では、回の ❌ の結果を読み、`leader-fix-request.md` の「修正の依頼の前に確認する順」で確認して、修正の依頼を書くか、人間を呼ぶ。`修正の依頼: <N> 回目` の行は、`leader-principal.md` の「修正の依頼の数え方」で数える。`直す指摘:` の行は `decide` だけが書くので、置かない。

`principal` では、依頼に `前の回: <頼む回のコメントの ID>` の行を置く。`返事を待つ役:` と `確認するコミット:` の行と `squad-review-wait watch` は、`leader-principal-final.md` の手順のとおりにする。

`principal` の最終レビューを投稿する前に `squad-review-next check <本文のファイル>` を流す。結果は [leader-review-request.md](leader-review-request.md#手で書く依頼の確認) の「手で書く依頼の確認」に従う。

頼む前に、人間を呼ぶコメントより後に、その工程の `振り分け:` の行を持つ依頼がないことを確認する。あれば頼み済みなので、頼まない。古い起こしや流し直しで、同じ回の依頼を 2 つ書かないためである。

「待つ」のあとに終了 3 で置かれる起こしは、`--round` なしの `pick` が置くので、指示に回も `decide` の流し直しもない。起きたリーダーは、「使用率の待ちの起こしで起きたとき」の手順 1 と 2 のとおり、同じ `pick` を流し直す。終了 0 なら、上の表のとおり、その回の依頼を手で書く。
