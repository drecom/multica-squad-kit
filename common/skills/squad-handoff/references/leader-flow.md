# リーダーの手順: 作業先・要件と設計・受け渡し

このファイルはリーダーの手順で、リーダーだけが読む。ほかの役は読まない。リーダーの指示の「場面と手順」から、新しい要望を受けたとき、作業先を決めるとき、要件と設計を進めるとき、実装のフェーズを頼むとき、依頼を書くときに読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## 作業先を決める

最初に振り分ける前に、タスクの metadata の `repository` を決めて書く。一覧が一つならそれを使い、二つ以上ならプロジェクトの説明にある各リポジトリの役割とタスクの本文から決める。どの役割にも当たらない、二つ以上に当たる、説明が未記入で決められないときは、人間を呼んで止まる。選択の先頭を自動で使わない。ただし、要件を決める役がなく最上位の役がある構成で、要望が二つ以上のリポジトリの役割に当たるときは、親に `repository` を書かず、止まらずに下の「複数のリポジトリにまたがる要望」に従う。

振り分けのたびに、`repository` が「このプロジェクトの値」の一覧にあるかを確認する。人間が書いた値も同じく確認し、一覧にない値や外したリポジトリのタスクは、人間を呼んで止まる。上の複数のリポジトリにまたがる親は、親ではなく各 sub-issue の `repository` で確認する。書き方と各役の確認は、squad-handoff の「タスクの作業先を決める」に従う。

### 複数のリポジトリにまたがる要望

要件を決める役があるときは、その役が要件を合意するときにリポジトリごとの sub-issue に分ける。親にはリポジトリ間の I/F の合意を残し、sub-issue ごとに作業先と stage を確認し、設計からの流れを通す。

要件を決める役がなく、最上位の役がないときは、人間と合意済みの要件をリポジトリごとの sub-issue に分ける。親にはリポジトリ間の I/F の合意を残し、sub-issue ごとに作業先と stage を設定して、設計からの流れを通す。要件を自分で定義しない。

要件を決める役がなく、最上位の役があるときは、親に `repository` を書かず、人間も呼ばない。要件の見直しを頼む前に、次の順で進める。どのリポジトリに分けるかを本文から決められないときは、今のとおり人間を呼んで止まる。

1. リポジトリごとの sub-issue を、担当なしの `backlog` で作る。最初のステージも `backlog` にする。本文には、親の要件のうちそのリポジトリの分を書き、リポジトリ間の I/F は親に残す。要件を自分で定義しない
2. 各 sub-issue の metadata の `repository` に `OWNER/REPO` を書き、先に入れるリポジトリから順に `--stage` を付ける。値が「このプロジェクトの値」の一覧にあることを確認する
3. 親のタスクで要件の見直しを頼む。見直しの頼み方は `leader-principal.md` の「最上位の役を呼ぶところ」にある。sub-issue では見直さない
4. 結果を受けるまで、sub-issue の担当と状態を変えない

結果のあとは、`leader-principal.md` の「要件の見直し」に従う。✅ で本文の値が合えば、人間を呼ばずに最初のステージの sub-issue にスクワッドの担当と状態を付けて回す。各 sub-issue は、設計からの流れを通す。❌ か ⚠️ なら、指摘を添えて人間を呼ぶ。分け方を直すときは、人間が本文とあわせて sub-issue も直す。最初のステージも担当なしの `backlog` で作るのは、squad-handoff の「新しいタスクを作るとき」の決まりの例外である。

## 要件と設計を進める

要件を決める役があるときは、新しい要望をその役に頼んで要件を合意してもらう。合意されていない要件を設計や実装へ回さない。

要件を決める役がないときは、合意済みの要件と受け入れ条件を確認する。不足や未合意があれば、人間に準備と合意を頼んで止まる。自分で要件を定義しない。そろっていて最上位の役があれば、次の有効な役へ回す前に、`leader-principal.md` の「最上位の役を呼ぶところ」に従って要件の見直しを頼み、結果を受けてから回す。最上位の役がなければ、そのまま次の有効な役へ直接回す。複数のリポジトリにまたがる要望は、見直しの前に、上の「複数のリポジトリにまたがる要望」の順で sub-issue を作る。

設計の役があるときは、合意された要件の設計をその役に頼む。人間の設計とフェーズの分け方の承認を受けてから実装へ回す。ラベル `重要` のあるタスクは、`leader-principal.md` に従い、承認の前に最上位の役の見直しを挟む。

設計の役がなく、最上位の役があるときは、人間の設計が届いたら実装を頼まず、`leader-principal.md` の「最上位の役を呼ぶところ」に従って設計の見直しを頼む。共通 2 の対象で security-reviewer にも頼んだときは、結果の扱いと見せ直しを `leader-principal.md` に従う（次の「結果を受けたら」の文は、最上位の役だけに頼んだときの扱いである）。結果を受けたら、人間をメンションして結果を示し、指摘を直したうえで設計とフェーズを承認するよう頼み、`in_review` にする。直した設計を最上位の役に見せ直さない。最上位の役の結果より前に人間が承認と書いていても、結果のあとにもう一度承認を頼む。承認を受けてから、次の有効な実装の役へ回す。設計が必要なのに届いていなければ、人間に設計の手配を頼んで止まる。自分で設計や draft PR を作らない。

設計の役も最上位の役もないときは、必要な設計と承認が揃っているか確認し、次の有効な実装の役へ直接回す。設計が必要なのに未準備なら、人間に設計の手配と承認を頼んで止まる。自分で設計や draft PR を作らない。

要件を決める役と設計の役へ頼む前に、`squad-usage-wait pick <タスク> planner` か `squad-usage-wait pick <タスク> designer` を流す。コマンドの時間切れは 120 秒以上にする。終了コード 0 なら、その役へ頼み、出力の `振り分け:` の行を依頼に添える。終了 3 は、役の系統が上限に近いので、依頼を書かず、出力の `使用率の待ち:` の行をタスクのコメントに写して終える。起こしは `pick` が置いていて、人間は呼ばない。終了 4 と 1 の扱いは [leader-dispatch.md](leader-dispatch.md) の「役の選び方」に従う。使用率の待ちの起こしで起きたときも、同じ `pick` から頼み直す。

## フェーズを頼む

承認された実装のフェーズは、一覧の順に、一度に 1 フェーズだけ頼む。前のフェーズの成果物が共有されてから次へ進む。全部のフェーズが揃うまでレビューを始めない。バグは再現手順と期待する動作を確認し、なければ起票した担当に補ってもらう。

実装のフェーズを頼む前の役の選び方は、`leader-dispatch.md` に従う。

## 依頼の書き方と受け渡し

- 依頼は、スキル squad-handoff の「引き継ぐとき」の「リーダーの依頼」の型で書く。実装のフェーズならフェーズ番号とそのフェーズの内容だけを写す。成果物と合意の記録はタスクのコメントと metadata を参照してもらう
- 担当はスクワッドのままにし、依頼先をメンションする。返事の先として自分をメンションしない。振り分けたら今回の実行を終える
- ステージのある sub-issue は、親の children を見て、次がすでに backlog から出ていれば重ねて進めない
- `multica squad activity` がリーダーの実行でないため失敗したら、流し直さず、追加コメントもせず、最後の返答に失敗を 1 行書く

### 設計との差の扱い

実装と修正の役の引き継ぎにある `設計との差:` の行を、次のとおり扱う。

| 引き継ぎ | すること |
| --- | --- |
| `設計との差: なし`、`設計との差: 照らす設計なし` | 今のとおり次へ進む |
| `設計との差:` の行がない | `なし` と同じに扱う。設計の役へ回さず、行を返させる依頼もしない。流し直しの前に動き出した実行の引き継ぎには行がなく、挙げ漏れはレビューで見つかるため |
| 差を挙げた行がある | レビューも最終レビューも頼まずに、設計の役へ回す。依頼に差の行をそのまま写す。この依頼には `設計の変更:` の行を置かない |

設計の役は、差ごとに `設計との差の扱い: <ファイル> <表に載せる | 戻す | 設計を変える>` の行と、そのあとリーダーがすることを返す。行を読み、次のとおり進める。

| 扱い | すること |
| --- | --- |
| 表に載せる | 設計の役が変更の一覧の行だけを直して push したものとして受け取る。設計の変更として扱わず、手戻りの見直しにも人間の承認にも回さず、止めていたレビューを頼む |
| 戻す | 戻す変更と代わりにすることを、差を返した役へ頼む。修正の役へは修正の依頼として回し、`修正の依頼:` の行で数える。実装の役へは同じフェーズを頼み直す |
| 設計を変える | 変える決めたことと理由を受け取り、`設計の変更: 実装を始めたあと` の行を置いて設計の役に設計の変更を頼む。変えた設計の承認と手戻りの見直しの当てはめは、`leader-principal.md` の今の決まりに従う |

表に載せるのは、差が設計の決めたことを変えないときだけである。既存の決まりを消す・弱める削除や言い換えは、戻すか設計を変える。扱いが混ざるときは、設計を変える差の設計の変更と承認を先に済ませ、次に戻す差を頼み、最後にレビューを頼む。

戻す差を修正の役へ回す前には、下の「修正の依頼の前に確認する順」の 3 と 4 に当てはめる。❌ の指摘ではないので、同じ誤りと同じ部品には数えず、`同じ部品:` と `同じ誤り:` の行を置かない。

### 同じ誤りや差し戻しが続くとき

修正の役へ差し戻すときは、この節の用語と数え方に従う。1 回目の失敗や差し戻しは、原因を確認し、依頼のコメントに原因を書いてから、同じ役へ頼み直してよい。原因が確認できなかったときは、確認した方法を添えて「未確認」と書く。

#### 診断に入る条件

この節の診断の手順は、リーダー自身の指示の原則 7 に最上位の役の診断があるときだけ使う。ないときと、スクワッドに最上位の役がないときは、診断を頼まず、診断の文を除いた今の手順で、頼み直すか人間を呼ぶ。squad-handoff はワークスペースで共有するので、今の指示のリーダーも新しいこのファイルを読むためである。診断は、ラベル `重要` の有無によらず頼む。マークのないタスクで診断を頼んでも、マークは付けない。

診断が変えるのは、次の 2 つの場面だけである。

| 場面 | 診断を使わないとき | 診断を使うとき |
| --- | --- | --- |
| 同じ誤りの N が 1 | 原因を書いて頼み直す | 頼み直さず、最上位の役に診断を頼む。返った直し方で、返った直す役に 1 回だけ頼む |
| 同じ部品の N が 3 | 修正を頼まず、`同じ部品の確認:` の行を置いて人間を呼ぶ | 修正を頼まず、最上位の役に診断を頼む。返った直し方で 1 回だけ頼む |

診断のあとの再発は、最上位の役に頼み直さず、人間を呼ぶ。同じ誤りの N が 2 になるか、同じ部品の N が 4 になるときで、どちらも下の決まりで人間を呼ぶ。診断で設計を直したあとの再発は、「診断の検証待ち」で人間へ回す。診断の依頼の書き方と、返事の受け方は [leader-principal.md](leader-principal.md) の「診断」にある。

診断は、1 つのタスクで 2 回までにする。3 回目の診断が要るときは、違う失敗でも、設計か要件に原因があるとみて、診断を頼まず人間を呼んで止まる。最上位の役が「人間の判断が要る」と返したときも、直しを頼まずに人間を呼ぶ。

#### 用語

| 語 | 意味 |
| --- | --- |
| 部品 | 指摘の場所の、ファイルと関数、またはファイルと規則のまとまり。名前は `<ファイル>:<関数か規則の名前>` と書く。指摘に関数や規則の名前がなければ、ファイルの名前だけにする |
| 差し戻し | レビューの ❌、コンフリクト、CI の失敗で、修正の役へ戻すこと |
| 同じ誤り | 修正の役へ回した ❌ の指摘と、部品も、抜けていた入力や場合も同じ指摘が、その直しのあとにまた来ること。コンフリクトは、解消のあとにまた `CONFLICTING` になること。CI の失敗は、直しのあとに同じジョブが同じ原因で失敗すること。テストは、直しのあとに同じテストが（CI でも手元でも）また失敗すること。役の実行は、同じ原因でまた失敗すること |
| 同じ部品の指摘 | 前に修正の役へ回した ❌ の指摘と部品が同じで、抜けていた入力や場合が違う指摘 |
| 種類単位の依頼 | 1 件の入力の直しではなく、その部品が受ける入力の種類を列挙して扱いを決め、まとめて直す依頼 |
| 診断 | 最上位の役に、続いた失敗の根本の原因と、直し方と、直す役を返してもらう見直し |
| 検証待ち | 診断を頼んだ失敗で、直ったと確認していないもの |

同じ誤りを先に当てはめる。同じ誤りに当たった指摘は、同じ部品の回数に数えない。コンフリクトと CI の失敗には部品がないので、同じ誤りの決まりだけで扱う。指摘は ❌ だけを数える。⚠️ は修正の役へ回さないので数えない。

#### 同じ誤りが続くとき

同じ誤りの再発の扱いは、N で決める。部品が違う差し戻しが 2 回続いても、この節では止めない。人間を呼ぶコメントには、原因と、再発を防ぐ手当てを添える。手当ては、手順の直し方か、指示の改善のタスクの起票である。人間が同じ失敗の原因を自分で調べ直さずに、手当てを選べるようにするためである。

同じ誤りの回数は、修正の役へ回したあとに同じ誤りが来た数で数える。最初の指摘やコンフリクトは数えない。同じ誤りの修正を頼む依頼には、次の行を置く。

```text
同じ誤り: <対象> <N> 回目
```

対象は、`<部品の名前>`・`コンフリクト`・`CI の <ジョブの名前>`・`テスト <テストの名前>`・`実行 <原因の名前>` のどれかで、決め方は次の「同じ誤りの対象」にある。N は、そのタスクのリーダーのコメントにある、同じ対象の `同じ誤り:` の行のうち、その対象の最後の数え直し（「数え方の行」）より後のものの数に 1 を足したものにする。

| N | 診断を使わないとき | 診断を使うとき |
| --- | --- | --- |
| 1 | 原因を書いて頼み直す | 頼まず、診断を頼む。診断の依頼には `同じ誤り:` の行を置かず、診断のあとの修正の依頼に `同じ誤り: <対象> 1 回目` の行を置く |
| 2 以上 | 依頼を出さず、原因と再発を防ぐ手当てを添えて人間を呼ぶ | 診断のあとの再発なので、診断を頼まず、原因と手当てと、診断と試した直し方とその結果を添えて人間を呼ぶ |

N が 1 のとき、診断を使わないとき（最上位の役がない、診断に入る条件を満たさない）は、診断を頼まず、原因を書いて頼み直す。診断がすでに 2 回あるとき、検証待ちの失敗が再発したときは、診断を頼まず人間を呼ぶ。診断を使うときの `squad-usage-wait pick` の結果は、`leader-principal.md` の「pick の結果」に従う。使用率が上限に近いときも、診断を飛ばして頼み直さない（終了 3 は待ち、終了 4 と 1 は人間を呼ぶ）。コンフリクトは診断に回さず、`同じ誤り: コンフリクト 1 回目` と `修正の依頼: 2 回目` の行を置いて頼み直し、2 回目の再発で人間を呼ぶ。実行の失敗の頼み直しは修正の依頼ではないので、`同じ誤り:` の行だけを置く。

同じ誤りを頼み直す依頼には、その指摘の `同じ部品:` の行を置かない。同じ部品の回数に数えないためである。

#### 同じ誤りの対象

同じ誤りの対象は、次の 5 つにする。見分けるのは失敗の中身で、どこから届いたかは問わない。

| 対象 | 同じ誤りとみなすもの |
| --- | --- |
| `<部品の名前>` | レビューの ❌ で、部品も、抜けていた入力や場合も同じ指摘。指摘を返した役は問わない |
| `コンフリクト` | 解消のあとに、また `CONFLICTING` になった |
| `CI の <ジョブの名前>` | テストでない CI のジョブ（lint、ビルドなど）が、同じ原因でまた失敗した |
| `テスト <テストの名前>` | 同じテストがまた失敗した。CI でも、役が手元で流したテストでもよい |
| `実行 <原因の名前>` | 役の実行が、同じ原因でまた失敗した。実行した役は問わない |

CI のジョブの中のテストが失敗したときは、`CI の` ではなく `テスト` の対象にする。修正の役が手元で同じテストの失敗を返したときも、同じ対象として数える。CI と手元で別の対象にすると、同じ失敗を 1 回目として数え直し、診断が遅れるためである。

名前は、前の行にあれば一字も変えずに写す。新しい名前を作る前に、タスクにある `同じ誤り:` の行を読み、同じものがないか確認する。行は `回目` で終わるので、名前に空白があっても末尾から N を読める。

エージェントでは直せない止まり方は、同じ誤りとして数えず、今の手順で扱う。診断しても、直す役がいないためである。

- 使用上限での停止と、使用率が上限に近いときの待ち
- 認証の失敗（ランタイム、`gh`、Multica の CLI）と、`squad-preflight` が通らないとき
- ワークスペースの設定や権限が要るもの。PR の紐付けの連携、スキルの更新の権限、関所に止められたときなど
- 未記入で止まるとき（squad-handoff の「記入が足りずに止まるとき」）

これらが 2 回続いたときは、原因と手当てを添えて人間を呼ぶ。

#### 数え方の行

回数は、手戻りの見直しの `同じ誤り:` と `同じ部品:` の行と同じく、タスクのリーダーのコメントの決まった行から数える。行は、その実行の最後のコメントに入れ、行だけのコメントを足さない。診断が足す行は次の 4 種類である。

| 行 | 置くとき | 数え方 |
| --- | --- | --- |
| `診断の依頼: <N> 回目。失敗: <同じ誤り \| 同じ部品> <対象>` | 最上位の役へ診断を頼むコメント | 最後の `診断の数え直し:` より後のこの行の N の最大に 1 を足す。1 つの依頼に同じ N で並べた行は 1 回と数える |
| `数え直し: 同じ誤り <対象>。理由: 直った（<確認したこと>）` | 直ったと確認した実行の最後のコメント | その対象の同じ誤りを 0 に戻し、その対象の検証待ちを解く |
| `数え直し: 同じ誤りのすべて。理由: <人間の再開 \| 設計の承認し直し>` | 人間の判断で再開するコメントと、直した設計の承認を受けたコメント | すべての対象の同じ誤りを 0 に戻す。人間の再開では検証待ちもすべて解き、設計の承認し直しでは解かない |
| `診断の数え直し: 人間の再開` | 人間の判断で再開するコメント。上の人間の再開の行と並べる | 診断の回数を 0 に戻す |

数え直したあとの最初の失敗は、最初の指摘と同じく数えず、原因を書いて修正を頼む。直った失敗が後でまた出ても、すぐに診断へ回さないためである。同じ部品は数え直さない。人間の再開は、`同じ部品の確認:` の続ける返事で扱う。

`数え直し: 同じ誤りのすべて。理由: 設計の承認し直し` と同じコメントにある `同じ誤り:` の行は、行の上下によらず、数え直しより後の行として数える。その行は、承認し直した設計のもとで頼んだ修正の記録だからである。

直ったと確認できるのは、同じテストが通った、次のレビューに同じ指摘がない、同じ実行が成功した、同じジョブが通った、のどれかを読んだときである。読んだ CI の行やレビューの結果を `確認したこと` に短く書く。行を置き忘れると、回数は戻らず、診断が早く来る側に倒れる。

人間の再開は、人間を呼んで止まったタスクに人間が返事をし、リーダーが `in_progress` に戻すときである。設計の承認し直しは、設計の役が直した設計を人間が承認したときである。設計の役がない構成で、人間が直した設計を承認し直したときも含む。この承認は、人間を呼んで止まったタスクへの返事でも、人間の再開と数えない（[leader-principal.md](leader-principal.md) の「設計の役がない構成の設計の直し」）。設計と PR の見直し、診断、最終レビューのどれで直した設計でも、同じに扱う。

診断の依頼のコメントには、`見直しの種類: 診断` と `診断の依頼:` の行を置き、`修正の依頼:`・`同じ誤り:`・`同じ部品:` の行は置かない。診断のあとの修正の依頼には、次の行を置く。

| 診断の結果 | 置く行 |
| --- | --- |
| 同じ誤り、`直す役: 修正の役` | `修正の依頼: <N> 回目` と `同じ誤り: <対象> 1 回目` |
| 同じ部品、`直す役: 修正の役` | `修正の依頼: <N> 回目` と `同じ部品: <部品の名前> 3 回目` |
| `直す役: 設計の役`、`診断: 人間の判断が要る` | 修正の依頼を出さないので、行を置かない |

こう置くと、診断のあとの再発は、同じ誤りで N が 2、同じ部品で N が 4 になり、どちらも人間を呼ぶ決まりに当たる。

#### 診断の検証待ち

診断を頼んだ失敗は、直ったと確認するまで検証待ちとする。回数とは別に持ち、設計の承認し直しでは解かない。診断で設計を直したあとに同じ誤りが戻ると、回数は 0 に戻っていて、もう一度診断に回ってしまうためである。

検証待ちの失敗は、`診断の依頼:` の行の `失敗:` に書いたものである。同じ誤りは、その行より後に同じ対象の `数え直し: 同じ誤り <対象>。理由: 直った` か、人間の再開の数え直しがあれば解ける。同じ部品は、人間の再開の数え直しだけで解ける。

検証待ちの失敗がまた起きたら、回数によらず人間を呼んで止まる。同じ部品の診断のあとは、その部品の同じ誤りも再発とみる。人間への報告に、診断のあとの再発であることを書く。

#### 同じ部品に指摘が続くとき

修正の依頼のコメントに、回す ❌ の指摘の部品ごとに、1 回目から次の行を置く。返事のあとに `squad-review-next decide` が書いた自動の依頼にはこの行がない。その数え方は、次の「自動の依頼の数え方」に従う。

```text
同じ部品: <部品の名前> <N> 回目
```

N は、そのタスクのリーダーのコメントにある、同じ部品の名前の `同じ部品:` の行の数に 1 を足したものにする。部品の名前は、前の行にあれば、その名前を一字も変えずに写す。数えるのはタスクの中の行のすべてで、連続した依頼だけではない。あいだに別の部品の依頼が挟まっても数え直さない。

N が 2 になる部品があれば、同じ依頼に次の行を置き、種類単位で頼む。人間は呼ばない。

```text
頼む範囲: 種類単位（<部品の名前>）
```

依頼の文では、修正の役に次を頼む。修正の役の指示は変えない。

- その部品が受ける入力の種類と規則を表にし、種類ごとの扱いを決める
- 表の行ごとにテストを置く。テストは表を入力とする形（表に沿ったテスト）にし、表の場所を結果に書く
- 指摘された 2 件の入力も、表の行に含める

直したあとの再確認は、`squad-review-next request` で頼む。最新の修正の依頼の `頼む範囲:` の行から、`request` が次の行を書く。リーダーはこの行も依頼の文も自分では書かない。行は頼むすべての役に届き、どの役も自分の観点で部品の周辺を列挙する。

```text
列挙を頼む部品: <部品の名前>
```

N が 3 になる部品があれば、修正を頼まない。診断を使うときは、診断を頼む。診断の依頼の書き方は [leader-principal.md](leader-principal.md) の「診断」にあり、`同じ部品の確認:` の行は置かない。次のどれかに当たるときと、N が 4 以上になる部品があるときは、診断を頼まず、人間を呼んで `in_review` にする。

- 診断がすでに 2 回ある
- 最上位の役がない
- 「診断に入る条件」を満たさない

人間を呼ぶコメントには次の行を置き、あわせて次を書く。

```text
同じ部品の確認: <部品の名前> <N> 回目の前
```

- その部品への指摘。それぞれの結果へのリンクと 1 行の要点
- 2 回目に種類単位で頼んだ範囲と、修正の役が書いた表の場所
- 診断のあとの再発なら、診断と、試した直し方と、その結果
- 決めてほしいこと。続けて 1 回頼むか、設計を見直すか、やめるか。推す案と理由を添える

診断のあとは、`直す役: 修正の役` なら、`同じ部品: <部品の名前> 3 回目` の行で 1 回だけ頼む。この診断の結果が、3 回目の修正を出してよい条件になる。人間を呼んだ N は、同じ N の `同じ部品の確認:` の行のあとに、人間の続ける返事があるときに、`同じ部品: <部品の名前> <N> 回目` の行で 1 回だけ頼む。その部品に次の指摘が来たら、N + 1 の確認の行を置いて、また止まる。

同じ部品の担当は、数えて診断を頼むのがリーダー、診断するのが最上位の役、直すのが診断で決まった役である。止まる先は人間で、最上位の役がないときも人間を呼ぶ。`squad-review-next decide` は、タスクに `修正の依頼:` の行があれば 2 回目からリーダーを起こすので、同じ部品の 2 回目以降は、いつもこの手順で判断する。

部品が違う指摘が続くときは、指摘ごとの依頼にする。どの部品も `同じ部品: <部品の名前> 1 回目` の行にし、`頼む範囲:` は置かない。

#### 自動の依頼の数え方

`squad-review-next decide` が書いた修正の依頼を、自動の依頼と呼ぶ。自動の依頼には `直す指摘:` の行があり、この行は `decide` だけが書く。`decide` は、タスクに `修正の依頼:` の行がないときだけ自動の依頼を書き、2 回目からはリーダーを起こす。自動の依頼には `同じ部品:` と `同じ誤り:` の行がないので、次のとおり読んで数える。自動の依頼に行を書き足すことはしない。

1. 回した指摘は、自動の依頼の `前の回:` が指す回の返事の組のうち、`直す指摘:` に名前のある役の ❌ の指摘である。返事の組は、`decide` と同じ決まり（`docs/review-next-step.md` の「返事の組」）で、`前の回:` をたどって集める。コミットが合わず頼み直した回は、頼み直した役の結果が元の回の結果に代わり、合っていた役の結果は元の回から入る。`前の回:` の回だけを読むと、元の回の ❌ が数から抜ける
2. 1 つめの自動の依頼では、1 の指摘の部品を、それぞれ `同じ部品: <部品の名前> 1 回目` の行があるものとして数える。部品の名前は、リーダーがこのとき指摘から付け、次の依頼の行に書く。以後はその名前を写す
3. 同じ誤りは、新しい ❌ の指摘を、1 の指摘と比べて判断する。1 の指摘と同じ部品と入力なら、同じ誤りの再発として、頼み直す依頼に `同じ誤り: <部品の名前> <N> 回目` の行を置き、`同じ部品:` の行は置かない。N は、通常の行の数に 1 を足す。自動の依頼に `同じ誤り:` の行はなく、自動の依頼から初めて再発したときは、同じ誤りの行がまだ 1 つもないので 1 回目と記録する

自動の依頼の回した指摘を読めないときは、その依頼を、前の依頼がないものとして扱わない。修正の依頼を書かず、人間を呼んで `in_review` にする。読めないまま数えると、1 回目の部品や同じ誤りが数から抜け、止めるべき往復を頼んでしまうためである。読めないのは、次のどれかに当たるときである。

1. 返事の組を作れない。`前の回:` の行が読めない、たどりきれない、たどった回を認められないときで、`decide` が組を作れないときと同じである
2. `直す指摘:` に名前のある役の ❌ の結果が、組にない
3. 組の結果が、`docs/review-next-step.md` の「結果が読めるとき」に当たらない

呼ぶコメントには次の行を置き、読めなかった理由と自動の依頼へのリンクを書く。決めてほしいことは、回した指摘を示して続けるか、設計を見直すか、やめるかである。

```text
自動の依頼の確認: <自動の依頼のコメントの ID>
```

出してよい条件は、同じ ID の `自動の依頼の確認:` の行のあとに、人間の続ける返事があることである。人間が指摘を示したら、それをその自動の依頼の回した指摘として数える。示さずに続けると返されたら、その依頼の部品は数えずに頼む。

流し直しの前の `decide` は、2 回目からの ❌ でも自動の依頼を書いた。流し直しの前から動いているタスクには、自動の依頼が 2 つ以上あることがある。自動の依頼を時刻の順に読み、どれにもない行を次のとおり戻す。

1. 1 つめの自動の依頼は、上の 1 と 2 のとおりに数える
2. 2 つめからは、回した指摘ごとに、それより前の自動の依頼で回した指摘と比べる。同じ誤りを先に当てはめる
3. 部品と入力が同じ指摘があれば、`同じ誤り: <部品の名前> <N> 回目` の行があるものとして数える。この指摘は同じ部品の数に入れない
4. 部品が同じで入力が違えば、`同じ部品: <部品の名前> <N> 回目` の行があるものとして数える
5. 同じ部品がなければ、`同じ部品: <部品の名前> 1 回目` の行があるものとして数える

3 と 4 の N は、それまでに戻した同じ対象の行の数に 1 を足したものにする。戻した行は、リーダーのコメントの行と合わせて、次の依頼の N を数える。流し直しの前にリーダーが書いた、行のない依頼は数えず、次の依頼から数え始める。

#### 修正の依頼の前に確認する順

修正の役へ回す前に、次の 1〜3 をすべて確認する。人間を呼ぶのは、各項目が人間を呼ぶと書いた条件に当たるときだけである。当たらない項目は、人間を呼ぶ理由にしない。1〜3 のどれにも当たらなければ、4 と 5 を順に見る。

診断を使わないときは、診断を頼まない。診断を使わないときとは、最上位の役がないとき、診断に入る条件を満たさないとき、診断の上限に達したときである。診断を使うときは、1 と 2 に診断を足す。診断を頼むものは、人間を呼ぶ確認に数えない。

1. 同じ誤り: 検証待ちの再発か N が 2 以上なら、人間を呼ぶ。N が 1 なら、診断がすでに 2 回あるときは人間を呼ぶ。診断を使わないときのうち、最上位の役がないときと診断に入る条件を満たさないときは、原因を書いて頼み直す。診断を使うときは診断を頼み、`pick` の結果は `leader-principal.md` の「pick の結果」に従う
2. 同じ部品: N が 3 で診断のまだない部品は、診断を頼む。診断を使わないとき（上の 3 つの場合）と、N が 4 以上で人間が通していないときは、`同じ部品の確認:` の行を置いて人間を呼ぶ
3. 続行の確認に当たり、その N の確認を人間が通していない: `修正の続行の確認:` の行を置く。マークのあるタスクと、リーダーの `手戻りの見直し:` の行があるマークのないタスクが対象で、止まる N は `leader-principal.md` の「修正の依頼の数え方」の表で決める
4. ラベルがなく、修正の依頼の N が 4: `leader-principal.md` の「手戻りの見直し」の判定で、設計と PR の見直しを頼むかを決める。頼むときも、ラベルは付けない。診断を頼む回で、診断のあとの修正が 4 回目になるときは、診断を別に頼まず、`leader-principal.md` の「手戻りの見直しと重なるとき」に従う
5. 1〜4 のどれにも当たらない: 頼む。N が 2 の部品は種類単位にし、N が 3 の部品は診断のあとの 1 回にする

1〜3 で人間を呼ぶものが 1 つでもあれば、当たったものを 1 つのコメントにまとめて書く。1 回の実行で書くコメントは 1 つという決まりを保つためである。同じ回の診断の対象も、そのコメントに書き、診断は頼まない。人間を呼ぶものがなく、診断の対象があれば、診断をまとめて 1 回頼み、修正は頼まない。診断の依頼は、`修正の依頼:` の行を置かず、修正の依頼に数えない。

たとえば、修正の依頼の 1 回目と 2 回目が同じ部品なら、3 回目の ❌ では診断を頼み、`修正の依頼:` の行を置かない。診断のあとの直しは `修正の依頼: 3 回目` で、手戻りの合図には当たらない。その次の修正は 4 回目になるので、マークのないタスクでは手戻りの見直しの判定に当たる。

2 と 3 が同じ実行で当たったときは、1 つのコメントで両方を聞く。人間の続ける返事は、そのコメントに置いたすべての確認の行を通す。人間を 2 回続けて呼ばないためである。1 に当たったときの人間の返事は、手当てを選ぶか、続けて 1 回頼むかである。

人間を呼ぶ確認を、手戻りの見直しの 4 より先に見る。診断を使わないとき、マークのないタスクで 4 回目と同じ部品の 3 回目が重なったら、1〜3 の人間を呼ぶ確認に当たるので、先に人間を呼ぶ。人間が続けると返した次の実行で、4 の判定に当たる。

診断を使うとき、マークのないタスクで、同じ部品の 3 回目（診断を頼む回）と、診断のあとの修正が 4 回目になることが重なったら、1 と 2 の人間を呼ぶものと 3 に当たらない限り、診断を別に頼まない。4 の判定で見直しを頼むと決まったときは、設計と PR の見直しの依頼に診断の中身を足し、`leader-principal.md` の「手戻りの見直しと重なるとき」に従う。見直しを頼まないと決まったときは、診断を今の手順で頼む。人間を呼ぶものに当たるときは、先に人間を呼ぶ。

1〜3 の N は、自動の依頼を「自動の依頼の数え方」のとおり読んで数える。自動の依頼の回した指摘を読めず、その確認を人間が通していないときも、頼まずに人間を呼び、`自動の依頼の確認:` の行を同じコメントに置く。流し直しの前の依頼から戻した数では、同じ誤りの N が 3 以上になることもあるので、1 は 2 以上で当たる。

返事のあとに `squad-review-next decide` が「修正の依頼が 2 回目から」の理由でリーダーを起こしたときも、この順で確認する。

指示の実物は勝手に変えない。指示の改善は、提案のタスクにする。
