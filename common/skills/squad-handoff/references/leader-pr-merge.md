# リーダーの手順: マージの前の確認と人間を呼ぶとき

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、人間へ回すとき、マージの前の確認とコンフリクトを扱うとき、マージ待ちの定期確認で起きたときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## マージの前の確認

待ちの規則と、ほかのコメントのどちらで起きても、待っているタスクでは次の順を最初から流す。

1. PR の紐付けの確認。紐付いているか紐付いていないなら進め、ほかの判定は上の表のとおり止まる
2. 最上位の役があれば、`leader-principal-final.md` の最終レビューの head の照合。短い道を除くすべてのタスクで行い、変わっていれば今の head で最終レビューを頼み直す。短い道は、レビューと E2E の組の `確認するコミット:` と照合し、最終レビューは頼まない。PR の head は、1 の `pr:` の正規形で読む。紐付けの有無で変えない
3. コンフリクトの状態の確認。`leader-pr-ci.md` の「紐付いていない PR のその場の確認」の 3 を兼ねる
4. CI。見張りがあれば、紐付けの有無によらず `ci` と `ci-wait` を流し、`ci-now` は流さない。見張りがなければ、紐付いていないときだけ `ci-now` を流す。チェックなしは待たない
5. マージへ進めるときだけ、規則の入れ直し。`conflicts` を流し、紐付いていないなら続けて `unlinked` を流す。CI の待ちの間は登録しない。`decide` が流すので、手で流すのは `decide` を通らずにマージへ回すとき（コンフリクトの解消の引き継ぎのあとなど）だけにする
6. マージの依頼。同じコメントに `マージの依頼: <head の完全な SHA>` の行を置き、「人間を呼ぶコメントに添える行」を続ける。同じ head で 1 回だけ依頼する

手で書くマージの依頼は、字下げ、引用、HTML、入れ子の項目を使わずに書く。これらがあると、スクリプトは読めない記録として止まり、次へ進まない。

### decide が流すマージの前の確認

レビューと E2E、最終レビューの返事がそろったあと、決まりで決まるときは、`report` を流した役の `squad-review-next decide` が、上の順の紐付け・head の照合・コンフリクト・CI を流し、マージの依頼まで書く。紐付いていないときは `--leader` 付きで `unlinked` を登録し、`見張り:` の行を依頼に写す。CI を待つときは、マージを頼まず、`マージの前の CI の待ち: <ci-wait の行>` と `前の回: <回のコメントの ID>` を持つコメントを書いて終わる。リーダーが起きるのは、`decide` が `次の依頼を決められません:` で止まったときだけである。その理由が `紐付け:`、CI、`コンフリクト:` の行なら、上の順をリーダーが最初から流し直して扱う。

`squad-pr-watch conflicts` と `unlinked` は、`--leader <ID>` で起こす宛先を渡せる。省くと、今のとおり、呼んだ実行のリーダーを宛先にする。`decide` はリーダーの ID を渡して流すので、リーダーが手で流すときは省いてよい。

## コンフリクトの状態の確認

人間のマージへ回す直前に、`squad-pr-watch conflicts-check <タスク>` を流して PR の今の状態を読む。コマンドの時間切れは 120 秒以上にする。レビュー・E2E・CI を経て、または解消の引き継ぎを受けて、マージへ回すたびに流す。

出力の `コンフリクト:` の行に従って、次の動きを決める。行が出ないときや読めないときは「未確認」として扱う。

1. `CONFLICTING` なら、人間を呼ばない。`leader-dispatch.md` で有効な修正の役を選び、行を添えて `main` とのコンフリクトの解消を頼み、タスクを `in_progress` に戻す。解消の引き継ぎを受けたら、もう一度この確認から流す
2. 解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。`leader-repeat.md` の、同じ差し戻しが 2 回続いたら人間を呼ぶ決まりに合わせる
3. `MERGEABLE` なら、行を保存して、上の順の CI の確認へ進む。マージを依頼するときに行をそのまま添える
4. 「未確認」なら、行を保存して CI の確認へ進む。マージを依頼するときに行をそのまま添える。「なし」とは書かない

## 規則の入れ直し

手でマージへ回すときは、最上位の役の有無によらず、まず `squad-pr-watch conflicts <タスク>` を流す。この出力は規則の登録の結果で、PR の状態ではないので、人間への報告に使わない。状態は上の確認の行だけで書く。CI の見張り役がいれば `ci` も流す。紐付いていないときは、それに加えて `squad-pr-watch unlinked <タスク> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、あるときだけ渡す。紐付いているときは `unlinked` を流さない。待ちの途中で紐付けば、間隔を空けた確認は止まり、既存の CI とコンフリクトの見張りが引き継ぐ。

`unlinked` が `紐付け: 作業先と違う` か `紐付け: 不正な pr_url` の行を出したら、上の判定のとおり人間に metadata の修正を頼んで止まり、マージを頼まない。

`unlinked` の `見張り:` の行は、マージを頼むコメントにそのまま写す。0 以外で終わったときは、見張りなしでマージを頼み、登録できなかったことと、ホストでセットアップを流し直してほしいことを書く。

有効な修正の役へ解消を頼むのは、`leader-pr-ci.md` の「起きたときの確認」の条件がそろったときだけにする。それ以外は作業中の対象を変えない。解消で設計や挙動が変わらなければ、レビューを回し直さず、上の「マージの前の確認」を流してから人間へ戻す。ただしすべてのタスクで、最上位の役の最終レビューのあとに解消の push で head が変わったときは、人間へ戻す前に、`leader-principal-pick.md` の「最上位の役を呼ぶところ」の最終レビューを今の head でもう一度頼む。

## マージ待ちの定期確認で起きたとき

CI の見張り役がなく、規則でリーダー自身が起きたときは、規則の指示の `squad-pr-watch unlinked-check <タスク> <リーダーの ID>` を流す。`紐付け: 食い違い` は次の節、`紐付け: 作業先と違う` と `紐付け: 不正な pr_url` は上の判定と「人間を呼ぶコメントに添える行」のとおり扱う。

`CI <SHA>: 失敗あり` で始まり保留でない行は `leader-pr-ci.md` の「CI」の失敗で起きたときと同じに扱い、`コンフリクト: CONFLICTING` で `知らせ: 書いた` なら「起きたときの確認」に進む。それ以外は、行を `/note` の記録にして終える。

0 以外で終わったときも、取得できた行を先にこの手順で扱ってから、規則の記録のスレッドに失敗を書く。CI の失敗の行が出たのに、通信エラーの報告だけで終えない。次の回は知らせ済みになり、修正への回しを取りこぼすためである。

## 人間を呼ぶコメントに添える行

ほかの理由で人間を呼ぶコメントを書く前に、`squad-pr-watch link-check <タスク>` を流す。食い違いと未確認は、[leader-pr-link.md](leader-pr-link.md) の「PR の紐付けの確認」へ移って判定に従う。

紐付けの依頼だけのために人間を呼ばない。紐付いていないときは、ほかの理由で人間を呼ぶコメントに次の 1 行を添える。

| 呼ぶ理由 | 添える行 |
| --- | --- |
| マージを頼む | 紐付いていないので、マージのあとにタスクを `done` にしてほしい（または先に紐付けてほしい）。PR: `<正規形>` |
| 設計の承認、判断の依頼など、それ以外 | PR がタスクに紐付いていません。タスクの画面の PR の欄で `<正規形>` を紐付けてください。 |

`<正規形>` には、`link-check` の行の `pr:` の値を写す。metadata の `pr_url` を読み直して写さない。

作業先と違うときと不正なときは、紐付けの依頼ではなく、タスクの画面で metadata の `pr_url` か `repository` を直すよう頼む。判定の行だけを写し、不正な元の値はタスクの画面で見てもらう。タスクを `in_review` にし、返事のあとに判定し直す。

マージを頼むときは `見張り:` の行も続ける。どちらの行にも、役が PR の URL の下に残した `紐付けの失敗:` の段落を、空行の前までそのまま添える。警告に連携の案内があれば、ワークスペースの設定のコードの画面で、作業先のリポジトリが GitHub 連携につながっていることを確認する依頼も添える。連携がないと、タスクの画面からも紐付けられないためである。

更新前の引き継ぎの先頭にある紐付けの依頼と警告の文も、この段落と同じに扱う。失敗や先頭の依頼だけで止まらず、`link-check` の判定で決める。
