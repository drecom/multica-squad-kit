# リーダーの手順: マージの前の確認と人間を呼ぶとき

このファイルはリーダーだけが読む。「場面と手順」から、人間へ回すとき、マージの前の確認とコンフリクトを扱うとき、マージ待ちの定期確認で起きたときに、その実行の中で読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## マージの前の確認

待っているタスクでは、経路によらず次の順を最初から流す。

1. PR の紐付けの確認。紐付いているか紐付いていないなら進め、ほかの判定は上の表のとおり止まる
2. PR の head の照合。最上位の役の有無によらず、必ず通る。行は下の表で選び、PR の head は、1 の `pr:` の正規形で読む。紐付けの有無で変えない
3. コンフリクトの状態の確認。`leader-pr-ci.md` の「紐付いていない PR のその場の確認」の 3 を兼ねる
4. CI。見張りがあれば、紐付けの有無によらず `ci` と `ci-wait` を流し、`ci-now` は流さない。見張りがなければ、紐付いていないときだけ `ci-now` を流す。チェックなしは待たない
5. マージへ進めるときだけ、規則の入れ直し。`conflicts` を流し、紐付いていないなら続けて `unlinked` を流す。CI の待ちの間は登録しない。`decide` が流すので、手で流すのは `decide` を通らずにマージへ回すとき（コンフリクトの解消の引き継ぎのあとなど）だけにする
6. マージの依頼。同じコメントに `マージの依頼: <head の完全な SHA>` の行を置き、「手で書くマージの依頼の行」と「人間を呼ぶコメントに添える行」を続ける。同じ head で 1 回だけ依頼する

### head の照合の表

人間へ回す前の head の照合は、この表を正本にする。道は、リーダーのコメントの最も新しい `道:` の行で読む。経路（`decide` か手動）と、head が変わった理由（修正の push かコンフリクトの解消の push）は、行も行き先も変えない。

行は上から読み、最初に当たった行を使う。どの軸の値の組み合わせも、ちょうど 1 行に当たる。

| 行 | 道 | 重要のマーク | レビューと E2E の役 | 最上位の役 | 照合先 | 一致 | 一致しない・照合先を読めない |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 短い | ある | 問わない | 問わない | 照合しない | マージを頼まず、`leader-request.md` の「通常の道へ戻す」のとおり `道: 通常` を書いて設計を頼む。設計の承認のあとは、4 か 5 の行で扱う | 同じ |
| 2 | 短い | ない | ない | 問わない | 照合しない | 短い道にしない。`道: 通常` を書き、4 か 5 の行で扱う | 同じ |
| 3 | 短い | ない | ある | 問わない | 組の `確認するコミット:` | マージの前の確認の 3 へ進む | 今の head で、前の組と同じ役にレビューと E2E を頼み直す。最終レビューは頼まない |
| 4 | 通常 | 問わない | 問わない | ある | 最終レビューの `確認したコミット:` | マージの前の確認の 3 へ進む | 今の head で最終レビューをもう一度頼み、その結果を受けてから人間へ回す。見る範囲は、前の最終レビューからの差分にする |
| 5 | 通常 | 問わない | 問わない | ない | 照合しない | マージの前の確認の 3 へ進む | 当たらない |

表の読み方:

1. 一致は `decide` と同じ読み方にする。組の `確認するコミット:` は完全な SHA が大文字小文字を問わず一致、最終レビューの `確認したコミット:` はすべての値が head の先頭に当たるときに一致
2. 照合先を読めないときは、一致しない側に倒す。今の head を読めないときは、どの行でもマージを頼まず、出力を添えて人間を呼ぶ。`decide` は失敗で終わる
3. `decide` は、一致しないときマージの依頼を書かずにリーダーを起こし、「一致しない」の列に従わせる。手で流すときは自分で照合する
4. 頼み直した回の返事がそろったら、マージの前の確認を 1 から流し直す

手で書くマージの依頼は、字下げ、引用、HTML、入れ子の項目を使わない。あると、スクリプトは読めない記録として止まる。

### 手で書くマージの依頼の行

手で書くマージの依頼にも、`decide` の依頼と同じ 4 行を同じ形と順で、コンフリクトと CI の行のあと、各役の結論の行の前に置く。

```text
読む深さ: <深さ>（<重要のタスク | 重要でない>。<注意あり | 注意なし | 注意を読めない>、残した指摘 <N> 件、前からある不具合 <M> 件）
マージの前に人間がすること: <なし | 注意の 1 行 | PR の注意の <N> 行>
直さずに残した指摘: <N> 件
前からある不具合: <M> 件（<役> <n> 件、…）
```

1. 読む深さ: 重要のラベルがあれば `PR の概要と設計文書まで`。なければ、注意が「なし」でない・読めない、または残した指摘か前からある不具合が 1 件以上のとき `このコメントと PR の注意`、どれもなければ `このコメントだけ`
2. 人間がすること: PR の本文の注意を写す。2 行以上なら1 行ずつ `-` と空白で始め、10 行までにし、残りは `- 続きは PR の本文の注意を読む（残り <M> 行）` で示す
3. 残した指摘: ⚠️ を返した役の要約の `指摘の一覧:` の項目を 1 件ずつ `- <役> <番号>. <重大度>: <場所>。影響: <影響>` で続ける。⚠️ で `指摘の一覧:` がない要約は 1 件と数え、`- <役>: 指摘の行を読めない。結果を読む` と書く
4. 前からある不具合: 各役の要約のマークの行の件数を足す。0 件なら括弧を付けない

数えるのは、マージへ回す各役の最新の結果と最終レビューの結果で、その回で頼んだ役の、`確認したコミット:` がマージを頼む head と合う要約だけを使う。写す行は字下げ・引用・HTML・コードの囲みを外し、メンションのリンクは文字だけにする。

### decide が流すマージの前の確認

レビューと E2E、最終レビューの返事がそろったあと、決まりで決まるときは、`report` を流した役の `squad-review-next decide` が、上の順の紐付け・head の照合・コンフリクト・CI を流し、マージの依頼まで書く。紐付いていなければ `--leader` 付きで `unlinked` を登録し、`見張り:` を依頼に写す。連携なしのときは、依頼に添える行を上の 1 行と `見張り:` の行だけにし、`unlinked` の登録に失敗したら、何も書かずに `次の依頼を決められません:` で止まる。CI を待つときは、マージを頼まず、`マージの前の CI の待ち: <ci-wait の行>` と `前の回: <回のコメントの ID>` を持つコメントを書いて終わる。リーダーが起きるのは `decide` が `次の依頼を決められません:` で止まったときだけで、理由が `紐付け:`、CI、`コンフリクト:` の行なら、上の順を最初から流し直す。

`squad-pr-watch conflicts` と `unlinked` は、`--leader <ID>` で起こす宛先を渡せる。省くと呼んだ実行のリーダーが宛先になる。`decide` は ID を渡して流すので、手で流すときは省いてよい。

## コンフリクトの状態の確認

マージへ回す直前に、`squad-pr-watch conflicts-check <タスク>` を流して PR の今の状態を読む。コマンドの時間切れは 120 秒以上にする。マージへ回すたびに流す。

出力の `コンフリクト:` の行で次の動きを決める。行が出ない・読めないときは「未確認」。

1. `CONFLICTING` なら、人間を呼ばない。`leader-dispatch.md` で有効な修正の役を選び、行を添えて `main` とのコンフリクトの解消を頼み、タスクを `in_progress` に戻す。解消の引き継ぎを受けたら、もう一度この確認から流す
2. 解消を頼んだあと 2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。`leader-repeat.md` の、同じ差し戻しが 2 回続いたら人間を呼ぶ決まりに合わせる
3. `MERGEABLE` なら、行を保存して CI の確認へ進む。マージの依頼に行をそのまま添える
4. 「未確認」なら、3 と同じに進む。「なし」とは書かない

## 規則の入れ直し

手でマージへ回すときは、最上位の役の有無によらず、まず `squad-pr-watch conflicts <タスク>` を流す。この出力は登録の結果で PR の状態ではないので、報告に使わない。状態は上の確認の行だけで書く。CI の見張り役がいれば `ci` も流す。紐付いていないときは、それに加えて `squad-pr-watch unlinked <タスク> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、あるときだけ渡す。紐付いているときは `unlinked` を流さない。待ちの途中で紐付けば、間隔を空けた確認は止まり、既存の見張りが引き継ぐ。

`unlinked` が `紐付け: 作業先と違う` か `紐付け: 不正な pr_url` の行を出したら、上の判定のとおり人間に metadata の修正を頼んで止まり、マージを頼まない。

`unlinked` の `見張り:` の行は、マージを頼むコメントにそのまま写す。0 以外で終わったときは、見張りなしでマージを頼み、登録できなかったことと、ホストでセットアップを流し直してほしいことを書く。

ただし、`link-check` の行の末尾に `連携: なし` が付くときは、`unlinked` が 0 以外で終わってもマージを頼まない。見張りがないと、マージのあとに誰も `done` にしないためである。ホストでセットアップを流し直してほしいことだけを、人間に頼む。この依頼にも、紐付けと `done` を頼む行、`紐付けの失敗:` の段落、連携の案内は入れない。人間の返事を受けたら、`decide` を流し直して、見張りを登録できてからマージを頼む。

有効な修正の役へ解消を頼むのは、`leader-pr-ci.md` の「起きたときの確認」の条件がそろったときだけにする。それ以外は作業中の対象を変えない。解消の push で head が変わったときも、行き先は上の表のとおりにし、人間へ戻す前に「マージの前の確認」を流す。解消で設計や挙動が変わらないときに 4 役と E2E を回し直さないのは、表の 4 と 5 の行だけである。

## マージ待ちの定期確認で起きたとき

CI の見張り役がなく、規則でリーダー自身が起きたときは、規則の指示の `squad-pr-watch unlinked-check <タスク> <リーダーの ID>` を流す。`紐付け: 食い違い` は次の節、`紐付け: 作業先と違う` と `紐付け: 不正な pr_url` は上の判定と「人間を呼ぶコメントに添える行」のとおり扱う。

`CI <SHA>: 失敗あり` で始まり保留でない行は `leader-pr-ci.md` の「CI」の失敗と同じに扱い、`コンフリクト: CONFLICTING` で `知らせ: 書いた` なら「起きたときの確認」に進む。それ以外は、行を `/note` の記録にして終える。

0 以外で終わったときも、取得できた行を先にこの手順で扱ってから、規則の記録のスレッドに失敗を書く。CI の失敗の行が出たのに通信エラーの報告だけで終えない。次の回は知らせ済みになり、修正への回しを取りこぼす。

## 人間を呼ぶコメントに添える行

ほかの理由で人間を呼ぶ前に、`squad-pr-watch link-check <タスク>` を流す。食い違いと未確認は、[leader-pr-link.md](leader-pr-link.md) の「PR の紐付けの確認」へ移って判定に従う。

紐付けの依頼だけのために人間を呼ばない。紐付いていないときは、ほかの理由で人間を呼ぶコメントに次の 1 行を添える。行の末尾に `連携: なし` が付くときは、この表の「連携なし」の行に従う。

| 呼ぶ理由 | 添える行 |
| --- | --- |
| マージを頼む | 紐付いていないので、マージのあとにタスクを `done` にしてほしい（または先に紐付けてほしい）。PR: `<正規形>` |
| 設計の承認、判断の依頼など、それ以外 | PR がタスクに紐付いていません。タスクの画面の PR の欄で `<正規形>` を紐付けてください。 |
| 連携なしで、マージを頼む | 連携なしのリポジトリなので、マージのあとは見張りがマージを確認し、タスクを `done` にする。PR: `<正規形>` |
| 連携なしで、設計の承認、判断の依頼など、それ以外 | 添えない |

`<正規形>` は `link-check` の `pr:` を写し、metadata の `pr_url` を読み直さない。

作業先と違うときと不正なときは、タスクの画面で metadata の `pr_url` か `repository` を直すよう頼む。判定の行だけを写す。タスクを `in_review` にし、返事のあとに判定し直す。

マージを頼むときは `見張り:` の行も続ける。どちらの行にも、役が PR の URL の下に残した `紐付けの失敗:` の段落を、空行の前までそのまま添える。警告に連携の案内があれば、ワークスペースの設定のコードの画面で、作業先のリポジトリが GitHub 連携につながっていることを確認する依頼も添える。

連携なしのときは、マージを頼むコメントに上の 1 行と `見張り:` の行だけを添える。`紐付けの失敗:` の段落、連携の案内、紐付けと `done` を頼む行は添えない。役の `連携なし:` の段落も写さない。マージ以外のコメントには、どれも添えない。

更新前の引き継ぎの先頭にある紐付けの依頼と警告の文も同じに扱い、`link-check` の判定で決める。
