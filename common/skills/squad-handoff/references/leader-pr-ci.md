# リーダーの手順: PR の知らせ・CI・その場の確認

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、紐付いていない PR の知らせで起きたとき、PR のあるタスクで起きたとき、CI の結果を扱うときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

役の有無で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## 紐付いていない PR のその場の確認

PR を受け取ったとき、返事を待つ回を始める前、返事がそろったとき、マージへ回す前に、CI とコンフリクトを確認する。CI の見張り役の有無によらず、どちらも確認する。

1. CI の見張り役があれば、「CI」の手順で `squad-pr-watch ci` を流す
2. `squad-pr-watch ci-now <タスク> <リーダーの ID> <きっかけのコメント> [<見張り役の ID>]` を流す。見張り役の ID は、あるときだけ渡す。ただしマージへ回す前で見張り役があるときは、`ci-now` を流さず、「CI の待ち」の `ci-wait` で確認する
3. `squad-pr-watch conflicts-check <タスク>` を流す。コマンドの時間切れは 120 秒以上にし、`CONFLICTING` なら `leader-pr-merge.md` の「コンフリクトの状態の確認」の 1 と 2 に従う

マージへ回す前の `conflicts-check` は `leader-pr-merge.md` の「コンフリクトの状態の確認」と兼ね、同じ区切りで重ねて流さない。マージの前の確認の順は `leader-pr-merge.md` の「マージの前の確認」のとおりにする。

`ci-now` の行は、次のように読む。

| 行 | 動き |
| --- | --- |
| `CI <SHA>: 失敗あり` で始まり、保留でない | 「CI」の失敗で起きたときと同じに扱う |
| `CI <SHA>: 失敗あり（… の作業中なので保留）` | 役の引き継ぎや揃った知らせを受けるまで保留し、`ci-held` で拾う |
| `CI <SHA>: 失敗あり（… の区切りの途中なので保留）` | 区切りの続きの引き継ぎを受けるまで保留し、`ci-held` で拾う。`leader-run-cut.md` の「区切りの途中」に従う |
| `CI <SHA>: 失敗は知らせ済み` | 前の知らせのとおり扱い、新たに頼まない |
| `紐付け:` で始まる | `leader-pr-link.md` の「PR の紐付けの確認」の作業先と違うか不正な `pr_url` の行のとおり、人間を呼んで止まる。以降の確認や依頼へ進めない |
| 失敗なし、チェックなし、マージ済みか閉じている | 先へ進める |

`ci-now` が 0 以外で終わったときは CI を未確認とし、人間を呼ぶコメントに添える。見つけた失敗とコンフリクトは、紐付いているときと同じ条件で扱う。返事を待つ回の途中なら、全部がそろうまで直しを頼まない。修正へ回す条件、保留、同じワークフローの失敗と 2 回続いたコンフリクトの上限は変えない。

## 紐付いていない PR を受け取ったときの知らせ

`link-check` の行の末尾が `連携: なし` なら、この知らせは書かない。連携なしにした知らせは、切り替えた `squad-pr-link` が 1 回だけ投稿する。`link-check` は知らせを投稿も削除もしない。

PR を受け取った実行で `link-check` が「紐付いていない」を出したら、「紐付いていない PR のその場の確認」のあと、次の依頼より前に、漏れを 1 つの投稿で知らせる。次の依頼は、レビューと E2E の依頼（`squad-review-next request`）、次のフェーズの依頼、修正の役への依頼などである。知らせをマージの依頼まで先送りしない。

知らせは、きっかけのコメントへの返信で書き、次の 3 つを入れる。1 行目は、原則 5 のとおり起きたことと次の一手にする。

1. 警告: 引き継ぎの `紐付けの失敗:` の段落を、空行の前までそのまま写す。更新前の引き継ぎの先頭にある警告も同じに扱う。段落がなければ、`link-check` の行を写す
2. 連携の前提: 紐付けには、作業先のリポジトリがワークスペースの GitHub 連携につながっていることが要る。ワークスペースの設定のコードの画面で確認してほしいと書く。連携がないと、タスクの画面からも紐付けられないためである
3. 再発: タスクのコメントに前の漏れの記録（前の `紐付けの失敗:` の段落か、紐付けの依頼）があれば、再発と認める。原因と、再発を防ぐ手当てを、推す案として書く。手当ては、連携の確認や指示の改善のタスクの提案などである。前の漏れがなければ、この項は書かない

知らせでは、人間をメンションせず、タスクを `in_review` にせず、`squad-pr-link` を呼び直さない。紐付けのためだけに止まらず、次の依頼へ進める。指示・環境・連携の設定は、自分で変えない。原因は、確認した事実と推測を分けて書く（原則 3）。連携の前提は手順で決まる事実だが、この PR で連携がつながっていないことは確認していないためである。

知らせは、同じ PR につき 1 回にする。返事を待つ回の前やそろったときの区切りでは、繰り返さない。同じ実行で、設計の承認などほかの理由で人間を呼ぶコメントを書くときは、別に投稿せず、そのコメントに 3 つを入れる。マージを頼むコメントには、知らせを書いたあとも、`leader-pr-merge.md` の「人間を呼ぶコメントに添える行」を今のとおり添える。

## 起きたときの確認

PR のあるタスクで起きたときは、きっかけを問わず、返事を待つ回の途中でない限り、次の順に確認する。コンフリクトの知らせで起きたときだけに限らない。返事を待つ回の途中かどうかは、`leader-review-request.md` の手順で読んだ待ちの状態で決める。待ちの途中なら、作業中の対象を変えず、そちらの手順に従う。

1. 動いている実行を、`leader-run-status.md` の「起きたときの確認」の手順で確認する。その PR に触れる実行が動いているか、45 分を超えて動いている実行があるかを読む
2. `squad-pr-watch conflicts-check <タスク>` を流して、コンフリクトの状態を読む。出力の読み方は `leader-pr-merge.md` の「コンフリクトの状態の確認」と同じにする。コマンドの時間切れは 120 秒以上にする
3. 次の条件がすべてそろったときだけ、解消を修正の役へ頼む。頼み方は、`leader-pr-merge.md` の「コンフリクトの状態の確認」の 1 に従う
   - コンフリクトの行が `CONFLICTING` である
   - タスクが `in_review` で、前回はマージ待ちだった
   - 返事を待つ回の途中でない
   - その PR に触れる実行が動いていない

条件が 1 つでもそろわないときは、作業中の PR に修正の役を重ねて呼ばない。同じブランチに 2 つの実行が push するためである。作業中の対象を変えず、タスクの状態も変えない。

解消を頼んだあとの確認で、2 回続けて `CONFLICTING` なら、3 回目は頼まず、行を添えて人間を呼ぶ。この決まりは、起きたときの確認でも変えない。

## CI

紐付いている PR では、CI の見張りがあるときだけ確認する。見張りの ID は、リーダーの指示の「このスクワッドの役」にある。紐付いていない PR は、見張り役がなくても「紐付いていない PR のその場の確認」を流す。

metadata に `pr_url` があり、CI の見張り役がいれば、PR を受け取ったときと人間のマージへ回すときに `squad-pr-watch ci <タスク> <見張りの ID> <きっかけのコメント>` を流す。紐付いていないときも登録し、人間が待ちの途中で紐付けたあとに引き継ぐ。見張りが止まっていれば、次に人間を呼ぶコメントに添える。CI は下の待ちの規則で待つ。

CI の失敗で起きたとき、返事を待つ回の途中なら全部が揃うまで直しを頼まない。同じワークフローの失敗を一度修正へ回し、その push の後も失敗したなら、再び修正へ回さず人間へ返す。それ以外は有効な修正の役へ頼み、必要なら `in_progress` に戻す。修正の役の選び方は `leader-dispatch.md` に従う。

CI の見張り役がいるか、PR が紐付いていないときは、役の引き継ぎや揃った知らせを受けたら、次へ回す前に `squad-pr-watch ci-held <タスク> <きっかけのコメント>` で保留した失敗を拾う。見張り役がない場合も省かない。出たチェック名は同じ CI の失敗として扱う。取得が失敗したら人間へ返す。ただし CI を待つタスクでの再開と、見張り役がある構成で最終レビューが通ってマージの前の確認へ進むときは、`ci-held` ではなく下の `ci-wait` を使う。CI が読めないだけで人間を呼ばず、待ちの分岐に従う。

### CI の待ち

マージの前には、`ci` に続けて `squad-pr-watch ci-wait <タスク> <リーダーの ID> <きっかけのコメント> [<起きた規則>]` を流す。待ちの規則で起きた実行では、その規則の ID を最後の引数に渡す。出力の行で次を決める。

| 行 | 次の動き |
| --- | --- |
| 成功、チェックなし | 行を添え、マージの依頼へ進む |
| 実行中、未確認 | マージを頼まず、人間も呼ばない。状態は `in_progress` のまま、行と待っていることを書いて終わる |
| 実行中・未確認で待つ上限の 2 時間を超えた | 行を添えてマージを依頼し、CI の結果を見て判断してもらう。「通った」と書かない |
| 失敗あり | 今の CI の失敗の決まりで修正へ回す。人間は呼ばない |
| PR がマージ済みか閉じている、タスクが終わっている、マージを依頼済み、終わった規則で起きた | 依頼も状態変更もせず、行を書いて終わる |
| 終了コード 1 | 標準エラーの要約を添えて人間を呼び、`squad-task-post` で `in_review` にする |

紐付いていない PR でも待てる。待ちの規則は紐付いた PR の CI にしか反応しないので、紐付いていないときは 30 分ごとにリーダーが起き、読み直す。

`ci-wait` は、読んだ `pr_url` を GitHub の前に検証し、規則を作ったあとの読み直しにも同じ正規形を使う。作業先と違うか不正なら、GitHub を読まず、待ちの規則と metadata を消し、理由を標準エラーに書いて終了コード 1 で終える。`pr_url` がないときは、未確認として待つ。

待ちは head ごとに 2 時間まで、残り時間と 30 分の短い方でリーダーを 1 回起こす。CI が読めなくても待つ。登録後の再読で完了を拾い、終了時には規則と metadata を消す。詳細は設計文書 `docs/principal-review.md` の「マージの前に CI を待つ」を参照する。

待ちの規則で起きたときは、先に最新の `マージの前の CI の待ち:` のコメントを探す。そのコメントに `前の回: <回のコメントの ID>` があれば、上の `ci-wait` を直接流さず、`squad-review-next decide <タスク> <その回のコメントの ID> <起きた規則の ID>` を流す。`decide` が `ci-wait` を規則の ID 付きで流し、成功ならマージの依頼を 1 回だけ書き、規則を消す。出力の `次の依頼:` の行を最後の返答にする。`前の回:` がなければ、`ci-wait` を流す。

待っているタスク（metadata に `ci_wait_head` がある）で、CI の待ち以外の理由で修正、最終レビューの頼み直し、人間の呼び出しへ進むときは、先に `squad-pr-watch ci-wait-clear <タスク>` を流す。読み取りや削除に失敗すれば、終了コード 1 として人間へ返す。
