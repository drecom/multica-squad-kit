# リーダーの手順: 最上位の役を呼ぶところと選び方

このファイルはリーダーの手順で、リーダーだけが読む。リーダーの指示の「場面と手順」から、最上位の役を呼ぶとき、返事を待つとき、最上位の役を選ぶときに読む。前の実行で読んだ記憶で済ませず、その実行の中で読む。

最上位の役がないときは、このファイルを使わない。最上位の役の有無と系統で分かれる手順は、場合分けで書く。どの場合かは、リーダーの指示の「このスクワッドの役」で決まる。

## 最上位の役を呼ぶところ

呼ぶところは次の 6 つにする。重要のマークのあるタスクの設計の見直しに加え、2 の設計と PR の見直しは手戻りの合図でも頼む。最終レビューと、要件の見直しと、設計の役がない構成の設計の見直しと、診断は重要のマークの有無によらず行う。

1. 設計の見直し: 重要のマークのあるタスクで、設計の役が設計を出したあと
2. 設計と PR の見直し: 重要のマークがあるのに、PR に設計の見直し・設計と PR の見直しのどちらの結果もないとき。最終レビューの結果は数えない。判断の時機に新しく重要のマークを付けたときも、人間が承認のあとにラベルを付けたときも、同じに扱う。重要のマークのないタスクの手戻りの見直しも、`leader-principal.md` の「頼むかの判定」で頼むと決まったときは、この種類で頼む
3. 最終レビュー: すべてのタスクで、レビューと E2E の結果がそろい、どれにも ❌ がなくなったあと、人間のマージへ回す前。文書だけのタスクと、人間が重要のマークを外したタスクも含む
4. 要件の見直し: 要件を決める役がなく、最上位の役があるタスクで、人間の用意した要件を次の有効な役へ回す前
5. 設計の役がない構成の設計の見直し: 設計の役がなく、最上位の役があるタスクで、人間の用意した設計を実装の役へ回す前
6. 診断: 同じ誤りが 1 回目の再発になったとき、または同じ部品への指摘が続いて [leader-repeat.md](leader-repeat.md) の「同じ部品に指摘が続くとき」が診断を頼むと決めたとき。重要のマークの有無によらない

依頼のコメントには、`見直しの種類: <設計の見直し | 設計と PR の見直し | 最終レビュー | 要件の見直し | 診断>` の行を置く。設計の役がない構成の設計の見直しも、種類は `設計の見直し` にする。返事の待ち方は次の「返事の待ち方」に従う。

## 返事の待ち方

最上位の役への依頼も、ほかのレビューと同じく `squad-review-wait` で返事を待つ。最上位の役は 1 体だけを選ぶ。依頼の前に `squad-review-wait watch <タスク> <きっかけのコメント> <頼む役の ID>` を流し（security-reviewer も頼むときは、最上位の役の ID に続けて security-reviewer の ID を渡す）、依頼のコメントに `返事を待つ役:` の行と `確認するコミット: <完全な SHA>` の行を置き、その行だけでメンションする。`返事がそろいました` で起きたら、`squad-review-wait proceed <タスク> <きっかけのコメント>` を流し、`返事の待ち: 次に進む` を返した実行だけが進む。コマンドの時間切れは 90 秒以上にする。返ってきた `確認したコミット:` が依頼と合わなければ、同じコミットで頼み直す。2 回続けて合わなければ人間を呼ぶ。ただし、要件の見直しで見直さずに返った ❌（`確認したコミット: なし`）は除き、頼み直さず人間を呼ぶ。要件の見直しの `確認するコミット:` は、`leader-principal-design.md` の「要件の見直し」のとおり、コミットではなく本文の値にする。

設計の見直しと設計と PR の見直しの回は、設計の役がない構成の設計の見直しの回も含め、`report` を流した役の `squad-review-next decide` が次の依頼を書かず、`次の依頼を決められません: 設計の見直しの回はリーダーが扱う` でリーダーを起こす。✅ でも指摘があっても同じである。`leader-principal-design.md` の「設計の見直し」`leader-principal-design.md` の「設計の役がない構成の設計の見直し」`leader-principal-final.md` の「設計と PR の見直し」のとおり、結果の `設計への指摘:` の行と指摘を読んで扱う。要件の見直しの回も、PR を確認する前に `次の依頼を決められません: 要件の見直しの回はリーダーが扱う` でリーダーを起こす。`leader-principal-design.md` の「要件の見直し」のとおり、結果のマークと本文の値を読んで扱う。診断の回も、PR を確認する前に `次の依頼を決められません: 診断の回はリーダーが扱う` でリーダーを起こす。`leader-principal-diagnose.md` の「診断」のとおり、結果の `診断:` と `直す役:` の行を読んで扱う。最終レビューの回は、`decide` が次の依頼まで決める。結果に `設計への指摘: あり` があるときと、決められないときだけ、リーダーが起きるので、理由の行を読んで今の手順で扱う。`設計への指摘: あり` で起きたとき、設計の役がない構成では `leader-principal-design.md` の「設計の役がない構成の設計の直し」に従う。

## 最上位の役の選び方

最上位の役を呼ぶたびに、`squad-usage-wait pick <タスク> principal [<系統>]` でその場の使用率を読み直して選ぶ。30 分より古い値は使わない。上限に近くても、人間を呼ぶ代わりに、空いている系統へ回すか、空きが戻る時刻まで待つ。コマンドの時間切れは 120 秒以上にする。

### 実装した系統の決め方

最終レビューでは、`multica issue runs <タスク> --output json` を読み、指示の「このスクワッドの役」の ID と照合する。実装と修正の役のうち、状態が `completed` の実行だけを系統ごとに数え、多い方を実装した系統にする。`failed` と取り消しは数えない。同数か一覧を読めなければ、系統を決めない。

実装と修正の実行がなければ、設計の役のモデルで決める。モデルの確認方法は「このスクワッドの役」にある。`claude-` で始まれば Claude、それ以外は Codex とする。設計の役やモデルを確認できなければ、系統を決めない。成功で終えたが変更を積まなかった実行も数えるので、実際に多く書いた系統と逆になることがある。

### pick の結果

最終レビューで実装した系統を決められれば、`<系統>` に `Claude` か `Codex` を渡し、違う系統を優先する。設計の見直しと要件の見直しと診断と、実装した系統を決めないときは、系統を渡さない。両系統があるかと、読めないときの代わりの決まりは、スクリプトが名簿で決める。

| 終了コード | 意味 | すること |
| --- | --- | --- |
| 0 | 役を選んだ。`役:` と `振り分け:` の行を出す | `役:` のマークに対応する最上位の役へ、`振り分け:` の行を添えて頼む。最上位の役の一覧は、リーダーの指示の「このスクワッドの役」にある |
| 3 | 待つ。起こしを置き、`使用率の待ち:` の行を出す | 依頼を書かず、その行をタスクのコメントに写して終える。起こしで起きたら、同じ `pick` から頼み直す。人間は呼ばない |
| 4 | 待ち始めから通算 24 時間を超える | `使用率の待ち:` の行を写し、「待つ」「進める」「利用枠を足した」の 3 つの答えを示して人間を呼び、`in_review` にする。人間が答えたときの手順は [leader-dispatch.md](leader-dispatch.md) の「使用率の待ちで人間が答えたとき」にある |
| 1 | 使い方や読み取りの誤り | 標準エラーの要約を添えて人間を呼び、`in_review` にする |

最上位の役を飛ばさない。使用率の取得に失敗したとき、古い値を使わない。実装した系統を渡しても、優先する系統だけが上限の近くなら、スクリプトが理由を添えて同じ系統へ回す。
