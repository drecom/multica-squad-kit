# Multica での引き継ぎ

同じタスクのコメントで成果物を受け渡す。次の担当と人間が、コメントと状態から続きを始められるようにする。担当する範囲と権限は、依頼と自分の役の指示に従う。このスキルだけを根拠に、担当外の作業を始めない。

## このプロジェクトの値を使う

プロジェクトごとに違う値は、自分のエージェントの指示の末尾にある「このプロジェクトの値」を読む。このスキルの中に値を保存したり、名前から推測したりしない。

| 使う場面 | 写す値 |
| --- | --- |
| GitHub に書き込む | プロジェクトのリポジトリの一覧と、タスクまたは依頼の PR の作業先。紐付けだけの書き込みは、紐付け専用の一覧も照合する |
| タスクを作る | プロジェクトの ID、スクワッドの ID |
| リーダーに引き継ぐ | スクワッドのメンションのリンク |
| 人間に確認する | 呼ぶ人間のメンションのリンク |
| 見張りにリーダーを指定する | リーダーのエージェントの名前、または ID。呼ぶスクリプトの引数に合わせる |

メンションは、値にある完成したリンクをそのまま写す。名前だけでは通知できず、リンクの種類や ID を変えると別の相手を呼ぶことがある。必要な値がないときは、推測して作成・書き込み・メンションをせず、不足している値を報告する。

## 実行の始めの確認

GitHub に書き込む、または `squad-` の見張りを呼ぶ実行は、ほかの処理より先に `squad-preflight` を流す。タスクのある実行は `squad-preflight <タスク>`、タスクのない実行は引数なしにする。名前だけで呼び、絶対パスでは呼ばない。どちらもしない実行では、この確認は流さない。

終了コード 0 のときだけ、以降の処理へ進む。0 以外は、見つからないときの 127 も含め、次のとおりにして止まる。

1. GitHub の読み取り・書き込みも、見張りの呼び出しも行わない
2. 「人間を呼んで止まるとき」に従い、呼ぶ人間をメンションし、タスクを `in_review` にする
3. 報告に、使えなかったものと直し方を書く。`squad-preflight` の出力は、そのまま添える

ガードは、エージェントの実行で、許可していないリポジトリへの `gh` の書き込みと `git push` を止める仕組みである。`squad-preflight` が見つからないときは、「ガードのディレクトリが PATH にありません。動いているタスクがないときに、同じプロジェクトでセットアップを流し直してください」と報告する。確認が通らなくても、報告と状態の変更には `multica` の CLI を使える。

タスクのない見張りは、オートパイロットの指示にある報告のしかたで、呼ぶ人間に知らせる。

## 書き込んでよいリポジトリ

GitHub の issue、PR、コメント、push などの書き込みは、「このプロジェクトの値」にあるリポジトリの一覧に含まれるものだけにする。次の紐付け専用の例外を除き、同じワークスペースに紐付いている別のリポジトリも読むだけにする。`multica repo list` に出ることや、人間の GitHub の認証で書けることは、このプロジェクトから書き込む許可にならない。

「紐付け専用のリポジトリ」が指示にある場合は、その一覧の既存の GitHub の issue にも紐付けコメントと Assignees の同期を書ける。具体的な同期の方法はプロジェクトのスキルに従う。この例外から GitHub の issue の作成、コード変更、PR の作成・コメント・レビュー、push を許可しない。一覧がなければ、紐付けにもこの例外を使わない。

一覧の中でも、タスクの作業は次の「タスクの作業先を決める」の一つのリポジトリで行う。PR へのコメントとレビュー結果は、その PR があるリポジトリへ書く。

ホストの `gh` と `git push` のガードに止められたら、ガードを避ける呼び方や設定の変更をせず、呼ぶ人間に知らせる。

## タスクの作業先を決める

リポジトリで作業するタスクは、1 タスクにつき 1 リポジトリ・1 PR にする。作業先はタスクの metadata の `repository` に `OWNER/REPO` で残す。役ごとに本文から推測し直さない。紐付け専用の一覧は、タスクの作業先や定期処理の対象には使わない。

| 担当する仕事 | 確認することと作業 |
| --- | --- |
| リーダー | 最初に振り分ける前に `repository` を決めて書く。既存の値も人間が書いた値も、プロジェクトの一覧にあることを確認してから振り分ける。要件を決める担当がなく最上位の役がある構成で、要望が二つ以上のリポジトリにまたがる親は、親に `repository` を書かず、sub-issue の値で確認する。 |
| 要件を決める | 作業先を確認し、複数のリポジトリにまたがる要望は、要件を合意するときにリポジトリごとの sub-issue に分ける。 |
| 設計・実装・修正 | `repository` のリポジトリを checkout し、そのリポジトリの `AGENTS.md` と作業別のルールを読む。そこで PR を作るか既存の PR に積む。 |
| レビュー・QA | 依頼の PR の URL からリポジトリを決め、プロジェクトの一覧と照合して checkout する。metadata の読み取りは不要。 |
| 定期の確認や見張り | オートパイロットや依頼で明示された一つのリポジトリを一覧と照合して使う。リポジトリを使わない見張りのために checkout しない。 |

リーダーは、一覧が一つならそれを `repository` に書く。二つ以上なら、プロジェクトの説明にある各リポジトリの役割とタスクの本文から決める。どの役割にも当たらない、二つ以上に当たる、役割が未記入などで決められなければ、人間を呼んで止まる。選択の先頭を代わりに使わない。ただし、要件を決める担当がなく最上位の役がある構成の、二つ以上に当たる親は、止まらずに分割へ進む。親に `repository` を書かず、`leader-flow.md` の「複数のリポジトリにまたがる要望」に従う。

metadata は `multica issue metadata set <タスク> --key repository --value <OWNER/REPO> --type string` で書く。既存の値が一覧になければ、勝手に別の値へ直さず人間を呼んで止まる。外したリポジトリを作業先に持つタスクも同じ扱いにする。

要件・設計・実装・修正の担当は、`repository` がないか一覧にないとき、作業を始めずリーダーに返す。既存の PR がその値と違うリポジトリにあれば、作業を進めず不一致を返す。レビュー・QA は PR の URL を使うが、一覧にない PR は同じくリーダーへ返す。PR 以外の検証は、依頼が明示した対象を一覧と照合し、作業先が分からなければ推測せず返す。

複数リポジトリの sub-issue には、それぞれの作業先を `repository` に書く。先に入れるリポジトリから順にステージを付け、リポジトリの間で合わせる I/F は親のタスクの要件として合意する。各 sub-issue は一つのリポジトリのタスクとして、設計からの流れを通す。要件を決める担当を置かないときは、リーダーがこの分割を行う。最上位の役があれば、要件の見直しの前に、担当なしの `backlog` で分ける。

## タスクの状態と担当

| 状態 | 意味 | 変える人 |
| --- | --- | --- |
| `in_progress` | エージェントの番 | リーダー。振り分けを始めるときと、人間の返事を受けて再開するとき |
| `in_review` | 人間の判断・承認・マージを待つ | 人間を呼んで止まるエージェント |
| `done` | PR がマージされた | Multica の GitHub 連携 |
| `cancelled` | やめた | 人間 |

状態は `multica issue status` で変える。マージと取り下げは人間が決めるので、エージェントの実行が終わっただけでは `done` にしない。結果を書けば完了する運用のタスクについて、自分の役の指示に例外が明記されていれば、その指示に従う。

タスクの担当は「このプロジェクトの値」のスクワッドにし、作業する役は担当にせずメンションで呼ぶ。担当がスクワッドなら、人間の返事はリーダーへ届く。オートパイロットが `create_issue` で作る運用のタスクは、オートパイロットが決めた担当のままにする。

## 呼ぶ人間

通常は、「このプロジェクトの値」にある呼ぶ人間のメンションのリンクを写す。そのスクワッドやエージェントの持ち主が、ランタイムと利用枠を提供し、作業を見て判断するため。起票しただけの人であることがあるので、タスクの作成者を代わりに呼ばない。

持ち主とオーナーは別の語である。オーナーは、ワークスペースの権限の名前（オーナー・管理者・メンバー）である。持ち主は、スクワッドやエージェントなどを作り、そのランタイムと利用枠を提供する人で、`creator_id` や `owner_id` で読む。呼ぶ相手は持ち主で、オーナーとは限らない。

複数の担当者のタスクを横断する運用では、役の指示に従い、対象のタスクの担当から持ち主をたどる。

- 担当がスクワッドなら、`multica squad get` の `creator_id`
- 担当がエージェントなら、`multica agent get` の `owner_id`
- 担当がメンバーなら、そのメンバー
- 担当がなければ親のタスクの担当。それでも分からなければ、メンションせず結果に書く

名前は `multica workspace member list` の `name`、人間のリンクの ID は `user_id` を使う。メンバーの登録行の ID と取り違えない。

## 本文の書き方

PR の本文とコメント、タスクの本文とコメントには、次の決まりを共通で使う。意味のまとまりで区切り、読み手が要点を追えるようにする。

- 1 文は短くする。目安は 60 字以内、読点は 2 つまでとし、長いときは 2 文に分ける
- 段落は意味のまとまり 1 つにつき 1 つにする。1 段落は 2〜4 文、200 字ほどまでとし、段落の間は空行にする
- 段落の中では改行しない。1 文ごとの改行もしない
- 箇条書きの 1 項目は 1〜2 文にする。3 文以上になるときは、項目を分けるか、段落の文章にする
- 箇条書きは、同じ種類のものが 3 つ以上並ぶときに使う。順序や優先があるときは番号付きにする
- 2 つ以下の項目や、理由でつながる話は文章で書く。箇条書きの入れ子は 1 段までにする
- 表は、いくつかの項目を 2 つ以上の同じ観点で比べるときに使う。セルは語句か 1 文にする
- 見出しのすぐ下に、その節の結論を 1〜2 文で書く。見出しだけを続けない

既存の定型は、形も置き場所も変えない。対象は PR テンプレートの見出し、タスクの metadata の `repository`・`branch`・`pr_url`、PR の結果の先頭の行である。`確認したコミット:`、`見直し:`、`返事を待つ役:` の行と、タスクに記録する実装の一覧の列も同じように扱う。

### 言い回し

役が書く文は、次の 6 つの決まりで言い回しを決める。食い違うときは、上の決まり・コメントと本文の型・固定の行・作業先の書き方の正本を優先する。

- 事実: 依頼・資料・実行の結果にない事実・理由・数値・予定を書かない。分からないことは、分からないと書く
- 足さないもの: 前置き・依頼の言い直し・末尾のまとめ直し・頼まれていない別案・していないことの列挙を書かない
- 確かさ: 確認したこと・予定・推測を、文末で書き分ける。予定や推測を言い切りにしない
- 語: 同じものを同じ語で書く。普段使う漢語と技術の語はそのまま使い、新しい語を作らない
- 文の分け方: 長さの目安に合わせるために、理由や条件のつながりを切らない
- 読み直し: 出す前に 1 回読み直し、上の 5 つを見る

この決まりは、「本文の書き方」の始めに挙げた本文に加え、作業先のリポジトリに書く文書にも使う。AI が読むもの（役の指示・共通スキル・`AGENTS.md`・作業別のルール・記入用のひな形）を書くときと変えるときも同じである。判定に使う語、固定の行、スクリプトが読む行は、言い回しを理由に変えない。

次は、確かさと足さないものの例である。手元の行は、書く人が持つ依頼・資料・実行の結果である。直した後の文は、直す前の文と手元の行にないことを書かない。

```text
手元: 原因は推測で、CI はまだ流し直していない。
直す前: 原因はキャッシュの古さである。CI を流し直せば通る。
直した後: 原因はキャッシュの古さだと見ている。CI を流し直せば通る見込みである。

直す前: 依頼を確認した。依頼はリンクの切れを直すことである。2 件を直した。以上、リンクの切れを 2 件直した。
直した後: リンクの切れを 2 件直した。
```

書き直しと修正では、読める文は直さず、読み手が止まる理由を言える所だけを直す。直したあとは、否定・条件・例外、求める強さ、誰がするか、確かさが前と同じかを見比べる。

## コメントと本文の型

エージェントが書いて人間が読む 4 種の文に、型を 1 つずつ置く。型の本体は、今その種類の決まりがある節に置き、この節は索引と共通の項目名を決める。

長さの目安を超えるときは、まず置き場所の列へ移せる内容がないかを見直す。結果の目安は、表とスクリーンショットを除く文で数える。

| 種類 | 型を置く節 | 長さの目安 | 目安を超える内容の置き場所 |
| --- | --- | --- | --- |
| タスクのコメント | 「引き継ぐとき」 | 1,000 字 | 根拠と出力を PR のコメントか添付ファイルに置き、リンクか名前を書く |
| タスクの本文 | 下の「タスクの本文」 | 3,000 字 | 経緯と根拠をタスクのコメントに置き、本文からリンクする |
| PR の本文 | 「PR の本文の置き場所と順序」 | 3,000 字 | その節の置き場所の表に従う |
| レビューと QA の結果 | 「PR にレビューやテストの結果を書く」 | 表の外の文で 3,000 字 | 長いログと検出の一覧を別の PR のコメントに置き、リンクする |

### 共通の項目名

すべての役は、同じ項目に次の名前を使う。「使わない名前」の列は、役が別の名前として使ってはいけない語である。

| 項目 | 書くこと | 使わない名前 |
| --- | --- | --- |
| 結論 | 1 行目に、何をして次に何を頼むかを書く。項目名は付けない | 要約、まとめ |
| 成果物 | PR のブランチと URL、結果のコメントへのリンク、添付の名前と sha256 | 結果、結果へのリンク、成果 |
| 確認したこと | 流したコマンドと結論を 1 件 1 行で書く | 確認した内容、確認の行、検証結果 |
| 決めてほしいこと | 人間に決めてほしい問い。案ごとの良い点・悪い点と、推す案を添える | 質問、選択肢、推す答え |
| 残っていること | 終わっていない作業と、次の担当に頼むこと | 次の手、残作業 |

PR の本文では、テンプレートの見出しの「確認」をそのまま使う。見出しは固定の行で、確認したことと同じ中身を書く。

タスクのコメントでは、2 行目からの項目を `<項目>:` で始める。中身が 1 行に収まらないときは、項目名の行のあとに箇条書きを続ける。コメントには Markdown の見出しを使わない。短いコメントで見出しが続くと、「本文の書き方」の、見出しだけを続けない決まりに反するためである。

固定の行は、決まった名前と位置のまま置く。型の項目は、固定の行のあとに続ける。固定の行と型の項目が同じ位置を求めるときは、固定の行を優先する。

項目名は、固定の行の名前と重ねない。リーダーの依頼の対象・頼む範囲・返してほしいものには、項目名を付けず文で書く。`頼む範囲:` の行は、見張りのスクリプトが決まった形で読む固定の行だからである。

### タスクの本文

タスクの本文は、`##` の見出しで背景・要件・やらないこと・受け入れ条件の順に書く。

| 見出し | 書くこと |
| --- | --- |
| 背景 | 誰が何に困っているか。根拠のタスクや PR へのリンク |
| 要件 | 満たすべきこと。確認できる形で、番号付きで書く |
| やらないこと | 今回は扱わないと決めたことと、その理由 |
| 受け入れ条件 | 検証する人がテストケースにできる粒度で、番号付きで書く |

要件と受け入れ条件に番号を付けるのは、成功の条件の表が番号で指すためである。不具合のタスクは、再現手順・実際の動作・証拠を背景に、期待する動作を要件に書く。

次は、不具合のタスクの見本である。

```markdown
## 背景

設定の画面で保存を押すと、入力した名前が消える。PR の E2E で見つけた。

- 再現手順: 設定の画面で名前に「山田」と入れ、保存を押す
- 実際の動作: 画面が読み込み直され、名前の欄が空になる
- 証拠: 保存の応答が 500 で、ログに `name is required` が出る

## 要件

1. 保存を押したあとも、入力した名前が残る

## やらないこと

- 設定の画面のほかの欄の見直し。この不具合と関わらないため

## 受け入れ条件

1. 名前を入れて保存し、画面を読み込み直しても名前が残る
```

## PR を作る・実装を積む

コードを PR で渡す仕事は、1 タスクにつき 1 PR にする。最初に PR を作る担当が次を行う。

- ブランチ名とタイトルの種類は、最後に入る変更で決める。実装まで進むものは、設計だけの時点でも機能や修正の種類にする。ドキュメントだけで終わるものにだけドキュメントの種類を使う
- プロジェクトの PR テンプレートがあれば、その見出しに沿って本文を作り、`gh pr create --body-file` で渡す
- PR を作った直後に `squad-pr-link <タスク> <PR の URL>` を呼ぶ。`<タスク>` には実行に渡されたタスクの ID を渡し、呼ぶ前に metadata の `pr_url` を書かない
- 終了コードが 0 なら、metadata の `pr_url` はスクリプトが書いたので、`branch` だけを置く。次の担当と見張りが、対象を取り違えないようにするため
- 0 以外なら、止まらずに `branch` と `pr_url` を自分で置く。コマンドが見つからないとき（終了コード 127）も同じに扱う
- 失敗したときも、紐付けの依頼だけのために人間を呼ばず、引き継ぎの先頭にも依頼を書かない。失敗の事実と標準エラーの警告の文は、成果物の PR の URL のすぐ下に、下の `紐付けの失敗:` の段落で残す。リーダーが、ほかの理由で人間を呼ぶコメントに依頼と警告をまとめるため
- タスクの識別子・作業番号・進行の記録は Multica 側に置き、PR の本文やコミットメッセージへ持ち出さない

```text
紐付けの失敗: <標準エラーの警告の 1 行目>
<標準エラーの警告の 2 行目（あるときだけ）>
```

この段落は空行の前までとし、警告の文をそのまま写す。2 行目は、404 で待ち切れたときの連携の案内で、ないこともある。`紐付け:` は判定の出力なので、段落の頭には使わない。設計の役が自分で人間に承認を頼むコメントでも、この段落を残す。警告の 1 行目が、タスクの画面で紐付ける依頼を含むためである。

スクリプトを呼ぶのは PR を作った直後の 1 回だけにする。`pr_url` があると、紐付けずに飛ばすため、失敗後の紐付けはリーダーの確認が試み直す。それでも紐付かないときだけ、人間がタスクの画面で行う。

実装を push するたびに、`gh pr edit --title --body-file` でタイトルを実装に合わせ、本文を最新の状態の要約に書き直す。前の状態の記述に追記せず、フェーズごとの経緯も書かない。実装の分担と作業番号はタスクの本文・コメントに置き、PR には持ち出さない。PR は draft のまま渡し、通常の ready への切り替えとマージは人間に任せる。役の指示で明示された自動処理は、その許可と条件の範囲だけで行う。

### PR の本文の置き場所と順序

最初の本文も push 後の書き直しも、次の表で情報の置き場所を決める。正本がある情報は本文に写さず、読み手が正本へ進めるようにする。

| 情報 | 置き場所 | PR の本文での扱い |
| --- | --- | --- |
| 設計と、その理由・検討した案 | プロジェクトの設計文書（docs など） | 写さず、該当する節を名前で示す |
| 実装の分担・作業番号 | Multica のタスクの本文・コメント | 書かない |
| 作業の進行や経緯 | Multica のタスクの本文・コメント | 書かない。コミットメッセージは変更した動作と理由を書く |
| 検証のコマンドと結論 | PR の本文の確認 | 最新の push の結果だけを 1 件 1 行で書く |
| 通らなかった検証の出力、検出の一覧、対応表などの長い根拠 | PR のコメント | 写さず、確認の行からリンクする |
| レビューと E2E の結果 | PR のコメント | 書かない |

本文は、プロジェクトの PR テンプレートの見出しの順にする。テンプレートが概要・理由・確認・注意の見出しなら、それぞれ次を書く。

1. 概要: 1 文目で、この PR のマージで何が変わるかを書く
2. 理由: 設計文書に書かない判断（PR の進め方など）を書く。設計の理由と検討した案は、設計文書の節の名前で示す
3. 確認: 検証のコマンドと結論を書き、テンプレートのチェックを付ける。長い根拠は PR のコメントへリンクする
4. 注意: 先頭に、人間がマージの前に判断・作業することを書く。ないときは「なし」と書く

長さの目安は 3,000 字以内とする。超えるときは、表の置き場所に移せる情報がないか見直す。折りたたみで長さを隠さない。

ZIP などで渡すと依頼に決まっている仕事は、その成果物を確定して添付する。リポジトリや PR に積むと読み替えない。

次は、PR の本文の見本である。

```markdown
## 概要

役の指示が、コメントの型を写さずに共通スキルの節を指すようになる。設計は `docs/example.md` の「型の置き場所」にある。

## 理由

設計の理由と検討した案は、設計文書の「検討した案」にある。

## 確認

- [x] 関連テスト `bash tests/run.sh tests/agent-templates-test.sh`: 通った
- [x] `bash scripts/check.sh`: 通った
- [x] `bash scripts/manifest.sh` と生成差分の確認: 差分は MANIFEST だけ

## 注意

なし
```

## PR にレビューやテストの結果を書く

最初の行を `<マーク> <自分のエージェントの名前>: <結論>` にする。同じ GitHub の認証で書いても、担当した役と結果を読み分けられるようにするため。

| マーク | 意味 |
| --- | --- |
| ❌ | 直すまでマージしない。必須の指摘、セキュリティの高・中、設計の性能基準に届かないもの、E2E の失敗 |
| ⚠️ | 指摘はあるがマージは止めない。推奨、セキュリティの低など |
| ✅ | 指摘なし、またはテスト成功 |

結果は、次の順に書く。マークの表と、承認の操作を使わない決まりは、このあとも変えない。

1. マークの行。結論に重大度ごとの件数を `推奨 1 件` の形で添える
2. 固定の行。`確認したコミット:`、`列挙した範囲:` など、役の指示が決める行
3. 前提。環境と確認した範囲を 1 文で書き、QA のほかの役は要るときだけ書く
4. 結果の表。QA だけが書き、列はケース・手順・期待する結果・実際の結果・判定・成功の条件の番号にする
5. 指摘。重大度の順に番号を付けて 1 件 5 行ほどで書き、1 行目を `<重大度>: <場所>` にして影響と直し方を続ける
6. 見た範囲。指摘がないときだけ、`見た範囲:` で始めて 3 行以内で書き、確認した項目を長く並べない
7. 人間が確認する条件。QA だけが、確認する人が人間の成功の条件の番号を並べる
8. スクリーンショット。載せ方は「画像を載せる」に従う

場所の書き方と、影響に足す中身は、役ごとに違う。場所をファイルと行・画面・ケースのどれで示すかは、役の指示に従う。攻撃の経路や数値を足すかも、役の指示に従う。

次は、コードのレビューで指摘が 1 件ある結果の見本である。

```text
⚠️ example-code-reviewer: 推奨 1 件。マージは止めない
確認したコミット: 0123456789abcdef0123456789abcdef01234567

1. 推奨: `lib/answers.sh:42`
   - 影響: 回答ファイルに空の行があると、登録の名前が空になる
   - 直し方: 読む前に空の行を飛ばし、空の行の例をテストに足す
```

本文の観点や細部は自分の役の指示に従う。`gh pr review --approve` と `--request-changes` は使わない。承認は人間が行うため。

## PR の状態を書く

この節の対象は、PR のコンフリクトと CI の結果だけである。レビュー・E2E・テストの結果は、「確認したコミット:」の決まりで扱う。

- PR のコンフリクトや CI の結果を、タスクのコメントや PR のコメントに書くときは、読んだ値と、読んだ時点の head の SHA を添える。SHA は 7 文字以上で書く
- 見張りのスクリプトが値と head の行を出したとき（`squad-pr-watch conflicts-check` の `コンフリクト:` の行、`ci-check` の `CI <SHA>:` の行）は、その行をそのまま写す
- 空の出力、読めなかった結果、`UNKNOWN` のように決まらなかった値は「未確認」と書く。「なし」や「通った」とは書かない

## タスクのコメントを書く

結果は、実行の最後に 1 回だけ書く。途中経過や計画では次の担当を呼ばない。きっかけのコメントがあるときは、その実行で指定された親コメントへ返信し、前の実行の返信先を使い回さない。

本文を UTF-8 のファイルとして実行の作業ディレクトリ内に保存し、`multica issue comment add --content-file` で投稿する。本文を引数や標準入力に直接渡さず、文字列の改行エスケープで改行を作らない。一時ファイルはその作業ディレクトリの `tmp/` に置き、投稿が成功したあとだけ片付ける。コマンドを続けて書くときは、投稿の成功を条件に片付ける。

添付する成果物は `--attachment` で届ける。実行の中だけにあるファイルのパスを、読める成果物のリンクとして渡さない。

タスクのコメントの本文には、URL のパスや、省略の点から始まるパスを書かない。画面名・処理名・関数名で示す。Multica の WAF が本文を権限エラーで拒否することがあるため。正確なパスが必要なら、PR の本文やコメントへ書き、タスクには PR のリンクを置く。GitHub の PR へのリンクは書いてよい。

投稿が `You do not have permission to access this resource.` で拒否されたら、本文のパスやコードの断片を外して再投稿する。それでも届かなければ、詳細を PR の結果か添付ファイルに置き、呼ぶ人間にその場所と投稿できなかったことを知らせる。通らなかった検証の出力は、パスの有無によらず、PR があれば PR のコメントに、なければ添付ファイルに置く。タスクのコメントには、結論とそのリンクまたは添付の名前を書く。

## 画像を載せる

PR には `gh` の `--attach`、タスクには `multica issue comment add --attachment` を使う。画像を別の置き場に置いて URL を書く方法は使わない。

画像と本文のファイルは、作業ディレクトリの `tmp/` に置く。PR のコメントには、次の形で載せる。`gh pr create` と `gh pr edit` にも同じ `--attach` が使える。

```bash
gh pr comment <PR> --body-file tmp/result.md --attach 'tmp/shot.png#<説明>'
```

本文に `![説明](./shot.png)` のような参照を書き、同じ画像を `--attach` で渡すと、参照がアップロード先の URL に置き換わる。`--body-file` の本文の中のパスは、本文のファイルのディレクトリから探し、なければ作業ディレクトリから探す。

本文に参照のない画像は、コメントの末尾に足される。説明は `#` の後ろに書き、なければファイルの名前を使う。

載せたあとは、終了コードだけでなく、`gh pr view <PR> --json comments` でコメントの本文を確認する。手元のパスが残っていないことと、参照がアップロード先の URL に置き換わったことを見る。

PR に載せられなかったときは、同じ画像をタスクのコメントに `multica issue comment add --attachment` で載せ、「人間に操作を頼む前に」に従う。PR に載せるまで作業を止めることはしない。

## 人間に操作を頼む前に

「できない」「口がない」として人間に操作を頼む前に、試した方法とコマンドの出力をコメントに残す。

1. 使う CLI の `--help` で、その操作のコマンドとフラグを探す。画像を PR に載せるなら `gh pr comment --help` の `--attach` を見る
2. 見つかった方法を実際に流す
3. 失敗したら、コマンド、終了コード、標準エラーを含む出力を残す。出力は下のとおりファイルにして添える
4. 人間に頼むコメントには、探したヘルプ、流したコマンド、理由を書く

`--help` に方法がなかったときも、その結果を残す。画像を PR に載せられなかったときは、次の表で理由と頼むことを分ける。

| 理由 | 見分け方の例 | 人間に頼むこと |
| --- | --- | --- |
| 認証 | `gh auth status` が未ログインを示す。401 で返る | ホストの `gh` のログイン |
| 権限 | 403 や 404 で返る。push の権限がない | リポジトリの権限、または PR への手での添付 |
| ガード | 標準エラーが `gh のガード:` で始まる | ガードを避けない。古い `gh` なら `gh` の更新 |
| ファイルの形 | 対応していない形式や大きさのエラー | なし。役が PNG に変えて載せ直す |

試したコマンドと出力は、`tmp/` のテキストのファイルに書き、タスクのコメントに `--attachment` で添える。本文には、試したコマンドの名前、終了コード、理由を書く。出力にはパスが混ざるため、「タスクのコメントを書く」に従って本文から分ける。

ガードに止められたときは、「書き込んでよいリポジトリ」のとおり、ガードを避ける呼び方をしない。本物の `gh` を絶対パスで呼ぶことや、`gh api` でアップロードを組み立てることも、避ける呼び方に入る。

## 引き継ぐとき

成果物を確定し、依頼どおりに共有したあと、最後のコメントの先頭に「このプロジェクトの値」のスクワッドのメンションのリンクを写してリーダーへ返す。リーダー個人のエージェントへのリンクに替えない。スクワッドのリンクが、スクワッドのリーダーとしての実行を起こすため。

コメントは、場面ごとの次の型で書く。目安は 1,000 字以内とし、根拠は正本へのリンクにする。項目の名前は「コメントと本文の型」の「共通の項目名」に従う。

| 場面 | 1 行目 | 続く項目の順 |
| --- | --- | --- |
| 引き継ぐ | スクワッドのメンションと結論 | 成果物、確認したこと、残っていること |
| 人間を呼んで止まる | 呼ぶ人間のメンションと結論 | 決めてほしいこと、成果物、確認したこと、残っていること。ないものは省く |
| リーダーの依頼 | 頼む役のメンションと頼むこと | 固定の行のあとに、対象、頼む範囲、返してほしいものを項目名なしの文で書く |
| レビューと E2E の返事 | `確認したコミット:` の行 | マークの行、`設計への指摘:` などの固定の行、成果物、確認したこと |

1 行目は、メンションを先頭に置き、同じ行で結論を続ける。完了したフェーズや範囲もここに入れる。通らなかった確認の出力は、PR のコメントか添付ファイルに置き、確認したことの行からリンクか名前で示す。

レビューと E2E の返事では、マークの行が結論になる。`/note` で返すと決まっている報告は、1 行目の `/note` の行のあとに、引き継ぐ場面の型で書く。どちらの場面も、行の順は「レビューと E2E の返事を返す」と役の指示の決まりのままである。

次は、人間を呼んで止まる場面の見本である。メンションのリンクの ID は「このプロジェクトの値」から写すので、見本では山かっこのままにする。

```text
[@持ち主](mention://member/<ユーザーの ID>) 設計を draft PR にしました。設計とフェーズの承認を頼みます。
決めてほしいこと: 変更の知らせを、どの PR で CHANGELOG に書くか
- 案 1: この PR で次のバージョンの節に書く。書き忘れないが、同時に進む PR と同じ節でぶつかる
- 案 2: バージョンを上げる PR で書く。ぶつからないが、書き忘れることがある
- 推す案: 案 1
成果物: ブランチ agent/designer/abc123、PR https://github.com/OWNER/REPO/pull/124
確認したこと:
- `bash scripts/check.sh` 通った（終了コード 0）
- `bash tests/run.sh tests/links-test.sh` 通った（終了コード 0）
残っていること: 承認のあと、リーダーへ返す
```

`見直し:` など、役の指示や次の節で決まっている行の形と置き場所は変えない。

依頼や自分の役の指示が `/note` で返すと決めている報告は、その指示に従う。レビューや E2E の返事を待つ登録がある依頼は、次の手順を使う。

## レビューと E2E の返事を返す

依頼の `確認するコミット:` に指定されたコミットを手元に用意し、実際の HEAD が一致することを確認してから検証する。指定がなければ、PR の head、または依頼されたブランチの最新を使う。差分は PR の base からそのコミットまでを見る。前の実行の結果を確認し直さずに返さない。

報告の先頭に `確認したコミット: <SHA>` を置き、実際の HEAD の完全な SHA を書く。用意できなければ `確認したコミット: なし` と理由を書く。依頼がコミットの代わりに ZIP などを指定しているときは、その名前と sha256 などの識別値を依頼と合わせて報告する。

結果のファイルは、`確認したコミット:` の行のすぐ次の行を `<マーク> <自分のエージェントの名前>: <結論>` にする。マークの意味は「PR にレビューやテストの結果を書く」の表に従う。メンションと文章の結論は、この行より前に置かない。

報告に `設計への指摘: <あり | なし>` の行を置く。`あり` は、指摘が設計そのものに関わり、コードの修正では解決しないときに書く。最上位の役の `設計` の種類の指摘も `あり` にする。コードで直せる指摘や、指摘がないときは `なし` にする。設計そのものへの指摘でも、人間を呼ばず、この行を `あり` にして `report` で返す。

`返事を待つ役:` の行がある依頼の結果は、`squad-review-wait report <タスク> <きっかけのコメント> <結果のファイル>` で投稿する。この場合は自分でリーダーをメンションせず、全員がそろったかも自分で判断しない。スクリプトが `/note` の結果を書き、そろった知らせを出す。`返事の回:` の行は `report` が結果に足すので、書かない。`report` は、全員がそろったあと、次の依頼を書いたりタスクの状態を変えたりすることがある。それでも、役は次の依頼を自分で書かず、状態も変えない。

スクリプトは、投稿後に 20 秒ほど待って読み直すことがある。コマンドの時間切れは 600 秒以上にする。途中で実行が止まっても、結果が投稿済みなら `report` を流し直さない。重複した報告になるため。

`返事を待つ役:` の行がない依頼や、スクリプトが「返事を待つ役の登録がありません」と投稿前に止まった場合は、通常の「引き継ぐとき」で返す。登録のない結果を無通知で返すとリーダーに届かないため。

## 更新を知らされたときに照合する

登録を「更新した」「反映した」と知らされたとき、または受け取った内容が知らせと合わないときは、人間へ問い返す前に、登録を自分で読んで照合する。どれも読むだけで、登録は変えない。

| 読むもの | コマンド | 写す値 |
| --- | --- | --- |
| 接続先 | `multica auth status` | サーバーの行だけ。利用者の名前とメールアドレスは写さない |
| ワークスペース | `multica workspace get --output json` | ID と名前 |
| スキルの一覧と ID | `multica skill list --output json` | 共通スキルと検証スキルの、名前と ID |
| 本文と追加のファイル | `multica skill get <スキルの ID> --with-content --output json` | `updated_at`、`content_hash`、追加のファイルの名前。本文は写さず、照らす節の見出しを書く |
| 役への割り当て | `multica agent skills list <エージェントの ID> --output json` | 割り当てられたスキルの名前 |
| 役の指示の更新の時刻 | `multica agent get <エージェントの ID> --output json` | `updated_at` |

検証スキルは、一覧のうち名前が `-verify` で終わり、自分のエージェントの名前と同じ先頭を持つものにする。選べなければ、当てはまるものをすべて書く。

照らす相手は 3 つある。今の登録（上の表で読んだ値）、この実行が受け取った内容（渡されたスキルの名前と本文）、知らせの内容（更新したと言われたもの。承認された本文があればその本文）である。

報告は、対象ごとに次の行で書く。役の指示・共通スキルの更新と、プロジェクトの検証スキルの更新を、別の行に分ける。セットアップの流し直しは前の 2 つだけを変え、検証スキルは変えないので、まとめて「更新された」と書くと取り違えるため。

```text
照合: <役の指示 | 共通スキル | 検証スキル | 割り当て> <変わった | 変わっていない | 読めなかった | 基準なし>
```

行のあとに、ID と更新の時刻（割り当ては、今のスキルの名前の一覧）を続ける。

- 基準は、知らせが応えている自分の前の報告の時刻にする。更新の時刻が基準より後なら「変わった」、前なら「変わっていない」と書く。割り当ては、前の報告に書いた一覧と比べる
- 基準にできる前の報告がないときは、「基準なし」と書き、今の値だけを添える。時刻だけから「変わった」と決めない
- 承認された本文が示されているときは、今の本文の該当する節がそれと同じかも書く
- 登録と割り当てがあるのに、この実行が本文を受け取っていないときは、その事実を書く。原因は調べない
- 読めなかったものは、「読めなかった」と書き、流したコマンド、終了コード、標準エラーの 1 行目を残す。読めなかったものを、変わったとも変わっていないとも書かない

自分で読める値を、人間に尋ねない。照合のあとも不足が残るときは、照合の行を添えて、今の決まりのとおり止まる。割り当てのない役が、CLI で本文を読んで代わりに従うことはしない。

## 記入が足りずに止まるとき

検証スキルの節やプロジェクトの説明が未記入で止まるときは、セットアップが起票した記入のタスクを示す。未記入なら推測で検証しない。未記入や未実行は成功にしない。

止まると報告する前に、その実行で受け取った内容で未記入かを確認する。前の報告、タスクのコメント、リーダーの依頼文にある「未記入」は根拠にしない。

| 確認する対象 | 未記入とみなすとき |
| --- | --- |
| 検証スキル | その実行で受け取った本文に、作業先の `` ## `OWNER/REPO` `` の節がない。または、今回の検証に使う欄に `[記入:` が残る |
| プロジェクトの説明 | その実行で受け取った説明の、今回の作業に要る箇所に `[記入:` が残る |

今回の検証に使わない欄の `[記入:` では止まらない。記入済みなら止まらずに進める。リーダーと要件・設計の役は検証スキルを受け取らないので、説明についてだけ確認する。スキルの割り当てや取り込みの不足は、記入とは分け、不足を書いて止まる。

### 記入のタスクを探す

「このプロジェクトの値」のプロジェクト ID を使い、`multica issue list --project <プロジェクト ID> --metadata squad_kit_task=<種類> --output json` で探す。人がタイトルを直しても探せるよう、タイトルの一致では探さない。

| 足りないもの | 探すマーク | 選び方 |
| --- | --- | --- |
| 検証スキルの、作業先の節がない | `squad_kit_task=repository-change` | `squad_kit_targets` に `added:<作業先>` を含むもの。なければ下の `project-instructions` |
| 検証スキルの欄、プロジェクトの説明 | `squad_kit_task=project-instructions` | プロジェクトに 1 つ |

前者は「OWNER/REPO の増減を説明と検証スキルに反映する」、後者は「プロジェクトの説明と検証スキルを記入する」として起票される。状態は絞らず、完了と取り下げも読む。複数あれば、当てはまるものをすべて報告に書く。一覧を読めなかったときは、見つからなかったときと分け、読めなかったことと理由を書く。

### 未記入の報告を返す

「人間を呼んで止まるとき」の形で、1 行目に未記入で止まったことと、先に片付ける記入のタスクを書く。報告には次を書く。

1. 足りない欄。検証スキルの節の見出しと欄の名前、またはプロジェクトの説明の箇所
2. 確認したこと。その実行で受け取った検証スキルか説明で読んだこと
3. 記入のタスク。識別子（タスクへのリンク）、タイトル、今の状態
4. 残っていること。記入のタスクを先に片付け、記入を終えたらこのタスクに返事をすれば再開すること

記入のタスクが `done` か `cancelled` なのに未記入のときは、状態をそのまま書く。記入が反映されていないので確認してほしいと添える。記入のタスクが見つからないときは、足りない欄と、見つからなかったこと、探したマークを書いて止まる。

レビューや E2E の依頼で `返事を待つ役:` の行がある実行は、人間を直接呼ばない。上の 1〜4 を結果に書き、その検証は未実行として、「レビューと E2E の返事を返す」の手順で返す。

結果には、`設計への指摘:` の行のすぐ次に、次の 1 行をそのまま書く。`確認したコミット:`、マークの行、`設計への指摘:` の行の順は変えない。マークは ✅ にしない。未記入や未実行は成功にしないためである。上の 1〜4 は、この行のあとの本文に書く。

```text
未実行: 検証スキルが未記入
```

この行があると、`squad-review-next decide` はマークと `設計への指摘:` の行によらず、結果をリーダーへ戻す。修正、最終レビュー、マージの依頼は書かれない。リーダーは「リーダーが報告を受けたとき」の手順で扱う。

### リーダーが報告を受けたとき

未記入の報告を人間へ返すときや、人間の返事で再開するときは、記入のタスクをその実行で探し直す。前の報告にある状態を写さず、今の状態を書く。

報告のあとに記入のタスクが `done` になっていれば、人間を呼ばず、止まった役にもう一度確認するよう頼む。報告より前から `done` だったときは、記入が反映されていないおそれがあるので、人間を呼んで止まる。同じ役が同じ理由で 2 回止まったときも、人間を呼んで止まる。

## 人間を呼んで止まるとき

「このプロジェクトの値」の呼ぶ人間のリンクを写し、「引き継ぐとき」の場面「人間を呼んで止まる」の型で書く。タスクを `in_review` にし、それ以上エージェントを呼ばずに実行を終える。

## 新しいタスクを作るとき

先に `multica issue search` で同じものがないか確認する。`--project` には「このプロジェクトの値」のプロジェクト ID、`--assignee-id` にはスクワッドの ID を渡す。担当なしにすると次の担当が起きないため、作る時点で渡す。

ラベルは仕事に合わせて `開発`、`運用`、`指示の改善` のいずれかを 1 つ付ける。`検証` は、人が動作確認のためのタスクに使う。ラベルの ID は `multica label list` の名前から引き、作成後に `multica issue label add` で付ける。

元のタスクから分けるなら sub-issue にする。順番があるものは `--stage` でステージを揃える。最初より後のステージは、担当を付けず `backlog` で作り、前のステージが終わったらリーダーが担当と状態を設定する。担当を付けてすぐ起動し、前のステージを待たずに進むことを防ぐため。例外として、要件を決める担当がなく最上位の役がある構成の複数のリポジトリの親は、最初のステージも担当なしの `backlog` で作る。`leader-flow.md` の「複数のリポジトリにまたがる要望」に従い、最上位の役の見直しのあとに回す。

## リーダーの手順

`references/leader-*.md` は、リーダーの手順である。リーダーだけが読み、ほかの役は読まない。

リーダーは、自分の指示の「場面と手順」の表から、その場面のファイルを選び、その実行の中で読む。手順の詳細はそれぞれのファイルにあり、このスキルには置かない。

## サブエージェントに分けるとき

依頼された範囲と権限の中で作業を分ける。親は、次の文をサブエージェントへの指示にそのまま写す。

```text
あなたはサブエージェントです。Multica のタスクにコメントもメンションもせず、タスクの状態も変えないでください。結果（変えたこと、コミットとブランチ、確認したことと結果）は、最後の返答として親のエージェントに返してください。
```

親は全員の結果を受け取り、依頼どおりに共有できる成果物へまとめてから、最後に 1 回で引き継ぐ。サブエージェントはタスクの割り当てで起きた独立の実行と区別し、コメント・メンション・状態変更をせず、結果を親へ返す。
